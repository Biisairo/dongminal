# 3.8 찾기 일치 눈금·미니맵 표식

## 목표

- 3.3 뒤 남은 것: 다 센 일치를 칠한 뒤 한 번 오는 화면 프레임(일치 1만 1천 개에서 약 20 ms). 스크롤바 눈금(`cm-scrollbar.js`) 약 4.6 ms, 미니맵 표식 수집(`edFindSources`·`collect`) 약 2 ms, CM 레이아웃 약 4.5 ms.
- 사용자 결정(2026-11-24): 같은 픽셀에 걸리는 눈금 표식을 합치고, 많으면 나눠 그린다. 미니맵으로 넘기는 표식도 줄 단위로 합친다. 보이는 결과는 같아야 한다.
- 사용자 결정(2026-11-24): `e2e/editor-find-perf.spec.ts` 는 평소 e2e 에서 건너뛰고 환경 변수(예: `OTTER_E2E_PERF=1`)를 줄 때만 돈다. 같은 방식의 기존 관례가 있으면 따른다.

## 완료 조건

- 시험 먼저(RED): 표식 합치기 단위 시험, 일치 1만 개에서 그 프레임 16 ms 이하 측정(이전/새). 관련 node·e2e 한두 개, 게이트. 전체 시험 금지.

## 진행 기록

### 2026-11-24 agent-pf-3-8 — 눈금 칠하기 합치기·미니맵 표식 줄 단위·성능 시험 분리 (review)

**커밋**: `pf/3.8` 의 `d190e0c4`.

**바꾼 것**

- `web/js/ui/cm-scrollbar.js`: `edRulerRects(items)` 를 새로 둔다. 그리는 순서로 잇단 항목이 lane·색이 같고 세로로 겹치거나 맞닿으면 사각형 하나로 합친다. 사이에 다른 색이 끼면 건너서 합치지 않는다. `paint` 는 합친 사각형만 칠하고, 색(`getPropertyValue`)은 변수마다 한 번만 읽는다. 눈금 항목 `items`(e2e 어댑터 `edCmRulerItems` 가 읽는다)는 바꾸지 않았다.
- `web/js/ui/cm-find.js`: 미니맵으로 넘기는 찾기 표식을 `edFindMinimapMarks` 로 줄마다 하나만 만든다. 같은 줄에서는 현재 일치가 이기고, 현재 일치의 줄은 맨 뒤에 둔다. 종전에는 일치마다 표식 하나를 만들고 `sort` 와 `lineAt` 을 불렀다. 눈금 항목은 종전처럼 일치마다 하나다.
- `e2e/editor-find-perf.spec.ts`: `OTTER_E2E_PERF=1` 일 때만 돈다(`test.skip`). **기존 관례는 없었다.** e2e 의 `OTTER_E2E_*` 변수(`KEEP_HOME`·`KEEP_PEERS`·`PREBUILT_BIN`·`RUN`·`STRICT_FLAKY`) 중 시험을 건너뛰는 용도는 없어서 이 이름을 새로 쓴다. 화면 프레임에도 16 ms 문턱을 건다. 유휴 콜백(`FireIdleCallback`) 작업은 따로 나눠 출력만 한다.

**동작 변경**

| | 이전 | 새 | 이유 |
|---|---|---|---|
| 눈금 칠하기 | 항목마다 `fillRect` 를 한 번 하고 색을 한 번 읽는다 | 합친 사각형마다 한 번 칠하고, 색은 변수마다 한 번 읽는다 | 일치 1만 개가 track 몇 px 에 몰려 같은 자리를 수천 번 칠했다 |
| 미니맵 찾기 표식 | 일치마다 하나(같은 줄은 현재 일치가 마지막에 칠해져 이겼다) | 줄마다 하나(현재 일치가 이기고 맨 뒤) | 미니맵은 줄마다 한 색이라 보이는 결과가 같다 |
| `editor-find-perf` | 늘 돈다. 찾기 계산 작업만 판정한다 | `OTTER_E2E_PERF=1` 일 때만 돈다. 화면 프레임도 판정한다 | 사용자 결정(2026-11-24) |

보이는 결과에 대해:
- 색이 불투명하면 합친 사각형의 픽셀은 종전과 같다. 다만 분수 좌표에서 맞닿은 두 사각형의 경계 한 줄은 종전에 안티앨리어싱이 두 번 겹쳐 아주 조금 옅었고, 이제는 꽉 찬다.
- 색이 반투명이면 겹친 부분이 종전에는 더 진했다. 찾기 색은 `--accent`·`--text-bright` 다.

**"많으면 나눠 그린다"를 하지 않은 이유**: 합친 뒤 사각형 수는 track 의 픽셀 줄 수와 색 바뀜 수를 넘지 않는다. 일치 1만 1천 개도 사각형 셋이다(단위 시험). 그래서 나눠 그릴 만큼 많아지는 경우가 없다. 사용자 결정의 문구와 다르므로 확인을 바란다.

**측정** — `OTTER_E2E_PERF=1` 로 `editor-find-perf` 를 돌렸다(2만 줄 파일, `value_1`, 일치 11,111개). 다른 Rust 빌드 때문에 load average 가 6~23 이었다. 그래서 base(perf-m1, 3.3+3.7)와 new 를 번갈아 쟀다.

| | 화면 프레임 최대 | 찾기 계산 작업 최대 |
|---|---|---|
| base | 19.9 · 19.2 · 19.0 · 18.7 · 18.5 ms | 9.9~10.8 ms |
| new | 14.3 · 14.1 · 14.6 · 14.9 · 14.4 · 14.4 · 14.2 · 14.2 · 15.0 · 14.4 · 14.2 ms (11회) | 9.5~10.3 ms |

- RED: base 에서 화면 프레임 19.2·19.9 ms 로 실패했다. 단위 시험은 `edRulerRects is not defined` 로 실패했다.
- 3.3 때 보고한 rAF 밖 50 ms 이상치의 정체를 확인했다. 트레이스로 보면 `FireIdleCallback` → `work`(vendor `chunk-W3VBIL6C.js`), 곧 **CodeMirror 언어 파서의 유휴 시간 배경 파싱**이다. 큰 파일을 연 뒤 계속 돌아서 찾기와 무관하게 측정 창에 걸린다(약 10회에 1회, 45~52 ms). 시험은 이것을 `idle=` 로 따로 출력한다.

**시험 결과**

- `node --test` cm-ruler-merge(새) · cm-scrollbar · cm-find · cm-find-scan · cm-setup · cm-minimap: 62/62 통과
- e2e `editor-find-panel` · `editor-minimap` · `editor-link-marks`: 45 통과, `editor-find-perf` 는 환경 변수 없이 skipped
- e2e `editor-find-perf`(`OTTER_E2E_PERF=1`): new 에서 8/8 통과(그 앞의 3회 중 1회는 위 유휴 파싱이 '찾기 계산'으로 분류돼 실패했고, 이를 나눈 뒤 다시 쟀다)
- `npx tsc -p e2e --noEmit` 통과. `check-timers` · `check-e2e-waits` · `check-load-order` · `check-i18n-literal` · `check-code-refs` 통과. `check-file-size` 는 `runs-panel.js` 506줄(기존 위반) 하나만 남았다.

**남은 위험**

- 화면 프레임의 여유가 1~2 ms 다(13.6~15.0 ms). 남은 몫은 CodeMirror 레이아웃과 눈금 `read`(일치마다 위치 계산)다. 부하가 큰 기계에서는 16 ms 를 넘을 수 있다. 다만 이 시험은 이제 `OTTER_E2E_PERF=1` 일 때만 돈다.
- 언어 파서의 유휴 콜백 작업(최대 약 50 ms)은 찾기와 무관한 별도 비용이다. 입력이 그 사이에 오면 지연된다. 3.7 이 다룬 파서 설정 쪽 일이다.
- e2e 어댑터의 `minimapOf(cls, line)` 는 일치마다 미니맵 표식을 찾는다. 한 줄에 현재 일치와 다른 일치가 함께 있으면, 다른 일치의 표식은 이제 없다(현재 일치가 이긴다). 지금 시험 본문은 줄마다 일치가 하나라 영향이 없다.

**코드와 어긋난 문서**: 없음. 이슈 목표의 "눈금 약 4.6 ms"는 3.3 의 표본 값 그대로다.

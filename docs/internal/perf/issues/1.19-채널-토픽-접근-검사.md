# 1.19 채널 토픽 접근 검사 확인 (보안)

## 목표

자동 보안 검토 지적(MEDIUM): `httpapi/src/full_topics.rs` 는 토픽 본문을 얻으려고 `127.0.0.1` 에서 온 것처럼 꾸민 내부 요청(`internal_get`, `INTERNAL_ADDR`)으로 GET 처리기(`api_claude_accounts_list`·`api_focus_get`·`api_telegram_get` 등)를 부른다. 채널 구독자가 원격(접근 허용 목록·요청 게이트를 거친 비루프백)일 때, 원래 GET 경로가 루프백 여부나 출처로 거르는 검사를 이 경로가 건너뛰는지 확인한다.

- 사실 조사: 채널 업그레이드가 GET 경로와 같은 접근 정책(ACCESS_ALLOWLIST·REQUEST_GATE 등)을 거치는가, 각 토픽의 원래 GET 처리기·미들웨어가 요청의 remote_addr/host 로 판단하는 것이 있는가(특히 telegram·claude.accounts 같은 민감 값).
- 실제로 우회가 되면: 재현 시험(RED) 후 수정. 권장 방향 — 채널에 업그레이드 요청의 신원(remote_addr·host)을 보관하고, `sub` 때 그 토픽의 GET 과 같은 정책을 적용, 실패하면 거절. 내부 요청은 구독자의 신원으로 만든다.
- 우회가 안 되면 근거(파일:줄)를 적고 닫는다.

## 완료 조건

- 조사 결과, (필요하면) 재현 시험과 수정, 바꾼 crate 의 lib 시험·fmt·clippy. 전체 시험 금지.

## 진행 기록

### 2026-11-24 agent-pf-1-19 — 조사 결과: 우회 없음 (review)

결론: 채널 full 토픽으로 원격 구독자가 GET 으로 못 받는 값을 받는 길은 없다. 코드를 바꾸지 않았고 커밋도 없다.

근거 (`rust/crates/webserver/httpapi/src/` 기준, pf/1.19 = c50d31e6):

1. 채널 업그레이드는 GET 과 같은 게이트를 지난다.
   - `/channel` 과 `/api/*` 는 같은 `Server::gated` 를 지난다 — `serve.rs:183-191` 에서 `access_gate` 뒤에 `request_gate` 를 부르고, mux(`serve.rs:69-81`)는 그 뒤에 고른다.
   - `access_gate`(`access_api.rs:37-64`)는 경로를 보지 않는다. 출발지 IP 하나로 판정한다(FR-ACL-11).
   - `request_gate`(`reqgate.rs:135-184`)의 예외는 `gate_exempt`(`reqgate.rs:117-125`)뿐이고, `/channel` 은 `/api/*` 처럼 예외가 아니다(`:124`). Host·Origin·authority 판정이 같다. 업그레이드와 토픽 GET 은 둘 다 GET 이라 Sec-Fetch-Site·Content-Type 판정(`:161-163`)을 둘 다 건너뛴다.
   - 기존 시험이 이것을 고정한다: `tests/access.rs:146-160`(`covers_every_surface`, `/api/state`·`/api/settings`·`/channel` 모두 403), `tests/channel.rs:95-98`(`/channel` 은 gate 예외가 아니다).
2. full 토픽 8개의 GET 처리기는 요청의 신원(remote_addr·host·Origin)을 보지 않는다.
   - `api_settings_get`(`settings.rs:183`), `api_update_get`(`update_api.rs:32`), `api_claude_accounts_list`(`claude_accounts.rs:519`), `api_focus_get`(`openurl.rs:121`), `api_telegram_get`(`telegram_api.rs:177`)은 인자를 `_r` 로 받아 쓰지 않는다.
   - `api_state_get`(`tools_api.rs:199`)은 `r.rid()` 만 쓴다(`toolio.rs:26-32`). `api_edges_get`(`edge_api.rs:229` → `edge_do` `:168-207`)은 `If-Match` 머리만, `api_chat_get`(`chat_api.rs:69` → `chat_do` `:103-142`)은 상태 조회일 때 요청에서 아무것도 읽지 않는다.
   - 라우트 표(`routes.rs`)에는 경로별 미들웨어가 없다. 신원으로 판정하는 처리기는 `api_server_bind`·bind GET 의 `local`(`rebind.rs:584·594`), attention claim(`attention.rs:425-451`), `/api/open-url/where`(`openurl.rs:83-102`), whoami·usage 뿐이고, 모두 full 토픽이 아니다.
3. 토픽 본문은 구독자마다 다르게 만들 수도 없다. `refresh_full_topic` 이 한 번 만든 본문을 `publish_full` 로 모든 구독자에게 낸다(`full_topics.rs:139-147`). 원래 GET 의 본문도 호출자와 상관없이 같으므로 `internal_get`(`full_topics.rs:71-87`)의 `127.0.0.1` 신원은 결과를 바꾸지 않는다.

남는 차이 (우회 아님, 규격대로):
- 허용 목록을 바꾼 뒤에도 이미 열린 채널은 토픽을 계속 받는다. 같은 원격이 새 GET 을 보내면 403 이다. 이것은 FR-ACL-12("이미 수립된 WebSocket 연결은 목록 변경으로 끊지 않는다. 게이트는 연결 수립 시점에만 판정한다")가 정한 동작이다. 바인드를 루프백으로 바꿀 때는 `rebind_conns.rs:73` 의 `revoke_remote` 가 원격 연결을 끊는다.
- 위험(LOW): 앞으로 누가 full 토픽 GET 처리기에 신원 검사를 더하면, `internal_get` 의 `127.0.0.1` 신원 때문에 채널 경로에서는 그 검사가 늘 통과한다. 지금은 해당 처리기가 없다. 그런 검사를 더할 때는 이 이슈의 권장 방향(채널에 업그레이드 신원 보관 → `sub` 때 같은 정책)을 함께 해야 한다.

시험: 코드를 바꾸지 않아 돌리지 않았다. RED 대상이 없다(재현할 우회가 없다).

코드와 어긋난 문서 (고치지 않음):
- `ACCESS_ALLOWLIST_SRS.md` FR-ACL-11·12, `REQUEST_GATE_SRS.md` FR-RQG-11~13 본문은 아직 `/ws` 를 적는다. 지금 같은 자리는 `/channel` 이다(머리말 개정 주석만 있다).

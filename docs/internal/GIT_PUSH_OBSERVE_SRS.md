# SRS: git 관측을 서버가 밀어 준다 — IEEE 29148

> **문서 상태**: 승인·구현완료

> 상태: **초안**. `EVENT_TIMER_HUB_SRS` O-1 의 후속.

---

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

브라우저가 저장소 하나를 보고 있으면 **60초에 180번** 묻는다 — signature 120회
(500ms), status 60회(1s). 변화가 한 번도 없어도 그렇다.

이 물음의 답은 **누가 묻든 같다.** 서버는 이미 그것을 알고 있고, 알아내는 비용도
이미 치르고 있다. 브라우저가 그것을 500ms마다 다시 물을 이유가 없다.

**서버가 확인하고, 바뀌었을 때만 알린다.**

### 1.2 왜 `fsnotify` 가 아닌가

`EVENT_TIMER_HUB_SRS` 초안은 이 일을 "서버에 파일 감시를 도입한다" 고 적었다.
**틀렸다.**

| | `ReadSignature` | 파일 감시 |
|---|---|---|
| 비용 | read 1회 + stat 2회 = **0.02ms** (FR-GIT-19 §2.6) | 워처 등록·유지, 재귀 감시 |
| 플랫폼 | 없음 — `os.Stat` 뿐 | inotify 한도 · FSEvents 지연 · Windows 별도 API |
| 정확도 | **실측으로 다듬어졌다** (아래) | 이벤트 폭주·누락을 새로 다뤄야 한다 |

마지막 줄이 결정적이다. 이 저장소의 signature 는 두 번 넓혀졌다:

- `RefsMtimeNs` — ref 파일이 생기거나 사라지면 부모 디렉터리 mtime 이 바뀐다.
  브랜치·태그·원격 추적 ref 의 추가·삭제가 여기 잡힌다 (FR-GVR-21).
- `RefsShape` — **디렉터리 mtime 은 파일시스템이 갱신을 미룰 수 있다.** Windows
  러너에서 `git branch` 뒤 45초 동안 그대로였다 (FR-CEM-32 실측). 이름을 접은
  값은 시각과 무관하다.

파일 감시로 바꾸면 이 지식이 버려진다. **감시는 signature 를 대체하지 못하고,
signature 를 감시하는 주체만 바뀌면 된다.**

### 1.3 범위 (Scope)

| 묶음 | 내용 | 리스크 |
|---|---|---|
| **W** | 서버의 signature 감시와 `git_changed` 방송 | **MEDIUM** |
| **S** | 감시 대상 집합 — 누가 보고 있는가 | **MEDIUM** |
| **C** | 브라우저: signature 폴링 제거, status 는 안전망으로 | **MEDIUM** |

**범위 밖**: `git status` 자체를 미는 것. 방송은 "바뀌었다" 만 나르고 내용은
브라우저가 받아 간다 — status 응답은 크고(파일 목록 전체) 보는 이가 없을 수도
있다. FR-BGV-1 이 백그라운드 목록에 쓴 것과 같은 판단이다.

### 1.4 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **signature** | `.git` 의 변화를 싸게 감지하는 값. read 1회 + stat 2회 |
| **감시 대상** | 서버가 signature 를 확인하는 저장소 집합 |
| **관심 표명** | 브라우저가 "이 저장소를 보고 있다" 를 서버에 알리는 일 |
| **안전망 폴링** | 푸시가 끊겼을 때를 위한 낮은 빈도의 확인 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 서버는 이미 이 패턴을 갖고 있다

`hub/foreground.go` 가 그것이다 — 티커로 조회하고(`StartForegroundPoll`),
**값이 바뀐 것에 대해서만** notifier 가 뜨며(FR-TAN-9), 그 notifier 가
`hub.Broadcast` 로 간다. `attn_tracker.go` 도 1초 티커를 갖는다.

그 파일의 주석이 이 SRS 의 논거를 미리 적어 두었다:

> C-3 이 막는 것은 **브라우저의 새 요청**이며, 그것은 늘지 않는다.

서버가 도는 것은 브라우저의 요청이 아니다.

### 2.2 signature 는 git 을 실행하지 않는다

`ReadSignature(gitDir, commonDir)` — `os.ReadFile(HEAD)` 1회, `os.Stat` 2회,
그리고 `refs` 아래 디렉터리 walk(상한 256). gitdir 해석(`rev-parse`)은
`Store` 가 TTL 로 캐시하므로 감지 경로에 git 이 돌지 않는다.

### 2.3 `Store` 는 폴링을 갖지 않는 것이 설계다

> 폴링·디바운스는 여기 없다. 무엇을 언제 물을지는 **클라이언트가 정하고**,
> Store 는 물음이 겹칠 때 git 을 아끼는 일만 한다.

그리고 `Observed` 의 주석:

> 활성이 아닌 리포의 배지가 이것을 쓴다 — 그래서 **폴링 대상이 활성 1개로
> 유지된다** (FR-GIT-24).

**이 제약을 이 SRS 가 깨면 안 된다.** 서버가 도는 대상도 "지금 누가 보고 있는
것" 이어야 하며, `Store` 의 LRU 64개 전부가 아니다.

### 2.4 브라우저의 두 계층은 이미 하나의 관측자에 모여 있다

`GitObserver` 가 앱당 하나이고 single-flight 를 쥔다 (FR-SVS-31). 칸이 넷이어도
요청은 한 벌이다. 그러므로 **줄일 대상은 "칸 수" 가 아니라 "주기" 다.**

### 2.5 60초에 180번

| 계층 | 주기 | 60초 |
|---|---|---|
| signature | 500ms | 120 |
| status | 1000ms | 60 |
| **합** | | **180** |

변화가 없어도 그렇다. 원격(Tailscale)·모바일에서 이 왕복은 배터리와 지연으로
직접 나타난다.

### 2.6 signature 는 작업 트리를 보지 못한다 — **초안의 오류**

초안은 "서버가 signature 를 감시한다" 로 설계했다. 그 구현은 e2e 에서 곧바로
막혔다: 작업 트리에 파일을 만들었는데 방송이 나가지 않았다.

signature 가 보는 것은 `HEAD` · `index` · `refs` 다. **파일을 만들거나 고치는
것은 그 어느 것도 건드리지 않는다.** 종전에 그 변화를 잡던 것은 signature
폴링(500ms)이 아니라 **status 폴링(1s)** 이었다 — 그러므로 서버가 관측하는 것도
status 여야 한다.

비용은 옮겨질 뿐 늘지 않는다. 종전에도 브라우저가 1초마다 status 를 시켰고 그것이
서버에서 git 을 돌렸다. 이제 서버가 스스로 돌리고 결과가 바뀌었을 때만 알린다 —
**git 실행 횟수는 같고 네트워크 왕복이 사라진다.**

`fsnotify` 를 쓰지 않는 판단은 그대로다. 작업 트리 쪽은 `git status` 가 이미
정확하고, `.git` 쪽은 signature 가 실측으로 다듬어져 있다 (§1.2).

### 2.7 표명과 첫 회차 사이에 틈이 있다

`Note` 가 기준선 없이 등록하면 첫 `Tick` 이 그때의 관측을 기준선으로 삼는다.
표명과 그 회차 사이(최대 한 주기)에 생긴 변화는 기준선에 섞여 **"바뀐 적 없는"
것이 된다.** 창을 열자마자 파일을 만드는 e2e 가 그 자리를 밟았다 — 화면이
안전망(30초)까지 낡은 채였다.

브라우저는 표명 시점에 그 관측을 **응답으로 받았다.** 그러므로 그 값이 곧
"브라우저가 아는 상태" 이고 기준선으로 정확하다. `Note` 가 관측을 함께 받는
이유가 이것이다.

재표명은 기준선을 덮지 않는다. 안전망 폴링의 응답으로 갈아 끼우면 마지막 방송과
그 응답 사이의 변화를 잃는다.

### 2.8 알림의 식별자는 signature 가 아니다

payload 에 signature 를 실었더니 브라우저의 중복 거르기가 작업 트리 변화를 통째로
삼켰다 — 그때 signature 는 그대로이므로 "이미 본 값" 으로 판정된다.

**거르는 근거는 방송을 내보내게 만든 그 판단과 같아야 한다.** 그래서 `mark`
(관측 전체를 접은 값)를 싣는다.

이 셋은 모두 검사가 잡았다. §4 의 G-8·G-10·B-3 이 그 자리를 지킨다.

### 2.9 폴링이 가려주던 결함 하나

`refresh()` 는 뷰들의 `reload()` 를 배열로 모은 뒤 `collect()` 와 함께
`Promise.allSettled` 로 기다린다. **`_reloadViews` 는 async 가 아니므로** 그중
하나가 동기 throw 하면 배열을 만드는 자리에서 터지고, `collect()` 는 아예 불리지
않는다 — 사용자가 새로고침을 눌렀는데 status 를 다시 받지 않는다.

D-POLL-2 의 `finally` 가 지킨 것은 **잠금**(`_refreshing`)이었고, 관측은 지키지
않았다. 종전에는 1초 폴링이 곧 그 자리를 메워 드러나지 않았다. 폴링이 푸시로
바뀌자 보였다 — `git-polling P8` 이 그 자리다.

**폴링을 줄이면 그것이 가려주던 것이 드러난다.** 이 SRS 의 부수 효과 중 가장
값어치 있는 것이다.

### 2.10 설정 마이그레이션은 불가능하다

주기의 기본값이 바뀌므로, 저장된 옛 기본값(500/1s)을 새 기본으로 옮기려 했다.
**저장된 값이 기본을 담은 것인지 사용자가 고른 것인지 구분할 수단이 없다** —
설정은 하나의 블롭으로 저장되고, 테마만 바꿔도 현재 주기가 함께 실린다.

그 마이그레이션은 주기를 명시로 세우는 검사까지 삼켰다(실측: `B1`·`B2` 가
1초를 저장했는데 30초로 돌았다). 걷어냈다 — **저장된 값은 그대로 존중한다.**
저장된 설정이 없으면 새 기본을 받고, 있으면 그것이 그 사람의 선택이다.

### 2.11 제약 (Constraints)

| # | 제약 | 출처 |
|---|---|---|
| C-1 | 외부 관측 동작 불변 — 사용자가 보는 갱신 속도는 **같거나 빨라야** 한다 | 사용자 지시 |
| C-2 | Go 테스트와 e2e 전량 통과, 개수 동일 | 저장소 관례 |
| C-3 | `Store` 에 폴링을 넣지 않는다 (§2.3). 감시는 `hub` 계층의 일이다 | §2.3 |
| C-4 | 감시 대상은 "지금 보고 있는 것" 이다. LRU 전체가 아니다 (FR-GIT-24) | §2.3 |
| C-5 | 푸시가 끊겨도 화면은 낡지 않는다 — 안전망이 있어야 한다 | FR-RLC-25 |
| C-6 | 브라우저의 기존 계약을 잃지 않는다: FR-RMS-22·28·29 · FR-GIT-21·22·23 · FR-SVS-31·45 | `EVENT_TIMER_HUB_SRS` §4.1 |

## 3. 요구사항 (Requirements)

### 3.1 묶음 W — 서버의 감시

**FR-GPO-1** `internal/webserver/hub/gitwatch.go` 에 감시자를 둔다.
`hub/foreground.go` 와 같은 형태다 — 티커 하나, 변화 시에만 방송.

**FR-GPO-2** 주기는 `GitWatchInterval` = **1000ms**. 브라우저의 종전 **status**
주기와 같다 — 사용자가 보는 갱신 속도가 느려지면 안 된다 (C-1). signature
주기(500ms)가 아닌 이유는 회차가 status 를 관측하기 때문이다 (§2.6).

**FR-GPO-3** 회차마다 감시 대상 각각의 **관측(status + signature)** 을 읽고,
직전과 다를 때만 방송한다. 같으면 아무것도 하지 않는다 (FR-TAN-9 와 같은 계약).
비교 대상은 `obsMark` — signature 값, HEAD·브랜치·ahead/behind, 그리고 세 그룹의
파일 목록(경로·XY·서브모듈 상태)을 접은 값이다.

**FR-GPO-4** 방송 payload:

```json
{"action":"git_changed","args":{"repo":"<abs>","mark":"<obsMark>"}}
```

`mark` 를 싣는 이유는 브라우저가 **이미 받은 알림인지** 판정할 수 있게 하기
위해서다 — 재연결 직후의 중복 수집을 막는다. signature 가 아닌 이유는 §2.9.

**FR-GPO-5** 관측을 읽다 오류가 나면 **그 저장소를 감시에서 뺀다.** 저장소가
사라졌거나 gitdir 이 깨진 것이며, 그 판정과 화면 처리는 브라우저의
`GIT_REPO_MISSING` 경로가 이미 갖고 있다 (FR-RMS-6). 감시자가 그것을 흉내내지
않는다.

**FR-GPO-6** 감시는 **브라우저 요청을 만들지 않는다.** `Store.Status` 를 직접
부르며, 그것은 TTL 캐시와 single-flight 를 지난다 (FR-GIT-21·63) — 감시 회차가
브라우저의 요청과 겹치면 git 은 한 번만 돈다.

### 3.2 묶음 S — 감시 대상

**FR-GPO-10** 감시 대상은 **관심 표명으로 정해진다.** 브라우저가
`/api/git/status` 를 부르면 그 저장소가 대상에 들어간다. 별도 API 를 만들지
않는다 — status 요청이 곧 "지금 이것을 본다" 이기 때문이다.

표명은 **그때의 관측을 함께 받는다** (§2.7). 브라우저가 응답으로 받은 그 값이
기준선이어야 표명과 첫 회차 사이의 변화를 놓치지 않는다. 재표명은 수명만
갱신하고 기준선을 덮지 않는다.

**FR-GPO-11** 표명은 **만료된다.** `GitWatchTTL` = **90초** 동안 status 요청이
없으면 대상에서 빠진다. 브라우저의 안전망 폴링(FR-GPO-20)이 그보다 잦으므로,
보고 있는 동안에는 만료되지 않는다.

> **개정 — `GIT_WATCH_LEASE_SRS` FR-GWL-1~5 가 이 조항을 대체한다.**
>
> 마지막 문장의 전제가 깨졌다. `POLL_INTERVAL_SETTINGS_SRS` FR-PIS-9 가 안전망
> 주기에 `2분`과 `끔`을 추가하면서 "폴링이 TTL 보다 잦다" 가 더는 성립하지 않았고,
> 그 결과 **안전망을 끄면 본줄인 이 방송까지 죽었다** (11-git-polling `GP-1`, P0).
>
> 지금 임대를 쥐는 것은 status 요청이 아니라 **SSE 구독**이다. 임차인이 있는
> 저장소는 유휴로 만료되지 않고, 임차인이 없는 표명에만 이 90초가 적용된다.

**FR-GPO-12** 대상 수에 상한을 둔다 — `GitWatchCap` = **16**. 넘으면 가장 오래된
표명부터 뺀다. 브라우저 여럿이 각자 다른 저장소를 봐도 상한 안에 든다.

> **개정 — `GIT_WATCH_LEASE_SRS` FR-GWL-6.** 퇴출 순서에 임차인이 앞선다:
> 임차인 없는 것이 먼저 나간다. 퇴출은 이제 로그에 남는다(종전에는 조용했다).

**FR-GPO-13** 감시 대상이 없으면 티커는 **돌되 아무것도 하지 않는다.** 티커를
멈췄다 켜는 대신 빈 순회를 하는 이유는, 시작·정지의 경합을 다루는 비용이 500ms
마다의 빈 순회보다 크기 때문이다.

### 3.3 묶음 C — 브라우저

**FR-GPO-20** signature 폴링(500ms)을 **없앤다.** status 폴링은 남기되 주기를
`GIT_STATUS_POLL_MS` 1초 → **30초**로 늘린다. 이것은 두 가지를 겸한다:

> **후속 (2026-09-08)**: 이 조항은 주기를 `0`(꺼짐)으로 두었을 뿐 계층은 코드에
> 남겨 두었다 — "설정으로 되살릴 수 있다, 푸시를 믿지 못하는 환경의 손잡이로
> 남긴다" 였다. 그 손잡이는 **한 번도 켜지지 않았고**, 켜질 수 있다는 것 자체가
> 위험이었다(여기서 없앤 60초당 120회 요청이 되살아난다). 계층은
> [POLL_INTERVAL_SETTINGS_SRS](./POLL_INTERVAL_SETTINGS_SRS.md) FR-PIS-1 에서
> 실제로 걷어냈다. 서버의 `StartGitWatch` 와 `/api/git/signature` 종단은 남는다.

- 푸시가 끊겼을 때의 안전망 (C-5)
- 관심 표명의 갱신 (FR-GPO-11 의 90초보다 세 배 잦다)

**FR-GPO-21** `git_changed` 를 받으면 **즉시 수집한다.** 자기가 보는 저장소가
아니면 무시한다.

**FR-GPO-22** payload 의 `mark` 가 마지막으로 본 값과 같으면 수집하지 않는다
(FR-GPO-4). 재연결 직후 서버가 현재 상태를 다시 알릴 수 있다. **signature 로
거르지 않는다** — §2.8.

**FR-GPO-23** `sse:open` 에 **한 번 수집한다.** 구독이 끊겨 있던 동안의 변화는
방송으로 오지 않았다 — `state-registry` 의 재검증과 같은 규약이다.

**FR-GPO-24** `_cadence` 의 백오프(FR-RMS-22)와 소실 고정 주기(FR-RMS-6)는
**그대로 산다.** 안전망 폴링도 실패하면 늦춰져야 한다.

### 5.1 폴링을 재던 검사 여덟

기존 검사 여덟이 폴링을 직접 재고 있었다. **재는 계약은 그대로 두고 표현만**
옮겼다 — "폴링이 도는가" 가 아니라 그 폴링이 지키던 것이 무엇이었는지로.

| 검사 | 재던 것 | 새 표현 |
|---|---|---|
| `P1` | status 폴링이 돈다 | **변화가 화면에 따라온다** — 애초의 계약(V6)이다 |
| `P7` | signature 폴링이 안 죽는다 | **겹친 수집이 단일 비행 잠금을 남기지 않는다** — 겹침의 자리가 폴링 둘에서 푸시+안전망으로 바뀌었을 뿐 계약은 같다 |
| `P8` | 두 번째 누름이 요청을 낸다 | 같음. 다만 **제품 결함**이 드러나 함께 고쳤다 (§2.9) |
| `P9` | 다음 관측이 다시 그린다 | 같음. 안전망을 검사용으로 줄여 "다음 관측"을 만든다 |
| `B1`·`B2` | 실패 백오프 | 같음. 기준 주기를 **명시로 세운다** — 재는 것은 비율이지 기준값이 아니다 |
| `G8` | 폴링 주기·요청 수 불변 | **관측은 살아 있고 뷰 조회는 늘지 않는다** — FR-GVR-7 의 핵심은 뒤쪽이다 |
| `X6` | 보이는 표면만 폴링 | 같음(NFR-RTU-1). 안전망에도 같은 경계가 적용된다 |

`P7` 하나만 재던 대상(signature 계층)이 사라졌고, 나머지 일곱은 계약이 그대로
살아 있다. **검사 개수는 변하지 않는다** (C-2).

**중단 지점**: 단계 3 에서 FR-RMS-22·28 이나 FR-GIT-21·22 가 흔들리면 멈춘다.
`EVENT_TIMER_HUB_SRS` 가 그 계약을 검사로 고정해 두었으므로 (§4.1) 흔들리면 곧
드러난다.

# SRS: 칸별 시선 — 슬롯이 창을 각자의 눈으로 본다 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 두 줄이다.

> **git 이랑 editor 를 두 칸에 놓았는데 같은 창을 못 본다.**
>
> **폴링은 한 번만 하고 화면만 여러 칸에 보이면 되지 않나. 이 기회에 window·git·
> editor 전부 모델/뷰로 나눠서 칸마다 독립적으로 볼 수 있게 하자.**

[`WINDOW_SLOTS_SRS`](./WINDOW_SLOTS_SRS.md) 는 콘텐츠 영역을 칸으로 나눴고, 그
§1.2 는 **"슬롯은 창을 담는 그릇이지 창의 내용을 바꾸지 않는다"** 를 범위 밖에 두었다.
그 선이 지금 두 곳에서 걸린다.

1. 두 칸이 같은 창을 보면 **항상 같은 탭**을 본다 — `activeTab` 이 pane 에 붙은
   워크스페이스 상태이기 때문이다 (`app-layout.js:419`). 그래서 "왼쪽 Changes,
   오른쪽 History" 가 성립하지 않는다.
2. 창의 내용을 그리는 실체 중 **칸을 모르는 것**이 있다. `GitPanel` 은 앱에 하나이고
   (`app.js:45`), `FileTree` 는 창에 하나다 (`app-editor.js:247`). DOM 노드는 부모가
   하나뿐이므로 두 칸에 같은 것을 그리면 뒤에 그린 칸이 앞 칸에서 **떼어 간다**.

본 SRS 는 그 선을 옮긴다. 슬롯은 그릇에서 **시선**이 된다 — 창은 하나이고 관측도
하나인데, **보는 자리마다 자기 시선을 갖는다.**

그 규약은 새로 만드는 것이 아니다. **터미널 창이 이미 그 모양이다** (§2.1).

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **T** 칸별 탭 | 활성 탭이 칸의 것이 된다. 워크스페이스와의 관계, `dmctl` 이 보는 값 |
| **X** 탐색기 | `FileTree` 의 관측(캐시·git 색)과 시선(펼침·선택·스크롤) 분리 |
| **O** Git 관측 | 폴링·`status`·소실을 `GitObserver` 로 뺀다. 앱에 하나 |
| **V** Git 시선 | `GitPanel` 이 칸별 인스턴스가 된다. 조작 상태가 칸의 것이 된다 |
| **E** 편집기 문서 | 같은 파일을 두 칸에서 열 때 문서는 하나다. 저장 충돌 소멸 |
| **F** 결함 | 이 작업에 반드시 걸리는 기존 결함 |
| **I** 인터페이스 | App 표면·저장소 키·DOM 의 이름 계약 |

**미포함:** §6 비목표. 특히 **창 타입의 불변식은 한 줄도 바뀌지 않는다** — Git 창은
여전히 탭을 더할 수 없고, Editor 창에는 여전히 편집기 탭만 산다. 서버 스키마도
바뀌지 않는다.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **관측 (observation)** | 서버·파일시스템에서 온 사실. 누가 보든 같다. `git status`, 파일 목록, PTY 출력 |
| **시선 (view state)** | 그 사실을 **어떻게 보고 있는지**. 칸마다 다를 수 있다. 활성 탭·선택·펼침·스크롤·커서 |
| **문서 (document)** | 편집 중인 파일의 내용과 dirty. 관측이 아니다 (사용자가 만든다) — 그러나 같은 파일이면 하나여야 한다 |
| **칸별 탭 오버라이드** | 칸이 pane 마다 "내가 보는 탭"을 적어 둔 것. 없으면 `pn.activeTab` 을 따른다 |
| **포커스 칸** | WINDOW_SLOTS_SRS 의 정의 그대로. 키 입력과 사이드바 클릭이 향하는 칸 |

## 2. 현재 상태 (조사로 확정한 사실)

**설계 판단의 근거이므로 추측이 아닌 파일:줄로만 적는다.**

### 2.1 터미널 창은 이미 모델/뷰가 갈려 있다 — 이것이 규약의 원본이다

| 층 | 실체 | 자리 |
|---|---|---|
| 모델 | PTY. 서버에 하나 | `internal/webserver` |
| 시선 | `Tool` 인스턴스. **칸마다 하나** | `_mkTool(toolId, name, slot)` (`renderer.js:417`) |

`this.tools` 의 키가 `_slotKey(id,slot)` = `toolId@1` 이므로 (`app-slots.js:40`) 두 칸이
같은 터미널을 보면 각자의 xterm 이 같은 PTY 를 구독한다. **데이터는 하나, 화면은
둘이다.**

편집기 본문도 같은 키 규약 위에 있다 — `fileEditors` 의 키가 `_slotKey(at.id,slot)`
다 (`renderer.js:401`).

따라서 본 SRS 가 git·탐색기에 요구하는 것은 **이 규약의 확장**이며, 새 추상 계층을
세우는 일이 아니다.

### 2.2 활성 탭은 창의 것이다 — 칸이 같은 탭에 묶이는 유일한 이유

`activeTab` 은 pane 에 붙어 워크스페이스에 저장된다. 쓰는 자리가 여럿이다 —
`app-layout.js:272·296·315·419`, `app-dnd.js:32·77`, `app-cmd.js:505`,
`app-attn.js:222`, `app-tool.js:105`.

칸 둘이 같은 창을 보면 `layout` 이 같으므로 pane 구성도 같고 `activeTab` 도 같다.
**칸을 갈라도 화면이 같은 근본 원인이 이 한 줄이다.**

### 2.3 "이 브라우저가 보고 있는 것" 이라는 범주가 이미 있다

원격 워크스페이스 변경을 적용할 때, 구조 변경은 받아들이면서 **보는 자리는 로컬이
이긴다** (`app-cmd.js:266-292`).

```js
// Preserve per-window viewport state: activeWindow and each window's
// focusedPane. Remote structural changes (splits/tabs) are applied
// but this window stays on its own window/pane.
```

이 범주에 이미 셋이 있다.

| 값 | 영속 | 근거 |
|---|---|---|
| `activeWindow` | sessionStorage | `app-cmd.js:279` |
| 창별 `focusedPane` | sessionStorage (`focusedPanes`) | `app-focus.js:26-34` |
| Git 창의 활성 리포 | 워크스페이스 + 로컬 우선 | FR-GRR-2 (`app-cmd.js:274-292`) |

**칸별 탭은 이 목록의 네 번째 항목이다.** 규약은 이미 정해져 있으므로 발명할 것이
없다.

### 2.4 `dmctl` 은 활성 탭을 삼중 조건으로 읽는다

```go
isActive := sess.ID == s.ActiveWindow && sess.FocusedPane == rg.ID && rg.ActiveTab == tab.ID
```

`internal/shared/workspace/manager.go:545`, `internal/helper/runtimebin/dmctl_listworkspace.go:311`.

칸별 탭을 **순수 로컬로만** 두면 `dmctl` 이 말하는 활성 탭과 화면이 어긋난다. FR-SVS-14
가 이것을 규정한다.

### 2.5 GitPanel 은 관측과 시선을 한 객체에 담고 있다

`constructor` (`panel.js:13-63`) 의 필드가 두 종류로 갈린다.

**관측** — 누가 보든 같다

`_status`·`_missing`·`_errMsg`·`_staleNote`·`_failStreak`·`_obsSig`·`_lastSig`·
`_lastViewFp`·`_gitMissing`·`_refreshing`·`_seq`·`_gen`. 전부 `panel.js` 안에서만
쓰인다(`_seq` 만 `branches.js`·`console.js`·`tag.js`·`remote.js` 가 stale 판정에 읽는다).

폴링도 여기 있다 — `_applyCadence`·`_reschedule`·`_stop`·`collect`·`_pollSignature`
(`panel.js:2451-2480`).

**시선** — 칸마다 달라야 하는 것

`_sel`(33곳)·`_anchor`·`previewFile`·`commitFile`·`_collapsed`·`_dirCollapsed`·
`_shown`·`_fileView`·`_sideBy`·`_ignWs`·`_diffKey`·`_prevKey`·`_hunkKey`·`_hunks`·
`_hunkSel`·`_diffPos`·`_note`·`_writing`.

### 2.6 하위 뷰 모듈은 이미 `panel` 을 주입받는다 — 이것이 V 를 싸게 만든다

일곱 모듈이 **같은 모양**이다.

```js
constructor(panel){ this.panel=panel; this.app=panel.app; this._el=null; ... }
```

`history.js:20`, `branches.js:18`, `stash.js:17`, `console.js:13`, `worktrees.js:19`,
`commit.js:16`, `remote.js:27`.

그리고 각 모듈은 이미 **자기 시선**을 갖는다 — `_el`·`_repo`·`_msg`·`_recs`.

**따라서 `GitPanel` 자체를 칸별 인스턴스로 만들면 이 일곱 모듈은 한 줄도 바뀌지
않고, `panel` 에 있던 시선 18개가 자동으로 칸의 것이 된다.** 시선 필드를 하나씩
옮기고 조작 API 마다 칸 인자를 더하는 설계보다 압도적으로 작다 (§4 D-3).

### 2.7 `elFor` 는 view 별 단일 DOM 이다

```js
elFor(view){ let el=this._els.get(view); if(!el){ ... } }
```

`panel.js:120`. `_render(view)` 도 `this._els.get(view)` 로 **하나**를 꺼낸다
(`:176`).

다만 실제 그리기 함수는 **이미 `el` 을 인자로 받는다** — `_renderChanges(el)`·
`_renderHistory(el)`·`_paintHeadIn(el)`·`_wireHead(el)`. `paintHeads()` 는 이미
`_els.values()` 를 **순회**한다 (`:406`), `_paintAllViews()` 도 `_els.keys()` 순회다
(`:241`). "한 관측을 여러 DOM 에 칠한다" 는 개념이 이미 코드에 있다.

### 2.8 탐색기는 관측과 시선이 한 객체에 섞여 있다

`FileTree` (`file-tree.js:12-32`) 는 창별 인스턴스이고 (`app-editor.js:247`), 다음을
함께 들고 있다.

| 성질 | 필드 |
|---|---|
| 관측 | `_kids`(디렉터리 목록 캐시)·`_st`·`_dirSt`·`_partial`(git 색)·`_ign`(무시 이름) |
| 시선 | `_open`(펼침)·`_sel`(선택)·`_scrollY`·`_edit`(인라인 입력)·`_busy` |

git 색은 인스턴스가 직접 가져온다 — `fetch(GIT_STATUS_API+'?repo='+…)`
(`file-tree.js:309`). **인스턴스를 칸마다 늘리면 이 요청이 칸 수만큼 늘어난다.**

`mount()` 는 항상 같은 `this.el` 을 돌려주므로 (`:110`) 두 칸이 같은 Editor 창을
보면 탐색기가 뒤 칸으로 옮겨간다 — 앞 칸은 편집기 본문만 남고 탐색기 자리가 빈다.

### 2.9 편집기는 문서를 뷰가 소유한다 — 이미 데이터 손실 경로다

`FileEditor` 는 내용(Monaco 모델)과 `_dirty` 를 자기 안에 갖는다
(`file-editor.js:182-191`), 그러면서 인스턴스는 **이미 칸별**이다 (`renderer.js:401`).

따라서 같은 파일 탭을 두 칸에 두면 독립 편집기 둘이 같은 파일을 각자 편집한다.

| 결과 | 근거 |
|---|---|
| 한쪽 저장이 다른 쪽 저장에 덮인다 (lost update) | `save()` 가 자기 버퍼를 그대로 PUT 한다 (`:379-389`) |
| `● ` dirty 표시가 서로 밟는다 | `tab.dirty` 는 워크스페이스 공유값인데 양쪽이 쓴다 (`:421`) |

**슬롯 기능이 이미 열어 둔 결함이며, 본 SRS 의 E 묶음이 이것을 닫는다.**

### 2.10 전역 `app.gitPanel` 조회가 네 곳 있다

`dialog.js:63`, `menu.js:22`, `confirm.js:119`, `history.js:87` 이
`window.app.gitPanel` 을 직접 읽는다. 칸별 인스턴스가 되면 **이들은 어느 칸인지
모른다** (§7 R-2).

### 2.11 비포커스 칸의 첫 클릭은 유실된다 (기존 결함, M1 검증 중 관측)

칸 el 에 걸린 mousedown 이 포커스를 옮기고 **곧바로 `render()` 를 돈다** —
`slotFocusTo` (`app-slots.js`) → `render()`. 그런데 render 는 `.slot`·`.pn`·`.ed-win`
을 지우고 다시 만들므로 (`renderer.js`), mousedown 을 받은 요소가 문서에서 떨어진다.
브라우저는 mousedown 과 mouseup 이 같은 조상을 공유하지 않으면 **click 을 발생시키지
않으므로**, 그 클릭은 어떤 핸들러에도 닿지 않는다.

결과: 다른 칸의 탭·탐색기 행을 누르면 **첫 번째 클릭은 포커스만 옮기고 아무 일도
일어나지 않는다.** 사용자는 두 번 눌러야 한다.

e2e 로 확인했다 — 포커스를 먼저 옮기고 누르면 같은 클릭이 정상 동작한다. 슬롯 도입
(FR-WSL-55) 때부터 있던 것이지만, 칸마다 다른 것을 보게 되는 본 SRS 이후로는 다른
칸을 누를 일이 훨씬 많아지므로 체감이 커진다.

포커스 이동은 **DOM 구조를 바꾸지 않는다** — 바뀌는 것은 `.slot-focused` 클래스와
소유권 흐림뿐이다. 그러므로 전체 재구성이 필요하지 않다 (§3.6 FR-SVS-61).

### 2.12 죽은 편집기 회수가 칸 1만 안다 (기존 결함)

```js
const tid=k.endsWith('@1')?k.slice(0,-2):k;
if(!allTabIds.has(tid)){v.destroy();app.fileEditors.delete(k)}
```

`renderer.js:199-201`. `SLOT_MAX` 는 4인데 (`app-slots.js:22`) `@2`·`@3` 은 이 파싱을
지나지 못해 `tid` 가 `tabid@2` 로 남고, 살아 있는 탭인데도 `allTabIds` 에 없으므로
**매 render 마다 destroy 된다.** `_slotReap` 의 `slotOf` 는 올바르게 파싱한다
(`app-slots.js:322`) — 이쪽만 낡았다.

## 3. 요구사항 (Requirements)

### 3.1 T — 칸별 활성 탭

- **FR-SVS-1** 칸은 pane 마다 "내가 보는 탭" 을 적어 둘 수 있다. 이것을 **칸별 탭
  오버라이드**라 한다.
- **FR-SVS-2** 오버라이드가 없는 pane 은 `pn.activeTab` 을 따른다. **단일 슬롯 모드는
  오버라이드를 두지 않는다** — 그 상태의 동작은 본 SRS 이전과 완전히 같아야 한다
  (WINDOW_SLOTS_SRS D-4).
- **FR-SVS-3** 칸이 창을 받을 때(칸 추가·`slotOpen`·`_slotOnSwitch`), 그 창의 모든
  pane 에 대해 오버라이드가 없으면 **그 순간의 `pn.activeTab` 으로 초기화한다.**
  초기화하지 않으면 다른 칸이 탭을 바꿀 때 이 칸이 따라 움직인다.
- **FR-SVS-4** 탭을 고르는 모든 길은 **그 칸의 오버라이드만** 바꾼다. 다른 칸은
  움직이지 않는다.
- **FR-SVS-5** 오버라이드가 가리키는 탭이 사라지면 그 pane 의 오버라이드는 `pn.activeTab`
  으로 되돌아간다. 그것도 없으면 pane 의 첫 탭이다.
- **FR-SVS-6** 오버라이드는 `sessionStorage` 에 남는다 — 새로고침 후 각 칸이 보던
  탭으로 돌아온다. 칸 배치(`slots`)와 같은 범주이므로 같은 키 안에 둔다 (FR-WSL-72).
- **FR-SVS-7** 워크스페이스 구조 변경이 원격에서 와도 오버라이드는 살아남는다 —
  `focusedPane` 복원과 같은 자리, 같은 규약이다 (`app-cmd.js:283-286`).
- **FR-SVS-8** 창 안 pane 이동(`paneNavigate`)·칸 넘김(`slotNavigate`)은 오버라이드를
  건드리지 않는다. 포커스가 움직이는 것과 보는 탭이 바뀌는 것은 다른 사건이다.
- **FR-SVS-9** 탭 바는 그 칸의 오버라이드를 활성으로 그린다. 같은 창을 보는 두 칸의
  탭 바가 서로 다른 탭을 활성으로 보이는 것이 정상이다.
- **FR-SVS-10** 탭을 닫으면 **그 칸의** 오버라이드가 이웃 탭으로 간다. 다른 칸이 그
  탭을 보고 있었다면 그 칸도 FR-SVS-5 로 이동한다.
- **FR-SVS-11** 드래그로 탭을 다른 pane·창으로 옮기면, 옮긴 칸의 오버라이드가 그 탭을
  따라간다 (`app-dnd.js:32·77` 이 지금 `activeTab` 에 하는 일과 같은 뜻).
- **FR-SVS-12** 알람이 부른 탭 활성화(`app-attn.js:222`)는 **포커스 칸**에 적용한다.
  알람은 사용자를 부르는 것이고 사용자는 포커스 칸에 있다.
- **FR-SVS-13** `_isToolFocusedActive`(FR-PAN-9) 의 "지금 보이는 탭인가" 판정은
  **어느 칸에서든 보이면 보이는 것**으로 한다. 두 칸 중 하나에 떠 있는데 알람이
  울리면 그것이 결함이다.
- **FR-SVS-14** 포커스 칸의 오버라이드는 워크스페이스 `pn.activeTab` 에도 반영한다.
  `dmctl` 의 활성 판정(§2.4)이 "포커스 칸이 보는 것" 으로 정확히 유지되어야 하고,
  이것은 `focusedPane` 이 로컬이면서 워크스페이스에도 쓰이는 것과 같은 취급이다.
  비포커스 칸의 오버라이드는 워크스페이스에 쓰지 않는다.

### 3.2 X — 탐색기

- **FR-SVS-20** 탐색기의 **관측**(디렉터리 목록 캐시·git 색·무시 이름)은 **루트마다
  하나**다. 같은 루트를 보는 칸이 둘이어도 `fetch` 는 한 벌이다.
- **FR-SVS-21** 탐색기의 **시선**(펼침·선택·스크롤·인라인 입력)은 **칸마다 하나**다.
  칸마다 다른 폴더를 펼쳐 볼 수 있다.
- **FR-SVS-22** 관측이 갱신되면 그 루트를 보는 **모든** 칸이 다시 칠해진다. 칠하기는
  각 칸의 시선을 딛는다 — 한 칸의 펼침 상태가 다른 칸의 칠하기에 새면 안 된다.
- **FR-SVS-23** 칸이 사라지면 그 칸의 시선은 회수된다. 그 루트를 보는 칸이 하나도
  남지 않으면 관측도 회수하고 폴링을 멈춘다.
- **FR-SVS-24** 창별 `_edTrees` 규약(FR-EDT-57)은 칸별로 확장된다 — 키가
  `_slotKey(winId, slot)` 가 된다. 칸 0 의 키는 `winId` **그대로**다 (FR-WSL-75 와
  같은 이유).

### 3.3 O — Git 관측

- **FR-SVS-30** 폴링과 관측을 **`GitObserver`** 로 분리한다. 앱에 하나다.
  옮기는 것: §2.5 의 관측 필드 12개와 폴링 함수 5개.
- **FR-SVS-31** `git status` 요청 수는 **칸 수와 무관하다.** 칸을 넷으로 늘려도
  네트워크 요청은 단일 슬롯 모드와 같다. single-flight(FR-GIT-21)·즉시 1회
  계약(FR-GIT-22)·활성 리포 한정(FR-GIT-24)은 그대로다.
- **FR-SVS-32** 관측이 갱신되면 살아 있는 **모든** `GitPanel` 이 통지를 받아
  칠한다. 통지는 관측자가 하고, 무엇을 칠할지는 각 패널이 자기 시선으로 정한다.
- **FR-SVS-33** 소실(FR-RMS-6~11)은 관측의 성질이다 — 모든 칸이 동시에 소실 안내로
  간다. 분기는 여전히 한 자리다 (FR-RMS-19).
- **FR-SVS-34** 활성 리포는 Git 창에 붙어 있으므로(FR-GIT-29) **모든 칸이 같은
  리포를 본다.** 칸마다 다른 리포를 보는 것은 비목표다 (§6).
- **FR-SVS-35** stale 판정(`token()`·`isStale()`)은 관측자의 것이다. 하위 모듈이
  읽는 `_seq`(`branches.js`·`console.js`·`tag.js`·`remote.js`)는 관측자를 지나게
  한다.
- **FR-SVS-36 (사후 추가)** 관측이 도는 조건은 **Git 창이 화면에 있는가**이지
  *활성 창인가*가 아니다.

  > **접수**: *"히스토리 그래프가 변경사항을 바로바로 갱신하지 않아."*
  >
  > **실측** (칸 둘, 칸 0 = 터미널 창에 서고 칸 1 = Git 창):
  >
  > | 상황 | Git 뷰가 화면에 | `_pollOk()` | 새 커밋이 보이나 |
  > |---|---|---|---|
  > | 단일 칸, Git 창 활성 | 있다 | 참 | 보인다 |
  > | 다른 창 갔다 복귀 | 있다 | 복귀 시 참 | 보인다 |
  > | **칸 둘, 터미널 칸에 섬** | **있다** | **거짓** | **안 보인다** |
  >
  > `_pollOk`(`panel-poll.js`)가 `ws.activeWindow` 하나만 보기 때문이다. 슬롯이
  > 생기기 전에는 "활성 창 = 보이는 창"이라 그 판정이 옳았지만, **칸이 여럿이면
  > 여러 창이 동시에 보인다** (FR-WSL-1). 눈앞의 History 가 멎은 채로 남는 것이
  > 그 전제가 깨진 자리다.

- **FR-SVS-37** "화면에 있는가"의 판정은 **App 한 자리**에 둔다. 슬롯의 안을 아는
  것은 App 이고, Git 패널이 `_slots` 를 직접 들여다보면 슬롯 표현이 바뀔 때마다
  그 자리도 따라 고쳐야 한다.

- **FR-SVS-38** 단일 슬롯 모드의 판정은 **종전과 한 글자도 다르지 않다** —
  `_slots` 가 없으면 보이는 창은 활성 창 하나다 (FR-WSL-4, D-4).

- **FR-SVS-39** 요청 수는 늘지 않는다 (FR-SVS-31). 칸 넷이 모두 Git 창을 보아도
  관측자는 하나이고 주기도 하나다 — 바뀌는 것은 **돌지 말지의 판정**뿐이다.

- **FR-SVS-39a** 이 판정은 Git 창의 **모든 탭**을 되살린다. Changes 는 관측
  (`collect`)이, 나머지 다섯(History·Branches·Stash·Console·Worktrees)은
  `_reloadViews` 가 이미 받고 있었다 — 멎어 있던 것은 그 둘을 부르는 **주기**
  하나였다. 열지 않은 뷰는 각자의 조기 반환이 그대로 거른다 (FR-GVR-4).

- **FR-SVS-39b** 탐색기의 git 색도 같은 원칙을 따른다. 지금은 **활성 창의 트리
  하나**만 폴링하므로(`_edActiveTree`), 칸 둘에 Editor 창을 놓으면 서 있지 않은
  쪽이 멎는다. 보이는 **모든** 트리를 폴링한다 — 관측은 루트마다 하나이고
  캐시·single-flight 가 그 위에 있으므로(FR-EDT-77) 같은 루트를 둘이 보아도
  git 실행은 한 번이다.

- **FR-SVS-39c** 로그를 받는 도중 관측이 낡으면(`isStale`) 그 응답은 버리되
  **로딩 잠금은 푼다.** 지금은 잠긴 채로 나가므로 `_load` 의 `if(this._loading)
  return this._loadP` 가 이후 모든 요청을 삼킨다 — 커밋 목록이 영영 멎는다.

  > **접수**: *"히스토리의 왼쪽 창은 업데이트 되는 걸 보면 draw 문제일 것 같다."*
  > 왼쪽(refs)은 `_loadRefs()` 라는 별도 경로라 그 잠금이 없다. 그래서 **한쪽만
  > 살아 있는** 것으로 보였고, 그것이 이 결함의 지문이다.

### 3.4 V — Git 시선

- **FR-SVS-40** `GitPanel` 은 **칸별 인스턴스**가 된다. §2.5 의 시선 필드 18개가
  자동으로 칸의 것이 된다.
- **FR-SVS-41** 하위 뷰 모듈 일곱은 **바뀌지 않는다.** `constructor(panel)` 로
  주입받는 구조(§2.6)가 그대로 칸별 분리를 준다.
- **FR-SVS-42** 같은 뷰를 두 칸에서 볼 수 있다. 각 칸이 자기 루트 DOM 을 갖는다 —
  `_els` 의 키가 칸을 포함한다.
- **FR-SVS-43** 두 칸이 같은 Changes 를 볼 때 한 칸의 파일 선택·그룹 접힘·미리보기
  대상은 **다른 칸에 영향을 주지 않는다.** 왼쪽에서 파일 A 의 diff, 오른쪽에서 파일
  B 의 diff 를 나란히 볼 수 있다.
- **FR-SVS-44** 쓰기 조작(스테이징·커밋·체크아웃 등)의 **결과**는 관측이므로 모든
  칸에 반영된다. 조작이 시작된 칸이 어디인지는 결과에 영향을 주지 않는다.
- **FR-SVS-45** 쓰기 중복 방지(`_writing`)는 **관측자의 것**이다. 칸별로 두면 두 칸이
  같은 쓰기를 동시에 보낸다.
- **FR-SVS-46** 칸이 사라지거나 다른 창을 받으면 그 칸의 `GitPanel` 과 뷰가 파괴된다.
  Monaco 는 DOM 을 떼는 것으로 풀리지 않으므로 `_destroyViews()` 를 지나야 한다
  (FR-GIT-56).
- **FR-SVS-47** 전역 `app.gitPanel` 조회 네 곳(§2.10)은 **포커스 칸의 패널**을
  가리키게 한다. 메뉴·확인창·다이얼로그는 사용자가 방금 조작한 자리의 것이고, 그
  자리는 포커스 칸이다.

### 3.5 E — 편집기 문서

- **FR-SVS-50** 같은 파일의 **문서는 하나**다. 내용과 dirty 는 문서의 것이며 칸의
  것이 아니다.
- **FR-SVS-51** 한 칸에서 타이핑하면 같은 파일을 보는 다른 칸에 즉시 보인다.
- **FR-SVS-52** 커서·선택·스크롤·접힘은 **칸마다** 남는다.
- **FR-SVS-53** 저장은 문서 하나에 대한 한 번이다. 한쪽 저장이 다른 쪽 저장을 덮는
  일이 없어진다 (§2.9).
- **FR-SVS-54** `● ` dirty 표시는 문서의 dirty 를 딛는다. 같은 파일을 보는 두 칸의
  탭이 동시에, 같게 표시된다.
- **FR-SVS-55** 문서는 그 파일을 보는 칸이 하나도 남지 않을 때 회수된다.

### 3.6 F — 함께 고치는 결함

- **FR-SVS-60** 죽은 편집기 회수가 칸 1~3 전부를 올바르게 파싱한다 (§2.12). 파싱은
  `_slotReap` 의 `slotOf` 와 **같은 한 자리**를 쓴다 — 두 자리에 두면 다시 어긋난다.
- **FR-SVS-61** 비포커스 칸을 누른 **그 한 번**이 목적한 일을 한다 (§2.11). 칸 포커스
  이동이 전체 `render()` 를 돌지 않아야 한다 — 포커스는 클래스와 흐림만 바꾸므로
  구조를 다시 만들 이유가 없다. 탭 전환·창 열기처럼 **구조가 실제로 바뀌는** 경로는
  지금처럼 render 를 돈다.

### 3.7 I — 인터페이스 계약

- **FR-SVS-70** 칸별 상태의 키는 **모두 `_slotKey` 를 지난다** (`app-slots.js:40`).
  칸 0 의 키는 접미사가 없다.
- **FR-SVS-71** `sessionStorage` 의 `slots` 키에 탭 오버라이드가 함께 들어간다.
  형식이 어긋나면 키를 지우고 단일 슬롯 모드로 떨어진다 (FR-WSL-72 의 규약 그대로).
- **FR-SVS-72** 단일 슬롯 모드의 DOM 은 한 글자도 바뀌지 않는다 (D-4). 기존 e2e 가
  그 위에 서 있다.

## 4. 설계 결정 (Design Decisions)

- **D-1 규약을 발명하지 않는다.** 모델/뷰 분리의 원본은 터미널(§2.1)이다. git·탐색기·
  편집기를 그 규약에 맞추는 것이며, 공통 추상 계층(`ViewBase` 류)을 새로 만들지
  않는다. 타입마다 관측의 성질이 다르고(서버 PTY / 폴링 / 파일시스템 / 사용자 편집)
  억지로 한 인터페이스에 넣으면 어느 쪽도 맞지 않는다.

- **D-2 칸별 탭은 오버라이드다.** `layout` 을 칸마다 복제하지 않는다. 복제하면 구조
  변경(분할·탭 추가) 동기화가 칸마다 갈라져 어느 것이 진실인지 알 수 없다. 오버라이드는
  `pn.activeTab` 위에 얇게 얹히고, 대상이 사라지면 폴백한다 (FR-SVS-5).

- **D-3 `GitPanel` 을 칸별로 만든다 — 시선 필드를 옮기지 않는다.** 시선 18개를 별도
  객체로 빼고 조작 API 마다 칸 인자를 더하는 설계는 하위 모듈 일곱과 조작 API 전부를
  건드린다. `panel` 자체를 칸별로 두면 §2.6 의 주입 구조가 그 일을 이미 해 준다 —
  일곱 모듈은 바뀌지 않는다. **작은 쪽을 택한다.**

- **D-4 관측자는 통지만 한다.** `GitObserver` 는 어떤 패널이 무엇을 그리는지 모른다.
  갱신되면 "바뀌었다" 를 알리고, 무엇을 칠할지는 각 패널이 자기 시선으로 정한다.
  관측자가 뷰를 알면 칸 수만큼 분기가 늘어난다.

- **D-5 탐색기 관측의 단위는 루트다.** 창이 아니다 — 두 Editor 창이 같은 루트를 보면
  요청이 두 벌이 될 이유가 없고, 칸별 시선이 생기면 "창별" 이라는 단위가 어차피
  무의미해진다.

- **D-6 편집기 문서는 Monaco 의 `ITextModel` 을 공유한다.** Monaco 는 한 모델을 여러
  에디터에 붙이는 것을 공식 지원하며, 그때 커서·스크롤·접힘은 에디터별로 남는다 —
  FR-SVS-51·52 가 그것으로 그대로 충족된다. 직접 동기화 계층을 만들지 않는다.

- **D-7 문서의 단위는 파일 경로다.** 탭이 아니다. 같은 파일을 두 탭에서 열 수 있다면
  탭 단위 문서는 같은 손실을 다시 만든다.

- **D-8 전역 진입점은 포커스 칸을 가리킨다** (FR-SVS-47). 메뉴·확인창을 칸마다 두는
  것은 뜻이 없다 — 그것들은 화면에 하나만 서고, 사용자가 방금 조작한 자리에 속한다.

## 5. 마일스톤

각 M 은 **그것만으로 사용자 눈에 보이는 결과**를 낸다. 앞 M 이 뒤 M 을 막지 않는다.

| M | 묶음 | 결과 | 리스크 |
|---|---|---|---|
| **M1** | T, F | 왼쪽 Changes, 오른쪽 History. 접수한 요구의 본체 | LOW |
| **M2** | X | 칸마다 다른 폴더를 펼친다. 요청 수는 그대로 | LOW |
| **M3** | O, V | 같은 탭 두 칸에서 서로 다른 파일 diff | MEDIUM |
| **M4** | E | 같은 파일 두 칸. 저장 충돌 소멸 | MEDIUM |
| **M5** | F (FR-SVS-61) | 다른 칸을 누른 첫 클릭이 곧바로 듣는다 | LOW |

**M1 만으로 접수한 요구(§1.1 첫 줄)가 해소된다.** 두 칸이 서로 다른 탭을 보면
`_els` 가 view 별로 갈리므로 (§2.7) Git 의 DOM 충돌이 발생하지 않는다. M3 는 "같은
탭을 두 칸에" 를 위한 것이다.

## 6. 비목표 (Non-goals)

- 창 타입의 불변식 변경. Git 창은 여전히 탭을 더할 수 없고, Editor 창에는 편집기
  탭만 산다
- 서버 워크스페이스 스키마 변경. 칸은 클라이언트의 것이다 (FR-WSL-2)
- 칸마다 다른 Git 리포 (FR-SVS-34). 활성 리포는 창의 것이다 (FR-GIT-29)
- 모바일 다중 슬롯 (FR-WSL-60~62)
- 실시간 협업 편집. FR-SVS-51 은 **같은 브라우저의 칸 사이**에서만이다
- 공통 모델/뷰 추상 계층 (D-1)
- `SLOT_MAX` 변경

## 8. 검증 (Verification)

각 TC 는 e2e 로 고정한다. **M 마다 기존 검사 전부가 함께 통과해야 한다.**

### M1

- **TC-SVS-1** 칸 둘에 같은 Git 창을 놓고 왼쪽에서 Changes, 오른쪽에서 History 를
  고른다 → 양쪽이 각자의 탭을 보인다. 양쪽 탭 바의 활성 표시가 서로 다르다
- **TC-SVS-2** 그 상태로 새로고침 → 각 칸이 보던 탭으로 돌아온다 (FR-SVS-6)
- **TC-SVS-3** 오른쪽 칸이 보던 탭을 닫는다 → 오른쪽만 이웃 탭으로 가고 왼쪽은
  그대로다 (FR-SVS-10)
- **TC-SVS-4** 단일 슬롯 모드에서 탭 전환 → 본 SRS 이전과 동일한 DOM·동일한
  `activeTab` (FR-SVS-72)
- **TC-SVS-5** 포커스 칸에서 탭을 바꾼 뒤 `dmctl list-workspace` → 활성 탭이 포커스
  칸이 보는 것과 같다 (FR-SVS-14)
- **TC-SVS-6** 칸을 넷으로 늘려 각 칸에 편집기 탭을 띄운다 → 렌더가 반복돼도 어느
  편집기도 파괴되지 않는다 (FR-SVS-60)
- **TC-SVS-50** 다른 클라이언트가 창을 만들어 `workspace_changed` 가 온다 → 구조는
  따라오지만 각 칸이 보던 탭은 그대로다 (FR-SVS-7)
- **TC-SVS-54** 탭을 다른 분할 칸으로 옮긴다 → 옮긴 칸의 시선이 그 탭을 따라가고,
  다른 칸은 자기가 보던 탭을 그대로 본다 (FR-SVS-11)
- **TC-SVS-55** 칸 사이를 오간다 → 두 칸의 시선이 그대로다 (FR-SVS-8)
- **TC-SVS-56** 알람이 다른 탭의 도구를 부른다 → **포커스 칸**이 그 탭으로 가고 다른
  칸은 끌려가지 않는다 (FR-SVS-12)
- **TC-SVS-58** 형식이 어긋난 `slots` 키로 로드한다 → 키가 지워지고 단일 슬롯 모드로
  떨어진다 (FR-SVS-71)

### M2

- **TC-SVS-10** 칸 둘에 같은 Editor 창. 왼쪽에서 폴더 A, 오른쪽에서 폴더 B 를 펼친다
  → 양쪽 펼침이 독립이고 양쪽 모두 탐색기가 보인다
- **TC-SVS-11** 그동안 `/api/git/status` 요청 수가 단일 슬롯 모드와 같다 (FR-SVS-20)
- **TC-SVS-12** 한 칸을 없앤다 → 남은 칸의 펼침·스크롤이 유지된다 (FR-SVS-23)

### M3

- **TC-SVS-20** 칸 둘에서 같은 Changes 를 본다 → 양쪽 모두 목록이 보인다 (FR-SVS-42)
- **TC-SVS-21** 왼쪽에서 파일 A, 오른쪽에서 파일 B 를 고른다 → 각 칸의 미리보기가
  서로 다른 파일을 보인다 (FR-SVS-43)
- **TC-SVS-22** 그동안 `/api/git/status` 요청 수가 단일 슬롯 모드와 같다 (FR-SVS-31)
- **TC-SVS-23** 왼쪽에서 파일을 스테이징 → 양쪽 목록이 함께 갱신된다 (FR-SVS-44)
- **TC-SVS-24** 리포 폴더를 지운다 → 두 칸이 함께 소실 안내로 간다 (FR-SVS-33)
- **TC-SVS-25** 칸을 없앤다 → 그 칸의 Monaco 가 파괴된다 (FR-SVS-46)
- **TC-SVS-51** 두 칸이 각자 파일을 고른 뒤 리포를 바꾼다 → 양쪽 시선이 함께
  되돌아간다. 이전 리포의 선택이 새 리포의 헤더와 함께 보이는 순간이 어느 칸에도
  없다 (FR-SVS-34)
- **TC-SVS-53** 두 패널이 같은 쓰기를 동시에 부른다 → 요청은 한 번만 나간다
  (FR-SVS-45)
- **TC-SVS-57** 포커스 칸을 옮겨 가며 `app.gitPanel` 을 본다 → 언제나 포커스 칸의
  패널이다 (FR-SVS-47)

### M5

- **TC-SVS-40** 칸 0 이 포커스인 상태에서 칸 1 의 탭을 **한 번** 누른다 → 칸 1 이
  포커스가 되고 **그 탭이 열린다**. 두 번 누를 필요가 없다
- **TC-SVS-41** 같은 조건에서 칸 1 의 탐색기 폴더를 한 번 누른다 → 펼쳐진다

### M4

- **TC-SVS-30** 같은 파일을 두 칸에서 연다. 왼쪽에서 타이핑 → 오른쪽에 즉시 보인다
  (FR-SVS-51)
- **TC-SVS-31** 커서를 각 칸에서 다른 곳에 둔다 → 서로 움직이지 않는다 (FR-SVS-52)
- **TC-SVS-32** 왼쪽에서 저장 → 오른쪽의 dirty 표시가 함께 사라진다. 오른쪽에서 다시
  저장해도 왼쪽 내용이 되돌아가지 않는다 (FR-SVS-53·54)
- **TC-SVS-52** 칸 하나를 없앤다 → 다른 칸이 보고 있으므로 문서와 모델이 남는다.
  탭까지 닫으면 둘 다 거둬진다 (FR-SVS-55)

### M6 — 보이면 갱신된다 (사후 추가)

- **TC-SVS-60** 칸 둘에 터미널 창과 Git 창을 놓고 **터미널 칸에 선다.** 밖에서
  커밋을 만든다 → 옆 칸의 History 에 그 커밋이 나타난다 (FR-SVS-36)
- **TC-SVS-61** 같은 배치에서 Changes·Branches 도 따라온다 — 멎어 있던 것은 뷰가
  아니라 주기였다 (FR-SVS-39a)
- **TC-SVS-62** 단일 슬롯 모드의 판정은 종전과 같다 — Git 창이 활성이면 돌고,
  아니면 돌지 않는다 (FR-SVS-38)
- **TC-SVS-63** 칸 둘에 Editor 창을 놓고 한쪽에 선다. 밖에서 파일을 고친다 →
  **양쪽** 탐색기의 git 색이 따라온다 (FR-SVS-39b)
- **TC-SVS-64** 로그를 받는 도중 관측이 낡는다 → 그 응답은 버려지되 **다음 로드가
  돈다.** 새 커밋이 목록에 나타난다 (FR-SVS-39c)

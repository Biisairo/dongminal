# SRS: 워크스페이스 저장 충돌 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 것은 콘솔 로그다.

> **"`:58146/api/workspace:1 Failed to load resource: the server responded with a
> status of 409 (Conflict)`"** (여러 줄 되풀이)

처음 판단은 "소음" 이었다. **재현으로 그것이 틀렸음을 확정했다** — 409 는 소음이
아니라 **다른 화면이 만든 창이 사라지는 경로**다 (§2.5).

```
시작:          서버의 일반 창 1
A 가 창 추가:  서버 2  | B(아직 모름) 1
B 가 저장:     서버 1  | PUT 응답 [409, 200]
판정:          A 의 창이 사라졌다
```

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **C** 충돌 | 409 를 만나면 **남의 변경을 지우지 않는다** — 이번 저장을 포기하고 원격을 채택한다 |
| **R** 재시도 | 연속 충돌에 상한과 백오프를 둔다 |
| **A** 적용 | 저장이 포기된 경우 미뤄 둔 원격 적용을 **버리지 않는다** |

**미포함:** §6 비목표. 특히 **저장을 쪼개는 일은 하지 않는다** (§1.5 I-1).

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **rev** | 워크스페이스의 판 번호. 저장마다 1 오른다 (`manager.go:223`) |
| **ETag / If-Match** | 화면이 아는 rev. 서버의 것과 다르면 저장은 409 다 |
| **원격 채택** | 서버의 워크스페이스를 화면에 적용하는 일 (`_applyRemoteWorkspace`) |
| **미뤄 둔 적용** | 저장 중에 온 `workspace_changed` 를 나중에 처리하려 남긴 표시 (`_wsApplyPending`) |
| **일반 창** | Git 창·Editor 창이 아닌 창 |

### 1.5 착수 전 확정된 결정

사용자 인터뷰로 굳혔다. **스펙보다 앞선다.**

| # | 물음 | 답 |
|---|---|---|
| **I-1** | 충돌할 때 누가 이기는가 | **원격 우선.** 남의 변경을 지우지 않는다. 대가는 내가 방금 한 조작이 사라질 수 있는 것이며, 그것은 다시 하면 되는 일이다 |
| **I-2** | 무제한 재시도를 어떻게 하는가 | **상한과 백오프** |

I-1 이 배제한 것 둘을 적어 둔다 — 나중에 "왜 이렇게 하지 않았나" 가 다시 묻히지
않게 하기 위해서다.

- **창 합집합**: 양쪽의 창을 다 지킨다. 그러면 **다른 화면에서 닫은 창이 되살아난다**
  — 닫힌 것과 새로 생긴 것을 구별할 수 없기 때문이다.
- **저장 쪼개기**: 창 배치와 기기별 값을 나눠 저장한다. 원인에 가장 가깝지만
  워크스페이스 스키마와 여러 종단을 건드리는 대규모 작업이다.

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 저장은 rev 가 정확히 맞아야 통과한다

`internal/shared/workspace/manager.go:212`:

```go
if ifMatch != "" {
    want, err := strconv.ParseUint(ifMatch, 10, 64)
    if err != nil || want != cur {
        return 0, ErrStale
    }
}
```

그리고 모든 저장이 `newRev := cur + 1` 로 rev 를 올린다. **그러므로 어느 화면이
저장하면 다른 모든 화면의 ETag 가 그 순간 낡는다.**

### 2.2 화면은 거의 모든 조작에서 저장한다

`_save()` 는 창 추가·삭제, 탭 이동, 폭 조정, 이름 변경, 포커스 이동에서 불린다.
화면이 여럿이면 충돌의 창구가 그만큼 넓다.

### 2.3 409 재시도는 `git` 과 `editors` 만 병합한다

`web/js/core/app.js:333~365`. 재조회한 원격에서 `git`(핀·초안·즐겨찾기)과
`editors`(목록)는 채택하고, **`windows` 는 로컬 것을 그대로 다시 밀어붙인다.**

주석이 그 이유를 적고 있다 — 핀은 서버가 권위이고 초안·즐겨찾기는 클라이언트가
주인이라는 것. `windows` 에 대한 판단은 그 자리에 **없다.**

### 2.4 저장이 끝나면 미뤄 둔 적용을 **버린다**

`app.js:381`:

```js
// Deferred workspace_changed events from during the save were almost
// certainly echoes of our own PUT ... Drop them — any genuinely newer
// external change will land as a future SSE event with rev > our new wsETag
this._wsApplyPending=false;
```

가정은 "진짜 새 변경은 나중에 또 온다" 다. 성공한 저장에서는 옳다.

**409 재시도로 남의 것을 지운 뒤에는 틀리다** — 그때 우리 PUT 이 마지막 저장이므로
그 뒤에 올 SSE 가 없다. 그래서 손실이 그 자리에서 확정된다.

### 2.5 재현: 다른 화면이 만든 창이 사라진다

두 브라우저 컨텍스트로 확인했다. B 의 SSE 를 끊어 "아직 알림이 도착하지 않은 순간"
을 만든 뒤 A 가 창을 만들고 B 가 저장했다.

| 단계 | 서버의 일반 창 | B 가 아는 수 |
|---|---|---|
| 시작 | 1 | 1 |
| A 가 창 추가 | **2** | 1 (모름) |
| B 가 저장 (PUT `[409, 200]`) | **1** | 1 |

**A 의 창이 사라졌다.** 409 는 그 손실의 신호였다.

### 2.6 재시도에 상한도 백오프도 없다

`this._savePending=true; continue;` — 조건은 `while(this._savePending)` 하나다.
두 화면이 서로 밀어내는 동안 이 루프가 끝없이 돌 수 있다.

### 2.7 원격을 채택하는 길은 이미 있고 정교하다

`_onWorkspaceChanged`(`app-cmd.js:192`)가 그것이다: 저장 중이면 미루고, rev 를
견주고, **적용 직전에 다시 견주어** 낡은 스냅샷을 버린다 (FR-GRR-4). 도구 목록의
자가 치유도 그 안에 있다.

**새로 만들 것이 아니라 이 길을 쓰면 된다.**

### 2.8 판(`?v=`)은 서버가 계산한다

손으로 올릴 값이 없다.

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 묶음 C — 충돌 (FR-WSC-1~5)

- **FR-WSC-1** 저장이 409 를 받으면 **그 저장을 포기한다.** 같은 본문을 다시 밀어
  붙이지 않는다 (I-1).

  근거는 §2.5 다: 우리는 우리가 무엇을 바꾸려 했는지 알지만 **남이 무엇을 바꿨는지는
  모른다.** 그 상태에서 우리 본문을 밀어붙이는 일은 남의 변경을 지우는 일이다.
- **FR-WSC-2** 409 뒤에는 원격 상태를 **채택한다** — `windows` 까지다. 적용기는
  이미 있는 `_applyRemoteWorkspace` 를 쓴다 (§2.7 / D-2): 낡은 모양의 마이그레이션,
  편집기 탭 정리, Editor 창 재조정이 그 안에 있다.

  채택은 **409 를 받은 그 자리에서** 일어난다 (그 GET 이 준 값으로). 비행이 끝난 뒤
  SSE 경로에게 맡기지 않는 이유는 그것이 `/api/state` 를 한 번 더 읽어 같은 일을
  두 번 하기 때문이다.
- **FR-WSC-2b** 그 채택에는 도구 목록을 **모른다고 말한다.** `/api/workspace` 는
  도구를 싣지 않으므로 안다고 하면 빈 목록이 사실이 되어 살아 있는 도구·pane·창이
  차례로 지워진다 (FR-TLU-5·6 이 그 함정을 적고 있다).
- **FR-WSC-3** 미뤄 둔 적용은 종전대로 버린다 (§2.4). 409 뒤에도 버리는 이유는
  FR-WSC-2 가 **그 자리에서 이미 채택했기** 때문이다 — 남겨 두면 같은 일을 두 번
  한다.
- **FR-WSC-4** 채택 중에 새 저장이 예약되면(재조정이 창을 고친 경우가 그렇다) 그것을
  **잃지 않는다.** 비행이 끝날 때 대기 중인 저장이 있으면 다음 비행이 선다.
- **FR-WSC-5** 사용자가 그 사이 새로 조작했으면 그것은 **다음 저장으로 나간다.**
  포기하는 것은 이번 본문이며 사용자의 다음 의도가 아니다.

### 3.2 묶음 R — 재시도 (FR-WSC-6~9)

- **FR-WSC-6** 연속 충돌 횟수를 센다. 성공하면 0 으로 되돌린다.
- **FR-WSC-7** 연속 충돌이 잦으면 다음 저장을 **잠시 미룬다** (백오프). 두 화면이
  서로 밀어내는 동안 그 사이를 벌린다.
- **FR-WSC-8** 연속 충돌이 상한을 넘으면 **그 사실을 기록한다.** 조용히 되풀이하면
  아무도 그것이 일어나는지 모른다 — 접수한 로그가 그 증거다.
- **FR-WSC-9** 백오프는 저장을 **잃지 않는다.** 미룬 뒤 대기 중인 저장이 있으면
  그것이 나간다.

### 3.3 묶음 A — 적용 (FR-WSC-10~11)

- **FR-WSC-10** 원격 채택은 화면을 다시 그린다. 그 비용은 409 가 드물다는 전제
  아래 받아들인다 — 잦으면 그것은 백오프(FR-WSC-7)가 말할 일이다.
- **FR-WSC-11** 채택 뒤 화면의 ETag 는 원격의 것이다. 다음 저장이 곧바로 또 409 가
  되지 않아야 한다.

## 5. 확정 결정 (Decisions)

- **D-1 원격 우선이다.** I-1 — 남의 창이 사라지는 것은 되돌릴 수 없고, 내 폭 조정이
  사라지는 것은 다시 하면 된다. 두 손실의 무게가 다르다.
- **D-2 원격 채택을 새로 쓰지 않는다.** `_applyRemoteWorkspace` 가 이미 그 일을
  하며 낡은 모양의 마이그레이션·편집기 탭 정리·Editor 창 재조정을 갖고 있다 (§2.7).
  저장 경로에 두 번째 적용기를 만들면 그 둘이 갈라진다.

  **처음에는 `_onWorkspaceChanged` 에게 맡기려 했다.** 그것이 `/api/state` 를 다시
  읽으므로 409 처리가 방금 채택한 것을 덮어썼고, 그 자리를 재던 기존 검증(E11 /
  FR-EDT-21)이 그것을 잡았다 — 적용기를 직접 부르는 편이 읽기도 한 번이고 같은
  값을 두 번 해석하지도 않는다.
- **D-3 서버는 건드리지 않는다.** rev 검사는 옳다 — 잃어버린 갱신을 막는 것이 그
  일이며, 문제는 **화면이 409 를 어떻게 다루는가** 였다.
- **D-4 `git`·`editors` 의 병합은 그대로 둔다.** 그 판단에는 근거가 적혀 있고
  (핀은 서버 권위, 초안·즐겨찾기는 클라이언트 주인) 이번 변경이 그것을 뒤집을
  이유가 없다. 다만 그 병합 뒤에 **재시도하지 않는다** 는 점이 달라진다.
- **D-5 저장을 쪼개지 않는다.** I-1 이 배제했다 (§1.5).

## 6. 비목표 (Non-goals)

1. 저장을 창 배치와 기기별 값으로 쪼개기 (D-5).
2. 서버측 필드별 병합·CRDT.
3. 충돌을 사용자에게 물어보기 — `_save` 는 사용자의 조작마다 도는 자리이며 거기서
   묻는 것은 조작을 막는 일이다.
4. 창 합집합 (§1.5 가 배제했다 — 닫은 창이 되살아난다).
5. rev 검사를 느슨하게 하기 (D-3).

# 2.5.1 스냅숏 행 수 = termScrollback

## 목표

2.5 는 깨움 스냅숏의 기록 행 수를 서버 상수 5,000 으로 두었고, 2.9 는 브라우저 스크롤백을 설정 `termScrollback`(기본 5,000, 500~50,000)으로 바꿨다. 둘이 같아야 깬 터미널과 줄곧 깨어 있던 터미널의 기록이 같다(2.5 의 원래 근거). 서버가 설정을 읽어 스냅숏 행 수로 쓰거나 `term.open` 에 행 수를 싣는 쪽 중 단순한 쪽으로 맞춘다. 설정을 바꾸면 다음 깨움부터 반영.

## 완료 조건

- RED: 설정을 바꾸면 스냅숏 기록 행 수가 따라간다(단위 또는 e2e 하나). 바꾼 crate lib·fmt·clippy, 프론트 단위 전체, tsc. 전체 시험 금지.

## 진행 기록

### 2026-11-25 agent-pf-2-6 — review (브랜치 pf/2.6, 2.6 위에 이어서, **커밋 거절됨**)

**고른 쪽**: 서버가 설정을 읽는다(`term.open` 에 행 수를 싣지 않음). 설정 blob 은 이미 서버에 있고 `termHistoryLines` 를 같은 길로 읽는다 — 프로토콜·`ScreenFlights` 열쇠를 바꾸지 않아 더 단순하다.

**바꾼 것**

- 서버 `screen_config.rs`: `termScrollback` 서술자를 읽는 `parse_scrollback`, `Server::wake_history()`(스냅숏을 물을 때마다 blob 에서 읽음 — 바꾸면 다음 깨움부터). 표를 읽지 못하면 0(화면만) — 내장 자산이라 실제로는 일어나지 않는다. 서술자 읽기를 `spec(key)`·`parse(spec, blob)` 로 나눠 두 키가 함께 쓴다.
- `channel/screens.rs`: `ScreenFlights::get(hub, tool, history)`. 동시 깨움은 먼저 물은 쪽의 행 수를 쓴다. 상수 `WAKE_HISTORY` 를 지웠다.
- `term.rs`: 깨움·흐름 제어·틈의 스냅숏이 모두 `wake_history()` 를 쓴다.
- 브라우저 `term-pane.js` `wake()`: xterm 이 있으면 `term.options.scrollback = termScrollbackNow()` — 잠든 동안 설정을 바꾸면 깰 때 xterm 도 따른다(만들 때만 읽던 것).

**지운 것**: `WAKE_HISTORY`(5,000 상수).

**동작 변경**

| 무엇 | 이전 | 새 | 이유 |
|---|---|---|---|
| 스냅숏 기록 행 수 | 서버 상수 5,000 | 설정 `termScrollback`(기본 5,000, 500~50,000, 범위 밖은 기본값) | 깬 터미널과 줄곧 깨어 있던 터미널의 기록이 같아야 한다(2.5 근거, D-25) |
| 깬 xterm 스크롤백 | 만들 때의 설정 값 그대로 | 깰 때마다 지금 설정 값 | 설정을 바꾸면 다음 깨움부터 반영(D-M2-11) |

**남은 위험**

- LOW: 설정을 줄여도 이미 깨어 있는 터미널의 xterm 은 다음 깨움까지 옛 값이다(설계대로). 흐름 제어 스냅숏은 새 값으로 오므로 그 사이엔 xterm 이 더 적거나(잘림) 많은 줄을 받는다 — 화면은 같다.
- LOW: 50,000줄이면 스냅숏이 수 MB 다. 깨움 시간(NFR-PRF-14)은 5,000줄로만 쟀다(2.5). 2.10 재측정에서 큰 값도 재야 한다. 채널 상한 위험은 2.6 기록.

# SRS: 재연결 폭주의 종식과 끊긴 순간의 기록 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 하나다.

> **"한번씩 접근이 안돼. 테일스케일을 이용해서 원격으로 접속 중인데 한번씩 서버에
> 접속이 안되고 어쩔때는 ssh 를 이용해서도 접근이 안될 때가 있어."** → 이어서
> **"분석 다 됐으면 해결가능할까?"**

**원인은 확정되지 않았다.** 조사로 가설 넷을 기각했고
(`CONNECTIVITY_INVESTIGATION.md` §1), 남은 것은 이 머신에서 볼 수 없는 구간이다.
그리고 사용자가 밝힌 사실 하나가 이것을 더 좁힌다 — 끊길 때의 모양이 **"로딩 중
멈춤" 과 "연결 거부" 둘 다 있었다.** 둘은 다른 계층을 가리키므로 **원인이 하나가
아닐 수 있다.**

그래서 본 SRS 는 원인을 고치지 않는다. 두 가지를 한다.

1. **밝혀진 유일한 실제 결함을 없앤다** — 재연결 폭주. 그것이 원인이었는지도
   함께 가려진다 (묶음 A).
2. **끊긴 순간이 기록에 남게 한다.** 지금은 "끊겼다" 는 사실 자체가 아무 데도
   남지 않아, 다음에 겪어도 오늘과 같은 자리에 선다 (묶음 B).

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 폭주 종식 | 되풀이해 없는 도구를 부르는 연결을 **붙잡아 둔다.** 재연결의 계기 자체를 없앤다 |
| **B** 끊긴 순간의 기록 | 서버가 주기적으로 자기 상태를 한 줄 남긴다. 그 공백과 값이 원인을 가른다 |

**미포함:** §6 비목표. 특히 **원인의 수정**은 범위 밖이다 — 아직 모른다.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **미스** | 없는 도구 id 로 들어온 `/ws` 연결 |
| **되풀이 미스** | `MissRepeatWindow` 안에 같은 도구로 다시 온 미스 |
| **붙잡기 (hold)** | `OpExit` 을 보낸 뒤 소켓을 **닫지 않고** 두는 것. 닫지 않으면 클라이언트에 재연결의 계기가 서지 않는다 |
| **스냅샷** | 서버가 주기적으로 남기는 자기 상태 한 줄 |
| **공백** | 스냅샷은 이어지는데 요청 기록만 끊긴 구간 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 폭주는 줄었으나 멎지 않았다

`CONNECTIVITY_INVESTIGATION.md` §1.1 의 실측에 이어, 16:00~16:05 재측정:

| 지표 | 10:04 (최초) | 14:45 | 16:05 |
|---|---|---|---|
| 미스 유입 | 초당 ~95 | 초당 ~15 | **초당 ~3** |
| TIME_WAIT (:58146) | 2,881 | 164 | **92** |

FR-RCS-9 의 2초 지연이 규모를 30배 낮췄다. 그러나 **멎지는 않았다** — 옛 탭은
스스로 회복하지 않고 사람이 닫기 전까지 남는다.

**그리고 이 값은 가변적이다.** 죽은 도구와 열린 탭 수에 비례하므로 언제든 최초
관측치로 돌아갈 수 있다. 그때는 임시 포트(16,384)가 실제로 마른다.

### 2.2 왜 지금까지의 방어로는 멎지 않는가

`ws_miss.go` 는 되풀이 미스를 **2초 늦춘 뒤 `OpExit` 을 보내고 닫는다.** 닫는
순간 클라이언트의 `onclose` 가 서고, 그것이 `_scheduleReconnect` 의 유일한
계기다 (`term-pane.js:351·356`).

즉 **연결을 닫는 한 재연결은 반드시 다시 온다.** 지연은 주기를 늘릴 뿐 고리를
끊지 못한다.

**거절(upgrade 거부)은 더 나쁘다.** 거절하면 클라이언트는 즉시 다음 시도로 가고,
백오프가 자라지 못하는 옛 탭에서는 연결율이 **오히려 오른다.** TIME_WAIT 도 똑같이
쌓인다 — 거절한 연결도 닫힌 연결이다.

고리를 끊는 자리는 하나뿐이다: **닫지 않는 것.**

### 2.3 끊긴 순간은 아무 데도 남지 않는다

로그에 남는 것은 **온 요청**뿐이다 (`server.go:184`). 요청이 오지 않은 구간과
서버가 죽은 구간과 로그가 비어 있는 구간이 **기록상 구별되지 않는다.**

그래서 사용자가 "한번씩 안 된다" 고 말한 그 순간들에 대해 지금 우리가 아는 것은
아무것도 없다. 원인을 좁히려면 그 구간에 **서버가 무엇을 보고 있었는지**가
있어야 한다.

### 2.4 두 증상은 다른 계층을 가리킨다

사용자 확인: 끊길 때 **"로딩 중 멈춤"과 "연결 거부"가 둘 다 있었다.**

| 증상 | 뜻 | 가리키는 계층 |
|---|---|---|
| 로딩 중 멈춤 | TCP 는 섰는데 응답이 없다 | 서버 · 포트/자원 고갈 |
| 연결 거부 | 경로 자체가 없다 | Tailscale · 네트워크 |

**하나의 원인으로 둘을 다 설명하기 어렵다.** 그러므로 진단은 이 둘을 **가를 수
있어야** 하며, 그것이 묶음 B 의 설계 목표다 (FR-CNR-8).

---

### 2.5 hijack 된 뒤에는 컨텍스트가 절단을 알리지 않는다 (구현 중 실측)

묶음 A 를 처음 구현했을 때 붙잡기는 `r.Context()` 와 타이머만 기다렸다. 실제
서버(포트 58199)에 curl 로 미스를 여덟 번 보내고 **끊은 뒤** 스냅샷을 읽었다:

```
diag reqAge=37s wsAge=37s ws=4 tools=0 miss=1 hold=4 goroutines=18 allocMB=1
```

`hold=4` 가 그대로다. WebSocket upgrade 는 연결을 hijack 하며, 그 뒤로 `net/http`
는 그 연결을 관리하지 않으므로 **`r.Context()` 가 절단으로 취소되지 않는다.**

이대로면 닫힌 탭 하나가 10분씩 자리를 먹고, 상한 64 가 차면 붙잡기가 종전
동작으로 내려가 방어가 무력해진다. **읽기만이 절단을 알려준다** — FR-CNR-6 이
그래서 개정됐다.

> 이 사실은 묶음 B 가 없었으면 발견되지 않았다. 진단이 자기 자신의 첫 사용자가
> 된 셈이다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 A — 폭주의 종식

**FR-CNR-1.** `missTracker` 는 창 안의 **횟수**를 센다. 지금은 마지막 시각만
기억해 "되풀이인가" 만 답한다 — 임계를 두려면 횟수가 있어야 한다.

**FR-CNR-2.** 같은 도구의 미스가 `MissHoldAfter`(5회)를 넘으면, `OpExit` 을 보낸
뒤 **소켓을 닫지 않고 붙잡는다.** 클라이언트에 `onclose` 가 서지 않으므로
재연결의 계기가 사라진다 (§2.2).

**FR-CNR-3.** 붙잡기는 `MissHoldMax`(10분) 또는 요청 컨텍스트 종료 중 먼저 오는
것에서 끝난다. 서버 종료가 붙잡기에 발목잡히지 않아야 한다.

**FR-CNR-4.** 동시에 붙잡는 연결 수에 상한을 둔다 — `MissHoldLimit`(64). 넘으면
붙잡지 않고 **지금까지의 동작(지연 후 닫기)으로 내려간다.** 상한이 없으면 방어가
새로운 고갈이 된다.

**FR-CNR-5.** 첫 미스와 임계 이하의 되풀이 미스는 **지금과 같다** — `OpExit` 을
보내고 닫는다. 규약을 지키는 클라이언트는 그 한 번으로 판정을 끝내므로
(FR-RCS-1), 그들에게는 아무것도 바뀌지 않는다.

**FR-CNR-6 (개정).** 붙잡는 동안 서버는 그 연결에 아무것도 쓰지 않는다. **읽기는
한다 — 읽되 버린다.** 연결이 끊기면 그 즉시 붙잡기를 푼다.

> **처음에 이 조항은 "읽지도 않는다" 였고, 그것은 틀렸다.** 구현 후 실측에서
> 드러났다 (§2.5) — upgrade 로 hijack 된 뒤에는 `r.Context()` 가 클라이언트
> 절단으로 취소되지 **않는다.** curl 이 끊은 뒤에도 스냅샷의 `hold=4` 가 그대로
> 남았다. 읽기만이 절단을 알려주므로, 읽지 않으면 닫힌 탭이 10분씩 자리를 먹고
> 상한(64)이 차서 방어가 무력해진다.

**FR-CNR-7.** 붙잡기가 시작·종료될 때 로그를 남긴다. 이 방어가 언제 몇 개를
붙잡고 있었는지가 §2.1 의 지표와 함께 읽혀야 한다.

### 3.2 묶음 B — 끊긴 순간의 기록

**FR-CNR-8.** 서버는 `DiagSnapshotEvery`(60초)마다 자기 상태를 **한 줄** 남긴다.
그 줄은 §2.4 의 두 증상을 가를 수 있어야 한다 — 최소한 아래를 담는다.

| 항목 | 왜 |
|---|---|
| `reqAge` | 마지막 HTTP 요청 이후 흐른 초. **공백을 만드는 것이 이 값이다** |
| `wsAge` | 마지막 WS 연결 이후 흐른 초 |
| `ws` | 지금 붙어 있는 WS 수 |
| `tools` | 살아 있는 도구 수 |
| `miss` · `hold` | 미스 추적 중인 도구 수, 붙잡고 있는 연결 수 (묶음 A 의 지표) |
| `goroutines` · `allocMB` | 서버 자신의 부하 |

**FR-CNR-9.** 스냅샷은 **값이 변하지 않아도 남긴다.** 변할 때만 남기면 조용한
구간이 로그에서 사라지고, 그 조용함이 곧 우리가 찾는 증거다.

**FR-CNR-10.** 스냅샷은 `shouldLogRequest` 의 필터를 타지 않는다 — 그것은 요청
로그의 규칙이고 이것은 요청이 아니다.

**FR-CNR-11.** 마지막 요청 시각은 **모든** HTTP 요청이 갱신한다. 핫패스 필터로
로그에서 빠지는 `/api/ping` 도 포함이다 — 로그에 안 남는 것과 오지 않은 것은
다르며, 그 차이가 이 기능의 전부다.

**FR-CNR-12.** 스냅샷은 서버 수명과 함께 시작하고 끝난다. 고루틴 하나이며 종료
시 정리된다.

## 4. 설계 결정 (Design Decisions)

| # | 결정 | 근거 |
|---|---|---|
| **D-1** | 붙잡되 거절하지 않는다 | RECONNECT_STORM D-6 은 "바르게 행동하는 쪽을 망가뜨려 잘못 행동하는 쪽을 막지 않는다" 였다. 붙잡기는 `OpExit` 을 **여전히 보내므로** 그 결정을 뒤집지 않는다. 거절은 그것을 뒤집으면서 효과도 없다 (§2.2) |
| **D-2** | 닫지 않는 것이 유일한 수단이다 | `onclose` 가 재연결의 유일한 계기다. 지연은 주기를 늘릴 뿐이고 거절은 주기를 줄인다 |
| **D-3** | 임계 5회 · 10분 · 64개 | 임의의 값이다. 5회면 규약을 지키는 클라이언트가 지날 일이 없고, 10분이면 사람이 탭을 닫을 시간이며, 64개면 탭 수의 현실적 상한이다. **상한이 있다는 것이 값보다 중요하다** |
| **D-4** | 스냅샷은 로그로 남긴다 | 새 저장소를 만들지 않는다. 로그는 이미 로테이션이 있고(선행 커밋), 사후에 읽는 것이 목적이므로 조회 종단이 필요 없다 |
| **D-5** | Tailscale 상태를 서버가 묻지 않는다 | 외부 명령을 60초마다 부르는 비용이 얻는 것보다 크다. `reqAge` 의 공백이 이미 "경로가 있었는가" 를 답한다 |
| **D-6** | 원인을 고치지 않는다 | 모르기 때문이다. 추측으로 고치면 다음에 재발했을 때 무엇이 원인이 아니었는지도 알 수 없게 된다 |

## 6. 비목표 (Non-goals)

- **원인의 수정.** 아직 모른다 (D-6). 본 SRS 는 원인 후보 하나를 제거하고, 다음
  발생 때 원인이 확정되도록 준비한다.
- **Tailscale·네트워크 계층의 설정 변경.** `RECONNECT_STORM_SRS` §1.2 와 같다.
- **옛 탭의 원격 종료.** 서버가 클라이언트를 새로고침시킬 수단은 없다. 붙잡기는
  그 탭을 **조용하게** 만들 뿐이며, 그것으로 충분하다.
- **진단의 조회 종단·UI.** 사후에 로그를 읽는 것이 목적이다 (D-4).
- **접근 경로의 이중화.** 사용자가 이번 범위에서 고르지 않았다.

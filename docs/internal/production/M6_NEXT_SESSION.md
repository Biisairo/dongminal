## M6 의 목표는 "flaky 수정" 이 아니다

로드맵이 목표를 재서술했고 그 근거가 §M6 머리말에 있다. 요약하면:

  1차 감사(`TEST-5`)는 "flaky 아홉 건이 모두 관측 → 전체 재렌더 → DOM 교체라는
  동일 기전" 이라 판정했다. `11 §5` 가 9건을 코드로 매핑해 **그 판정이 절반만
  맞다**는 것을 확인했다 — 기전은 **셋**이고, **9건 중 8건이 제품 결함으로
  설명된다.** "테스트가 취약한 것" 이 아니다.

그래서 **가장 먼저 할 것은 낙관적 레이아웃 보호**다 (`_onWorkspaceChanged` 가
아직 저장되지 않은 로컬 레이아웃 변경을 덮지 않게). **flaky 5~6건이 거기서
닫힌다.** `app.js:531-556` 이 이미 rev 비교로 절반을 하고 있다.

**`fixtures.ts` 의 "재렌더는 앱의 정상 동작이므로 견디는 쪽은 테스트다" 는
근거가 없다** — git 관측은 `render()` 를 부르지 않는다(`app-git.js:610`).
탭이 사라지는 진짜 이유는 워크스페이스 재채택이고, 그것은 정상 동작이 아니다.

## M5 가 남긴 것 — 지금 쓸 수 있는 것

이번 마일스톤이 **진단 도구를 만들었다.** M6 은 그것을 처음 쓰는 마일스톤이다.

  · **요청 ID** — 응답 헤더 `X-Request-Id`. 접근 로그·핸들러 로그·데몬 RPC 로그가

    헤더에서 ID 를 집어 서버 로그를 보면 그 요청이 무엇을 했는지 전부 나온다
  · **`DONGMINAL_LOG_LEVEL=debug`** — 데몬 RPC 줄이 그때만 나온다. 상관관계를
    쫓을 때 켠다

  · **`X-Error-Code`** — 모든 오류 응답의 코드. e2e 가 "실패했다" 대신
    **"무엇으로 실패했다"** 를 단언할 수 있다. 뜻은 `docs/external/errors.md`
  · **`.lastexit`** — 비정상 종료 판정. `doctor --bundle` 이 담는다
  · **`scripts/perf-probe.sh`** — `GP-7`(1초마다 `git status`)의 **before/after 를

## 흔들림 — 목록을 물려받지 마라

전량을 **일곱 번** 쟀고 **일곱 번 다 다른 목록**이 나왔다. M5 의 마지막 실행은
`git-console` K2 하나가 실패했고 **단독으로는 7/7 통과**했다.

**그러나 M6 은 그 태도를 바꾸는 마일스톤이다.** 지금까지는 "쫓지 마라" 가 맞았다 —
근거가 없었기 때문이다. `11 §5` 가 **9건을 코드로 매핑했으므로** 이제는 근거가
있고, 그 8건은 쫓을 대상이다.

가르는 법: **`11` 이 매핑한 9건인가**. 그 목록에 있으면 제품 결함이고, 없으면
종전대로 단독 재현으로 가린다.

### 매핑 표에 **한 건이 빠져 있다** — `GP-10` 은 스펙이 둘이다 (2026-09-12 확인)

`11 §5` 표는 `GP-10` 의 증상을 **`git-console` K2 하나로** 적어 두었다. 그런데
CI 에서 같은 기전이 **다른 스펙**을 무너뜨렸다:

```
e2e/git-view-refresh.spec.ts:197
  G3 (V-GVR-3 / FR-GVR-1·2): push 뒤 Console 맨 위에 그 명령이 있다
  → unexpected value "git stash list --format=%gd%x00%H%x00%gs%x00%ct%x00"
```

K2 와 G3 은 **같은 단언**(“Console 맨 위”)이고, 관측마다 끼어드는 `stash list` 가
그 자리를 가로챈다 — `core/write.go:52` · `write/stash.go:103` ·
`panel-poll.js:157`, 표의 1번 그대로다.

**대조할 자리는 셋이다.** `grep -rn "git-con-argv" e2e/` 가 그 목록이며, 지금
이렇다:

| 자리 | 무엇을 단언하나 |
|---|---|
| `git-console.spec.ts:27` (`argvs` 헬퍼) | K2 를 포함한 Console 목록 검사들 |
| `git-view-refresh.spec.ts:214` | **G3** — push 뒤 맨 위가 `git push` |
| `git-view-refresh.spec.ts:260` | **G5** — 실패한 push 뒤 맨 위가 `git push` |

K2 만 보고 닫으면 나머지 둘이 남는다.

**그리고 기존 완화가 듣지 않는다는 것이 중요하다.** `git-view-refresh` 의 두
검사는 이미 `stopConsolePoll(page)` 를 부르고 있는데도 G3 이 무너졌다. 즉 끼어든
`stash list` 는 **Console 폴링이 아닌 경로**에서 왔다 — 표가 지목한
`_reloadViews` 다. 고칠 때 이 사실이 판별자다: 폴링을 멈춰도 남으면 `GP-10` 이고,
멈춰서 사라지면 다른 것이다.

같은 회차에 `git-console` K2 도 로컬 전량에서 flaky 로 잡혔고, 다음 회차의 CI
에서는 **G3 이 통과했다.** 간헐이라는 사실 자체가 표의 판정(제품 결함)과 어긋나지
않는다 — 관측 시점과 단언 시점의 경주다.

## 착수 전제가 바뀌었다 — 터미널 재접속 (2026-09-12)

M6 착수 **직전에** 접수된 렌더 결함을 닫았다 (`TERMINAL_RESUME_SRS`, 커밋
`fix(term): 재접속은 이어 붙이는 것이지 다시 뿌리는 것이 아니다`). M6 이 알아야
할 것만 적는다.

  · **WS 프로토콜에 op 가 하나 늘었다** — `OpSeq`(`0x04`), 9바이트
    (오프셋 8 BE + 전량재생 플래그 1). `/ws` 에 `since=` 질의가 생겼다.
    `docs/external/api.md` §WebSocket 이 정본이다
  · **재접속이 더 이상 스크롤백을 되뿌리지 않는다.** `since` 가 보유 창 안이면
    델타만 오고 화면을 지우지 않는다. 창 밖·최초 접속만 전량 재생이며 그때는
    화면·스크롤백을 먼저 지운다
  · **e2e 의 타이밍이 바뀌었다.** 서버가 프레임을 하나 더 보내므로, "응답이 없어
    타임아웃할 때까지 기다린다" 로 쓰인 검사는 **일찍 끝난다.** 그 대기에
    기대고 있던 것이 하나 있었고(아래) M6 에서 또 나올 수 있다

### 그 작업이 드러낸 것 셋 — M6 이 같은 함정을 밟는다

  1. **`Tool.resize` 와 종료가 같은 fd 를 두고 겹쳤다.** `pty.Setsize` 가 지나는
     `os.File.Fd()` 는 참조 계수를 우회한다 — `Read`·`Write` 와 달리 이 경로만
     보호가 없었다. `TestHandleWS_OpResize` 가 500ms 타임아웃을 기다리는 동안
     우연히 안전했고, 프레임이 하나 늘어 그 대기가 사라지자 `-race` 에서 매번
     났다. `tmu`+`termClosed` 로 좁게 막았다 (`toolhub/tool.go`)
  2. **`-shuffle=on` 이 뽑는 순서에 따라 아홉이 함께 무너졌다.**
     `captureLog` 가 표준 `log` 만 가로챘는데, 같은 패키지의 `reqid_test.go` 가
     `dmlog.Init` 를 부르므로 **그 검사가 먼저 도는 순서에서는** 출력이 slog 로
     빠져 버퍼가 내내 비었다. 원인이 파일 밖이라 읽어서는 보이지 않는다.
     **CI 가 `-shuffle=on` 이므로 이것이 기존 간헐 실패의 한 축이었다.**
     로그를 읽는 검사를 새로 쓰면 `dmlog` 계층을 버퍼 위에 세워라
  3. **golangci-lint 의 패키지 분석 캐시가 지적을 덮는다.** 무관한 변경이 어느
     패키지의 캐시를 무효화하면 그 패키지 몫이 **그때** 튀어나온다. 직전 main 이
     "found no issues" 였다고 해서 깨끗한 것이 아니다 — `dmlog.Infof(nil, …)`
     177곳의 `SA1012` 가 그렇게 숨어 있었고, `.golangci.yml` 에 `dmlog.` 줄만
     제외하는 규칙을 세워 정리했다 (근거는 그 파일의 주석)

### e2e 를 새로 쓸 때 — 이번에 물린 것 둘

  · **셸 문법을 쓰지 마라.** Windows 의 셸은 PowerShell 이고
    `for i in …; do …; done` 을 파싱하지 못한다. `echo` 한 줄은 두 셸이 같이
    받는다 — 기존 스펙들이 전부 그 형태인 데는 이유가 있다
  · **커서 칸의 공백을 글자로 세지 마라.** `translateToString(true)` 는 한 번도
    쓰이지 않은 칸만 걷어내므로 커서가 써 놓은 공백은 남는다. ConPTY 는 그 한
    칸을 달리 남긴다 — 화면을 견주려면 줄 끝 공백을 정규화하라

## M6 착수 직전에 끼어든 일 (2026-09-12)

사용자가 접수한 렌더 결함 때문에 M6 **앞에** 한 마일스톤 크기의 작업이 들어갔다.
본문 §"착수 전제가 바뀌었다" 가 M6 이 알아야 할 것을 추린 것이고, 여기는 기록이다.

| 커밋 | 무엇을 |
|---|---|
| `fix(term)` | `TERMINAL_RESUME_SRS` FR-TRS-1~21 — 재접속 델타 재개, 전량 재생 멱등화, 앞머리 정렬, 겹침 제거, 재그리기 넛지. 곁가지로 `resize`/종료 fd 경쟁과 `captureLog` 순서 의존 |
| `chore(lint)` | `SA1012` 을 `dmlog` 호출 줄에서만 제외 (탐침으로 다른 자리 검출 확인) |
| `fix(e2e)` | Windows 러너 대응 — PowerShell 문법, 커서 칸 공백 |

**원인 요약.** WS 가 붙을 때마다 서버가 스크롤백 전량을 되뿌리는데 받는 쪽 xterm
은 재접속 너머로 살아남아 그 내용을 이미 가지고 있었다. 실측: WS 연결 916 회에
스냅샷 송신 898 회, claude 를 띄운 도구는 매번 1 MiB 전량.

**검증.** `make gates` · `go test -race -shuffle` 시드 4종 · `npm run
lint/typecheck/unit` · 로컬 전량 e2e 1553 통과 · CI `verify` 전체 초록.

**e2e 가 화면이 아니라 수신량을 재는 이유**를 남겨 둔다 — 평범한 셸로는 증상이
재현되지 않는다. 옛 코드로 세 번 끊었다 붙이면 2,256 바이트가 다시 왔는데 화면은
108 자 그대로였다(되뿌린 것에 섞인 커서 이동이 같은 자리를 덮는다). 증상은 TUI 의
1 MiB 스크롤백에서 나오고, 그것을 e2e 에 세우는 것은 무겁고 흔들린다. **다시 받지
않으면 겹쳐 그릴 수도 없다** — 그 상위 성질을 재면 증상의 크기와 무관하게
결정적이다.

**M6 로 넘기는 것 하나**: `GP-10` 이 `git-view-refresh` G3 도 무너뜨린다는 사실
(본문 §"매핑 표에 한 건이 빠져 있다"). 그것은 M6 착수 순서 ② 의 일이므로
여기서 손대지 않았다.

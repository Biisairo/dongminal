# SRS: 새 판이 나온 것을 사용자가 **묻지 않아도** 알게 한다 — IEEE 29148

> **문서 상태**: 승인·구현완료

> **이 문서는 기존 결정을 뒤집는다.** `M5 G3-3` 은 "묻지 않으면 나가지 않는다"
> 였다. 이 SRS 는 그것을 "**기본으로 확인하되 끌 수 있고, 끈 것이 실제로
> 네트워크를 막는다**" 로 바꾼다. 근거와 대가는 §2.2 에 적는다.

---

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

`dongminal update --check` 는 이미 있다. 최신 태그를 읽고, semver 로 견주고,
새 판이면 그렇게 말한다 (`internal/ctl/cli/update.go`). **문제는 그것을 아무도
치지 않는다는 것이다.**

업데이트 확인은 사용자가 필요를 느끼는 순간이 없는 종류의 일이다. 필요를 느끼는
때는 이미 늦은 때다 — 고쳐진 결함을 여전히 맞고 있거나, 공지된 취약점이 자기
판에 해당하는 것을 모르고 있을 때다. 이 저장소는 그 일을 이미 한 번 겪었다:

> `d306f7b docs(security): 고쳐진 취약점을 공지로 남긴다 — 릴리스된 판이 해당한다`

공지를 남겨도, 그 공지에 닿는 경로가 "사용자가 스스로 명령을 친다" 하나뿐이면
공지는 도착하지 않는다. **이 SRS 는 도착 경로를 만든다.**

### 1.2 불변 조항 (Invariant) — 이 문서의 유일한 결론

> **끈 것은 실제로 나가지 않아야 한다.**

기본을 켜는 대신 이 조항을 진다. 토글이 표시만 감추고 뒤에서 네트워크를 계속
쓰면, 그것은 기능이 아니라 거짓말이다. 설계가 갈릴 때 판정 기준은 "사용자가 끈
상태에서 소켓이 열리는가" 다 — 열리면 그 설계는 틀렸다.

### 1.3 범위 (Scope)

**포함**: 서버의 확인(기동 · SSE 연결 · 24시간 타이머 · 토글 켬) · 메모리 캐시 ·
`GET/PUT /api/update` · SSE `update_changed` · 웹 상태바 배지 · 설정 페이지 토글 ·
`server.json` 의 진실값 · 환경변수 킬스위치 · 기존 문서 개정.

**제외**: §6 비목표.

### 1.4 용어 (Definitions)

| 용어 | 뜻 |
|---|---|
| **확인(check)** | GitHub Releases API 에 최신 태그를 묻는 1회 네트워크 왕복 |
| **안내(notice)** | 확인 결과 "새 판 있음" 을 사용자 화면에 보이는 것 |
| **판(version)** | `internal/ctl/cli.Version` 에 주입된 릴리스 태그. 주입 없으면 `dev` |
| **토글** | 확인을 켜고 끄는 사용자 조작. 진실값은 `server.json` 에 산다 |
| **캐시** | 마지막 확인 결과를 담은 **메모리** 한 칸. 프로세스와 함께 나고 죽는다 |
| **트리거** | 캐시를 갱신하는 계기. 트리거가 오면 확인이 돈다 |

## 2. 전체 설명 (Overall Description)

### 2.1 지금 있는 것

| 자리 | 사실 |
|---|---|
| `internal/ctl/cli/update.go` | `--check` 옵트인. GitHub API 1회. 5초 타임아웃. 내려받지 않음 |
| `internal/ctl/cli/update.go:versionNewer` | semver 3자리 비교. `v1.10.0 > v1.9.0` 을 올바로 판정 |
| `internal/ctl/cli/version.go:20` | `var Version = "dev"` — ldflags 주입 |
| `internal/shared/serverconf/conf.go` | `server.json` 은 `host·port·logLevel·logFile` 넷 |
| `internal/webserver/httpreq/body.go:13` | `PUT /api/settings` 는 **JSON 인지도 보지 않고** 저장 |
| `internal/webserver/httpapi/static.go:115` | CSP `connect-src 'self' ws: wss:` |
| `web/js/core/app-statusbar.js` | 상태바. `/api/stats`·`/api/ping` 를 주기 폴링 |

### 2.2 이전 동작 / 새 동작 / 이유

**이전 동작** — `dongminal update --check` 를 사람이 직접 칠 때만 확인한다.
치지 않으면 제품은 자기 판이 낡았다는 것을 영원히 모른다.

**새 동작** — 서버가 최신 판을 메모리에 **캐시**한다. 그 캐시를 갱신하는 계기는
넷이다: 서버 기동 · 브라우저의 SSE 연결 수립(새로고침·끊겼다 붙음이 모두 여기로
온다) · 마지막 확인으로부터 24시간 타이머 · 토글 끔→켬. 새 판이면 웹 상태바에
배지가 뜬다. 사용자는 설정 페이지에서 끌 수 있고, 끄면 확인 자체가 돌지 않는다.

**타이머는 보조다.** 갱신의 주된 계기는 사용자가 화면을 여는 순간이다 — 새로고침,
재접속, 서버 재기동. 사람이 화면을 여는 그때가 안내를 볼 수 있는 유일한 때이므로,
그때 캐시를 새로 채우는 것이 가장 정직하다. 24시간 타이머는 **한 번도 끄지 않고
띄워 둔 세션**만을 위한 것이다 — 그런 세션은 위 셋 중 아무것도 오지 않는다.

**이유** — 종전 원칙("묻지 않으면 나가지 않는다")이 지키려던 것은 *사용자가
통제하지 못하는 트래픽을 만들지 않는다* 였다. 그 목적은 **옵트아웃으로도 지켜진다** —
끌 수 있고, 끈 것이 실제로 멎고, 그 사실을 처음에 알리면 통제는 사용자에게 있다.
반면 옵트인이 치른 대가는 회수되지 않았다: 켠 사람이 없어서 기능이 도달하지
않았고, 보안 공지가 그 실패의 실증이다.

**대가** — 기본 켜짐은 사용자가 아무것도 하지 않아도 이 제품이 한 번은 밖으로
나간다는 뜻이다. 그래서 `FR-UPD-10`(첫 고지)과 `FR-UPD-11`(킬스위치)이 이
변경의 조건부다. 둘 없이 기본만 켜는 것은 이 SRS 가 승인하지 않는다.

### 2.3 제약 (Constraints)

| ID | 제약 | 출처 |
|---|---|---|
| C-1 | 브라우저는 `api.github.com` 에 직접 못 나간다 | CSP `connect-src 'self' ws: wss:` (`static.go:115`) |
| C-2 | 서버는 브라우저 설정 블롭을 런타임에 해석하지 않는다 | `D-CFG-1` |
| C-3 | `server.json` 은 브라우저 블롭 값을 받지 않는다 | `D-CFG-5` |
| C-4 | 설정 파일이 깨져도 기동을 막지 않는다 | `FR-CFG-15` / `D-CFG-3` |
| C-5 | 설정 블롭의 키는 `web/js/core/settings-schema.js` 가 단일 원천 | `FR-CFG-2`·`FR-CFG-10` |

**C-1 이 주체를 정한다.** 브라우저가 스스로 확인하려면 CSP 를 뚫어야 하고, 그것은
배지 하나를 위해 XSS 방어면을 넓히는 거래다. 서버가 확인한다.

**C-2·C-3 이 토글의 자리를 정한다.** §4 `D-UPD-2` 참조.

## 3. 구체 요구사항 (Specific Requirements)

### 3.1 기능 요구사항 — 확인 (Check)

| ID | 요구사항 |
|---|---|
| **FR-UPD-1** | 서버는 토글이 켜져 있을 때 최신 릴리스를 확인한다. 확인 주체는 서버 프로세스 단 하나다 — 브라우저 창이 몇 개든 확인 횟수는 늘지 않는다 |
| **FR-UPD-2** | 캐시를 갱신하는 트리거는 넷이다: **①** 서버 기동 **②** 브라우저의 SSE 연결 수립 **③** `마지막 확인 + 24시간` 타이머 **④** 토글 끔→켬. **트리거가 오면 확인한다** — 통과 조건을 따로 두지 않는다 |
| **FR-UPD-2a** | 트리거 ② 는 새로고침과 재연결을 **함께** 덮는다. 둘 다 SSE 연결 수립이며, 그 둘을 따로 세는 코드를 두지 않는다 (`D-UPD-7`) |
| **FR-UPD-2b** | 확인은 **single-flight** 다. 진행 중인 확인이 있으면 새 트리거는 그 결과에 합류하고, 두 번째 요청을 만들지 않는다. 창 넷을 한꺼번에 새로고침해도 요청은 1건이다 |
| **FR-UPD-2c** | 타이머는 확인이 끝날 때마다 `마지막 확인 + 24시간` 으로 **다시 건다**. 트리거가 무엇이었든 같다 — 방금 새로고침으로 갱신했다면 타이머도 거기서 다시 센다 |
| **FR-UPD-2d** | 캐시는 **메모리에만** 산다. 프로세스가 죽으면 함께 죽고, 다음 기동이 트리거 ① 로 다시 채운다 (`D-UPD-9`) |
| **FR-UPD-2e** | 확인 실패는 캐시를 **바꾸지 않는다**. 직전 결과가 있으면 그대로 남고, 없으면 "모름" 이다. 다음 트리거에 자연히 다시 시도된다 |
| **FR-UPD-3** | 확인은 기동도 SSE 연결도 막지 않는다. 별도 고루틴에서 돌고, 실패해도 서버 상태에 영향이 없다 |
| **FR-UPD-4** | 확인 실패는 **조용하다**. 사용자 화면에 오류를 띄우지 않고, 로그에 한 줄 남긴다. 망이 없는 것은 사용자가 할 일이 아니다 |
| **FR-UPD-5** | 확인은 기존 `fetchLatest`·`versionNewer`·`semverParts` 를 **재사용한다**. 판정 로직을 두 벌로 만들지 않는다 |
| **FR-UPD-6** | 확인 타임아웃은 기존 `updateTimeout`(5초)을 따른다 |

### 3.2 기능 요구사항 — 안내 (Notice)

| ID | 요구사항 |
|---|---|
| **FR-UPD-7** | `GET /api/update` 는 마지막 확인 결과를 돌려준다: 지금 판 · 최신 판 · 새 판 여부 · 릴리스 링크 · 마지막 확인 시각 · 토글 상태 |
| **FR-UPD-8** | `GET /api/update` 는 **네트워크에 나가지 않는다**. 캐시만 읽는다. 확인을 거는 자리는 트리거 넷이지 이 핸들러가 아니다 — 배지를 읽는 것과 캐시를 채우는 것은 다른 일이다 |
| **FR-UPD-8a** | 확인 결과가 **바뀌었을 때만** SSE 로 `{"action":"update_changed"}` 를 브로드캐스트한다. 브라우저는 그것을 받고 `GET /api/update` 를 다시 읽는다 — `tools_background_changed` 와 같은 규약이다 |
| **FR-UPD-8b** | 결과가 그대로면 브로드캐스트하지 않는다. 하루에 한 번 바뀌는 값이 매 연결마다 방송되면 그것은 소음이다 |
| **FR-UPD-9** | 웹 상태바는 "새 판 있음" 일 때만 배지를 띄운다. 배지는 릴리스 링크로 연결된다. 최신이거나 확인 실패이거나 꺼져 있으면 **아무것도 보이지 않는다** |
| **FR-UPD-9a** | 배지 조회는 페이지 로드 1회 · 토글 변경 1회 · `update_changed` 수신 1회다. **주기 폴링을 새로 만들지 않는다** |
| **FR-UPD-9b** | 지금 판이 `dev` 이거나 비어 있으면 배지를 띄우지 않는다. 견줄 기준이 없는 것을 "뒤졌다" 로 말하면 거짓이다 (`update.go` 의 기존 판정과 같다) |

### 3.3 기능 요구사항 — 통제 (Control)

| ID | 요구사항 |
|---|---|
| **FR-UPD-10** | 서버는 **최초 1회** 확인 사실을 고지한다. `dongminal start` 출력에 한 줄 — 무엇을 하는지, 어디로 나가는지, 어디서 끄는지. 고지했다는 사실은 `server.json` 옆에 표식으로 남겨 반복하지 않는다 |
| **FR-UPD-11** | `DONGMINAL_NO_UPDATE_CHECK=1` 이면 확인이 돌지 않는다. **다른 모든 계층을 이긴다.** 에어갭·CI 환경과 검사의 결정론성이 이 한 줄에 달린다 |
| **FR-UPD-12** | 진실값은 `server.json` 의 `updateCheck` (bool, 기본 `true`) 다 |
| **FR-UPD-13** | `PUT /api/update` 는 토글을 바꾸고 `server.json` 에 기록한다. **설정 블롭에 쓰지 않는다** |
| **FR-UPD-14** | 토글 변경은 **재기동 없이** 즉시 반영된다. 끄면 타이머가 풀리고 진행 중인 확인의 결과를 버린다. 켜면 즉시 1회 확인한다 (트리거 ④) |
| **FR-UPD-15** | 설정 페이지에 체크박스를 둔다. 사용자에게는 설정이 한 곳이다 — 저장 경로가 둘인 것은 내부 사정이며 화면에 새지 않는다 |
| **FR-UPD-16** | `server.json` 의 `updateCheck` 가 bool 이 아니면 **기본값으로 떨어지고 경고만 낸다**. 기동을 막지 않는다 (C-4) |
| **FR-UPD-17** | `dongminal update --check` 는 **그대로 남는다**. 주기 확인과 무관하게 언제든 즉시 확인할 수 있다. 토글이 꺼져 있어도 이 명령은 돈다 — 사람이 직접 친 것은 언제나 사용자의 의사다 |

## 4. 결정 (Decisions)

| ID | 결정 | 근거 |
|---|---|---|
| **D-UPD-1** | 확인은 **서버가** 한다. 브라우저가 아니다 | CSP `connect-src 'self'` 를 배지 하나로 넓히는 거래는 성립하지 않는다. 창이 열이어도 확인 주체는 하나다 |
| **D-UPD-2** | 토글의 진실값은 **`server.json`** 이다. 설정 블롭이 아니다 | 블롭에 두면 서버가 블롭을 파싱해야 하고 D-CFG-1 이 그 자리에서 끝난다. 이 값은 표시 취향이 아니라 "프로세스가 밖으로 나갈지" 이며 서버만 집행할 수 있다 |
| **D-UPD-3** | 설정 UI 는 **한 곳**, 저장 경로는 **둘** | 화면의 통일과 저장소의 분리는 충돌하지 않는다 — 충돌한다고 보는 순간 둘 중 하나를 잘못 접는다 |
| **D-UPD-4** | 배지는 **폴링하지 않는다.** 바뀔 때 밀어 준다 | 하루 한 번 바뀌는 값을 3초 주기에 얹으면 28,800배의 낭비이고 `/api/stats` 의 책임을 흐린다 |
| **D-UPD-5** | 여전히 **내려받지 않는다** | 설치 형태가 여럿이라(빌드·릴리스 산출물·패키지 매니저) 자기 바이너리를 덮으면 패키지 관리자와 싸운다. 이 SRS 가 바꾸는 것은 "언제 확인하는가" 뿐이다 |
| **D-UPD-6** | 고지는 **한 번**이고, 표식은 `server.json` 의 키 자체다 | 매번이면 소음, 한 번도 없으면 몰래 나간 것이 된다. 표식을 따로 두면 그 둘이 어긋날 때 진실을 말할 수 없다 |
| **D-UPD-7** | 새로고침과 재연결을 **따로 세지 않는다** | 코드에서 그 둘은 같은 사건(SSE 연결 수립)이다. 두 이름을 가진 하나의 훅을 둘로 나누면 나중에 한쪽만 고쳐진다 |
| **D-UPD-8** | **낡음 가드를 두지 않는다** — 트리거가 오면 확인한다 | 가드를 씌우면 낡음 기준·시각 영속·실패 시각 분리·백오프 넷이 따라 들어온다. 배지 하나에 그 넷은 균형이 맞지 않는다. 대가(rate limit 403)는 조용히 실패하고 다음 트리거에 복구된다 |
| **D-UPD-9** | 캐시는 **메모리에만** 산다 | 재기동 자체가 트리거 ① 이라 이어 줄 값이 없다. 파일·경로·깨진 파일 처리와 그 검사를 없는 값을 위해 두는 셈이다 |

아래는 위 표의 근거를 푼 것이다.

### D-UPD-1 — 확인은 서버가 한다

브라우저가 아니다. 근거는 C-1 이다. CSP 의 `connect-src 'self'` 를 배지 하나
때문에 넓히는 것은 방어면을 영구히 늘리고 얻는 것은 임시다. 부수 효과도
서버 쪽이 낫다 — 창이 열 개여도 확인은 하루 한 번이다.

### D-UPD-2 — 토글의 진실값은 `server.json` 이다. 설정 블롭이 아니다

**설정 블롭에 두면 `D-CFG-1` 이 깨진다.** 서버가 그 키를 읽으려면 블롭을
파싱해야 하고, `PUT /api/settings` 가 "받은 바이트를 JSON 인지도 보지 않고
저장한다"(`httpreq/body.go:13`)는 계약이 그 자리에서 끝난다. 키 하나의 편의로
그 경계를 여는 거래는 성립하지 않는다.

**그러면 `D-CFG-5` 는 어떻게 되는가.** `D-CFG-5` 가 금지한 것은 *브라우저 블롭의
값*을 `server.json` 으로 옮기는 것이다 — 그건 D-CFG-1 을 뒷문으로 뒤집는 짓이기
때문이다. `updateCheck` 는 그 부류가 아니다. 이것은 브라우저의 표시 취향이 아니라
**서버 프로세스가 밖으로 나갈지 말지**이고, 서버 말고는 집행할 주체가 없다.
블롭에 두는 쪽이 오히려 D-CFG-1 위반이다. 이 키의 자리는 `server.json` 이 유일하다.

### D-UPD-3 — 설정 UI 는 한 곳, 저장 경로는 둘

사용자는 설정 페이지에서 켜고 끈다. 그 체크박스만 `PUT /api/settings` 가 아니라
`PUT /api/update` 로 간다. **화면의 통일과 저장소의 분리는 충돌하지 않는다** —
충돌한다고 보는 순간 둘 중 하나를 잘못 접는다.

### D-UPD-4 — 배지는 폴링하지 않는다. 바뀔 때 밀어 준다

하루에 한 번 바뀌는 값이다. `_pollStats` 에 얹으면 3초마다 묻게 되고, 그건
28,800배의 낭비이자 `/api/stats` 의 책임을 흐린다. 페이지 로드 1회로 읽고,
그 뒤에 값이 바뀌면 SSE 가 `update_changed` 로 알린다 (`FR-UPD-8a`).

이 조합이 "새로고침 때 확인" 의 어색함도 푼다. 연결 훅이 확인을 **걸어 두고**
곧바로 돌아오므로 연결은 지연되지 않고, 확인이 끝나 결과가 바뀌면 그때
브로드캐스트가 배지를 세운다. **기다리지 않고도 그 자리에서 보인다.**

### D-UPD-7 — 새로고침과 재연결을 따로 세지 않는다

사용자의 말은 "새로고침하거나 세션 끊겼다가 연결될 때" 였다. 코드에서 그 둘은
같은 사건이다 — 둘 다 `handleCommandSSE` 의 연결 수립이다. 이 저장소가 이미
그렇게 쓰고 있다 (`focus.go:28`, `handlers_attention.go:287`,
`handlers_runs_headless.go:116` 이 모두 "SSE 재연결로 정렬" 이라 적는다).
**두 이름을 가진 하나의 훅을 둘로 나누면, 나중에 한쪽만 고쳐진다.**

### D-UPD-8 — 확인을 거르지 않는다. 단순함을 사고 요청 몇 건을 낸다

트리거에 "낡았니?" 가드를 씌우면 요청은 줄지만, 그 대가로 **낡음 기준 · 시각
영속 · 실패 시각 분리 · 백오프** 넷이 따라 들어온다. 배지 하나를 세우는 일에 그
넷을 들이는 것은 균형이 맞지 않는다. 트리거가 오면 확인한다 — 코드도, 이 문서도,
검사도 그만큼 짧아진다.

**대가는 명시한다.** GitHub 비인증 API 는 IP당 시간 60건이다. 한 시간에 60번
넘게 새로고침하면 403 이 오고, 그때 `FR-UPD-4` 에 따라 조용히 실패해 배지가 뜨지
않는다. 다음 새로고침에 저절로 복구된다. **이 실패의 피해가 작다는 것이 위 거래를
성립시키는 근거다** — 크다면 가드를 다시 넣어야 한다.

억제는 `FR-UPD-2b`(single-flight) 하나만 둔다. 이건 절약이 아니라 **정합성**이다.
창 넷이 같은 질문을 동시에 던지는 것은 캐시라는 말과 어긋난다.

### D-UPD-9 — 캐시는 메모리에만 산다

디스크에 남기면 "재기동해도 24시간이 이어진다" 를 얻는다. 그런데 **재기동 자체가
트리거 ① 이라 어차피 그 자리에서 다시 확인한다.** 이어 줄 것이 없는 값을 위해
파일 · 경로 · 깨진 파일 처리 · 그 검사를 두는 셈이다. 캐시는 프로세스와 함께
나고 죽는다.

### D-UPD-5 — 여전히 내려받지 않는다

`update.go` 의 기존 판단을 그대로 유지한다. 설치 형태가 여럿이라(직접 빌드 ·
릴리스 산출물 · 패키지 매니저) 스스로 자기 바이너리를 덮으면 패키지 관리자와
싸운다. **이 SRS 가 바꾸는 것은 "언제 확인하는가" 뿐이다. "무엇을 하는가" 는
그대로다.**

### D-UPD-6 — 고지는 한 번이고, 끄는 법을 함께 말한다

기본 켜짐을 정직하게 만드는 것이 `FR-UPD-10` 이다. 매번 띄우면 소음이 되어
읽히지 않고, 한 번도 안 띄우면 몰래 나간 것이 된다. 한 번 띄우고 표식을 남긴다.

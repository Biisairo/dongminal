# SRS: 샌드박스 창 — 컨테이너로 격리된 Window — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

Window 하나를 컨테이너 하나에 대응시켜, 그 Window 안의 모든 도구가 호스트가 아닌 컨테이너 안에서 도는 **샌드박스 창**을 제공한다. 사용자가 신뢰하지 않는 코드·AI 에이전트·프로젝트별 툴체인을 호스트와 분리된 자리에서 돌리게 하는 것이 목적이다.

### 1.2 범위 (Scope)

**포함:**

- 샌드박스 프로파일 2종(`scratch` / `dev`)과 각각의 마운트·네트워크·헬퍼 정책
- 기본 마운트와 동적 마운트 (FR-SBX-39/40)
- Window ↔ 컨테이너 1:1 생명주기 (지연 생성, Window 폐기 시 회수, 부팅 시 고아 회수)
- 도구 기동 경로의 `ProcSpec` 분기 (`toolhub.StartTool`)
- 컨테이너 안 `dmctl` 의 전달(리눅스 바이너리)과 서버 연결
- `workspace.json` 의 Window 스키마 확장
- 컨테이너 런타임 부재·실패 시의 동작
- 샌드박스 창을 열고 구분하는 최소 UI (FR-SBX-34)

**미포함:** §5 비목표 참조. 특히 **HTTP API 인증·권한 스코프는 이 SRS 의 범위가 아니다** — 그 부재가 §3.3 의 격리 등급을 결정한다.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **샌드박스 창** | `sandbox` 필드를 가진 Window. 그 안의 모든 도구가 대응 컨테이너 안에서 실행된다 |
| **프로파일** | 샌드박스 창의 정책 묶음 — 이미지·마운트·네트워크·헬퍼 노출 |
| **대응 컨테이너** | 샌드박스 창 하나에 1:1 로 매인 컨테이너 |
| **컨테이너 런타임** | `docker` 명령. 호스트에 설치된 Docker Engine / Docker Desktop |
| **헬퍼** | `dmctl` 등 multi-call 바이너리 (`internal/helper/runtimebin`) |
| **격리 경계** | 컨테이너 안 코드가 호스트에서 임의 코드를 실행할 수 없는 성질 |

## 2. 현황 (Identified Issue)

### 2.1 도구는 언제나 호스트에서 돈다

`toolhub.StartTool` (`tool.go:215`) 이 도구를 띄우는 유일한 자리이며, 언제나 호스트의 로그인 셸을 띄운다.

```go
sh := platform.Current().Shell.Shell(binDir)      // tool.go:221
term, err := platform.Current().PTY.Start(platform.ProcSpec{
    Path: shell,                                   // tool.go:249
    Args: append([]string{shell}, shellArgs...),
    Env:  env,
    Dir:  startDir,
}, cols, rows)
```

격리 수단이 없어, 사용자는 신뢰하지 않는 코드를 돌릴 때 호스트 전체를 걸어야 한다. AI 에이전트를 권한 확인 없이 돌리는 경우도 같다.

**이 구조는 동시에 기회다.** 기동 경로가 한 곳이므로 격리 도입에 필요한 분기도 한 곳이다.

### 2.2 Window 는 컨테이너를 걸기에 적합한 유일한 계층이다

`ENTITY_MODEL_RESTRUCTURE_SRS.md` 가 확정한 계층에서 **Client** 는 휘발성 뷰포트이고 **Window** 는 서버 영속 작업공간이다. 따라서 브라우저를 닫아도 Window 는 남는다.

컨테이너를 Tool 에 걸면 같은 Window 의 탭들이 파일시스템·설치 패키지·백그라운드 프로세스를 공유하지 못해, 한 탭의 `npm install` 이 옆 탭에 보이지 않는다. Pane 은 레이아웃 산물이라 사용자가 신뢰 단위로 인식하지 않는다. Window 만이 "여기부터 저기까지가 격리된 자리"라는 사용자 통념과 일치하며, 생명주기도 컨테이너와 정확히 포개진다.

### 2.3 도구 기동 경로에 Window 정보가 없다

`ToolManager.Create(cwd string, cols, rows uint16)` (`manager.go:283`) 는 어느 Window 에 속하는지 모른다. 생산 경로의 호출자는 넷이다.

| 호출자 | 자리 |
|--------|------|
| `apiToolsCreate` | `httpapi/handlers_api.go:245` |
| `handleWS` | `httpapi/handlers_ws.go:23` |
| `createHeadlessTool` | `httpapi/handlers_runs_headless.go:74` |
| `create` | `daemon/ipc/paned.go:184` |

Tool→Window 매핑은 `workspace.json` 에 있고 그 파일은 브라우저가 쓴다. 도구 생성 시점에 그 매핑이 아직 저장되지 않았을 수 있으므로, **매핑을 조회해서 얻을 수 없고 호출자가 실어 보내야 한다.**

### 2.4 헬퍼는 이미 TCP 로 붙지만, 호스트 아키텍처에 묶여 있다

`runtimebin/http.go` 가 `dmctl` 의 유일한 서버 접근 경로이며 순수 HTTP 다.

```go
func baseURL() string {
    return fmt.Sprintf("http://%s:%s",
        envOr(dmenv.EnvHost, dmenv.DefaultHost),
        envOr(dmenv.EnvPort, dmenv.DefaultPort))
}
```

유닉스 소켓(`platform/ipc.go` 의 `paned.sock`)은 웹서버↔데몬 내부 전송이지 `dmctl` 경로가 아니다. 따라서 컨테이너에서의 연결은 `DONGMINAL_HOST` 를 바꾸는 것으로 족하며 **전송 계층 신규 구현이 필요 없다.**

남는 것은 두 가지다.

1. `dmctl` 은 `dongminal` 본체에 내장된 multi-call 바이너리이고 `install.go` 가 호스트 아키텍처용으로 `~/.dongminal/bin/dmctl` 에 설치한다. macOS·Windows 호스트의 그 파일은 **리눅스 컨테이너에서 실행되지 않는다.**
2. HTTP API 에 인증이 없다 (`httpapi` 와 `runtimebin` 어디에도 `Authorization` 헤더가 없다). 도구 신원은 `DONGMINAL_TOOL_ID` 환경변수의 자기소개이며 서버는 검증하지 않는다.

### 2.5 실측 (2026-09-03, 개발기)

```
$ echo $DONGMINAL_HOST:$DONGMINAL_PORT
0.0.0.0:58146
$ lsof -nP -iTCP -sTCP:LISTEN | grep dongminal
dongminal 53054 dykim 7u IPv6 TCP *:58146 (LISTEN)
```

서버는 `--expose` 로 `0.0.0.0` 에 떠 있다(`options.go:44` `ExposeHost`). 이 구성에서는 컨테이너가 `host.docker.internal` 로 호스트 API 에 도달한다. 루프백 전용(`127.0.0.1`) 구성일 때의 도달성은 §3.4 가 다룬다.

### 2.6 실기 확인 (2026-09-03, macOS arm64 / Docker 29.6.2 linux/arm64)

설계의 핵심 가정을 `debian:stable-slim` 컨테이너와 **실제 `platform.PTY` 경로**로 확인했다. FR-SBX-12 가 규정한 `ProcSpec` 을 그대로 띄운 결과다.

| 확인 | 결과 |
|------|------|
| 탭 간 파일시스템 공유 (§2.2) | 한 `exec` 가 쓴 파일을 다른 `exec` 가 읽는다 |
| **PTY 리사이즈 전파** | `Resize(120,40)` → 컨테이너 안 `stty size` 가 `40 120`. `docker exec -it` 를 지나 SIGWINCH 가 전달된다 |
| `--rm` 없는 정지 | `docker stop` 후 컨테이너가 `Exited` 로 존속하고, 재시작하면 파일이 그대로다 |
| 정지 상태 `exec` | `container ... is not running` 오류 — 붙기 전에 시작이 필요하다 (FR-SBX-26) |
| 컨테이너 제거 | 붙어 있던 `exec` 가 종료코드 137 로 죽는다. 기존 `onExit` 경로로 도구 종료를 감지할 수 있다 (FR-SBX-28) |
| 라벨 회수 범위 | `--filter label=dongminal.home=...` 로 자기 것만 걸린다. 다른 홈은 0건 (FR-SBX-9) |

리사이즈 전파와 종료 감지가 확인된 것이 특히 중요하다. 이 둘이 깨졌다면 FR-SBX-12 의 `docker exec` 방식 자체를 재설계해야 했다.

**미확인:** Linux · Windows 호스트에서의 재현(V-11)과 Windows 경로 마운트. 이 확인은 개발기가 macOS 하나뿐이라 남아 있다.

`scratch` 프로파일의 전 경로를 실제 런타임으로 확인했다.

| 확인 | 결과 |

`dev` 프로파일을 실제 런타임으로 확인했다.

| 동적 마운트 | 창을 열 때 준 폴더가 `/work` 에 붙고, 기본 마운트와 서로 다른 자리에 들어간다 |
| 설정창 | 저장한 정의가 `~` 표기를 지킨 채 파일에 남고, 프로파일 목록에 즉시 반영된다 |

`scratch` 는 이 셋을 모두 갖지 않는다 — 그것이 이 프로파일만 격리 경계인 이유다.

## 3. 요구사항 (Requirements)

### 3.1 기능 요구사항 (Functional)

#### 3.1.1 프로파일

**FR-SBX-1** 샌드박스 프로파일은 `scratch` · `dev` 두 종이다.

| | `scratch` | `dev` |
|---|---|---|
| 용도 | 신뢰하지 않는 코드 실행 | 작업 환경 (개발 · AI 에이전트) |
| 기본 이미지 | `debian:stable-slim` | 사용자 지정(필수) |
| 기본 마운트 (FR-SBX-39) | **없음** | 적용 |
| 동적 마운트 (FR-SBX-40) | **없음** | `/work` |
| 네트워크 | `none` | `bridge` |
| 헬퍼(`dmctl`) | **없음** | 있음 |
| 격리 등급 (§3.3) | 경계 | 비경계 |

종전의 `agent` 를 두지 않는다. `dev` 와 정책이 한 항목도 다르지 않았고, 이름만 다른 프로파일은 사용자에게 "무엇이 다른가" 라는 질문만 남긴다. AI 에이전트를 돌리는 자리는 `dev` 이며, 그 용도의 차이는 이미지 내용물이 담는다.

**FR-SBX-2** 프로파일은 Window 생성 시 확정되며 이후 변경할 수 없다. 변경하려면 새 Window 를 만든다 — 컨테이너가 이미 떠 있는 상태에서 정책을 바꾸면 이미 실행 중인 도구가 어느 정책 아래 있는지 알 수 없게 된다.

**FR-SBX-3** `dev` 는 이미지를 명시해야 한다. 기본 이미지를 두지 않는 것은 이 프로파일의 유용성이 전적으로 이미지 내용물(툴체인·에이전트 CLI)에 달려 있어, 임의의 기본값이 언제나 틀리기 때문이다. 이미지 없이 생성 요청이 오면 오류다(FR-SBX-20).

**FR-SBX-4** 프로파일 정의는 `~/.dongminal/sandbox.json` 에 둔다. 파일이 없으면 `scratch` 만 사용 가능하며, 그 부재는 오류가 아니다.

```json
{
  "mounts": [
    "~/.claude:/root/.claude",
    { "host": "~/.ssh", "container": "/root/.ssh", "readonly": true },
    { "host": "~/shared", "container": "/shared", "scratch": true }
  ],
  "dev": { "image": "node:22", "ports": [3000, "5173-5180"] }
}
```

**파일에서 오는 것은 이미지 · 포트 · 기본 마운트뿐이다.** 네트워크·마운트·헬퍼는 프로파일 **종류**가 정한다. 그것들을 개별로 켜고 끌 수 있으면 §3.3 의 격리 등급이 설정 조합만큼 늘어나 등급 자체가 무의미해진다.

**FR-SBX-36 (scratch 재정의 금지)** 정의 파일은 `scratch` 를 덮을 수 없다. 시도하면 오류다.

`scratch` 는 세 프로파일 중 유일한 격리 경계다(§3.3). 그 정책이 설정 한 줄로 바뀔 수 있으면 — 네트워크가 열리거나 헬퍼가 들어오면 — 경계가 조용히 사라진다. 정의 파일이 깨져도 `scratch` 는 살아남는다. 그것은 파일이 아니라 코드가 갖는 프로파일이기 때문이다.

#### 3.1.2 Window ↔ 컨테이너 생명주기

**FR-SBX-5** 샌드박스 창 하나에 대응 컨테이너 하나가 1:1 로 매인다. 컨테이너 이름은 `dongminal-sbx-<windowUUID>` 이며, 라벨로 `dongminal.home=<DONGMINAL_HOME>` 과 `dongminal.window=<windowUUID>` 를 단다. 이름은 조회의 키이고 라벨은 회수(FR-SBX-8)의 키다.

**FR-SBX-6** 대응 컨테이너는 **지연 생성**한다 — 그 Window 의 첫 도구가 기동할 때 만든다. Window 생성 시점에 만들지 않는 것은, Window 생성이 브라우저 주도이고 서버는 명령을 중계할 뿐이라 생성 실패를 사용자에게 돌려줄 자리가 없기 때문이다. 도구 기동은 실패를 보고할 자리가 분명하다.

**FR-SBX-7** 컨테이너는 유지 프로세스로 띄우고(`docker run -d`), 도구는 `docker exec` 로 그 컨테이너에 붙는다. 이로써 같은 Window 의 탭들이 파일시스템과 프로세스 공간을 공유한다(§2.2).

**`--rm` 을 쓰지 않는다.** 컨테이너의 파일시스템은 설치한 패키지와 작업 산출물을 담으므로, 도구가 하나도 남지 않은 순간에도 사라져서는 안 된다. 이 하나로 프로파일별 영속성 분기가 불필요해진다.

**PID 1 을 런타임의 init 에 맡긴다(`--init`).** 유지 프로세스를 그대로 PID 1 로 두면 신호의 기본 동작이 적용되지 않아 SIGTERM 이 무시되고, 정지 한 번에 강제 종료 대기(기본 10초)를 그대로 치른다 — 실측에서 서버 종료가 10초 걸렸고 종료 코드가 137(SIGKILL)이었다. 샌드박스 창은 사용자가 프로세스를 여럿 띄우는 자리이므로 좀비 수확도 여기서 필요하다.

**FR-SBX-8 (생명주기 단일 규칙)** **Window 가 존재하는 동안 대응 컨테이너가 존재한다. 제거는 Window 폐기 시에만 한다.**

| 사건 | 대응 컨테이너 |
|------|-------------|
| Window 생성 | 아직 없다 (FR-SBX-6) |
| 첫 도구 기동 | 생성 |
| 탭 닫힘 · 도구 종료 | 유지 |
| 그 Window 의 모든 탭이 닫힘 | 유지 |
| Client 이탈 (브라우저 닫힘) | 유지 |
| 데몬 재시작 | **유지** (FR-SBX-26) |
| 서버 정상 종료 | **정지** — 제거하지 않는다 (FR-SBX-44) |
| 서버 강제 종료 · 크래시 | 돌던 채로 남는다 (걸 자리가 없다). 다음 기동이 재사용한다 |
| 호스트 재부팅 | 정지된 채 존재 → 다음 기동 시 재시작 (FR-SBX-26) |
| **Window 폐기(`closeWindow`)** | **제거** |
| 서버 부팅 시 고아 발견 | 제거 (FR-SBX-9) |

Client 이탈과 데몬 재시작에서 제거하지 않는 것이 요점이다 — Window 는 서버 영속 엔티티이므로(§2.2) 뷰가 사라져도 살아 있어야 한다.

**FR-SBX-9** 부팅 시 회수는 라벨 `dongminal.home` 이 자기 홈인 컨테이너 중, `workspace.json` 에 없는 Window 의 것만 대상으로 한다. 여러 인스턴스가 한 호스트에서 도는 구성에서 다른 인스턴스의 컨테이너를 지우지 않기 위해서다.

**FR-SBX-26 (재사용과 재시작)** 도구 기동 시 대응 컨테이너가 이미 있으면 만들지 않고 재사용한다. 정지된 상태면 시작한 뒤 붙는다.

데몬을 재시작하면 도구는 복원하지 않지만(기존 동작) 컨테이너는 남는다. 둘이 다른 것은 모순이 아니다 — "복원해도 돌던 작업이 아니라 빈 셸이 되살아날 뿐"이라는 판단은 **셸 프로세스**에 대한 것이고, 컨테이너의 파일시스템은 설치한 패키지와 산출물이라 실질 가치가 있다. 프로세스는 살리지 않고 파일시스템만 살린다.

**FR-SBX-27 (detach 금지)** 샌드박스 창의 도구는 백그라운드로 보낼 수 없다. 요청은 명시적 오류로 막고 사유를 보인다.

백그라운드 도구는 정의상 "어느 탭에도 매이지 않은" 도구이지만(`detach` 도움말, ENTITY_MODEL_RESTRUCTURE_SRS §1.3), 샌드박스 도구는 컨테이너에 매이고 컨테이너는 Window 에 매인다. 두 소유 관계가 공존하면 FR-SBX-8 의 단일 규칙이 모순된다 — Window 를 닫을 때 돌고 있는 백그라운드 작업을 죽이거나, 주인 없는 컨테이너를 남겨 회수 규칙과 고아 판정을 전부 복잡하게 만든다. 금지가 가장 단순하고 정직하다.

**FR-SBX-28 (외부 제거 감지)** 대응 컨테이너가 dongminal 밖에서 제거되거나 종료되면, 그 컨테이너에 붙어 있던 도구들은 `docker exec` 가 끊기며 종료된다. 서버는 이를 도구 종료로 처리하고 사유를 보인다 — 살아 있다고 믿는 좀비 도구를 남기지 않는다.

#### 3.1.3 도구 기동

**FR-SBX-10** `ToolManager.Create` 는 샌드박스 컨텍스트를 인자로 받는다. §2.3 의 이유로 조회가 아니라 **주입**이다.

```go
type Placement struct {
    WindowUUID string // 대응 컨테이너의 키
    Profile    string // 비어 있으면 일반 창 — 도구는 호스트에서 돈다
}
```

**프로파일을 UUID 와 함께 받는 것이 핵심이다.** UUID 만 받고 프로파일을 `workspace.json` 에서 조회하면, 브라우저가 창을 저장하기 전에 탭을 만드는 순간 샌드박스 창이 일반 창으로 읽혀 호스트에서 뜬다 — 경쟁 조건 하나가 그대로 조용한 강등이 된다.

`Restore` 는 이 컨텍스트를 받지 않는다. 샌드박스 도구는 영속되지 않으므로(FR-SBX-33) 복원 경로에 오지 않는다.

**FR-SBX-11** 도구 생성 요청은 샌드박스 컨텍스트를 실어 보낸다.

| 경로 | 전달 방식 |
|------|-----------|
| `POST /api/tools` | 질의 문자열 `window` · `sandbox` |
| 데몬 RPC `create` | 파라미터 `window` · `profile` |
| 그 밖(헤드리스·WS 재부착) | 빈 컨텍스트 — 호스트에서 뜬다 |

**FR-SBX-33 (영속 제외)** 샌드박스 도구는 `tools.json` 에 기재하지 않는다.

기재하면 재시작 시 **호스트 셸로** 되살아난다. 복원 경로에는 Window 도 프로파일도 없기 때문이다. 백그라운드 도구를 빼는 기존 규칙(FR-EM-12/FR-BG-9)과 같은 자리이되 이쪽이 더 무겁다 — 그쪽은 빈 셸이 되살아나는 낭비지만, 이쪽은 격리가 조용히 사라진 채 사용자가 계속 일한다.

잃는 것은 프로세스뿐이다. 컨테이너는 남아 있으므로(FR-SBX-26) 그 창에 탭을 다시 열면 하던 자리로 돌아간다.

**FR-SBX-12** 샌드박스 도구의 `ProcSpec` 은 `docker exec` 로 만든다. 그 외의 것 — PTY 생성, 리사이즈, 출력 스트림, 종료 수확 — 은 호스트 도구와 **완전히 같은 경로**를 탄다.

```
Path: "docker"
Args: ["docker","exec","-it","-w",<컨테이너 안 작업디렉터리>, <컨테이너>, <셸>,"-l"]
```

**FR-SBX-13** 동적 마운트가 있는 프로파일은 도구를 컨테이너 안 `/work` 에서 연다. 없는 프로파일(`scratch`)에서는 이미지의 기본 작업 디렉터리를 쓴다.

호스트 경로를 그대로 쓰지 않는 것은 이식성 때문이다. `C:\src\app` 이나 `/Users/…` 는 리눅스 컨테이너 안에서 의미가 없고, 게스트가 항상 리눅스라는 전제(NFR-SBX-1)가 한 자리를 고정할 수 있게 해 준다.

#### 3.1.4 헬퍼 전달과 연결

**FR-SBX-14 (버전 추종)** 컨테이너에 넣는 `dmctl` 은 **실행 시점의 서버 버전에 맞춰 그때그때 확보한다.** 캐시 경로에 버전을 포함한다.

```
~/.dongminal/cache/dmctl-<version>-linux-<arch>
```

버전이 경로에 들어가는 것이 요점이다. 서버가 새 버전으로 올라가면 경로가 달라져 자동으로 새로 확보하게 된다. 버전 없는 고정 경로(`dmctl-linux-<arch>`)를 쓰면 업그레이드 후에도 옛 바이너리를 계속 쓰게 되고, 그 불일치는 오류가 아니라 **조용한 오동작**으로 나타난다 — `dmctl` 이 서버가 더 이상 제공하지 않는 형식으로 요청하거나, 새 서브커맨드를 모른 채 실패한다.

**FR-SBX-15 (확보 경로)** 확보 방법은 `cli.Version` 에 따라 갈린다.

| `cli.Version` | 확보 방법 |
|---------------|-----------|
| 릴리스 태그 (`v1.2.3`) | 릴리스 자산 `dongminal-linux-<arch>` 를 그 **태그에서** 내려받는다 (`latest` 가 아니다) |
| `dev` (소스 빌드) | 소스 트리에서 `GOOS=linux GOARCH=<arch> go build` 로 만든다 |
| 그 외 | 확보 불가 → 기동 실패 (FR-SBX-20) |

`dev` 를 다운로드로 해결할 수 없는 것은 대응하는 릴리스가 존재하지 않기 때문이다(`version.go`: 새기지 않으면 `dev`). 소스에서 빌드한 사용자는 정의상 소스와 Go 툴체인을 갖고 있으므로 크로스 빌드가 성립한다. `latest` 를 받지 않는 것도 같은 이유다 — 서버보다 새 `dmctl` 이 들어오면 FR-SBX-14 가 막으려던 불일치가 그대로 재현된다.

**FR-SBX-29 (직접 배치와 정리)** 해당 버전의 캐시 경로에 사용자가 파일을 놓아두면 확보 절차를 건너뛰고 그것을 쓴다 — 오프라인 환경의 도피구다. 서버 기동 시 현재 버전이 아닌 캐시는 지운다. 버전마다 파일이 쌓이는 것을 막는다.

**FR-SBX-16** 헬퍼는 `/usr/local/bin/dmctl` 에 **읽기 전용**으로 붙인다. 이미 `PATH` 에 있는 자리를 고르는 것은, 별도 디렉터리에 두면 `PATH` 를 손봐야 하고 `-e PATH=` 로 덮으면 이미지가 세운 `PATH` 가 통째로 날아가기 때문이다. 읽기 전용인 것은 컨테이너 안에서 고쳐 쓸 수 있으면 그 자체가 호스트로 나가는 통로가 되기 때문이다.

컨테이너 안 `dmctl` 은 아래 환경으로 서버에 붙는다. 전송 계층 변경은 없다(§2.4). 리눅스 호스트에서도 같은 이름이 서도록 `--add-host` 로 게이트웨이를 명시한다.

```
DONGMINAL_HOST=host.docker.internal
DONGMINAL_PORT=<서버 포트>
DONGMINAL_TOOL_ID=<도구 UUID>
```

**FR-SBX-17** `scratch` 컨테이너에는 `dmctl` 을 넣지 않으며 네트워크도 `none` 이다. 이 프로파일만이 격리 경계이기 때문이다(§3.3).

#### 3.1.5 마운트

마운트는 두 종류다. **무엇이 매번 같고 무엇이 이번에만 다른가**로 갈린다.

| | 기본 마운트 | 동적 마운트 |
|---|---|---|
| 정의하는 곳 | `sandbox.json` 최상위 `mounts` | 창을 열 때 |
| 대상 경로 | 항목마다 지정 | `/work` 고정 |
| 개수 | 여럿 | 하나 |
| 성격 | 설정 · 자격증명 — 창이 달라도 같다 | 이번에 무엇을 작업하는가 |

**FR-SBX-39 (기본 마운트)** `mounts` 는 샌드박스 창이면 언제나 붙는 마운트다. 두 형식을 받는다.

```
"~/.claude:/root/.claude"                                   간편 — docker -v 관용구
{ "host": …, "container": …, "readonly": …, "scratch": … }  세부
```

`~` 는 사용자 홈으로 편다. **호스트 경로가 실재하지 않으면 오류다** — 사용자가 직접 적은 경로이므로 오타를 알려야 한다. 자동 승계인 동적 마운트가 조용히 건너뛰는 것과 갈리는 지점이며, 근거는 FR-SBX-41 이 갖는다.

**FR-SBX-39a (scratch 는 기본적으로 제외)** 기본 마운트는 `dev` 에만 붙는다. `scratch` 는 비어 있다.

`scratch` 의 존재 이유가 "무엇을 돌릴지 모를 때 여는 자리" 이기 때문이다. 자격증명이 거기 함께 들어가면 그 자리가 사라진다 — 읽기 전용이어도 키는 그대로 읽히고, 쓰기면 컨테이너 안 코드가 `authorized_keys` 나 셸 rc 를 고쳐 호스트로 나온다.

**FR-SBX-39b (항목별 예외)** 항목에 `"scratch": true` 를 적으면 그 항목은 `scratch` 에도 붙는다. 그렇게 붙은 순간 **그 프로파일은 격리 경계가 아니며**, 등급 계산(FR-SBX-37)이 이를 그대로 반영해 UI 표기가 따라 바뀐다.

읽기 전용이어도 경계에서 뺀다. 경계라는 말이 사용자에게 뜻하는 바는 "여기서 무슨 일이 나도 호스트는 무사하다" 인데, 읽기 전용 마운트는 그 폴더의 내용을 유출시킨다. 실행을 주지 않는다는 이유로 경계라 부르면 사용자는 유출 가능성을 보지 못한다.

**FR-SBX-40 (동적 마운트)** 창을 열 때 작업 폴더 하나를 지정한다. 컨테이너 안 `/work` 에 붙고, 도구는 그 자리에서 열린다.

지정하지 않으면 창을 여는 시점의 작업 디렉터리를 쓴다 — 종전 동작이 그대로 기본값이다. `scratch` 에는 붙지 않는다.

**FR-SBX-41 (없는 경로)** 동적 마운트의 원본이 실재하지 않으면 **마운트하지 않고 진행한다.** 기본 마운트가 오류인 것과 갈린다.

승계된 값이기 때문이다. 사용자가 적은 적 없는 경로로 창이 열리지 못하면 원인을 짐작할 수 없다. 반대로 기본 마운트는 사용자가 직접 적은 것이므로 오타를 삼키면 "설정한 대로 안 된다" 가 된다.

어느 쪽이든 **없는 경로를 런타임에 넘기지는 않는다.** 컨테이너 런타임은 존재하지 않는 원본을 받으면 호스트에 그 디렉터리를 만든다(§2.6 실측).

**FR-SBX-42 (마운트 변경)** 마운트를 바꾸면 다음 컨테이너 생성부터 적용된다. 이미 있는 대응 컨테이너에는 적용되지 않으며, 적용하려면 재생성해야 하므로 **파일시스템이 초기화된다**(FR-SBX-22). 포트와 같은 제약이다(FR-SBX-32).

#### 3.1.5 포트 노출

**FR-SBX-30 (선언된 포트만 매핑)** `dev` 프로파일은 노출할 포트를 프로파일 정의에 적고, 컨테이너 생성 시 **호스트와 같은 번호로** 매핑한다.

```json
{ "dev": { "image": "...", "ports": [3000, "5173-5180"] } }
```

세 가지가 이 형태를 강제한다.

1. **컨테이너 런타임은 실행 중인 컨테이너에 포트 매핑을 더할 수 없다.** 매핑은 `docker run` 시점에 확정되고, 바꾸려면 재생성뿐이다. 따라서 포트는 프로파일에 미리 적히는 것 말고 다른 자리가 없다.
2. **전 포트 매핑(`-p 1-65535`)은 성립하지 않는다.** 매핑마다 프록시 자원이 잡혀 기동이 실질적으로 불가능해진다.
3. **`--network host` 는 쓰지 않는다.** 리눅스 호스트에서만 온전하고 네트워크 격리가 통째로 사라져, NFR-SBX-1 과 §3.3 을 동시에 깬다.

호스트 포트를 컨테이너 포트와 같은 번호로 두는 것도 요점이다. 개발 서버는 자기 주소를 `http://localhost:3000` 으로 찍는데, 호스트에서 번호가 달라지면 그 출력이 그대로 틀린 안내가 된다.

**FR-SBX-31 (포트 충돌)** 선언한 포트를 호스트에서 이미 쓰고 있으면 컨테이너 생성이 실패한다. 다른 포트로 자동 대체하지 않는다 — 사용자가 적은 번호와 실제 번호가 어긋나는 편이 실패보다 나쁘다. 실패는 FR-SBX-20 의 사유로 보인다.

**FR-SBX-43 (설정창)** 기본 마운트와 `dev` 이미지·포트는 설정창에서 다룬다. 저장은 곧바로 반영되며, 서버를 다시 띄우게 하지 않는다.

정의 파일을 손으로 고치게 두지 않는 이유는 마운트의 생김새 때문이다 — 경로 둘과 표식 둘이 한 항목을 이루고, 그중 하나(`scratch`)는 격리 등급을 바꾼다. 그 조합을 텍스트로 적게 하면 틀리기 쉽고, 틀린 채 저장되면 다음 기동이 통째로 막힌다.

**저장 전에 검증한다.** 화면이 보낸 것과 파일에서 읽은 것이 같은 문(`ParseConfig`)을 지나야 규칙이 갈리지 않으며, 거부 사유는 그대로 사용자에게 보인다. 깨진 정의가 파일에 닿으면 그것을 고칠 화면조차 열지 못한다.

반영이 즉시여도 **이미 떠 있는 컨테이너는 바뀌지 않는다**(FR-SBX-42). 설정창이 그 사실을 함께 적는다.

**FR-SBX-44 (서버 종료)** 서버가 정중히 내려갈 때 이 홈의 대응 컨테이너를 **정지한다. 제거하지 않는다.**

서버가 내려가는 것은 Window 가 사라진 것과 다르다 — 창은 `workspace.json` 에 그대로 있다. 정지는 자원만 놓고 파일시스템은 남기며, 다음에 그 창을 열면 FR-SBX-26 이 시작해 하던 자리로 돌려놓는다. 실측으로 정지 전에 남긴 파일이 재기동 뒤에도 그대로임을 확인했다.

강제 종료(SIGKILL·크래시·전원)에는 걸 자리가 없다. 그때 컨테이너는 돌던 채로 남지만, 다음 기동은 running 이든 exited 든 재사용하므로 동작에 차이가 없다. 정지 실패도 삼킨다 — 종료 절차가 거기서 막히면 서버가 내려가지 못한다.

#### 3.1.7 사용자 진입점

**FR-SBX-34 (UI)** 샌드박스 창은 아래 세 자리로 다룬다.

| 자리 | 동작 |
|------|------|
| 창 목록의 `+ New` **안쪽 오른쪽 박스** | 눌러서 샌드박스 창을 연다 |
| 창 목록 항목의 배지 | 그 창이 샌드박스임을 표시한다 |
| 실패 알림 | 기동 실패의 **사유**를 보인다 |

진입점을 별도 버튼으로 세우지 않고 `+ New` 안에 두는 것은, 샌드박스 창이 새 창의 **변종**이지 다른 동작이 아니기 때문이다. 자리가 그 관계를 말한다.

배지는 선택이 아니다. 어느 창이 격리됐는지 구분할 수 없으면 사용자가 격리를 신뢰할 근거가 없고, §3.3 의 등급 표시도 걸 자리가 없다.

실패 사유를 보이는 것도 마찬가지다 — 런타임 미설치·데몬 미실행이 흔한 실패이고, 사유 없이 실패하면 "눌러도 아무 일이 없다" 만 남는다 (FR-SBX-20).

**FR-SBX-35 (CLI)** `dmctl new-window --sandbox <프로파일>` 로도 연다. 에이전트와 워크플로우의 진입점이다.

**FR-SBX-32 (포트 변경)** 프로파일의 포트를 바꾸면 다음 컨테이너 생성부터 적용된다. 이미 있는 대응 컨테이너에는 적용되지 않으며, 적용하려면 그 컨테이너를 재생성해야 하므로 **파일시스템이 초기화된다**(FR-SBX-22). 이 대가를 사용자에게 알린 뒤 확인을 받는다.

여유 있게 대역으로 선언해 두는 편을 권한다. 나중에 포트 하나가 더 필요해질 때 치르는 비용이 재생성이기 때문이다.

#### 3.1.5 스키마

**FR-SBX-18** `wsWindow` 에 `sandbox` 필드를 더한다. 없으면 일반 Window 다.

```go
type wsWindow struct {
    ID          string    `json:"id"`
    Name        string    `json:"name"`
    Layout      *WsLayout `json:"layout"`
    FocusedPane string    `json:"focusedPane"`
    OwnerRunID  string    `json:"ownerRunId,omitempty"`
    Sandbox     string    `json:"sandbox,omitempty"` // 프로파일 이름
}
```

`OwnerRunID` 가 이미 Window 메타데이터의 선례다(`manager.go:495`).

**FR-SBX-19** `schemaVersion` 은 올리지 않는다. `sandbox` 는 선택 필드이며 없을 때의 의미(일반 Window)가 구 파일의 의미와 같아, 구 파일이 새 코드에서 오독되지 않는다.

#### 3.1.6 실패 처리

**FR-SBX-20** 아래는 모두 **도구 기동 실패**로 처리하며 사용자에게 사유를 보인다.

| 조건 | 사유 |
|------|------|
| `docker` 명령 없음 | 컨테이너 런타임 미설치 |
| 데몬 응답 없음 | 런타임 미실행 |
| 이미지 없음 / pull 실패 | 이미지 해결 실패 |
| `dev` 에 이미지 미지정 | 설정 오류 (FR-SBX-3) |
| 리눅스 `dmctl` 확보 실패 | 헬퍼 전달 실패 (FR-SBX-14) |

**FR-SBX-21 (안전 필수)** 샌드박스 기동에 실패했을 때 **호스트 셸로 대체 기동하지 않는다.** 사용자가 격리된 줄 알고 신뢰하지 않는 코드를 호스트에서 실행하게 되는 것이 이 기능이 막으려던 바로 그 사고다. 조용한 강등은 기능 부재보다 나쁘다.

**FR-SBX-22** 컨테이너가 외부에서 제거된 뒤 그 Window 에서 도구를 기동하면, 프로파일에 따라 컨테이너를 다시 만들고 기동한다. 이때 이전 컨테이너의 파일시스템 상태는 없으므로, 재생성임을 사용자에게 고지한다. 조용히 새 컨테이너를 내주면 사용자는 설치해 둔 것이 사라진 이유를 알 수 없다.

### 3.2 비기능 요구사항 (Non-functional)

**NFR-SBX-1** 호스트 OS 별 분기 코드를 두지 않는다. 게스트는 항상 리눅스 컨테이너이므로 샌드박스 내부는 모든 호스트에서 동일하다. 호스트 차이(경로 표기·`host.docker.internal` 해석)는 컨테이너 런타임이 흡수한다.

**NFR-SBX-2** 샌드박스가 아닌 Window 의 동작은 바뀌지 않는다. 샌드박스 컨텍스트가 빈 경로는 종전 코드와 같아야 한다.

**NFR-SBX-3** 컨테이너 런타임이 없는 호스트에서 `dongminal` 의 나머지 기능은 영향받지 않는다. 런타임 탐지는 샌드박스 창 기동 시점에만 한다.

**NFR-SBX-4** 도구 하나가 기동하는 데 드는 추가 지연은 컨테이너가 이미 떠 있는 경우 `docker exec` 1회다. 컨테이너 생성은 Window 당 1회로 한정한다(FR-SBX-6·7).

### 3.3 격리 등급 (Isolation Grade)

**이 절은 요구사항인 동시에 이 기능의 한계 선언이다.**

HTTP API 에는 인증이 없고 `dmctl` 은 워크스페이스 전체를 조작할 수 있다(§2.4). 따라서 `dmctl` 이 있는 컨테이너 안의 코드는 아래가 가능하다.

```
dmctl 로 비샌드박스 창을 찾는다 → 그 창의 셸에 입력을 주입한다 → 호스트에서 임의 실행
```

즉 **헬퍼 노출과 격리 경계는 양립하지 않는다.**

**FR-SBX-37 (등급은 정책에서 파생된다)** 격리 등급은 프로파일 정책에서 계산한다 — 헬퍼가 없고 네트워크가 닫혀 있을 때만 경계다. 등급을 따로 적어 두면 정책이 바뀔 때 표기가 따라오지 않고, 그 어긋남은 "격리된 줄 알았다" 로 끝난다.

**FR-SBX-23** 각 프로파일의 격리 등급을 아래로 확정하고, 사용자에게 보이는 자리(문서·창 생성 UI)에 명시한다.

| 프로파일 | 등급 | 의미 |
|---|---|---|
| `scratch` | **격리 경계** | 컨테이너 안 코드가 호스트에서 임의 실행을 할 수 없다 |
| `dev` | **비경계** | 작업 환경이 목적. 호스트 조작이 가능하다 |

**FR-SBX-24** `dev` 프로파일을 보안 기능으로 표기하지 않는다. AI 에이전트를 이 안에서 돌릴 때 실제로 막는 것은 에이전트의 **실수** — 잘못된 삭제, 오염시키는 설치, 의존성 훼손 — 이며 그것으로 충분히 유용하다. 막지 못하는 것을 막는다고 적으면 사용자가 그 신뢰에 기대어 실제 위험을 감수한다.

**FR-SBX-25** 프로파일을 고르는 자리에 각각의 등급을 함께 보인다. 고른 뒤가 아니라 **고르는 순간** 보여야 한다 — 그때가 사용자가 위험을 감수할지 정하는 유일한 시점이다.

**FR-SBX-38** 인증·권한 스코프가 도입되면(§5 비목표) `dev` 의 등급을 재평가한다. 그때까지 이 표가 유효하다.

## 5. 비목표 (Non-goals)

- **HTTP API 인증·권한 스코프.** `dev` 를 격리 경계로 만들려면 필요하지만, 무인증 API 전체를 건드리는 별도 작업이다. 이 SRS 는 그 부재를 §3.3 으로 명시할 뿐 해결하지 않는다
- **Docker 외 런타임** (podman·containerd·rootless). `docker` 명령 하나만 대상으로 한다
- **이미지 빌드 기능.** 이미지는 사용자가 준비한다. `Dockerfile` 을 읽거나 빌드하지 않는다
- **Windows 컨테이너.** 리눅스 컨테이너만 대상이다 (NFR-SBX-1 의 전제)
- **중첩 샌드박스.** 샌드박스 창 안에서 다시 샌드박스 창을 열지 않는다
- **실행 중인 컨테이너에 포트 매핑 추가.** 런타임이 지원하지 않는다 (FR-SBX-30). 재생성이 유일한 길이다
- **컨테이너 자원 제한** (cpu·memory·pids). 후속 과제
- **기존 Window 의 샌드박스 전환.** FR-SBX-2 가 금지한다

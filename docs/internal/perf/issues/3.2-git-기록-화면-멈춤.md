**남은 결함 — 설계 결정 필요(blocked 사유)**

큰 diff 의 글자 단위 계산이 상한 없이 메인 스레드에서 돈다. vendor 설정으로는 막히지 않는다: `timeout` 은 상한이 되지 못하고(100 ms 를 줘도 7.4초), `scanLimit` 은 평범한 diff 도 파일 전체 한 조각으로 뭉갠다(SPA_PROFILE §2-1-2). 선택지:

- **A(권장)** 줄 단위 diff 를 먼저 하고, 바뀐 조각 중 작은 것만 글자 단위로 다듬는 `diffConfig.override` 함수. 줄 diff 는 이미 있는 `edDiffLines`(Myers, 편집 수 상한)를 쓴다. 상한을 넘거나 조각이 크면 그 조각은 통째로 바뀐 것으로 보인다. 평범한 diff 의 화면은 거의 같고, 큰 diff 는 줄 단위 강조가 된다. `gitDiffIgnoreWs` 의 상한 초과 폴백(`CM.diff(a,b)`, 지금도 상한 없음)도 같은 길로 묶는다. 조각 크기 상한과 줄 diff 편집 수 상한(현행 2,000 이면 현실형 3,200줄 변경이 한 조각이 된다) 값을 정해야 한다.
- B 크기 문턱: 파일이 크면 줄 단위만 쓴다. 단순하지만 비용은 크기가 아니라 바뀐 글자 수에 비례해 문턱을 정할 근거가 약하다(50 KB 를 모두 고친 파일도 1.2초).
- C Worker: `MergeView` 는 diff 를 생성자 안에서 동기로 계산하고 미리 계산한 조각을 받지 않는다. vendor 를 바꿔야 해서 권하지 않는다.
- D 서버의 git hunk 를 쓴다: 편집 중인 문서(작업 트리 축)는 매 입력마다 다시 계산해야 해서 서버 왕복이 붙는다. 권하지 않는다.

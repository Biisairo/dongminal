# SRS: 질문에 답하는 자리는 하나다 — IEEE 29148

> **문서 상태**: 승인·구현완료

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 하나다.

> **"`11;rgb:3f3f/3f3f/3f3f2026;0$y2048;0$y2031;0$y1010;0$y1011;0$y` 같은
> 문자열이 입력되는 문제."**

그 문자열은 **터미널이 낸 답장**이다. 원인은 둘이었고, 하나는 이미 닫혔다 —
재생된 스크롤백의 낡은 질의에 새 xterm 이 답하던 자리를 `TERMINAL_RESUME_SRS`
FR-TRS-5a 가 막았다. 본 SRS 는 **남은 하나**를 닫는다: 같은 도구에 붙은
클라이언트가 여럿이면, 질의 하나에 **답이 여럿 나간다.**

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 좌석 | 서버가 도구마다 **응답 좌석**을 하나 두고, 누가 그 주인인지 각 연결에 통보한다 |
| **B** 승계 | 연결이 붙거나 떨어지면 좌석을 다시 계산해 그 도구의 모든 연결에 다시 통보한다 |
| **C** 억제 | 브라우저는 좌석 주인이 아니면 **질의의 답**을 보내지 않는다 |

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **질의** | 앱이 PTY 출력으로 내보내는 물음. 화면에 찍히지 않는다 (`ESC]11;?`, `ESC[?2026$p` …) |
| **답장** | 터미널이 그 물음에 PTY **입력**으로 돌려주는 답. 사용자가 친 키와 같은 통로다 |
| **보고** | 터미널이 스스로 내는 것 전부. 답장 + 포커스 보고(`ESC[I`·`ESC[O`) (`TERM_REPORT_RE`) |
| **좌석** | 한 도구에 대해 **답장을 보낼 자격**. 언제나 하나뿐이다 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 클라이언트는 도구마다 여럿이다

`handlers_ws.go` 의 주석이 그 사실을 적고 있다 — *"When a new window opens, the
frontend creates WS connections for ALL tools."* 브라우저 창이 둘이면 **모든
도구에 연결이 둘**이고, 데스크톱과 폰을 같이 쓰면 그것이 기본 상태다.

### 2.2 출력은 방송, 입력은 합류

```
앱 --출력--> 서버 --broadcast--> 창A xterm
                   \-----------> 창B xterm

창A xterm --답장--\
                   >--> PTY stdin --> 앱      ← N:1
창B xterm --답장--/
```

질의 하나를 **두 xterm 이 다 본다.** 각자 자기에게 물은 것으로 알고 각자 답한다.

### 2.3 앱은 답을 하나만 먹는다

앱의 파서는 질의 하나에 답 하나를 기대한다. 둘째 답은 파서를 지나 **입력 줄에
남고**, 그것이 프롬프트에 찍힌 그 문자열이다. 키 입력이 N:1 로 합류하는 것은
**의도된 동작**이다 — 어느 창에서 타이핑해도 같은 터미널이 움직여야 한다. 답장만
불어나면 안 된다.

### 2.4 포커스로는 가를 수 없다

크기의 주인을 가르는 `resizeCheck` 는 `windowFocused` 가 거짓이면 **무조건
거짓**이다. 그것을 좌석 판정에 쓰면 브라우저가 백그라운드일 때 **아무도 답하지
않는다** — 앱은 질의 대기에 걸린다. 크기는 안 보내도 그만이지만 답장은 아니다.

## 3. 요구사항 (Requirements)

### 3.1 좌석 (묶음 A)

**FR-RPS-1.** 서버는 도구마다 **응답 좌석**을 정확히 하나 둔다. 주인은 그 도구에
붙은 연결 중 **가장 먼저 붙은 것**이다.

**FR-RPS-2.** 좌석은 두 배선(direct·daemon)이 **같은 자리**에서 관리한다. 근거는
사실 하나다 — PTY 가 어느 프로세스에 있든 **WS 연결은 언제나 webserver 에 있다.**

**FR-RPS-3.** 새 op `OpReplySeat`(`0x06`). 페이로드는 **1 바이트**다.

```
[0]  uint8  — 1=이 연결이 좌석의 주인, 0=아니다
```

이 op 를 모르는 옛 클라이언트는 조용히 버린다 (`OpSeq`·`OpSize` 와 같은 규약).

**FR-RPS-4.** 통보의 자리는 **재생보다 앞**이다. 재생·라이브보다 먼저 닿아야 그
구간의 질의를 만나기 전에 좌석이 정해져 있다.

### 3.2 승계 (묶음 B)

**FR-RPS-5.** 연결이 붙거나 떨어지면 좌석을 다시 계산하고, 그 도구의 **모든
연결에 다시 통보한다.** 승계는 그 통보다 — 주인만 골라 알리는 길을 따로 두지
않는다.

**FR-RPS-6.** 통보 실패는 그 연결을 끊지 않는다. 죽은 소켓은 바로 뒤의 재생이나
방송이 다시 만나고, 판정은 그쪽이 한다.

### 3.3 억제 (묶음 C)

**FR-RPS-7.** 브라우저는 좌석의 주인이 아니면 **답장을 보내지 않는다.** 판정은
`TERM_REPORT_RE` 에 걸리되 포커스 보고가 아닌 것이다.

**FR-RPS-8.** **포커스 보고(`ESC[I`·`ESC[O`)는 좌석과 무관하다.** 그것은 질의의
답이 아니라 **그 창 고유의 사실**이다. 폰에서 터미널을 탭한 사실을 데스크톱이
대신 말할 수는 없다.

**FR-RPS-9.** 통보를 받기 전의 기본값은 **주인**이다. 좌석을 모르는 서버에 붙은
탭은 종전 그대로 돈다 (FR-TRS-3 과 같은 규약 — 모르는 것은 오류가 아니다).

## 4. 결정 (Decisions)

| # | 결정 | 근거 |
|---|---|---|
| **D-1** | 좌석은 **서버가 정한다** | 브라우저끼리는 서로의 존재를 모른다. 같은 사실을 두 곳에서 계산하면 둘 다 주인이거나 둘 다 아닌 창이 열린다 |
| **D-2** | 기준은 **접속 순서**이지 포커스가 아니다 | 포커스는 "아무도 아님" 이 정상 상태이지만 좌석은 그 상태를 허용할 수 없다 (§2.4). `resizeCheck` 를 쓰면 브라우저가 백그라운드일 때 아무도 답하지 않고, 앱은 질의 대기에 걸린다 |
| **D-3** | 승계는 **전체 재통보**다 | 주인에게만 "너로 바뀌었다" 를 보내면 나머지는 자기가 아닌 것을 **추론**해야 한다. 추론하는 상태는 어긋난다 |
| **D-4** | 좌석 레지스트리는 **`hub` 에 산다** | 그곳이 "서버가 권위로 드는 휘발성 레지스트리" 의 자리다 (`FocusRegistry` 가 선례). 서버가 재시작하면 모두 풀리는 성질도 같다 |

## 6. 비목표 (Non-goals)

- **옛 프론트가 보내는 중복 답장을 서버가 거르는 것.** 서버가 입력에서 답장
  모양을 골라 버리면, 그 목록에서 하나만 빠져도 **정상 답장이 사라져 앱이 질의
  대기에 걸린다.** 좌석을 모르는 탭은 새로고침이 해소한다
- **좌석을 포커스·활성 탭에 맞추는 것** (D-2)
- **방송을 줄이는 것.** 화면은 모든 연결이 그대로 받는다

## 7. 리스크 (Risks)

| 리스크 | 등급 | 완화 |
|---|---|---|
| 좌석 주인의 소켓이 느려 답장이 늦는다 | **LOW** | 앱의 질의는 타임아웃을 갖는다. 소켓이 끊기면 FR-RPS-5 가 즉시 승계한다 |
| 좌석 통보와 질의가 경주한다 (통보 전에 질의가 닿음) | **LOW** | 통보가 재생보다 앞이다 (FR-RPS-4). 그 전의 기본값은 주인이므로(FR-RPS-9) **최악이 종전 동작**이다 |
| `TERM_REPORT_RE` 가 사용자의 키를 답장으로 오판해 삼킨다 | **MEDIUM** | 목록은 벤더 실측으로 세웠고(FR-TRS-5a), 화살표·F 키·마우스와 겹치지 않음을 V-RPS-8 의 반증이 지킨다 |
| 두 배선의 통보 자리가 어긋난다 | **MEDIUM** | V-RPS-7 이 두 배선을 같은 검사로 묶는다 (`buildReplay` 를 함께 쓰게 한 FR-TRS-12 와 같은 규약) |

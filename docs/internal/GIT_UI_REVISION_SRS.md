## 1. 서론 (Introduction)

### 1.1 목적 (Purpose)

MVP(M1~M5) 구현 후 사용자 검토에서 나온 UI 결정 셋을 요구사항으로 확정한다.

1. **Git 창과 일반 창의 경계** — 지금은 Git 창 안에서 분할·탭 추가가 되어 두 세계가
   섞인다. 그것을 막는다.
2. **Git 창의 진입점** — 지금은 WINDOWS 목록과 창 전환 단축키가 Git 창을 일반 창과
   같이 다룬다. GIT 섹션만 진입점으로 남긴다.
3. **선택 어휘와 표식** — 파일 목록의 체크박스를 없애고 행 클릭 + 보조키로 옮긴다.
   GIT 섹션의 이모지 표식을 없앤다.

### 1.2 범위 (Scope)

**대상**: 좌측 사이드바 WINDOWS·GIT 섹션, Git 창의 창 골격(탭 행·상단 바·분할),
Changes 탭 파일 목록의 선택, `Open File` 의 대상 창.

**비대상**: git 실행 계층(`internal/git`), API 표면, Diff·History·Branches·Stash 의
내부 동작, 안전 정책(묶음 J), 다이얼로그 규약(묶음 P).

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **Git 창** | `type: "git"` 인 창. 워크스페이스에 최대 1개 (FR-GIT-26) |
| **일반 창** | `type` 이 없거나 `terminal` 인 창 |
| **follow 항목** | GIT 섹션 최상단 1줄. 포커스된 터미널의 cwd 로 확정한 리포 (FR-GIT-9) |
| **핀 항목** | 사용자가 고정한 리포 (FR-GIT-11) |
| **선택(selection)** | 일괄 동작(스테이지·언스테이지·버리기)의 대상 집합 |
| **포커스 행** | 선택 안에서 마지막으로 클릭한 행. 미리보기가 이 행을 보인다 |

## 2. 전반 기술 (Overall Description)

### 2.1 근거 (Rationale)

Git 창을 일반 창처럼 다룬 원 설계(FR-GIT-27·30)의 의도는 "특수 창을 새로 배우게
하지 않는다" 였다. 실사용에서 그 대가가 드러났다:

- Git 창 안에서 터미널을 띄우고 편집기를 열 수 있으니 **Git 창이 또 하나의 작업
  창**이 된다. Git 을 창으로 분리한 의도(단일 리포·싱글턴·고정 탭)가 흐려진다.
- WINDOWS 목록에 `Git` 이 섞여 있어 **진입점이 둘**이다. 사용자는 GIT 섹션의 리포
  목록을 진입점으로 쓰는데, 창 목록의 `Git` 은 "어느 리포인지 모르는 창"이다.

따라서 Git 창을 **닫힌 창**으로 다시 정의한다: 고정 탭 6개만 있고, 진입은 리포
항목으로만 한다.

### 2.2 제약 (Constraints)

- 창 데이터 모델의 `type`(FR-GIT-25)과 싱글턴(FR-GIT-26)은 그대로다.
- 활성 내부 탭·활성 리포의 영속(FR-GIT-29)과 브로드캐스트(FR-GIT-31)도 그대로다.
- 기존 워크스페이스에 이미 Git 창 안의 터미널·편집기 탭이 있을 수 있다 — 하위호환
  처리가 필요하다 (FR-GIT-189).

## 3. 요구사항 (Requirements)

### 3.1 폐기 (Withdrawn)

| **FR-GIT-30** | "Git 창은 다른 창과 마찬가지로 창 목록·창 전환 단축키의 대상이다" | §2.1. FR-GIT-181 가 대체한다 |

### 3.2 개정 (Amended)

- **FR-GIT-13 (개정)** 좌측 사이드바는 GIT 섹션을 가지며 follow 1개와 핀 목록,
  `+ Add` 진입점을 표시한다. **표식에 이모지를 쓰지 않는다** (FR-GIT-187·188).
- **FR-GIT-41 (개정)** 파일 우클릭의 `Open File` 은 **Git 창이 아닌 창**에 편집기
  탭을 열고 그 창을 활성화한다 (FR-GIT-185).
- **FR-GIT-69 (개정)** 파일 다중 선택의 수단은 체크박스가 아니라 **행 클릭 +
  보조키**다 (FR-GIT-183).

### 3.3 신규 — Git 창의 경계

- **FR-GIT-179** Git 창은 **닫힌 창**이다. 내부는 고정 탭 6개
  (`Changes / Diff / History / Branches / Stash / Console`)뿐이며, 사용자는 그 안에
  분할 칸을 만들거나 탭을 더할 수 없다.
- **FR-GIT-180** Git 창이 활성인 동안 분할·새 탭 진입점은 **동작하지 않고 화면에도
  보이지 않는다**: 상단 바의 `Split H`·`Split V`, 탭 행의 `+`, 단축키
  `splitH`·`splitV`·`newTab`, 모바일 상단의 `+`.
  - 근거: 눌리지만 아무 일도 하지 않는 버튼은 고장으로 읽힌다. 자리를 없앤다.
- **FR-GIT-181** 다른 창의 탭을 끌어다 Git 창에 놓을 수 없다. 드래그 중 Git 창의
  탭 행·본문은 드롭 대상으로 표시되지 않는다.
- **FR-GIT-182** Git 창은 WINDOWS 목록에 표시하지 않으며, 창 전환 단축키
  (`windowNext`·`windowPrev`)의 순환 대상이 아니다. **유일한 진입점은 GIT 섹션의
  리포 항목이다** (FR-GIT-15).
- **FR-GIT-183** Git 창을 닫는 수단은 Git 창 자신의 상단 바에 둔다 — WINDOWS 목록의
  `×` 가 사라지기 때문이다. 닫은 뒤 리포 항목을 다시 클릭하면 새로 만들어진다
  (FR-GIT-26 유지).
- **FR-GIT-184** Git 창이 활성인 동안에도 WINDOWS 목록의 다른 창은 클릭으로 갈 수
  있어야 한다. Git 창에서 나가는 길이 항상 있어야 한다.
- **FR-GIT-185** `Open File` 의 대상 창은 **직전에 활성이었던 일반 창**이다. 그런
  창이 없으면 새로 만든다. 연 뒤 그 창을 활성화한다 — 열었는데 보이지 않으면
  사용자는 실패로 읽는다.
- **FR-GIT-186** 이 개정 이전에 만들어져 Git 창 안에 터미널·편집기 탭을 가진
  워크스페이스는 로드 시 그 탭들을 **일반 창으로 옮긴다**. 조용히 버리지 않는다 —
  사용자의 작업 상태다.

### 3.4 신규 — 파일 목록의 선택

- **FR-GIT-187** 파일 행의 체크박스를 없앤다. 선택은 행 자체로 한다. 그룹 머리의
  일괄 버튼(`모두 스테이지` 등, FR-GIT-66~68)은 그대로 둔다 — 선택과 무관한 별개의
  진입점이다.
- **FR-GIT-188** 선택 조작 (FR-GIT-52 의 클릭 의미를 유지한다):

  | 조작 | 선택 | 미리보기 |
  |---|---|---|
  | 클릭 | 그 행 **하나로 바꾼다** | 그 행 |
  | `Cmd`/`Ctrl` + 클릭 | 그 행을 **토글**한다 | 그 행 |
  | `Shift` + 클릭 | 앵커부터 그 행까지 **범위**로 바꾼다 | 그 행 |
  | 더블클릭 | 바뀌지 않는다 | Diff 탭으로 연다 (FR-GIT-52) |

  - 앵커는 마지막으로 보조키 없이 클릭한 행이다. 범위는 화면에 보이는 순서를
    따르며 그룹 경계를 넘는다 (기존 FR-GIT-69 규약 유지).
- **FR-GIT-189** 선택된 행은 배경 강조로, **포커스 행은 그것과 구분되는 표식**으로
  보인다. 둘을 같게 그리면 미리보기가 어느 행을 보이는지 알 수 없다.
- **FR-GIT-190** 일부만 스테이지된 파일(FR-GIT-70)의 표시는 체크박스의
  indeterminate 가 아니라 **행의 상태 문자 색**으로 한다.
- **FR-GIT-191** 선택은 status 에 남아 있는 경로만 뜻한다 (기존 동작 유지) —
  사라진 경로의 선택은 저절로 잊힌다.

### 3.4.1 신규 — 동작의 진입점

지금은 **선택 동작 줄**(파일 목록 위의 `Stage`·`Unstage`·`Discard`·`Clear`)과
**행 인라인 버튼**(`+`·`−`·`↺`)이 같은 일을 두 자리에서 한다. 화면이 무거워지고,
"이 버튼은 무엇을 대상으로 하나"가 자리마다 달라 읽히지 않는다.

- **FR-GIT-207** 선택 동작 줄을 **없앤다**. 스테이지·언스테이지·버리기의 진입점은
  **행 인라인 버튼 하나**다 (그룹 머리의 일괄 버튼 FR-GIT-66~68 은 그대로 둔다).
- **FR-GIT-208** 행 인라인 버튼의 **대상은 클릭한 행이 선택에 들어 있는지로
  정한다**:

  | 상황 | 대상 |
  |---|---|
  | 클릭한 행이 현재 선택에 **들어 있다** | **선택된 행 전체** |
  | 클릭한 행이 선택에 **없다** | 그 행 하나 |
  | 선택이 비어 있다 | 그 행 하나 |

  - 선택 전체가 대상일 때도 그 동작이 뜻을 갖는 행만 남긴다 (기존 `_selTargets`
    규약 유지) — staged 행을 stage 하거나 untracked 행을 unstage 하는 것은 아무
    일도 하지 않는다.
- **FR-GIT-209** `Clear`(선택 해제) 버튼을 없앤다. 다른 행을 평클릭하면 선택이 그
  행으로 바뀌므로(FR-GIT-188) 해제만을 위한 자리가 필요 없다.

### 3.5 신규 — GIT 섹션의 표식

- **FR-GIT-192** GIT 섹션 항목은 **이모지를 쓰지 않는다**. 상태 표식은 WINDOWS
  목록의 점(`.si-dot`)과 **같은 어휘**다: 활성 리포는 accent 로 채운 점, 그 밖에는
  흐린 점.
- **FR-GIT-193** follow 항목과 핀 항목의 구분은 표식이 아니라 **배치**로 한다.
  follow 는 항상 최상단 1줄이고, 그 아래에 얇은 구분선을 둔다.
- **FR-GIT-194** 저장소가 아닌 follow 항목은 흐리게 보이고 점을 그리지 않는다 —
  가리키는 리포가 없으므로 상태가 없다 (FR-GIT-10 유지).

### 3.5.1 결함 — follow 가 서버의 cwd 로 넘어간다

**증상**: dongminal 과 아무 상관 없는 디렉터리에서 follow 항목을 눌러 Git 창에
들어가면, follow 줄이 곧바로 `dongminal` 로 바뀐다.

**원인**: follow 는 "포커스된 터미널 칸의 도구"(`?tool=`)로 정해지는데, 포커스가
터미널이 아니면(Git 창·편집기 탭) 빈 값이 가고 **서버가 자기 cwd 로 답한다**
(`gitFollowCwd`). 서버의 cwd 는 dongminal 을 띄운 자리이므로 사용자가 가 본 적
없는 리포가 뜬다. FR-GIT-182 로 Git 창 진입이 잦아지며 늘 보이게 됐지만, 원인은
그 전부터 있었다.

- **FR-GIT-210** 포커스가 터미널이 아닐 때 follow 는 **마지막으로 포커스됐던
  터미널**의 cwd 를 유지한다. 서버의 cwd 로 넘어가지 않는다. 그 터미널이 사라졌으면
  follow 는 "저장소 아님"이다 — 임의의 리포를 가리키지 않는다 (FR-GIT-10 과 같은
  뜻이다).

### 3.7 신규 — 버튼 라벨의 언어

- **FR-GIT-200** Git 표면의 **버튼 라벨은 영어**로 쓴다. `스테이지`·`언스테이지`·
  `버리기`·`모두 스테이지`·`해제`·`트리`·`플랫`·`실행`·`취소`·`복사`·`닫기`·
  `적용`·`이동`·`생성`·`되돌리기`·`다시 시도` 등이 대상이다.
  - 근거: git 자체의 어휘(stage·unstage·discard·stash·amend)가 영어이고 화면에
    이미 `Fetch`·`Pull`·`Push`·`Commit`·`Apply`·`Pop`·`Drop` 이 영어로 서 있다.
    같은 줄에서 한글과 영어가 섞이면 어느 것이 git 명령인지 흐려진다.
- **FR-GIT-201** 다이얼로그의 **선택지 버튼**도 같다 (dirty checkout 3선택,
  이름 충돌 선택지).
- **FR-GIT-202** **버튼이 아닌 것은 바꾸지 않는다** — 안내문·사유·오류 메시지·
  placeholder·툴팁(`title`)·그룹 머리는 한글로 남는다. 그것들은 설명이고, 설명은
  읽는 사람의 말이어야 한다.

### 3.8 신규 — 폼 컨트롤의 테마

지금은 체크박스·라디오가 **브라우저 기본 위젯**이다. 앱의 테마(44종)와 무관한 색
으로 그려져 어두운 테마에서 흰 사각형이 튀고, 라이트 테마에서도 앱의 accent 와
어긋난다. 실제로 보이는 자리: 커밋의 `amend`, 커밋 옵션 3개(sign-off·no-verify·
commit all), Fetch·Pull·Push 의 `▾` 옵션, Diff 의 `Ignore Whitespace`, stash 생성
옵션 2개, 브랜치 생성의 checkout 옵션, 설정 모달의 알림 항목.

- **FR-GIT-203** 체크박스·라디오는 **앱 테마의 토큰**(`--bg`·`--border`·`--accent`)
  으로 그린다. 브라우저 기본 위젯을 그대로 쓰지 않는다.
- **FR-GIT-204** 상태는 **채움**으로 구분한다: 꺼짐은 빈 상자(투명 바탕 +
  `--text-dim` 테두리), 켜짐은 accent 로 **꽉 찬** 상자다. **체크 표식(✓)을 그리지
  않는다.**
  - 근거: 14 px 상자 안의 획은 어떤 방식으로 그려도(회전 테두리·SVG 마스크·
    clip-path·글리프) 끝이 뭉툭하거나 비율이 어긋나 지저분하다 — 4종을 실제로
    그려 비교한 결과다.
  - 비었나 찼나는 색이 아니라 **면적**의 차이이므로 흑백으로 떨어뜨려도 남는다.
    비활성은 흐림, 포커스는 윤곽선으로 따로 구분한다.
- **FR-GIT-205** `select` 도 같은 토큰으로 그린다.
- **FR-GIT-206** 컨트롤 상자는 **14 px**, 그것을 담은 라벨 행은 **22 px** 이상이다.
  히트 영역은 상자가 아니라 행 전체다 — 상자를 키워 라벨보다 무겁게 만들지 않는다.

**범위 주의**: 이 요구는 Git 표면만이 아니라 **앱 전역**이다. 컨트롤을 두 벌로
그리면 같은 체크박스가 자리마다 달라 보인다.

# 채널 압축 조사·측정 — 2026-11-24

> 상위: `docs/internal/PERF_OPTIMIZATION_SRS.md` FR-CON-9 · D-11 · `perf/CHANNEL_PROTOCOL.md` A-C1
> 조사용 코드는 저장소 밖(`/private/tmp/otter-zip-spike/`)에 두었고 커밋하지 않았다.

## 1. 결론

> **§8 의 추가 측정(sockudo-ws·yawc × 압축·비압축 × 로컬·원격)이 이 절을 보완한다.** 로컬 손해와 원격 이득의 숫자, 그리고 "sockudo-ws 로 전부 압축" 안과 "yawc 로 원격만 압축" 안의 비교가 §8.4 에 있다.

- **권장 crate: `yawc` 0.5** (`default-features = false`). 표준 permessage-deflate 를 지원하고, 연결마다 압축을 켜고 끌 수 있으며, 압축 여부와 상관없이 **스트림 타입이 하나**다. 실제 Chromium 과 붙여 압축 협상과 텍스트·바이너리 왕복을 확인했다(§3).
- **설정: context takeover 켬, 압축 단계 기본(6), 최소 압축 크기 임계값 없음.** 원격 주소일 때만 압축을 제안한다(FR-CON-9).
- **사용자 결정이 하나 필요하다: yawc 의 라이선스는 MPL-2.0 이다.** 지금 `rust/deny.toml` 허용 목록에 없다. 쓰려면 `notify`·`xxhash-rust` 처럼 그 crate 에만 예외를 연다. MPL-2.0 은 파일 단위 copyleft 라서, yawc 파일을 고치지 않고 쓰기만 하면 우리 코드에는 의무가 생기지 않는다.

## 3. 브라우저 확인 (yawc + Chromium)

시험 서버(hyper 1 + `WebSocket::upgrade_with_options`)에 Playwright Chromium 으로 두 번 붙었다. 한 번은 압축을 켜서, 한 번은 꺼서 붙었다.

| 연결 | 응답 `Sec-WebSocket-Extensions` | 브라우저 `ws.extensions` | 텍스트 왕복 | 바이너리 3 B 보내기 | 바이너리 100 KB 받기 |

## 4. 측정 — 압축률과 CPU

- 방법: `scripts/perf/agent-sim.py` 의 출력을 30초 떴다(초당 60줄, 5초마다 몰아치기). 파이프 read 한 번을 메시지 하나로 보았다.
- 실제 텍스트 표본으로는 저장소의 색 입힌 `git log -p` 2.3 MB 를 썼다.
- 압축은 Rust `flate2`(yawc 와 같은 miniz 백엔드)로 했다. RFC 7692 대로 메시지마다 sync flush 를 하고, 꼬리 4바이트를 뗐다. CPU 는 5회 중 가장 빠른 값이다(M4).
- 비율은 압축 후 크기 ÷ 원래 크기다. 작을수록 좋다.

| 표본 (메시지 평균) | 독립 L6 (no takeover) | **takeover L6** | takeover L1 | 독립 L1 |
|---|---|---|---|---|
| 줄 출력 (153 B, 30초 229 KB) | 0.60 · 77 ms/MB | **0.26 (3.8배) · 39 ms/MB** | 0.36 · 14 ms/MB | 0.64 · 51 ms/MB |
| TUI 출력 (2 KB, 30초 1.1 MB) | 0.26 · 10 ms/MB | **0.15 (6.7배) · 24 ms/MB** | 0.25 · 3 ms/MB | 0.31 · 6 ms/MB |
| 실제 diff, 4 KB 조각 | 0.31 · 11 ms/MB | **0.20 (5.0배) · 16 ms/MB** | 0.28 · 5 ms/MB | 0.34 · 5 ms/MB |
| 실제 diff, 64 KB 조각 | 0.20 · 9 ms/MB | **0.19 (5.3배) · 11 ms/MB** | 0.27 · 5 ms/MB | 0.28 · 3 ms/MB |
| JSON workspace full (3.6 KB, 창 5×탭 3) | 0.11 | **0.11 (8.8배)** | 0.14 | 0.14 |
| JSON activity delta (295 B × 200) | 0.67 | **0.07 (13.4배)** | 0.08 | 0.67 |

읽는 법:
- **메시지가 작을수록 context takeover 의 몫이 크다.** 작은 메시지는 혼자 압축하면 거의 줄지 않는다(delta 0.67, 줄 출력 0.60). 앞 메시지를 사전으로 쓰면 13배까지 준다. 채널의 메시지는 대부분 수백 B~수 KB 다.
- agent-sim 은 낱말이 적은 흉내라 실제보다 잘 줄어든다. 실제 diff 표본은 takeover L6 에서 5배다. 실제 에이전트 출력은 **4~6배**로 보면 된다.

## 7. 위험과 남은 일

- **라이선스**: MPL-2.0 → `deny.toml` 예외가 필요하다(사용자 결정).
- **의존성 중복**: yawc 가 `rand 0.8` 을 끌어온다. 워크스페이스는 0.10 이라 `multiple-versions = "warn"` 경고가 하나 늘어난다. `nom 8`·`crossbeam-queue`·`pin-project`·`sha1` 이 새로 들어온다.
- **성숙도**: 0.x 이고 한 조직이 관리한다. tungstenite 보다 사용자가 훨씬 적다. API 가 바뀔 수 있으므로 판을 고정한다.
- **우리 서버에 붙이는 자리**: 우리 핸들러는 hyper `Request` 대신 자체 `Req` 를 받는다. 길은 둘이다.
  1. `Req` 에서 hyper `Request` 를 만들어 `upgrade_with_options` 를 부른다.
  2. 핸드셰이크 응답은 지금처럼 우리가 만들고 `WebSocket::from_stream_with_extensions(io, Role::Server, 합의한 확장 문자열, Options)` 를 부른다. 이 경우 확장 합의(클라이언트 제안 파싱) 몇 줄을 우리가 갖는다.

  C6 착수 때 둘 중 하나를 시험으로 고른다.
- **"두 벌" 정리 범위**: 서버에서 tungstenite 를 쓰는 곳은 채널(`channel/mod.rs`), LSP(`lsp_api.rs`), 옛 `/ws`(C6 에서 사라짐), `toolhub/conn.rs`(`SafeConn`), `hub/replyseat.rs`, 그리고 시험의 WebSocket 클라이언트다. D-11 대로 하나로 맞추려면 이 전부를 yawc 로 옮긴다. yawc 는 클라이언트도 된다.
- **압축 부채널(CRIME 류)**: 같은 압축 문맥에 비밀(터미널에 찍힌 토큰 등)과 공격자가 고를 수 있는 내용이 섞이면, 망 관찰자가 암호문 크기로 비밀을 추측할 수 있다. 원격 경로(Tailscale/WireGuard)는 암호화돼 있다. 공격하려면 출력 내용을 조종하면서 크기를 반복해서 관찰해야 하므로 현실 위험은 낮다고 본다. 기록해 둔다.
- 측정은 흉내 출력과 diff 표본으로 했다. M2 뒤 `scenario.mjs` remote 단계에서 실제 채널 바이트로 다시 잰다.

## 8. 추가 측정 — sockudo-ws·yawc × 압축·비압축 × 로컬·원격

### 8.1 방법

- 서버: 두 crate 를 같은 시험 서버(hyper 1 업그레이드)에 올렸다.
  - yawc 는 `upgrade_with_options` 를 쓴다.
  - sockudo-ws 는 `negotiate_server_deflate` 로 협상하고 101 응답을 우리가 만든 뒤 `CompressedWebSocketStream::server`·`WebSocketStream::server` 를 쓴다.
  - 압축은 두 crate 모두 takeover 켬, 단계 6, 임계값 0 으로 같게 맞췄다.
- 브라우저 확인: 두 crate 모두 Chromium 이 `permessage-deflate` 를 협상했다(`ws.extensions`). 텍스트·바이너리 왕복, 키 왕복, 500 KB 스냅숏이 모두 오갔다.
- 재생: 앞서 뜬 agent-sim 출력(TUI 555 프레임, 줄 출력 1497 프레임)을 30초에 고르게 보냈다. 5초마다 200줄 몰아치기를 4 KB 조각으로 더했다. 메시지마다 `[종류][보낸 시각 µs]` 9바이트 머리를 붙였다.
- 망:
  - 로컬은 루프백이다.
  - 원격은 **직접 만든 TCP 프록시**로 흉내 냈다. 왕복 150 ms(한쪽 75 ms)를 걸고, 방향마다 대역폭 2 Mbps·10 Mbps 를 1460 B 단위로 맞췄다.
  - **CDP 망 제한(`Network.emulateNetworkConditions`)은 WebSocket 에 실제 망처럼 걸리지 않았다.** 지연 150 ms 를 걸어도 평상시 프레임 지연이 15 ms 였고, 압축된 94 KB 스냅숏이 2 Mbps 에서 1.7초 걸렸다(계산상 0.5초). 그래서 그 값은 버렸다.
- 지표:
  - 와이어 바이트: 서버 TCP 계층에서 셌다(30초 재생분, 스냅숏 따로).
  - 서버 CPU: 프로세스 CPU 시간(getrusage)을 재생한 원래 데이터 1 MB 로 나눴다.
  - 메인 스레드: CDP `Performance.getMetrics` 의 TaskDuration 이다(같은 재생을 따로 한 번 더 돌려 쟀다).
  - 지연: 서버가 보낸 시각부터 브라우저 `onmessage` 까지다. 같은 기계의 시계이고 해상도는 0.1 ms 다.
  - 키 왕복: 250 ms 마다 작은 텍스트를 보내고 서버가 같은 것을 돌려준다.
  - 연결당 메모리: 조건마다 새 서버 프로세스를 띄웠다. 연결 50개를 열어 각자 스냅숏을 네 번 주고받은 뒤의 RSS 증가를 50으로 나눴다. 세 번 재서 가운데 값을 쓴다.
- 두 crate 를 동시에 돌렸다. CPU 는 프로세스별로 재므로 서로 섞이지 않는다. 지연에는 약간의 잡음이 섞였을 수 있다.

### 8.3 로컬 손해와 원격 이득 (한 줄씩)

- **로컬 손해(압축을 켜면)**:
  - 서버 CPU 가 약 3배다(TUI 34 → 105~110 ms/MB). 절대값은 에이전트 하나의 TUI 30초에 40 ms 에서 130 ms 로, 코어 하나의 0.4% 다.
  - 메시지 지연이 TUI 에서 +0.1~0.2 ms, 작은 줄 출력에서 **+1.2~1.4 ms(p50)** 다.
  - 스냅숏 도착이 1 ms 에서 7~10 ms 로 는다. 압축 CPU 가 약 7 ms 든다.
  - 키 왕복 p95 는 0.4~1.1 ms 에서 0.5~3.2 ms 로 흔들렸다. 잡음 수준이다.
  - 메모리는 연결당 +469 KB(yawc)·+687 KB(sockudo-ws) 다.
  - 메인 스레드 사용률은 차이가 없다(0.1~0.3%).
- **원격 이득(압축을 켜면)**:
  - 바이트가 TUI −85%, 줄 −79% 다.
  - 몰아치기 p95 가 2 Mbps 에서 160 → 90 ms, 10 Mbps 에서 93~96 → 79~84 ms 다.
  - 스냅숏 500 KB 가 2 Mbps 에서 **2.08 → 0.46초**, 10 Mbps 에서 0.48 → 0.16초다.
  - 평상시 지연은 2 Mbps TUI 에서 p95 86 → 80 ms 이고, 10 Mbps 에서는 차이가 없다.
- **crate 차이**:
  - 바이트·CPU·지연은 두 crate 가 측정 오차 안에서 같다.
  - 다른 것은 셋이다: 압축 연결의 메모리(sockudo-ws 가 연결당 약 220 KB 더 든다), 라이선스, 타입 구조.

### 8.4 두 안의 비교와 권장안

| | A. sockudo-ws 로 모든 연결 압축 | B. yawc 로 원격만 압축 |
|---|---|---|
| 라이선스 | MIT — `deny.toml` 변경 없음 | MPL-2.0 — `deny.toml` 예외 필요 |
| 코드 갈래 | 늘 `CompressedWebSocketStream` 하나. 비압축 타입을 쓰지 않으므로 "두 벌" 문제가 사라진다. 단 deflate 를 제안하지 않는 클라이언트는 거절해야 한다. 주요 브라우저는 모두 제안하고, 서버 시험·otterctl 의 WebSocket 클라이언트도 제안해야 한다 | `WebSocket` 하나. 원격 판정에 따라 `Options` 만 다르다 |
| 로컬 비용 | CPU 약 3배(코어 1% 미만), 작은 메시지 지연 +1~1.5 ms, 스냅숏 +7~9 ms, 탭당 +687 KB | 0 |
| 원격 이득 | 같다 (바이트 −80~85%, 2 Mbps 스냅숏 2.1 → 0.46초) | 같다 |
| 성숙도 | 3.x, 18만 내려받기, 기능이 많은 crate(HTTP/2·3, io_uring 등). 최소 기능으로 써야 한다 | 0.5, 95만 내려받기 |
| 입력 지연 예산(50 ms)과의 관계 | 로컬 증가분 1~1.5 ms 는 예산의 3% 안이다 | 영향 없음 |

**권장: 두 안 모두 성능 요구(NFR)를 만족한다.** 고르는 기준은 성능이 아니라 라이선스와 코드 구조다.
- **라이선스 예외를 열고 싶지 않으면 A(sockudo-ws 전부 압축)** 를 권한다. 로컬에서 잃는 것이 측정상 작다. 지연 +1.5 ms 이하, CPU 코어 1% 미만, 탭당 0.7 MB 다. 그리고 압축 여부 분기가 없어 코드가 한 갈래가 된다. 조건은 셋이다: 기능을 `permessage-deflate,tokio-runtime` 만 켤 것, 판을 고정할 것, deflate 를 제안하지 않는 연결은 거절할 것.
- **로컬 비용을 0 으로 두고 싶고 MPL-2.0 예외를 받아들일 수 있으면 B(yawc 원격만)** 다.
- A 를 고르면 §1 의 권장 crate 를 sockudo-ws 로 바꾸고, FR-CON-9("원격 접속에서만 켠다")를 "모든 연결에서 켠다"로 고쳐야 한다(사용자 결정).

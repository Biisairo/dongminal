## 3. 이 세션이 값을 치르고 안 것

**다음 세션이 같은 값을 다시 치르지 않게** 적는다.

### 3-1. 이 저장소의 게이트는 진짜다. 전제를 의심하지 마라

`make gates` **33종 전량 통과** 상태에서 감사를 시작했다. 그래서 214건은 거의
전부 **게이트가 재지 않는 표면**에 있다. 요청에 담긴 전제 하나는 사실과 달랐다:

| 분류 | 실측 |
|---|---:|
| 미구현 (완료 표기인데 코드 없음) | **0** |
| 잘못 구현 | **0** |
| 고아 SRS | **0** |
| 1급 코드의 TODO/FIXME/HACK | **0** |
| 생성물(`errors.md`·`decisions.md`) 비동기 | **0** (diff 0줄) |

**손으로 적는 문서만 낡았다.** 기계가 재는 문서는 하나도 낡지 않았다.

### 3-2. 게이트의 사각지대가 곧 발견의 자리다

| 게이트 | 보는 것 | **못 보는 것** |
|---|---|---|
| `check-hardcoded-color` | `web/*.css` 의 `:root` **밖** | `:root` **안** · `web/js/**` · `index.html` → 색 위반 **25건** |
| `check-i18n` | **한글** 리터럴 | **영어** 리터럴 → 사용자 노출 영문 **113개** |
| `check-focus` | `outline:none` 쓴 자리의 짝 | **애초에 링을 안 그리는 자리** → 버튼 30종 |
| `check-font-size` | 글자 크기 | **상자 크기** → 배율 2.29 에서 22px 상자에 27px 글자 |
| `check-css-vars` 등 | `readdirSync('web')` | **비재귀** → 하위 디렉터리 |

B2·B4 의 게이트를 세울 때 이 표를 먼저 봐라. 새 검사도 같은 함정에 빠질 수 있다.

### 3-3. `DESIGN_TOKENS_SRS` §7.6 잔여표의 **세는 방법이 틀렸다**

표는 *"키트 클래스와 **함께 붙는** 옛 클래스를 열거한다"* 로 채운다. 그래서
**한 번도 병기되지 않은 것을 못 본다.** 표는 "탭 넷만 남았다" 고 말하지만 실제로는
버튼 **여섯 종 98개**가 남아 있다(`.sc-key`·`.mkb-btn`·`.fe-render`·`.fe-offer-no`
넷은 표에 **아예 없다**). 이 표를 믿고 `style-kit.css` 의 D-5 를 닫으면 닫히지
않은 채로 닫힌다. **B2 에서 표의 채우는 방법을 고쳐라.**

### 3-4. 감사 보고서는 근거이지 정답이 아니다 — 세 번 틀렸다

감사 에이전트가 낸 214건 중 셋이 틀렸고, **코드를 직접 읽어서** 잡았다. B2 에서도
보고서를 그대로 믿지 말고 확인해라.

1. **참조 필드가 둘이 아니라 다섯이었다.** 감사는 `Members`·`Member.Worktree` 만
   지목했으나 타입을 읽어 `Record.Worktree`·`Record.Coordinator`·
   `Member.FilesModified` 를 더 찾았다. `Coordinator` 공유는 테스트로 재현됐다.
2. **`jsonFail`→`fsFail` 축소 제안은 틀렸다.** 같은 것은 본문뿐이고, `jsonFail` 은
   `failFn` 타입의 구현 둘 중 하나이며 나머지가 터미널 표면의 `textFail` 이다 —
   줄이면 `uploadInto`·`serveDownload` 가 공유하는 추상이 깨진다. 게다가
   `jsonFail` 은 **이미 헤더를 세우고 있었다**.
3. **`failRead` 로의 이동 제안은 더 나빴다.** `failRead` 는 코드를 상태에서
   파생하므로 413 이 `body_too_big`(좁음) → `too_large`(넓음)로 **물러선다**.
   `codes_doc.go` 가 두 코드에 서로 다른 복구 안내를 달아 두었다.

근거는 `SAFETY_CORRECTNESS_SRS.md` 의 FR-SAF-4·12·13 주석 블록에 있다.

### 3-5. 복사가 잠복 버그를 드러낸다 — 놀라지 마라

`run.Store` 에 복사를 넣자 `TestPreamble_WaitsForLateHandoff` 가 깨졌다. 조사해
보니 **그 테스트가 데이터 레이스에 기대어 통과하고 있었다**: `apiRunPreamble` 이
늦게 오는 인수인계를 기다린 뒤 멤버만 다시 읽고 `rec` 는 낡은 것을 썼는데,
`rec.Members` 가 저장소와 공유된 덕에 뒤늦은 요약이 비쳤다. `rec` 도 다시 읽게
고쳤다(`handlers_runs.go`).

**교훈: 공유를 끊으면 그 공유에 기대던 코드가 드러난다.** B2 에서 렌더 경로를
건드릴 때 같은 일이 난다 — 전량 검사로 판정해라.

### 3-6. e2e 는 부하에 민감한 자리가 있다

1회차 전량에서 **1,723건 통과 · 실패 1 · flaky 1**.

- 실패: `git-menu.spec.ts` "Esc·바깥 클릭으로 닫힌다". **격리에서는 65/65 통과**
  (`--repeat-each=5`). 제 변경과의 연결은 **조사해서 배제했다** — `defer` 는
  자기 네이티브 `setTimeout` 을 쓰고(`timer-hub.js:219`) 고친 `_tick`(`kind==='after'`)을
  지나지 않으며, 메뉴의 `keydown` 은 동기 등록이다(`ui-kit.js:492`). 그 자리
  주석이 이 증상의 전력을 이미 적어 두었다("H14 · F9").
- flaky: `git-worktrees.spec.ts` V151. `cloneRun` 이 worktree 포인터 동일성을
  깨지만 `WorktreeTargets` 가 **`Path` 로** 중복을 거르므로 무관하다.

**2회차는 완전히 깨끗했다**: 통과 **1,725** · 실패 **0** · flaky **0** ·
`make e2e` `EXIT=0` (*"e2e ok — 8샤드 전부"*). 그러므로 1회차의 둘은 **부하 민감
flake 로 확정**이며 B1 의 회귀가 아니다. 판정 근거 셋: ① 2회차 전량 녹색
② 격리 `--repeat-each=5` 에서 65/65 ③ 위의 경로 분석.

`parity-flaky.txt` 는 `0` 이다(알려진 flaky 없음). 그러니 이 둘을 그냥 넘기지 마라.

## 4. 변하지 않는 규약

`CONTRIBUTING.md` 가 원본이다. 어기지 마라.

1. **SRS → 테스트 → 코드.** RED 를 **실제로** 보고 나서 구현한다. 이미 구현했다면
   `git stash` 로 코드만 되돌려 확인한다.
2. **게이트를 느슨하게 만들어 통과시키지 않는다.** `make gates` 가 막으면 코드를
   고친다. 게이트를 고치는 것은 그 게이트가 재는 것이 바뀌었을 때뿐이다.
3. **새 게이트를 세우면 탐침으로 검출을 확인하고 지운다.**
4. **동작을 바꾸면 근거 문서를 같은 변경에서 고친다.** 이전 동작 / 새 동작 /
   이유 셋을 적는다.
5. **커밋 메시지에 FR 번호를 단다. AI 서명(`Co-Authored-By` 등)을 넣지 않는다.**
6. **생성물을 직접 고치지 않는다** — `docs/external/errors.md`(원천
   `apierr/codes_doc.go`) · `docs/internal/decisions.md`(원천 SRS 결정 항목).
7. **색은 팔레트를 바꾸지 않는다** (`DESIGN_TOKENS_SRS` FR-TOK-16). 테마는
   **54종**이고, 모든 색은 기존 토큰의 조합으로만 만든다. 새 hex 를 넣지 마라.

로 받아라.

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 이렇다.

> **"작업을 하다보면 git 이 있는데 editor 에 색상 표시가 안 되고 git 에서도 ? 만
> 뜨고 내용이 안 뜨는 경우가 있어. 그 경우 중 하나가 git submodule 인 경우인 것
> 같고, 다른 경우들도 살펴보고 고쳐줘야 해."**

조사 결과 이 한 문장 뒤에 **서로 다른 네 개의 결함**이 있었다. 셋은 실측으로
재현했고 하나는 코드 판정으로 확정했다.

| # | 사실 | 사용자에게 보이는 모습 |
|---|---|---|
| 1 | 중첩 저장소는 `--untracked-files=all` 로도 `? nested/` 한 줄로 축약된다 | Git 패널에 `?` 한 줄. 눌러도 Diff 가 비어 있다 |
| 2 | 그 경로는 **끝에 `/` 가 붙어** 탐색기의 어떤 노드와도 짝이 맞지 않는다 | 그 폴더도, 그 안의 파일도 색이 없다 |
| 3 | 등록된 서브모듈은 **폴더인데 파일 맵**으로 들어간다 | 같음 — 폴더에 색이 없다 |
| 4 | `repo` 는 심볼릭 링크를 푼 값이고 루트는 원본이라 비교가 어긋난다 | 그 창의 색이 **영구히** 꺼진다 |

본 SRS 는 넷을 함께 닫는다. 넷이 한 문서인 이유는 **하나만 고치면 나머지가 그대로
같은 증상을 만들기 때문**이다 — 사용자가 본 것은 네 결함의 합집합이지 어느 하나가
아니다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **S** 서버 표면 | 상태 항목이 디렉터리임을 서버가 확정해 싣는다. 미추적 경로의 `/` 정규화 |
| **X** 탐색기 | 디렉터리 항목의 색, 하위 상속, 접어 올림 |
| **G** Git 패널 | 디렉터리 행의 표시와 클릭 결과, 그 자리의 진입점 |
| **R** 복구 | 루트 판정의 정규화, `_gitOff` 고착 해제 |
| **A** 저장소 안의 루트 | Editor 루트가 저장소 루트가 아닐 때의 색 |

**미포함:** §6 비목표. 특히 **서브모듈 내부를 관측하지 않는다** (D-DIR-5).

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|---|---|
| **디렉터리 항목 (dir entry)** | `git status` 가 파일이 아니라 디렉터리 하나로 보고한 상태 항목 |
| **중첩 저장소 (nested repo)** | 저장소 워킹 트리 안에 있는 **별개의** 저장소. `.gitmodules` 에 등록되지 않았다 |
| **서브모듈 (submodule)** | `.gitmodules` 에 등록되어 gitlink(모드 160000)로 추적되는 디렉터리 |
| **상속 색 (inherited status)** | 디렉터리 항목의 상태를 그 하위 전체가 물려받은 것 |
| **저장소 안의 루트** | Editor 루트가 저장소의 루트가 아니라 그 **하위**인 상태 |

## 2. 현재 상태 (조사로 확정한 사실)

**추측이 아닌 실측과 파일:줄로만 적는다.** 픽스처는 부모 저장소 하나에 등록된
서브모듈(`sub`) · 중첩 저장소(`nested`) · 일반 미추적 폴더(`plaindir`) · 빈
폴더(`emptydir`) 를 둔 것이다.

### 2.1 서버는 이미 `-uall` 을 준다. 그래도 중첩 저장소는 접힌다

```
$ git status --porcelain=v2 -uall
1 .M S.MU 160000 160000 160000 1a86970c… 1a86970c… sub
? nested/
? plaindir/a.txt
? plaindir/b.txt
```

`--untracked-files=all` 은 `status.go:249` 가 이미 준다 (FR-GIT-215). 그 옵션은
**일반 폴더를 파일 단위로 펴지만**(`plaindir/a.txt`·`b.txt`) **중첩 저장소는 펴지
못한다** — git 은 다른 저장소 안을 들여다보지 않기 때문이다.

**빈 폴더(`emptydir`)는 어느 옵션으로도 보고되지 않는다.** git 이 빈 디렉터리를
추적하지 않기 때문이다.

> **따라서 `?` 로 오는 디렉터리 항목은 사실상 중첩 저장소 하나뿐이다.** 이 사실이
> FR-DIR-22(그 자리에서 저장소로 추가) 를 성립시킨다 — 대상이 무엇인지 알기 때문에
> 진입점을 놓을 수 있다.

### 2.2 두 종류의 디렉터리 항목이 서로 다른 문법으로 온다

| 종류 | 레코드 | 경로 | 구별 근거 |
|---|---|---|---|
| 중첩 저장소 | `? nested/` | **끝에 `/`** | 경로의 마지막 문자 |
| 서브모듈 | `1 .M S.MU … sub` | 슬래시 없음 | `sub` 필드가 `S` 로 시작 |

`sub` 필드는 이미 파싱돼 `FileEntry.Sub` 로 보존된다 (`status.go:26`) — `N...` 이면
서브모듈이 아니라는 뜻이라 생략된다. **정보는 이미 서버에 있고 클라이언트가 그것을
쓰지 않는다.**

### 2.3 탐색기는 폴더 색을 `_dirSt` 에서만 찾는다

```js
web/js/ui/file-tree-paint.js:321-325
  _stOf(p,kind){
    const rel=this._rel(p);
    if(!rel) return '';
    return (kind==='dir'?this._dirSt.get(rel):this._st.get(rel))||'';
  }
```

`_dirSt` 는 `_rollup(m)` 의 결과이고, `_rollup` 은 **경로의 상위 조각만** 채운다
(`:302-310` 의 `p.lastIndexOf('/')` 루프). 그래서 `sub` 는 `_st['sub']='M'` 로
들어가지만 `_dirSt` 에는 없다 — 탐색기가 그 노드를 `kind==='dir'` 로 물으므로
**색이 나오지 않는다.**

FR-EDT-75("폴더 자신이 상태를 갖는 일은 없다 — git 은 폴더를 추적하지 않는다")가 이
구조의 근거였고, **그 전제가 서브모듈에서 거짓이다.** git 은 gitlink 를 통해
디렉터리 하나를 그대로 추적한다.

### 2.4 `nested/` 는 어떤 노드와도 짝이 맞지 않는다

```js
web/js/ui/file-tree.js:192-195
  _rel(p){
    if(p===this.root) return '';
    return p.slice(this.root==='/'?1:this.root.length+1);
  }
```

탐색기가 만드는 상대경로에는 끝 슬래시가 없다(`nested`). 상태 맵의 키는 `nested/`
다. **두 문자열은 같지 않다.** 그 결과 폴더에도, 그 안의 파일에도 색이 없다 —
하위 파일은 애초에 status 에 나오지도 않는다(§2.1).

`_rollup` 도 이 키를 상위로 접어 올리지 못한다. `lastIndexOf('/')` 가 **맨 끝의
슬래시**를 먼저 잡아 `nested` 를 폴더로 등록하는데, 우연히 맞는 그 한 겹은
루트 직하일 때뿐이고 `a/b/nested/` 는 `a/b/nested` 를 등록한 뒤 계속 올라간다 —
즉 지금도 접어 올림 일부는 동작하지만 **그것은 우연이고 문서화된 규칙이 아니다.**

### 2.5 심볼릭 링크 경로에서 색이 영구히 꺼진다

```js
web/js/ui/file-tree-paint.js:255
  if(d.repo!==this.root){this._gitOff=true;this._setStatus(null);return}
```

실측 — `/tmp/…/parent` 로 물었을 때의 응답이다.

```
requested = /tmp/claude-501/…/gt/parent            ← 원본 그대로
repo      = /private/tmp/claude-501/…/gt/parent    ← EvalSymlinks 를 지난 값
```

`this.root` 는 워크스페이스에 저장된 값(사용자가 추가한 형태)이므로 macOS 의
`/tmp` 처럼 링크가 낀 경로에서는 **비교가 반드시 어긋난다.** 그 순간 `_gitOff=true`
가 되고, 이 플래그를 되돌리는 코드가 없다 — **그 창의 색은 새로고침 전까지 영영
돌아오지 않는다.**

같은 고착이 4xx·503 에도 걸린다(`:249`). 503 은 "git 이 없다"이므로 고착이
관례대로 옳지만(GIT_REPO_MISSING 의 판정 관례), 404(`not_repo`)는 **그 사이에
`git init` 이 일어날 수 있는** 사유다. 통합 작업에서 좌측 pane 의 `git init` 버튼이
바로 그 일을 한다 — 고착이 남으면 init 직후에도 색이 없다.

### 2.6 Git 패널은 디렉터리 행을 파일로 취급한다

행을 클릭하면 `_openDiff(group,{path,origPath})` 가 선택을 옮기고 Diff 탭을 연다
(`panel-diff.js:46-49`, `:263`). 대상이 디렉터리면 diff 종단은 내용을 주지 못한다
— 실측에서 `/api/git/diff*` 는 `sub`·`nested/` 둘 다에 내용을 주지 않았다.

git 자신이 서브모듈에 주는 diff 는 두 줄뿐이다.

```
-Subproject commit 1a86970c…
+Subproject commit 1a86970c…-dirty
```

**이것을 파일 diff 처럼 보여 주는 것은 사용자를 돕지 않는다.** 사용자가 알아야 할
것은 "여기는 다른 저장소이고, 그 안의 변경은 이 저장소의 관측 대상이 아니다" 라는
사실과, **그 저장소로 가는 길**이다.

### 2.7 저장소 안의 루트는 색을 갖지 못한다

FR-EDT-69 는 색을 **루트가 저장소의 루트일 때만** 입힌다. 근거는 D-6("중첩 탐지는
펼침마다 `rev-parse` 가 붙는다")이었는데, 그 근거는 **펼침마다 판정하는 설계**를
기각한 것이지 **루트 한 번의 판정**을 기각한 것이 아니다. `status` 응답은 이미
`repo` 로 "이 경로가 속한 저장소의 루트"를 알려 주므로 추가 호출이 없다.

지금은 `~/repo/app/src` 를 Editor 로 추가하면 `~/repo/app` 이 저장소인데도 색이
전혀 없다. 사용자가 접수한 "git 이 있는데 색상 표시가 안 된다"에 이 경우가 포함될
수 있다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 S — 서버 표면

**FR-DIR-1.** `query.FileEntry` 에 `dir bool` 을 더한다. 참인 항목은 **파일이 아니라
디렉터리 하나**를 가리킨다. 판정 근거는 둘이며 서버가 확정한다.

| 근거 | 판정 |
|---|---|
| `?` 레코드의 경로가 `/` 로 끝난다 | `dir=true` |
| `1`·`2` 레코드의 `sub` 가 `S` 로 시작한다 | `dir=true` |

그 밖의 항목은 `dir=false` 다. **클라이언트가 경로의 마지막 문자로 판정하지
않는다** — 판정 자리가 둘이 되면 한쪽만 고쳐진다.

**FR-DIR-2.** `?` 레코드의 경로에서 **끝의 `/` 를 벗겨서 싣는다.** 벗긴 사실은
`dir:true` 가 보존한다.

경로 문법이 항목마다 달라지면 그 경로를 받는 모든 곳(탐색기 매칭·스테이지·
discard·ignore·diff)이 각자 슬래시를 처리해야 한다. **문법은 한 가지여야 한다.**

**FR-DIR-3.** 서브모듈 여부는 기존 `sub` 필드로 판정할 수 있으므로 새 필드를 더하지
않는다. `dir` 이 참인 항목 중 `sub` 가 비어 있으면 중첩 저장소, `S` 로 시작하면
서브모듈이다.

**FR-DIR-4.** `Total`(FR-GIT-14 의 배지)의 계산은 바뀌지 않는다 — 디렉터리 항목도
경로 하나로 센다.

**FR-DIR-5.** 응답에 `rootMatch bool` 을 더한다. **요청한 경로가 그 저장소의
루트인가**를 서버가 판정한 결과다.

클라이언트는 정규화를 알지 못하고 알 필요도 없다. 서버는 `repo` 를 `EvalSymlinks`
로 정규화하지만 `requested` 는 원본 그대로 싣는다(§2.5) — 그 둘을 클라이언트가
비교하게 두면 링크가 낀 경로에서 반드시 어긋난다. **비교는 정규화를 아는 쪽에서
한다.**

**FR-DIR-6.** 중첩 저장소·서브모듈 경로를 저장소로 추가할 수 있는지 판정하는
종단을 신설하지 않는다. 기존 `POST /api/editors/add`(FR-EDT-23·33)가 이미 존재
검사와 저장소 루트 판정을 하고, 그것이 그대로 이 자리의 계약이다.

### 3.2 묶음 X — 탐색기의 색

**FR-DIR-10.** 상태 맵을 셋으로 나눈다 — 파일 맵(`_st`) · 접어 올림 맵(`_dirSt`) ·
**디렉터리 항목 맵(`_dirOwn`)**. `dir:true` 인 항목은 `_dirOwn` 으로 간다.

**FR-DIR-11. FR-EDT-75 를 개정한다.** 폴더가 자기 상태를 가질 수 있다. 근거는
gitlink(모드 160000)와 중첩 저장소이며, 둘 다 git 이 **디렉터리 하나를** 상태의
단위로 보고한 것이다. 개정된 규칙은 이렇다.

```
폴더의 색  =  자기 항목(_dirOwn)  >  접어 올림(_dirSt)
```

자기 항목이 있으면 그것이 이긴다 — 접어 올림은 **하위의 사실을 요약한 것**이고,
자기 항목은 **그 폴더 자신에 대한 git 의 보고**다.

**FR-DIR-12.** 디렉터리 항목의 색은 **하위 전체가 상속한다.** 하위에 자기 상태를
가진 항목이 있으면 그쪽이 이긴다.

상속이 필요한 이유는 §2.1 이다 — 중첩 저장소 안의 파일은 부모의 status 에 **결코
나오지 않는다.** 상속이 없으면 사용자는 "폴더는 초록인데 안은 전부 무색" 을 본다.

**FR-DIR-13.** 접어 올림(FR-EDT-73·74)은 디렉터리 항목도 대상으로 삼는다. 우선순위
표(`EDITOR_TREE_ST_RANK`)와 삭제 제외 규칙은 그대로다 (D-5).

**FR-DIR-14.** 부분 스테이지의 노랑(FR-EDT-72a)은 디렉터리 항목에도 그대로
적용한다 — 서브모듈은 staged 와 unstaged 를 함께 가질 수 있다(실측의 `S.MU` 는
워킹 트리 쪽 변경이다).

**FR-DIR-15.** 상속 색은 **표시에만** 쓴다. 스테이지·discard 같은 조작의 대상
경로를 상속으로 파생시키지 않는다 — 그 조작의 대상은 언제나 status 가 실제로 준
경로다.

### 3.3 묶음 G — Git 패널의 디렉터리 행

**FR-DIR-20.** 디렉터리 항목의 행은 그것이 디렉터리임을 보인다. 표시는 경로 뒤의
`/` 이며, **`dir:true` 에서 파생한다** (경로 문자열이 아니라).

**FR-DIR-21.** 디렉터리 행을 고르면 Diff 탭은 **파일 diff 대신 사유와 진입점**을
보인다. 문구는 종류에 따라 갈린다.

| 종류 | 문구 |
|---|---|
| 서브모듈 | `서브모듈입니다 — 이 저장소는 커밋 하나로만 이 폴더를 추적합니다. 안의 변경은 여기서 보이지 않습니다.` |
| 중첩 저장소 | `다른 저장소입니다 — 이 저장소는 안을 들여다보지 않습니다.` |

**FR-DIR-22.** 그 자리에 진입점 하나를 둔다 — **`저장소로 추가`**. 누르면 그 경로가
Editor 목록과 Git 핀에 함께 더해지고(FR-EDT-33·39), 그 저장소의 창으로 이동한다.

이미 목록에 있으면 버튼은 `저장소로 이동` 이 되고 창 전환만 한다.

**FR-DIR-23.** 스테이지·언스테이지·discard·ignore 는 디렉터리 항목에도 종전대로
동작한다 (`git add <dir>` 이 성립한다). **막지 않는다** — 사용자가 서브모듈의
커밋 이동을 스테이지하는 것은 정상적인 작업이다.

**FR-DIR-24.** Changes 의 트리 보기에서 디렉터리 항목은 **잎(leaf)** 이다. 자기
이름의 폴더 노드를 만들지 않는다 — 그 폴더 안에 다른 항목이 있을 수 없으므로
(§2.1) 접히는 노드를 만들면 눌러도 아무것도 없는 자리가 된다.

### 3.4 묶음 R — 판정과 복구

**FR-DIR-30.** 루트가 저장소의 루트인지는 **`rootMatch` 로 판정한다** (FR-DIR-5).
클라이언트가 경로 문자열을 비교하지 않는다.

**FR-DIR-31.** `_gitOff` 는 **되돌릴 수 있는 상태**다. 사유마다 수명이 다르다.

| 사유 | 처리 |
|---|---|
| 503 (git 없음) | 굳힌다 — 다시 물어도 같다 (기존 관례) |
| 404 `not_repo` · 그 밖의 4xx | **굳히지 않는다.** 폴링 주기를 늦춰(`EDITOR_GIT_BACKOFF_MS`) 계속 관측한다 |
| `rootMatch=false` | 굳히지 않는다 — 저장소가 나중에 생길 수 있다 |
| 전송 실패 · 5xx | 이번 회차만 건너뛴다 (기존) |

**근거.** 통합 작업의 `git init` 버튼(REPO_TAB_UNIFY_SRS)이 바로 이 404 를 참에서
거짓으로 바꾸는 조작이다. 굳혀 두면 init 직후에도 색이 없고, 사용자는 init 이
실패했다고 읽는다.

**FR-DIR-32.** 창이 활성화되는 순간(FR-EDT-78 의 즉시 갱신 계기)에는 백오프를
무시하고 한 번 관측한다.

### 3.5 묶음 A — 저장소 안의 루트

**FR-DIR-40. FR-EDT-69 를 개정한다.** Editor 루트가 저장소의 **안**이면 그 저장소의
상태로 색을 입힌다. 색이 없는 경우는 이제 **저장소가 아예 없을 때뿐**이다.

**FR-DIR-41.** 상태 경로의 기준은 언제나 **저장소 루트**다. 탐색기는 자기 루트가
저장소 루트보다 깊으면 그 차이(`repoPrefix`)를 상대경로 앞에 붙여 맞춘다.

```
저장소 루트  /Users/me/app
Editor 루트  /Users/me/app/src        →  repoPrefix = "src/"
트리의 노드  /Users/me/app/src/a.ts   →  status 의 키 "src/a.ts"
```

**FR-DIR-42.** `repoPrefix` 는 서버가 준 `repo` 와 **서버가 준 정규화 결과**로
계산한다. 클라이언트가 심볼릭 링크를 풀 수 없으므로, 서버는 `rootMatch` 와 함께
**요청 경로의 정규화 결과**(`requestedResolved`)를 싣는다. 접두 계산은 정규화된
두 값 사이에서만 한다.

**FR-DIR-43.** 루트가 저장소 안일 때 **접어 올림은 루트 밖으로 새지 않는다** —
루트보다 위의 경로는 애초에 트리에 없으므로 계산에서 버린다.

### 3.6 비기능 요구 (NFR)

**NFR-DIR-1.** git 실행 횟수가 늘지 않는다. 본 SRS 의 모든 판정은 **기존
`GET /api/git/status` 한 번의 응답**에서 나온다 (NFR-EDT-2 를 그대로 유지).

**NFR-DIR-2.** 상속 색 계산은 트리를 그리는 시점에 **경로당 상수 시간**이어야 한다.
행마다 디렉터리 항목 전체를 훑으면 항목이 많은 저장소에서 스크롤이 끊긴다 —
접두 조회는 조상 경로를 따라 올라가며 맵을 찾는 방식(최대 경로 깊이만큼)으로 한다.

**NFR-DIR-3.** 다시 그리기 보존 규약(FR-RPT-*)을 깨지 않는다.

## 6. 비목표 (Non-goals)

1. **서브모듈 내부의 관측.** 서브모듈마다 `git status` 를 따로 돌리지 않는다 —
   서브모듈 수만큼 git 실행이 늘어 NFR-EDT-2 가 깨진다 (D-DIR-5).
2. **서브모듈 조작.** `submodule update`·`sync` 같은 명령을 붙이지 않는다.
3. **중첩 저장소의 자동 등록.** 진입점은 버튼 하나이고 누르는 것은 사용자다.
4. **`.gitignore` 된 경로의 표시.** 상태가 없는 것이 정상이다.
5. **Diff 뷰어 자체의 개선.** 바뀌는 것은 디렉터리를 골랐을 때 무엇을 보이느냐뿐이다.

## 7. 확정 결정 (Decisions)

| id | 결정 | 근거 |
|---|---|---|
| **D-DIR-1** | 디렉터리 판정은 **서버가** 하고 `dir` 로 싣는다 | 근거가 둘(끝 슬래시·`sub` 필드)이라 클라이언트에 두면 두 벌이 된다 |
| **D-DIR-2** | 미추적 디렉터리의 끝 `/` 를 **벗겨서** 싣는다 | 경로 문법이 하나여야 매칭·조작·diff 가 각자 슬래시를 처리하지 않는다 (§2.4) |
| **D-DIR-3** | 폴더도 자기 상태를 가질 수 있다 — FR-EDT-75 개정 | gitlink 는 디렉터리 하나를 그대로 추적한다. 옛 전제가 서브모듈에서 거짓이다 (§2.3) |
| **D-DIR-4** | 디렉터리 항목의 색을 **하위가 상속**한다 | 중첩 저장소 안의 파일은 부모 status 에 결코 나오지 않는다 (§2.1) |
| **D-DIR-5** | 서브모듈 내부는 관측하지 않는다 | 실행 횟수가 서브모듈 수만큼 는다. 대신 **그 저장소를 여는 진입점**을 준다 (FR-DIR-22) |
| **D-DIR-6** | 루트 판정은 서버의 `rootMatch` 로 한다 | 정규화를 아는 쪽이 비교해야 한다. 링크가 낀 경로에서 클라이언트 비교는 반드시 어긋난다 (§2.5 실측) |
| **D-DIR-7** | `_gitOff` 는 **사유마다 수명이 다르다** | 404 는 `git init` 으로 뒤집히는 사유다. 굳히면 init 이 실패한 것처럼 보인다 |
| **D-DIR-8** | 저장소 **안**의 루트에도 색을 입힌다 — FR-EDT-69 개정 | D-6 이 기각한 것은 펼침마다의 판정이지 루트 한 번의 판정이 아니다. `status` 응답이 이미 저장소 루트를 준다 (§2.7) |
| **D-DIR-9** | 디렉터리 항목의 조작(스테이지 등)을 막지 않는다 | `git add <dir>` 은 정상적인 작업이고, 서브모듈 커밋 이동의 스테이지가 그것이다 |
| **D-DIR-10** | 트리 보기에서 디렉터리 항목은 **잎**이다 | 그 폴더 안에 다른 항목이 있을 수 없다 (§2.1). 접히는 빈 노드는 고장으로 읽힌다 |

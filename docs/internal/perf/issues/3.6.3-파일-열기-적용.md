# 3.6.3 프레임 스케줄러 적용 — 파일 열기

- `edOpenFile` 67~74 ms(`tabsFit`·`apiSend`·`_placeLayout`, 3.7 기록)를 트레이스로 나눠 잰 뒤, 레이아웃 읽기를 같은 프레임의 쓰기 뒤로 모으고 비필수 일을 `idle` 로 미룬다.

**측정을 먼저 바로잡는다 — 3.7 의 "edOpenFile 67~74 ms" 는 측정 잡음이다**

- 트레이스 이벤트로 그 작업을 나눠 보니 74.6 ms 중 `CpuProfiler::StartProfiling` 이 65.4 ms 였다. JS 표본과 레이아웃은 합쳐 ~9 ms 다.
- `profile.mjs` 는 단계마다 트레이스를 새로 시작한다. CPU 프로파일러는 그 단계의 첫 JS 실행에서 켜지고, 그 비용이 그 작업에 얹힌다. editor 단계의 첫 JS 가 `edOpenFile` 이었다.
- 단계 시작에 `page.evaluate(() => 0)` 와 500 ms 대기로 예열하면 65 ms 는 예열 작업으로 옮겨 가고, `edOpenFile` 은 **이전 바이너리에서도 16 ms 초과 목록에 없다**.
- 같은 잡음이 다른 단계에도 있을 수 있다: 첫 JS 가 잴 동작인 단계(3.1·3.7 의 `git-open`·`doc-md`·`doc-render`·`editor-big` 등)는 첫 작업에 ~65 ms 가 얹힌다. `boot` 는 `goto` 앞에서 시작하므로 부팅 스크립트에 얹힌다. 3.4.1 의 boot 지표도 이 경로인지 확인이 필요하다.

**조정자 결정(2026-11-25)**: A(`tabsFit` 합치기)와 B(겹친 그리기 없애기)를 3.6.3 에서 한다. 3.6.2 는 이 커밋을 딛는다.

# 데몬 화면 상태용 에뮬레이터 비교 — 2026-11-24 (이슈 2.1, OQ-1·A-1)

> 상위: `PERF_OPTIMIZATION_SRS.md` §3.2 FR-TRM-1~8 · A-1 · A-2 · D-6 · D-7
> 조사 코드(커밋하지 않음): `/private/tmp/otter-emu-spike/` — `emu/`(Rust), `node/ref.mjs`(xterm.js 기준), `compare.py`·`snapcheck.py`, `corpus/`

## 1. 결론

**`alacritty_terminal 0.26` 을 권한다.** A-1(xterm.js 와 사용자가 차이를 모를 만큼 같은 화면)과 A-2(스냅숏을 xterm.js 가 다시 해석 없이 같은 화면으로 그림)를 모두 만족했다. 다만 두 가지는 우리가 만든다.

1. **기록 5만 줄은 crate 에 맡기지 않는다.** 두 후보 모두 기록을 셀 격자로 들고 있어 터미널 하나에 130~160 MB 가 든다(목표 NFR-PRF-10 은 8 MB). 에뮬레이터에는 짧은 기록만 두고, 위로 밀려난 줄은 우리 줄 저장소에 압축해 옮긴다(FR-TRM-2). 50,000줄이 글자만으로 4.0 MB, deflate 로 0.62 MB 였다.
2. **스냅숏 직렬화기는 우리가 만든다.** alacritty 에는 화면 → ANSI 출력 기능이 없다. 이번 조사에서 만든 120줄 남짓의 직렬화기로 모든 자료가 같은 화면을 냈다. OSC 8 링크는 셀에 따로 들어 있으므로 직렬화기가 다시 내보내야 한다(§3).

어느 후보도 A-1 을 못 맞추는 상황은 아니다 — 멈출 이유는 없다.

## 3. xterm.js 와의 일치 (A-1)

기준은 앱이 쓰는 판과 같은 `@xterm/headless 5.5.0` + `addon-unicode11 0.8.0`(활성 11). 같은 바이트를 넣고 화면의 모든 셀(글자·폭·전경·배경·속성), 커서, 대체 화면 여부, 기록 마지막 40줄을 견줬다.

| 자료 | 크기 | alacritty | vt100 |
|---|---|---|---|
| 경계 벡터 — 한글·한자·이모지·결합 문자·ZWJ, 마지막 열의 와이드 문자 줄바꿈, SGR 16/256/RGB·굵게·기울임·밑줄·반전·흐림·취소선·숨김, OSC 8·OSC 0, 스크롤 영역(DECSTBM), IL/DL, ICH/DCH, REP, EL, 커서 저장·복원, 탭, 커서 숨김, 대체 화면 왕복 | 80×24 | 다른 셀 4 (OSC 8 링크 밑줄) | 다른 셀 13 (취소선·숨김 속성 잃음) |
| vim 실제 녹화 (번호·구문 강조·이동) — 끝난 뒤 / 도는 중 | 100×30 | 0 / 0 | 0 / 0 |
| less 실제 녹화 — 끝난 뒤 / 도는 중 | 100×30 | 0 / 0 | 0 / 0 |
| top 실제 녹화 | 100×30 | 0 | 0 |
| agent-sim 줄 출력 (6초) + 기록 40줄 | 120×40 | 0 | 0 |
| agent-sim TUI 출력 (6초) + 기록 40줄 | 120×40 | 0 | 0 |

- **alacritty 의 4셀**: xterm.js 는 OSC 8 링크 칸에 밑줄을 칠한다. alacritty 는 링크를 셀의 `hyperlink()` 로 따로 든다. 스냅숏이 OSC 8 을 다시 내보내면 xterm.js 가 같은 밑줄과 링크를 만든다 — 직렬화기의 할 일이다.
- **vt100 의 13셀**: 셀 API 에 취소선·숨김이 없어 그 속성을 잃는다. 고칠 길이 없다(crate 를 고쳐야 한다).
- vt100 은 기록을 "뷰포트를 위로 올려서" 한 화면씩만 읽게 한다. 위로 받기(FR-TRM-5)를 하려면 화면 단위로 오르내려야 한다. alacritty 는 `grid[Line(-k)]` 로 아무 줄이나 바로 읽는다.

## 4. 스냅숏 (A-2)

후보의 격자 → 최소 재그리기 시퀀스(지우기, 줄마다 커서 이동 + 바뀔 때만 SGR + 글자, 커서 위치·보임) → 새 xterm.js 에 넣고 원래 화면과 견줬다.

| 자료 | 원래 바이트 | 스냅숏 바이트 | 결과 (두 후보 같음) |
|---|---|---|---|
| vim 도는 중 | 4,480 | 2,075 | 같다 |
| less 도는 중 | 1,277 | 1,553 | 같다 |
| top | 4,905 | 2,882 | 같다 |
| agent-sim 줄 | 183,639 | 6,965 | 같다 |
| agent-sim TUI | 224,100 | 7,345 | 같다 |
| 경계 벡터 | 813 | 908 | 위 §3 의 차이만 남는다 |

- 스냅숏 크기는 화면 크기에 비례하고 출력량과 무관하다(A-2 의 가정이 맞다). 많이 쏟아진 뒤 깨울수록 이득이 크다(TUI 224 KB → 7 KB).
- 입력 모드(마우스 추적·괄호 붙여넣기·앱 커서 키 등)는 이번 직렬화기에 넣지 않았다. 지금 서버의 `TermModes::restore_bytes` 가 하는 일이고, 두 후보 모두 그 모드를 상태로 든다(alacritty `TermMode`, vt100 `mouse_protocol_mode` 등). 구현 때 함께 직렬화한다.

## 5. 성능

M4, 릴리스 빌드, 120×40, 터미널 4개에 각각 64 MB 를 넣었다. 메모리는 기록 50,000줄이 찬 뒤의 RSS 증가분 ÷ 4.

| 지표 | alacritty | vt100 |
|---|---|---|
| 처리량 — 줄 출력 | **175 MB/초** | 80 MB/초 |
| 처리량 — TUI | **214 MB/초** | 126 MB/초 |
| 터미널당 메모리 — 기록 5만 줄(줄 출력) | 160 MB | 148 MB |
| 터미널당 메모리 — TUI(기록 39,130줄) | 128 MB | 143 MB |

- 처리량은 둘 다 넉넉하다. 기준선의 TUI 부하가 터미널 12개 합쳐 초당 0.6 MB 였으니, alacritty 로 코어 하나의 0.3% 안팎이다.
- 메모리는 둘 다 목표(8 MB)의 16~20배다. **셀 격자 기록을 그대로 쓰면 안 된다**(§6).

## 6. 기록 저장 설계 (FR-TRM-2·5, 권장안의 전제)

- 에뮬레이터의 기록 상한은 작게 둔다(예: 1,000줄 → 120열 기준 약 3 MB).
- 데몬이 출력을 넣을 때마다 기록이 일정 줄을 넘으면, 오래된 줄을 셀에서 읽어 **줄 단위 압축 형태**(글자 + 속성 구간, 블록마다 deflate)로 우리 저장소에 옮기고 `grid.update_history()` 로 에뮬레이터에서 지운다. alacritty 의 `update_history(n)` 은 가장 오래된 줄부터 줄인다(코드로 확인, 구현 때 시험으로 굳힌다).
- 한 번에 넣는 바이트가 상한보다 많은 줄을 밀어 올리지 않도록, 넣기 전에 줄바꿈 수로 나눠 넣는다(데몬 읽기 단위는 64 KB 이하).
- 크기 어림: 5만 줄이 글자만 4.0 MB, deflate 0.62 MB(agent-sim). 속성 구간을 더해도 터미널당 목표 8 MB 안에 든다. 실제 에이전트 출력은 agent-sim 보다 덜 줄어든다 — 구현 뒤 NFR-PRF-10 으로 잰다.
- 위로 받기(FR-TRM-5)는 이 저장소에서 줄 구간을 풀어 보낸다. 에뮬레이터를 거치지 않는다.

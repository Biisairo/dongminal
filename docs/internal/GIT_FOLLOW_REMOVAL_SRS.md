## 1. 서론 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 **"하단바의 깃 표시가 현재 터미널 경로의 깃으로 바뀌지 않는다 …
마지막으로 들어간 git 창과 연동되는 것 같은데 실시간 연동되어야 하지 않나"** 였고,
조사 뒤 사용자가 **"follow 를 지우고 add 를 개선하는 쪽"** 으로 결정했다.

조사 결과 하단바 chip 은 고장이 아니다. `_gitChip`(`web/js/core/app-git.js:304`)은
`gitPanel.repo` — **활성 리포** — 를 읽으며, 그것이 FR-GIT-57 이 요구한 값이다.
어긋난 것은 **문서와 구현이 갈린 지점**이다.

| 자리 | 무엇이라 말하는가 |
|---|---|
| GIT_SRS §1.3 용어표 | follow = 포커스된 터미널 칸의 cwd 로 활성 리포를 **자동 결정하는 모드** |
| GIT_SRS FR-GIT-9~15 | follow 는 **사이드바 항목 하나**이고, 활성 리포 전환은 FR-GIT-15 의 **클릭**이다 |
| 구현 | 본문을 따랐다 — `setRepo` 를 부르는 자리는 전부 사용자의 명시적 선택이다 |

즉 "모드" 는 **한 번도 존재한 적이 없다.** 이 문서는 그 정의를 지우는 쪽으로
불일치를 닫는다.

### 1.2 범위 (Scope)

- **범위 안**: GIT 섹션의 follow 행, `/api/git/repos` 의 `follow` 필드와 그것을
  만드는 서버 조회, follow 를 딛는 클라이언트 상태(`_gitFocusToolId`·`_lastTermTool`),
  그리고 `+ Add` 의 대체 동작.
- **범위 밖**: 핀(FR-GIT-11·12·223)의 뜻과 동작, 활성 리포의 영속(FR-GIT-29),
  하단바 chip 의 판정(FR-GIT-57~59). **셋 다 그대로 둔다** — chip 은 이미
  활성 리포를 정확히 따르고 있고, 이 문서가 바꾸는 것은 활성 리포에 이르는 길뿐이다.
- **하지 않기로 한 것**: 활성 리포를 터미널 cwd 에 자동 연동하는 "follow 모드"
  (D-FLW-1 의 근거).

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **활성 리포** | Git 창이 현재 표시 중인 리포. **사용자가 고른 것이며 스스로 바뀌지 않는다** (이 문서가 GIT_SRS §1.3 의 정의를 이것으로 대체한다) |
| **핀** | `workspace.json` 에 영속하는 리포 목록 (FR-GIT-11) |
| **현재 터미널의 리포** | 포커스된 터미널 칸의 cwd 가 속한 저장소의 루트. **화면에 상주하지 않고**, `+ Add` 를 여는 순간에만 조회한다 |

## 2. 전반 기술 (Overall Description)

### 2.1 근거 — 왜 지우는가

follow 가 **지금 유일하게 하는 일**은 핀하지 않은 리포를 한 번의 클릭으로 여는
것이다. 그 값어치는 실재하지만, 그것을 위해 다음이 상주한다.

1. `/api/git/repos` 가 3초마다 `rev-parse --show-toplevel` 를 **한 번 더** 돈다.
2. 포커스가 터미널을 떠나도 "마지막 터미널" 을 붙드는 상태 두 개
   (`_lastTermTool`·`_gitFocusToolId`, FR-GIT-210) 가 유지된다.
3. 사이드바에 **자기만 규칙이 다른 행**이 하나 있다 — 지울 수 없고(FR-GIT-193),
   끌 수 없고(FR-GIT-223), `×` 대신 자리만 잡고(FR-GIT-239), 저장소가 아닐 때의
   전용 표시를 갖는다(FR-GIT-194).

그리고 "모드로 승격" 은 **핀과 충돌한다.** 사이드바의 활성 판정이 경로 하나이므로
(`renderer.js:154`), follow 행과 핀 행이 같은 리포를 가리키면 두 줄이 함께 켜진다.
모드가 생기면 "무엇을 보는가(경로)" 와 "왜 그것을 보는가(모드)" 가 갈리고, 판정을
둘로 나눠야 하며, 사용자는 "A 를 보는데 핀 A 는 왜 꺼져 있나" 를 배워야 한다.
**규칙을 하나로 되돌리는 편이 화면이 정직하다.**

### 2.3 제약 (Constraints)

1. **핀의 뜻을 바꾸지 않는다.** 서버가 `rev-parse` 로 재확인한 루트를 저장하는
   규약(FR-GIT-12·62)과 저장소가 아니게 된 핀을 지우지 않는 규약을 유지한다.
2. **자격증명을 담지 않는다** (FR-GIT-104).
3. 목록의 다시 그리기는 FR-RPT 규약을 지킨다 — 요소를 새로 만들지 않고, 판정
   근거(`sig`)에는 렌더러가 읽는 값 전부를 넣는다.

## 3. 요구사항 (Requirements)

### 3.1 제거

- **FR-FLW-1** GIT 섹션은 **핀 목록만** 그린다. follow 행을 그리지 않는다.
  이로써 FR-GIT-9·10·13(⟳ 부분)·193·194·210·239 는 **철회된다** — 대상이 없어진
  요구사항이며, 미구현이 아니라 폐기다.
- **FR-FLW-2** `/api/git/repos` 응답에서 `follow` 를 뺀다. 그 조회는 **`+ Add` 가
  여는 순간에만 도는 전용 엔드포인트**(`GET /api/git/repo-at?tool=`)로 옮긴다
  (FR-FLW-6). 목록 조회는 `?tool=` 을 받지 않는다. **죽은 값을 남기지 않는다** —
  남기면 3초마다 도는 `rev-parse` 가 아무도 읽지 않는 값을 위해 계속 돈다.
- **FR-FLW-3** 목록 조회에서 도구 인자를 뗀다. 칸 포커스 변화에 따른 **목록
  새로고침**을 제거한다 — 목록은 핀에서만 오므로 포커스와 무관하다.
  **마지막으로 포커스된 터미널의 추적은 남긴다** (`_lastTermTool`): `+ Add` 가
  그것을 딛으며, FR-GIT-210 이 잡아낸 사실 — Git 창에 들어간 순간 대상이
  dongminal 자신으로 바뀌는 것 — 은 `+ Add` 에서도 똑같이 일어난다. 추적은
  ~~**포커스가 바뀔 때 값만 갱신하고 아무것도 조회하지 않는다.**~~ → **FR-FLW-13
  이 갱신 방식을 대체한다.** 아무것도 조회하지 않는다는 규약은 그대로다.
- **FR-FLW-13** `+ Add` 가 딛는 터미널은 **여는 순간 워크스페이스에서 계산한다.**
  포커스가 터미널이 아니면(Git·Editor 창) 일반 창의 활성 탭에서 찾고
  (`_anyTermToolId`), **기억(`_lastTermTool`)은 그 계산이 아무것도 찾지 못할 때의
  마지막 근거로만** 쓴다.

  근거는 FR-FLW-3 의 갱신 방식이 실제로 성립하지 않았다는 것이다. "포커스가 바뀔
  때" 의 갱신 계기가 공개 `setFocus()`(칸 클릭) 하나뿐인데, 포커스가 실제로 옮겨
  가는 통로는 그것 말고도 **창 전환**(`switchWindow`)·**탭 전환**(`switchTab`)·
  **탭 추가**(`addTab`) 셋이 더 있고 모두 그 계기를 지나지 않는다. 그래서 기억이
  낡은 채로 우선 쓰였고, `+ Add` 는 사용자가 방금 떠나온 자리가 아니라 마지막으로
  **클릭한** 자리를 채웠다 — 창마다 cwd 가 다른 워크스페이스에서 그것은 "이상한
  경로" 로 읽힌다.

  계기를 셋 더 다는 대신 계기를 지운다. 계산은 워크스페이스의 지금 상태를 읽으므로
  세 통로를 저절로 따라가며, 여전히 서버에 아무것도 묻지 않는다.
- **FR-FLW-4** 활성 리포는 **사용자가 고른 것이며 스스로 바뀌지 않는다.**
  GIT_SRS §1.3 의 follow 정의를 이 문장으로 대체한다.
- **FR-FLW-11** GIT 섹션에 핀이 하나도 없으면 **안내를 보인다.** follow 행이 늘 한
  줄을 채우고 있었으므로 이 섹션은 빈 적이 없었다 — 빈 자리는 고장처럼 읽힌다.
- **FR-FLW-12** 상태바의 **브랜치 chip 을 제거한다.** FR-GIT-57·58·59 는 **철회**된다.
  활성 리포는 터미널을 따라가지 않으므로 하단바에 상주하는 브랜치 표시는 "지금 있는
  곳" 으로 오해되기만 한다. **진행 중 원격 작업 표시(FR-GIT-112)는 남는다** — 그것은
  리포가 아니라 지금 돌고 있는 작업을 알리는 것이라 목적이 다르다.
  설정 항목(`STATUS_ITEMS.git`)은 남되 **남은 것을 가리키도록 라벨을 고친다** —
  없는 기능을 켜는 스위치를 두지 않는다.

### 3.2 `+ Add` — 잃은 길을 대신한다

- **FR-FLW-5** `+ Add` 는 **지금 터미널의 리포를 한 번의 클릭으로 추가할 수 있어야
  한다.** 경로를 타이핑하게 하는 것은 follow 가 대신하던 일을 대신하지 못한다.
- **FR-FLW-6** 그 리포는 **다이얼로그를 여는 순간** 서버에 묻는다. 화면에 상주시키지
  않는다 — 상주시키면 그것이 곧 follow 의 부활이다.
- **FR-FLW-7** 임의 경로 입력도 계속 가능해야 한다 (FR-GIT-12 유지). 저장소가
  아니면 거부하고 **사유를 그 자리에 보인다** — 다이얼로그가 조용히 닫히면 사용자는
  추가된 줄 안다.
- **FR-FLW-8** 이미 핀된 리포를 다시 추가하는 것은 **성공으로 답한다** (서버의 핀은
  이미 멱등이다). 다만 그 사실을 사유로 알린다 — 목록이 늘지 않은 이유가 보이지
  않으면 사용자는 실패로 읽는다.
- **FR-FLW-9** 현재 터미널이 저장소가 아니거나 터미널이 없으면 그 자리는 **사유와
  함께 비활성**이다. 경로 입력은 그대로 쓸 수 있다.

### 3.3 화면 규약

- **FR-FLW-10** `+ Add` 는 `window.prompt` 를 쓰지 않는다. FR-FLW-6~9 가 한 줄
  텍스트로 담기지 않으며, 네이티브 프롬프트는 사유를 보일 자리가 없다.
  기존 다이얼로그 규약(`GitDialog`)을 딛는다 — 새 프레임워크를 만들지 않는다.

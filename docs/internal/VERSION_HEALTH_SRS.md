## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

두 가지를 세운다.

1. **데몬과 서버의 판이 다르면 그것이 드러난다.** 지금은 조용히 공존한다.
2. **`GET /api/health` 가 "이 인스턴스가 어떤 상태인가" 를 한 번에 답한다.**
   지금은 그런 종단이 없다.

M3 의 나머지가 이 위에 선다 — 손상 감지(`G4-2`)도 백업 복원(`G4-1`)도
**사실을 실어 보낼 자리**가 있어야 하고, 그 자리가 헬스다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 이름 | 갭 |
|---|---|---|
| **묶음 V** | 판 핸드셰이크 (Version) | `G3-1` |
| **묶음 H** | 헬스 종단 (Health) | `G2-2` |
| **묶음 S** | 기동의 대기와 안내 (Start) | `G3-1` |

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 말 | 뜻 |
|---|---|
| **프로토콜 판** | 데몬 IPC 의 문법 판. 지금 `1` 이며 `paned.go:179` 에 상수로 박혀 있다 |
| **빌드 판** | 그 바이너리의 판 (`cli.Version`). 릴리스마다 바뀐다 |
| **불일치** | 서버의 판과 데몬의 판이 다른 것. 둘은 **다른 프로세스**이고 따로 갱신된다 |
| **헬스** | 이 인스턴스의 지금 상태. 살아 있는가가 아니라 **무엇이 어긋나 있는가** |

## 2. 현재 상태 (조사로 확정한 사실, 2026-09-11)

### 2.1 `hello` 는 프로토콜 판만 내고, **클라이언트는 그것을 버린다**

```go
// internal/daemon/ipc/paned.go:179
return toolipc.PanedResponse{ID: req.ID, Result: map[string]interface{}{
    "version":  1,
    "tool_ids": ids,
}}
```

```go
// internal/webserver/toolclient/client.go:137
if _, err := pc.call("hello", map[string]interface{}{"server_pid": 0}); err != nil {
```

`_` 다. **응답을 읽는 코드가 없다.** 그래서 판이 무엇이든 연결은 성립한다.

### 2.2 빌드 판은 hello 에 실리지 않는다

`cli.Version`(`version.go:20`, 기본 `"dev"`)은 핸드셰이크 어디에도 없다. 즉 **낡은
데몬 위에 새 서버가 붙어도 아무도 모른다.** 데몬은 PTY 를 들고 있으므로 이 조합이
가장 오래 산다 — 서버만 재시작하는 것이 흔한 조작이기 때문이다.

### 2.3 `/api/health` 는 **없다**

`dongminal health`(`ctl/cli/health.go`)는 CLI 이고, HTTP 로는 `/` 를 핑한다.
`/api/ping` 이 있으나 생존만 답한다. 그러므로 지금 **"서버는 떴는데 데몬이 끊겼다"
를 한 번에 말해 주는 자리가 없다.**

### 2.4 `waitReady` 는 **HTTP 만** 기다린다

```go
// internal/ctl/cli/start.go:268
if ping(url+"/api/ping", time.Second) { return true }
```

데몬 연결은 보지 않는다. 그래서 `start` 가 "준비됨" 을 찍은 직후에도 도구 생성이
실패할 수 있다 — 서버는 떴지만 데몬 소켓에 아직 붙지 않은 창이 있다.

### 2.5 `workspace.Manager` 는 `rev` 를 알지만 **영속 실패는 기억하지 않는다**

`CurrentRev()`(`manager.go:195`)는 있다. 마지막 저장 실패를 담는 자리는 없다 —
그것이 `GO-10`("영속 실패가 성공으로 보임")이며 이 문서는 **그 사실을 실어 나르는
자리**만 만든다. 원인 조치는 M3 의 뒤 묶음이다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 V — 판 핸드셰이크

**FR-VHL-1** `hello` 응답은 **판 둘을 따로** 싣는다.

| 키 | 뜻 |
|---|---|
| `version` | 프로토콜 판. 지금 `1`. **호환의 판정자** |
| `build` | 그 데몬 바이너리의 `cli.Version` |

둘을 한 값으로 합치지 않는다 — 프로토콜은 거의 안 바뀌고 빌드는 릴리스마다 바뀐다.
합치면 **모든 릴리스가 프로토콜 불일치로 읽힌다.**

**FR-VHL-2** 클라이언트는 `hello` 의 결과를 **읽는다**(§2.1 의 `_` 를 없앤다).

**FR-VHL-3** **프로토콜 판이 다르면 연결을 거부한다.** 문법이 다른 상대와 말을
이어 가면 실패가 엉뚱한 자리에서 난다. 거부는 `connect()` 의 오류이며, 재연결
감독(`supervise`)이 종전대로 다룬다.

**FR-VHL-4** **빌드 판이 다르면 연결은 유지한다.** 프로토콜이 같으면 통신은
성립하므로 끊을 이유가 없다 — 끊으면 사용자의 PTY 가 죽는다. 대신 그 사실을
**기억하고 헬스에 싣는다** (`FR-VHL-11`).

> 이 비대칭이 이 문서의 중심이다. 프로토콜 불일치는 **고장**이고, 빌드 불일치는
> **알려야 할 상태**다. 같게 다루면 둘 중 하나가 틀린다.

**FR-VHL-5** 판을 **모르는** 데몬(응답에 키가 없는 옛 데몬)은 프로토콜 `1` 로
읽고 빌드는 **비운다.** 비운 것과 다른 것은 구별된다 (`FR-CBG-5`) — 빈 빌드는
불일치가 아니다.

### 3.2 묶음 H — 헬스 종단

**FR-VHL-10** `GET /api/health` 를 둔다. 몸통은 이렇다.

```json
{
  "version": "<서버 빌드>",
  "uptime": 1234,
  "daemon": {"connected": true, "pid": 4242, "protocol": 1,
             "build": "0.9.1", "mismatch": true},
  "workspace": {"rev": 17, "lastPersistErr": ""},
  "tools": 3,
  "ws": 1
}
```

**FR-VHL-11** `daemon.mismatch` 는 **빌드가 서로 다를 때만** 참이다. 데몬이 없는
모드(direct)에서는 `connected:false` 이고 `mismatch` 는 **거짓**이다 — 없는 것은
어긋난 것이 아니다.

**FR-VHL-12** 헬스는 **상태 코드로 판정하지 않는다.** 어긋난 것이 있어도 `200` 이고
사실은 몸통에 있다. 503 으로 답하면 그 뒤의 필드를 아무도 읽지 않고, "왜" 가
사라진다. 생존 판정이 필요한 쪽은 `/api/ping` 을 그대로 쓴다.

**FR-VHL-13** 새 종단도 **같은 게이트를 지난다** (`REQUEST_GATE_SRS`). 헬스라고
경계를 비켜 가지 않는다 — 여기 실리는 것은 pid·판·경로 길이이며, 노출 모드에서
익명에게 줄 것이 아니다.

**FR-VHL-14** 몸통에 **경로·명령·자격은 싣지 않는다.** 담는 것은 숫자와 판과
불리언이다. `lastPersistErr` 는 **분류 문자열**이며 원문 경로를 포함하지 않는다.

### 3.3 묶음 S — 기동의 대기와 안내

**FR-VHL-20** `waitReady` 는 **데몬 연결까지** 기다린다 — `/api/health` 의
`daemon.connected` 가 참이 될 때까지다.

  - 이전 동작: `/api/ping` 이 답하면 준비됨
  - 새 동작: 헬스가 데몬 연결을 보고해야 준비됨
  - 이유: §2.4. "준비됨" 직후의 도구 생성이 실패할 수 있었다

**FR-VHL-20a** **데몬이 없는 모드에서는 종전대로다.** `connected` 가 영원히 거짓인
구성이 있으므로, 그때는 HTTP 응답만으로 준비됨이다.

> **구현에서 확정한 형태 (2026-09-11)**: 초안은 "그 인스턴스가 데몬을 띄우기로
> 했는가를 `start` 가 안다" 고 적었으나, 기동 시점에는 **아직 모른다** — 데몬은
> 서버가 필요할 때 띄우고 소켓은 그 뒤에 생긴다. 그래서 형태를 바꿨다:
>
> - 단단한 관문은 **종전의 `waitReady`(HTTP)** 그대로다. 여기서 실패하면 기동 실패다
> - 그 위에 **유한한 덤 대기**를 얹는다(`waitDaemonConnected`). 붙으면 그 사실과
>   판을 얻고, **붙지 않아도 기동을 막지 않는다**
>
> 이 형태는 직접 모드에서 매달릴 수 없다. "기다릴 것이 없었다" 와 "실패했다" 를
> 호출자가 가르지 않아도 되기 때문이다.

**FR-VHL-20b** 헬스가 **없는** 서버(옛 판)에 붙어도 기동은 성립한다. 404 는
"모른다" 이며 실패가 아니다 — `FR-VHL-5` 와 같은 정신이다.

**FR-VHL-21** `start` 가 빌드 불일치를 보면 **안내를 낸다** — *"데몬이 이전 판으로
돌고 있습니다. 반영하려면 데몬을 재시작해야 하며 **실행 중인 세션이 사라집니다**."*

**자동으로 재시작하지 않는다** (사용자 재확인 2026-09-11: *"주의 재시동은 절대
하지 않는다"*). 데몬을 내리면 그 위의 PTY 가 **전부** 죽는다 — 실행 중인 에이전트
세션이 사라진다는 뜻이고, 그 대가는 사용자가 고를 일이지 이 명령이 대신 고를 일이
아니다. 이 조항은 편의를 위해서도 완화되지 않는다.

### 3.4 비기능

| ID | 요구사항 |
|---|---|
| NFR-VHL-1 | 헬스는 **아무것도 고치지 않는다.** 읽기 전용이며 부작용이 없다 |
| NFR-VHL-2 | 헬스 한 번의 비용은 이미 메모리에 있는 값을 읽는 것뿐이다. 디스크·소켓을 새로 두드리지 않는다 |
| NFR-VHL-3 | 판 판정이 실패해도 **도구는 죽지 않는다** — 빌드 불일치는 기록이고, 프로토콜 불일치만 연결을 거부한다 |

## 4. 설계 결정 (Design Decisions)

- **D-1. 프로토콜과 빌드를 가른다** (`FR-VHL-1`). 합치면 모든 릴리스가 고장이 된다.
- **D-2. 빌드 불일치로 끊지 않는다** (`FR-VHL-4`). 끊는 비용이 사용자의 PTY 다.
- **D-3. 헬스는 언제나 200** (`FR-VHL-12`). 상태 코드는 이유를 담지 못한다.
- **D-4. `lastPersistErr` 는 자리만 만든다.** 채우는 것은 `GO-10` 의 일이며 M3 의
  뒤 묶음이다 — 자리가 먼저 있어야 그때 한 줄로 끝난다.

## 6. 비목표 (Non-goals)

1. **`GO-10` 의 원인 조치.** 이 문서는 `lastPersistErr` 의 **자리**만 만든다.
2. **백업·손상 감지**(`G4-1`·`G4-2`). M3 내부 순서 ②다.
3. **프로토콜 판의 인상.** 지금 `1` 이며 이 문서는 그것을 바꾸지 않는다.
4. **자동 데몬 재시작.** 세션 손실은 사용자가 고른다 (`FR-VHL-21`).
5. **메트릭 종단**(`SEC-26` 의 나머지). 헬스는 사람이 읽는 것이고 메트릭은 기계가
   읽는 것이다 — 형식도 수명도 다르다.

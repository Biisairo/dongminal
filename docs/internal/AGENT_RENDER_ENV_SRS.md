- 관련: [`M11_SRS`](./M11_SRS.md) §2.4e·2.4f (재현과 원인) ·

## 1. 개요

### 1.1 목적

Claude Code 는 터미널 폭이 바뀌면 **옛 프레임을 스크롤백에 남긴다.** 기기를 오가며
쓰면 그것이 계속 쌓여 위쪽 대화를 읽을 수 없게 된다.

터미널 쪽에서 되살릴 수 없다는 것은 조사로 확정됐다 (`M11_SRS` §2.4e·2.4f) —
스크롤백에 남은 것은 이미 배치가 끝난 글자이고, 원본을 가진 것은 앱뿐이다.

**앱에 해결책이 이미 있다.** dongminal 은 그것을 켜 주기만 하면 된다.

### 1.2 왜 이것이 dongminal 의 일인가

사용자가 매번 `/tui fullscreen` 을 치게 할 수도 있다. 그러나 이 결함은 **dongminal
에서 쓸 때 특히 심하다** — 여러 기기와 분할을 오가는 것이 이 제품의 사용 방식이고,
그때마다 폭이 바뀐다. 제품이 만든 조건이면 제품이 갖추는 것이 맞다.

### 1.3 조사 — 세 에이전트의 처지가 다르다 (2026-09-19)

| 에이전트 | 리사이즈 때 위쪽 | 제어 수단 | 조치 |
|---|---|---|---|
| **Claude Code** | **옛 프레임이 남는다** ([#49086](https://github.com/anthropics/claude-code/issues/49086)·[#54732](https://github.com/anthropics/claude-code/issues/54732) 외 다수) | 환경변수 `CLAUDE_CODE_NO_FLICKER` | **주입한다** |
| **Codex** | source-backed history 에서 스크롤백 재구성 ([PR #18575](https://github.com/openai/codex/pull/18575)) | `config.toml` 의 `[tui]` — **환경변수 없음** | 하지 않는다 |
| **oh-my-pi** | ED3 후 transcript 재구성 | `PI_TUI_RESIZE_MODE` 등 | 하지 않는다 |

Codex·omp 를 건드리지 않는 근거는 둘이다. ① **이미 스스로 처리한다** — 기본값이
알맞고 손댈 이유가 없다. ② Codex 는 TUI 설정이 TOML 전용이라 **사용자의 설정
파일을 고쳐야** 하는데, 남의 파일을 대신 쓰는 것은 얻는 것에 비해 침습적이다.

### 1.4 범위

**포함** — 새로 만드는 도구의 환경에 값을 넣는 일과 그 스위치.

**비포함** — 이미 떠 있는 도구(환경은 프로세스가 시작할 때 정해진다) · 사용자의
`~/.claude/settings.json`·`~/.codex/config.toml` 수정 · 터미널 쪽에서 잔재를
되살리는 일(불가능함이 확정됐다).

## 2. 요구사항

**FR-ARE-1** 새 도구의 환경에 `CLAUDE_CODE_NO_FLICKER=1` 을 넣는다. 그 도구에서
띄운 Claude Code 는 **fullscreen 렌더링**으로 서고, 대화가 alt screen 에 살아
스크롤백을 건드리지 않는다.

**FR-ARE-2** **사용자의 뜻이 이긴다.** `/tui default` 를 치면 Claude Code 가
재시작하며 이 변수를 지우므로(공식 동작), 주입은 *기본값 제안*이지 강제가 아니다.
이 성질이 있기에 기본값을 켬으로 둘 수 있다.

**FR-ARE-3** 설정으로 끌 수 있다. 자리는 **Settings ▸ Terminal**, 기본값은 **켬**
(사용자 결정 2026-09-19).

**FR-ARE-4** 이미 떠 있는 도구는 바뀌지 않는다. 환경은 프로세스 시작 시점에
정해진다 — 다음에 여는 터미널부터 적용된다. 화면에 그 사실을 적는다.

**FR-ARE-5** **toolhub 는 어느 에이전트도 알지 않는다.** 무엇을 넣을지는 호출자가
정하고, toolhub 는 받은 것을 환경에 얹는다 — `Placement` 가 컨테이너·프로파일을
모르는 것과 같은 경계다 (`manager_create.go` 의 규약).

**FR-ARE-6** daemon 모드에서도 같다. 도구를 만드는 것은 데몬이므로 값은 `create`
RPC 를 타고 건너간다. 필드를 모르는 옛 데몬에서는 **주입이 없을 뿐** 깨지지 않는다.

**FR-ARE-7** 서버가 설정 blob 에서 **이 키 하나만** 읽는다.

> `handlers_settings.go` 가 *"브라우저 설정은 서버가 해석하지 않는 JSON blob"* 이라
> 적어 두었고, 이 요구는 거기에 예외를 낸다. 예외인 이유는 분명하다 — 값을 쓰는
> 주체가 **서버**(도구를 띄우는 쪽)인데 값을 정하는 자리는 **브라우저**(설정 화면)
> 이기 때문이다. 대안이던 "서버 전용 설정"은 화면에서 못 바꾸게 되어 `FR-ARE-3` 과
> 어긋난다. 읽는 키는 하나이며 해석은 불리언 하나에서 멎는다.

## 3. 검증

| ID | 확인 | 층 |
|---|---|---|
| V-ARE-1 | 켜져 있으면 새 도구의 환경에 `CLAUDE_CODE_NO_FLICKER=1` 이 있다 | Go |

| V-ARE-4 | 필드를 싣지 않는 옛 요청도 그대로 도구를 만든다 (관대함) | Go |
| V-ARE-5 | Settings ▸ Terminal 에 스위치가 있고, 끄면 저장된다 | e2e |

## 4. 비목표

1. **Codex·omp 의 설정 주입** (§1.3). 이미 스스로 처리하며, 건드리면 위험만 는다.
2. **사용자 설정 파일 수정.** 우리는 환경만 정한다.
3. **이미 떠 있는 도구에 소급 적용.** 환경은 시작 시점의 것이다.

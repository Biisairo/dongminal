# SRS: 메모장 · 탐색기의 살아있는 반영 · 캐럿 애니메이션 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 셋이다.

> **① "editor 에 브라우저 세션에 저장되는 메모장을 만들고싶어. 이미있는 에디터기능을
> 사용해서 만들자. 좌하단의 고정탭에있는 `~` 홈 위에 고정탭으로 만들면 될 것 같아."**
>
> **② "git 에서도 있던 문제인데 수정 및 깃 변경 반영이 에디터의 파일탐색기에
> 즉각적으로 반영되지 않는것 같은 문제가 있어."**
>
> **③ "에디터탭에서 커서가 애니메이션으로 움직여. vsc 처럼 그냥 움직이도록 수정."**

①의 "브라우저 세션" 은 인터뷰에서 **철회되었다.** 조사 결과 이 앱에는 저장 위치의
3계층 규약이 있고(§2.1) 브라우저 저장소 두 곳 어디에도 **내용**이 사는 선례가
없다 — 둘 다 설정과 시선만 담고 내용은 전부 서버에 있다. 메모 본문을 브라우저에
두면 그것이 유일한 예외가 되고 브라우저 탭을 닫는 순간 사라진다. 사용자가 그
사실을 듣고 **"그냥 서버에 저장하자"** 로 확정했다 (D-1).

### 1.2 범위 (Scope)

**포함:**

- 메모장의 서버 저장, 전용 메모장 창, 사이드바 Editor 패널의 고정 행.
- 탐색기의 디렉터리 목록이 바깥의 변경(터미널·git·다른 에이전트)을 스스로 따라가는 일.
- 편집기 캐럿의 부드러운 이동 제거.

**미포함:**

- 서버 파일 감시(fsnotify)와 SSE 푸시 (D-6에서 기각).
- 메모의 검색·태그·정렬·동기화. 메모는 **파일**이므로 기존 탐색기가 하는 것 이상을
  발명하지 않는다.
- git 상태 폴링 주기의 변경. 사용자가 목록 감지 주기를 **"깃과 동일하게"** 로
  확정했으므로 기준은 이미 있는 `EDITOR_GIT_POLL_MS` 하나다.
- 편집기의 다른 Monaco 옵션. 접수한 말은 **캐럿**이다.

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **메모 루트** | 메모 파일들이 사는 서버의 디렉터리. `$DONGMINAL_HOME/notes` |
| **메모장 창** | 메모 루트를 `editor.root` 로 갖는 Editor 창. 전용 창이되 **새 창 타입이 아니다** |
| **고정 행** | 사이드바 Editor 패널 최하단(`#editor-root`)에 사는 행. 지금은 `~` 하나뿐이다 |
| **겹** | 디렉터리 한 층. 탐색기는 겹 단위로 읽는다 (FR-EDT-59) |
| **스탬프** | 한 겹의 변경 여부를 나타내는 서버의 값. 그 디렉터리의 mtime |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 저장 위치의 3계층 규약

전수 조사(`grep -rno "localStorage\.[a-zA-Z]*Item("` 및 sessionStorage 동일)의 결과다.

| 계층 | 수명 | 지금 들어 있는 것 |
|---|---|---|
| `localStorage` | 브라우저 영속 | **설정·취향뿐** — `sidebarWidth`·`sidebarTab`·diff 보기 방식·커밋창 높이·날짜 형식·알림 on/off·agents 패널 폭 |
| `sessionStorage` | 그 브라우저 탭 한정 | **"지금 어디를 보고 있는가"** — `activeWindow`·`focusedPanes`·슬롯 수·`displayMode`·복귀 창 |
| 서버 `workspace.json` / 파일 | 영속·기기 공유 | **구조와 내용** — 창·pane·탭, `editors.list`, git 핀 |

**내용이 브라우저에 사는 자리는 하나도 없다.** 이것이 D-1 의 근거다.

### 2.2 Editor 루트는 이미 "창 하나 · 탐색기 하나 · 탭들" 을 전부 준다

`_edRoots()` 가 돌려주는 경로마다 `_edReconcile` 이 창을 하나씩 **멱등하게** 세운다
(`app-editor.js`, FR-EDT-42). 그 창은 탐색기·Monaco 탭·분할·새 파일 만들기·이름
변경·삭제·업로드·다운로드를 전부 이미 갖는다. 서버의 루트 가드(`fsRoot`)도
`Entries.Roots()` 를 그대로 딛는다 (`handlers_fs.go:120`).

> 즉 **메모 루트를 `Roots()` 에 한 줄 더하는 것만으로** 메모장 창·메모 목록·메모
> 추가·메모 편집·메모 저장이 전부 성립한다. 이것이 "이미있는 에디터기능을 사용해서
> 만들자" 의 문자 그대로의 실행이다 (D-2).

`_edFixed()` 는 지금 `[{path:home,root:true}]` 하나를 돌려주고, `SidebarList` 가
그것을 `#editor-root` 컨테이너에 그린다 (`sidebar-list.js` `_paintInto`). 배열이므로
**앞에 한 항목을 더하면 `~` 위**다 — 접수한 말이 요구한 자리 그대로다.

### 2.3 탐색기의 디렉터리 목록은 스스로 갱신되지 않는다 (결함)

`file-tree.js:9` 가 계약을 못박는다.

> *"갱신 계기는 셋뿐이다 (FR-EDT-67) — 새로고침 · 조작 후 재조회(M5) · git 색 폴링.
> **파일 감시는 하지 않는다.**"*

그리고 셋 중 **폴링이 갱신하는 것은 색뿐이다.** `pollGit()` 은 `/api/git/status` 를
읽어 `_st`·`_dirSt`·`_partial` 만 바꾸고(`file-tree-paint.js:158~212`), 겹의 캐시인
`_kids` 는 건드리지 않는다. `_kids` 를 다시 채우는 자리는 `load(dir)` 뿐이고 그것을
부르는 곳은 ① 새로고침 버튼 ② `toggle()` 의 첫 펼침 ③ `revealPath` ④ 자기
조작(생성·이름변경·삭제) 넷이다.

**결과:** 터미널에서 파일을 만들거나, `git checkout` 이 파일을 더하고 지우거나, 다른
에이전트가 파일을 쓰면 — 사용자가 새로고침 버튼을 누르기 전까지 탐색기는 **영영**
옛 목록을 보인다. "즉각적으로 반영되지 않는다" 가 아니라 **아예 반영하지 않는다.**

색은 3초 폴링이 잡으므로 이쪽은 지연(≤3초)이지 누락이 아니다.

### 2.4 겹의 변경을 묻는 종단이 없다

`/api/fs/list` 는 겹 전체(항목 배열)를 준다. 변경 여부만 묻는 값싼 종단이 없으므로,
클라이언트가 지금 "바뀌었나" 를 알려면 겹 전체를 다시 받는 수밖에 없다.

`/api/fs/ignored` 가 **겹 단위 POST 종단의 선례**다 (`handlers_fs_ignored.go`) — 같은
루트 가드를 지나고, 한 번의 요청으로 겹 하나를 판정하며, 4xx 를 클라이언트가 판정으로
굳힌다. 새 종단은 그 모양을 따른다 (D-5).

### 2.5 캐럿 애니메이션은 명시적으로 켜져 있다

`web/js/ui/file-editor.js:351` 의 `cursorSmoothCaretAnimation: 'on'`. Monaco 의 기본값은
`'off'` 이고 VS Code 의 기본값도 `off` 다 — 즉 **끄는 것이 곧 "vsc 처럼"** 이다.

같은 자리 349행의 `smoothScrolling: true` 도 VS Code 기본값(`false`)과 다르지만
그것은 **스크롤**이지 캐럿이 아니다. 접수한 말의 대상이 아니므로 건드리지 않는다
(D-8).

## 3. 요구사항 (Requirements)

### 3.1 묶음 N — 메모장

**FR-NOT-1.** 서버는 **메모 루트**를 하나 갖는다. 경로는 `$DONGMINAL_HOME/notes` 이며,
`worktrees`·`git-worktrees` 와 같은 규약(`dataPath(cfg.DataDir, …)`)으로 파생한다.
경로는 저장하지 않고 매번 파생한다 — 홈이 그렇다 (`Store.Home`, FR-EDT-17).

**FR-NOT-2.** 메모 루트는 **없으면 만든다.** 조회 시점에 `MkdirAll` 하며, 만들지
못하면 그것이 곧 "메모장 표면이 없다" 이다 (FR-NOT-11).

**FR-NOT-3.** `GET /api/editors` 의 응답에 `notes` 를 더한다. 응답은
`{home, notes, list}` 가 된다. `notes` 는 `list` 에 들어 있지 않다 — `home` 과 같은
규약이다 (FR-EDT-29).

메모 루트를 파생하는 자리는 `Store.Notes()` **하나**이며 `List()` 의 시그니처는
그대로 둔다. `List()` 는 목록의 자리이고 메모 루트는 목록이 아니다 — 홈이
`Home()` 으로 따로 서 있는 것과 같은 근거다. 바뀌는 호출처가 둘(`Roots`·
`apiEditorsGet`)뿐이므로 시그니처를 넓혀 얻을 것이 없다.

**FR-NOT-4.** `Entries.Roots()` 는 `[home, notes, ...editors.list]` 를 돌려준다.
이 한 줄이 메모 루트에 대한 `/api/fs/*` 전부 — 조회·생성·이름변경·삭제·업로드·
다운로드 — 를 열어 준다 (FR-EDT-113).

**FR-NOT-5.** `POST /api/editors/add` 로 메모 루트를 더하려 하면 **오류가 아니라
무변경**이다. 홈에 대한 규약(FR-EDT-16)과 같다 — 고정 행이 이미 대표하므로 일반
목록에 같은 경로가 두 번 있을 이유가 없다.

**FR-NOT-6.** 클라이언트의 `_edRoots()` 에 메모 루트가 들어간다. 따라서
`_edReconcile` 이 **메모장 창**을 멱등하게 세운다 (FR-EDT-42). 새 창 타입을 만들지
않는다 — 메모장 창은 `type==='editor'` 이고 `editor.root` 만 메모 루트다.

**FR-NOT-7.** `_edEntries()` 는 메모 루트를 일반 행 목록에서 **뺀다.** 홈을 빼는 것과
같은 이유다 (FR-EDT-16·37) — 고정 행이 이미 대표한다.

**FR-NOT-8.** `_edFixed()` 는 `[메모 행, root 행]` 순으로 돌려준다. 그리기와 순회가
같은 함수(`SidebarList.entries`)를 지나므로 **화면의 순서와 순회의 순서가 같다**
(FR-EDT-6·14). 메모 행이 `~` **위**에 그려진다.

**FR-NOT-9.** 메모 행의 표시 이름은 `메모장` 이고 툴팁은 메모 루트의 절대경로다.
`_edName(root)` 이 그 규칙의 유일한 자리다 — 행 이름과 창 이름이 같은 규칙을 써야
사용자가 둘을 같은 것으로 읽는다 (FR-EDT-10·44).

**FR-NOT-10.** 메모 행에는 `×` 가 없고 재배치의 출발점도 대상도 아니다. root 행과
같다 (FR-EDT-15) — 지울 수 있는 것은 사용자가 더한 행뿐이고 메모 루트는 그것이
아니다.

**FR-NOT-11.** 서버가 `notes` 를 주지 못하면 **메모 행만 없다.** Editor 탭 전체는
그대로다. `home` 을 모를 때 표면 전체가 사라지는 것(FR-EDT-120)과 **다르다** — 홈은
root 창의 근거이지만 메모 루트는 자기 행 하나의 근거일 뿐이다.

**FR-NOT-12.** 메모를 여러 개 두는 수단은 **메모장 창의 탐색기가 이미 가진 "새 파일"**
이다. 별도의 추가 진입점을 만들지 않는다 (D-3).

**FR-NOT-13.** `_editors` 의 **목록만** 갈아끼우는 자리는 함수 하나(`_edPatchList`)를
지난다. `home`·`notes` 는 그 함수가 보존한다.

> **이 요구는 구현 중에 걸린 결함에서 나왔다.** `_edApply` 를 부르는 자리는 셋이고
> (`_edApplyLinked`·`_edMutate`·`_applyRemoteWorkspace`) 셋 다 목록만 새로 알면서
> 나머지 필드를 리터럴로 도로 실어 보냈다. `notes` 를 더하며 앞의 둘만 고치자
> 셋째(`app-cmd.js`)가 `notes` 를 지웠고, `_edRoots()` 에서 메모 루트가 빠지자
> **재조정이 메모장 창을 삭제했다** — 워크스페이스 동기화 한 번에 사라진 것이다.
> 전체 e2e 가 `tool-list-unknown` 의 창 수(4→3)로 이것을 잡았다. 리터럴이 셋으로
> 흩어져 있는 한 필드가 늘 때마다 같은 실수가 가능하므로, 고친 것은 그 한 자리가
> 아니라 **자리가 셋이라는 사실**이다 (D-9).

### 3.2 묶음 L — 탐색기의 살아있는 반영

**FR-FSL-1.** 서버에 `POST /api/fs/stamp` 를 둔다. 요청은 `{root, dirs:[절대경로…]}`,
응답은 `{stamps:{절대경로: 문자열}}` 이다.

**FR-FSL-2.** 스탬프의 값은 그 디렉터리의 `ModTime` 을 유닉스 나노초로 적은 문자열이다.
클라이언트는 그 값을 **해석하지 않는다** — 같은지 다른지만 본다. 그래야 나중에 근거를
바꿔도(예: 크기·항목 수 혼합) 클라이언트가 따라 바뀌지 않는다.

**FR-FSL-3.** 읽을 수 없는 겹(사라졌거나 권한이 없다)은 응답에서 **빠진다.** 오류가
아니다 — 한 겹의 실패가 나머지 겹의 답을 막지 않는다 (FR-EDT-63 과 같은 근거).

**FR-FSL-4.** 루트 가드는 조회·조작과 **같다** (`fsRoot` + `fsResolveExisting`).
새 가드는 새 구멍이다 (FR-ETR 의 규약).

**FR-FSL-5.** `dirs` 의 개수에 상한을 둔다. 상한을 넘으면 `bad_request` 다 — 한 요청이
서버에서 무한정 stat 하지 않게 하는 자리다.

**FR-FSL-6.** 클라이언트는 **관측(`FileTreeStore`)** 에 마지막 스탬프를 기억한다.
루트마다 하나이므로 같은 루트를 보는 칸이 넷이어도 요청은 한 벌이다 (FR-SVS-20).

**FR-FSL-7.** 스탬프를 묻는 주기는 **git 색 폴링과 같은 틱**이다 (`EDITOR_GIT_POLL_MS`).
새 타이머를 만들지 않는다 — 두 관측이 다른 속도로 도는 것은 사용자가 볼 이유가 없는
사실이고, 두 벌로 두면 한쪽만 고쳐진다 (FR-EDT-77 과 같은 근거).

**FR-FSL-8.** 묻는 대상은 **`_kids` 에 캐시된 겹 전부**다 — 루트와 펼쳐진 폴더들이다.
접힌 폴더는 캐시가 있어도 화면에 없으므로 묻지 않는다.

**FR-FSL-9.** 스탬프가 **직전과 달라진 겹만** `load(dir)` 로 다시 읽는다. 같은 겹은
요청이 나가지 않는다 — 이것이 "펼친 폴더 전부 재조회" 와 갈리는 자리이며 요청 수를
겹 수가 아니라 **변경 수**에 비례하게 만든다.

**FR-FSL-10.** `GET /api/fs/list` 의 응답도 그 겹의 스탬프를 함께 싣고, `load(dir)`
은 그것을 기억한다. **읽은 목록과 기억한 스탬프가 같은 관측이어야** 하기 때문이다.

> 스탬프를 폴링에서만 채우면 창이 하나 열린다: `load` 가 T0 에 목록을 읽고 폴링이
> T1 에 스탬프를 처음 본다면, 그 사이의 변경은 "처음 본 겹" 으로 기록되어 **영영
> 재조회되지 않는다** — 다음 변경이 올 때까지 화면이 거짓을 말한다. 서버는
> `apiFSList` 에서 이미 그 디렉터리를 `Stat` 하므로 값을 싣는 비용이 없다.

여전히 기억된 스탬프가 없는 겹은 재조회하지 않는다. 값만 기억한다 — 목록을 아직
읽지 않은 겹이므로 다시 읽을 것도 없다.

**FR-FSL-11.** 응답에서 빠진 겹(FR-FSL-3)은 기억에서도 지운다. 사라진 폴더가 다시
생기면 그때는 FR-FSL-10 의 "처음 본 겹" 이다.

**FR-FSL-12.** 종단이 없거나 4xx 를 내면 **그 루트에서는 다시 묻지 않는다.**
`_gitOff`·`_ignOff` 와 같은 관례다 (FR-ETR-4) — 굳히지 않으면 옛 서버에 붙은 새
브라우저가 3초마다 영영 404 를 받는다. 전송 실패와 5xx 는 판정이 아니므로 다음
회차에 다시 묻는다.

**FR-FSL-13.** 이 관측은 **git 과 무관하다.** git 이 없는 루트, 저장소가 아닌 루트,
`_gitOff` 로 굳은 루트에서도 목록은 따라간다. 메모 루트가 바로 그런 루트다.

**FR-FSL-14.** 화면에 없는 창의 탐색기는 묻지 않는다. 대상은 `_edVisibleTrees()` 가
정하며 `document.hidden` 이면 회차 자체가 없다 — git 폴링과 같은 게이트다.

### 3.3 묶음 K — 캐럿

**FR-CUR-1.** 편집기의 캐럿은 **애니메이션 없이** 이동한다.
`cursorSmoothCaretAnimation` 을 `'off'` 로 둔다.

**FR-CUR-2.** 깜빡임(`cursorBlinking:'blink'`)은 그대로다. 접수한 말은 "움직임" 이지
"깜빡임" 이 아니다.

## 4. 설계 결정 (Design Decisions)

**D-1. 메모 내용은 서버에 산다.** §2.1 이 근거다 — 이 앱의 브라우저 저장소는 설정과
시선만 담는다. 사용자가 그 사실을 듣고 확정했다.

**D-2. 메모는 파일이고 메모장 창은 Editor 창이다.** 전용 `/api/notes` 모델
(id·제목·본문 레코드)과 전용 창 타입을 만들 수도 있었다. 그러나 그러면 CRUD 종단·
창 타입·편집기 뷰·목록 UI 를 새로 짓고, 그렇게 지은 것이 이미 있는 탐색기·Monaco·
분할·저장이 하는 일을 되풀이한다. 메모를 파일로 두면 **새 코드는 "루트가 하나 더
있다" 는 사실뿐**이고, 덤으로 메모가 터미널·git·백업에서 그냥 보인다.

**D-3. 메모 추가의 진입점을 만들지 않는다.** 메모장 창의 탐색기에 이미 "새 파일"
버튼과 우클릭 메뉴가 있다 (FR-EDT-80). 두 번째 진입점은 두 벌의 규칙이 된다.

**D-4. 고정 행은 목록의 앞이 아니라 `fixed` 배열의 앞이다.** `_edFixed()` 의 반환
배열 순서가 곧 `#editor-root` 안의 그리기 순서이고 순회 순서다 (`SidebarList.entries`).
`_edEntries()` 쪽을 건드리지 않으므로 사용자가 더한 행들의 순서·재배치는 한 줄도
바뀌지 않는다.

**D-5. 변경 감지는 mtime 스탬프 폴링이다.** 세 후보를 견주었다.

| 후보 | 요청 수 | 감지 범위 | 비용 |
|---|---|---|---|
| git status 파생 | 0 (기존 폴링에 얹음) | git 저장소 안만 | 없음 |
| **mtime 스탬프 (채택)** | **주기당 1** | **전부** | 종단 하나 |
| fsnotify + SSE | 0 (푸시) | 전부, 진짜 즉시 | 감시 수명 관리·재귀 상한·플랫폼 한계 |

첫째는 사용자가 **"git 이 없을수도 있잖아"** 로 기각했다. 셋째는 D-6 이 기각한다.
mtime 은 겹 안의 항목 **추가·삭제·이름변경**에 반드시 움직인다 — 그것이 목록이
바뀌는 경우의 전부다. 파일 **내용**만 바뀐 것은 겹의 mtime 을 움직이지 않지만 그때는
목록도 바뀌지 않으므로 재조회할 이유가 없다 (그 변화는 git 색이 말한다).

**D-6. fsnotify 를 도입하지 않는다.** 진짜 즉시 푸시이지만 대가가 범위 밖이다 —
감시 등록·해제의 수명을 칸·창·루트와 맞춰야 하고, 재귀 감시에 상한이 필요하며
(`node_modules` 하나가 수만 개의 watch 가 된다), 플랫폼마다 이벤트 유실과 핸들
상한이 다르다. 사용자가 주기를 **"깃과 동일하게"** 로 확정했으므로 3초면 요구가
충족된다.

**D-7. 스탬프 폴링은 새 타이머를 만들지 않는다.** `_edStartGitPoll` 의 틱에 얹는다.
같은 화면의 두 관측이 다른 주기로 돌면 사용자는 "색은 바뀌었는데 목록은 안 바뀐"
중간 상태를 본다.

**D-9. 부분 갱신은 함수로 못박는다.** "아는 값을 도로 실어 보내는" 리터럴은 필드가
늘 때마다 조용히 깨지는 형태다. 값을 보존하는 책임을 호출처 셋에 나눠 두는 대신
함수 하나에 둔다 — 넷째 호출처가 생겨도 같은 실수를 할 자리가 없다 (FR-NOT-13).

**D-8. `smoothScrolling` 은 건드리지 않는다.** VS Code 기본값과 다르지만 접수한 말의
대상이 아니다. 요구되지 않은 변경은 하지 않는다.

## 6. 비목표 (Non-goals)

- 메모의 검색·정렬·태그·이름 규칙. 메모는 파일이고 탐색기가 이미 하는 일이 전부다.
- 메모의 기기 간 실시간 동기화. 서버 파일이므로 같은 서버를 보는 브라우저는 같은
  내용을 보지만, 동시 편집의 병합은 이 SRS 의 일이 아니다 (기존 파일 편집과 같다).
- git 상태 폴링 주기·캐시 TTL 의 변경.
- 탐색기의 파일 **내용** 변경 감지. 겹의 목록이 대상이다.
- `smoothScrolling` 을 비롯한 다른 Monaco 옵션.

## 7. 위험 (Risks)

**R-1. mtime 의 해상도.** 파일시스템에 따라 mtime 이 초 단위일 수 있다. 같은 초 안에
두 번 바뀌면 두 번째를 놓친다. 다음 주기에 또 묻고 그때는 다르므로 **영구 누락은
아니다** — 최악이 한 주기 더 늦는 것이다.

**R-2. 네트워크 파일시스템의 mtime 갱신 지연.** NFS·SMB 마운트에서 겹의 mtime 이
늦게 보일 수 있다. 새로고침 버튼이 여전히 있으므로 사용자가 되찾을 길이 남는다.

**R-3. 메모 루트가 홈 아래일 때의 중복.** `$DONGMINAL_HOME` 이 사용자 홈 아래이므로
root 창(`~`)의 트리를 파고들면 메모 루트가 **그 안에도** 보인다. 결함이 아니다 —
git 핀과 Editor 행이 겹칠 때와 같으며, 가장 깊은 루트가 이기는 규칙(FR-EDT-95)이
파일 열기를 메모장 창으로 보낸다.

**R-4. 스탬프 요청이 늘어나는 경우.** 겹을 아주 많이 펼친 사용자다. 요청 **수**는
주기당 1로 고정이고 늘어나는 것은 서버의 stat 횟수뿐이며, FR-FSL-5 의 상한이 그
꼬리를 자른다.

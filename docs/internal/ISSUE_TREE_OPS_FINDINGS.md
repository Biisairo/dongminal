## 1. migration 으로 넘긴 세션이 Run 멤버를 이어받지 못한다

**일어난 일**
- #37 잎 노드가 맥락 60% 에서 `/dongminal:migration` 으로 새 탭에 넘겼다.
  - 옛 탭: `0fb8cb58-…` · toolId `01a1aae3-b160-…`
  - 새 탭: `b41567cf-…` · toolId `01a1ae03-bb28-…`
- 멤버 `01a1aae3-c3a0-7000-ae80-f140e2c8e585` 는 옛 탭에 묶인 채 남았다. 옛 탭이 닫히자 `state=lost` 가 되었다.

**빠진 것**
- dmctl 에 멤버를 다른 탭으로 옮기는 명령이 없다. 예: `run member --rebind --member <uuid> --at <새 탭>`.

- `node_taken` 판정이 `lost` 멤버도 「맡고 있음」으로 본다. 승계 경로가 없으니 그 노드는 다시 맡을 수 없다.

**바라는 동작**
- migration 이 멤버의 탭 · toolId 를 새 세션으로 옮긴다. member id · role · 트리 노드는 그대로 둔다.
- 옛 탭의 멤버는 `lost` 가 아니라 「승계됨」으로 기록한다.

  - 트리 노드

- 하위 이슈를 더하거나 순서를 바꾸면, 서브이슈 순서를 진행 순서에 맞게 다시 놓는다. 예: `reprioritizeSubIssue`.

## 5. 상태 표시가 명령마다 다르다

- 같은 시각에 같은 루트 노드가 명령마다 다르게 보였다.
  - `dmctl status --at <루트 탭>`: `state=done`
  - `run tree`: `ccr#32 state=ready`
  - 몇 분 뒤 `run status` · `run tree`: `working`
- 하위를 띄우고 쉬는 중간 노드의 상태는 #35 처럼 `ready` 로도, #33 · #34 처럼 `working` 으로도 보인다. 같은 상황인데 표시가 갈린다.
- 바라는 동작: 「하위를 기다리며 쉬는 중간 노드」를 따로 나타내는 상태가 하나 있다. 예: `waiting-children`.

## 6. 발사대 문서가 스킬 문서의 위치를 알려 주지 않는다

- 배정 엔벨로프에는 「이 문서의 절대 경로」를 넣어야 한다. 그런데 문서는 그 경로를 적지 않는다. 플러그인 캐시에도 없어서 `~/.dongminal/bin/agent-plugin/commands/issue-tree.md` 를 찾느라 여러 번 탐색했다.
- issue-tree 문서가 가리키는 스펙 `docs/internal/ISSUE_AGENT_TREE_SRS.md` 는 상대 경로라, 대상 저장소(ccr)에서는 찾을 수 없다.
- 바라는 동작: 두 경로를 절대 경로로 적거나, 경로를 알려 주는 명령을 둔다. 예: `dmctl doc issue-tree`.

## 7. issue-tree 노드의 migration 이 배정을 새 세션에 넘기지 않는다

**지금 상태(확인한 사실)**
- issue-tree 노드 절차 6-3 은 다음 셋만 말한다. migration 에 실을 내용은 정하지 않는다.
  - `/dongminal:migration` 으로 넘긴다.
  - 탭 이름을 같게 한다.
  - 하위에게 새 toolId 를 알린다.
- `migration.md` 는 issue-tree 를 「범위 밖」으로만 언급한다. 그래서 절차는 일반 세션과 같다. 문서 한 장과 「읽어라」 엔벨로프만 보낸다.
- 부모가 새 세션에 넣어 주는 것도 없다.

**일어난 일**
- #37 인계 엔벨로프의 내용은 부모 #35 의 즉석 지시와 #37 세션의 판단으로 채워졌다. 들어간 것은 역할 · Run · member id · 부모 toolId · 맥락 기준 · 노드 절차 경로 · report 명령 · 닫는 규약이다.
- 다른 노드가 migration 하면 이 중 일부가 빠질 수 있다.
  - 맥락 기준이 빠지면, 새 세션은 다시 넘길 기준을 모른다.
  - 부모 toolId 가 빠지면, 「완료」를 보낼 곳을 모른다.
  - 목표 경로 · 커밋 허용 · 병렬 가지 여부가 빠지면, 노드 절차를 따를 수 없다.

**바라는 동작**
- issue-tree 노드가 migration 하면 **배정 블록 전체**를 새 세션에 다시 싣는다. 이 일은 절차나 명령이 보장한다.
  - 배정 블록: `[ISSUE-TREE 배정]` 의 모든 줄(노드 · 사슬 이름 · 목표 경로 · 부모 · 그룹 · Run · 병렬 가지 · 맥락 기준 · 커밋)과 member id 다.
  - 방법 예: migration 이 Run 멤버이면 `dmctl` 이 배정을 기록에서 읽어 엔벨로프에 자동으로 붙인다. 또는 issue-tree 전용 인계 틀을 둔다.
- 배정이 바뀌었으면 바뀐 값을 싣는다. 예: 맥락 기준 정정 · 끼어든 이슈(2번).
- 새 세션이 일을 시작하면 부모에게 새 toolId 를 알린다. 멤버 승계(1번)도 같은 걸음에서 한다.

## 8. issue-tree 가 일반 Run 을 그대로 써서 노드의 깊이가 드러나지 않는다

**지금 상태(확인한 사실)**
- 발사대는 일반 `dmctl run start ... --isolation per-run --tree <ref>` 로 Run 하나를 연다. 모든 노드는 그 Run 에 `run member` 로 붙는다. 그래서 Run 쪽에서 보면 다섯 노드(#32 · #33 · #34 · #35 · #37)가 **같은 높이의 멤버**다.
  - `run status` 는 멤버를 평평한 목록으로 낸다.
  - 프리앰블의 「조정자」는 모든 멤버에서 발사대 하나다. 부모 · 자식 관계는 Run 기록에 없다.
- 깊이는 **사슬 이름의 문자열**에서만 나온다.
  - 서버(`handlers_runs_tree.go`)가 role `ccr#32›33›34` 를 잘라 `parent` 를 정한다.
  - 대시보드의 「이슈 트리」 영역(`web/js/ui/run-tree.js`)은 그 `parent` 로 `--depth` 를 세어 들여 쓴다.
  - CLI 의 `run tree` 도 들여 쓴다.
- 그런데 Run 화면의 나머지는 일반 Run 그대로 평평하다. 나머지는 멤버 그래프(SVG) · 카드 · 타임라인이다(`runs-panel.js` `_runBuildRoot`). 이 부분에서는 깊이가 보이지 않는다.
  - 화면을 직접 보고 확인하지는 않았다. 코드로 확인했다.
- 결과: 사용자가 Run 을 열면 노드 다섯이 한 줄로 늘어선 일반 Run 처럼 보인다. 이슈 트리 구조는 위쪽의 작은 영역에서만 보인다.

**사용자 지시**
- issue-tree 는 일반 Run 을 쓰지 말고 **issue-tree 전용 Run** 을 만든다.
- 지금 Run 을 쓰는 것은 issue-tree 뿐이므로, Run 을 issue-tree 에 특화해서 만들어도 된다.
- 목표는 **각 이슈 노드의 깊이(부모 · 자식 구조)가 제대로 보이는 것**이다.

**바라는 동작**
- 부모 · 자식 관계를 Run 이 **데이터로** 가진다. 사슬 이름 문자열에서 추정하지 않는다.
  - 예: `run member --parent <부모 member>`
  - 이 데이터가 있으면 끼어든 이슈(2번)나 노드가 맡은 이슈의 변경도 구조로 표현할 수 있다.
- Run 화면의 중심(그래프 · 카드)이 이슈 트리 모양이다. 루트 → 중간 → 잎의 깊이와, 병렬 가지가 보인다.
  - 각 노드에 이슈 번호 · 제목 · 상태 · 맥락 사용률이 보인다.
  - 상태에는 「하위를 기다리는 중」(5번)이 포함된다.
- 병렬 가지는 지금 새 Run 으로 갈라진다. 이 경우에도 한 트리로 이어 보인다.
- 「조정자」는 발사대가 아니라 각 노드의 부모다(4번과 함께 푼다).
- 닫힌 하위 이슈(완료된 노드)도 트리에 흔적으로 남긴다. 예: #36 · #74 · #62 · #63 이 끝난 노드로 보인다. 그래야 진행 순서가 보인다.

# 요구: 맥락 기준 migration 의 기본값 · 설정 · 훅 (사용자 지시 · 2026-11-06)

## 지금 상태(확인한 사실)

- 맥락 기준은 issue-tree 의 인자 `--ctx` 뿐이다. 기본값은 **60**이다(`commands/issue-tree.md` 15행). 설정 파일에서 바꿀 자리가 없다.
- 그 값을 보는 것은 **중간 노드의 안전 지점**(노드 절차 6-3)뿐이다. 잎 노드의 절차에는 맥락 검사가 없다.
  - 이번에 #37 잎 노드가 61% 에서 넘긴 것은 부모 #35 가 「지금 넘겨라」라고 지시했기 때문이다. 절차가 넘긴 것이 아니다.
- 플러그인 훅(`agent-plugin/hooks/hooks.json`)은 `SessionStart` 하나뿐이다. 내용은 `dmctl agent-context claude` 다. 맥락 사용률을 보는 훅은 없다.

## 요구

1. **issue-tree 맥락 기준의 기본값을 60 → 50 으로 낮춘다.**
2. **그 값을 설정에서 바꿀 수 있게 한다.**
   - 인자 `--ctx` 는 설정보다 우선한다.
   - 우선순위는 `--ctx` > 설정 > 기본값 50 이다.
   - 켬 · 끔도 설정으로 둔다. 끄면 노드가 맥락 때문에 넘기지 않는다.
3. **훅으로 모든 에이전트에 맥락 기준 migration 을 적용한다.**
   - issue-tree 노드가 아닌 일반 세션에도 적용한다.
   - 훅이 맥락 사용률을 보고, 기준 이상이면 에이전트에게 `/dongminal:migration` 을 하라고 알린다.
   - 훅 이벤트와 알림 방식은 dongminal 이 정한다. 후보는 `UserPromptSubmit` · `Stop` · `PostToolUse` 에서 additional context 를 넣는 방식이다.
4. **훅의 설정과 issue-tree 의 설정은 별개다.**
   - 값(퍼센트)과 켬 · 끔을 따로 둔다. 예:
     - `migration.hook.enabled` · `migration.hook.ctxPct`
     - `issueTree.migration.enabled` · `issueTree.migration.ctxPct`
   - 한쪽을 바꿔도 다른 쪽의 값이나 켬 · 끔이 바뀌지 않는다.
   - 기본값은 둘 다 50 이다. 훅의 켬 · 끔 기본값은 dongminal 이 정하되, 정한 값을 문서에 적는다.
5. **issue-tree 노드도 잎 노드의 맥락 검사를 절차에 넣는다.** 지금은 중간 노드에만 있다. 넘길 자리(안전 지점)는 「하위 이슈를 하나 끝내고 커밋한 뒤」처럼 정의해서 적는다.

## 사용자 결정: issue-tree 의 migration 과 일반 훅을 나눈다(2026-11-06)

**이유**: issue-tree 노드가 migration 할 때는 일반 세션보다 넘길 것이 더 많다(7번: 배정 블록 · member id · 멤버 승계 · 부모 알림). 일반 훅이 issue-tree 노드에서 걸리면 이 내용을 빼고 일반 migration 을 하게 된다. 그래서 두 동작을 나눈다.

**규칙**
- issue-tree 가 에이전트를 띄울 때, 기동줄에 **「이 세션은 issue-tree 노드다」라는 표시**를 넣는다.
- 일반 맥락 훅은 그 표시가 있는 세션을 건너뛴다.
- issue-tree 노드는 issue-tree 설정(`issueTree.migration.*`)과 노드 절차만 따른다. migration 할 때는 7번의 내용을 함께 넘긴다.
- 표시가 없는 세션은 일반 훅 설정(`migration.hook.*`)을 따른다.
- 두 설정의 값과 켬 · 끔은 서로 영향을 주지 않는다(요구 4).

**표시를 넣을 자리(사실과 후보)**
- 지금 기동줄은 `claude '--allowedTools' 'Bash(dmctl:*)' -- '<프리앰블>'` 이다. 이 기동줄은 `dmctl run launch --member <uuid>` 가 낸다.
- 표시를 넣는 방법은 dongminal 이 고른다. 후보는 셋이다.
  - (가) 환경 변수: 기동줄 앞에 `DONGMINAL_ISSUE_TREE=1` 같은 변수를 붙인다. 훅 명령은 에이전트의 환경을 물려받으므로 바로 읽을 수 있다.
  - (나) 에이전트 인자: `claude --settings <json>` 처럼 그 세션에서만 훅을 끄는 설정을 넘긴다.
  - (다) 서버 판정: 훅이 `dmctl` 에 자기 toolId 를 물어, issue-tree 배정을 받은 Run 멤버인지 판정한다.
- **migration 으로 이어받은 새 세션도 같은 표시를 가져야 한다.** 그러지 않으면 넘긴 다음 세션부터 일반 훅이 다시 걸린다. 그래서 issue-tree 노드의 migration(7번)이 새 세션을 띄울 때도 같은 기동 방식을 쓴다.

## 사용자 결정: 일반 훅은 기준을 넘긴 뒤 매 훅마다 「넘기기」를 강하게 제안한다(2026-11-06)

- **언제**: 맥락 사용률이 기준(`migration.hook.ctxPct` · 기본 50)을 넘은 **바로 그 훅부터** 알린다. 그 뒤로는 **매 훅마다** 다시 알린다. 한 번 알리고 끝내지 않는다.
- **무엇을**: 알림마다 **현재 맥락 사용률**(예: 「지금 맥락 57% · 기준 50%」)을 함께 싣는다. 그리고 `/dongminal:migration` 으로 세션을 넘기라고 제안한다.
- **얼마나 세게**: 강하게 제안하되 **강제는 아니다**.
  - 넘기면 안 되는 경우가 있다. 작업이 한창이고 지금 맥락이 그 작업에 꼭 필요할 때다. 예: 여러 파일에 걸친 수정을 반쯤 했거나, 디버깅 단서를 머릿속에 들고 있을 때다. 이럴 때는 에이전트가 넘기지 않아도 된다.
  - 그 밖의 경우에는 넘기라는 말을 분명히 한다. 「무조건」보다 조금 느슨한 정도다.
  - 알림을 받았다고 반드시 넘겨야 하는 것은 아니다.
- **하지 않는 것**: `Stop` 으로 턴 끝냄을 막아 강제로 넘기게 하지 않는다.
- **어느 훅 이벤트에 걸지**는 dongminal 이 정한다. 「기준을 넘긴 뒤 매 훅」이 뜻을 지키도록, 도구 호출마다 불리는 이벤트(`PostToolUse`)를 포함하는 것이 자연스럽다.
  - 맥락 사용률은 `dmctl status --json` 의 `context.usedPct`(statusline 근거)로 읽는다.
  - 값을 읽을 수 없으면 알리지 않는다. 대신 그 사실을 한 번 알린다.
- issue-tree 노드에도 같은 세기의 문구를 쓸지는 이 결정의 범위 밖이다. issue-tree 는 자기 절차(안전 지점)를 따른다.

## 사용자 결정: 설정은 설정창이 저장하는 같은 파일에 둔다(2026-11-06)

**확인한 사실**
- 설정창이 저장하는 곳은 `~/.dongminal/settings.json` 이다. 서버의 `settingsStore` 가 JSON 을 통째로 받아 이 파일에 쓴다(`internal/webserver/httpapi/handlers_settings.go` 21행).
- 설정 항목 목록과 기본값의 원본은 `web/js/core/settings-defaults.js` 의 `SETTINGS_SCHEMA` 다(CONFIG_MANAGEMENT_SRS FR-CFG-2).
- 같은 파일에 맥락 관련 값이 이미 있다. `orchestration.contextWarnRatio`(기본 0.70)와 `orchestration.contextCriticalRatio`(기본 0.85)다(`run.ContextPolicy` · FR-CBG-2). 이 값들은 Run 멤버의 맥락 등급(ok · warn · critical)을 표시하는 기준일 뿐이다. migration 을 시키지 않는다.

**결정**
- migration 설정 넷을 `~/.dongminal/settings.json` 에 더한다. `SETTINGS_SCHEMA` 에 넣어 설정창 항목으로도 보이게 한다.
  - 일반 훅: `migration.hook.enabled` · `migration.hook.ctxPct`(기본 50)
  - issue-tree: `issueTree.migration.enabled` · `issueTree.migration.ctxPct`(기본 50)
  - 키 이름은 예시다. 기존 스키마의 이름 규약을 따라 dongminal 이 정한다. 예: `orchestration.*` 아래에 둔다.
- 저장소별 덮어쓰기는 두지 않는다. 우선순위는 `--ctx` 인자(issue-tree 만) > 설정 > 기본값 50 이다.
- 훅과 `dmctl` 은 이 값을 서버나 파일에서 읽는다. 값이 비었거나 말이 안 되면 기본값으로 돌아간다. `ContextPolicy.withDefaults` 와 같은 규칙이다.

**함께 알아 둘 점**
- 표시 기준인 warn 70% 와 migration 기준 50% 는 서로 다른 값이다. 그래서 50~70% 구간에서는 대시보드가 `ok` 인데 훅은 넘기라고 할 수 있다.
- 이 차이를 그대로 둘지는 dongminal 이 정한다. 예를 들어 migration 기준을 넘기면 별도 표시를 붙일 수 있다. 정한 내용은 문서에 적는다.

# 추가 기능: 최상단 표시줄에 포커스된 탭 이름을 보인다(사용자 지시 · 2026-11-06)

issue-tree 와는 따로인 화면 기능이다.

**지금 상태(확인한 사실)**
- 최상단 표시줄의 `#window-name` 은 `web/js/ui/renderer-chrome.js` 의 `_rTopbar()` 가 칠한다(118행).
- 내용은 `_rWinTitle(w)` 가 만든다. 형식은 `<창 종류 라벨> · <window 이름>` 이다(88~95행). 예: `Terminal · renderer`. 탭 이름은 들어가지 않는다.
- 칸(slot)이 여럿이면 표시줄을 **비운다**(FR-STB-11 · 12 · D-STB-1). 그 자리는 각 칸의 머리글이 이어받고, 표시줄 자리에는 칸 마커가 선다(SLOT_MARKER_SRS FR-SMK-1 · 2).

**요구**
- 표시줄에 지금 **포커스된 탭의 이름**까지 보인다. 「포커스된 탭」은 그 window 에서 포커스를 가진 pane 의 활성 탭이다.
  - 예: `Terminal · renderer · ccr#32›33›34›35›37 3D 피킹 질의`
- 포커스가 다른 pane 이나 탭으로 옮겨 가거나 탭 이름이 바뀌면 바로 따라간다.
- 탭 이름이 길면 줄인다. 줄이는 방식(말줄임 · 툴팁으로 전체 보기 등)은 기존 탭 표시 규약을 따른다.

**사용자 결정: window 이름이 보이는 모든 자리에 붙인다**
- window 이름을 보이는 자리는 둘이다.
  - 최상단 표시줄 `#window-name`: 칸이 하나일 때 쓴다.
  - 각 칸의 머리글 `.slot-head`: 칸이 여럿일 때 쓴다(`renderer-layout.js` 73행).
- 두 자리 모두 **같은 함수 `_rWinTitle(w)`** 로 window 이름을 만든다.
- 두 자리 모두 그 window 의 포커스된 탭 이름까지 보인다.
  - 칸이 여럿이면, 각 칸 머리글이 **자기 window** 에서 포커스된 탭 이름을 보인다.
  - 칸이 하나면, 최상단 표시줄이 보인다.
- 구현 자리는 `_rWinTitle` 하나, 또는 그것을 감싸는 함수 하나로 모은다. 두 자리가 따로 놀지 않게 하기 위해서다.
- 모바일 표시줄도 같은 규칙을 따르는 것이 자연스럽다. 모바일은 화면 폭이 좁으므로 줄이는 방식은 dongminal 이 정한다.

## 12. issue-tree Run 의 동시 진행 문제 — 분석과 수정

- **요구:** 병렬 실행처럼 여러 노드가 동시에 진행될 때, 동작하는 위치에 따라 정보가 중복되거나 충돌할 수 있다. 이 문제를 분석하고 고친다.
- **정해야 할 것 셋:**
  1. 질문이 생기면 어느 조상까지 올라가는가.
  2. 질문에 아무도 답할 수 없으면 누가 사용자에게 묻는가.
  3. 결정 사항이 생기면 누가 기록하는가.
- **착수 때 할 일:** 지금 노드 절차(`commands/issue-tree.md`)와 Run 프리앰블(`run/preamble.go`)이 셋을 어떻게 다루는지 먼저 적는다. 그다음 병렬 가지에서 질문이나 결정이 겹치는 경우를 찾는다. 같은 질문이 두 번 사용자에게 가거나, 한 결정을 두 노드가 다르게 기록하는 경우가 그 예다. 세 질문의 답은 SRS 에서 결정으로 적는다. 4번(프리앰블과 절차의 충돌)·7번(migration 의 배정 이관)과 겹치므로 함께 다룬다.

## 13. 다음 형제 이슈로 가는 세션 교체는 부모가 한다

- **원문(사용자 · 2026-11-07):** "다음 형제 이슈로 이동할 때 leaf 가 직접 하는게 아닌 무조건 부모에 의해 세션이 닫히고 열려야 한다. migration 하는 경우는 같은 이슈를 진행하면서 컨텍스트 사이즈가 부족할 때 뿐 이다."
- **요구:**
  - 잎 노드는 다음 형제 이슈로 스스로 넘어가지 않는다. 자기 이슈를 끝내면 부모에게 보고하고, **부모가** 그 세션을 닫고 다음 형제의 세션을 연다.
  - migration 은 **같은 이슈**를 이어 가다 맥락이 모자랄 때만 쓴다. 다른 이슈로 넘어가는 수단이 아니다.
- **착수 때 할 일:** 지금 노드 절차(`commands/issue-tree.md`)와 migration 명령(`commands/migration.md`)이 형제 이동을 어떻게 하는지 확인한다. 잎이 형제로 넘어가는 길이 있으면 없앤다. 7번(migration 의 배정 이관)·1번(Run 멤버 이어받기)과 함께 다룬다.

## 14. 세션에 넘기는 지시가 이슈 운영 전부를 담는다

- **원문(사용자 · 2026-11-07):** "스스로 migration 및 부모가 세션을 열 때, 단순히 이슈를 해결하는 것 뿐만 아닌 깃허브 이슈 위치를 진행중으로 옮기고 중간에 필요할때 이슈에 메모를 추가하고, 자식이슈가 필요할 때 이슈를 만들고, 이슈를 닫고, 완료로 옮기고 하는 등의 모든 동작을 할 수 있도록 프롬프트를 잘 전달하여야한다"
- **요구:** 새 세션에 넘기는 지시(부모가 여는 노드의 지시, migration 의 인계 문서·엔벨로프)는 이슈를 푸는 일만이 아니라 아래 운영 동작을 모두 담는다.
  - 착수할 때 이슈를 "진행 중" 으로 옮긴다(프로젝트 보드의 상태).
  - 필요할 때 이슈에 메모(코멘트)를 남긴다.
  - 하위 이슈가 필요하면 만든다.
  - 끝나면 이슈를 닫고 "완료" 로 옮긴다.
- **착수 때 할 일:** 지금 노드에 주는 지시(`commands/issue-tree.md` 의 노드 절차, Run 프리앰블 `run/preamble.go`)와 migration 인계가 이 동작을 얼마나 담는지 표로 대 본다. 규약의 주인은 그 프로젝트의 지시 문서다(FR-IAT-55·D-IAT-7). 그래서 지시는 "그 규약을 읽고 이 동작들을 하라" 를 빠뜨리지 않는 쪽으로 쓴다. 4번(프리앰블과 절차의 충돌)과 함께 다룬다.

# 참고: server-driven 구현 내용 (2026-11-07, 사용자 지시)

이 문서에 착수하기 전에 끝낸 `SERVER_DRIVEN_ACTIONS_SRS`(승인·구현완료)의 내용이다. issue-tree 노드와 migration 세션은 dmctl·HTTP 로 서버를 직접 부르므로, 서버가 무엇을 거절하고 어떻게 알리는지 알아야 한다. 커밋은 `7ba5f781`~`4979072c` 다.

## 바뀐 원칙

- **판단의 주인은 서버다**(D-SDA-1). 버튼을 켤지, 메뉴 항목을 막을지, 입력이 맞는지를 서버가 답한다. 화면은 그 답을 그린다.
- **화면을 거치지 않은 요청도 같은 규칙으로 거절된다**(D-SDA-3·FR-SDA-9). 에이전트가 dmctl·curl 로 보내도 화면과 같은 판정을 받는다. 예전에는 화면만 막던 12건(자기 하위로 옮기기, 이름의 `/`, 현재 브랜치 checkout 등)이 이제 서버에서도 거절된다.
- **거절은 사유 코드로 온다**(D-SDA-5). 본문에 한국어 문장(`message`)을 싣지 않는다. 코드의 뜻은 `docs/external/errors.md` 에 있다.

## 장치

- **답의 모양:** `{"ok": bool, "why": "<코드>", "args": {…}}`. `ok` 가 참이면 `why`·`args` 가 없다. 답과 실행 거절은 같은 판정 함수를 부른다(D-SDA-6) — 답이 거짓이면 실행도 같은 코드로 거절된다.
- **1층(상태에 싣는 답):** `GET /api/git/status` 의 `actions` 처럼 상태 응답에 함께 온다.
- **2층(열 때 묻는 답):** `GET /api/git/actions?…`(git 메뉴·대화상자 입력), `POST /api/fs/actions`(파일 메뉴), `POST /api/fs/validate-name`, `POST /api/editors/validate`, `POST /api/access/check`.
- **오류 방언은 표면마다 다르다:** git `{error,args}` · fs `{code,args}` · 평문(`X-Error-Code` 헤더) · runs `{error,detail}`. 코드를 읽으려면 헤더 `X-Error-Code` 를 먼저 본다.
- **상수:** 상한·목록은 `GET /api/meta`·`GET /api/git/policy` 가 보낸다. 서버가 보낼 수 없는 두 벌은 게이트 `scripts/check-shared-constants` 가 대조한다.

## issue-tree 운영에 닿는 것

- **Run 의 종료·삭제·멤버 분리**(묶음 R): 목록·그래프의 Run·멤버에 `actions`(`run.close`·`run.delete`·`run.member.detach`)가 실린다. 종료는 `force` 뜻을 유지한다(D-SDA-9). 닫힌 Run 에 대한 요청은 `run_closed`, 붙지 않은 멤버는 `member_not_attached` 로 거절된다. 조정자 절차가 Run 을 닫을 때 이 코드를 읽는다.
- **dmctl 의 이름 상한**(D-SDA-8): 창·탭·그룹 이름이 64자(UTF-16)를 넘으면 `/api/commands` 가 400 `name_too_long` 로 거절한다. 노드 이름을 긴 이슈 제목으로 지으면 걸린다 — 잘라서 보낸다.
- **Run 의 짧은 id**(K-l): `/api/tools/background` 의 Run 멤버에 `runShort` 가 있다. 화면이 runId 를 자르지 않는다.
- **샌드박스**(K-i): `/api/sandbox/runtime` 의 `ready`·`installed`, `/api/sandbox/profiles` 의 `workPicks`·헤더 `X-Sandbox-Only-Default`.

## 1. 서론 (Introduction)

### 1.1 목적 (Purpose)

2026-08-27 사용자 검토에서 나온 **오류 3건**과, E1·E3 의 공통 원인을 확정한다.

| E2 | "그래프 모양이 VSCode 의 Git Graph 확장과 다르다 … 모든 선을 왼쪽으로 붙여 그리는데 이쪽은 그러지 않아 두 번째 그래프가 혼자 떨어져 있다" | FR-GIT-117·119(개정), FR-GIT-228~231 |
| E3 | "히스토리에서 브랜치 더블클릭 체크아웃이 구현되지 않았다" | FR-GIT-232 |

E1·E3 는 **같은 원인**이다 — 사용자가 만들지 않은 계기(폴링·서버 푸시)로 목록을
다시 그리면서 **DOM 요소를 새로 만들어, 요소에 붙어 있던 상태를 깨뜨린다.** 그 상태에는
hover, 진행 중인 더블클릭, native 드래그, 글자 선택, 기본 툴팁이 있다.

전수 조사에서 **같은 원인의 자리 5곳을 더 찾았다** (§2.2). 그래서 방어를 자리마다
따로 두지 않고 **공통 규약 하나**로 만든다 (FR-RPT-6) — 자리마다 손으로 막으면 다음
목록에서 또 빠진다. 실제로 이 저장소는 같은 함정을 세 번 만나 세 번 다르게 막았다.

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **자기 계기(user-driven)** | 사용자의 행동이 직접 부른 다시 그리기 (클릭·키·드롭) |
| **바깥 계기(ambient)** | 사용자가 만들지 않은 계기 — 폴링 타이머, 서버 푸시(SSE), 다른 클라이언트·다른 에이전트의 변경 |
| **요소 상태(element state)** | DOM 요소에 붙어 있고 값으로 다시 만들 수 없는 상태: `:hover`, `:focus`, 진행 중인 CSS transition, 진행 중인 더블클릭의 첫 클릭, native 드래그 세션, 글자 선택, 표시 중인 기본 툴팁 |
| **관측 동일성(observation identity)** | 이번에 그릴 내용이 지금 그려져 있는 것과 같음 |
| **행 동일성(row identity)** | 같은 항목이 다시 그린 뒤에도 **같은 DOM 요소**로 남음 |
| **희소 레인(sparse lane)** | `activeLanes` 의 인덱스. 갈래가 살아 있는 동안 바뀌지 않는다 |
| **열(column)** | 화면에서 선이 놓이는 x 위치의 정수 좌표. 빈 열이 없다 |
| **행 공간 S(i)** | 행 i 에서 살아 있는 희소 레인을 순서를 지켜 0..n-1 로 촘촘히 매긴 것 |
| **색 키(color key)** | 팔레트를 고르는 정수. 열이 아니라 갈래에 붙는다 |
| **배지(badge)** | 커밋 행에 붙는 ref 표식 (`.git-hist-badge`, FR-GIT-126) |

## 2. 전반 기술 (Overall Description)

### 2.1 근거 (Rationale) — 하나의 원인

목록을 다시 그리는 흔한 모양은 이것이다.

```js
container.innerHTML='';
for(const item of items) container.appendChild(build(item));
```

값으로 화면을 만드는 방식이라 **읽기 쉽고, 자기 계기에서는 옳다.** 사용자가 무언가를
눌러서 목록이 바뀌었으면 다시 그려지는 것이 맞다.

**바깥 계기에서는 틀린다.** 요소를 버리고 새로 만들면 값으로 되살릴 수 없는 것이
함께 사라진다.

| 잃는 것 | 사용자가 보는 것 |
|---|---|
| `:hover` | hover 로만 보이는 버튼이 사라진다. 새 요소는 **다음 마우스 이동까지** `:hover` 를 받지 못한다 |
| 진행 중인 transition | `transition:opacity .1s` 가 0 에서 다시 시작한다 — 주기마다 페이드인이다 |
| 더블클릭의 첫 클릭 | 두 번째 클릭이 **다른 요소**에 떨어져 브라우저가 `dblclick` 을 만들지 않는다 |
| native 드래그 세션 | 끌고 있던 요소가 DOM 에서 빠지면 드래그가 취소된다 — 재배치가 조용히 실패한다 |
| 글자 선택 | 복사하려고 고른 범위가 사라진다 |
| 표시 중인 기본 툴팁 | `title` 툴팁이 닫힌다 — 읽는 중에 사라진다 |

E1 은 이 표의 첫 두 줄이고, E3 는 세 번째 줄이다. 원인이 하나이므로 **방어도 하나**여야
한다.

**이 저장소는 이미 같은 함정을 세 번 만났고, 세 번 다르게 막았다.**

| 자리 | 막은 방법 | 근거가 적힌 곳 |
|---|---|---|
| History 목록 | `_winKey` 가 같으면 행을 만들지 않는다 | `history.js` `_paintRows` |
| refs 사이드바 | `dataset.sig` 가 같으면 요소를 만들지 않고 선택만 고친다 | `history.js` `_paintRefs` — "다시 만들면 더블클릭의 두 번째 클릭이 새 요소에 떨어져 브라우저가 `dblclick` 을 만들지 않는다" |
| 알람 표식 | 전체 `render()` 대신 클래스만 토글한다 | `app-attn.js` `_attnRefresh` — "전체 render() 를 피해 포커스 플리커(xterm blur/refocus)를 막는다" |
| Branches 트리 | HEAD 가 바뀔 때만 다시 받는다 | `panel.js` `_paint` — "목록 전체를 폴링마다 다시 그리면 스크롤이 매초 흔들린다" |

같은 문제를 네 번째로 손으로 막는 대신 **규약과 공통 수단**을 만든다.

### 2.3 근거 — E2 는 다른 원인이다

`buildLaneGraph` 는 희소 레인 인덱스를 갈래가 사는 동안 유지하고, 비워진 레인은
**뒤쪽만** 잘라낸다(`while … pop()`). 가운데 갈래가 먼저 끝나면 그 인덱스는 빈 채
남고, 새 머리가 와서 채울 때까지 화면에 **빈 열**로 보인다. 오른쪽 갈래가 혼자
떨어져 보이는 것이 그것이다.

현재 알고리즘으로 실측했다 (`--all` 에서 세 갈래 중 가운데가 먼저 끝나는 모양).

```
A1  lane=0 pass=[]      parents=[0]
B1  lane=1 pass=[0]     parents=[1]
C1  lane=2 pass=[0,1]   parents=[2]
B2  lane=1 pass=[0,2]   parents=[]     ← B 갈래가 끝난다
A2  lane=0 pass=[2]     parents=[0]    ← 열 1 이 빈다
C2  lane=2 pass=[0]     parents=[2]    ← C 가 열 2 에 홀로 남는다
A3  lane=0 pass=[2]     parents=[]
C3  lane=2 pass=[]      parents=[]
```

압축은 **색과 함께 풀어야 한다.** 지금 `_svg` 의 색은 열에서 파생한다
(`pal[l%pal.length]`). 열을 압축하면 갈래가 왼쪽으로 옮겨질 때 색이 함께 바뀌어,
같은 갈래가 중간에 색을 갈아입는다. FR-GIT-119 는 "테마 팔레트에서 파생"만 요구하고
열에서 파생하라고 하지 않았으므로, 색 키를 **갈래(희소 레인)** 에 붙인다.

압축하면 선이 행 경계에서 열을 옮긴다. 그러려면 각 세그먼트가 **위 끝과 아래 끝의
열을 따로** 알아야 한다. 지금의 행 모델(`passThrough` 가 열 하나짜리 배열)로는
표현할 수 없으므로 모델을 넓힌다. 넓히는 방향은 하나로 정해진다.

**공간의 정의.** 행 i 의 공간 T(i) 는 **행 i 에 들어올 때 살아 있는 갈래에 그 행의
커밋 레인을 더한 것**을 순서를 지켜 0..n-1 로 촘촘히 매긴 것이다. 마지막 행 다음의
공간 T(n) 은 마지막 행을 나갈 때 살아 있는 갈래로 만든다.

- 행 i 는 **위 끝과 점을 T(i)**, **아래 끝을 T(i+1)** 로 그린다.
- 행 i 의 아래 끝 공간이 곧 행 i+1 의 위 끝 공간이므로 **선이 끊기지 않는다.**
- 커밋의 진입선은 위 끝과 점이 같은 공간이라 **늘 곧게** 내려온다. 갈래가 열을
  옮기는 것은 아래 끝에서 일어나고, 그 행 안에서 곡선으로 이어진다.
- T(i) 는 행 i+1 의 커밋 레인까지 알아야 정해진다(새 머리가 빈 자리를 채우면 그
  오른쪽 열이 한 칸 밀린다). 그래서 **위상과 배치를 나눈다** — 위상은 앞을 보지 않고,
  배치는 위상 결과를 한 번 더 훑는다 (FR-GIT-117 개정).

### 2.3.1 참조 구현 — VSCode Git Graph 가 실제로 하는 것

사용자가 기준으로 든 도구(`mhutchie/vscode-git-graph`)의 `web/graph.ts` 를 읽고
확인했다. **추측이 아니라 그 코드가 근거다.**

| # | 규칙 | 근거 |
|---|---|---|
| R1 | **행마다 열을 왼쪽부터 촘촘히** 나눠 준다. 갈래를 머리 행 순서로 처리하고, 각 행에서 `nextX`(아직 안 쓰인 가장 왼쪽 열)를 집는다 → 결과가 **나이 순 촘촘한 배치**다 | `registerUnavailablePoint(x,…){ if(x===this.nextX){ this.nextX=x+1; … } }` · `getNextPoint()` |
| R2 | 커밋 **점**의 열은 한 번 정해지면 고정이다. 그러나 통과선은 그 행의 다음 빈 열을 받으므로, 앞 갈래가 끝나 열이 비면 **왼쪽으로 휜다** | `addToBranch(branch,x){ if(this.onBranch===null){ … this.x=x } }` · `branch.addLine(lastPoint, curPoint, …)` 이 `x1≠x2` 면 곡선/각진 전이로 그린다 |
| R3 | 갈래는 **first-parent 사슬을 끝까지 걸어가며** 한 덩어리로 잡는다. 머리 행 순서로 처리하므로 **트렁크가 뿌리까지 자기 색을 유지**한다. 색은 재사용되는 슬롯 번호이고 갈래가 사는 동안 고정이며, 앞 갈래가 **끝난 뒤에야** 다시 쓴다 | `determinePath` 의 normal 분기 루프 (`vertex=parentVertex; parentVertex=vertex.getNextParent()`) · `getAvailableColour(startAt)` · `availableColours[branch.getColour()]=i` |
| R4 | 머지가 **이미 배치된 부모**로 갈 때는 새 갈래·새 색을 만들지 않고, 그 사이 행마다 자기 열을 집고 내려가 부모 점에 붙는다 | `determinePath` 의 merge 분기 — `getPointConnectingTo` / `parentBranch.addLine(…)` |

**따라서 "선은 분기·머지가 아니면 혼자 휠 수 없다" 는 Git Graph 의 동작이 아니다.**
Git Graph 에서 통과선은 자기 일이 없는 행에서도 왼쪽으로 휜다 — 열이 비었기
때문이다. 고정되는 것은 커밋 점의 `x` 뿐이다. `git log --graph` 도 같다 (`|/ /`).

이 판은 R1~R4 를 그대로 따른다. 이탈은 하나뿐이고 FR-GIT-235 에 적었다 — 부모가
없는 커밋에서 선을 내리지 않는다.

### 3.1 개정 (Amended)

- **FR-GIT-117 (개정)** 그래프의 **위상**(어느 갈래가 어느 커밋을 잇는지)은 부모
  관계로부터 **단일 전방 패스**로 계산한다 — 뒤를 보지 않는다. **배치**(그 갈래가

  - 배치를 나누는 것은 압축이 **행 경계의 양쪽 공간**을 모두 알아야 하기 때문이다
    (§2.3). 상한 접기(`clampLanes`, FR-GIT-120)도 이미 같은 자리의 별도 패스다.
  - 각 행에 대해 커밋의 **열**, 통과 세그먼트의 **위·아래 열**, 부모 세그먼트의
    **아래 열**, 새 머리 여부, 그리고 각 세그먼트의 **색 키**를 산출한다. 열은
    **빈 자리 없이 왼쪽부터** 매긴다 (FR-GIT-228).
- **FR-GIT-119 (개정)** 레인 색은 현재 테마의 팔레트에서 파생한다. 색을 하드코딩하지
  않으며, **열이 아니라 갈래에서** 고른다 — 갈래가 열을 옮겨도 색은 그대로다
  (FR-GIT-230).

### 3.2 교차 관심사 — 바깥 계기의 다시 그리기 규약

**증상**(사용자 검토 E1): "changes 에서 행 위에 마우스를 올리고 있으면 버튼이 약
1초에 한 번씩 깜빡인다." **원인과 같은 원인의 다른 자리**: §2.1·§2.2.

- **FR-RPT-1** **바깥 계기로 다시 그리는 목록은, 그릴 내용이 지금 그려진 것과 같으면
  다시 그리지 않는다.** 같은 값을 그려 넣는 일은 화면을 바꾸지 않으면서 요소 상태만
  버린다.
- **FR-RPT-2** 관측 동일성의 판정 근거는 **그 목록의 렌더러가 읽는 값 전부**다.
  판정에 쓰지 않는 값이 화면에 닿으면 갱신이 **조용히 멈춘다** — 근거를 좁히지 않는다.
  - 값이 아닌 것(요소 상태)은 근거가 아니다.
  - 판정은 그린 직후의 값을 요소에 남겨 다음 회차와 비교한다. 요소가 없으면(첫 그리기)
    무조건 그린다.
- **FR-RPT-3** **내용이 실제로 바뀐 회차에도, 바뀌지 않은 항목은 같은 DOM 요소로
  남는다.** 순서가 바뀌면 요소를 **옮긴다** — 지우고 다시 만들지 않는다.
  - 항목의 동일성은 **키**로 판정하고, 다시 만들지 여부는 **그 항목의 보이는 값
    전부**로 판정한다 (FR-RPT-2 와 같은 규칙).
  - 사라진 항목의 요소는 제거한다.
- **FR-RPT-4** FR-RPT-3 은 **요소 상태를 가진 목록**에 적용한다. hover 로만 보이는
  컨트롤, 더블클릭·드래그 제스처, 선택해서 복사하는 본문, `title` 툴팁 중 하나라도
  있으면 대상이다.
- **FR-RPT-5** **자기 계기의 다시 그리기는 대상이 아니다.** 사용자가 만든 변화는
  화면이 바뀌는 것이 맞고, 그 순간 요소 상태가 갱신되는 것도 맞다.
- **FR-RPT-6** 두 규약은 **한 곳에 구현하고 목록이 그것을 쓴다.** 목록마다 가드를
  손으로 쓰면 다음 목록에서 또 빠진다 — 이 저장소가 이미 네 곳에서 네 번 다르게
  막았다 (§2.1).
- **FR-RPT-7** 적용 자리는 §2.2 의 조사 결과 전부다. 공통 수단은
  `web/js/ui/repaint.js` 의 `paintIfChanged`(FR-RPT-1)·`reconcileList`(FR-RPT-3)다.
- **FR-RPT-8** **다시 그리기에 업힌 판정은 관측 경로로 옮긴다.** 그리지 않으면
  판정도 멈추기 때문이다.
  - 그리는 함수는 **값을 화면에 옮기는 일만** 한다. "무엇을 할지" 를 정하는 일은
    관측이 도착하는 자리에서 한다.
  - 판정의 계기가 **값이 아니라 "새 응답이 왔다"** 인 것이 특히 위험하다 — 값이
    같으면 그리지 않으므로 그 판정은 영원히 오지 않는다.
  - 실제로 하나 있었다: 원격 pull 의 충돌 판정(FR-GIT-111)이 `GitRemote.paint` 에
    업혀 있었고, 계기가 `status` **객체가 바뀌었는지**였다. 관측 경로
    (`_applyStatus` → `notifyStatus`)로 옮겼다. `GitConfirm.notify`·`GitDialog.notify`
    는 이미 그 자리에 있었다 — 규약이 먼저 있었고 한 곳이 빠져 있었던 것이다.

#### 3.2.1 이 판이 남기는 자리 — 레이아웃·탭 골격

`Renderer._rLayout` 은 같은 원인을 갖는다 (§2.2 #8). **이 판에서 고치지 않는다.**

- 계기가 **실제 워크스페이스 변경**이다. 폴링이 아니라 무언가가 정말 바뀐 것이며,
  다시 그리는 것 자체가 틀리지 않았다.
- 관측 동일성 판정의 근거가 **레이아웃 트리 전체**(창·분할·탭·활성 탭·포커스·도구
  이름·알람·모바일 모드)다. FR-RPT-2 를 지키지 못하면 **레이아웃이 조용히 얼어붙는다** —
  이 판의 다른 다섯 자리보다 실패의 값이 크다.
- 여기의 다시 그리기는 터미널 재부착을 부르고, 그 비용 때문에 이미 여러 경로가
  `render()` 를 피해 가도록 만들어져 있다 (`_attnRefresh`·`_gitReposRefresh`). 즉
  **핫 경로가 아니다.**

**남기는 것을 조용히 하지 않는다** — `GIT_REMAINING` §6 에 별건으로 적는다.

### 3.3 결함 — 그래프의 선이 왼쪽으로 붙지 않는다

**증상**(사용자 검토 E2): §1.1. **원인**: §2.3.

- **FR-GIT-228** 각 행의 열은 **그 행에서 살아 있는 갈래를 순서를 지켜 0 부터 촘촘히**
  매긴 것이다. **빈 열이 없다.**
  - "살아 있는"은 행에 들어올 때와 나갈 때를 각각 본다 — 행 i 의 위 끝은 행 i-1 이
    나갈 때의 공간으로, 아래 끝과 점은 행 i 가 나갈 때의 공간으로 그린다.
  - 갈래 사이의 **좌우 순서는 뒤집히지 않는다.** 압축은 자리를 당기는 것이며 정렬을
    다시 하는 것이 아니다.
- **FR-GIT-229** 선은 **행 경계에서 끊기지 않는다.** 행 i 의 아래 끝 열 집합은 행 i+1
  의 위 끝 열 집합과 **같다**.
  - 열이 옮겨지는 세그먼트는 그 행 안에서 이어 그린다 (FR-GIT-118 — 행이 자기 SVG 로
    완결된다).
- **FR-GIT-230** 색은 **갈래에 붙는다.** 한 갈래는 살아 있는 동안 같은 색을 유지하며,
  열을 옮겨도 바뀌지 않는다. 팔레트는 테마에서 파생한다 (FR-GIT-119).
- **FR-GIT-234** 열은 **갈래를 머리 행 순서로 처리하며** 행마다 "아직 안 쓰인 가장
  왼쪽 열"을 집는 것으로 정한다 (§2.3.1 R1). 그 결과 오래된 갈래가 늘 왼쪽이다.
  - 한 갈래의 열은 **왼쪽으로만** 움직인다 — 오른쪽으로 밀리는 일이 일어날 수 없다.
    새 갈래는 늘 나중에 처리되므로 이미 자리를 잡은 갈래의 열을 건드리지 못한다.
  - 왼쪽으로 몇 칸을 가는지는 제한하지 않는다. 한 행에서 여러 갈래가 함께 끝날 수
    있고, 그러면 오른쪽 선이 그만큼 당겨진다 (`git log --graph` 의 `|/ /`).
  - 새 갈래(새 머리, 머지의 두 번째 부모)는 그 행의 **가장 오른쪽** 열을 받는다.
  - **행 순서로 레인을 배정하면 안 된다**: 그러면 나중 행의 갈래가 트렁크의 뿌리를
    먼저 물어 가고, 트렁크가 **중간에서 색을 갈아입는다.** 갈래는 first-parent
    사슬을 끝까지 걸어가며 잡아야 한다 (R3). V128·V130 이 그것을 고정한다.

- **FR-GIT-235** 갈래는 **first-parent 사슬을 끝까지** 잡는다 (§2.3.1 R3).
  - 머리에서 시작해 첫 부모를 따라 내려가며, 이미 다른 갈래에 든 커밋을 만나면 멈춘다.
  - 그래서 트렁크는 **뿌리까지 자기 색을 유지한다.** 뒤에서 시작한 갈래의 선이 그
    사슬로 **붙는다** — 사슬을 빼앗지 않는다.
  - 이미 배치된 커밋으로 가는 선은 그 사이 행마다 자기 열을 집고 내려가 부모 행에서
    붙는다 (R4). 한 행에서 곧바로 대각선으로 뛰지 않는다.
  - **부모가 없는 커밋에서는 선을 내리지 않는다.** Git Graph 는 이 경우에도 목록
    끝까지 걸어가며 선을 그리지만(`parentVertex` 가 null 인데 루프가 그대로 돈다),
    뿌리 커밋은 보통 마지막 행이라 그 코드가 도는 일이 없어 드러나지 않는 것이다.
    `--all` 에서 뿌리가 중간에 오면 **아무 데도 닿지 않는 선이 아래로 늘어진다** —
    그것은 따르지 않는다 (이 판의 유일한 의도적 이탈).

- **FR-GIT-231** 상한 접기(FR-GIT-120)는 **압축된 열에** 적용한다. 접힌 뒤에도
  세그먼트 목록은 중복이 없고 오름차순이며, 접힘이 실제로 일어난 행에만 표식을
  세운다. 원본 배치를 제자리에서 고치지 않는다 (기존 규약 유지).
  - 압축이 열을 줄이므로 접힘이 일어나는 행은 **줄어들거나 같다.** 늘어나면 압축이
    틀린 것이다.

### 3.4 결함 — 커밋 행의 브랜치 배지에 기본 동작이 없다

**증상**(사용자 검토 E3): "히스토리에서 브랜치 더블클릭 체크아웃이 구현되지 않았다."

**진단 — 스펙에 없던 것이다.** FR-GIT-222 는 **Branches 탭과 History refs 사이드바**
둘만 덮으며, 둘 다 구현돼 있고 e2e 로 확인된다 (B12·B13·H12 통과, 2026-08-27 실행).
남은 자리는 **커밋 행의 ref 배지**다 — 여기에는 리스너가 하나도 없고, 우클릭도
커밋 메뉴가 받는다.

- **FR-GIT-232** 커밋 행의 **ref 배지는 그 ref 를 대상으로 하는 자리**다.
  - **더블클릭**은 그 ref 의 기본 동작이다 — `GitMenu` 의 primary 후보를 그대로 쓴다
    (FR-GIT-222 와 **같은 경로**). 로컬 브랜치는 Checkout, 원격 브랜치는 추적
    브랜치를 만드는 Checkout 이다.
  - **우클릭**은 그 ref 의 메뉴를 연다 — 브랜치 배지는 branch 메뉴, 태그 배지는 tag
    메뉴다. 커밋 메뉴가 아니다.
  - **현재 브랜치와 태그의 더블클릭은 아무 일도 하지 않는다** — 후보가 없거나 전부
    비활성이면 그만둔다 (FR-GIT-222 의 규약. 태그 체크아웃은 detached 가 되므로
    가벼운 제스처에 싣지 않는다).
  - **배지의 클릭은 행으로 올라가지 않는다.** 올라가면 첫 클릭이 상세를 접거나 펴서
    행 창이 다시 만들어지고(`_ver` → `_paintRows`), 두 번째 클릭이 새 요소에 떨어져
    `dblclick` 이 만들어지지 않는다 — §2.1 의 셋째 줄과 같은 함정이다. 따라서 배지의
    단일 클릭은 **아무 일도 하지 않는다.**
  - 커밋 행의 더블클릭은 배지 밖에서도 상세를 여닫지 않는다 — 두 번째 클릭을 무시한다
    (refs 사이드바가 이미 쓰는 규약).
  - 종류를 모르는 배지(`kind` 가 빈 값, `shortRefName` 이 네임스페이스를 모를 때)는
    **대상이 아니다** — 아무 리스너도 붙이지 않는다. 뜻을 모르는 ref 로 저장소를
    바꾸지 않는다.

### 3.4.1 결함 — 체크아웃 뒤 커밋 목록의 HEAD 표식이 낡는다 (E4)

**어떻게 찾았나**: FR-GIT-232 를 구현하고 검증하다 드러났다. 배지를 더블클릭하면
체크아웃은 실제로 되는데(`headName()` 이 바뀐다) **그 배지의 HEAD 표식이 움직이지
않는다.** refs 사이드바는 갱신된다.

**원인**: `afterRefWrite` 는 refs 사이드바만 다시 받고(`reloadRefs` → `_loadRefs`)
**커밋 목록은 다시 받지 않는다.** 커밋 행의 `head` 표식과 배지의 `head` 표식은 둘 다
`git log` 의 decoration(`c.isHead`·`r.isHead`)에서 오므로, 목록을 다시 받기 전까지
낡은 값이 남는다.

**E1·E3 와 원인이 다르다** — 요소를 버려서가 아니라 **값을 다시 받지 않아서**다.
접수된 3건에 들어 있지 않지만, FR-GIT-232 가 배지를 동작 자리로 만들면서 "눌렀는데
표시가 그대로"가 되므로 함께 고친다.

- **FR-GIT-233** 커밋 목록의 HEAD 표식은 **살아 있는 관측에서 파생한다.**
  - 커밋 행의 표식은 그 커밋이 `status.oid` 와 같을 때 선다.
  - ref 배지의 표식은 그것이 로컬 브랜치이고 이름이 `status.branch` 와 같을 때 선다.
    detached 에서는 어느 배지에도 서지 않는다 (FR-GIT-144 의 상태와 맞는다).
  - 관측이 아직 없으면 `git log` 의 decoration 을 그대로 쓴다 — 첫 그리기가 표식 없이
    보이지 않게 한다.
  - **대안을 택하지 않은 이유**: `afterRefWrite` 에서 커밋 목록을 다시 받는 방법도
    있으나, 300개를 다시 받으면서 **스크롤과 펼친 상세가 목록 맨 위로 돌아간다** —
    체크아웃은 목록을 처음부터 다시 읽는 일이 아니다. 파생은 요청을 늘리지 않고
    표식만 정확해진다.

### 3.5 Changes 목록의 적용 (FR-RPT 의 Git 적용)

- **FR-GIT-227** Changes 목록은 FR-RPT-1·3 을 따른다.
  - 관측 동일성의 근거는 **`/api/git/status` 응답 중 화면에 닿는 값 전부**다. 관측이
    같으면 Changes 를 다시 그리지 않는다. 폴링이 아닌 계기(선택·접기·미리보기 도착)는
    FR-RPT-5 로 대상이 아니다.
  - 행의 "보이는 값"은 상태 문자·경로 표시·선택·포커스·부분 스테이지·충돌·들여쓰기다.
    하나라도 다르면 다시 만든다.
  - 보호되는 것은 hover 뿐이 아니다 — **FR-GIT-52 의 파일 행 더블클릭**도 같은 보호를
    받는다.

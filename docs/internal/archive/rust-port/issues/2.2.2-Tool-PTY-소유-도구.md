## 목표

PTY 하나를 소유하는 도구 한 개의 수명을 옮긴다. StartTool·readPTY(출력 → outbuf, 모드·주의·cwd 관측), 주의·활동 상태 기계, Freeze/Thaw, 종료·크기 변경·쓰기, cwd, 기록. 블로킹 PTY 읽기는 전용 스레드나 spawn_blocking 에서 돈다 (FR-RSP-33·36).

  - Go 와 다르게 한 내부 결정:
    ① 환경 의존 함수는 조회 함수(`Getenv`)를 인자로 받는다. edition 2024 에서 `set_var` 가 unsafe 라 검사가 프로세스 환경을 바꾸지 않게 하려는 것이다.
    ② readPTY 는 `catch_unwind` 를 두른 전용 std 스레드다. 종료 알림(on_exit)은 Go 의 `go` 처럼 새 스레드에서 부른다.
    ③ `kill` 의 wait 는 보조 스레드 + `recv_timeout(50ms)` 이다.
    ④ 검사의 시계·바쁨 판정은 전역을 쓰지 않고 `maybe_idle_with`·직접 시각 설정으로 잰다(병렬 검사 경쟁 방지). 전역 갈아 끼우기 API 는 다른 crate 검사용으로 남겼다.
    ⑤ Go `Tool.PID` 필드(쓰이지 않음)는 옮기지 않았다.
    ⑥ `user.Current().Username`: unix 는 nix `User::from_uid`(cgo 와 같음), 실패하면 `$USER`. Windows 는 `%USERDOMAIN%\%USERNAME%` 로 근사한다(Go 는 토큰 조회). Windows 의 도구 셸 `USER`·`LOGNAME` 이 다를 수 있다.
    ⑦ detached 도구도 `kill` 하면 `done` 이 취소된다(Go 는 nil 채널이라 영원히 막힌다). pid 없는 도구에는 `terminate_wait` 가 곧바로 돌아오므로 관측 차이는 없다.
  - 남은 위험: `wait` 오류 로그의 신호 이름은 SIGHUP·INT·KILL·TERM 만 Go 문구와 같고, 나머지는 `signal N` 이다. 2.2.3 의 ToolManager(Create·Delete·FreezeAll·handover·SnapshotToolSince)는 이 API 위에 선다.

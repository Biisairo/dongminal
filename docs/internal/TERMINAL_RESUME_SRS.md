# SRS: 재접속은 이어 붙이는 것이지 다시 뿌리는 것이 아니다 — IEEE 29148

> **문서 상태**: 승인·구현완료

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 하나다.

> **"랜더가 자꾸 깨진다. 터미널에 이전 글자가 보이고 글자가 중복으로 출력된다.
> 이전에 랜더 내용이 그대로 남아있는게 제일 문제다."**

원인은 조사로 **확정됐다**(§2). 하나가 아니라 셋이고, 셋 다 같은 자리에서
나온다 — **WS 가 붙을 때마다 서버가 스크롤백 전량을 되뿌리는데, 받는 쪽
터미널은 그 내용을 이미 화면에 가지고 있다.**

본 SRS 는 그 되뿌리기를 **이어 붙이기**로 바꾼다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 오프셋 재개 | 클라이언트가 마지막으로 본 바이트 오프셋을 들고 붙는다. 서버는 **그 뒤만** 보낸다 |
| **B** 전량 재생의 멱등화 | 재개할 수 없을 때(창 밖·최초 접속)만 전량을 뿌리되, **앞서 화면과 스크롤백을 지운다** |
| **C** 잘린 앞머리 정렬 | 바이트 tail 은 시퀀스 한가운데서 잘린다. 전량 재생의 앞머리를 안전한 경계로 민다 |
| **D** 겹침 제거 | 스냅샷과 라이브 스트림이 겹치는 구간을 오프셋으로 잘라낸다 |
| **E** 재그리기 넛지 | 전량 재생 뒤에만, 소유 창이 PTY 에 `SIGWINCH` 를 일으켜 TUI 가 스스로 전체를 다시 그리게 한다 |

**미포함:** §6 비목표. 특히 **서버측 터미널 에뮬레이션(headless VT)** 은 범위
밖이다 — 그것이 근본해이지만 규모가 M6 을 통째로 넘는다 (§4 D-5).

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **오프셋** | 도구가 켜진 뒤 PTY 가 낸 누적 바이트 수. `outbuf.Stream.totalIn` 이 그 값이다 |
| **보유 창** | 스트림이 지금 돌려줄 수 있는 오프셋 구간 `[end-retained, end)` |
| **델타 재개** | 요청 오프셋이 보유 창 안이라서, 그 뒤의 바이트만 보내는 것 |
| **전량 재생** | 재개할 수 없어 보유분 전체를 보내는 것. **클리어가 반드시 앞선다** |
| **넛지** | PTY 크기를 한 행 줄였다 되돌려 TUI 에 `SIGWINCH` 를 일으키는 것 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 되뿌리기는 연결마다 일어난다

`~/.dongminal/server.log` (2026-09-12 실측):

```
07:10:41.823 ws connected  tool=01a090f6-…
07:10:41.857 [ws-daemon] snapshot tool=01a090f6-… len=1048576 retained=1048576
```

WS 연결 **916 회**, 그중 스냅샷 송신 **898 회**. 끊김의 형태는
`readWS error … connection reset by peer` 가 **6 개 도구에 동시에** 찍히는
것이다 — 브라우저 탭 하나가 끊기면 그 창의 모든 도구가 한꺼번에 재접속한다.

`01a090f6` 은 claude 를 띄운 도구이고, 스냅샷이 **매번 1 MiB 전량**이다
(`toolhub/conn.go:31` `bufMax = 1<<20`). 버퍼가 늘 꽉 차 있다는 뜻이다.

### 2.2 기전 M1 — 지우지 않은 터미널에 겹쳐 쓴다 (주범)

- 서버: `httpapi/handlers_ws.go:115`(direct)·`:177`(daemon) 이 **연결마다**
  스크롤백 전량을 `OpOutput` 으로 보낸다.
- 클라: `web/js/ui/term-pane.js` 는 xterm 인스턴스를 재접속 너머로 **재사용**한다
  (`open()` 은 `_opened` 로 1 회, `reconnectNow()` 는 "pane 을 다시 만들지
  않는다" 를 명시한 계약 — SOFT_RELOAD_SRS D-3). 그런데 `term.reset()`·`clear()`
  를 **부르는 자리가 한 곳도 없다.**

> 그래서 화면에 이미 있는 내용 **위에** 같은 1 MiB 가 한 번 더 그려진다.
> 접수한 말 "이전 글자가 보이고 글자가 중복으로 출력된다" 가 이것이다.

`architecture.md` 의 그 절(당시 제목 §터미널 스냅샷 재생)은 이 재생을 "브라우저가
붙거나 **새로고침**하면" 으로 적었다 — **빈** xterm 이 전제다. 드롭-재접속은 그
전제 밖인데 같은 경로를 탄다.

### 2.3 기전 M2 — 스냅샷이 시퀀스 한가운데서 잘린다

`outbuf/stream.go:60` 의 `Snapshot` 은 `buf[len-max:]` 를 그대로 준다. 시퀀스
경계도 UTF-8 경계도 보지 않는다. **보유량이 상한을 채운 도구는 항상 반쪽 CSI
로 시작한다** — §2.1 의 `retained=1048576` 이 바로 그 상태다. 재생 앞머리에서
파서가 어긋나면 그 뒤 몇 바이트가 글자가 아니라 제어로 먹힌다.

### 2.4 기전 M3 — 터미널 모드가 보유 창 밖이면 복원되지 않는다

daemon 모드는 `termReset` 을 스냅샷 **앞에** 보내 alt screen(`?1049l`)·마우스
보고를 끈다. 그런데 실제 PTY 가 alt screen 안이고 그것을 켠 `?1049h` 가 보유
창 밖으로 밀려났으면, 클라이언트는 main screen 인 채로 라이브 델타를 받는다 —
**영구 desync** 다.

direct 모드는 순서가 **반대**다 — 스냅샷을 먼저 보내고, `tool.Restored` 일
때만 `termReset` 을 뒤에 보낸다. 두 모드가 같은 입력에 다르게 반응한다.

### 2.5 기전 M4 — 구독과 스냅샷이 겹친다

`handlers_ws.go:171` 의 주석이 사실을 이미 적고 있다.

> *"The small overlap between the snapshot and the buffered live stream may
> duplicate a few bytes, which xterm.js redraws harmlessly"*

**harmless 가 아니다.** 실측 RPC 왕복은 `07:01:49.890584 → .928077` = **38 ms**
이고, 그동안 TUI 가 낸 델타가 스냅샷과 함께 두 번 들어간다.

### 2.6 증상의 크기는 무엇이 흐르는가에 달렸다

평범한 셸로는 **재현되지 않는다.** 실측(2026-09-12): 셸 하나에 평문 열 줄을 낸 뒤
소켓을 끊었다 붙였더니 **892 바이트가 다시 왔는데 화면은 한 글자도 달라지지
않았다** — 되뿌린 것에 섞인 커서 이동이 같은 자리를 덮었기 때문이다.

그래서 검증은 화면이 아니라 **수신량**을 잰다 (V-TRS-16). 다시 받지 않으면 겹쳐
그릴 수도 없고, 그 성질은 흐르는 것이 무엇이든 결정적이다. 같은 실측에서 세 번
끊었다 붙이면 **2,676 바이트**가 다시 왔다.

### 2.7 왜 스스로 낫지 않는가

claude 같은 TUI 는 **델타만** 보낸다. 자기 화면 상자를 상대 커서 이동으로
고쳐 그릴 뿐, 전체를 다시 그리지 않는다. 그래서 **한 번 어긋난 화면은 복구되지
않는다** — 사용자가 무엇을 해도 그대로 남는다. 접수한 말의 "제일 문제" 가
이 성질이다.

### 2.8 고칠 수 있다는 근거

`readPTY`(`toolhub/tool.go:372-374`)는 **같은 raw 바이트를** 같은 순서로
`stream.Feed` 와 구독자 push 에 넘긴다. 즉 **스트림의 바이트 오프셋이 라이브
스트림의 오프셋과 같은 좌표계다.** 그리고 `ToolSnapshot` 은 이미
`TotalBytesIn` 을 IPC 로 나르고 있다(`toolclient/client.go:716`). 재개에
필요한 좌표가 **이미 있다.**

## 3. 요구사항 (Requirements)

### 3.1 묶음 A — 오프셋 재개

**FR-TRS-1.** `outbuf.Stream` 은 절대 오프셋을 공개한다.

- `Feed(p) (dropped int, end int64)` — `end` 는 이 청크를 포함한 누적 입력 바이트.
- `Offset() int64` — 현재 누적 입력 바이트.
- `Since(off int64) (data []byte, end int64, ok bool)`.

**FR-TRS-2.** `Since` 의 판정은 보유 창 하나로 한다. 보유 창은 `Snapshot` 이
돌려주는 구간과 **같다** — 두 창을 두면 "스냅샷에는 있는데 재개는 안 되는"
구간이 생긴다.

| 조건 | 결과 |
|---|---|
| `off == end` | `data` 빈 슬라이스, `ok=true` (완전 동기) |
| `end-retained <= off < end` | `data = buf[off:]`, `ok=true` |
| `off < end-retained` | `ok=false` (창 밖) |
| `off > end` | `ok=false` (데몬 재시작 등으로 좌표계가 바뀜) |
| `off < 0` | `ok=false` |

**FR-TRS-3.** 브라우저는 `/ws` 에 `since=<정수>` 를 실어 붙는다. 값이 없거나
정수로 파싱되지 않으면 **전량 재생**이다 — 오류가 아니다.

**FR-TRS-4.** 델타 재개가 성립하면 서버는 델타만 `OpOutput` 으로 보낸다.
**클리어를 보내지 않는다.** 화면은 이미 맞아 있고, 지우면 그 순간 사용자가
보던 것이 사라진다.

**FR-TRS-5.** 델타에도 `stripOSC777`·`stripSnapshotQueries` 를 적용한다.
델타 역시 **기록**이지 라이브가 아니다 — 그 구간의 질의에 지금 답하면
`architecture.md` 가 적은 `56;9R` 폭주가 그대로 돌아온다.

**FR-TRS-6.** 서버는 전송 직후 새 op `OpSeq`(`0x04`)로 좌표를 통보한다.
페이로드는 **9 바이트**다.

```
[0..7]  int64 big-endian  — 이 시점까지 클라이언트가 본 오프셋
[8]     uint8             — 0=델타 재개, 1=전량 재생
```

**FR-TRS-7.** 브라우저는 `OpSeq` 의 값을 자기 오프셋으로 세우고, 그 **뒤에**
오는 `OpOutput` 페이로드의 **바이트 길이**를 더해 유지한다. 다음 연결의
`since` 가 그 값이다.

> 이 계산이 성립하려면 `OpSeq` 뒤의 `OpOutput` 이 PTY raw 와 1:1 이어야 한다.
> 그래서 FR-TRS-8 이 순서를 못박는다.

**FR-TRS-8.** `termReset`·전량 재생·델타는 **모두 `OpSeq` 앞에** 보낸다.
`OpSeq` 뒤의 `OpOutput` 은 라이브 PTY 바이트뿐이다. `OpError` 는 다른 op 이므로
계산에 들어가지 않는다.

**FR-TRS-9.** `OpSeq` 를 모르는 클라이언트(배포가 닿지 않은 옛 탭)는 그것을
조용히 버린다. `_onOp` 의 분기는 if/else 사슬이고 모르는 op 는 이미 버려진다 —
**바꾸지 않는다**는 것이 요구다.

### 3.2 묶음 B — 전량 재생의 멱등화

**FR-TRS-10.** 전량 재생은 반드시 이 순서다.

```
① termReset                                   (모드 초기화)
② ESC[?1049l  ESC[H  ESC[2J  ESC[3J           (대체화면 이탈·홈·화면·스크롤백)
③ 경계 정렬한 스냅샷                            (FR-TRS-13)
④ OpSeq(offset, full=1)
```

**FR-TRS-11.** ②가 요점이다. **무엇이 그려져 있었든 결과가 같아야 한다** —
그것이 "멱등" 의 뜻이고, M1 이 없어지는 자리다.

**FR-TRS-12.** direct 모드와 daemon 모드는 **같은 바이트를 같은 순서로** 보낸다.
지금처럼 갈리면 어느 쪽이 맞는지 물을 수 없다 (§2.4). `tool.Restored` 분기는
`termReset` 을 **조건부로** 만들던 자리였고, ①이 항상 나가므로 사라진다.

### 3.3 묶음 C — 앞머리 정렬

**FR-TRS-13.** 전량 재생의 스냅샷은 앞머리를 **첫 `\n`(0x0A) 다음 바이트**까지
민다. 상한 `TRS_ALIGN_SCAN`(4 KiB) 안에 `\n` 이 없으면 밀지 않는다.

> 근거: `0x0A` 는 UTF-8 연속 바이트(`0x80..0xBF`)로 나타날 수 없고, CSI 의
> 파라미터·중간·최종 바이트 범위에도 없다. 따라서 `\n` 바로 뒤는 **문자
> 경계이자 시퀀스 경계임이 보장된다.** OSC 문자열 페이로드 안에는 나타날 수
> 있으나, 그 경우는 상한 안에서 다음 `\n` 을 만나 자연히 해소된다.

**FR-TRS-14.** 델타에는 정렬을 적용하지 **않는다.** 델타의 시작은 이전 연결이
정확히 끊은 자리이므로 이미 경계다. 밀면 바이트를 잃는다.

### 3.4 묶음 D — 겹침 제거

**FR-TRS-15.** 데몬의 출력 push 이벤트는 그 청크의 끝 오프셋을 함께 나른다
(JSON `end`). 필드가 없는 옛 데몬의 이벤트는 `end=0` 으로 읽히며, 그때는
겹침 제거를 **하지 않는다** — 지금 동작과 같아질 뿐 나빠지지 않는다.

**FR-TRS-16.** 웹서버는 `OpSeq` 로 통보한 오프셋 `O` 보다 **완전히 앞선** 라이브
청크(`end <= O`)를 버리고, **걸친** 청크(`end-len(data) < O < end`)는 앞부분을
잘라 `data[O-(end-len(data)):]` 만 보낸다.

**FR-TRS-17.** direct 모드는 `AddClient` 가 등록 시점의 오프셋을 돌려주고,
`readPTY` 는 `Feed` 와 클라이언트 목록 확보를 **한 번의 `cmu` 구간**에서 한다.
그래야 "등록 오프셋 이전은 재생이, 이후는 broadcast 가" 로 빈틈 없이 갈린다.

> 락 순서는 항상 `cmu → stream.mu` 다. 역순으로 잡는 자리를 만들지 마라.

### 3.5 묶음 E — 재그리기 넛지

**FR-TRS-18.** 브라우저는 `OpSeq` 의 플래그가 **전량 재생(1)** 일 때만 넛지를
보낸다. 델타 재개에는 보내지 않는다 — 필요 없고 리플로우만 만든다.

**FR-TRS-19.** 넛지는 `_resizeCheck(this.id, this._slot)` 를 통과할 때만 나간다.
크기의 주인이 아닌 창이 PTY 를 흔들면 주인 창의 화면이 깨진다 (FR-WSL-14 의
같은 근거).

**FR-TRS-20.** 넛지는 `OpResize(cols, rows-1)` 를 보내고 한 tick 뒤
`OpResize(cols, rows)` 를 보낸다. `rows <= 1` 이면 보내지 않는다.

**FR-TRS-21.** 넛지는 `TIMERS` 를 거쳐 건다 (`EVENT_TIMER_HUB_SRS`). 원시
`setTimeout` 을 쓰지 않는다.

### 3.6 비기능 (Non-functional)

**NFR-TRS-1.** 델타 재개의 정상 경로는 **바이트 0 중복·0 손실**이어야 한다.
이것이 본 SRS 의 합격선이다.

**NFR-TRS-2.** `Since` 는 `Snapshot` 과 같은 락 아래 상수 시간 슬라이싱이다.
새 고루틴·새 버퍼 복제 경로를 만들지 않는다.

**NFR-TRS-3.** 프로토콜 변경은 **덧붙이기만** 한다. 기존 op 의 의미·형식을
바꾸지 않는다 (FR-TRS-9).

## 4. 결정 (Decisions)

| # | 결정 | 근거 |
|---|---|---|
| **D-1** | 재접속은 **델타 재개**로 한다. 전량 재생은 재개 불가일 때의 강등 경로다 | 중복도 손실도 0 이 되는 유일한 방법이다. 필요한 좌표(`totalIn`)가 **이미 스트림에 있고** IPC 로도 이미 나른다 (§2.8) — 새 저장소를 만들지 않는다 |
| **D-2** | 오프셋은 **서버가 통보**하고 클라이언트가 누적한다. op 를 하나 더한다 | 스냅샷은 필터(`stripOSC777`)를 거쳐 길이가 변하므로 클라이언트가 길이로 좌표를 유도할 수 없다. 반대로 모든 프레임에 8 바이트를 붙이면 옛 탭의 해석이 깨진다 (FR-TRS-9) |
| **D-3** | 전량 재생 앞에 **하드 클리어**를 둔다 | 재생을 멱등으로 만드는 것이 요점이다. 클라이언트에 `term.reset()` 을 시키는 길도 있으나, 그러면 "지금 온 것이 재생인가" 를 클라이언트가 판정해야 하고 판정 자리가 둘이 된다 |
| **D-4** | 넛지는 **전량 재생 뒤에만**, **클라이언트가** 보낸다 | 서버는 그 순간의 진짜 행 수도, 크기의 주인이 누구인지도 모른다. 클라이언트에는 `_resizeCheck` 라는 이미 선 판정이 있다 (FR-TRS-19) |
| **D-5** | 서버측 headless VT 는 하지 않는다 | 그것이 근본해이고(tmux·mosh 의 길), 기전 셋을 모두 없앤다. 그러나 규모가 M6 을 통째로 넘고, D-1 로 관측되는 증상이 사라진다. 필요가 남으면 그때 별도 SRS 로 연다 |
| **D-6** | `Restored` 조건부 `termReset` 을 없앤다 | 두 모드가 다른 바이트를 보내던 자리다 (§2.4). 조건을 없애면 **항상** 초기화되므로 조건이 필요 없다 |

## 6. 비목표 (Non-goals)

- **끊김 자체를 줄이는 것.** 본 SRS 는 끊긴 **뒤**를 고친다
- **서버측 터미널 에뮬레이션** (D-5)
- **스크롤백 상한 조정.** `bufMax` 는 그대로 1 MiB 다
- **클라이언트 스크롤백의 서버 동기화.** 델타 재개가 성립하면 클라이언트의
  긴 스크롤백은 그대로 살아남는다 — 그것이 D-1 을 고른 이유 중 하나다

## 7. 리스크 (Risks)

| 리스크 | 등급 | 완화 |
|---|---|---|
| 오프셋 좌표계가 어긋나 델타가 엉뚱한 자리부터 온다 | **HIGH** | 좌표의 원천을 `outbuf.Stream` **하나**로 둔다 (FR-TRS-1). 라이브·스냅샷이 같은 `readPTY` 루프에서 나온다는 것이 §2.8 의 실측 근거다. V-TRS-2·13·15 가 그 자리를 직접 대조한다 |

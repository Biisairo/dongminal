**남은 결함 — 설계 결정 필요(blocked 사유)**

큰 diff 의 글자 단위 계산이 상한 없이 메인 스레드에서 돈다. vendor 설정으로는 막히지 않는다: `timeout` 은 상한이 되지 못하고(100 ms 를 줘도 7.4초), `scanLimit` 은 평범한 diff 도 파일 전체 한 조각으로 뭉갠다(SPA_PROFILE §2-1-2). 선택지:

- **A(권장)** 줄 단위 diff 를 먼저 하고, 바뀐 조각 중 작은 것만 글자 단위로 다듬는 `diffConfig.override` 함수. 줄 diff 는 이미 있는 `edDiffLines`(Myers, 편집 수 상한)를 쓴다. 상한을 넘거나 조각이 크면 그 조각은 통째로 바뀐 것으로 보인다. 평범한 diff 의 화면은 거의 같고, 큰 diff 는 줄 단위 강조가 된다. `gitDiffIgnoreWs` 의 상한 초과 폴백(`CM.diff(a,b)`, 지금도 상한 없음)도 같은 길로 묶는다. 조각 크기 상한과 줄 diff 편집 수 상한(현행 2,000 이면 현실형 3,200줄 변경이 한 조각이 된다) 값을 정해야 한다.
- B 크기 문턱: 파일이 크면 줄 단위만 쓴다. 단순하지만 비용은 크기가 아니라 바뀐 글자 수에 비례해 문턱을 정할 근거가 약하다(50 KB 를 모두 고친 파일도 1.2초).
- C Worker: `MergeView` 는 diff 를 생성자 안에서 동기로 계산하고 미리 계산한 조각을 받지 않는다. vendor 를 바꿔야 해서 권하지 않는다.
- D 서버의 git hunk 를 쓴다: 편집 중인 문서(작업 트리 축)는 매 입력마다 다시 계산해야 해서 서버 왕복이 붙는다. 권하지 않는다.

**동작 변경**

- 이전: vendor 글자 단위 diff 가 두 글 전체를 비교했다. 공백 무시 모드도 줄 비교 상한(2,000)을 넘으면 상한 없는 `CM.diff` 로 돌아갔다.
- 새: 줄 단위로 먼저 비교하고, 바뀐 덩어리 중 작은 것만 글자 단위로 다듬는다. 줄 비교가 상한을 넘으면 공통 앞뒤 줄을 뺀 구간 하나가 바뀐 것으로 보인다. 예산을 넘는 덩어리는 줄째 강조된다. 공백 무시 모드의 줄 비교 상한도 4,000 이 됐다.
- 이유: 글자 단위 diff 는 바뀐 글자 수에 비례해 느려지고 상한이 없다. 2만 줄을 모두 고친 파일에서 60초 넘게 멎었다.

**상한 값의 근거 (측정, Node 24·같은 기계, 2만 3천 줄 파일)**

- 줄 비교 편집 수 `GIT_DIFF_LINE_MAX_EDITS=4000`: `edDdMyers` 의 비용·메모리(trace 가 편집 수의 제곱으로 는다) — 편집 1,000: 9 ms·7 MB / 2,000: 34 ms·16 MB / 3,200: 85 ms·47 MB / 5,000: 171 ms·103 MB / 8,000: 404 ms·258 MB. 현실형 변경(3,100줄 추가·100줄 수정, 편집 3,200)은 2,000 에서는 포기(→ 한 덩어리), 4,000 에서는 28 ms·28 MB 로 풀린다. 최악(4,000 꽉 참)은 120 ms·64 MB 안팎이다.
- 글자 단위 예산 `GIT_DIFF_REFINE_BUDGET=32,000,000`(덩어리 길이 = 두 쪽 글자 수 합, 그 제곱의 누적): vendor `CM.diff` 를 덩어리 하나에 돌린 비용 — 비슷한 글 2.3천자 4 ms / 5.8천자 4 ms / 1.2만자 13 ms, 서로 무관한 글(최악) 2.3천자 21 ms / 5.8천자 105 ms / 1.2만자 411 ms / 2.4만자 1,081 ms. 최악 비용이 길이 제곱에 비례(약 3e-6 ms/자²)하므로, 제곱 누적 3,200만이면 최악 100 ms 안팎이다. 덩어리 하나로는 약 5,600자(두 쪽 합, 40줄 안팎씩)까지 다듬는다. 흩어진 한 줄 수정 340곳(제곱 누적 약 570만)은 모두 다듬어진다.

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 한 줄이다.

> **"샌드박스 열 때 mount, 프로파일 설정창이 안 떠."**

그리고 인터뷰에서 하나가 더 확정됐다.

> **"scratch 는 mount 가 아니라 copy 인 걸로 하자."**

앞은 결함이고 뒤는 설계 변경이다. 둘은 같은 자리에서 만난다 — 선택창이 떠야
작업 폴더를 고를 수 있고, 고른 폴더가 `scratch` 에서 무엇이 되는지가 뒤의 결정이다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **P** 선택창 | 언제 뜨는가. 무엇을 담는가. 프로파일이 없을 때 |
| **C** 복사 | `scratch` 의 작업 폴더가 컨테이너에 들어가는 방식과 그 상한 |
| **G** 등급·표시 | 복사한 창이 여전히 격리 경계인가. 화면에 무엇으로 보이는가 |
| **S** 서버 표면 | 프로파일 목록 응답에 실리는 값 |

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|---|---|
| **선택창 (pick dialog)** | 샌드박스 창을 열 때 프로파일과 작업 폴더를 고르는 대화상자 (`_pickSandbox`) |
| **작업 폴더 (work dir)** | 사용자가 고른 호스트 경로. 컨테이너 안 `/work` 에 대응한다 |
| **마운트 (mount)** | 호스트 경로를 컨테이너에 **잇는다.** 컨테이너 안 변경이 호스트에 그대로 남는다 |
| **복사 (copy)** | 호스트 경로의 내용을 컨테이너 안으로 **넣는다.** 컨테이너 안 변경은 호스트로 돌아오지 않는다 |
| **작업 방식 (work kind)** | 프로파일이 작업 폴더를 다루는 방식 — `mount` · `copy` · `none` |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 선택창이 뜨지 않는 조건이 실제로 성립해 있다

```js
web/js/core/main.js:49
  const mustAsk = list.length>1 || list.some(p=>p.workspace);
```

실측 — 이 기기의 응답이다.

```
$ curl -s localhost:58146/api/sandbox/profiles
[{"name":"scratch","image":"debian:stable-slim","isolated":true,"helper":false,"workspace":false}]
```

`~/.dongminal/sandbox.json` 이 없으면 `LoadProfiles` 가 `scratch` 하나만 낸다
(`profiles.go:44-46`, FR-SBX-4). 그 하나는 `Workspace=false` 다 (`sandbox.go:71-73`).
**따라서 `mustAsk` 는 거짓이고 선택창은 뜨지 않는다** — `▣ Box` 를 누르면 아무것도
묻지 않고 창이 열린다.

이것은 스펙대로의 동작이지만(`고를 것도 물을 것도 없으면 그대로 연다`),
**사용자에게는 "설정창이 안 뜬다" 로 보인다.** 그리고 그 판단은 옳다 — 작업 폴더를
고를 길이 화면 어디에도 없고, 프로파일을 늘리는 길(`sandbox.json`)도 화면에서
보이지 않는다.

### 2.2 `scratch` 는 작업 폴더를 받지 않는다

| 프로파일 | Workspace | Network | Helper | BaseMounts |
|---|---|---|---|---|
| `scratch` | **false** | `none` | 없음 | 없음 |
| `dev` | true | `bridge` | 있음 | 설정 파일의 것 |

`create` 는 `p.Workspace && rs.HostDir != ""` 일 때만 `-v <host>:/work` 를 붙인다
(`sandbox.go:164-166`). `scratch` 는 그 조건에 닿지 못한다.

FR-SBX-40 이 그렇게 정한 근거는 **격리**다 — 마운트는 컨테이너 안 코드에 호스트
파일을 내주고, 그러면 `scratch` 가 더 이상 경계가 아니다 (FR-SBX-39b 가 같은
이유로 `"scratch": true` 항목을 등급에서 뺀다).

> **복사는 그 근거에 걸리지 않는다.** 컨테이너 안에서 무슨 일이 나도 호스트
> 파일은 그대로다. 그래서 `scratch` 에 작업 폴더를 줄 수 있는 유일한 방식이다.

### 2.3 컨테이너는 `docker run -d` 하나로 만들어진다

`create` 가 `run -d --init --name …` 을 부르고(`sandbox.go:155`), 도구는 나중에
`docker exec -it …`(`:225`)로 붙는다. **생성과 도구 기동 사이에 자리가 있다** —
복사가 들어갈 곳이 거기다.

컨테이너는 `--rm` 없이 만들어지고 제거는 Window 폐기에서만 일어난다(FR-SBX-7/8).
따라서 **이미 있는 컨테이너에 다시 붙는 경로**(`Ensure` 의 `start`)와 **새로 만드는
경로**(`create`)가 갈려 있다.

### 2.4 작업 폴더의 검사는 이미 있다

```go
internal/shared/sandboxplace/place.go:119-125
  if prof.Workspace && pl.HostDir != "" {
      if err := p.stat(pl.HostDir); err != nil {
          return nil, fmt.Errorf("작업 폴더가 없습니다: %s", pl.HostDir)
      }
  }
  rs := sandbox.RunSpec{HostDir: pl.HostDir}
```

FR-SBX-41(없는 경로면 창을 열지 않는다)의 자리다. **복사의 상한 검사도 여기
붙는다** — 같은 종류의 판정이고, 실패의 뜻도 같다(창을 열지 않는다).

### 2.5 선택창은 이미 필요한 것을 거의 다 갖고 있다

`_pickSandbox`(`app-tool.js:51-120`)에는 작업 폴더 입력·`지금 위치` 버튼·최근 경로
목록·프로파일 버튼(격리 등급 배지 포함)이 이미 있다. 빠진 것은 셋뿐이다.

1. **뜨지 않는다** (§2.1)
2. 입력란이 `list.some(p=>p.workspace)` 로만 나타난다 — 프로파일별 뜻의 차이를
   말하지 않는다
3. 프로파일이 하나뿐일 때 **그것을 늘리는 길**을 안내하지 않는다

## 3. 요구사항 (Requirements)

### 3.1 묶음 P — 선택창

**FR-SPK-1.** `▣ Box` 를 누르면 **언제나** 선택창이 뜬다. 프로파일 수와 작업 방식에
관계없다. `mustAsk` 분기를 없앤다.

**FR-SPK-2.** 프로파일이 하나도 없으면(런타임 부재 등) 종전대로 선택창 대신 사유를
알린다 (FR-SBX-20). 그 경로는 바뀌지 않는다.

**FR-SPK-3.** 선택창은 작업 폴더 입력을 **언제나** 보인다. `scratch` 하나뿐인
환경에서도 보인다 — 그것이 이번 변경의 요지다.

**FR-SPK-4.** 작업 폴더 입력은 **비어 있는 것이 기본**이다. 지금 있는 자리는
`지금 위치` 버튼으로만 넣는다 (FR-SBX-40 의 규약을 유지한다 — 승계는 사용자가 고르지
않은 자리를 컨테이너에 들여보내는 일이다).

**FR-SPK-5.** 프로파일 버튼은 자기 **작업 방식**을 함께 보인다.

| 작업 방식 | 버튼의 표기 | 뜻 |
|---|---|---|
| `copy` | `복사` | 고른 폴더의 내용이 컨테이너로 들어간다. 호스트로 돌아오지 않는다 |
| `mount` | `마운트` | 고른 폴더가 컨테이너에 이어진다. 컨테이너 안 변경이 호스트에 남는다 |
| `none` | 표기 없음 | 이 프로파일은 작업 폴더를 쓰지 않는다 |

**FR-SPK-6.** `none` 인 프로파일을 고르면 입력한 작업 폴더는 **버려진다.** 그
사실을 버튼의 툴팁이 밝힌다.

**FR-SPK-7.** 프로파일이 `scratch` 하나뿐이면 선택창 아래에 안내 한 줄을 둔다 —
**`마운트가 필요하면 설정에서 dev 프로파일을 정의하세요`** 와 설정 화면의 Sandbox
탭으로 가는 버튼. 그 버튼은 선택창을 닫고 설정을 연다.

**근거.** 이 안내가 없으면 `scratch` 만 있는 사용자는 프로파일을 늘리는 길이 있다는
것 자체를 알 수 없다 (§2.1 의 "설정창이 안 뜬다" 의 절반이 이것이다).

**FR-SPK-8.** Esc·바깥 클릭으로 닫으면 창을 열지 않는다 (기존 `cleanup(null)`).

**FR-SPK-9.** 고른 작업 폴더는 종전대로 최근 목록에 기억된다 (`_sbxRemember`).
**비어 있는 값은 기억하지 않는다.**

### 3.2 묶음 C — 복사

**FR-SPK-10. `Profile` 에 작업 방식을 둔다** — `WorkKind` 는 `mount`·`copy`·`none`
셋 중 하나다. 기존 `Workspace bool` 을 대체한다.

| 프로파일 | WorkKind |
|---|---|
| `scratch` | `copy` |
| `dev` | `mount` |

불리언을 남겨 두고 복사 플래그를 따로 더하지 않는 이유는, 두 값이 동시에 참인
상태(마운트이면서 복사)가 **뜻을 갖지 않기 때문**이다. 표현할 수 없는 상태는
타입이 막는 편이 낫다.

**FR-SPK-11.** `copy` 인 프로파일은 컨테이너를 **만들 때 한 번** 작업 폴더의 내용을
`/work` 로 복사한다. 수단은 `docker cp <host>/. <name>:/work` 다.

`.`(끝의 점)이 요점이다 — 그것이 "폴더 자체"가 아니라 "폴더의 내용"을 뜻하며,
그래야 `/work` 아래에 원본 폴더 이름의 한 겹이 더 생기지 않는다.

**FR-SPK-12.** 복사는 **`create` 경로에서만** 일어난다. 이미 있는 컨테이너에 다시
붙는 경로(`Ensure` 의 `start`)에서는 복사하지 않는다.

**근거.** 컨테이너는 창을 닫아도 남고(FR-SBX-7), 사용자는 그 안에서 계속 작업한다.
붙을 때마다 복사하면 **컨테이너 안의 작업을 호스트의 옛 내용이 덮는다.**

**FR-SPK-13.** 컨테이너를 재생성하면 다시 복사된다. 그 결과 컨테이너 안의 변경은
사라진다 — 이는 FR-SBX-22(재생성은 파일시스템을 초기화한다)와 같은 규약이며 새로운
성질이 아니다.

**FR-SPK-14.** 복사 전에 원본을 잰다. **상한을 넘으면 창을 열지 않고 사유를
밝힌다.**

| 상한 | 기본값 | 사유 문구 |
|---|---|---|
| `SandboxCopyMaxBytes` | 2 GiB | `작업 폴더가 너무 큽니다(N GiB > 2 GiB) — 더 좁은 폴더를 고르거나 dev 프로파일로 마운트하세요` |
| `SandboxCopyMaxFiles` | 50,000 | `작업 폴더의 항목이 너무 많습니다(N > 50,000) — …` |

**세다가 멈추지 않는다.** 먼저 전부 세고, 넘으면 아무것도 복사하지 않는다
(FR-EDT-118 과 같은 근거 — 절반만 들어간 트리가 거부보다 나쁘다).

**FR-SPK-15.** 셀 수 없으면(권한 오류 등) 창을 열지 않는다. 사유를 그대로 밝힌다.

**FR-SPK-16.** 제외 규칙을 두지 않는다. `.git`·`node_modules` 도 그대로 복사된다.

**근거.** 무엇이 빠졌는지 사용자가 알 수 없는 복사는 "복사했다" 는 말을 거짓으로
만든다. 큰 폴더는 FR-SPK-14 가 **거부로** 다룬다 — 조용히 줄이지 않는다.

**FR-SPK-17.** 복사가 실패하면 창을 열지 않고, 만들어진 컨테이너를 **되돌린다**
(`docker rm -f`). 반쯤 채워진 컨테이너를 남기면 다음 열기가 FR-SPK-12 에 따라
복사를 건너뛰어 그 상태가 굳는다.

**FR-SPK-18.** `copy` 프로파일도 도구의 시작 디렉터리는 `/work` 다 — `ExecSpec` 의
`-w` 조건을 `WorkKind != none` 으로 넓힌다. 단 **작업 폴더를 고르지 않았으면**
`/work` 를 만들지도, `-w` 를 주지도 않는다.

**FR-SPK-19.** 작업 폴더가 없거나 디렉터리가 아니면 창을 열지 않는다 —
마운트와 복사가 같은 규칙이다 (FR-SBX-41 유지).

### 3.3 묶음 G — 등급과 표시

**FR-SPK-20. 복사는 격리 등급을 낮추지 않는다.** `scratch` 에 작업 폴더를 복사해도
그 창은 여전히 격리 경계다(`isolated:true`).

**근거.** 등급이 답하는 물음은 "컨테이너 안 코드가 호스트를 조작할 수 있는가" 이고
(FR-SBX-23·37), 복사에서 그 답은 아니오다. 마운트와 달리 되돌아오는 통로가 없다.

**FR-SPK-21.** 다만 **되돌아오지 않는다는 사실은 반드시 보인다.** 세 자리에 같은
말이 선다.

| 자리 | 표시 |
|---|---|
| 선택창의 프로파일 버튼 | `복사` 배지 + 툴팁 `고른 폴더의 내용이 컨테이너로 복사됩니다. 컨테이너 안 변경은 호스트로 돌아오지 않습니다.` |
| 선택창의 입력란 도움말 | 고른 프로파일이 `copy` 면 같은 문장을 한 줄로 |
| 사이드바 창 배지 | `▣ scratch · 복사` (기존 `▣ <profile>` 의 확장) |

**FR-SPK-22.** 창 배지의 확장은 `copy` 이면서 **작업 폴더를 실제로 받은** 창에만
붙는다. 폴더 없이 연 창에는 붙지 않는다 — 복사한 것이 없다.

### 3.4 묶음 S — 서버 표면

**FR-SPK-23.** `GET /api/sandbox/profiles` 응답의 `workspace` 를 `work` 로 바꾼다 —
값은 `"mount"`·`"copy"`·`"none"` 이다.

```json
[{"name":"scratch","image":"debian:stable-slim","isolated":true,
  "helper":false,"work":"copy"}]
```

**FR-SPK-24.** 옛 `workspace` 불리언은 남기지 않는다. 소비자는 이 저장소의 프론트
하나뿐이고, 둘을 함께 두면 어느 것이 진실인지 판정하는 자리가 생긴다.

**FR-SPK-25.** 복사 상한은 서버 상수이며 응답에 싣지 않는다. 화면이 미리 막지
않고 서버가 거부한다 — 판정 자리를 둘로 만들지 않는다.

### 3.5 비기능 요구 (NFR)

**NFR-SPK-1.** 상한 이내(2 GiB·50,000 항목)의 폴더 복사가 창 열기를 **60초 이내**로
끝낸다. 로컬 SSD·로컬 런타임 기준이다.

**NFR-SPK-2.** 복사 중에는 그 사실이 화면에 보인다 — 진행 표시 없이 60초가 흐르면
사용자는 고장으로 읽는다.

**NFR-SPK-3.** 상한 검사(세기)는 복사 자체보다 훨씬 빨라야 한다 — `os.Lstat` 만
쓰고 내용을 읽지 않는다.

## 6. 비목표 (Non-goals)

1. **컨테이너 → 호스트 되가져오기.** 복사는 단방향이다. 내보내기 수단을 만들지
   않는다 (D-SPK-4).
2. **증분 동기화.** 복사는 컨테이너 생성 시 1회다. 파일 감시로 이어 붙이지 않는다.
3. **설정 화면에서 dev 프로파일을 만드는 UI.** 선택창은 설정으로 **보내기만** 한다.
   `sandbox.json` 편집 UI 자체는 별건이다.
4. **제외 규칙(ignore) 문법.** FR-SPK-16.
5. **`scratch` 의 네트워크·헬퍼 정책 변경.** 그대로 `none`·없음이다.

## 7. 확정 결정 (Decisions)

| id | 결정 | 근거 |
|---|---|---|
| **D-SPK-1** | 선택창은 **언제나** 뜬다 | 사용자 지시. 작업 폴더를 고를 길이 그것뿐이고, 지금은 그 길이 조건 뒤에 숨어 있다 (§2.1 실측) |
| **D-SPK-2** | `scratch` 의 작업 폴더는 **복사**다 | 사용자 지시. 마운트는 격리 경계를 깨지만(FR-SBX-39b) 복사는 돌아오는 통로가 없어 깨지 않는다 |
| **D-SPK-3** | 수단은 `docker cp <host>/. <name>:/work` | 런타임이 이미 주는 표준 수단이다. 이미지 빌드도, 볼륨도 필요 없고 `create` 와 도구 기동 사이에 그대로 들어간다 (§2.3) |
| **D-SPK-4** | 되가져오기를 만들지 않는다 | 내보낸 결과를 사용자가 손으로 합쳐야 하므로, 있는 편이 오히려 "돌아온다" 는 오해를 만든다. 되가져와야 하는 작업은 `dev`(마운트)의 자리다 |
| **D-SPK-5** | 복사는 **생성 시 1회**, 재접속에는 없다 | 붙을 때마다 복사하면 컨테이너 안의 작업을 호스트의 옛 내용이 덮는다 (FR-SPK-12) |
| **D-SPK-6** | 상한을 넘으면 **거부**한다. 조용히 줄이지 않는다 | 무엇이 빠졌는지 모르는 복사는 "복사했다" 를 거짓으로 만든다 (FR-SPK-16) |
| **D-SPK-7** | 복사는 등급을 낮추지 않는다 | 등급이 답하는 물음은 "호스트를 조작할 수 있는가" 이고 복사에서 답은 아니오다 (FR-SPK-20) |
| **D-SPK-8** | `Workspace bool` 을 `WorkKind` 로 **대체**한다 | 불리언 둘이면 "마운트이면서 복사" 라는 뜻 없는 상태가 표현된다 |
| **D-SPK-9** | 복사 실패는 컨테이너를 되돌린다 | 반쯤 채워진 컨테이너가 남으면 FR-SPK-12 때문에 그 상태가 굳는다 |

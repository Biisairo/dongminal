## 1. 소개

### 1.1 목적

이 문서는 otterminal 의 성능 최적화 요구사항을 정한다. 대상은 브라우저 화면(프론트), 브라우저와 서버의 연결, 서버, 데몬이다. 목표는 기계가 바쁠 때도 입력이 막히지 않고, 오래 켜 두어도 메모리가 늘지 않는 것이다.

### 1.2 범위

- 대상: `web/`(프론트), 브라우저↔서버 연결(터미널 WebSocket·SSE·REST 폴링), `rust/crates/webserver`(서버), `rust/crates/daemon`·`shared/toolhub`(데몬과 도구 출력).
- 비대상: 2.4 비목표.

### 1.3 용어

| 용어 | 뜻 |
|---|---|
| 깬 터미널 | 지금 화면에 보이는 터미널 칸 |
| 잠든 터미널 | 숨은 창·탭에 있어 보이지 않는 터미널 |
| 채널 | 브라우저 탭 하나가 서버와 여는 WebSocket 하나 (FR-CON) |
| 화면 상태 | 데몬이 터미널마다 유지하는 화면 격자, 커서, 모드, 기록 줄 (FR-TRM) |
| 스냅숏 | 화면 상태를 직렬화한 것. 브라우저가 다시 해석하지 않고 바로 그린다 |
| 순번 | 채널로 보내는 변화마다 붙는 단조 증가 번호 |
| 재현 시나리오 | 기준선 문서 §1 의 단계(idle·load·contention·remote·long) |

### 1.4 사용자 결정

| # | 결정 | 날짜 |
|---|---|---|
| D-1 | 재현 상황은 에이전트 동시 출력, 창·탭 다수, 장시간, 원격·모바일, 기계의 다른 부하 전부다 | 2026-11-24 |
| D-2 | 완료 기준은 기존 예산(입력 p95 50/100 ms) + 유휴 시 CPU 거의 0 + 장시간 메모리 증가 없음. 숫자는 기준선으로 정한다(§4) | 2026-11-24 |
| D-3 | 프론트는 기존 부품 체계(`Component`·`View`·`Controller`)를 SPA 런타임으로 키운다. 가상 DOM 은 만들지 않는다. 멀티 페이지(iframe)는 쓰지 않는다 | 2026-11-24 |
| D-4 | DOM 을 쓰지 않는 무거운 계산은 측정에서 드러나면 Web Worker 로 옮긴다 | 2026-11-24 |
| D-5 | 연결은 브라우저 탭당 WebSocket 하나(채널)로 합친다. 구독, 변화량 + 순번, 흐름 제어를 쓴다. REST 는 명령에만 쓴다. 옛 연결과 함께 두며 기능별로 옮기고, 다 옮긴 뒤 옛 연결을 지운다 | 2026-11-24 |
| D-6 | 잠든 터미널은 브라우저 버퍼를 비운다. 데몬이 터미널마다 화면 상태를 유지하고, 깨어나면 스냅숏을 보낸다(tmux·Zellij·Zed RFC 방식). 재생 방식을 거치지 않고 바로 이 방식으로 간다 | 2026-11-24 |
| D-7 | 기록은 데몬이 터미널마다 5만 줄, 브라우저는 깬 터미널마다 5천 줄을 갖는다. 그보다 위는 스크롤할 때 받아 온다. 두 값은 설정으로 바꿀 수 있다 | 2026-11-24 |
| D-8 | 운영 인스턴스(Go 판)는 고려하지 않는다 | 2026-11-24 |
| D-9 | 브라우저의 상태용 주기 GET 을 전부 없앤다(FR-CON-7 의 5개, Claude 계정, git 계열, 텔레그램). 사건 없이 계속 변하는 값(CPU·메모리)은 서버가 구독자가 있을 때만 재서 민다 | 2026-11-24 |
| D-10 | 상태 토픽은 토픽별로 싣는 것을 나눈다. 자주 바뀌는 토픽은 id 단위 변화량, 드물게 바뀌는 토픽(워크스페이스·설정 등)은 바뀔 때 최신 전체 값을 민다 | 2026-11-24 |
| D-11 | 채널은 원격 주소에서 표준 `permessage-deflate` 로 압축한다. 서버의 WebSocket 구현은 이를 지원하는 crate 하나로 통일한다(채널·LSP). 같은 일을 하는 구현을 두 벌 두지 않는다 | 2026-11-24 |
| D-12 | D-11 을 고친다: 로컬·원격을 구분하지 않고 모든 채널 연결을 압축한다. crate 는 sockudo-ws(MIT)이고, 서버 WebSocket(채널·LSP)과 시험·otterctl 클라이언트를 이것 하나로 통일한다. 근거는 `perf/COMPRESSION_2026-11-24.md` §8 | 2026-11-24 |

## 2. 전체 설명

### 2.1 기준선 요약

기준선(`BASELINE_2026-11-24.md`, 에이전트 12개 중 3개 보임)에서 드러난 것:

1. 브라우저 힙이 출력량만큼 계속 는다. 10분에 9.6 → 85 MB. 스크롤백 5만 줄을 잠든 터미널도 모두 갖는다.
2. 잠든 터미널도 출력을 모두 받고 해석한다. 받는 양의 약 75% 가 화면에 나오지 않는다. 약한 기기 흉내(CPU 4배 감속)에서 메인 스레드 50%.
3. 유휴 시 분당 82건 폴링(`ping`·`stats` 3초, `runs`·`tools/activity`·`tools/background` 5초).
4. 부팅 요청 338건, 스크립트 299개 3.8 MB. git·문서 렌더·언어 두 벌을 처음에 모두 싣는다.
5. 서버·데몬 CPU 2~3%, 메모리 일정 — 병목이 아니다.

M4 기계에서는 입력 p95 가 예산 안이었다(§6 재현하지 못한 것). 그래서 이 SRS 는 입력 지연 자체보다 **평소에 하는 일과 쌓는 메모리를 줄이는 것**을 겨눈다. 그것이 기계가 바쁘거나 RAM 이 빠듯할 때 입력이 밀리는 원인이다.

### 2.2 구조 개요

```
브라우저 탭 ── 채널(WebSocket 1개) ── 서버 ── IPC ── 데몬
   │  구독: 깬 터미널 출력, 상태 토픽          │        └ 터미널마다 화면 상태(5만 줄)
   │  받음: 스냅숏 · 변화량(순번) · 이벤트      │
   └─ REST: 명령(창 열기, 설정 저장 …)       └ 채널 다중화, 흐름 제어
```

### 2.3 가정

- A-1 (중요): Rust 터미널 에뮬레이터 crate(`alacritty_terminal` 또는 `vt100` 계열)로 데몬 안에서 xterm.js 와 사용자가 차이를 모를 만큼 같은 화면 상태를 만들 수 있다. M2 착수 시 후보를 비교 시험으로 확인하고, 안 되면 멈추고 알린다.
- A-2: 스냅숏을 xterm.js 가 다시 해석 없이 그릴 수 있는 형식(화면 격자 → 최소 ANSI 재그리기 시퀀스)으로 만들 수 있다. 스냅숏의 크기는 화면 크기 + 요청한 기록 줄 수에 비례한다.
- A-3: 평문 HTTP 에서 브라우저는 HTTP/2 를 쓰지 않는다. 그래서 채널 통합이 동시 연결 6개 제한 문제를 함께 푼다.

### 2.4 비목표

- 가상 DOM 프레임워크, 외부 UI 라이브러리 도입(D-3).
- 화면을 iframe·여러 페이지로 나누기(D-3).
- 운영 전환(D-8).
- 성능 회귀를 CI 게이트로 강제하기(`PERFORMANCE_BUDGET.md` §5 와 같은 이유 — 러너 부하가 값을 흔든다). 측정은 `scripts/perf/scenario.mjs` 로 사람이 돌린다.

## 3. 요구사항

### 3.1 채널 — 연결 통합 (M1)

- **FR-CON-1** 브라우저 탭은 서버와 WebSocket 하나(채널)만 연다. 터미널 출력·입력, 서버 이벤트, 상태 변화가 모두 이 채널로 오간다. 편집기 LSP WebSocket 은 이 SRS 범위 밖으로 둔다.
- **FR-CON-2** 채널 메시지는 종류(토픽)를 갖는다. 터미널 출력은 바이너리 프레임, 나머지는 JSON 프레임이다.
- **FR-CON-3** 브라우저는 토픽을 구독·해지한다. 서버는 구독한 토픽만 보낸다.
- **FR-CON-4** 상태 토픽의 변화는 "다시 받아라" 신호가 아니라 **변화량 또는 최신 전체 값**을 싣는다(D-10). 어느 쪽인지는 토픽마다 정한다(`perf/CHANNEL_PROTOCOL.md` §5.2). 메시지마다 토픽별 순번을 붙인다.
- **FR-CON-5** 브라우저가 순번의 빈틈을 발견하면 그 토픽의 전체 상태를 한 번 다시 받는다. 다시 연결할 때는 토픽마다 마지막 순번을 알리고, 서버는 그 뒤의 변화량 또는 전체 상태를 보낸다.
- **FR-CON-6** 흐름 제어: 서버는 채널별 보낼 양을 잰다. 브라우저가 늦으면 터미널 출력은 화면 상태 스냅숏으로 합쳐 보내고(FR-TRM-6), 상태 토픽은 최신 것만 남긴다. 서버 메모리는 채널마다 상한을 넘지 않는다.
- **FR-CON-7** 생존 확인은 채널의 ping/pong 하나로 한다. `GET /api/ping`·`/api/stats`·`/api/runs`·`/api/tools/activity`·`/api/tools/background` 의 주기 폴링을 없앤다. Claude 계정·git 계열·텔레그램 페어링의 주기 폴링도 없앤다(D-9). 그 정보는 토픽으로 온다.
- **FR-CON-8** REST 는 명령(요청·응답)에만 쓴다. 상태를 알기 위한 주기 GET 은 남기지 않는다. 사건 없이 계속 변하는 값(CPU·메모리)은 서버가 구독자가 있을 때만 재서 토픽으로 민다. 남는 서버 내부 주기는 FR-SRV-2 에 따라 이유와 주기를 적는다.
- **FR-CON-9** 압축(`permessage-deflate`)은 로컬·원격을 구분하지 않고 모든 연결에서 켠다. 서버 WebSocket 은 이를 지원하는 crate 하나(sockudo-ws)로 통일한다(D-11·D-12).
- 프레임·토픽·순번·흐름 제어 상한의 하위 설계는 `docs/internal/perf/CHANNEL_PROTOCOL.md` 다.
- **FR-CON-10** 옮기는 동안 옛 경로(칸별 WebSocket·SSE·폴링)와 채널이 함께 돈다. 기능마다 채널로 옮기고 시험을 통과하면 옛 경로를 지운다. M1 이 끝나면 옛 경로는 없다.

### 3.2 터미널 — 서버 화면 상태와 구독 (M2)

- **FR-TRM-1** 데몬은 터미널마다 화면 상태를 유지한다. PTY 출력은 데몬 안의 에뮬레이터를 먼저 지난다(A-1).
- **FR-TRM-2** 데몬의 기록은 터미널마다 기본 5만 줄이다(D-7). 기록은 셀 격자가 아니라 줄 단위의 압축된 형태로 둔다. 설정으로 바꿀 수 있다.
- **FR-TRM-3** 브라우저는 깬 터미널의 출력만 구독한다. 잠든 터미널은 구독을 해지하고, 그 xterm 버퍼를 비운다(또는 인스턴스를 버린다).
- **FR-TRM-4** 터미널이 깨면 서버가 스냅숏(현재 화면 + 최근 기록 5천 줄, D-7)을 보낸다. 그 뒤로는 순번이 붙은 출력을 이어 보낸다. 스냅숏과 이어지는 출력 사이에 빠지거나 겹치는 바이트가 없다.
- **FR-TRM-5** 브라우저가 가진 기록(5천 줄)보다 위로 스크롤하면, 그 위 구간을 서버에서 받아 온다. 받는 동안에도 입력과 출력은 막히지 않는다.
- **FR-TRM-6** 흐름 제어(FR-CON-6)로 출력이 밀리면, 서버는 밀린 출력을 버리고 다음 프레임에 스냅숏을 보낸다. 화면은 최종 상태와 같다.
- **FR-TRM-7** 같은 터미널을 여러 브라우저 탭·기기가 구독해도 데몬의 화면 상태는 한 벌이다.
- **FR-TRM-8** 지금 동작에 기대는 기능(검색, 복사, 링크, 주의 상태 판정, 화면 읽기 `read-screen`)은 서버 화면 상태 또는 깬 터미널 버퍼로 같은 결과를 낸다. 잠든 터미널의 `read-screen` 은 서버 화면 상태에서 답한다.

### 3.3 프론트 — SPA 런타임 (M3)

- **FR-SPA-1** 화면 등록부: 기능 화면(git 창, 편집기, 설정, 채팅, 문서 렌더, Run 화면 등)은 등록부에 이름과 싣기 함수를 갖는다. 처음 열 때 그 화면의 스크립트·CSS 를 싣는다.
- **FR-SPA-2** 부팅 때 싣는 것은 첫 화면(창·탭·터미널·목록 패널)에 필요한 것뿐이다. 언어 파일은 활성 언어 한 벌만 싣는다.
- **FR-SPA-3** 생명주기: 화면(View)은 `mount`·`wake`·`sleep`·`unmount` 를 갖는다. 보이지 않으면 `sleep` 이고, 잠든 화면은 이벤트 구독·타이머·그리기를 하지 않는다. 깨면 필요한 상태를 다시 받아 그린다.
- **FR-SPA-4** 프레임 스케줄러: DOM 쓰기는 스케줄러에 맡긴다. 한 프레임에 같은 대상의 쓰기는 한 번으로 합친다. 입력 처리와 깬 터미널 그리기가 다른 그리기보다 먼저다. 한 프레임의 비필수 작업은 예산(예: 8 ms)을 넘으면 다음 프레임으로 미룬다.
- **FR-SPA-5** 무거운 계산(측정에서 한 번에 16 ms 를 넘는 비 DOM 작업)은 Web Worker 로 옮긴다(D-4). 대상은 M3 착수 시 측정으로 정한다.
- **FR-SPA-6** 기존 `<script>` 전역 구조와 시험 하네스(`web/js/test/harness.mjs`)는 유지한다. 지연 로딩도 클래식 스크립트로 싣는다. ES 모듈·번들러로 옮기지 않는다.

### 3.4 서버·데몬 (M4)

- **FR-SRV-1** 채널 다중화와 흐름 제어(FR-CON-6)는 서버가 맡는다. 출력 하나를 여러 구독자에게 보낼 때 인코딩은 한 번만 한다.
- **FR-SRV-2** 서버와 데몬은 유휴 시 주기 작업을 하지 않는다. 남는 주기 작업은 이유와 주기를 문서에 적는다.
- **FR-SRV-3** 서버가 띄우는 외부 프로세스(git·lsof 등)는 유휴 시 0이다. 필요할 때만 띄우고 결과를 같은 계기 안에서 나눠 쓴다.

## 4. 성능 요구사항 (완료 기준)

## 5. 단계 (마일스톤)

이슈 관리: `docs/internal/perf/issues/`(파일 하나가 이슈 하나, 형식은 `perf/README.md`). 에이전트 규칙은 `perf/AGENT_RULES.md`, 진행 상태는 `perf/STATUS.md` 다. 통합 브랜치는 `perf-m1`, 이슈 브랜치는 `pf/<이슈 ID>` 다.

각 단계는 시험 → 구현 → `scenario.mjs` 재측정 순서다. 단계가 끝날 때 전후 숫자를 이 문서 §7 에 적는다.

| 단계 | 내용 | 먼저 하는 이유 |
|---|---|---|
| M0 | 측정 도구(`scripts/perf/`)와 기준선을 커밋한다 | 다른 모든 단계의 판정 도구다 |
| M1 | 채널 — FR-CON 전부. 폴링 제거 | M2 의 구독·순번·흐름 제어가 이 위에 선다 |
| M2 | 서버 화면 상태와 터미널 구독 — FR-TRM 전부 | 메모리·잠든 터미널 비용(발견 1·2)을 푼다 |
| M3 | SPA 런타임 — FR-SPA 전부 | 부팅·유휴·그리기 비용(발견 3·4)을 푼다 |
| M4 | 서버·데몬 마무리 — FR-SRV 전부 | 병목은 아니므로 마지막이다 |

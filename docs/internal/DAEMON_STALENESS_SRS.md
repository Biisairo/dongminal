# SRS: 낡은 데몬의 감지 — IEEE 29148

> **문서 상태**: 승인·구현완료

| | |
|---|---|
| 근거 | 사용자 접수 — "매 빌드에서, 방금 빌드한 것으로 재실행할 때 `--restart-daemon` 이 필요한지 알려 달라" |
| 선행 | `VERSION_HEALTH_SRS` — 판 핸드셰이크(`FR-VHL-1/2`). 이 문서는 그 위에 **로컬 빌드에서도 성립하는** 판을 얹는다 |
| 성격 | 기존 빌드 스크립트·데몬 기동·두 CLI 출력의 개정. 새 액션 없음 |

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

한 가지를 세운다.

**빌드한 직후, 지금 도는 데몬이 그 빌드의 코드로 갈아탈 필요가 있는지가 드러난다.**

지금은 드러나지 않는다. 그래서 사람은 둘 중 하나를 한다 — 늘 `--restart-daemon`
을 붙여 **필요 없는 터미널 세션 손실**을 감수하거나, 붙이지 않고 **낡은 데몬 위에서
고친 줄 알았던 버그를 다시 본다**. 둘 다 사실을 모르기 때문에 치르는 값이다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 이름 | 요구 |
|---|---|---|
| **묶음 F** | 데몬 지문 새기기 (Fingerprint) | `FR-DFP-1..3` |
| **묶음 R** | 도는 데몬이 자기 판을 남긴다 (Record) | `FR-DFP-4..6` |
| **묶음 N** | 알림 세 자리 (Notify) | `FR-DFP-7..11` |

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 말 | 뜻 |
|---|---|
| **데몬 지문** | `dongminald` 프로세스가 실행하는 코드의 내용 해시. 빌드 때 계산되어 바이너리에 새겨진다 |
| **정의역** | 지문이 세는 소스의 범위 — `go list -deps dongminal/internal/daemon/boot` 의 저장소 패키지 (§3.1) |
| **낡은 데몬** | 도는 `dongminald` 의 지문이 디스크의 바이너리와 다른 상태. 서버만 재시작하면 남는다 |
| **모른다** | 지문이 빈 값인 상태. **불일치가 아니다** (`FR-VHL-5` 와 같은 원칙) |

### 1.4 참조 (References)

- `VERSION_HEALTH_SRS` — `hello` 가 프로토콜 판과 빌드 판을 따로 싣는다
- `RELEASE_SRS` `FR-RVN-1/2` — `cli.Version` 을 ldflags 로 새기는 단일 경로
- `ORCHESTRATION_V2_SRS` `FR-CBG-5` — **모른다 ≠ 괜찮다**
- `CI_GATES_SRS` — 새 스크립트도 같은 게이트를 지난다

## 2. 현재 상태 (조사로 확정한 사실, 2026-09-17)

### 2.1 한 바이너리가 두 프로세스로 돈다

```
dongminal start --foreground   pid 76723   웹서버 — 포트를 점유한다
dongminal d                    pid 76726   dongminald — PTY 를 소유한다
```

`start` 는 `killPort` 로 앞의 것을 죽이고 새 바이너리로 뜬다. 뒤의 것은
`--restart-daemon` 없이는 **옛 바이너리 그대로 계속 돈다** (`start.go:106`).
데몬은 PTY 를 들고 있어 이 조합이 가장 오래 산다.

### 2.2 빌드 판은 로컬에서 판별에 쓸 수 없다

`hello` 는 이미 빌드 판을 싣고 클라이언트가 읽는다(`FR-VHL-1/2`). 그러나
`scripts/build.sh` 는 `VERSION` 이 비면 ldflags 를 새기지 않고, 그때 값은
`cli.Version` 의 기본값 `dev` 다. **로컬 빌드는 언제나 `dev` 대 `dev`** 이므로
불일치 판정이 성립하지 않는다 — 판이 가장 자주 갈리는 자리에서 판이 침묵한다.

### 2.3 데몬이 실행하는 코드 경계는 기계적으로 뽑힌다

```
$ go list -deps dongminal/internal/daemon/boot | grep '^dongminal/' | wc -l
16          # 저장소 전체 60 패키지 중
```

이 16개가 데몬 프로세스 안에서 도는 저장소 코드의 전부다. 나머지 44개 —
`webserver/**`·`ctl/**` 대부분 — 는 데몬 프로세스에 없다. **웹서버만 고친
빌드는 데몬을 재시작할 이유가 없다**, 그리고 그것이 대다수의 빌드다.

### 2.4 데몬은 자기 판을 디스크에 남기지 않는다

`PanedServer.Listen` 은 `paned.pid` 를 쓴다(`paned_server.go:100`). 판은 메모리에만
있고(`ps.buildVersion`) `hello` 로만 나간다. 그래서 **소켓에 붙지 않고서는 도는
데몬이 무엇인지 알 수 없다** — 빌드 스크립트가 알기에는 비싼 경로다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 F — 데몬 지문 새기기

**FR-DFP-1** `scripts/build.sh` 는 빌드하는 **대상마다** 데몬 지문을 계산해
바이너리에 새긴다.

```
-X dongminal/internal/ctl/cli.DaemonBuild=<지문>
```

`cli.Version` 과 같은 경로를 쓴다 (`RELEASE_SRS FR-RVN-1`). 두 벌로 적지 않는다.

**FR-DFP-2** 지문의 **정의역**은 다음과 같다.

| | |
|---|---|
| 패키지 | `go list -deps dongminal/internal/daemon/boot` 중 `dongminal/` 접두의 것 |
| 파일 | 그 패키지들의 `GoFiles` + `EmbedFiles` |
| 대상 | `GOOS`/`GOARCH` 를 그 빌드 대상으로 두고 계산한다 |

대상별로 계산하는 이유는 `platform` 패키지가 OS 마다 다른 파일을 갖기 때문이다.
호스트 기준으로 한 번만 계산하면 **크로스 빌드 산출물의 지문이 그 바이너리의
내용과 무관해진다**.

`EmbedFiles` 를 세는 이유는 `shared/runtime` 이 `//go:embed all:shellhooks`·
`all:agentplugin` 으로 헬퍼와 플러그인을 담기 때문이다. 그 자산만 바뀐 빌드도
데몬이 설치하는 것을 바꾼다 (`boot.Run` → `runtime.Install`).

지문은 파일 내용에서만 나온다 — **경로·타임스탬프·빌드 환경이 들어가지 않는다.**
같은 소스는 어느 기계에서 빌드해도 같은 지문이어야 재현 가능 빌드가 유지된다
(`build.sh` 의 `REPRO_FLAGS` 와 같은 근거).

**FR-DFP-3** 새기지 않으면 `cli.DaemonBuild` 는 **빈 값**이다. 빈 값은
**모른다**이며 불일치가 아니다. `go build` 를 손으로 부른 바이너리, 검사
바이너리가 그 상태다.

### 3.2 묶음 R — 도는 데몬이 자기 판을 남긴다

**FR-DFP-4** 데몬은 `Listen` 에 성공한 뒤 자기 지문을 `$DONGMINAL_HOME/paned.build`
에 한 줄로 쓴다. 자리·수명·권한(`0600`)은 `paned.pid` 와 같다 — 같은 사실의 두 면이다.

**FR-DFP-5** 지문이 빈 값이면 그 파일을 **지운다**. 남겨 두면 앞선 데몬이 남긴
값이 지금 도는 데몬의 것인 양 읽힌다 — 침묵보다 나쁜 것은 틀린 말이다.

**FR-DFP-6** 값은 기존 `boot.Run(home, version)` 과 **같은 경로**로 주입된다.
데몬 층은 `ctl/cli` 를 import 하지 않는다 (`FR-VHL-1` 의 층 근거를 그대로 따른다).

### 3.3 묶음 N — 알림 세 자리

**FR-DFP-7** `scripts/build.sh` 는 **호스트 빌드**(인자 없는 기본 모드)가 끝나면
판정 한 줄을 낸다. `--all`·`--os` 는 배포 산출물을 만드는 모드이므로 내지 않는다 —
그 산출물은 이 기계에서 도는 데몬과 무관하다.

**FR-DFP-8** 판정은 네 상태다.

| 상태 | 조건 | 출력 |
|---|---|---|
| **미실행** | `paned.pid` 가 없거나 그 pid 가 죽어 있다 | 데몬 미실행 — `start` 가 새 바이너리로 기동한다 |
| **일치** | `paned.build` == 새 지문 | 데몬 코드 그대로 — `start` 만 하면 된다 (세션 보존) |
| **불일치** | `paned.build` != 새 지문 | ⚠ 데몬 코드가 바뀌었다 — `start --restart-daemon` (세션을 잃는다) |
| **모른다** | 새 지문이 비었거나 `paned.build` 가 없다 | 판을 모른다 — 확실히 하려면 `--restart-daemon` |

**모른다**를 **일치**로 접지 않는다. 낡은 데몬 위에서 고친 줄 알았던 버그를 다시
보는 것이 이 문서가 없애려는 바로 그 값이다.

**FR-DFP-9** `dongminal start` 가 데몬을 살려 둔 채 뜰 때
(`socketExists && !RestartDaemon`, `start.go:110`) 불일치면 기존 "dongminald 실행 중
(세션 보존)" 줄 아래에 경고를 덧댄다. 빌드와 기동 사이에 시간이 떠도 잡힌다.

**FR-DFP-10** `dongminal health` 는 데몬 줄 아래에 판 일치 여부를 한 줄 낸다.
불일치를 **실패로 세지 않는다**(종료 코드 0 을 유지한다) — 낡은 데몬은 어긋남이지
고장이 아니고, `health` 의 종료 코드는 생존의 답이다.

**FR-DFP-11** 세 자리의 판정은 **한 함수**에서 나온다. 세 벌로 적으면 한 곳만
고쳐지고, 그때 세 출력이 서로를 반박한다.

### 3.4 비기능 (Non-functional)

**NFR-DFP-1** 지문 계산은 호스트 빌드 한 번에 **1초를 넘지 않는다**. 빌드마다
치르는 값이므로 사람이 기다림을 느끼면 안 된다.

**NFR-DFP-2** 판정은 **소켓에 붙지 않는다**. 파일 둘(`paned.pid`·`paned.build`)만
읽는다 — 데몬이 멈춰 있어도, 소켓이 막혀 있어도 답이 나와야 한다.

## 5. 설계 결정 (Design Decisions)

**D-1 판을 손으로 올리지 않는다.** `DaemonVersion = 3` 같은 상수는 올리기를
잊는 순간 **거짓 음성**이 된다 — 그리고 잊는 쪽이 사람의 기본값이다. 게이트로
강제할 수는 있으나, 그 게이트가 하는 일(데몬 패키지에 diff 가 있는가)을 이미
지문이 정확히 한다. 검사를 더할 바에 계산을 둔다.

**D-2 정의역에 `cmd/dongminal` 을 넣지 않는다.** 데몬 프로세스의 동작은
`boot.Run` 이 전부이고 `main` 의 몫은 argv 판별이다. `main` 패키지는 웹서버
코드 전부를 의존하므로 넣으면 **거의 모든 빌드가 불일치로 읽힌다** — 그때 이
기능은 "늘 `--restart-daemon`" 과 같아지고, 없느니만 못하다. 대가는 진입점
판별이 바뀐 빌드를 놓치는 것인데, 그 변경은 그 자체로 큰 변경이라 사람이 안다.

**D-3 파일이지 RPC 가 아니다.** 빌드 스크립트가 JSON-RPC 클라이언트를 갖게 되면,
데몬이 응답하지 않는 상태 — 판정이 **가장 필요한 상태** — 에서 답을 못 낸다.
`paned.pid` 옆의 한 줄이면 족하다 (NFR-DFP-2).

**D-4 `paned.build` 는 `paned.pid` 와 같은 수명을 갖는다.** 둘을 다른 자리에서
쓰면 한쪽만 낡는다.

## 6. 비목표 (Non-goals)

- **자동 재시작.** 데몬 재시작은 터미널 세션 손실이다. 그 결정은 사람의 것이며,
  이 문서는 결정에 필요한 사실만 놓는다.
- **릴리스 산출물 간 비교.** `dist/` 의 바이너리는 이 기계의 데몬과 무관하다.
- **부분 재시작 (세션을 살린 채 데몬만 교체).** 별개의 큰 주제다.
- **`cli.Version` 의 대체.** 빌드 판과 데몬 지문은 다른 것을 센다 —
  `FR-VHL-1` 이 프로토콜 판과 빌드 판을 합치지 않은 것과 같은 근거다.

# SRS: Git 창 — 쓰기 뒤 뷰 갱신의 누락 — IEEE 29148

## 1. 개요

### 1.1 목적

접수한 말은 한 줄이다.

> **"깃 패널에서 changes 를 제외한 다른 탭들은 업데이트가 느린 것 같다. 예를 들어
> push 를 했는데 history 가 바로 안 바뀐다."**

증상은 "느리다"이지만 실체는 **아예 갱신하지 않는 것**이다. 사용자가 새로고침을
누르거나 리포를 다시 고를 때까지 화면이 옛 사실을 보인다.

### 1.2 범위

**포함:** 원격 작업(push·pull·fetch) 완료 뒤의 뷰 갱신, 전체 새로고침의 누락 대상.

**미포함:** 폴링 주기의 변경, 파일 감시 도입, 뷰 내부 렌더링의 변경. **갱신을
부르는 자리만 고친다.**

## 2. 현재 상태 (코드에서 확인한 사실)

### 2.1 갱신을 부르는 자리 전수

| 뷰 | 갱신하는 자리 |
|---|---|
| **Changes** (status) | 폴링 2계층 · `signal()`(가시성·포커스·cwd·저장) · 모든 쓰기의 `adopt()` · 원격 작업 완료 |
| History | `afterCommitOp`(전체) · `afterRefWrite`·`afterStashRefWrite`(refs만) · 새로고침 버튼 |
| Branches | 〃 (전체) · 새로고침 버튼 |
| Console | `_write()` — **모든 로컬 쓰기가 지나는 한 곳** · 새로고침 버튼 |
| Stash | `adoptWrite()` — stash 자신의 쓰기만 |
| Worktrees | 자기 쓰기(`_load()`) · 새로고침 버튼 |

### 2.2 결함 ① — 원격 작업이 끝나도 Changes 만 갱신된다

`web/js/git/remote.js` 의 `_finish(job)` 은 작업이 끝날 때 **`panel.collect()` 하나만**
부른다 (FR-GIT-107 이 그것을 요구했다). 그래서 push·pull·fetch 뒤에

- **History** 가 옛 refs 를 보인다 — push 로 원격 추적 브랜치가 움직였는데 그대로다.
- **Branches** 가 옛 ahead/behind·upstream 을 보인다.
- **Console** 에 방금 실행한 명령이 없다. 잡은 `_write()` 를 지나지 않기 때문이다 —
  **그런데 서버는 잡을 기록에 남긴다** (`domain/git/jobs/job.go` 의 `RecordWrite`).
  즉 데이터는 이미 있고 읽으러 가지 않을 뿐이다.

로컬 쓰기(커밋·브랜치·스태시)는 이 문제가 없다 — `afterCommitOp`·`afterRefWrite` 가
이미 History·Branches 를 다시 읽는다. **원격 경로에만 그 대응물이 없다.**

### 2.3 결함 ② — 전체 새로고침이 Stash 를 건너뛴다

`GitPanel.refresh()` 는 `collect`·History·Branches·Console·Worktrees 다섯을 돌리고
**Stash 를 넣지 않는다.** 그래서 터미널에서 `git stash` 한 뒤 새로고침을 눌러도
Stash 탭은 바뀌지 않는다. 새로고침은 "지금 사실을 다시 받아 온다"는 뜻이므로 이
누락은 그 약속을 깬다.

## 3. 요구사항

**FR-GVR-1.** 원격 작업이 끝나면 그 작업이 바꿀 수 있는 뷰를 **모두** 다시 읽는다.
갱신은 `GitPanel` 이 소유한다 — 다른 `after*Write` 들과 같은 자리여야 "무엇이
무엇을 바꾸는가"가 한 파일에 모인다.

**FR-GVR-2.** 종류에 따라 범위가 다르다.

| 종류 | History | Branches | Console |
|---|---|---|---|
| `push` | **refs 만** (`reloadRefs`) — 커밋은 늘지 않는다 | 전체 | 전체 |
| `fetch` · `pull` | **전체** (`reload`) — 새 커밋이 들어온다 | 전체 | 전체 |

**FR-GVR-3.** **실패해도 갱신한다.** 실패한 push 도 Console 에 남아야 하고, 부분적으로
움직인 refs 가 있을 수 있다 (`afterCommitOp` 가 실패에도 갱신하는 것과 같은 근거).

**FR-GVR-4.** 열린 적 없는 뷰에는 **요청이 나가지 않는다.**

> **초판의 전제는 틀렸다.** "기존 `if(this._xxxView)` 가드를 그대로 쓰면 된다" 고
> 적었으나, **뷰 넷은 Git 창을 여는 순간 전부 만들어진다** — `detach()` 가
> `this._console().unmount()` 처럼 모든 접근자를 부르기 때문이다(실측: 탭을 하나도
> 누르지 않아도 `{con,hist,br,st}` 가 전부 참). 그 가드는 "열린 적 있는가" 를
> 가르지 못한다.

실제로 요청을 막는 것은 **각 뷰 안의 판정**이다. History·Branches·Stash 는
`_el`·`_repo` 가 없으면 조기 반환하므로 열지 않은 상태에서 요청이 나가지 않는다.

**Console 만 예외이며, 그것은 의도된 기존 동작이다.** `GitConsole.reload()` 에는
그 판정이 없고, 이미 **모든 로컬 쓰기**가 `GitPanel.post()` 에서 열지 않은 Console
의 기록을 받아 온다 (FR-GIT-218 — "방금 실행한 명령이 Console 의 맨 위에 있어야
한다"). 원격 작업만 다르게 굴 이유가 없으므로 **같은 규약을 따른다.** 비용은
사용자 조작 하나당 `/api/git/records` 한 번이고, 그 종단은 메모리 기록을 읽을
뿐 git 을 실행하지 않는다.

**FR-GVR-5.** 갱신은 `collect()` 의 완료를 기다리지 않는다. 서로 독립이며, 기다리면
화면이 그만큼 늦는다.

**FR-GVR-6.** `refresh()` 의 대상에 **Stash 를 더한다.** 새로고침은 열려 있는 모든
뷰를 다시 받아 온다는 뜻이다.

**FR-GVR-7.** 위 어느 것도 **폴링 주기를 바꾸지 않는다.** 갱신을 부르는 자리만
는다 — 주기를 줄이면 git 실행이 늘고 FR-GIT-24 의 절약이 깨진다.

## 5. 비목표

1. **폴링을 빠르게 하지 않는다.** 증상은 "느리다"였으나 원인은 "안 한다"이므로 주기는
   답이 아니다.
2. **파일 감시(watch) 를 넣지 않는다** — `GIT_INTEGRATION_ANALYSIS` §4.5 의 기각 근거가
   그대로 걸린다.
3. **터미널에서 일어난 변화의 실시간 반영은 범위 밖이다.** 그쪽의 계기는 `signal()` 과
   새로고침이며, 이 SRS 는 새로고침이 약속을 지키게 하는 데까지만 간다 (FR-GVR-6).

## 6. 확정 결정

| id | 결정 | 근거 |
|---|---|---|
| **D-1** | 갱신 지식은 `GitPanel.afterRemoteJob(kind)` 하나에 둔다 | `remote.js` 가 뷰를 하나씩 알면 "무엇이 무엇을 바꾸는가"가 두 파일로 갈린다 |
| **D-2** | push 는 refs 만, fetch·pull 은 전체 | push 로 커밋이 늘지 않는다. 전체를 다시 읽는 것은 그만큼 비싸다 |
| **D-3** | 실패해도 갱신한다 | 실패도 Console 에 남고 refs 가 움직였을 수 있다 |
| **D-4** | 주기는 손대지 않는다 | 원인이 주기가 아니다 (§5 비목표 1) |
| **D-5** | Console 은 열지 않아도 갱신한다 | 이미 배포된 `post()` 의 성질과 같다. 원격만 다르게 굴면 같은 사실이 두 규약을 갖는다 (FR-GVR-4) |
| **D-6** | `GitStash` 에 `reload()` 를 둔다 | 나머지 네 뷰가 전부 그 이름이다. 바깥에서 `_load()` 를 부르면 뷰마다 부르는 이름이 갈린다 |
| **D-7** | Console 폴링의 가시성 판정에 **`isConnected` 를 더한다** | 이 작업 중 발견한 별건의 누수다 — `vis` 클래스만 보면 떠난 탭에서도 2초마다 계속 받는다. 탭을 바꾸면 본문이 버려지지만 클래스는 남기 때문이다 |

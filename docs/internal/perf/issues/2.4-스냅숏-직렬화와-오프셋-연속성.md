# 2.4 스냅숏 직렬화와 오프셋 연속성 (FR-TRM-4, A-2)

## 목표

화면 + 최근 기록 N줄(기본 5,000)을 최소 재그리기 ANSI 로 직렬화한다. 커서·SGR·OSC 8·대체 화면(주 화면 포함)·스크롤 영역·원점·자동 줄바꿈·삽입·문자 집합·앱 커서 키·키패드·마우스·괄호 붙여넣기·포커스 보고·창 제목을 싣는다(`TermModes::restore_bytes` 의 일을 옮긴다). 머리: 오프셋 `end`·크기·대체 화면·첫 기록 줄 번호·cwd. `cmu` 잠금 안에서 만들어 `end` 와 한 순간을 맞춘다. IPC 메서드(가칭 `screen`)와 기능 이름(가칭 `FEATURE_SCREEN_STATE`)을 더한다.

설계: `perf/M2_DESIGN.md` §2.4. 결정: D-18. 분할점이 시퀀스·UTF-8 한가운데인 경우(HIGH 위험)를 먼저 시험으로 드러내고 대응을 정한다.

## 완료 조건

- RED: 스냅숏을 새 xterm(headless)에 넣은 화면 = 원래 바이트를 넣은 화면(대체 화면 중 포함, OSC 8 포함).
- RED: 임의 분할점 k 에서 `스냅숏(k) + 바이트[k..]` 의 최종 화면·기록 = 바이트 전체. 분할점이 이스케이프·UTF-8 한가운데여도.
- RED: 모드 왕복 — 각 모드를 켠 뒤 스냅숏 → 새 xterm 의 모드가 같다.
- 스냅숏 크기·생성 시간을 잰다(5천 줄, NFR-PRF-14 예산 판단용).
- 바꾼 부분의 시험(단위·관련 e2e 한두 개)·fmt·clippy·관련 게이트 통과. 전체 시험은 마일스톤 끝에서 한 번만(2.10).
- 시험을 먼저 쓰고 RED 를 확인한 뒤 구현한다.
- 동작을 바꿨으면 이전 동작 / 새 동작 / 이유를 진행 기록과 커밋 메시지에 적는다.

착수 때 조정자에게 하위 셋(2.4.1 직렬화기·2.4.2 저장소 연결·2.4.3 IPC)으로 나누자고 알렸다. 답이 없어 한 브랜치(pf/2.4)에서 셋을 차례로 했다.

**바꾼 것**

- termstate `Screen::snapshot(history) -> Snapshot{bytes, back, first_line}` (`snap.rs`). RIS 뒤에 다음을 최소 재그리기 ANSI 로 쓴다(ED2 는 쓰지 않는다 — alacritty 는 ED2 때 화면을 기록으로 밀고 xterm.js 는 그러지 않는다).
  - 저장소 줄(ANSI, 받는 쪽이 지금 폭으로 감쌈)
  - 에뮬레이터 기록 행·화면 행(감싼 행은 자동 줄바꿈으로 잇는다)
  - 대체 화면이면 가려진 주 화면 → 주 커서·펜 → `?1049h` → 대체 화면 행
  - 저장 커서(DECSC)·스크롤 영역·원점·문자 집합(G0~G3)·SO·모드(`restore_bytes` 의 모드 + 앱 커서·키패드·자동 줄바꿈·삽입·LNM·alternate scroll·커서 보임)·DECSCUSR·제목(OSC 2)·펜(SGR·밑줄 종류·밑줄 색·OSC 8)
  - 커서: 줄바꿈 대기면 마지막 칸을 다시 찍는다. 아니면 커서 앞 칸을 펜 그대로 마지막에 다시 찍는다(아래 결합 문자).
- 가려진 주 화면 읽기: alt 격자 clone → `swap_alt` → 주 화면 읽기 → `swap_alt` → alt 격자 되씌움. 두 번째 바꾸기가 고치는 주 화면 저장 커서는 alt 동안 커서와 늘 같다. 분할점 시험(대체 화면 녹화 vim·less·top·alt-roundtrip)으로 굳혔다.
- 분할점이 시퀀스·UTF-8 한가운데인 경우(HIGH 위험) — **오프셋을 물린다**. 끝나지 않은 바이트는 화면을 바꾸지 않았으므로 스냅숏에 넣지 않고 `back` 만큼 앞에서부터 이어 보내게 한다. 시퀀스 안에서 C0 가 이미 실행됐으면(물리면 두 번 실행) 물리지 않고 끝나지 않은 바이트를 스냅숏 끝에 붙인다(실행된 C0 는 뺀다). 바닥 상태는 vte 가 알려 주지 않아 vte 0.15 표를 옮긴 스캐너(`scan.rs`)가 따라간다. 같은 스캐너가 스크롤 영역(alacritty 비공개)·SO/SI·ED3·RIS 를 본다. 착수 때 조정자에게 알린 방침(끝나지 않은 바이트를 스냅숏에 붙임)에서 바꿨다 — 받는 쪽이 끊긴 바이트를 다루지 않아도 되고, xterm.js 5.5 의 UTF-8 이어 읽기 결함(아래)도 피한다.
- 새 이모지 보정(사용자 결정): U+1F000 이상 넓은 글자 뒤에 CHA 로 열을 다시 찍는다. 한글·한자에는 붙지 않는다.
- 줄 저장소 연결(`hist.rs`, `emu.rs`): Screen 이 `LineStore` 를 든다. `feed` 는 `split_for_rows(…, SLACK=256)` 조각마다 넣고, 에뮬레이터 기록이 `EMU_KEEP=1,000` 을 넘으면 넘는 만큼 오래된 **완결된 논리 줄**을 저장소로 옮긴다(걸친 줄은 기다리고, 256 행을 넘게 밀리면 끊는다). 에뮬레이터 상한 = keep + 2×SLACK + 화면 행 수(크기 바꿀 때 다시 잡음). ED3·RIS 면 저장소를 비우고 번호는 잇는다(대체 화면 중 ED3 는 비우지 않음 — alacritty 가 주 화면 기록을 두므로). 스냅숏의 기록 N 행이 에뮬레이터로 모자라면 저장소에서 지금 폭 기준으로 채운다. `first_line` 은 실린 가장 오래된 저장소 줄 번호(없으면 저장소 끝 번호).
- toolhub: `Tool::screen(history) -> Option<ToolScreen>` — `cmu` 안에서 스냅숏과 링 오프셋을 함께 잡는다. `end = 링 오프셋 - back`. `ToolManager::screen_tool`. `SCREEN_HISTORY` 상수를 지우고 `Screen::new(c, r, HISTORY_CAP)`(저장소 상한 50,000).
- IPC: `toolipc::METHOD_SCREEN = "screen"`, `FEATURE_SCREEN_STATE = "screen"`(DAEMON_FEATURES 에 추가), `ScreenParams{history, id}`, `ScreenResult{alt, cols, cwd, data, end, firstLine, rows}`. 데몬 `handlers::screen`(없는 도구 CODE_NOT_FOUND). 서버 `ToolClient::screen_tool(id, history)`. 쓰는 곳은 아직 없다(2.5).
- 공개 표면 변경: `Screen::new` 의 세 번째 인자가 "에뮬레이터 기록 상한" → "줄 저장소 상한". `drop_oldest` 비공개로(저장소 옮기기가 한 길). `Attrs` 에 밑줄 종류 넷·`ANY_UNDERLINE`·`intersects`·`is_empty`, `Cell.underline`(밑줄 색), `Color: Default`, `Screen::store()`, `EMU_KEEP`, `HISTORY_CAP` 재내보냄.
- 시험 자료: `testdata/check-snap.mjs`(xterm.js 확인), `architecture.md` 의 hello.features 표에 `screen` 줄.

**동작 변경**

- 데몬 화면 상태의 UTF-8 이어 읽기 — 이전: 바이트를 vte 에 그대로 넣었다. vte 0.15.0 은 앞 조각에서 끊긴 UTF-8 글자를 이어 읽을 때 뒤따르는 글자를 삼킨다(`advance_partial_utf8` 가 `valid_bytes - old_bytes` 만큼 건너뜀; 예 `e\xcc` | `\x81a` → `a` 를 잃음). 새: 바닥 상태에서 끊긴 UTF-8 앞 바이트를 글자가 모일 때까지 들고 있다. 이유: PTY 읽기는 글자 한가운데서 끊긴다(2.2 부터 있던 결함, 시험 `utf8_split_across_feeds_keeps_following_char`).
- 데몬 메모리 — 이전: 에뮬레이터 기록 1,000줄(상한). 새: 에뮬레이터 1,000 + 여유(최대 1,000 + 512 + 화면 행) + 저장소(최대 50,000 논리 줄, 압축). 이유: FR-TRM-2·D-14. 측정은 2.10.
- 데몬 IPC — `hello.features` 에 `screen` 이 붙는다. 옛 서버는 모르는 이름을 무시한다.

  - 분할점 시험: 오라클은 "새 에뮬레이터에 스냅숏(k) → 바이트[..k] 의 상태와 같다(화면·기록(저장소 포함 논리 줄)·대체 화면·주 화면·커서·저장 커서·펜·문자 집합·모드·제목·스크롤 영역·SO·끝나지 않은 바이트)" + "스냅숏(k) + 바이트[k-back..] = 바이트 전체". 2 KB 이하 자료는 모든 k, 그보다 긴 vim·less·top 은 7바이트마다 + 시퀀스 한가운데 전부, agent-sim 은 60개 표본, 저장소를 거치는 시험(keep 5·50)도 한다.
  - 모드·문자 집합·펜·링크·커서·제목·대체 화면 상태 왕복(모든 분할점), 64 KB 넘는 한 청크 6,000줄에서 줄을 잃지 않음(2.3 에서 넘어온 연결 시험), ED3 뒤 저장소 비움·번호 이음, 긴 감싼 줄이 통째로 옮겨짐, 스냅숏이 저장소 줄로 기록을 채움(`first_line`).

**남은 위험 / 2.5 이후가 알아야 할 것**

- xterm.js 5.5 UTF-8 이어 읽기 결함: `Utf8ToUtf32.decode` 가 interim 의 이어 바이트가 0x80 이면(하위 6비트 0) 길이를 잘못 세어 글자를 잃는다(예 바이트로 `\xe2\x80` | `\x94c` 를 write → `—` 를 잃음). 앱 브라우저는 `TextDecoder(stream)` 으로 문자열을 만들어 write 하므로(`term-output.js:18`) 실시간 중계는 걸리지 않는다. 스냅숏은 오프셋을 물려 바이트 경로에서도 피한다. 2.5 가 스냅숏을 바이트로 xterm 에 바로 넣지 않도록 지금 디코더 경로를 그대로 쓰면 된다.
- 깨움 예산(NFR-PRF-14 100 ms): 5,000 행 스냅숏 443 KB + base64. 2.5 가 측정한다. 넘으면 M2 §4 대응(화면 먼저·기록 뒤)을 정해야 한다.
- 스냅숏이 싣지 않는 상태: 사용자 탭 정지(HTS), 색표 바꾸기(OSC 4/10/11), kitty 키보드 모드, 제목 스택. RIS 뒤에도 남는 제목 사본(alacritty 는 RIS 때 제목 사건을 보내지 않는다).
- 16색은 30~37·90~97 꼴로 쓴다. 원래 `38;5;1` 로 칠한 칸은 xterm 의 "굵은 글자 밝게" 가 걸리게 된다(드묾).
- REP(CSI b) 가 스냅숏 바로 뒤에 오면 앞 글자가 커서 바로 앞 칸일 때만 맞는다.
- 아주 긴 논리 줄(256 행 넘게 걸침)은 저장소에서 둘로 끊긴다.
- `TermModes::restore_bytes`·`snapshot`(링 재생)은 남긴다 — 서버가 아직 쓰고, 옛 데몬 경로다(D-27). 지우는 것은 2.5 이후(FR-CON-10).
- 인계(2.9): 새 데몬은 빈 화면 상태·빈 저장소로 시작한다.

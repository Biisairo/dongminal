# SRS: 사이드바 상단 탭 — Windows / Git 분리 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 한 줄이다.

> **"window/git 을 좌측패널 상단 탭으로 변경하게 한다."**

현재 좌측 사이드바는 `Windows` 목록과 `Git` 섹션을 **세로로 쌓아** 하나의 스크롤
컨테이너 안에서 높이를 나눠 쓴다. 그 결과 **양쪽 다 좁다** — Git 섹션은
`max-height:40%` 로 잘리고(`style.css:1492`), Windows 목록은 남은 60% 를 쓴다. 창이
많거나 핀 리포가 많으면 어느 쪽도 한눈에 들어오지 않는다.

본 SRS 는 이 세로 분할을 **탭 전환**으로 바꾼다. 한 번에 하나만 보이고, 보이는
쪽은 **사이드바 전체 높이**를 쓴다.

### 1.2 범위 (Scope)

**포함:** 사이드바 상단 탭 바 신설, `Windows`/`Git` 두 패널의 배타 표시, 활성 탭
영속, 모바일 드로어 대응, 자동 전환 규칙, 배지. **그리고 2026-08-28 사용자 인터뷰로
추가된 셋** — 탭의 인터페이스화(§3.6), 탭↔콘텐츠 창 연동(§3.7), 단축키(§3.8).

**미포함:** §6 비목표. 특히 **Git 패널 내부의 동작과 Git 창 내부의 동작은 한 줄도
바뀌지 않는다.**

#### 함께 닫히는 보류건

`GIT_REMAINING.md` §1.2 가 "결정이 필요하다 — 코드를 봐도 답이 나오지 않는다" 로
남겨 둔 두 건이 **이번 인터뷰로 결정됐고, 이 SRS 가 닫는다.**

| 건 | 접수한 말 | 이번에 하는 것 |
|---|---|---|
| **I5** | git 으로 바로가기 · git pin/live 리스트 순회 | 탭마다 직행 키 신설 + 순회 키를 활성 탭 기준으로 재해석 (§3.8) |
| **I6** | git 에서 단축키로 window 로 돌아갈 때 원래 있던 윈도우로 우선 이동 | 탭 활성화가 콘텐츠 창까지 전환하며, 대상은 `_lastPlainWindow` (§3.7) |

> I5 의 보류 근거였던 `GIT_REVIEW4_SRS` §3.6.6 의 키 충돌("두 안이 같은 키를 다툰다")
> 은 해소됐다 — 채택된 안은 그 둘 중 어느 쪽도 아니다 (D-9).

## 2. 전체 설명 (Overall Description)

### 2.1 현재 구조 — 조사로 확정한 사실

```html
<!-- web/index.html:22-31 (현재) -->
<div id="sidebar">
  <div class="sb-title">Windows</div>
  <button id="add-window">+ New</button>
  <button id="add-preset">★ Preset</button>
  <div id="windows"></div>          <!-- flex:1 1 auto -->

  <div class="sb-title git-sec-title">Git</div>
  <div id="git-repos"></div>        <!-- flex:0 1 auto; max-height:40% -->
  <button id="git-add-repo">+ Add</button>

  <button id="settings-btn">⚙</button>
</div>
```

| 사실 | 근거 |
|---|---|
| 두 목록이 같은 flex 컬럼에서 높이를 다툰다 | `style.css:27` `#windows{flex:1 1 auto}` · `style.css:1492` `#git-repos{flex:0 1 auto;max-height:40%}` |
| 렌더 진입점은 둘로 이미 갈려 있다 | `renderer.js:36` `_rSidebar()` · `renderer.js:74` `_rGitSection()` |
| 갱신 주기도 다르다 | Windows 는 SSE `workspace_changed`, Git 은 **3초 폴링** (`_gitReposRefresh`) |
| git 이 없는 환경이면 Git 섹션 전체가 `display:none` | `renderer.js:79-84` `this.app._gitOff` |
| 두 목록 모두 **드래그 재배치**를 갖는다 | `_siEl` 의 dragstart/drop · 핀 재배치 (FR-GIT-223) |
| 두 목록 모두 `reconcileList` 로 **요소를 보존**한다 | FR-RPT-2/3 — 새로 만들면 hover·드래그가 깨진다 |
| Git 창은 Windows 목록에 **없다** | FR-GIT-182 — 진입점은 Git 섹션의 리포 항목뿐 |

**설계상 중요한 것**: 두 패널은 렌더 함수·데이터 원천·갱신 계기가 **이미 완전히
분리돼 있다.** 탭으로 가르는 데 필요한 것은 컨테이너와 표시 제어뿐이며, 렌더 로직에는
손댈 것이 없다. 이것이 본 변경의 리스크를 낮게 만든다.

**주의해야 할 것**: FR-GIT-182 때문에 **Git 창으로 들어가는 유일한 문이 Git 패널**이다.
탭을 도입하면 그 문이 탭 하나 뒤로 숨는다 — §3.4 의 자동 전환·배지 규칙이 이를 보상한다.

### 2.2 목표 구조

```html
<div id="sidebar">
  <div id="sb-tabs">                              <!-- 신설 -->
    <button class="sb-tab active" data-panel="windows">Windows</button>
    <button class="sb-tab" data-panel="git">Git<span class="sb-tab-badge"></span></button>
  </div>
  <div class="sb-panel" id="sb-panel-windows">    <!-- 신설 래퍼 -->
    <button id="add-window">+ New</button>
    <button id="add-preset">★ Preset</button>
    <div id="windows"></div>
  </div>
  <div class="sb-panel" id="sb-panel-git" hidden> <!-- 신설 래퍼 -->
    <div id="git-repos"></div>
    <button id="git-add-repo">+ Add</button>
  </div>
  <button id="settings-btn">⚙</button>            <!-- 탭 밖. 항상 보인다 -->
</div>
```

`.sb-title` 두 개는 사라진다 — 탭 이름이 그 역할을 대신한다.

### 2.3 제약 (Constraints)

- **C-1** 번들러가 없다. 새 JS 는 `index.html` 에 `<script>` 로 등록하며 로드 순서가
  의존성이다.
- **C-2** 사이드바 너비는 `--sb-w` (기본 150px, 100~400 조절 가능)다. 탭 바는 **150px
  에서도 두 탭이 잘리지 않아야** 한다.
- **C-3** 다시 그리기 보존 규약(FR-RPT-2/3)을 깨지 않는다. 탭 전환이 `reconcileList`
  가 지키는 DOM 요소를 파괴하면 안 된다.
- **C-4** 모바일에서 사이드바는 상단 드로어다 (`style.css:493` `body.mobile #sidebar`).
  탭은 거기서도 동작해야 한다.

## 3. 요구사항 (Specific Requirements)

### 3.1 탭 바 (FR-SBT-1 ~ 5)

**FR-SBT-1** 사이드바 최상단에 탭 바(`#sb-tabs`)를 둔다. 탭은 `Windows`·`Git` 둘이며,
**정확히 하나**가 활성이다.

**FR-SBT-2** 탭을 누르면 해당 패널만 보이고 다른 패널은 숨는다. 전환은 **표시 속성
변경만**으로 하며 DOM 을 제거하거나 다시 만들지 않는다 (C-3).

> **구현 규약**: 숨김은 `hidden` 속성 또는 `display:none` 으로 한다. `visibility`·
> `opacity` 는 쓰지 않는다 — 숨은 패널이 레이아웃 공간을 차지하면 보이는 쪽이
> 전체 높이를 쓴다는 목적 자체가 무너진다.

**FR-SBT-3** 보이는 패널은 사이드바의 **남은 높이 전부**를 쓴다. `#git-repos` 의
`max-height:40%` 제약을 **제거한다** — 그 제약은 세로 공존 때문에 있었고, 공존이
사라지면 근거도 사라진다.

**FR-SBT-4** `⚙ Settings` 버튼은 탭 밖 최하단에 남아 **어느 탭에서나 보인다.**

**FR-SBT-5** 탭 바는 `--sb-w` 최소값 100px 에서도 두 탭 이름이 읽혀야 한다. 두 탭이
너비를 균등 분할하고(`flex:1`), 이름이 넘치면 말줄임한다.

### 3.2 활성 탭의 영속 (FR-SBT-6 ~ 8)

**FR-SBT-6** 활성 탭은 `localStorage` 에 보관한다 (키: `sidebarTab`). 워크스페이스에
넣지 않는다 — **보는 방식은 클라이언트의 것**이고, 다른 기기의 사이드바를 바꿔서는
안 된다. 사이드바 너비(`sidebarWidth`)가 이미 이 규약을 따른다.

**FR-SBT-7** 새로고침 시 보관된 탭을 복원한다. 값이 없거나 알 수 없는 값이면
`Windows` 다.

**FR-SBT-8** `_gitOff`(git 이 없는 환경)이면 **Git 탭 자체를 숨긴다.** 보관된 탭이
`git` 이어도 `Windows` 로 떨어진다. 지금 Git 섹션 전체를 감추는 동작(`renderer.js:79`)의
탭 판이다.

### 3.3 렌더 (FR-SBT-9 ~ 11)

**FR-SBT-9** `_rSidebar()`·`_rGitSection()` 의 **내용은 바꾸지 않는다.** 탭은 컨테이너
층의 변경이며 목록 렌더 로직은 그대로다.

**FR-SBT-10** 숨은 패널도 **계속 렌더한다.** Git 3초 폴링과 Windows SSE 갱신을 탭
활성 여부로 끄지 않는다.

> **근거**: 배지(FR-SBT-12)가 숨은 쪽의 변화를 알려야 하고, 전환 순간에 낡은 목록이
> 잠깐 보이는 것을 피해야 한다. 3초에 한 번의 DOM 갱신은 비용이 아니다.

**FR-SBT-11** 탭 전환 시 그 패널의 스크롤 위치를 **보존한다.** 숨김이
`display:none` 이면 스크롤이 0으로 돌아가므로, 전환 전 `scrollTop` 을 저장하고
복원한다.

### 3.4 발견성 보상 (FR-SBT-12 ~ 15)

> FR-GIT-182 로 Git 창의 유일한 문이 Git 패널인데, 탭이 그 문을 한 겹 뒤로 옮긴다.
> 아래 넷이 그것을 보상한다.

**FR-SBT-12** `Git` 탭에 **배지**를 둔다. 비활성일 때, 핀 리포 중 **변경사항이 있는
리포 수**를 보인다. 0이면 배지가 없다. 활성 탭일 때는 목록에 그 정보가 이미 있으므로
배지를 띄우지 않는다.

**FR-SBT-13** `Windows` 탭에 **주의(attention) 배지**를 둔다. 비활성일 때, 알람이 있는
창 수를 보인다. 지금 `.si.attn` 이 목록 안에서만 알리던 것을 탭까지 끌어올린다.

**FR-SBT-14** Git 창으로 포커스가 옮겨지면 사이드바가 **자동으로 `Git` 탭으로
전환**된다. 반대로 일반 창으로 옮겨지면 **자동으로 `Windows` 탭으로 전환**된다.

> **근거**: Git 창에 있는데 사이드바가 Windows 를 보이면, 지금 보고 있는 것이 목록
> 어디에도 없다 (FR-GIT-182). 사이드바가 **본문을 따라간다**는 규칙이 그 모순을 없앤다.

**FR-SBT-15 (개정, 2026-08-28)** ~~FR-SBT-14 의 자동 전환은 사용자의 수동 전환을
덮어쓰지 않는다.~~ → **탭과 활성 창은 한 상태의 두 표현이며, 어긋난 상태를 두지
않는다.**

사용자 결정으로 탭 전환이 **콘텐츠 창까지 바꾸게 되었으므로**(§3.7 FR-SBT-22),
"탭은 Windows 인데 보고 있는 것은 Git 창" 이라는 상태는 더 이상 만들어질 수 없다.
탭을 고르면 창이 따라가고(FR-SBT-22), 창이 바뀌면 탭이 따라간다(FR-SBT-14). 두
방향이 모두 있으므로 "수동 선택을 보존하는 예외" 는 성립하지 않는다.

> **뒤집은 근거.** 구 FR-SBT-15 는 탭이 **표시 전용**이라는 전제 위에 있었다. 그
> 전제가 사라졌다 — 탭은 이제 **조작**이다. 두 개의 진실(사용자가 고른 탭 / 실제
> 활성 창)을 유지하면, §3.8 의 순회 키가 무엇을 순회해야 하는지 답할 수 없다.

### 3.5 모바일 (FR-SBT-16 ~ 17)

**FR-SBT-16** 모바일 드로어에서도 탭이 동작한다. 탭 바는 드로어 상단에 고정되고
패널만 스크롤한다.

**FR-SBT-17** 모바일에서 탭의 터치 타깃은 최소 44px 높이다. 데스크톱은 30px 로,
사이드바의 다른 행(`.si` 30px, 버튼 `min-height:30px`, FR-GIT-226)과 맞춘다.

### 3.6 탭 인터페이스화 (FR-SBT-18 ~ 21)

> 사용자 결정(2026-08-28): **"이후 추가 탭이 생길 수 있으므로 해당 탭 인터페이스화.
> 현재의 window 구현이 기준임."** 구 비목표 3("세 번째 탭을 만들지 않는다")을
> 철회한다 — 지금 셋째를 만들지는 않되, **셋째가 올 자리를 만든다.**

**FR-SBT-18** 탭은 **서술자의 배열**로 정의한다. 배열 순서가 표시 순서이자 직행 키의
번호다 (FR-SBT-26). `Windows` 가 첫째, `Git` 이 둘째다.

**FR-SBT-19** 탭 서술자의 계약은 다음과 같다. 필드는 **창 목록이 실제로 하는 일**에서
뽑았다 — 가상의 확장성을 위해 쓰이지 않는 훅을 만들지 않는다.

| 필드 | 필수 | 의미 |
|---|---|---|
| `id` | ✓ | 안정 식별자. 영속(FR-SBT-6)·단축키 라벨의 키 |
| `label` | ✓ | 탭 헤더에 보이는 이름 |
| `panelId` | ✓ | 이 탭이 보이게 할 패널 래퍼 id (§3.9.1) |
| `badge()` | | 헤더 배지 값. `0`·`null` 이면 표시하지 않는다 (FR-SBT-12/13) |
| `visible()` | | 탭 자체의 표시 여부. `Git` 은 `!_gitOff` (FR-SBT-8) |
| `onActivate()` | | 활성화 시의 콘텐츠 창 전환 (§3.7) |
| `cycle(dir)` | | 순회 키가 이 탭에서 무엇을 순회하는지 (§3.8) |

**FR-SBT-20** `cycle(dir)` 이 없는 탭이 활성일 때 순회 키는 **아무 일도 하지
않는다.** 보이지 않는 목록을 대신 순회하지 않는다.

**FR-SBT-21** 새 탭을 더하는 비용은 **서술자 1개의 추가**여야 한다. `index.html`·
단축키 맵·순회 디스패치를 다시 열지 않는다. 이 사실을 `architecture.md` 에 한 절로
남긴다.

### 3.7 탭 전환과 콘텐츠 연동 (FR-SBT-22 ~ 25)

> 사용자 결정(2026-08-28): **"탭 선택이 Git 창까지 전환."** 이것이 `GIT_REMAINING`
> §1.2 의 **I6**("git 에서 창 순회로 돌아갈 때 원래 있던 윈도우로 우선 이동")을
> 닫는다.

**FR-SBT-22** 탭을 활성화하면 사이드바 패널이 바뀌고, **콘텐츠 영역의 활성 창도 함께
바뀐다.**

| 활성이 된 탭 | 콘텐츠 영역 |
|---|---|
| `Windows` | **마지막으로 활성이었던 일반 창** |
| `Git` | Git 창 |

**FR-SBT-23** `Windows` 탭 복귀의 대상은 `app-layout.js:96` 이 **이미 유지하고 있는**
`_lastPlainWindow` 다.

```js
if(cur&&!this._isGitWin(cur)) this._lastPlainWindow=cur.id;
```

**I6 은 새 상태를 요구하지 않는다** — 이 값을 쓰는 경로만 있으면 닫힌다. 이로써
"원래 있던 윈도우" 의 정의를 **"Git 창에 들어가기 직전의 일반 창"** 으로 확정한다
(`GIT_REMAINING` §1.2 가 남긴 두 후보 중 ②).

**FR-SBT-24** `_lastPlainWindow` 가 없거나 그 창이 이미 닫혔으면 일반 창 목록의
**첫 번째**로 간다. 일반 창이 하나도 없으면 아무 일도 하지 않는다.

**FR-SBT-25** `Git` 탭 활성화 시 Git 창이 **없으면 만들지 않는다.** 탭만 전환되고
콘텐츠는 그대로다. Git 창은 여전히 **리포를 골라야** 생긴다 (`app-git.js:53`
`_mkGitWindow` 경로 보존). 영속된 탭이 `Git` 인데 복원 시 Git 창이 없는 경우도 같다.

### 3.8 단축키 (FR-SBT-26 ~ 33)

> 사용자 결정(2026-08-28): **"단축키 넣는걸로 해야해. 각 탭당 탭으로 이동하는 단축키
> 넣을꺼야. 깃 탭 내에서 순회는 window 에서 순회와 동일한 단축키야."**
>
> 구 비목표 5 와 D-6("단축키는 이번에 안 넣는다")을 **철회한다.** 보류 근거였던
> `GIT_REVIEW4_SRS` §3.6.6 의 키 충돌 조사는 이 결정으로 해소됐다 — 모드 의존 토글이
> 아니라 **탭마다 고유한 직행 키**를 두고, 순회 키만 활성 탭을 따라 대상이 바뀐다.
> 이것이 `GIT_REMAINING` §1.2 의 **I5** 를 닫는다.

#### 3.8.1 직행 키

**FR-SBT-26** 탭마다 **직행 키**를 둔다. 배열의 n 번째 탭은 `Ctrl+Shift+Digit{n}` 이다.

| 키 | 대상 |
|---|---|
| `Ctrl+Shift+1` | 첫 번째 탭 (`Windows`) |
| `Ctrl+Shift+2` | 두 번째 탭 (`Git`) |
| `Ctrl+Shift+{n}` | n 번째 탭 — 탭이 늘면 **자동 확장** |

`Ctrl+Shift+Digit1~9` 는 **전부 미사용**임을 확인했다 (`helpers.js:79`
`SHORTCUT_DEFAULTS` 실측: 쓰이는 것은 `[ ] H V N T W D A ↑↓←→` 와 `Ctrl+Tab` 뿐).

**FR-SBT-27** 직행 키는 **토글이 아니다.** 이미 그 탭이 활성이면 아무 일도 하지
않는다 — FR-SBT-22 의 콘텐츠 전환도 일어나지 않는다. 같은 키를 두 번 눌러 왕복하는
동작을 만들지 않는다 (사용자 결정).

**FR-SBT-28** 번호 키를 고른 이유는 **FR-SBT-21 과 직결**된다. 니모닉 키(`G`=Git)는
탭이 늘 때마다 키를 발명하고 충돌을 검사해야 한다. 번호는 서술자 배열의 인덱스에서
**자동으로 파생**되므로, 새 탭을 더할 때 단축키를 고민하지 않는다.

**FR-SBT-29** 등록된 탭 수를 넘는 번호 키는 아무 일도 하지 않는다. `Digit1`~`Digit9`
까지 지원한다.

**FR-SBT-30** 직행 키는 `SHORTCUT_DEFAULTS` 에 `sidebarTab1`~`sidebarTab{N}` 으로
등록되고 `SHORTCUT_LABELS` 에 짝을 갖는다. 라벨의 탭 이름 부분은 **등록된 서술자에서
파생**한다. **네 자리를 함께 고친다** — 기본값 맵·라벨 맵·설정 UI·영속. 하나만
고치면 설정 화면에서 사라진다.

#### 3.8.2 순회 키의 재해석

**FR-SBT-31** `Ctrl+Shift+]` / `Ctrl+Shift+[` (`windowNext`/`windowPrev`)는 **활성
탭의 목록을 순회**한다. 새 키를 만들지 않는다 (사용자 결정).

| 활성 탭 | 순회 대상 |
|---|---|
| `Windows` | 일반 창 — **현행 동작 그대로** |
| `Git` | 리포 목록 |

**FR-SBT-32** 리포 순회의 규약은 **창 순회와 같다** (사용자 결정: "현재의 window
구현이 기준"). 구체적으로:

- 목록 끝에서 감싼다 (wrap-around)
- 이동 결과가 곧 **활성 리포**가 되어 Git 창이 그 리포를 연다
- 사이드바의 활성 행 표시가 따라 움직인다
- 목록이 비었거나 1개면 아무 일도 하지 않는다

**FR-SBT-33** 재해석의 구현 자리는 **한 곳**이다. `_cycleWindow` 를 감싸는 디스패치가
활성 탭의 `cycle(dir)` 를 부른다 (FR-SBT-19). `Windows` 탭의 `cycle` 이 기존
`_cycleWindow` 이고, `Git` 탭의 `cycle` 이 리포 순회다. `SHORTCUT_LABELS` 의
`windowNext`/`windowPrev` 라벨은 `다음 창` → `다음 항목 (활성 탭 기준)` 으로 고친다 —
모드 의존이 되었으므로 설명이 따라가야 한다.

> **탭 자체를 넘기는 순회 키는 두지 않는다.** 직행 키가 있고 탭 수가 적다. 필요해지면
> 그때 연다. `Ctrl+Tab`/`Ctrl+Shift+Tab`(콘텐츠 영역의 탭 순회)은 사이드바와 무관하며
> 변경하지 않는다.

### 3.8.3 Close Git 버튼의 제거 (FR-SBT-34 ~ 36)

> 사용자 결정(2026-08-28): **"깃을 탭으로하면 close git 버튼 없애도 될듯."**

**FR-SBT-34** 상단바의 `Close Git` 버튼(`index.html` `#git-close`)을 **제거한다.**

근거는 그 버튼의 존재 이유가 사라진다는 것이다. FR-GIT-183 이 버튼을 둔 이유는
주석에 그대로 적혀 있다 — *"Git 창은 WINDOWS 목록에 없으므로 닫는 길을 여기 둔다."*
탭이 생기면 Git 창을 **떠나는 길**이 상시 존재하므로(FR-SBT-22), 떠나기 위해 닫을
이유가 없다.

**FR-SBT-35** 그러나 **떠나는 것과 닫는 것은 다르다.** 이 제거의 귀결을 분명히 한다.

| 동작 | 구 `Close Git` | 새 `Windows` 탭 |
|---|---|---|
| 직전 일반 창으로 이동 | ✓ | ✓ (FR-SBT-23) |
| Git 창 **파괴** | ✓ | ✗ |

즉 **Git 창을 파괴하는 UI 경로가 사라진다.** 한 번 연 Git 창은 워크스페이스에 계속
남는다. 이를 수용하는 근거:

- Git 창에는 PTY 가 없다. 살아 있어도 프로세스도 메모리 버퍼도 붙들지 않는다
- 창 목록에 없으므로(FR-GIT-182) 창 순회를 방해하지 않는다
- 탭으로 언제든 오갈 수 있으니 "치워 둔다" 는 동기 자체가 사라진다

**FR-SBT-36** `App.prototype._gitCloseWindow` **함수는 남긴다.** 버튼만 없애고 함수를
지우지 않는 이유가 둘이다.

1. 그 함수의 복귀 로직(`_lastPlainWindow` → 없으면 첫 일반 창)이 **FR-SBT-23/24 가
   요구하는 것과 정확히 같다.** 탭 활성화가 그것을 재사용한다 — 두 벌로 만들면
   한쪽만 고쳐진다
2. Git 창을 파괴해야 하는 경로가 나중에 필요해질 수 있고(마이그레이션·복구), 그때
   함수를 되살리는 것보다 남겨 두는 편이 싸다

> **FR-GIT-183 은 폐기, FR-GIT-183a 는 계승된다.** 183(버튼)은 사라지고,
> 183a(복귀 대상 = 직전 일반 창)는 FR-SBT-23 이 이어받는다. `GIT_UI_REVISION_SRS`
> 에 이 대응을 기록한다.

**영향받는 기존 검증**: `e2e/git-ui-revision.spec.ts` 의 **V73 · V73b** 가
`#git-close` 를 직접 누른다. 둘 다 개정 대상이다 (§4.1).

### 4.1 기존 e2e 영향 — 착수 전 필수 조사

**Git 패널이 처음부터 보인다고 가정하는 모든 스펙이 깨진다.** `Windows` 가 기본

영향 범위는 **착수 전에 이미 세었다** (2026-08-28, `e2e/` 전수).

```

| 셀렉터 | 출현 | 탭 전환 후 |
|---|---:|---|
| `#windows` | 50 | **영향 없음** — `Windows` 가 기본 탭이다 |
| `#git-repos` | 26 | 탭을 먼저 열어야 한다 |
| `#git-add-repo` | 10 | 〃 |
| `git-sec-title` | 2 | **선택자 자체가 사라진다** (FR-SBT-9) — 이 2건은 탭 라벨 검사로 바꾼다 |
| `sb-title` | 0 | — |

영향받는 스펙 파일은 **12개**다 — `git-sidebar` · `git-worktrees` · `git-repaint` ·

`focus` · `regression-focus` · `regression-pane-scroll` · `session`.

수정량이 큰 쪽(`#git-repos`·`#git-add-repo` = 36개 지점)은 **셀렉터가 그대로**이고

```

#### 4.1.1 `#git-close` 를 직접 누르는 스펙 (FR-SBT-34 연계)

위 셀렉터 조사와 **성질이 다르다** — 앞의 것들은 "한 줄이 앞에 붙을 뿐"이지만,
이쪽은 **누를 버튼이 사라지므로 시나리오 자체를 다시 써야** 한다.

| 스펙 | 현재 검증하는 것 | 개정 방향 |
|---|---|---|
| `git-ui-revision.spec.ts` **V73** (FR-GIT-183) | `#git-close` 클릭 → git 창 0개 → 리포 재클릭 시 재생성 | 버튼이 없으므로 **"창 파괴" 부분을 뺀다.** 남는 것은 "Git 창을 떠났다 돌아올 수 있다" 이며, 이는 V-SBT-21/28 이 이미 덮는다 → **삭제 후보** |
| `git-ui-revision.spec.ts` **V73b** (FR-GIT-183a) | `#git-close` 클릭 → **직전에 활성이던 일반 창**으로 복귀 | **살린다.** 검증하는 성질(복귀 대상 = `_lastPlainWindow`)이 FR-SBT-23 으로 계승되므로, 트리거만 `#git-close` 클릭 → `Windows` 탭 클릭으로 바꾼다. 창 3개 중 **가운데**에 서는 설정도 그대로 유효하다 |

V73b 의 개정본이 곧 **I6 의 회귀 방어**다 — 이 스펙 하나가 "원래 있던 윈도우로
돌아간다" 를 이름이 아니라 동작으로 고정한다.

## 6. 비목표 (Non-goals)

1. **Git 패널 내부 동작은 바꾸지 않는다.** 리포 행·핀·배지·컨텍스트 메뉴 전부 그대로.
2. **Git 창(전용 창)의 내부는 바꾸지 않는다.** FR-GIT-181/182 유효. 바뀌는 것은
   **진입 경로**와 **퇴출 경로**뿐이다 (§3.7·§3.8.3).
3. ~~세 번째 탭을 만들지 않는다.~~ **(철회, 2026-08-28)** → **지금 세 번째 탭을
   만들지는 않되, 셋째가 올 자리를 만든다** (§3.6). Run 시각화 진입은 여전히 상단바다.
4. **탭 순서·이름을 사용자 설정으로 열지 않는다.** 순서는 서술자 배열이 정한다.
5. ~~탭 전환 단축키를 추가하지 않는다.~~ **(철회, 2026-08-28)** → **넣는다** (§3.8).
   보류 근거였던 I5 의 키 충돌은 사용자 결정으로 해소됐다.
6. **탭 자체를 넘기는 순회 키는 두지 않는다.** 직행 키로 충분하다 (§3.8.2 말미).
7. **`Ctrl+Tab` 계열(콘텐츠 탭 순회)은 건드리지 않는다.**
8. **I7(worktree 관리 탭)은 범위 밖이다.** 그것은 Git 창 **안**의 탭이며 사이드바
   탭과 무관하다.

## 6.1 구현 순서

```
1. 탭 바 + 패널 래퍼 — index.html·style.css. id 전부 보존       (§3.1, FR-SBT-1~5)
2. 서술자 배열 + 전환 + 영속 + 렌더·스크롤 보존                  (§3.2·3.3·3.6)
3. ───── 여기까지 행위 보존 리팩터. 기존 e2e 전량이 통과해야 한다 ─────
4. 배지 (Git·Windows)                                            (§3.4, FR-SBT-12/13)
5. 콘텐츠 연동 — onActivate + _lastPlainWindow + 재진입 가드      (§3.7, I6 해소)
6. 역방향 추종 — 활성 창 → 탭                                    (FR-SBT-14/15)
7. 단축키 — 직행 키 + 순회 재해석 + SHORTCUT_LABELS + 설정 UI     (§3.8, I5 해소)
8. 모바일                                                        (§3.5)
```

3단계가 게이트다. **거기서 기존 `e2e/git-*.spec.ts` 가 통과하지 않으면 다음으로 가지
않는다** — 이후 단계는 동작을 바꾸므로, 회귀와 신규 변경이 섞이면 원인을 가를 수 없다.

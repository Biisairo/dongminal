# 1.4 OS 이음매: dmenv·dmlog·platform

## 목표

OS 의존 호출을 모으는 이음매(platform)와 환경변수·로그 기초를 옮긴다. 다섯 대상 플랫폼 모두에서 cargo check 가 통과해야 한다. dmlog 의 로그 형식(daemon.log 등에 찍히는 줄)은 Go slog 출력과 같아야 한다. platform 이 크면(약 4200줄) 하위 이슈로 나눠도 된다. 가장 많은 이슈가 이 crate 를 기다리므로, 공개 API 를 먼저 정해 진행 기록에 적고 조정자에게 알린다.

## 대상 Go 코드

- `internal/shared/dmenv`
- `internal/shared/dmlog`
- `internal/shared/platform`

프로덕션 코드 약 4739줄.

## 완료 조건

- 대상 Go 패키지의 관측 동작을 Rust crate 가 동등하게 제공한다 (FR-RSP-1·3)
- 관측 동작을 검증하는 Go 테스트가 Rust 테스트로 옮겨져 통과한다 (V-RSP-1)
- `cargo fmt --check`, `cargo clippy -D warnings`, 격리 실행 `cargo test` 통과 (NFR-RSP-4)

- 2026-11-23 **공개 API 안 (조정자 확인 대기).** Go 이름을 Rust 관례로 옮기고, 의미는 Go 와 같다.

  **결정 필요 D-1 — 입출력 모델.** 권장안: **platform 은 동기(std) API 만 낸다.**
  근거: ① Go 가 블로킹 I/O + goroutine 모델이다. ② Windows 의 AF_UNIX 는 std·tokio 모두 지원하지 않아 windows-sys 로 직접 구현해야 하고, 그 위에 tokio 를 얹으면 IOCP 등록이라는 위험한 코드가 생긴다. ③ PTY 읽기도 Go 와 같이 블로킹이다.
  비동기 소비자(웹서버·데몬)는 `tokio::task::spawn_blocking` 이나 전용 스레드로 감싼다. unix 에서는 `IpcStream::into_std()` 뒤 `tokio::net::UnixStream::from_std` 로 바꿀 수 있다.
  대안: IPC 만 tokio 타입을 낸다(unix 는 쉬움, Windows 는 IOCP 직접 구현 필요 — 비권장).

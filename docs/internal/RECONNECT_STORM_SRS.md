# SRS: 재연결 폭주와 헬퍼 설치의 비원자성 — IEEE 29148

## 1. 개요

### 1.1 목적

접수한 말은 둘이다.

> **"한번씩 연결이 끊긴다. tailscale 을 이용하여 원격접속하고있다. health 를
> 확인하면 서버는 잘 작동중이다. 서버를 재시작하면 다시 접속이 된다."**

> **"한번씩 나오는 아래 오류 원천 차단 — `/bin/sh:
> /Users/dykim/.dongminal/bin/dmctl: No such file or directory`"**

둘은 별개의 결함이지만 같은 성질을 공유한다 — **정상 경로에서는 보이지 않고,
드문 조건에서만 열리는 창(window)이 있다.** 이 문서는 그 두 창을 닫는다.

### 1.2 범위

**포함**
- 존재하지 않는 도구를 향한 WebSocket 재연결의 종단 처리
- 재연결 백오프가 리셋되는 조건
- 헬퍼 심링크·복사 설치의 원자성

**미포함**
- 로그 로테이션 (§6 비목표 #1)
- 죽은 탭의 자동 정리·삭제 (§6 비목표 #2)
- Tailscale·네트워크 계층의 설정 변경 (§6 비목표 #3)

## 2. 현재 상태 (실측으로 확인한 사실)

### 2.1 결함 ① — WS 재연결이 지연 0 의 무한 루프를 돈다

2026-08-30 10:04 관측. `/tmp/dongminal.log` 발췌:

```
10:04:46.120669 ws connected addr=100.117.248.111:62053 tool=01a04d3b-f9bc-7000-a92a-621da644fef1
10:04:46.121254 ws addr=100.117.248.111:62053: tool 01a04d3b-... not found (sent toolhub.OpExit)
10:04:46.248803 ws connected addr=100.117.248.111:62056 tool=01a04d3b-f9bc-7000-a92a-621da644fef1
10:04:46.288007 ws connected addr=100.117.248.111:62057 tool=01a04d3b-f9bc-7000-a92a-621da644fef1
```

`01a04d3b-…` 는 07:56:21 에 kill 된 도구다 (`~/.dongminal/daemon.log`). 브라우저는
그것을 8시간 뒤에도 초당 수십 회 부르고 있다.

**사슬**

| # | 자리 | 하는 일 |
|---|------|---------|
| 1 | `httpapi/handlers_ws.go:52` | 없는 도구 요청에 `OpExit` 을 보내고 소켓을 닫는다 |
| 2 | `ui/term-pane.js:317·377` | `OP.EXIT` 수신 시 **화면에 `── exited ──` 를 쓰는 것이 전부다**. 재연결을 멈추지 않는다 |
| 3 | `ui/term-pane.js:361` | `ws.onopen` 이 `this._retryDelay=0` 으로 백오프를 리셋한다 |
| 4 | `ui/term-pane.js:346~352` | `_reconnect()` 가 `delay=this._retryDelay` 로 `setTimeout` 한다 |

WS **업그레이드 자체는 성공**한다. 그러므로 매 사이클이 `onopen`(백오프 리셋) →
`OpExit` → `onclose` → `_scheduleReconnect` → `delay 0` 으로 돈다. 백오프 코드는
존재하지만 **매 사이클 리셋되어 한 번도 자라지 못한다.**

### 2.2 왜 원격만 끊기고 health 는 통과하는가

실측 (2026-08-30 10:05):

| 지표 | 값 |
|---|---|
| 로그 유입 | 285 줄/초 ≈ **95 WS 연결/초** |
| `netstat` TIME_WAIT (:58146) | **2,881** |
| 그중 Tailscale 피어(100.x) | 657 |
| macOS 임시 포트 범위 | 49152–65535 = **16,384** |
| `net.inet.tcp.msl` | 15000 ms → TIME_WAIT = 2×MSL = **30초** |

95 conn/s × 30 s ≈ 2,850 — 실측 2,881 과 일치한다. 죽은 패널 수와 브라우저 탭 수에
**선형으로 비례**하므로 16,384 를 넘기는 것은 시간 문제다. 그때:

- Tailscale 피어는 tailscaled 유저스페이스 netstack 을 거친다. 세션 테이블과 포트가
  먼저 말라 **새 TCP 연결을 열지 못한다** → 원격 접속이 끊긴다.
- `dmctl health` 는 `http://localhost:PORT/` 를 친다 (`ctl/cli/health.go:17`).
  **루프백은 tailscaled 를 거치지 않고** 단발 요청이라 통과한다 → "서버는 정상".
- 서버를 재시작하면 폭주 참여자가 리셋되고 TIME_WAIT 은 30초 안에 회수된다
  → **다시 접속된다.**

관측된 세 증상이 모두 이 하나로 설명된다.

**부수 피해**: `/tmp/dongminal.log` 가 4.17 GB (일 ~2.4 GB 증가). 서버 CPU 8.4%.

### 2.3 결함 ② — 헬퍼 설치가 원자적이지 않다

`shared/platform/paths.go:44` `posixPaths.LinkOrCopy`:

```go
if existing, err := os.Readlink(dst); err == nil && existing == src {
    return nil                        // 같은 곳이면 no-op
}
if err := os.Remove(dst); err != nil && !errors.Is(err, os.ErrNotExist) {
    return err                        // ← 여기서 dst 가 사라진다
}
if err := os.Symlink(src, dst); err == nil {   // ← 이 사이가 ENOENT 창
    return nil
}
return copyExecutable(src, dst)
```

주석이 이미 위험을 적어 두었다 — *"매 기동마다 지웠다 다시 거는 동안 그 경로를
부르는 도구가 있으면 그 호출이 실패한다."* 그래서 **같은 곳을 가리킬 때만**
no-op 로 막았다. 그러나 그것은 조건부 방어다. `src`(= `os.Executable()` 의
`EvalSymlinks` 결과) 가 링크 대상과 **다른 모든 기동**에서 창은 그대로 열린다:

- `dist/` 산출물로 기동 (`scripts/build.sh --os …`)
- worktree 안의 바이너리로 기동
- 격리 인스턴스(`--isolated`)가 실 HOME 을 가리킨 경우

`~/.dongminal/bin/dmctl` 은 Claude Code 훅 10종이 **도구 사용마다** 부르는 경로다
(`~/.dongminal/bin/agent-hooks/claude.json`). 창이 아무리 짧아도 호출 빈도가
높으면 언젠가 겹친다 — 그것이 "한번씩"의 정체다.

`copyExecutable`(같은 파일 88행)에도 같은 성질의 창이 둘 있다:
- `openExecutable` 이 `O_TRUNC` 로 열어 **내용을 먼저 비운다** — 그 사이 exec 는
  ENOEXEC 로 실패한다.
- 열기에 실패해 `os.Rename(dst, aside)` 로 밀어낸 뒤 다시 열기까지 **dst 가 없다**
  — Windows 경로의 ENOENT 창이다.

| 가설 | 판정 | 근거 |

| Tailscale serve/funnel 프록시의 타임아웃 | **기각** | 서버는 `0.0.0.0:58146` 직접 바인드 (`restart.log`) |

| 파일 디스크립터 고갈 | **기각** | 그렇다면 루프백 health 도 함께 실패한다 |

### 2.5 결함 ③ — 자가 치유가 있는데 그것을 부르는 구독이 죽는다

FR-RCS-1·3 을 넣고 서버를 재기동한 뒤(10:24:30, `?v=172` 서빙 확인) **폭주가
멎지 않았다.** 8초 측정에서 728 연결 — 로컬 Chrome 72/초, Tailscale 피어 19/초.

원인은 이 코드가 **이미 존재한다**는 사실에서 드러난다 —
`app-cmd.js` `_applyRemoteWorkspace`:

```js
// FR-ATL-7: 서버가 모르는 도구는 죽은 도구다.
for(const [id,p] of Array.from(this.tools.entries())){
  if(!ok.has(id)){ try{p.destroy()}catch{} this.tools.delete(id); ... }
}
```

`destroy()` 는 `_destroyed=true` 를 세우고 소켓을 닫는다. **이것이 돌았다면
폭주는 스스로 멎었어야 한다.** 실제로 워크스페이스에는 죽은 도구 참조가 하나도
없었다(탭 6개 전부 살아 있는 도구를 가리킨다) — 그런데 클라이언트는 없는 도구
5개를 부르고 있었다. 즉 **그 클라이언트만 옛 세계에 남아 있었다.**

그 경로를 부르는 유일한 계기가 SSE 의 `workspace_changed` 다. 그리고
`app-cmd.js:76` 은:

```js
if(++retryCount>maxRetries){console.error("[cmd] SSE max retries, giving up");return}
```

`maxRetries=20`, 백오프는 30초 상한. 즉 **약 8분의 연속 실패로 구독을 영구히
포기하고, 페이지를 다시 열기 전에는 복구 수단이 없다.** 측정 시점의 SSE 재접속
시도는 8초간 **0회**였고, `/api/focus` 의 소유자는 **1명**뿐이었다(붙어 있는
클라이언트는 셋).

**사슬이 닫힌다:**

```
네트워크 끊김/서버 재기동
  → SSE 20회 실패 → 영구 포기            (app-cmd.js:76)
  → workspace_changed 가 영영 오지 않음
  → 죽은 도구 정리가 영영 돌지 않음       (_applyRemoteWorkspace)
  → 없는 도구로 무한 재접속               (§2.1)
  → 임시 포트 고갈 → 원격 접속 끊김        (§2.2)
```

그리고 이 사슬은 **JS 수정만으로는 이미 열려 있는 탭에 닿지 않는다.** 배포
직후에도 옛 탭은 계속 폭주한다 — 그것이 §2.5 를 관측한 경위다.

동시에 이것은 사용자가 말한 증상 자체이기도 하다. SSE 가 죽으면 화면이 서버의
사실을 더는 따라가지 않는다 — 터미널이 살아 있어도 **"연결이 끊긴" 것으로
보인다.**

## 3. 요구사항

### 3.1 묶음 R — 재연결 폭주 차단 (FR-RCS)

**FR-RCS-1** `OP.EXIT` 을 받은 터미널 패널은 그 도구가 **영구히 사라졌다고
판정하고, 다시 연결하지 않는다.** 최초 연결 경로와 재연결 경로 **둘 다** 같은
판정을 한다.

**FR-RCS-2** FR-RCS-1 의 판정이 선 패널은 사용자에게 사실을 보인다 — 화면의
`── exited ──` 한 줄은 스크롤 밖으로 밀려 사라지므로, **오버레이로 남긴다.**
"재연결 중" 오버레이와 구별되어야 한다.

**FR-RCS-3** 재연결 백오프는 **연결이 유효했음이 증명된 뒤에만** 리셋한다.
`onopen` 만으로는 리셋하지 않는다. 판정 기준은 "연결이 열린 채로
`WS_HEALTHY_MS` 이상 유지되었다"이다.

> **근거**: FR-RCS-1 은 관측된 원인을 직접 막고, FR-RCS-3 은 **서버가 소켓을 즉시
> 닫는 모든 경로**에 대해 폭주를 구조적으로 불가능하게 만든다. 원인 하나만 막으면
> 다음번 다른 원인에서 같은 사고가 난다.

**FR-RCS-4** 백오프 상한은 유지하되(`10s`), 리셋되지 않은 백오프는 그 상한까지
반드시 자란다. 즉 최악의 경우에도 죽은 패널 하나가 만드는 부하는 **0.1 conn/s**
이하다.

**FR-RCS-5** 패널이 파괴되었거나(`_destroyed`) FR-RCS-1 의 판정이 섰으면 대기 중인
`setTimeout` 이 깨어나도 새 소켓을 열지 않는다.

**FR-RCS-6** 커맨드 SSE 구독은 **포기하지 않는다.** 백오프에 상한
(`SSE_RETRY_MAX_MS`)은 두되 재시도 횟수 상한은 두지 않는다. 또한 `online` 과
`visibilitychange`(보이게 됨)에 백오프를 기다리지 않고 즉시 되붙는다 — 원격
사용에서 끊김의 대부분이 잠·네트워크 전환이며, 그때 30초를 기다릴 이유가 없다.

**FR-RCS-6a** FR-RCS-6 의 즉시 재접속은 구독이 실제로 닫혔을 때만 한다
(`EventSource.readyState === CLOSED`). 살아 있는 구독을 중복으로 열면 단일
실행자 규약(FR-SXE-2)이 깨져 생성 명령이 두 번 실행된다.

> **근거**: §2.5. 이 구독이 죽으면 `_applyRemoteWorkspace` 의 자가 치유가 영영
> 돌지 않는다. FR-RCS-1·3 만으로는 **이미 그 상태에 빠진 클라이언트를 구할 수
> 없고**, 새로 빠지는 것도 막지 못한다.

### 3.3 묶음 S — 서버 측 봉쇄 (FR-RCS-9)

**FR-RCS-9** 없는 도구를 향한 WebSocket 요청이 **짧은 시간에 되풀이되면**
서버가 응답을 늦춘다. `MissRepeatWindow` 안에 같은 도구 id 로 다시 오면
`MissDelay` 만큼 기다린 뒤 `OpExit` 을 보낸다.

**FR-RCS-9a** **첫 번째 미스는 늦추지 않는다.** 규약을 지키는 클라이언트는 한 번에
판정을 끝내므로(FR-RCS-1) 지연을 겪을 이유가 없다. 지연은 "판정을 무시하고 다시
온" 쪽에만 걸린다.

**FR-RCS-9b** 지연 중 요청이 취소되면(`r.Context().Done()`) 즉시 그만둔다 —
서버 종료가 지연에 발목잡히지 않는다.

**FR-RCS-9c** 추적 상태는 무한히 자라지 않는다. `MissRepeatWindow` 를 지난
항목은 버린다.

**FR-RCS-9d** `OpExit` 은 그대로 보낸다. upgrade 를 거절하지 않는다 — 거절하면
규약을 지키는 클라이언트도 도구가 사라졌다는 사실을 알 수 없어 FR-RCS-1 의
판정이 서지 않는다.

> **근거**: §2.5 의 마지막 문단. **클라이언트 측 수정은 이미 열려 있는 탭에
> 영영 닿지 않는다.** 실측으로 옛 탭 둘이 수정 배포·서버 재기동 뒤에도 초당
> 217연결을 유지했고, 그것을 멈추는 수단은 그 브라우저를 사람이 찾아 닫는 것뿐이었다.
> 이것은 이번 결함에 국한된 사정이 아니라 **웹 클라이언트를 가진 모든 배포의
> 항구적 조건**이다. 그래서 서버에 봉쇄를 둔다.

### 3.2 묶음 A — 헬퍼 설치의 원자성 (FR-ATI)

**FR-ATI-1** 헬퍼 설치는 **목적 경로가 단 한 순간도 비지 않게** 수행한다. 같은
디렉터리의 임시 이름에 만든 뒤 `os.Rename` 으로 목적 경로를 덮는다 — POSIX
`rename(2)` 는 원자적이고, 같은 디렉터리이므로 파일시스템 경계를 넘지 않는다.

**FR-ATI-2** FR-ATI-1 은 심링크 경로와 복사 경로 **둘 다**에 적용한다.

**FR-ATI-3** 이미 같은 대상을 가리키는 심링크면 아무 것도 하지 않는다 (현행 유지).
FR-ATI-1 은 그 조건이 성립하지 않을 때의 안전망이다.

**FR-ATI-4** 임시 이름은 목적 이름과 충돌하지 않으며, 실패 시 남기지 않는다.
동시에 두 프로세스가 설치해도 서로의 임시 파일을 건드리지 않는다.

**FR-ATI-5** Windows 의 "실행 중이라 열 수 없다" 경로는 유지한다 — 다만 목적
경로를 비우는 순서가 아니라, **임시 파일을 먼저 완성한 뒤 덮는** 순서로 한다.

**FR-ATI-6** 덮어쓰기가 **일시적으로 거부되면 물러섰다 다시 시도한다.** 거부에
목적 경로를 지워서 답하지 않는다.

> **근거 (실측, 2026-08-30)**: Windows CI 에서 120회 재설치 중 **4회** dst 가
> 비었다. 원인은 원자화 자체가 아니라 그 **실패 경로**였다 — 갓 쓴 파일을
> 바이러스 검사·인덱서가 잠깐 열어 두면 `MoveFileEx` 가 거부되고, 최초 구현은
> 그때 곧바로 "dst 를 옆으로 밀어내고 다시 걸기"로 넘어가 그 사이에 창을 열었다.
> 밀어내기는 **실행 중인 파일을 갱신할 때만** 필요한 마지막 수단이다.
>
> POSIX 에서는 이 거부가 나지 않아 개발 호스트(darwin)에서는 보이지 않았다.
> CROSS_PLATFORM_SRS R-1 이 말하는 바로 그 구멍이다.

## 5. 설계 결정

**D-1 — 두 겹으로 막는다.** FR-RCS-1(원인)과 FR-RCS-3(일반 방어)을 함께 넣는다.
한 겹이면 다음 원인에서 같은 사고가 반복된다. §2.2 의 피해 규모가 두 겹의 비용을
정당화한다.

**D-2 — `WS_HEALTHY_MS = 3000`.** 서버가 소켓을 즉시 닫는 실패는 모두 1초 안에
끝난다(§2.1 실측: 열고 닫기까지 0.6 ms). 3초는 그 전부를 "유효하지 않은 연결"로
가르면서, 정상 사용 중의 짧은 네트워크 끊김은 유효로 인정하는 자리다.

**D-3 — 죽은 패널을 자동으로 지우지 않는다.** 사용자의 레이아웃을 서버 사정으로
말없이 바꾸지 않는다. 사실만 보이고(FR-RCS-2) 처분은 사용자가 한다.

**D-4 — 임시 이름은 `dst + ".tmp" + pid`.** 같은 디렉터리를 보장하고(rename 원자성의
전제), pid 로 동시 설치의 충돌을 피한다. 랜덤 대신 pid 를 쓰는 이유는 실패로 남은
잔여물을 사람이 추적할 수 있게 하기 위해서다.

**D-5 — ~~서버 쪽에는 손대지 않는다.~~ 철회 (2026-08-30).**
원래의 논지는 "폭주는 신호를 무시한 쪽의 결함이므로 서버의 rate limit 은
대증요법이다"였다. **원인**에 대해서는 여전히 맞다 — 그래서 FR-RCS-9 는 원인을
고치지 않고 FR-RCS-1·3·6 이 고친다.

철회하는 이유는 다른 축의 사실이다: **배포된 클라이언트 수정은 이미 열려 있는
탭에 닿지 않는다.** 그 탭은 스스로 회복하지 않고, 사람이 찾아 닫기 전까지
무한히 부하를 만든다. 이것은 이번 결함의 사정이 아니라 웹 클라이언트를 가진
배포의 항구적 조건이고, 서버만이 그 자리에 있을 수 있다. FR-RCS-9 는 원인의
대체물이 아니라 **격리(containment)** 다.

**D-6 — 봉쇄는 지연이지 거절이 아니다.** upgrade 를 거절(429)하면 옛
클라이언트의 백오프가 살아나 더 강력하지만(그쪽은 `onopen` 에서만 리셋하므로),
동시에 규약을 지키는 클라이언트도 `OpExit` 을 받지 못해 FR-RCS-1 의 판정이
서지 않는다. **바르게 행동하는 쪽을 망가뜨려 잘못 행동하는 쪽을 막지 않는다.**

**D-7 — 첫 미스는 늦추지 않는다 (FR-RCS-9a).** 늦추면 진짜로 종료된 도구의
"종료됨" 표시가 매번 `MissDelay` 만큼 늦다. 한 번에 판정을 끝내는 클라이언트는
두 번째 요청을 보내지 않으므로, 첫 미스를 면제해도 봉쇄 효과는 그대로다.

## 6.1 반복하면 안 되는 것

**"이 결함의 원인이 아니다"를 코드만 읽고 판정하지 않는다.** 비목표 #4 는 코드를
읽고 "SSE 는 UI 갱신용이고 재연결과 무관하다"고 판정한 것이었다. 실제로는
**재연결을 멈추는 유일한 경로(`_applyRemoteWorkspace` 의 `destroy()`)가 그
구독에 매달려 있었다.** 판정을 뒤집은 것은 추론이 아니라 수정 배포 뒤의
재측정이다 — 서버는 새 JS 를 내보내는데 폭주는 그대로였다는 사실 하나다.

**클라이언트 측 수정은 배포로 끝나지 않는다.** 열려 있던 탭은 옛 JS 를 계속
돌린다. 수정이 도달했는지는 **서버가 무엇을 내보내는가**가 아니라 **부하가
떨어졌는가**로 확인한다.

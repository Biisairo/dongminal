# 1.20 열린 파일 수 상한 (Rust 이전 회귀)

## 배경 (2026-11-25 사용자 보고·조정자 확인)

- Go 판에서는 없던 "too many open files" 가 Rust 판에서 생겼다. 사용자는 `ulimit -n 65536` 으로 임시 해결했다.
- 원인: Go 런타임은 1.19 부터 시작할 때 RLIMIT_NOFILE soft 를 hard 까지 올리고(darwin 은 kern.maxfilesperproc 로 자름), os/exec 자식에게는 원래 soft 값을 돌려준다. Rust 판은 이 일을 하지 않아 launchd 기본 soft 256 에 머문다(`launchctl limit maxfiles` = 256 unlimited).
- 운영 서버 실측(lsof, 시작 5분 뒤): 총 357 fd 중 DIR 161 + REG 160 이 한 worktree 에 대한 fswatch kqueue 감시(항목마다 fd, fsnotify 와 같은 설계, 디렉터리당 KQUEUE_ENTRIES_MAX 4096). 데몬은 64. 이미 256 을 넘는다.

## 목표 (사용자 결정 2026-11-25: A안 + 누수 확인 둘 다)

1. otterminal 바이너리(서버·데몬·otterctl 등 모든 진입점)가 시작할 때 Go 와 같게 soft 를 올린다: unix 에서 soft = hard, darwin 은 min(hard, sysctl kern.maxfilesperproc) (hard 가 RLIM_INFINITY 면 그 값). 실패하면 조용히 그대로 둔다(로그만, eprintln 금지).
2. 자식 프로세스(PTY 셸, git·외부 명령 — `otter_shared_platform::process`·`pty/posix.rs` 의 pre_exec 등)에는 시작 때의 원래 soft 를 돌려준다. Go 의 os/exec 동작과 같게.
3. 격리 인스턴스에서 fd 누수 시험: 편집기 루트 열기/닫기, 터미널 열기/닫기, git 창 열기/닫기, 채널 재연결을 여러 번 되풀이한 뒤 fd 수가 처음 수준으로 돌아오는지(종류별) 잰다. 누수가 있으면 원인과 함께 보고(고치는 것은 따로 판단).

## 완료 조건

- 시험 먼저(RED): 상한 올리기 함수 단위 시험(hard 가 무한·유한·darwin 자르기), 자식이 원래 soft 를 받는지(자식에서 `ulimit -n` 또는 getrlimit 결과) 시험.
- 바꾼 crate 의 lib·fmt·clippy -D warnings, 관련 게이트. 누수 시험은 측정 스크립트 또는 e2e 하나. 전체 시험 금지.

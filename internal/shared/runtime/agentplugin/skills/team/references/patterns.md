# 팀 패턴 카탈로그

팀을 **어떤 모양으로 묶을 것인가**를 고르는 문서. 어떻게 띄우고 정리하는가는
`SKILL.md` 의 워크플로우가 표준이고, 여기 있는 것은 그 위에 올리는 **토폴로지**뿐이다.

패턴 고르기는 `SKILL.md` 의 선택 결정표에서 시작한다. 여기서는 고른 뒤에 읽는다.

모든 패턴이 같은 6절을 갖는다: **언제 쓰나 / 언제 쓰지 않나 / 멤버 구성 / 토폴로지 /
종료 조건 / dmctl 시퀀스**.

---

## 멤버끼리 직접 말한다

아래 8패턴 중 6개는 **멤버가 멤버에게 직접 말하는 것**이 패턴의 본체다. 그것은
금지가 아니라 이미 되는 일이다 — `dmctl msg` 에는 발신자·수신자가 조정자여야 한다는
제약이 없다. 다만 두 가지를 알아야 쓸 수 있다.

**① 상대를 어떻게 지목하는가.** 프리앰블은 `run member` 시점에 조립되므로 **그때 아직
없는 동료**를 담을 수 없다 — 첫 멤버의 프리앰블에는 동료가 0명이다. 그래서 명부는
박아 넣지 않고 멤버가 직접 조회한다:

```bash
dmctl run peers
# role=비평가  member=<member uuid>  to=<보낼 값>  state=working  headless=false
```

`to=` 를 그대로 `dmctl msg --to` 에 넣는다. `member=` 는 기록에서의 정체이므로
조정자에게 보고할 때 쓴다. 명부는 승계·이탈로 변하니 **말을 걸기 직전에** 부른다.

**답장은 명부를 다시 부를 필요가 없다** — 받은 엔벨로프 헤더의
`from=<라벨> (<uuid>)` 에서 괄호 안 uuid 를 `--to` 에 그대로 쓴다. 명부는 **먼저**
말을 걸 때 필요한 것이다.

**② 언제부터 되는가.** 기동 시점에는 동료가 아직 없다. 그래서 brief 에는 혼자
시작할 수 있는 일만 적고, **Barrier(전원 ready) 이후** 조정자의 Kickoff 가 P2P 를
연다. 순서의 문제이지 금지가 아니다.

조정자는 P2P 를 연 뒤에도 눈을 감지 않는다 — 멤버 간 메시지는 Run 기록에 남고
`dmctl run status` 에서 보인다. 그것이 P2P 를 안전하게 열 수 있는 근거다.

**P2P 패턴에는 세 가지가 반드시 있어야 한다** — 첫 발신자·왕복 상한·교착 시 탈출로.
셋 중 하나라도 없으면 무한 왕복이거나 상호 대기로 끝난다. 아래 각 패턴의 "4. 토폴로지"
가 그것을 명시한다. 새 패턴을 만들 때도 이 셋을 먼저 정하라.

## 1. supervisor-worker

**1. 언제 쓰나** — 같은 종류의 독립적인 서브태스크가 N개 있고, 서로 결과를 보지
않아도 되는 일.

**2. 언제 쓰지 않나** — 서브태스크가 서로의 산출물을 필요로 할 때. 그러면 조정자가
중계자가 되어 모든 왕복을 자기 컨텍스트로 통과시키게 되고, 조정자가 먼저 터진다.
그 경우는 pipeline 이나 blackboard 다.

**3. 멤버 구성** — 조정자 1 + worker N. worker 는 서로를 모른다. 최소 2명(N≥2).

**4. 토폴로지** — 성형. P2P 없음.

```
        조정자
      /   |   \
    w1   w2   w3        (worker 간 간선 없음)
```

**5. 종료 조건** — 모든 worker 가 `dmctl run report` 를 한 번씩 마쳤을 때. 판정은
`dmctl run status` 의 `outcome` 이지 조정자의 인상이 아니다.

**6. dmctl 시퀀스**

```bash
RUN=$(dmctl run start --objective "저장소 3개 영역 조사" --window "$WIN" \
      | sed -n 's/^run=\([^ ]*\).*/\1/p')

for pair in "핸들러:$T1" "저장소:$T2" "CLI:$T3"; do
  role=${pair%%:*}; tab=${pair##*:}
  dmctl run member --run "$RUN" --role "$role" --agent claude --at "$tab" --brief - <<B
$role 영역만 조사한다. 다른 영역은 보지 않는다. 끝나면 곧바로 보고한다.
B
done
# 이후 SKILL.md 의 4~6단계(병렬 기동 → Barrier → Kickoff)를 그대로 따른다.
```

## 2. pipeline

**1. 언제 쓰나** — 단계에 순서가 있고, 앞 단계의 산출물이 뒤 단계의 입력인 일.
분석 → 설계 → 구현 → 검증.

**2. 언제 쓰지 않나** — 단계가 사실은 독립일 때. 순서를 강제하면 병렬로 끝날 일이
직렬이 되어 가장 느린 단계가 전체 시간이 된다.

**3. 멤버 구성** — 단계당 1명, 최소 2명. 단계 하나에 두 관심사를 몰지 않는다.

**4. 토폴로지** — 인접 단계끼리 직접 연결. 조정자는 양 끝에만 있다.

```
    조정자 ──▶ A ──▶ B ──▶ C ──▶ 조정자
                └──── 막히면 조정자로 ────┘
```

- **첫 발신자**: 조정자가 Kickoff 를 A 에게만 보낸다. B·C 는 대기 상태로 뜬다
- **왕복 상한**: 인접 단계당 **1회 전달 + 되묻기 1회**. 되묻기가 두 번 필요하면
  단계 분할이 잘못된 것이므로 조정자에게 보고하고 멈춘다
- **교착 시 탈출로**: 다음 단계가 정한 상한(권장 10분) 안에 응답하지 않으면 기다림을
  접고 조정자에게 보고한다. 앞 단계는 이미 보고를 마쳤을 수 있으므로 뒤 단계를 대신
  깨우려 하지 않는다

**5. 종료 조건** — 마지막 단계가 조정자에게 최종 산출물을 보내고 전원이 보고했을 때.
중간 단계는 자기 산출물을 넘긴 직후 보고한다 — 파이프라인 끝까지 살아 있을 필요가 없다.

**6. dmctl 시퀀스**

```bash
dmctl run member --run "$RUN" --role "분석" --agent claude --at "$T1" --brief - <<'B'
입력 코드를 읽고 문제를 목록화한다. 목록이 서면 `dmctl run peers` 로 역할이 "설계" 인
동료를 찾아 그 to= 로 보낸다. 보낸 직후 보고한다. 설계의 응답을 기다리지 않는다.
B

dmctl run member --run "$RUN" --role "설계" --agent claude --at "$T2" --brief - <<'B'
분석에게서 문제 목록이 도착하기를 기다린다. 먼저 말을 걸지 않는다. 목록을 받으면
설계안을 만들어 역할이 "구현" 인 동료에게 보내고 보고한다.
B

# Kickoff 는 **첫 단계에만** 나간다. 뒤 단계는 앞 단계의 메시지로 깨어난다.
dmctl msg --to "$T1" - <<'MSG'
[TEAM-KICKOFF task-id=pipe-1]
status: START
동료가 전원 준비됐다. `dmctl run peers` 로 확인하고 시작하라.
MSG
```

## 3. debate (GAN)

**1. 언제 쓰나** — 정답이 없고 **더 나은 것**을 찾는 일. 글·설계·리뷰처럼 품질이
대립에서 나오는 경우.

**2. 언제 쓰지 않나** — 정답이 하나인 일. 사실 확인이나 계산에 비평가를 붙이면
합의를 위한 왕복만 늘고 답은 그대로다.

**3. 멤버 구성** — 생성자 1 + 비평가 1 (+ 심판 1). 최소 2명. 비평가를 여럿 두려면
red-team 이나 map-reduce 쪽이 맞다.

**4. 토폴로지** — 생성자와 비평가의 왕복이 곧 패턴이다.

```
    조정자 ──▶ 생성자 ◀──▶ 비평가
                  └──▶ 조정자 (최종본)
```

- **첫 발신자**: 생성자. 초안이 없으면 비평할 것이 없다. 비평가는 초안이 도착할
  때까지 먼저 말하지 않는다
- **왕복 상한**: **라운드 3회**를 넘기지 않는다. 종료 판정 주체는 **생성자**다 —
  비평가는 언제나 더 지적할 것을 찾아내므로 비평가에게 종료를 맡기면 끝나지 않는다.
  심판을 두면 심판이 판정 주체가 된다
- **교착 시 탈출로**: 상대가 상한(권장 10분) 안에 응답하지 않으면 현재까지의 최선을
  들고 조정자에게 보고한다. 상대를 재촉하는 메시지를 반복 송신하지 않는다

**5. 종료 조건** — 라운드 3회를 마쳤거나, 생성자가 "더 고칠 것이 없다"고 판정했을 때.
둘 중 먼저 오는 쪽이다. 생성자가 최종본을 조정자에게 보내고 전원이 보고한다.

**6. dmctl 시퀀스**

```bash
dmctl run member --run "$RUN" --role "생성자" --agent claude --at "$T1" --model opus --brief - <<'B'
주제에 대한 초안을 쓴다. 초안이 서면 `dmctl run peers` 로 "비평가" 를 찾아 보낸다.
비평을 받으면 개정한다. **라운드는 최대 3회**이고 종료 판정은 네가 한다. 마지막
개정본만 조정자에게 보내고 보고한다.
B

dmctl run member --run "$RUN" --role "비평가" --agent claude --at "$T2" --brief - <<'B'
생성자의 초안이 도착할 때까지 기다린다. 먼저 말을 걸지 않는다. 받으면 비평만 하고
(고쳐 쓰지 않는다) 생성자에게 돌려준다. 생성자가 종료를 알리면 보고한다.
B

dmctl msg --to "$T1" - <<'MSG'
[TEAM-KICKOFF task-id=debate-1]
status: START
동료가 전원 준비됐다. `dmctl run peers` 로 비평가를 확인하고 초안부터 써라.
MSG
```

## 4. reflection

**1. 언제 쓰나** — 혼자서도 되는 일이지만 **스스로에 대한 검토**가 품질을 가르는
경우. 자기 출력을 자기가 검토하면 같은 맹점이 반복된다.

**2. 언제 쓰지 않나** — 검토 기준이 외부에 있는 일(테스트·린터·컴파일러). 그건
사람이나 팀이 아니라 도구가 판정한다.

**3. 멤버 구성** — 생성자 1 + 검토자 1의 2인 루프. debate 와 다른 점은 **검토자가
대립자가 아니라는 것**이다. 같은 목표를 공유하며 결함만 짚는다.

**4. 토폴로지** — 2인 루프.

```
    조정자 ──▶ 생성자 ◀──▶ 검토자 ──▶ 조정자 (통과 판정)
```

- **첫 발신자**: 생성자. 산출물이 먼저다
- **왕복 상한**: **2라운드.** 종료 판정 주체는 **검토자**다 — "통과" 를 검토자가
  선언한다. 2라운드 안에 통과가 나오지 않으면 그 사실을 조정자에게 보고하고 멈춘다
- **교착 시 탈출로**: 상대 무응답이 상한을 넘으면 조정자에게 보고한다. 생성자가
  검토자 없이 자기 검토로 대체하지 않는다 — 그러면 패턴 자체가 사라진다

**5. 종료 조건** — 검토자가 통과를 선언했거나 2라운드를 소진했을 때.

**6. dmctl 시퀀스**

```bash
dmctl run member --run "$RUN" --role "생성자" --agent claude --at "$T1" --brief - <<'B'
<산출물>을 만든다. 다 되면 `dmctl run peers` 로 "검토자" 를 찾아 보내고, 지적을
받으면 고쳐서 다시 보낸다. 통과 선언을 받으면 보고한다. 최대 2라운드.
B

dmctl run member --run "$RUN" --role "검토자" --agent claude --at "$T2" --brief - <<'B'
생성자의 산출물이 올 때까지 기다린다. 결함만 짚어 돌려보낸다. 통과 판정은 네가
하고, 판정하면 그 사실을 생성자와 조정자 양쪽에 알린 뒤 보고한다.
B
```

## 5. map-reduce fan-out

**1. 언제 쓰나** — 넓게 찾아서 하나로 모으는 일. 리서치, 코드베이스 조사, 후보 비교.

**2. 언제 쓰지 않나** — 탐색 범위가 좁아 한 명이 다 볼 수 있을 때. 나누는 비용이
종합 비용보다 커진다.

**3. 멤버 구성** — 팬아웃 N (헤드리스 권장) + 종합자 1. 최소 3명(N≥2 + 종합자).
팬아웃 멤버는 화면에 붙일 이유가 없다 — 읽을 것은 결과뿐이다.

**4. 토폴로지** — 성형 + 종합자에게 1방향. 팬아웃끼리는 말하지 않는다.

```
        조정자
      /   |   \
    f1   f2   f3
      \   |   /
       ▼  ▼  ▼
        종합자 ──▶ 조정자
```

팬아웃끼리 말하게 하면 서로의 관점에 물들어 **독립성이 사라진다.** 넓게 찾는 것이
목적인데 답이 수렴해 버리면 패턴이 무너진다.

**5. 종료 조건** — 팬아웃 전원의 결과가 종합자에게 도착하고, 종합자가 종합본을
조정자에게 보냈을 때. 팬아웃 하나가 실패해도 종합자는 **남은 것으로 종합한다** —
전원을 기다리다 멈추지 않는다.

**6. dmctl 시퀀스**

```bash
for topic in "선행 연구" "경쟁 구현" "실패 사례"; do
  dmctl run member --run "$RUN" --role "$topic" --agent claude --at "$(next_tab)" --brief - <<B
$topic 만 조사한다. 다른 팬아웃 동료와 상의하지 않는다 — 독립성이 이 패턴의 전부다.
결과가 서면 \`dmctl run peers\` 로 "종합자" 를 찾아 보내고 보고한다.
B
done

dmctl run member --run "$RUN" --role "종합자" --agent claude --at "$TS" --model opus --brief - <<'B'
팬아웃 결과가 도착하기를 기다린다. 먼저 말을 걸지 않는다. 상한(20분) 안에 오지 않은
것은 빼고 남은 것으로 종합한 뒤, 빠진 주제를 명시해 조정자에게 보내고 보고한다.
B
```

## 6. blackboard

**1. 언제 쓰나** — 공유 산출물 하나를 여럿이 **점진적으로 쌓는** 일. 설계 문서,
체크리스트, 마이그레이션 계획.

**2. 언제 쓰지 않나** — 격리(worktree)가 필요한 일. 칠판은 **파일 공유가 전제**라
격리하면 각자 다른 칠판에 쓰게 된다. `--isolation` 은 `none` 이어야 한다.

**3. 멤버 구성** — 멤버 N + 공유 파일 규약 하나. 최소 2명. 파일 경로와 **각자 쓸
구역**을 조정자가 미리 정한다.

**4. 토폴로지** — 파일이 중심, 알림만 P2P.

```
    m1 ──┐          ┌──▶ m2
         ├── 칠판 파일 ──┤        (본문은 파일로, "썼다" 만 메시지로)
    m3 ──┘          └──▶ ...
```

- **첫 발신자**: 조정자가 Kickoff 에서 칠판 경로와 구역을 알린다. 이후 **먼저 쓴
  사람이 먼저 알린다**
- **왕복 상한**: 알림은 **자기 구역을 갱신한 직후 1회**. 알림에 대한 답신은 하지
  않는다 — 답신하면 N² 로 늘어난다
- **교착 시 탈출로**: 남의 구역이 비어 있어 진행할 수 없으면 **기다리지 말고**
  조정자에게 보고한다. 상대에게 재촉을 보내지 않는다

**5. 종료 조건** — 모든 구역이 채워졌을 때. 판정 주체는 조정자다 — 칠판을 읽어
확인하고 닫는다.

**6. dmctl 시퀀스**

```bash
BOARD=/tmp/board-$$.md
: > "$BOARD"

dmctl run member --run "$RUN" --role "설계" --agent claude --at "$T1" --brief - <<B
$BOARD 의 "## 설계" 절만 쓴다. 남의 절은 읽기만 하고 고치지 않는다. 다 쓰면
\`dmctl run peers\` 로 전원에게 "설계 절 갱신" 한 줄만 보낸다. 본문은 보내지 마라 —
칠판에 있다.
B
```

## 7. hierarchical

**1. 언제 쓰나** — 서브태스크 **하나가 혼자 팀만큼 큰** 일. 조정자 한 명이 말단까지
관리하면 조정자의 컨텍스트가 먼저 찬다.

**2. 언제 쓰지 않나** — 서브태스크가 한 명으로 감당되는 크기일 때. 계층을 만들면
전달 단계마다 의도가 마모된다. 계층은 **깊이 2까지**만 쓴다.

**3. 멤버 구성** — 조정자 1 + 중간 조정자 M + 말단 N. 중간 조정자는 자기 하위 팀에
대해 조정자 역할을 그대로 수행한다(자기 Run 을 연다).

**4. 토폴로지** — 계층 내에서만 직접 통신. 층을 건너뛰지 않는다.

```
            조정자
           /      \
      중간A        중간B
      /   \        /   \
    n1    n2     n3    n4      (n1 과 n3 은 말하지 않는다)
```

- **첫 발신자**: 위에서 아래로. 조정자 → 중간 조정자 → 말단. 말단이 먼저 위로
  말을 거는 것은 보고와 질문뿐이다
- **왕복 상한**: 층을 **건너뛴 메시지는 보내지 않는다.** 말단이 최상위 조정자에게
  직접 보고하면 중간 조정자가 자기 팀의 상태를 모르게 된다
- **교착 시 탈출로**: 중간 조정자가 응답하지 않으면 말단은 **자기 층에서 할 수 있는
  것까지 하고 보고**한다. 최상위로 직접 올라가지 않는다 — 그것은 중간 조정자가
  살아 있는지 판정할 수 있는 최상위 조정자의 몫이다

**5. 종료 조건** — 중간 조정자가 자기 하위 Run 을 닫고 상위에 보고했을 때. 상위
Run 은 중간 조정자들의 보고로 판정한다 — 말단의 보고를 직접 세지 않는다.

**6. dmctl 시퀀스**

```bash
dmctl run member --run "$RUN" --role "중간 조정자 A" --agent claude --at "$T1" --model opus --brief - <<'B'
이 영역은 혼자 하기에 크다. 너는 team 스킬로 **자기 팀을 만든다**:
`dmctl run start` 부터 `dmctl run close` 까지 네가 조정자다. 하위 팀이 끝나면
그 결과를 종합해 한 번 보고한다. 하위 멤버가 상위 조정자에게 직접 보고하게 하지 마라.
B
```

## 8. red-team

**1. 언제 쓰나** — 만든 것을 **깨뜨려 봐야** 하는 일. 보안 점검, 견고성 검증,
장애 시나리오.

**2. 언제 쓰지 않나** — 아직 만들 것이 없을 때. 설계 단계의 red-team 은 상상 속
결함을 만들어 낸다. 구현물이 있어야 공격이 성립한다.

**3. 멤버 구성** — 구현자 1 + 공격자 1 + 심판 1의 3자. 심판을 빼지 마라 — 구현자와
공격자만 두면 "그건 실제 위협이 아니다" 로 끝나는 논쟁이 남는다.

**4. 토폴로지** — 3자. 판정이 한 곳으로 모인다.

```
    구현자 ◀──▶ 공격자
        \        /
         ▼      ▼
           심판 ──▶ 조정자
```

- **첫 발신자**: 구현자. 공격 대상(코드·경로·전제)을 공격자에게 넘기는 것으로 시작
- **왕복 상한**: **공격 라운드 2회.** 종료 판정 주체는 **심판**이다. 공격자는 언제나
  다음 공격을 생각해 낼 수 있으므로 공격자에게 종료를 맡기면 끝나지 않는다
- **교착 시 탈출로**: 구현자와 공격자가 유효성을 두고 합의하지 못하면 **서로 설득하지
  말고 심판에게 넘긴다.** 심판이 무응답이면 양쪽 주장을 그대로 조정자에게 보고한다

**5. 종료 조건** — 심판이 각 공격에 유효/무효 판정을 내리고 그 목록을 조정자에게
보냈을 때. "공격이 다 막혔다" 는 종료 조건이 아니다 — 판정이 종료 조건이다.

**6. dmctl 시퀀스**

```bash
dmctl run member --run "$RUN" --role "공격자" --agent claude --at "$T2" --brief - <<'B'
구현자에게서 대상이 도착할 때까지 기다린다. 받으면 결함을 찾아 **재현 절차와 함께**
심판에게 보낸다. 구현자와 유효성을 두고 다투지 마라 — 판정은 심판이 한다. 최대 2라운드.
B

dmctl run member --run "$RUN" --role "심판" --agent claude --at "$T3" --brief - <<'B'
공격자의 보고를 받아 유효/무효를 판정한다. 필요하면 `dmctl run peers` 로 구현자에게
사실 확인을 요청한다. 2라운드가 끝나면 판정 목록을 조정자에게 보내고 보고한다.
종료 판정은 네가 한다.
B
```

## 패턴을 고르고 나서

- 멤버 하나에 두 패턴의 역할을 겸하게 하지 않는다 (**1멤버 1역할 1관심사**)
- 패턴을 섞으려면 Run 을 나눠라. 한 Run 안에서 pipeline 과 debate 를 겹치면 누가
  누구를 기다리는지 아무도 모른다
- 서버는 패턴을 모른다. `--pattern` 같은 플래그는 없고, 토폴로지는 brief 와 Kickoff 로
  만들어진다. 그래서 위의 세 항목(첫 발신자·왕복 상한·탈출로)을 **brief 에 적어야**
  실제로 성립한다

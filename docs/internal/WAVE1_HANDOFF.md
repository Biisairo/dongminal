> 테스트만 고쳤으면 증상만 사라지고, WS-7 이 `main.go` 에 배선하는 순간 프로덕션에
> 같은 레이스가 섰다.
>
> **`OnOutput`·`OnExit` 는 아직 맨 대입이다** (`main.go`). 같은 종류의 노출이며 이
> 묶음 밖이라 두었다 — `SetOnForeground` 주석이 그것을 가리킨다.

### 3.2 테스트 플레이크 2건 — 원인은 하나였다

전량 병렬 실행에서만 8~10회 중 1회 드러났다. **`ToolManager.Create`/`Delete` 가
띄우는 `go m.SaveAll()`** 이 원인이고, `SaveAll` 은 `dirty` 를 내리지 않으므로
**이미 뜬 goroutine 은 반드시 쓴다** — 동기 `SaveAll` 을 더 불러도 무력화되지 않는다.

두 가지로 나타났다:

1. **teardown 경합** — 늦은 쓰기가 `t.TempDir()` 정리보다 늦으면
   `directory not empty` 로 실패한다. **본문이 통과한 뒤에 테스트가 깨진다**
2. **단정 실패** — 늦은 쓰기가 테스트의 동기 저장을 덮거나, `os.WriteFile` 이
   원자적이지 않아 재적재가 부분 파일을 읽는다

`httpapi/background_test.go` 와 `daemon/ipc/paned_test.go` 양쪽에 **결과물의 안정으로
동기화하는 배수 헬퍼**를 세웠다(디렉터리 목록이 두 번 연속 같으면 밀린 쓰기가 없다).
저장 **전에** 배수하고, `t.TempDir()` **뒤에** Cleanup 을 등록해 LIFO 로 정리보다 먼저
돌게 했다.

> **한쪽만 고치면 다른 쪽이 남는다.** 원인은 `toolhub` 의 fire-and-forget 저장이고
> 테스트가 그것을 기다릴 수단이 없다는 것이다. 근본 해결은 `SaveAll` 을 기다릴 수
> 있게 만드는 것이지만 그것은 프로덕션 변경이라 이번 범위 밖으로 두었다.

## 5. 반복하면 안 되는 것 — 이번 세션에서 실제로 겪은 것

### 5.1 브리핑은 기억이 아니라 디스크에서 인용한다 (사고 3회)

조정자가 SRS 를 다시 읽지 않고 **덮어써진 초안**의 FR 번호·필드·동작 방향을
브리핑해 **세 워크스트림이 연달아 막혔다.** 셋 다 담당자가 멈추고 물어서 잡혔다.

가장 위험했던 것은 번호가 아니라 **방향이 반대인 지시**였다 — "재시작 후 도구 없으면
`lost`" 라고 썼는데 V-HLM-4 의 기대값은 **"`lost` 가 아님"** 이었다.

**절차**: `PARALLEL_DELIVERY_PLAN` §4.2.2. 요지는 ① 묶음 절을 `sed` 로 통째 출력
② FR 번호 **상한을 명시** ③ **검증 표의 각 항목이 어느 지시와 짝인지 확인** — 짝
없는 검증 항목이 곧 누락이다 ④ 브리핑에 "SRS 와 어긋나면 구현하지 말고 보고하라".

### 5.2 대칭적 추종은 수렴하지 않는다 (뒤집기 10회)

`ContextLevel` 단조 여부 하나가 **열 번** 뒤집혔다. 논거 부족이 아니었다 —
**담당자는 문서를 보고 코드를 고치고, 조정자는 코드를 보고 문서를 고쳤다.** 각자가
상대의 몇 분 전 상태를 보고 자기 쪽을 고치면 영원히 쫓는다.

**무엇이 실제로 끝냈나** — 담당자가 만든 프로토콜 하나였다:

> 문서를 읽는 즉시 맞추지 않는다. **mtime 이 3분 이상 변하지 않았을 때** 비로소 읽고,
> 한 번 맞추고, 끝낸다.

열 번의 실패와 열한 번째 성공의 차이는 **논거도 소유권도 성실성도 아니었다.**
`"읽는 즉시 맞추기"` 를 `"안정을 확인한 뒤 맞추기"` 로 바꾼 것 하나였다 — 읽은 값이
반영을 끝내기 전에 낡는다는 것이 원인의 전부였다.

`PARALLEL_DELIVERY_PLAN` §4.2.3 에 그 단계를 넣었다. **다른 워크스트림도 같은 함정을
밟으므로 반드시 읽혀라.**

> **그리고 그 항목의 동작 차이는 거의 없었다.** 갈리는 경우가 "압축 없이 transcript
> 축소" 하나뿐인데 그것은 SRS 가 이미 미해결 사각지대로 표시한 자리다.
> **"어느 쪽이 옳은가" 보다 "이 차이가 언제 드러나는가" 를 먼저 물었어야 했다.**

### 5.3 게이트는 모두가 손을 뗀 뒤에

작업 중인 워크스트림이 하나라도 있으면 `go test ./...` 결과가 **누구의 상태도
대표하지 않는다.** 미사용 import 하나로 패키지 5개가 `[build failed]` 가 되고,
회차마다 다른 워크스트림의 테스트가 깨진다.

### 5.4 플레이크는 원인을 특정하기 전에 넘어가지 않는다

두 건 다 겪었다.

- `TestToolManager_DeleteDetachedToolDoesNotPanic` — 원인은 제품이 아니라 **테스트가
  `go m.SaveAll()` 의 비동기 쓰기를 안 기다린 것**(`TempDir cleanup: directory not
  empty`). 쓰기 결과물의 등장으로 동기화해 닫았다
- `httpapi` 전량 1회 실패 — `fakeWorkIndex` 데이터 레이스. **`-race` 경고에 머물지
  않고 실제 실패를 냈다**

> **2026-08-28 웨이브 마감에서 같은 계열을 두 건 더 겪었고, 반복 횟수가 판정을
> 갈랐다.** 전량 병렬에서 **8~12회 중 1회**만 드러나는 것들이라 3회로는 통과처럼
> 보인다. 한쪽(teardown 경합)을 닫자 **그 밑에 숨어 있던 단정 실패**가 드러났다 —
> 첫 증상을 없앤 것으로 끝내지 마라. 상세는 §3.2.

### 5.5 서버 완성 ≠ 기능 완성

`--keep-tools`·고아 렌더가 **서버 테스트 전부 통과 + 사용자는 못 씀** 상태였다.
렌더가 CLI 파일에 있어 서버 테스트로는 안 잡힌다. **CLI 표면을 따로 검사하라.**

### 5.6 한쪽만 잠근 뮤텍스는 잠그지 않은 것이다 (2026-08-28)

`toolclient` 의 `fg` 수신 경로는 `pc.mu` 를 쥐고 콜백을 **읽었다.** 잠금이 보이므로
지난 세션은 이것을 "프로덕션은 옳고 테스트가 결함" 으로 분류했다. **틀렸다** — 쓰는
쪽이 맨 대입이라 happens-before 가 성립하지 않는다.

**그 오분류의 대가는 테스트 실패가 아니었을 것이다.** 테스트만 고쳤으면 증상은
사라지고, 그 다음 워크스트림이 `main.go` 에 콜백을 배선하는 순간 **프로덕션에 같은
레이스가 섰다.** 실제로 그 배선이 이번 웨이브에 들어왔다.

**잠금을 봤으면 반대쪽도 봐라.** 읽기에만 잠금이 있으면 그것은 잠금이 아니라
**잠금처럼 보이는 것**이다.

### 5.7 담당자가 조정자보다 나은 길을 찾는다 (2026-08-28)

WS-7 담당에게 판정으로 파일 두 개의 소유권을 **열어 줬는데 둘 다 쓰지 않았다.**
`workspace/manager.go` 대신 로컬 타입으로, `app.js` init 대신 `es.onopen` 의 기존
복구 규약으로 갔다(후자는 재연결까지 덮여 더 낫다).

> **소유권을 여는 판정은 상한이지 지시가 아니다.** "열어 줬으니 써라" 가 아니라
> "필요하면 써도 된다" 로 전달해야 담당자가 더 좁은 길을 찾는다.
>
> 반대 방향도 있었다 — 같은 담당자가 `WsTab` 에 필드를 **둘** 넣어야 한다고 판정을
> 정정해 왔다(`NameSource` 외에 `Type` 도 필요했다. 없으면 이름이 `Shell` 인 editor
> 탭이 auto 로 오판된다). 조정자가 못 본 것이다.

## 6.5 담당자가 남긴 제안 둘 — 처리 결과

### (1) `ORCHESTRATION_V2_SRS` §3.3.2 의 소유권 (WS-3 제안)

§3.3.2 에 넣은 규칙 **"코드와 문서를 같은 변경에서 함께 바꿔라"** 는 **지금 소유권
구조에서 아무도 지킬 수 없다.** 문서는 조정자 소유, 코드는 담당자 소유라 **어느 쪽도
둘을 한 변경에 담을 수 없다.** 규칙이 요구하는 원자성을 소유권이 막고 있다.

WS-3 제안: **그 한 절만 담당자에게 열어라.** 방향 결정은 조정자가 계속 하고, 담당자는
그 결정을 두 산출물에 **원자적으로 반영하는 역할**만 맡는다.

> 이 제안은 §3.3.2 에 국한된 것이 아니라 **일반 원칙의 후보**다. "문서와 코드가
> 짝을 이뤄야 하는 항목" 은 한 사람이 둘 다 쥐어야 한다. 다른 절에도 적용할지
> 판단해라.

### (2) `models_and_patterns.md` → `models.md` 개명 (WS-4 제안)

내용이 모델 가이드만 남았으므로 이름이 맞지 않는다. **다만 SRS 가 이 파일명을 두 곳에서
못 박고 있다** — FR-PAT-10 본문과 **V-PAT-2**(그 파일에 패턴 잔재 검색 → 0건).
개명하면 이미 서명된 검증 ID 가 그대로는 못 돈다.

고칠 자리 셋: `SKILL.md:328`, `SRS FR-PAT-10`, `SRS V-PAT-2`.
(archive 의 옛 SRS 2건은 역사 기록이라 손대지 않는다.)

WS-4 가 헤드리스 문안 반영 때 묶어서 하겠다고 했고, **SRS 두 줄은 조정자가 고쳐 줘야
한다.**

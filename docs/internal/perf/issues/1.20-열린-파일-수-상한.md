# 1.20 열린 파일 수 상한 (Rust 이전 회귀)

## 배경 (2026-11-25 사용자 보고·조정자 확인)

- Go 판에서는 없던 "too many open files" 가 Rust 판에서 생겼다. 사용자는 `ulimit -n 65536` 으로 임시 해결했다.
- 원인: Go 런타임은 1.19 부터 시작할 때 RLIMIT_NOFILE soft 를 hard 까지 올리고(darwin 은 kern.maxfilesperproc 로 자름), os/exec 자식에게는 원래 soft 값을 돌려준다. Rust 판은 이 일을 하지 않아 launchd 기본 soft 256 에 머문다(`launchctl limit maxfiles` = 256 unlimited).
- 운영 서버 실측(lsof, 시작 5분 뒤): 총 357 fd 중 DIR 161 + REG 160 이 한 worktree 에 대한 fswatch kqueue 감시(항목마다 fd, fsnotify 와 같은 설계, 디렉터리당 KQUEUE_ENTRIES_MAX 4096). 데몬은 64. 이미 256 을 넘는다.

## 목표 (사용자 결정 2026-11-25: A안 + 누수 확인 둘 다)

1. otterminal 바이너리(서버·데몬·otterctl 등 모든 진입점)가 시작할 때 Go 와 같게 soft 를 올린다: unix 에서 soft = hard, darwin 은 min(hard, sysctl kern.maxfilesperproc) (hard 가 RLIM_INFINITY 면 그 값). 실패하면 조용히 그대로 둔다(로그만, eprintln 금지).
2. 자식 프로세스(PTY 셸, git·외부 명령 — `otter_shared_platform::process`·`pty/posix.rs` 의 pre_exec 등)에는 시작 때의 원래 soft 를 돌려준다. Go 의 os/exec 동작과 같게.
3. 격리 인스턴스에서 fd 누수 시험: 편집기 루트 열기/닫기, 터미널 열기/닫기, git 창 열기/닫기, 채널 재연결을 여러 번 되풀이한 뒤 fd 수가 처음 수준으로 돌아오는지(종류별) 잰다. 누수가 있으면 원인과 함께 보고(고치는 것은 따로 판단).

## 완료 조건

- 시험 먼저(RED): 상한 올리기 함수 단위 시험(hard 가 무한·유한·darwin 자르기), 자식이 원래 soft 를 받는지(자식에서 `ulimit -n` 또는 getrlimit 결과) 시험.
- 바꾼 crate 의 lib·fmt·clippy -D warnings, 관련 게이트. 누수 시험은 측정 스크립트 또는 e2e 하나. 전체 시험 금지.
- 동작 변경 이전/새/이유.

## 진행 기록

### 2026-11-25 agent-pf-1-20 — review (커밋 a44c9f5c, pf/1.20)

**Go 동작 확인** (로컬 Go 1.27.2 소스): `syscall/rlimit.go` 의 `init` 이 `Cur < Max-1` 이면 원래 값을 `origRlimitNofile` 에 두고 `Cur = Max-1` 로 올린다. `rlimit_darwin.go` 가 `kern.maxfilesperproc` 에서 자른다. `exec_libc2.go`(darwin fork 자식)·`exec_linux.go`·`exec_unix.go`(`syscall.Exec`)가 exec 직전에 원래 값으로 되돌린다. `Setrlimit(NOFILE)` 을 부르면 되돌리기를 끈다.

**바꾼 것**
- `otter_shared_platform::nofile`(새): `raise_nofile_limit()`(soft = min(hard, darwin 의 kern.maxfilesperproc), 올렸을 때만 원래 rlimit 을 `OnceLock` 에 둔다), `restore_nofile_on_exec(&mut Command)`, crate 내부 `restore_in_child()`(pre_exec 용, setrlimit 하나·할당 없음). Windows 는 아무것도 하지 않는다.
- 진입점: `rust/crates/cmd/otterminal/src/main.rs` `main` 첫 줄. 제품 바이너리는 이것 하나다 — 서버(`start --foreground`)·데몬(`d`/otterminald)·제어 CLI·헬퍼(otterctl·shim 등 `runtimebin::dispatch`)가 모두 이 `main` 을 지난다. 실패는 otterlog 를 세운 뒤 `warnf!` 로 남긴다(헬퍼는 로그 전에 끝나므로 조용히). `rust/crates/scripts/*` 의 개발 도구 넷은 넣지 않았다.
- 자식 되돌리기(이미 있는 pre_exec 경로): `process.rs` `new_session`(→ `detach`: daemon.rs 데몬 기동·start.rs 서버 기동·handoff.rs·doctor_probe.rs, `new_group`: git/core spawn.rs 의 모든 git·lsp/process.rs), `pty/posix.rs` PTY 셸. 그리고 `helper/runtimebin/src/shim.rs` `exec_shim`(셸 안에서 진짜 claude 로 자기를 바꾸는 자리, Go `syscall.Exec` 와 같게)에 `restore_nofile_on_exec` 한 줄.
- 시험: `nofile/tests.rs` — 순수 판단 8건(hard 유한·무한, darwin 자르기, 이미 같음, 낮추지 않음, hard 0), 그리고 자기 시험 바이너리를 자식으로 다시 띄워(soft 는 프로세스 전체 값) soft 200 에서 올린 뒤 detach·new_group·restore_nofile_on_exec·PTY 자식이 `ulimit -n` = 200 을 받는지, 되돌리기를 걸지 않은 자식은 올린 값을 받는지 잰다.
- `e2e/fd-leak.spec.ts`(새): 편집기 루트(20 디렉터리×5 파일) 추가→열기→탐색기→제거, 터미널 창 열기→닫기, git 창 열기→닫기, `page.reload` 재연결을 1바퀴(예열) + 5바퀴 되풀이하고, lsof 의 번호 있는 fd 를 종류별로 센다. 닫은 뒤 30초 안에 총수가 예열 뒤 기준선 이하로 내려와야 한다. 편집기 루트를 연 동안 DIR fd ≥ 20 을 확인해 헛통과를 막는다.

**상한 확인** (일회성, 커밋하지 않음): `ulimit -Sn 256` 을 건 감싸개로 같은 e2e 를 편집기 루트 400 디렉터리로 돌렸다 → 서버가 DIR 401 개(총 ~430)를 오류 없이 쥐고 통과. 같은 감싸개로 터미널에서 `ulimit -Sn/-Hn` → `256/unlimited`(서버 → 데몬 → PTY 의 사슬에서 원래 값이 이어진다). 대조로 `ulimit -n 256`(hard 도 256, 올릴 수 없음)으로 돌렸을 때는 git API 가 500 을 내고 첫 관측이 서지 않았다.

**동작 변경**
- 이전: 물려받은 soft 그대로(launchd 기본 256). 감시가 디렉터리·파일마다 fd 를 써서 한 worktree 로 상한을 넘었다.
- 새: 시작 때 soft = min(hard, kern.maxfilesperproc)(Linux 는 hard). PTY 셸·분리 자식·git·LSP·shim 의 exec 대상은 시작 때의 soft 를 받는다.
- 이유: Go 1.19+ 런타임이 하던 일을 Rust 이전에서 빠뜨린 회귀. 자식 되돌리기도 Go 와 같다.

**시험 결과**: `cargo test -p otter-shared-platform --lib` 264 통과, `-p otter-helper-runtimebin --lib` 151 통과, `-p otterminal --bins` 22 통과. `cargo fmt --all --check` 통과. `cargo clippy -p otter-shared-platform -p otterminal -p otter-helper-runtimebin --all-targets -D warnings` 통과(호스트). 플랫폼 crate 는 x86_64·aarch64 linux-gnu·x86_64-pc-windows-msvc 대상으로도 clippy 통과. `scripts/check-logging.sh` 통과. e2e `fd-leak.spec.ts` 통과. `check-e2e-private.sh`·`check-file-size.mjs` 는 실패하지만 이번 변경과 무관한 기존 위반이다(activity-runs-refresh·git-repaint·perf-statusbar·run-view-live 의 `app._x`, runs-panel.js 506줄).

**Go 와 다른 점(의도)**
- Go 는 `Cur = Max-1` 로 올린다(Linux 에서 prlimit 으로 바뀐 것을 알아채려는 장치). 이슈 목표대로 `Cur = Max` 로 했다. darwin 은 어차피 maxfilesperproc 에서 잘린다.
- Go 는 모든 os/exec 자식에 되돌린다. 여기서는 이미 있는 pre_exec 경로와 shim 만 되돌린다. 나머지 일반 `Command` 자리는 올린 soft 를 물려받는다: sandbox exec(컨테이너 CLI), ext install(tokio), fs_search 의 rg, secrets(security), procinfo·handover 의 ps, privhelper 의 launchctl·sudo, migrate legacy_home, otterctl statusline 명령, swap validate(자기 바이너리), open/openurl(실행은 LaunchServices 가 한다). 모두 짧게 돌거나 select 에 기대지 않는 도구라 영향은 없다고 판단했다.

**남은 위험**
- LOW: 다른 에이전트가 같은 pre_exec(`process.rs` new_session·`pty/posix.rs`)를 고치면 병합 충돌이 날 수 있다. 각각 한 줄 더함과 주석 한 줄 바꿈이다.
- LOW: 위 "되돌리지 않는 자리" 가 Go 와 다르다. 필요하면 각 자리에 `restore_nofile_on_exec` 한 줄로 맞출 수 있다.

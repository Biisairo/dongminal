# SRS: Run 뷰의 슬롯 다중화 — IEEE 29148

## 1. 개요

### 1.1 목적

접수한 요구는 한 줄이다.

> **여러 창 및 슬롯에서 작업 중인데, 한쪽에서 수정되면 다른쪽에서는 수정이 안 되는
> 것 같다.**

재현했다. 같은 창을 두 칸에 놓고 Run 탭을 활성으로 두면 **한 칸이 빈다.**

```
슬롯 0 본문: children 0        ← 비어 있다
슬롯 1 본문: [run-view]
문서 전체 .run-view: 1개       ← 뒤에 그린 칸이 앞 칸에서 떼어 갔다
```

### 1.2 범위

**포함:** Run 뷰 인스턴스의 슬롯 다중화와 그 회수.

**미포함:** Run 대시보드의 내용·요청·그래프. ORCHESTRATION_V2_SRS 의 것이며 한 줄도
바뀌지 않는다.

---

## 2. 현행 분석

### 2.1 탭 타입 넷 중 Run 만 슬롯을 모른다

`renderer._mountTabBody(body,at)` 는 슬롯마다 불린다. 붙일 실체를 고를 때
**슬롯을 딛는 것이 규약**이다 (WINDOW_SLOTS_SRS FR-WSL-20·23, GIT_SLOT_VIEWS FR-SVS-40).

| 탭 타입 | 인스턴스 키 | 슬롯 |
|---|---|---|
| terminal | `_mkTool(toolId,name,**slot**)` → `_slotKey(toolId,slot)` | ✅ |
| editor | `_slotKey(at.id,**slot**)` | ✅ |
| git | `_gitPanel(**slot**)` | ✅ |
| **run** | `_runViewMap().get(tab.id)` — `app-runs.js:271` | ❌ |

DOM 노드는 한 부모에만 붙는다. 캐시가 하나이므로 두 번째 칸의 `appendChild` 가 첫
칸에서 노드를 **떼어 간다** — 앞 칸은 빈 상자가 된다.

Git 패널이 같은 문제를 이미 겪었고 그 해법이 규약으로 남아 있다 (`renderer.js:403`).

> Git 창은 싱글턴이지만 **패널은 칸마다** 있다 (FR-SVS-40·42) — 그래야 두 칸이 같은
> 뷰를 볼 때 뒤 칸이 앞 칸에서 DOM 을 떼어 가지 않는다.

### 2.2 키를 복합키로 바꾸면 **회수가 먼저 깨진다**

`_runViews` 를 읽는 자리는 셋이고, 셋 다 키가 **탭 id 그대로**라고 가정한다.

| 자리 | 가정 |
|---|---|
| `_runViewEl` (`:271`) | `m.get(tab.id)` |
| `_onRunChanged` (`:329~336`) | `live.has(tabId)` · `m.delete(tabId)` |
| `_runPaint` 예약 (`:390`) | `m.get(v.tabId)===v` |

편집기가 **정확히 이 실수를 이미 했다** (renderer.js 의 FR-SVS-60 주석).

> 편집기 Map 의 키는 복합키다 (FR-WSL-75) — 회수는 탭 id 로 판정한다. FR-SVS-60:
> 파싱은 `_slotBase` 한 자리다. **여기서 `@1` 만 잘라 내던 동안 칸 2·3 의 편집기는
> 살아 있는 탭인데도 매 render 마다 파괴됐다.**

그러므로 이 SRS 는 "키를 바꾼다" 가 아니라 **"키를 바꾸고 그 키를 읽는 세 자리를
함께 고친다"** 이다.

## 3. 요구사항

**FR-SRV-1** Run 뷰 인스턴스의 키는 `_slotKey(tab.id, slot)` 이다. 같은 Run 탭이 두
칸에 보이면 뷰도 DOM 도 **둘**이다.

**FR-SRV-2** `_runViewEl(tab, slot)` 이 슬롯을 인자로 받는다. 부르는 자리는
`renderer._mountTabBody` 하나이며 그것은 이미 자기 슬롯을 안다.

**FR-SRV-3** 단일 슬롯 모드의 키는 `tab.id` **그대로**다 — `_slotKey` 가 슬롯 0 에
접미사를 붙이지 않는다 (FR-WSL-75). 칸이 하나일 때의 동작은 한 글자도 바뀌지 않는다.

**FR-SRV-4** 키를 읽는 **세 자리 모두** 복합키를 안다 (§2.2).

1. 조회 — `_slotKey` 로 만든 키
2. 회수 — 살아 있는 탭 판정은 `_slotBase(k)` 로 한다. 그리고 **사라진 칸의 뷰도**
   거둔다 (`_slotReap`, FR-SVS-46 과 같은 자리).
3. 다시 그리기 예약 — 자기 키로 자기 자신인지 확인한다.

**FR-SRV-5** `_onRunChanged(runId)` 는 그 `runId` 를 보는 **모든 칸의 뷰**를 갱신한다.
한 칸만 갱신하면 이 SRS 가 고치려는 증상이 그대로 남는다.

**FR-SRV-6** 뷰가 거둬질 때 관측자와 예약된 다시 그리기를 함께 끊는다
(`_runDisposeView`) — 지금 하는 그대로이며, 칸마다 하나씩 하게 될 뿐이다.

**FR-SRV-7** 요청은 뷰마다 나간다. 같은 run 을 두 칸이 보면 첫 마운트에서 요청이
둘이다 — 뷰가 둘이므로 데이터도 둘이어야 하고, 한 뷰의 실패가 다른 뷰를 비우면 안
된다. (NFR-RVZ 의 "다시 그리기는 요청을 만들지 않는다" 는 뷰 단위 규칙이며 유지된다.)

## 4. 설계 결정

**D-1. 캐시를 슬롯별로 쪼갠다 — 뷰를 공유하고 DOM 만 복제하지 않는다.** DOM 만 둘로
만들면 상태(스크롤·hover·펼침)가 한 벌뿐이라 두 칸이 서로의 조작을 덮는다. 편집기·
Git 패널이 인스턴스 자체를 칸마다 둔 것과 같은 이유다.

**D-2. 회수를 세 자리 모두에서 고친다.** → §2.2. 편집기가 이미 낸 사고이고, 그
사고는 "키만 바꾸고 회수를 그대로 두었을 때" 났다.

## 5. 검증

| ID | 요구 | 검증 |
|---|---|---|
| TC-SRV-1 | FR-SRV-1·2 | 같은 창을 두 칸에 놓고 Run 탭을 활성으로 두면 **두 칸 모두** `.run-view` 를 갖는다 (문서 전체 2개) |
| TC-SRV-2 | FR-SRV-3 | 칸이 하나면 `.run-view` 는 하나이고 키에 접미사가 없다 |
| TC-SRV-3 | FR-SRV-4.2 | 두 칸에서 Run 탭을 본 뒤 다시 그려도 어느 칸의 뷰도 파괴되지 않는다 (편집기 FR-SVS-60 회귀와 같은 형태) |
| TC-SRV-4 | FR-SRV-4.2 | 칸을 줄이면 사라진 칸의 뷰가 거둬진다 |
| TC-SRV-5 | FR-SRV-5 | run 이 바뀌면 두 칸의 뷰가 **함께** 갱신된다 |
| TC-SRV-6 | FR-SRV-1 | Run 탭을 닫으면 그 탭의 뷰가 **모든 칸에서** 거둬진다 |

## 6. 비목표

1. Run 대시보드의 내용·API·그래프를 바꾸지 않는다.
2. `_buildPane` 이 `_aw()` 로 창 타입을 판정하는 문제(`renderer.js:497·504·513`)는
   별건이다 — 같은 "슬롯을 모르는 코드" 계열이지만 탭 바와 드래그의 동작 결함이며
   이 SRS 의 증상과 다르다.

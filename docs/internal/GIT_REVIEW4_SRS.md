따로 두지 않고 **공통 규약 하나**로 만든다 (FR-RPT-6) — 자리마다 손으로 막으면 다음
목록에서 또 빠진다. 실제로 이 저장소는 같은 함정을 세 번 만나 세 번 다르게 막았다.

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **자기 계기(user-driven)** | 사용자의 행동이 직접 부른 다시 그리기 (클릭·키·드롭) |
| **바깥 계기(ambient)** | 사용자가 만들지 않은 계기 — 폴링 타이머, 서버 푸시(SSE), 다른 클라이언트·다른 에이전트의 변경 |

| **관측 동일성(observation identity)** | 이번에 그릴 내용이 지금 그려져 있는 것과 같음 |
| **행 동일성(row identity)** | 같은 항목이 다시 그린 뒤에도 **같은 DOM 요소**로 남음 |
| **희소 레인(sparse lane)** | `activeLanes` 의 인덱스. 갈래가 살아 있는 동안 바뀌지 않는다 |

| **행 공간 S(i)** | 행 i 에서 살아 있는 희소 레인을 순서를 지켜 0..n-1 로 촘촘히 매긴 것 |
| **색 키(color key)** | 팔레트를 고르는 정수. 열이 아니라 갈래에 붙는다 |
| **배지(badge)** | 커밋 행에 붙는 ref 표식 (`.git-hist-badge`, FR-GIT-126) |

## 2. 전반 기술 (Overall Description)

### 2.1 근거 (Rationale) — 하나의 원인

목록을 다시 그리는 흔한 모양은 이것이다.

```js
container.innerHTML='';
for(const item of items) container.appendChild(build(item));
```

값으로 화면을 만드는 방식이라 **읽기 쉽고, 자기 계기에서는 옳다.** 사용자가 무언가를
눌러서 목록이 바뀌었으면 다시 그려지는 것이 맞다.

**바깥 계기에서는 틀린다.** 요소를 버리고 새로 만들면 값으로 되살릴 수 없는 것이
함께 사라진다.

| 잃는 것 | 사용자가 보는 것 |
|---|---|
| `:hover` | hover 로만 보이는 버튼이 사라진다. 새 요소는 **다음 마우스 이동까지** `:hover` 를 받지 못한다 |
| 진행 중인 transition | `transition:opacity .1s` 가 0 에서 다시 시작한다 — 주기마다 페이드인이다 |
| 더블클릭의 첫 클릭 | 두 번째 클릭이 **다른 요소**에 떨어져 브라우저가 `dblclick` 을 만들지 않는다 |
| native 드래그 세션 | 끌고 있던 요소가 DOM 에서 빠지면 드래그가 취소된다 — 재배치가 조용히 실패한다 |
| 글자 선택 | 복사하려고 고른 범위가 사라진다 |
| 표시 중인 기본 툴팁 | `title` 툴팁이 닫힌다 — 읽는 중에 사라진다 |

E1 은 이 표의 첫 두 줄이고, E3 는 세 번째 줄이다. 원인이 하나이므로 **방어도 하나**여야
한다.

**이 저장소는 이미 같은 함정을 세 번 만났고, 세 번 다르게 막았다.**

| 자리 | 막은 방법 | 근거가 적힌 곳 |
|---|---|---|
| History 목록 | `_winKey` 가 같으면 행을 만들지 않는다 | `history.js` `_paintRows` |
| refs 사이드바 | `dataset.sig` 가 같으면 요소를 만들지 않고 선택만 고친다 | `history.js` `_paintRefs` — "다시 만들면 더블클릭의 두 번째 클릭이 새 요소에 떨어져 브라우저가 `dblclick` 을 만들지 않는다" |
| 알람 표식 | 전체 `render()` 대신 클래스만 토글한다 | `app-attn.js` `_attnRefresh` — "전체 render() 를 피해 포커스 플리커(xterm blur/refocus)를 막는다" |
| Branches 트리 | HEAD 가 바뀔 때만 다시 받는다 | `panel.js` `_paint` — "목록 전체를 폴링마다 다시 그리면 스크롤이 매초 흔들린다" |

같은 문제를 네 번째로 손으로 막는 대신 **규약과 공통 수단**을 만든다.

### 2.3 근거 — E2 는 다른 원인이다

`buildLaneGraph` 는 희소 레인 인덱스를 갈래가 사는 동안 유지하고, 비워진 레인은
**뒤쪽만** 잘라낸다(`while … pop()`). 가운데 갈래가 먼저 끝나면 그 인덱스는 빈 채
남고, 새 머리가 와서 채울 때까지 화면에 **빈 열**로 보인다. 오른쪽 갈래가 혼자
떨어져 보이는 것이 그것이다.

현재 알고리즘으로 실측했다 (`--all` 에서 세 갈래 중 가운데가 먼저 끝나는 모양).

```
A1  lane=0 pass=[]      parents=[0]
B1  lane=1 pass=[0]     parents=[1]
C1  lane=2 pass=[0,1]   parents=[2]
B2  lane=1 pass=[0,2]   parents=[]     ← B 갈래가 끝난다
A2  lane=0 pass=[2]     parents=[0]    ← 열 1 이 빈다
C2  lane=2 pass=[0]     parents=[2]    ← C 가 열 2 에 홀로 남는다
A3  lane=0 pass=[2]     parents=[]
C3  lane=2 pass=[]      parents=[]
```

압축은 **색과 함께 풀어야 한다.** 지금 `_svg` 의 색은 열에서 파생한다
(`pal[l%pal.length]`). 열을 압축하면 갈래가 왼쪽으로 옮겨질 때 색이 함께 바뀌어,
같은 갈래가 중간에 색을 갈아입는다. FR-GIT-119 는 "테마 팔레트에서 파생"만 요구하고
열에서 파생하라고 하지 않았으므로, 색 키를 **갈래(희소 레인)** 에 붙인다.

압축하면 선이 행 경계에서 열을 옮긴다. 그러려면 각 세그먼트가 **위 끝과 아래 끝의
열을 따로** 알아야 한다. 지금의 행 모델(`passThrough` 가 열 하나짜리 배열)로는
표현할 수 없으므로 모델을 넓힌다. 넓히는 방향은 하나로 정해진다.

**공간의 정의.** 행 i 의 공간 T(i) 는 **행 i 에 들어올 때 살아 있는 갈래에 그 행의
커밋 레인을 더한 것**을 순서를 지켜 0..n-1 로 촘촘히 매긴 것이다. 마지막 행 다음의
공간 T(n) 은 마지막 행을 나갈 때 살아 있는 갈래로 만든다.

- 행 i 는 **위 끝과 점을 T(i)**, **아래 끝을 T(i+1)** 로 그린다.
- 행 i 의 아래 끝 공간이 곧 행 i+1 의 위 끝 공간이므로 **선이 끊기지 않는다.**
- 커밋의 진입선은 위 끝과 점이 같은 공간이라 **늘 곧게** 내려온다. 갈래가 열을
  옮기는 것은 아래 끝에서 일어나고, 그 행 안에서 곡선으로 이어진다.
- T(i) 는 행 i+1 의 커밋 레인까지 알아야 정해진다(새 머리가 빈 자리를 채우면 그
  오른쪽 열이 한 칸 밀린다). 그래서 **위상과 배치를 나눈다** — 위상은 앞을 보지 않고,
  배치는 위상 결과를 한 번 더 훑는다 (FR-GIT-117 개정).

### 2.3.1 참조 구현 — VSCode Git Graph 가 실제로 하는 것

사용자가 기준으로 든 도구(`mhutchie/vscode-git-graph`)의 `web/graph.ts` 를 읽고
확인했다. **추측이 아니라 그 코드가 근거다.**

| # | 규칙 | 근거 |
|---|---|---|
| R1 | **행마다 열을 왼쪽부터 촘촘히** 나눠 준다. 갈래를 머리 행 순서로 처리하고, 각 행에서 `nextX`(아직 안 쓰인 가장 왼쪽 열)를 집는다 → 결과가 **나이 순 촘촘한 배치**다 | `registerUnavailablePoint(x,…){ if(x===this.nextX){ this.nextX=x+1; … } }` · `getNextPoint()` |
| R2 | 커밋 **점**의 열은 한 번 정해지면 고정이다. 그러나 통과선은 그 행의 다음 빈 열을 받으므로, 앞 갈래가 끝나 열이 비면 **왼쪽으로 휜다** | `addToBranch(branch,x){ if(this.onBranch===null){ … this.x=x } }` · `branch.addLine(lastPoint, curPoint, …)` 이 `x1≠x2` 면 곡선/각진 전이로 그린다 |
| R3 | 갈래는 **first-parent 사슬을 끝까지 걸어가며** 한 덩어리로 잡는다. 머리 행 순서로 처리하므로 **트렁크가 뿌리까지 자기 색을 유지**한다. 색은 재사용되는 슬롯 번호이고 갈래가 사는 동안 고정이며, 앞 갈래가 **끝난 뒤에야** 다시 쓴다 | `determinePath` 의 normal 분기 루프 (`vertex=parentVertex; parentVertex=vertex.getNextParent()`) · `getAvailableColour(startAt)` · `availableColours[branch.getColour()]=i` |
| R4 | 머지가 **이미 배치된 부모**로 갈 때는 새 갈래·새 색을 만들지 않고, 그 사이 행마다 자기 열을 집고 내려가 부모 점에 붙는다 | `determinePath` 의 merge 분기 — `getPointConnectingTo` / `parentBranch.addLine(…)` |

**따라서 "선은 분기·머지가 아니면 혼자 휠 수 없다" 는 Git Graph 의 동작이 아니다.**
Git Graph 에서 통과선은 자기 일이 없는 행에서도 왼쪽으로 휜다 — 열이 비었기
때문이다. 고정되는 것은 커밋 점의 `x` 뿐이다. `git log --graph` 도 같다 (`|/ /`).

이 판은 R1~R4 를 그대로 따른다. 이탈은 하나뿐이고 FR-GIT-235 에 적었다 — 부모가
없는 커밋에서 선을 내리지 않는다.

### 3.2 교차 관심사 — 바깥 계기의 다시 그리기 규약

**증상**(사용자 검토 E1): "changes 에서 행 위에 마우스를 올리고 있으면 버튼이 약
1초에 한 번씩 깜빡인다." **원인과 같은 원인의 다른 자리**: §2.1·§2.2.

- **FR-RPT-1** **바깥 계기로 다시 그리는 목록은, 그릴 내용이 지금 그려진 것과 같으면
  다시 그리지 않는다.** 같은 값을 그려 넣는 일은 화면을 바꾸지 않으면서 요소 상태만
  버린다.
- **FR-RPT-2** 관측 동일성의 판정 근거는 **그 목록의 렌더러가 읽는 값 전부**다.
  판정에 쓰지 않는 값이 화면에 닿으면 갱신이 **조용히 멈춘다** — 근거를 좁히지 않는다.
  - 값이 아닌 것(요소 상태)은 근거가 아니다.
  - 판정은 그린 직후의 값을 요소에 남겨 다음 회차와 비교한다. 요소가 없으면(첫 그리기)
    무조건 그린다.
- **FR-RPT-3** **내용이 실제로 바뀐 회차에도, 바뀌지 않은 항목은 같은 DOM 요소로
  남는다.** 순서가 바뀌면 요소를 **옮긴다** — 지우고 다시 만들지 않는다.
  - 항목의 동일성은 **키**로 판정하고, 다시 만들지 여부는 **그 항목의 보이는 값
    전부**로 판정한다 (FR-RPT-2 와 같은 규칙).
  - 사라진 항목의 요소는 제거한다.
- **FR-RPT-4** FR-RPT-3 은 **요소 상태를 가진 목록**에 적용한다. hover 로만 보이는
  컨트롤, 더블클릭·드래그 제스처, 선택해서 복사하는 본문, `title` 툴팁 중 하나라도
  있으면 대상이다.
- **FR-RPT-5** **자기 계기의 다시 그리기는 대상이 아니다.** 사용자가 만든 변화는
  화면이 바뀌는 것이 맞고, 그 순간 요소 상태가 갱신되는 것도 맞다.
- **FR-RPT-6** 두 규약은 **한 곳에 구현하고 목록이 그것을 쓴다.** 목록마다 가드를
  손으로 쓰면 다음 목록에서 또 빠진다 — 이 저장소가 이미 네 곳에서 네 번 다르게
  막았다 (§2.1).
- **FR-RPT-7** 적용 자리는 §2.2 의 조사 결과 전부다. 공통 수단은
  `web/js/ui/repaint.js` 의 `paintIfChanged`(FR-RPT-1)·`reconcileList`(FR-RPT-3)다.
- **FR-RPT-8** **다시 그리기에 업힌 판정은 관측 경로로 옮긴다.** 그리지 않으면
  판정도 멈추기 때문이다.
  - 그리는 함수는 **값을 화면에 옮기는 일만** 한다. "무엇을 할지" 를 정하는 일은
    관측이 도착하는 자리에서 한다.
  - 판정의 계기가 **값이 아니라 "새 응답이 왔다"** 인 것이 특히 위험하다 — 값이
    같으면 그리지 않으므로 그 판정은 영원히 오지 않는다.
  - 실제로 하나 있었다: 원격 pull 의 충돌 판정(FR-GIT-111)이 `GitRemote.paint` 에
    업혀 있었고, 계기가 `status` **객체가 바뀌었는지**였다. 관측 경로
    (`_applyStatus` → `notifyStatus`)로 옮겼다. `GitConfirm.notify`·`GitDialog.notify`

#### 3.2.1 이 판이 남기는 자리 — 레이아웃·탭 골격

`Renderer._rLayout` 은 같은 원인을 갖는다 (§2.2 #8). **이 판에서 고치지 않는다.**

- 계기가 **실제 워크스페이스 변경**이다. 폴링이 아니라 무언가가 정말 바뀐 것이며,
  다시 그리는 것 자체가 틀리지 않았다.
- 관측 동일성 판정의 근거가 **레이아웃 트리 전체**(창·분할·탭·활성 탭·포커스·도구
  이름·알람·모바일 모드)다. FR-RPT-2 를 지키지 못하면 **레이아웃이 조용히 얼어붙는다** —
  이 판의 다른 다섯 자리보다 실패의 값이 크다.
- 여기의 다시 그리기는 터미널 재부착을 부르고, 그 비용 때문에 이미 여러 경로가
  `render()` 를 피해 가도록 만들어져 있다 (`_attnRefresh`·`_gitReposRefresh`). 즉
  **핫 경로가 아니다.**

**남기는 것을 조용히 하지 않는다** — `GIT_REMAINING` §6 에 별건으로 적는다.

### 3.3 결함 — 그래프의 선이 왼쪽으로 붙지 않는다

**증상**(사용자 검토 E2): §1.1. **원인**: §2.3.

- **FR-GIT-228** 각 행의 열은 **그 행에서 살아 있는 갈래를 순서를 지켜 0 부터 촘촘히**
  매긴 것이다. **빈 열이 없다.**
  - "살아 있는"은 행에 들어올 때와 나갈 때를 각각 본다 — 행 i 의 위 끝은 행 i-1 이
    나갈 때의 공간으로, 아래 끝과 점은 행 i 가 나갈 때의 공간으로 그린다.
  - 갈래 사이의 **좌우 순서는 뒤집히지 않는다.** 압축은 자리를 당기는 것이며 정렬을
    다시 하는 것이 아니다.
- **FR-GIT-229** 선은 **행 경계에서 끊기지 않는다.** 행 i 의 아래 끝 열 집합은 행 i+1
  의 위 끝 열 집합과 **같다**.
  - 열이 옮겨지는 세그먼트는 그 행 안에서 이어 그린다 (FR-GIT-118 — 행이 자기 SVG 로
    완결된다).
- **FR-GIT-230** 색은 **갈래에 붙는다.** 한 갈래는 살아 있는 동안 같은 색을 유지하며,
  열을 옮겨도 바뀌지 않는다. 팔레트는 테마에서 파생한다 (FR-GIT-119).
- **FR-GIT-234** 열은 **갈래를 머리 행 순서로 처리하며** 행마다 "아직 안 쓰인 가장
  왼쪽 열"을 집는 것으로 정한다 (§2.3.1 R1). 그 결과 오래된 갈래가 늘 왼쪽이다.
  - 한 갈래의 열은 **왼쪽으로만** 움직인다 — 오른쪽으로 밀리는 일이 일어날 수 없다.
    새 갈래는 늘 나중에 처리되므로 이미 자리를 잡은 갈래의 열을 건드리지 못한다.
  - 왼쪽으로 몇 칸을 가는지는 제한하지 않는다. 한 행에서 여러 갈래가 함께 끝날 수
    있고, 그러면 오른쪽 선이 그만큼 당겨진다 (`git log --graph` 의 `|/ /`).
  - 새 갈래(새 머리, 머지의 두 번째 부모)는 그 행의 **가장 오른쪽** 열을 받는다.
  - **행 순서로 레인을 배정하면 안 된다**: 그러면 나중 행의 갈래가 트렁크의 뿌리를
    먼저 물어 가고, 트렁크가 **중간에서 색을 갈아입는다.** 갈래는 first-parent
    사슬을 끝까지 걸어가며 잡아야 한다 (R3). V128·V130 이 그것을 고정한다.

- **FR-GIT-235** 갈래는 **first-parent 사슬을 끝까지** 잡는다 (§2.3.1 R3).
  - 머리에서 시작해 첫 부모를 따라 내려가며, 이미 다른 갈래에 든 커밋을 만나면 멈춘다.
  - 그래서 트렁크는 **뿌리까지 자기 색을 유지한다.** 뒤에서 시작한 갈래의 선이 그
    사슬로 **붙는다** — 사슬을 빼앗지 않는다.
  - 이미 배치된 커밋으로 가는 선은 그 사이 행마다 자기 열을 집고 내려가 부모 행에서
    붙는다 (R4). 한 행에서 곧바로 대각선으로 뛰지 않는다.
  - **부모가 없는 커밋에서는 선을 내리지 않는다.** Git Graph 는 이 경우에도 목록
    끝까지 걸어가며 선을 그리지만(`parentVertex` 가 null 인데 루프가 그대로 돈다),
    뿌리 커밋은 보통 마지막 행이라 그 코드가 도는 일이 없어 드러나지 않는 것이다.
    `--all` 에서 뿌리가 중간에 오면 **아무 데도 닿지 않는 선이 아래로 늘어진다** —
    그것은 따르지 않는다 (이 판의 유일한 의도적 이탈).

- **FR-GIT-231** 상한 접기(FR-GIT-120)는 **압축된 열에** 적용한다. 접힌 뒤에도
  세그먼트 목록은 중복이 없고 오름차순이며, 접힘이 실제로 일어난 행에만 표식을
  세운다. 원본 배치를 제자리에서 고치지 않는다 (기존 규약 유지).
  - 압축이 열을 줄이므로 접힘이 일어나는 행은 **줄어들거나 같다.** 늘어나면 압축이
    틀린 것이다.

### 3.4 결함 — 커밋 행의 브랜치 배지에 기본 동작이 없다

**증상**(사용자 검토 E3): "히스토리에서 브랜치 더블클릭 체크아웃이 구현되지 않았다."

**진단 — 스펙에 없던 것이다.** FR-GIT-222 는 **Branches 탭과 History refs 사이드바**
둘만 덮으며, 둘 다 구현돼 있고 e2e 로 확인된다 (B12·B13·H12 통과, 2026-08-27 실행).
남은 자리는 **커밋 행의 ref 배지**다 — 여기에는 리스너가 하나도 없고, 우클릭도
커밋 메뉴가 받는다.

- **FR-GIT-232** 커밋 행의 **ref 배지는 그 ref 를 대상으로 하는 자리**다.
  - **더블클릭**은 그 ref 의 기본 동작이다 — `GitMenu` 의 primary 후보를 그대로 쓴다
    (FR-GIT-222 와 **같은 경로**). 로컬 브랜치는 Checkout, 원격 브랜치는 추적
    브랜치를 만드는 Checkout 이다.
  - **우클릭**은 그 ref 의 메뉴를 연다 — 브랜치 배지는 branch 메뉴, 태그 배지는 tag
    메뉴다. 커밋 메뉴가 아니다.
  - **현재 브랜치와 태그의 더블클릭은 아무 일도 하지 않는다** — 후보가 없거나 전부
    비활성이면 그만둔다 (FR-GIT-222 의 규약. 태그 체크아웃은 detached 가 되므로
    가벼운 제스처에 싣지 않는다).
  - **배지의 클릭은 행으로 올라가지 않는다.** 올라가면 첫 클릭이 상세를 접거나 펴서
    행 창이 다시 만들어지고(`_ver` → `_paintRows`), 두 번째 클릭이 새 요소에 떨어져
    `dblclick` 이 만들어지지 않는다 — §2.1 의 셋째 줄과 같은 함정이다. 따라서 배지의
    단일 클릭은 **아무 일도 하지 않는다.**
  - 커밋 행의 더블클릭은 배지 밖에서도 상세를 여닫지 않는다 — 두 번째 클릭을 무시한다
    (refs 사이드바가 이미 쓰는 규약).
  - 종류를 모르는 배지(`kind` 가 빈 값, `shortRefName` 이 네임스페이스를 모를 때)는
    **대상이 아니다** — 아무 리스너도 붙이지 않는다. 뜻을 모르는 ref 로 저장소를
    바꾸지 않는다.

### 3.4.1 결함 — 체크아웃 뒤 커밋 목록의 HEAD 표식이 낡는다 (E4)

**어떻게 찾았나**: FR-GIT-232 를 구현하고 검증하다 드러났다. 배지를 더블클릭하면
체크아웃은 실제로 되는데(`headName()` 이 바뀐다) **그 배지의 HEAD 표식이 움직이지
않는다.** refs 사이드바는 갱신된다.

**원인**: `afterRefWrite` 는 refs 사이드바만 다시 받고(`reloadRefs` → `_loadRefs`)
**커밋 목록은 다시 받지 않는다.** 커밋 행의 `head` 표식과 배지의 `head` 표식은 둘 다
`git log` 의 decoration(`c.isHead`·`r.isHead`)에서 오므로, 목록을 다시 받기 전까지
낡은 값이 남는다.

**E1·E3 와 원인이 다르다** — 요소를 버려서가 아니라 **값을 다시 받지 않아서**다.
접수된 3건에 들어 있지 않지만, FR-GIT-232 가 배지를 동작 자리로 만들면서 "눌렀는데
표시가 그대로"가 되므로 함께 고친다.

- **FR-GIT-233** 커밋 목록의 HEAD 표식은 **살아 있는 관측에서 파생한다.**
  - 커밋 행의 표식은 그 커밋이 `status.oid` 와 같을 때 선다.
  - ref 배지의 표식은 그것이 로컬 브랜치이고 이름이 `status.branch` 와 같을 때 선다.
    detached 에서는 어느 배지에도 서지 않는다 (FR-GIT-144 의 상태와 맞는다).
  - 관측이 아직 없으면 `git log` 의 decoration 을 그대로 쓴다 — 첫 그리기가 표식 없이
    보이지 않게 한다.
  - **대안을 택하지 않은 이유**: `afterRefWrite` 에서 커밋 목록을 다시 받는 방법도
    있으나, 300개를 다시 받으면서 **스크롤과 펼친 상세가 목록 맨 위로 돌아간다** —
    체크아웃은 목록을 처음부터 다시 읽는 일이 아니다. 파생은 요청을 늘리지 않고
    표식만 정확해진다.

### 3.5 Changes 목록의 적용 (FR-RPT 의 Git 적용)

- **FR-GIT-227** Changes 목록은 FR-RPT-1·3 을 따른다.
  - 관측 동일성의 근거는 **`/api/git/status` 응답 중 화면에 닿는 값 전부**다. 관측이
    같으면 Changes 를 다시 그리지 않는다. 폴링이 아닌 계기(선택·접기·미리보기 도착)는
    FR-RPT-5 로 대상이 아니다.
  - 행의 "보이는 값"은 상태 문자·경로 표시·선택·포커스·부분 스테이지·충돌·들여쓰기다.
    하나라도 다르면 다시 만든다.
  - 보호되는 것은 hover 뿐이 아니다 — **FR-GIT-52 의 파일 행 더블클릭**도 같은 보호를
    받는다.

#### 3.6.1 I1 — Changes 행에 Open File

**증상**(접수): "changes 각 행에 open file 버튼 추가. 현재 staging·되돌리기 둘뿐."

- **FR-GIT-236** Changes 파일 행의 인라인 동작은 **Open File · Staging · 되돌리기**
  순이다.
  - Open File 은 **파일 행에만** 붙는다. 디렉터리 행·그룹 머리에는 붙지 않는다 —
    열 대상이 없다.
  - 동작은 **선언에서 나온다** (`GIT_ROW_ACTS`·`GIT_ACT_LABEL`·`GIT_ACT_TITLE`).
    행마다 조건을 손으로 쓰지 않는다.
  - 행 인라인 동작과 우클릭 메뉴는 **하나의 실행 경로로 합친다.** 지금은 갈라져
    있다 — 인라인 버튼은 전부 `panel.js` `_run` 을 지나지만, 메뉴의 `openFile` 은
    `_run` 을 지나지 않고 `app._gitOpenFile(panel.absPath(t))` 를 직접 부른다
    (`menu.js:57`). 두 벌로 두면 한쪽만 고쳐진다.
  - **다중 선택이어도 그 행 하나만 연다.** `_rowTargets`(`panel.js:835`)는 클릭한
    행이 선택 안에 있으면 선택 전체를 대상으로 묶으므로, 그 규약을 그대로 쓰면
    선택한 파일 수만큼 편집기 탭이 열린다 — 요청에 없는 동작이다.
  - 대상 창은 **Git 창이 아닌 창**이고, 없으면 만든다 (FR-GIT-41·185).
  - **행의 `sig` 에 이 버튼이 읽는 값을 넣는다** (FR-RPT-2). 넣지 않으면 그 값이
    화면에서 조용히 갱신되지 않는다.

#### 3.6.2 I2 — 경로 표시를 디렉터리와 파일명으로 가른다

**증상**(접수): "changes 의 경로 표시가 너무 흐리다 → 진하게. 다만 파일명과 같으면
보기 불편하므로 차이가 있게. 파일명도 더 잘 보이면 좋겠다."

- **FR-GIT-237** 평평한 보기의 경로 표시는 **디렉터리 부분과 파일명 부분을 각각의
  요소로** 나누어, 둘을 **다른 밝기**로 보인다.
  - **파일명이 더 강조된다** — "밝다"가 아니라 **대비가 강하다**다. 라이트 테마에서는
    강조가 더 **어두운** 쪽이다 (`GitHub Light` 의 `--text-bright` 는 `#1f2328`,
    `--text-muted` 는 `#656d76`). 밝기로 규칙을 쓰면 라이트 테마에서 거꾸로 된다.
  - 대비는 **색과 굵기 두 축**으로 낸다. 색만으로는 두 단계를 낼 수 없다 —
    `.git-file` 은 색을 정하지 않아 본문 `--text` 를 물려받고(`style.css:1001`),
    그 위로 쓸 수 있는 단계는 `--text-bright` 하나다. 없는 변수를 만들지 않는다.
  - 그래서 **파일명은 `--text-bright` + `font-weight:500`**, 디렉터리는 `--text`,
    화살표는 `--text-muted` 다. 이 조합은 이 저장소가 이미 쓰는 강조 어휘다
    (`.git-repo.active .git-repo-name`, `style.css:1373`).
  - 디렉터리를 `--text-bright` 로 올리지 않는다 — 올리면 파일명에 남는 단계가
    굵기뿐이고, 트리 보기의 디렉터리 행(`.git-dir-name` 은 `--text-muted`)보다
    평평한 보기의 디렉터리가 더 강해져 두 보기가 어긋난다.
  - **색은 테마 변수에서 파생한다.** 하드코딩하지 않으며, 라이트·다크 양쪽에서
    구별이 유지된다. CSS 에는 테마 분기 블록이 없다 — `THEMES` 의 값을
    `applyThemeObj` 가 인라인으로 덮으므로(`helpers.js:44`), 변수만 쓰면 따라온다.
  - **행의 `textContent` 는 바뀌지 않는다.** 요소를 나누는 것이지 글자를 바꾸는 것이
    아니다 — 기존 단정(`git-changes.spec.ts:128`·`:266`)이 텍스트로 걸려 있다.
  - rename 행(`origPath → path`)도 **같은 규칙 하나**로 가른다: 두 경로 각각의
    파일명이 강조되고 디렉터리가 가운데다. 화살표는 가장 약하다. 예외를 만들지 않는다.
  - 트리 보기는 이미 파일명만 보이므로 **바뀌지 않는다.**
  - 나눈 요소는 **행의 `sig` 가 읽는 값에 포함된다** (FR-RPT-2).
  - 경로에 디렉터리가 없으면(저장소 뿌리의 파일) 디렉터리 요소는 **만들지 않는다** —
    빈 요소가 자리를 먹지 않는다.

#### 3.6.3 I3 — 새로고침 버튼

**증상**(접수): "git 새로고침 버튼이 필요하다."

- **FR-GIT-238** Changes 헤더는 **새로고침 진입점**을 갖는다.
  - 자리는 Changes 헤더의 `.git-head-spacer` 뒤이며 **`.git-head-remote` 밖**이다.
    그 안에 넣으면 원격 버튼을 세는 기존 단정(`git-changes.spec.ts:70`)에 걸린다.
  - **전부 다시 받는다**: status(Changes) · History · Branches · Console. 어느 탭을
    보고 있는지에 따라 달라지지 않는다 — 같은 버튼이 늘 같은 일을 한다.
  - "전부"의 범위는 **이미 만들어진 뷰 전부**다. 탭의 뷰는 그 탭을 처음 열 때
    지연 생성되므로(`panel.js:659`·`680`·`700`), 한 번도 열지 않은 탭은 대상이
    아니다 — **보인 적이 없는 것은 낡을 수 없고, 열 때 새로 받는다.**
    - 판정 기준은 **활성 탭이 아니라 만들어졌는지**이므로 "어느 탭을 보고 있는지에
      따라 달라지지 않는다"는 뜻은 그대로다. History 를 보다 Changes 로 옮긴 뒤
      눌러도 History 는 다시 받는다.
    - 없는 뷰를 만들어 가며 받지 않는 것은 이 저장소가 이미 세운 원칙이다 —
      "보이지 않는 섹션을 위해 요청을 살 이유가 없다" (`_startGitReposPoll`,
      FR-STAT-17).
  - **History 는 공개 진입점을 새로 만들어야 한다.** 지금 있는 것은
    `reloadRefs()`(refs 사이드바만, `history.js:745`)뿐이고, 커밋 목록을 다시 받는
    것은 private `_reload()`(`history.js:776`)이며 그것은 `_open=null` 로 **펼친
    상세를 버린다.** private 을 밖에서 부르지 않는다 — 경계를 넘는 호출은 다음
    변경에서 조용히 깨진다.
  - `collect()` 는 status 만 받고 **Console 을 건드리지 않는다**(`panel.js:1374`
    `_applyStatus` 는 `_paint()` 로 History·Branches·Stash 의 `paintStatus` 만 부른다).
    그러므로 새로고침은 `collect()` 하나로 끝나지 않는다 — 넷을 각각 불러야 한다.
  - **자기 계기다** (FR-RPT-5). 사용자가 눌러서 갱신되는 것이므로 관측 동일성 가드의
    대상이 아니며, 값이 같아도 다시 받는다.
  - 받는 동안 진입점은 **다시 눌리지 않는다.** 겹쳐 부르면 같은 요청이 두 벌 나간다.
  - 실패는 **조용히 지나가지 않는다.** 이미 있는 실패 표현을 쓰고 새 표현을 만들지
    않는다.
  - History 를 다시 받으면 목록이 처음부터 다시 그려지므로 **스크롤이 맨 위로
    돌아간다.** 이것은 결함이 아니라 "전부 다시 받는다"의 값이며, 사용자가 그것을
    선택했다 (위 결정 표). 되돌릴 이유가 생기면 그때 별건으로 다룬다.

#### 3.6.4 I4 — live 행과 pin 행의 배지 자리를 맞춘다

**증상**(접수): "git 리스트에서 live 와 pin 의 수정사항 개수 위치가 다르다. live 는
pin 과 달리 삭제 버튼이 없어서 그 버튼 영역만큼 오른쪽으로 붙는다."

- **FR-GIT-239** GIT 섹션의 follow 행과 핀 행은 **오른쪽 끝 자리를 같게** 갖는다 —
  변경 개수 배지의 x 위치가 두 행에서 같다.
  - 수단은 **자리만 잡는 빈 칸**이다. follow 행에 `×` 를 만들지 않는다 — follow 는
    지울 수 있는 것이 아니다 (FR-GIT-193).
  - 이것은 이 저장소가 이미 쓰는 규약이다: **"자리는 늘 잡고 hover 에서만 보인다."**
  - 모바일의 다른 크기에서도 같아야 한다 — 자리 폭을 두 곳에 따로 쓰지 않는다.
    지금 모바일 폭은 `.git-repo-x` 에만 걸려 있어(`style.css:1390` 24px,
    `:1626` `--git-hit`) follow 행에는 적용될 대상이 없다. 빈 칸은 **같은 선언에서**
    폭을 받아야 한다.
  - 행 모양이 바뀌므로 `_gitRepoSig` 가 **새로 읽는 값을 함께 넣는다** (FR-RPT-2).

#### 3.6.5 I7 — 워크트리 관리 탭

**증상**(접수): "git 에 워크트리 생성·제거·관리 탭 및 기능 추가."

**경계가 이 항목의 핵심이다.** `internal/webserver/domain/worktree` 의 `Manager` 가
이미 Run 격리용 worktree 를 만들고 지운다. **사용자가 만든 worktree 를 Run 정리가
지우면 안 된다.**

- **FR-WKT-13** 사용자 worktree 의 영역은 `$DONGMINAL_HOME/git-worktrees` 이며, Run
  격리 영역 `$DONGMINAL_HOME/worktrees` 의 **형제**다. 두 영역은 교차하지 않는다.
  - 경로는 **파생**이다: `$DONGMINAL_HOME/git-worktrees/<repo>/<name>`. 사용자가
    경로를 직접 주지 않는다 — 서버가 임의 경로에 디렉터리를 만드는 표면을 열지 않는다.
  - **`<repo>` 는 저장소의 정체에서 파생한다** — 디렉터리 이름만으로 가르지 않는다.
    `<basename>-<정규화된 루트의 해시 앞자리>` 형태다.
    - 근거: 베이스이름만 쓰면 **서로 무관한 두 저장소가 같은 버킷을 공유한다**
      (계정이 다른 두 `app` 저장소를 각각 핀한 경우). 그러면 FR-GIT-242 의 "같은
      이름이 이미 있으면 거부한다"가 **남의 저장소 때문에** 발동하고, 최악의 경우
      두 저장소의 worktree 가 같은 경로를 다툰다.
    - 해시의 입력은 `Resolve` 가 만드는 **정규화된 저장소 루트**다. 사용자가 보낸
      문자열이 아니다 — 같은 저장소가 다른 표기로 오면 버킷이 갈라진다.
    - 베이스이름을 앞에 남기는 것은 FR-GIT-242 의 "만들어진 경로를 보인다"가
      사람이 읽을 수 있어야 한다는 뜻이기 때문이다. 순수 해시는 그 뜻을 잃는다.
    - Run 영역은 uuid 파생으로 재사용 불가를 **구조적으로** 보장하지만
      (FR-WKT-3·4), 사용자 영역은 이름을 사람이 정하므로 그 보장이 없다. 그래서
      충돌 검사가 필요하고, 검사의 범위가 **정확히 그 저장소**여야 한다.
  - 보호는 **두 겹**이며 둘 다 이미 있다.
    1. `Manager.checkPath` 는 자기 `root` **아래가 아니면** `unsafe_path` 로 거부한다
       (FR-WKT-10). 사용자 영역은 Run 영역의 형제이므로 Run 의 `Manager` 는 그 경로에
       **닿을 수 없다.**
    2. `Remove` 의 대상은 **Run 이 만든 worktree 만**이고 판정 근거는 Run 기록이다
       (FR-WKT-9). 기록에 없는 경로는 애초에 대상이 아니다.
  - 즉 **경로를 갈라 두는 것으로 구조적으로 안전하다.** 새 가드를 만들지 않는다.
- **FR-WKT-14** 위 보호를 **동작으로 고정한다** — Run 정리가 사용자 worktree 경로를
  거부한다는 것을 이름이 아니라 시험으로 세운다. 이름만으로 막으면 경로 규약이
  바뀔 때 조용히 열린다.

- **FR-GIT-28 (개정)** Git 창의 고정 탭은 **7개**다:
  `Changes / Diff / History / Branches / Stash / Console / Worktrees`. 이 탭들은
  생성·삭제되지 않는다.
  - 개정 근거: I7 이 요청한 것이 "관리 **탭**"이다. 기존 탭 안에 밀어 넣으면 Branches
    탭이 두 가지 일을 하게 된다.
- **FR-GIT-240** `Worktrees` 탭은 **활성 리포의 worktree 목록**을 보인다. 진실은
  `git worktree list` 다 — 이 목록이 그것과 다르면 사용자가 "어디 갔는가"를 헛갈린다.
  - 행은 **경로 · 브랜치(또는 detached) · 소유** 를 보인다.
  - **활성 리포 자신(main worktree)도 목록에 있다** — `git worktree list` 가 그것을
    포함하고, 빼면 목록이 진실과 달라진다. 다만 제거 대상이 아니다.
  - 소유는 **경로로** 판정한다: 사용자 영역 아래면 사용자 것, Run 영역 아래면 Run
    것, 그 밖이면 **바깥 것**(사용자가 터미널에서 직접 만든 것)이다.
- **FR-GIT-241** **Run 것과 바깥 것은 제거할 수 없다.** 제거 진입점을 만들지 않는다
  (비활성으로 보이지도 않는다 — 누를 수 없는 버튼은 고장으로 읽힌다, FR-GIT-180).
  - Run 것은 표식으로 구분한다. **이모지를 쓰지 않는다** (FR-GIT-187·192).
- **FR-GIT-242** 생성은 **이름 + 대상 ref** 를 받는다. 새 브랜치를 만들 것인지는
  선택이며, 만들지 않으면 그 ref 를 그대로 체크아웃한다.
  - 경로는 이름에서 파생한다 (FR-WKT-13). 사용자에게 경로를 묻지 않고, 만들어진
    경로를 **보인다** — 어디에 생겼는지 모르면 터미널에서 찾을 수 없다.
  - 이름·브랜치가 `-` 로 시작하면 거부한다 (FR-WKT-6 과 같은 근거: git 플래그 오인).
  - 같은 이름이 이미 있으면 거부한다. 조용히 다른 경로를 고르지 않는다.
- **FR-GIT-243** 제거는 **사용자 것만** 대상이다.
  - **더러운 worktree 는 거부하고 사유를 보인다.** 사용자의 작업을 지우지 않는다.
  - 브랜치를 함께 지우는 것은 **별도 선택**이며 기본이 아니다.
  - 파괴적 동작이므로 확인을 거친다 (기존 확인 규약 `GitConfirm` 을 쓴다).
- **FR-GIT-244** 행의 동작은 넷이다: **활성 리포로 열기 · 핀에 추가 · 터미널 탭
  열기 · 제거**.
  - "활성 리포로 열기"는 `gitPanel.setRepo` 를 지난다 — worktree 는 그 자신이 유효한
    git 저장소다.
  - "핀에 추가"는 기존 `_gitAddRepo` 경로를 그대로 쓴다.
  - "터미널 탭 열기"는 그 worktree 를 cwd 로 하며 **Git 창이 아닌 창**에 연다
    (FR-GIT-41·185 와 같은 경로).
  - 제거는 FR-GIT-243 을 따른다.
- **FR-GIT-245** 이 목록이 **바깥 계기로 다시 그려지면** FR-RPT-1·3 을 따른다. 행의
  `sig` 는 그 행이 읽는 값 전부다.
- **FR-GIT-246** worktree 의 git 실행은 **전부 `internal/webserver/domain/worktree`
  안에서** 한다. `domain/git` 의 명령 화이트리스트를 넓히지 않는다.
  - 근거: `readCommands`(`core/guard.go:19`)와 `writeCommands`(`core/write.go:20`)는
    **하위 명령 하나(`args[0]`)로만** 키잉되고, **두 목록의 교집합은 비어 있어야
    한다**는 불변식을 갖는다 (FR-GIT-95). 그런데 `git worktree` 는 한 하위 명령 안에
    읽기(`list`)와 쓰기(`add`·`remove`)가 함께 있다 — **어느 목록에 넣어도 불변식이
    뜻을 잃는다.** 읽기에 넣으면 `Exec` 로 `worktree remove` 가 나갈 수 있고, 쓰기에
    넣으면 `worktree list` 가 읽기 경로에서 막힌다.
  - `domain/worktree` 는 이미 `execAllowed`(`core/static_test.go:20`)의 **의도적
    예외**이며, `gone()` 이 그 안에서 `git worktree list --porcelain` 을 실행하고
    있다. worktree 를 그 패키지에 모으는 것은 새 예외를 만드는 것이 아니라 **이미
    있는 경계를 쓰는 것**이다.
  - `config` 가 같은 문제를 이미 한 번 풀었다 — 읽기 목록에 넣고 `guardConfigArgs`
    로 **읽기 플래그만** 허용한다. 그 길(=`guardArgs` 에 `worktree` 분기를 더해
    `list` 만 통과시키고 쓰기는 따로 두기)도 가능하지만 **택하지 않는다**: 읽기와
    쓰기가 두 패키지로 갈라져 `checkPath`·직렬화·잔여물 보고가 한쪽에만 있게 된다.
  - HTTP 표면은 기존 규약을 그대로 따른다 — 핸들러는 `internal/webserver/gitapi/`
    **바로 아래**에 둔다. 하위 디렉터리는 `execWriteAllowed`
    (`^internal/webserver/gitapi/[^/]*\.go$`, `core/write_test.go:35`)에 걸리며,
    `credScanDirs` 는 **재귀하지 않으므로**(`credentials_static_test.go:29`) 새 하위
    패키지를 만들면 자격증명 스캔에서 조용히 빠진다.
  - 사용자가 보낸 repo 경로는 `gitResolveRepo` 로 **실제 저장소 루트로 재확인**한
   뒤에만 쓴다 (`handlers_git_write.go:438`). 받은 문자열을 그대로 쓰지 않는다.
  - 보호 테스트 3개를 약화하지 않는다.
- **FR-WKT-7 (개정)** worktree 생성·제거의 **직렬화 단위는 저장소**다. Manager
  인스턴스가 아니다.
  - **왜 개정하는가**: 지금 `mu` 는 `Manager` 의 **인스턴스 필드**
    (`worktree.go:55`)인데, 그 존재 근거는 "`git worktree` 가 저장소의 공용
    common-dir 를 건드리므로 병렬 팬아웃에서 경합한다"(`worktree.go:53`)다. 근거는
    **저장소**를 말하고 구현은 **인스턴스**를 잠근다. Manager 가 하나뿐이어서
    (`cmd/dongminal/main.go:223` 이 유일한 생성 지점) 지금까지 둘이 같았다.
  - I7 이 사용자 영역용 **두 번째 Manager** 를 만들면 두 인스턴스가 각자의 `mu` 만
    잠근다. 사용자 worktree 와 Run worktree 는 **같은 저장소를 대상으로 할 수
    있으므로**, 그 순간 FR-WKT-7 이 막으려던 경합이 그대로 열린다.
  - 이것은 I7 이 만든 결함이 아니라 **I7 이 드러낸 기존 결함**이다. 자리마다 막지
    않고 근거가 말하는 단위로 올린다 (§2.1 의 교훈과 같다).
  - **잠금 키는 정규화된 저장소 루트다.** 지금 `Create`·`Remove` 는 `Spec.Repo` 를
    호출자가 준 그대로 쓰고 자체 정규화가 없다 — `Resolve` 가 만든 값을 호출자가
    그대로 넘겨준다는 **관례에 의존**한다. Manager 가 둘이 되면 그 관례가 두 곳에서
    지켜져야 하므로, 정규화를 **Manager 안으로** 옮긴다. 키가 다른 표현으로 들어오면
    직렬화가 조용히 갈라지고, 그것은 이 요구사항이 막으려던 것과 같은 실패다.
- **FR-GIT-247** 자격증명을 담을 자리를 만들지 않는다 (FR-GIT-104). worktree 는 원격
  인증에 닿지 않으므로 그 배제를 건드릴 이유가 없다.

#### 3.6.6 I5·I6 — 이번 판의 비대상 (사용자 결정, 2026-08-27)

**"나중에 다르게 구현한다"** 는 사용자 결정으로 범위에서 뺐다. 조사한 사실은 다음
판이 같은 자리를 다시 파지 않도록 남긴다.

- 접수한 말: I5 "단축키 — git 으로 바로가기 · git pin/live 리스트 순회" ·
  I6 "git 에서 창 순회 단축키로 window 로 돌아갈 때 원래 있던 윈도우로 우선 이동".
- **후보 ②(Git 창 안에서 `Ctrl+Shift+[ ]` 를 리포 순회로 재해석)와 I6 은 같은 키를
  두고 충돌한다.** I6 은 그 키가 **Git 을 떠나는 키**로 동작하기를 요구한다. 둘을
  함께 택할 수 없다.
- Git 창을 창 순회에 **합치는** 안은 `_cycleWindow` 의 `_plainWindows()` → 전체 창
  한 줄이지만, **FR-GIT-182 의 개정**이고 (그 조항이 폐기한 **FR-GIT-30 의 복원**이며)
  `e2e/git-window.spec.ts` **E7** · `e2e/git-ui-revision.spec.ts` **V72** 후반의 기대값을
  뒤집는다. 약화가 아니라 뒤집기로 처리해야 한다.
- 합치면 I6 이 **자동으로 만족되지 않는다**: Git 창은 생성 시 `ws.windows` 맨 뒤에
  push 되므로 순회로 나가면 배열 순서상 인접 창이며, "직전에 보던 창"이 아니다.
- 필요한 상태는 이미 있다 — `_lastPlainWindow` (FR-GIT-185, Open File 이 딛는 값).
- 리포 순회는 **순회 통합으로 해소되지 않는다**: Git 창은 워크스페이스에 하나뿐이고
  (FR-GIT-26) 활성 리포는 그 창에 붙는 값이다 (`git:{repo}`, FR-GIT-29).

## 5. 결정 (Decisions)

| # | 결정 | 대안 | 근거 |
|---|---|---|---|
| D1 | E1 을 **요소 상태 보존**으로 막는다 | hover 중에만 다시 그리기를 미룬다 | hover 는 증상 하나일 뿐이다. 더블클릭·드래그·선택·툴팁도 같은 원인으로 깨지므로 원인 쪽에 방어를 둔다 |
| D2 | 관측 동일성(FR-RPT-1)과 행 동일성(FR-RPT-3)을 **둘 다** 넣는다 | 하나만 | 앞의 것은 조용한 상태의 churn 을 없애고, 뒤의 것은 값이 실제로 바뀌는 동안에도 제스처를 지킨다. 둘은 다른 실패를 막는다 |
| D3 | 폴링 주기를 바꾸지 않는다 | 주기를 늘려 깜빡임을 줄인다 | 감지 지연이 늘어 FR-GIT-18~24·FR-STAT-17 의 뜻이 약해진다. 증상을 덮는 것이지 고치는 것이 아니다 |
| D4 | **공통 수단 하나**를 만들고 목록이 그것을 쓴다 (FR-RPT-6) | 자리마다 가드를 손으로 쓴다 | 이미 네 곳에서 네 번 다르게 막았고, 여섯 곳이 빠졌다. 다음 목록에서 또 빠진다 |
| D5 | #4 는 FR-RPT-1 만, #3 은 FR-RPT-3 을 적용한다 | 둘 다 FR-RPT-1 로 통일 | 처음에는 #3 도 FR-RPT-1 로 두었는데 **검증에서 듣지 않는 것이 드러났다** — 지연·CPU·업타임이 매초 달라 컨테이너 단위 판정이 거의 늘 "달라졌다"가 된다(V109 가 그때 실패했다). 지표를 항목으로 다루니 값이 그대로인 git chip 의 툴팁이 지켜진다. #4 는 한 기록이 행+상세 두 요소로 펼쳐져 키 하나에 요소 하나가 대응하지 않으므로 FR-RPT-1 로 둔다 — 그 자리의 실제 증상(2초마다 선택 소실)은 그것으로 사라진다 |
| D6 | `_rLayout` 은 남기고 **적는다** | 함께 고친다 | §3.2.1. 판정 근거가 레이아웃 트리 전체라 FR-RPT-2 를 못 지키면 레이아웃이 얼어붙는다. 계기도 실제 변경이고 핫 경로가 아니다 |
| D7 | 색 키를 **희소 레인**에 붙인다 | 갈래마다 새 색을 배정하고 대장을 관리한다 | 희소 레인 인덱스는 이미 갈래가 사는 동안 유지된다. 새 상태를 만들지 않는다 |
| D8 | 배지의 단일 클릭은 **아무 일도 하지 않는다** | refs 사이드바처럼 필터를 걸거나, 행으로 전파해 상세를 여닫는다 | 전파하면 첫 클릭이 행 창을 다시 만들어 더블클릭이 깨진다(§2.1). 필터는 요청에 없는 동작이다 |
| D9 | 태그 배지는 더블클릭 대상이 아니다 | detached 경고를 거쳐 체크아웃한다 | FR-GIT-222 의 확정 결정을 그대로 따른다 — 경고가 필요한 것을 가벼운 제스처에 싣지 않는다 |
| **D11** | **Git Graph 의 규칙을 그대로 따른다** — 열이 비면 통과선을 왼쪽으로 당기고, 그 이동을 그 행 안에서 곡선으로 이어 그린다 | 선을 태어난 열에 고정하고 빈 열을 남긴다 | 사용자가 기준으로 든 도구가 그렇게 한다 (§2.3.1 의 R1·R2 — `nextX`/`getNextPoint`). "선은 혼자 휠 수 없다" 는 규칙은 그 도구의 동작이 아니며, 그것을 따르면 가운데 갈래가 끝난 자리가 영구히 비어 원래 접수한 증상(E2)이 남는다. 대신 **오른쪽으로는 절대 움직이지 않는다** 는 더 강한 불변식을 FR-GIT-234 로 세웠다 |

| **D13** | FR-WKT-7 의 직렬화 단위를 **저장소로 올린다** | 두 번째 Manager 를 만들지 않고 사용자 worktree 도 Run Manager 의 root 아래에 둔다 | 후자는 `checkPath` 가 주는 구조적 보호를 포기하는 것이다(I7 경로 결정의 근거 전체가 무너진다). 직렬화는 근거가 이미 "저장소의 공용 common-dir" 이므로, 단위를 올리는 것이 구현을 근거에 맞추는 일이다 — 새 개념을 만들지 않는다 |

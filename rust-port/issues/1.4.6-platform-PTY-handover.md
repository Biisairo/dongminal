# 1.4.6 platform PTY·handover

## 목표

의사 터미널(POSIX openpty + 읽기 게이트, Windows ConPTY)과 데몬 교체용 handover(Freeze·Thaw·MasterFD, AdoptTerminal, PTYMasters, ChildTTYs, CloseSocketsBoundTo, SetCloseOnExec)를 옮긴다. FR-RSP-22(Go 데몬→Rust 데몬 handover)의 OS 쪽 바탕이다. 공개 API 는 부모 이슈 1.4 의 진행 기록 "공개 API 안" 을 따른다. 바꿔야 하면 조정자에게 먼저 알린다.

## 대상 Go 코드

- `internal/shared/platform/pty*.go`, `handover*.go` (약 1000줄)

## 완료 조건

- 대상 Go 코드의 관측 동작을 Rust 가 동등하게 제공한다 (FR-RSP-1·3)
- 관측 동작을 검증하는 Go 테스트가 Rust 테스트로 옮겨져 통과한다 (V-RSP-1)
- `cargo fmt --check`, `cargo clippy -D warnings`, 격리 실행 `cargo test` 통과 (NFR-RSP-4)
- OS 의존 코드가 있으면 windows·linux 대상 `cargo check` 통과 (NFR-RSP-5)
- 작업 전후 `rust/scripts/prod-pids.sh` 출력이 같다 (V-RSP-5)
- 진행 기록에 공개 API 요약과 Go 와 다르게 한 내부 결정이 있다

  - 고친 파일: `pty.rs`, `pty/posix.rs`(+tests), `pty/windows.rs`, `handover.rs`, `Cargo.toml`(windows-sys `Win32_System_Pipes` 를 더했다)
  - **공개 API**
    - `Pty::start(ProcSpec, cols, rows) -> io::Result<Box<dyn Terminal>>`
    - `Terminal { read, write, close, resize, size, foreground_pgid, pid, wait -> ExitStatus, terminate, kill, handover }`(모두 `&self`, `Send + Sync`). read 의 `Ok(0)` 이 EOF 다.
    - `closed_error()`(Go `os.ErrClosed` 문구 "file already closed")
    - `Handover { freeze, thaw, master_fd -> usize }`, `Frozen`, `is_frozen`
    - `adopt_terminal(fd: usize, pid) -> io::Result<Box<dyn Terminal>>`
    - `ChildTty { pid, tty }`, `pty_masters(&HashSet<usize>)`, `child_ttys(ppid)`, `command_name(pid)`, `close_sockets_bound_to(&[&str])`, `set_close_on_exec(fd, on)`
  - **Go 와 바이트 단위로 맞춘 관측 동작**
    - 자식은 새 세션의 리더이고 슬레이브가 제어 터미널이다(creack/pty 와 같다).
    - **argv·환경은 자식에서 execve 로 직접 넘긴다.** std `Command::envs` 는 환경을 이름순으로 정렬하므로 쓰지 않았다. 환경은 Go 와 같이 중복을 정리한 뒤 원래 순서로 넘기며, 검사로 확인했다.
    - 구분자가 없는 실행 파일 이름은 이 프로세스의 PATH 로 찾는다. 1.4.3 의 공용 `look_path` 를 쓴다.
    - 오류 문구는 Go 와 같다: `pty start P (cwd=D): exec: "x": executable file not found in $PATH` / `chdir D: …` / `fork/exec P: …`, `fd N 는 의사 터미널이 아닙니다: bad file descriptor`, `셸 pid 가 아닙니다: N`
    - 읽기 게이트: 깨우기 파이프와 함께 poll 하고, freeze 중의 출력은 커널 버퍼에 남는다(NFR-DSK-2).
    - Windows 는 ConPTY 다. 명령줄은 x/sys v0.36.0 `ComposeCommandLine`·`EscapeArg` 와 같으며 go1.27.2 실측값으로 검사했다. 환경 블록은 Go `envBlock` 과 같다(비면 물려받는다).
  - **FR-RSP-22 관련**: handover 에서 이 crate 가 맡는 OS 쪽은 다음 넷이다.
    1. 마스터 fd 의 close-on-exec 조작
    2. fd 와 단말 이름의 짝
    3. 직계 자식의 단말
    4. 넘겨받은 fd 로 터미널 다시 세우기(셸은 waitpid 로 거둔다)

    fd 전달의 **프레이밍**(어느 fd 가 어느 세션인지 적는 메시지)은 `internal/shared/handover`·`daemon/swap` 의 일이다. 이 이슈의 범위 밖이므로 해당 이슈가 Go 와 맞춘다. 시험은 모두 격리 실행에서, 이 프로세스가 띄운 셸로만 했다. 운영 데몬에는 손대지 않았다.
  - **테스트**
    - platform 전체 221개 통과(1.4.3·1.4.5 분 포함). 이 이슈 분은 약 30개다.
    - 옮긴 Go 테스트: pty·pty_posix·pty_handover_posix·pty_windows_resize 의 관측 검사 전부(windows 것은 Windows 에서만 컴파일된다).
    - 더한 검사: 환경 순서, 제어 단말·세션, EOF, Wait 두 번, 끝난 뒤 kill, 오류 문구, 실기 pty_masters·child_ttys·command_name·close_sockets_bound_to·close-on-exec.
    - PTY 테스트를 세 번 반복해 흔들림이 없음을 확인했다.
  - **게이트**: fmt, 다섯 대상 clippy -D warnings, 격리 테스트를 통과했다.
  - **Go 와 다르게 한 내부 결정**
    1. `wait` 는 오류 대신 `ExitStatus` 를 돌려준다(승인된 API). Go 의 `exit status N` 문구가 필요하면 소비자가 만든다.
    2. 띄운 셸을 두 번 Wait 하면 "exec: Wait was already called" 다. 거둔 뒤의 kill 은 "os: process already finished" 다(Go 와 같다).
    3. Windows 의 파이프는 `Arc<File>` 로 든다. close 는 자리만 비우고, 막혀 있는 read 가 끝난 뒤에 핸들이 닫힌다(Go os.File 과 같다).
  - **남은 위험**
    1. ConPTY 와 Windows 의 handover 쪽 빈 구현은 실기에서 돌려 보지 않았다(8.3).
    2. windows-sys 는 CreatePseudoConsole 을 정적으로 링크한다. 그래서 1809 미만의 Windows 에서는 바이너리가 아예 뜨지 않는다. Go 는 지연 로드해 오류 문구를 냈다. 최소 버전이 1809(C-1)이므로 관측 차이는 그 미만 OS 에서만 생긴다.
    3. 공용 `look_path` 는 "현재 폴더에서 찾음(ErrDot)" 을 None 으로 합친다. 그래서 그 경우 Go 의 "cannot run executable found relative to current directory" 대신 not found 문구가 나온다.
    4. POSIX 의 ProcSpec 환경 항목 중 `=` 가 없는 것도 Go 처럼 execve 에 그대로 넘긴다. NUL 이 든 항목은 오류다.
  - 끝 prod-pids.sh(시작과 같다): `38173 start --foreground` / `58470 d --handover-fd`
- 2026-11-23 보안 검토 반영(커밋 f5f9a8fd). 거둔 셸의 pid 는 다른 프로세스가 다시 쓸 수 있다. 그래서 거둔 뒤의 terminate·kill 은 신호를 보내지 않고 "os: process already finished" 를 돌려준다. 적용 범위: POSIX 는 넘겨받은 셸도 waitpid 뒤 표시하고, Windows 는 종료가 기록된 뒤다.
  **Go 와 다른 점:** Go 는 넘겨받은 셸과 Windows 에서 pid 로 그대로 kill 했다. 경합에서만 드러나는 차이이고, 잘못된 프로세스를 죽이지 않는 쪽으로 정했다. 테스트 221개 통과, 세 대상 clippy 통과.

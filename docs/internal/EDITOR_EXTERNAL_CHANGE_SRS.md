## 1. 개요

### 1.1 목적

편집기로 연 파일이 **밖에서 바뀌었을 때** 무엇을 보여줄지 정한다.

접수한 말 그대로다:

> *"사용자가 editor 에서 수정에 들어가기 전, 즉 파일을 열기만 하고 수정하기 전에는
> 해당 파일이 외부에서 수정·저장되면 그대로 바뀌어야 할 것 같다. 이게 맞는
> 동작인 것 같다."*

### 1.2 범위

`FileEditor` 가 연 텍스트 파일. 이미지·이진은 대상이 아니다(열지 않으므로).
git diff 뷰(`file-editor-diff.js`)는 자기 갱신 규약이 따로 있으며 이 문서 밖이다.

### 1.3 정의

| 말 | 뜻 |
|---|---|
| **clean** | 연 뒤 한 글자도 고치지 않은 상태 (`_dirty === false`) |
| **dirty** | 고쳤고 아직 저장하지 않은 상태 |
| **경합** | 우리가 읽은 뒤 디스크의 그 파일이 바뀐 것 |
| **표식** | 그 시점의 파일을 가리키는 **불투명 문자열**. 서버가 만들고 서버만 읽는다 |

## 2. 현재 상태 (조사로 확정한 사실, 2026-09-11)

### 2.1 `refresh()` 는 있는데 **dirty 를 보지 않는다**

`file-editor.js` 의 `refresh()` 는 파일을 다시 읽어 내용이 다르면 `setValue` 한다.
내용이 같으면 넣지 않는다 — `setValue` 가 커서를 1,1 로 되돌리고 undo 스택을
버리기 때문이다 (`FR-LSP-26b`).

**그러나 `_dirty` 를 확인하지 않는다.** 그래서 지금도 편집 중인 파일을 그 경로로
지나가면 편집본이 디스크 것으로 덮인다.

### 2.2 자동 감지는 **없다**

`refresh()` 를 부르는 자리는 둘뿐이다.

| 자리 | 계기 |
|---|---|
| `app-layout.js:480` | **이미 열린 파일을 다시 열 때** |
| `app-reload.js` | 내부 새로고침 |

즉 파일을 열어 둔 채 보고 있는 동안 밖에서 바뀌어도 화면은 그대로다.

### 2.3 파일 단위 감시 수단이 없다

`/api/fs/stamp` 는 **디렉터리** 감시이고 탐색기가 쓴다. `/api/file/probe` 는
`{kind, mime, size, maxBytes}` 를 주며 **`mtime` 이 없다.**

### 2.4 저장은 경합을 보지 않는다

`POST /api/file/write` 는 받은 내용을 그대로 쓴다. 우리가 읽은 뒤 디스크가
바뀌었는지 묻지 않는다 — **마지막에 저장한 쪽이 이긴다.**

### 2.5 편집기의 저장은 실패를 **닫기 경로에 알리지 않는다** (2026-09-11 추가)

`FileEditor.save()` 는 아무것도 반환하지 않고 실패를 `catch` 로 삼킨다. 탭 닫기의
"저장 후 닫기" 는 `await editor.save()` 뒤 **무조건 닫는다**
(`app-layout.js:580`). 바로 위의 git diff 경로는 같은 자리에서
`if(r==='save'&&!await this._gitViewSave(...)) return` 으로 **닫지 않는데**
(주석: *"저장이 실패하면 닫지 않는다 — 저장한 줄 알고 닫는 것이 곧 손실이다"*),
편집기 경로에만 그 가드가 없다.

지금은 실패가 드물어 드러나지 않았다. **경합(§3.3)을 들이는 순간 이것이 손실
경로가 된다** — 경합으로 저장이 막혔는데 탭이 닫힌다. `FR-RTU-103` 이 막으려던
바로 그것이다.

## 3. 요구사항

### 3.1 묶음 C — clean 일 때 (요구의 본문)

**FR-EXC-1** clean 인 편집기는 외부 변경을 **반영한다.** 내용이 같으면 넣지
않는다 (`FR-LSP-26b` 그대로 — 커서와 undo 를 지킨다).

**FR-EXC-2** 반영은 조용하다. clean 이었으므로 잃을 것이 없고, 물어볼 일도 없다.

### 3.2 묶음 D — dirty 일 때 (사용자 판정 2026-09-11)

**FR-EXC-3** dirty 인 편집기는 **건드리지 않는다.** 외부에서 바뀌었어도 편집본이
화면에 그대로 남는다.

> 접수한 판정: *"그냥 놔두고 저장하려 할 시 경합."*
>
> `U-10` 이 같은 값을 이미 치렀다 — 편집을 확인 없이 잃는 것이 이 제품에서 가장
> 비싼 실패다 (`FR-RTU-103`).

**FR-EXC-4** `refresh()` 는 **dirty 면 내용을 넣지 않는다.** §2.1 의 자리를 고치는
것이 이 요구다 — 자동 감지를 붙이지 않더라도 지금 있는 경로만으로 편집본이 덮인다.

### 3.3 묶음 S — 저장할 때 (경합)

**FR-EXC-5** 저장은 **경합을 검사한다.** 우리가 읽은 뒤 디스크의 그 파일이
바뀌었으면 그대로 덮지 않는다.

**FR-EXC-6** 검사의 재료는 서버가 정한다 — 읽을 때 준 표식을 저장 때 함께 보내고,
서버가 **자기가 아는 현재 값**과 견준다. 클라이언트가 스스로 판정하지 않는다:
판정을 클라이언트에 두면 두 창이 같은 파일을 볼 때 서로 다른 답을 갖는다.

**FR-EXC-7** 경합이면 **409** 다. 사용자에게는 그 사실과 선택지를 보인다 (`FR-EXC-9`).

**FR-EXC-11** 표식은 **불투명하다** (사용자 결정 2026-09-11). 클라이언트는 받은
문자열을 그대로 돌려보낼 뿐 해석하지 않는다.

- 읽을 때: `GET /api/file/read` 가 응답 **헤더** `X-File-Stamp` 로 준다. 본문은
  파일 원문이므로(`FR-CAPI-11`) 실을 자리가 거기뿐이다. `ETag` 를 쓰지 않는 것은
  브라우저의 조건부 GET 이 끼어들어 304 를 만들 수 있어서다.
- 저장할 때: `POST /api/file/write` 의 본문에 `stamp` 로 싣는다. 성공 응답은
  **새 표식**을 함께 준다 — 없으면 연속 저장의 두 번째가 스스로 경합이 된다.
- **내부 구성은 계약이 아니다.** 지금은 `mtime`(나노초)+크기이며 `os.Stat` 한 번이라
  싸다. 정밀도가 모자란 파일시스템이 문제가 되면 내용 해시로 바꾸며, 그때
  클라이언트는 한 줄도 바뀌지 않는다 — 그것이 불투명하게 두는 이유다.

**FR-EXC-6a** 표식이 **없는** 요청은 종전대로 통과한다. 옛 클라이언트와 표식을
가질 길이 없는 호출자(§2.4 의 공개 종단)를 막지 않는다.

### 3.4 묶음 P — 감지 (사용자 판정)

**FR-EXC-8** **폴링하지 않는다.** 접수한 판정은 *"파일 저장 시도할 때"* 다.
반영의 계기는 이미 있는 것들로 충분하다 — 탭으로 돌아올 때(§2.2)와 저장 시도다.

> 폴링을 두지 않는 이유는 비용만이 아니다. 열린 편집기 수만큼 종단이 늘고, 그
> 주기가 또 하나의 설정이 된다 (`POLL_INTERVAL_SETTINGS_SRS`). 지금 접수된 요구는
> 그것 없이 성립한다.

### 3.5 묶음 U — 경합 화면 (사용자 결정 2026-09-11, §6 미해결 1 해소)

**FR-EXC-9** 경합이면 **확인창 하나**를 띄운다. 버튼은 둘이다 — `취소` 와
**`내 것으로 덮어쓰기`**.

- **`디스크 것으로 덮기` 는 두지 않는다.** 그것은 편집본을 확인 없이 버리는
  쪽이고 `FR-RTU-103`(`U-10`)과 정면으로 걸린다. 그 선택지를 안전하게 주려면
  확인을 한 번 더 물어야 하는데, 그러면 확인이 두 걸음이 되어
  `CONFIRM_ONE_STAGE_SRS` `FR-COS-1` 과 충돌한다.
- `취소`하면 **편집본은 화면에 그대로 남고 dirty 도 그대로다** (`FR-EXC-3`).
  디스크도 그대로다. 사용자가 스스로 처리할 수 있는 상태로 둔다.
- `덮어쓰기`는 같은 내용을 **표식 없이** 다시 보낸다 (`FR-EXC-6a` 의 길). 그 한
  번은 사용자가 방금 명시적으로 승인한 것이다.

**FR-EXC-9a** 초기 포커스는 **`덮어쓰기`** 다 — `FR-PDA-1`. 이 창은 사용자가
저장을 누른 결과로 열리므로 목적 버튼이 저장 쪽이다. 안전은 **확인창이 존재한다는
사실**과 `Esc` 가 진다 (`POPUP_DEFAULT_ACTION_SRS` D-2). 기제는 `UIKit.modal` 이며
목적 버튼을 스스로 정한다 (`FR-PDA-11` — `kind:'danger'`).

> 이 조항은 2026-09-11 의 설계 검토에서 한 번 반대로 적힐 뻔했다. 이 저장소는
> 2026-09-10 에 *"UX 는 사용자가 하고자 했던 걸 유지하는 방향이지, 안전한 방향이
> 아니다"* 로 **"파괴적이면 취소를 기본으로" 라는 절충안을 이미 기각했다.**
> 새 확인창이 그 결정 이전으로 돌아가지 않게 여기 적어 둔다.

### 3.6 묶음 R — 외부 삭제 (사용자 결정 2026-09-11, §6 미해결 2 해소)

**FR-EXC-10** 열어 둔 파일이 밖에서 지워져도 **탭을 닫지 않는다.** clean 이든
dirty 든 같다 — 탭을 자동으로 닫으면 사용자가 보던 내용이 화면에서 사라지고,
그것이 `FR-EXC-3` 과 같은 손실이다.

**FR-EXC-10a** 없어진 파일에 저장하면 **새로 만든다.** 삭제는 **경합이 아니다** —
덮어쓸 상대가 없으므로 표식이 달라졌는지 물을 것도 없다. 서버는 표식을 받았더라도
대상이 없으면 그대로 쓴다.

**FR-EXC-10b** `refresh()` 가 읽기에 실패해도(404) 화면을 비우지 않는다. 종전
동작이며(catch 로 지나간다) 이 요구는 그것을 **계약으로 못박는다.**

### 3.7 묶음 L — 저장 실패는 닫기를 막는다 (§2.5 의 자리)

**FR-EXC-12** `FileEditor.save()` 는 **성공 여부를 반환한다.** 저장하지 못했으면
거짓이다 — 경합에서 취소한 것도 거짓이다 (쓰이지 않았으므로).

**FR-EXC-13** 저장이 실패하면 **탭도 창도 닫지 않는다.** git diff 경로가 이미
그렇게 한다(§2.5) — 편집기 경로를 그 계약에 맞춘다.

  - 이전 동작: `if(result==='save'){ await editor.save() }` 뒤 무조건 닫는다
  - 새  동작: 저장이 거짓을 주면 `return` — 탭이 남고 dirty 도 남는다
  - 이유: `FR-RTU-103`. 저장한 줄 알고 닫는 것이 곧 손실이다. 경합을 들이면서
    이 가드가 없으면 **이 스펙 자체가 손실 경로를 만든다**

**FR-EXC-13a** 창 닫기의 일괄 저장(`_edWinSaveDirty`)도 같다. 하나라도 저장하지
못했으면 거짓을 주고, 창은 닫히지 않는다.

**FR-EXC-14** **저장 왕복 중의 편집은 저장된 것으로 치지 않는다** (사용자 보고
`U-23`, 2026-09-11).

`save()` 는 시작 시점의 `getValue()` 를 담아 보낸다. 그 뒤의 `await` 는 망 왕복이고,
그 사이의 타이핑은 **그 요청에 들어 있지 않다.** 그런데 성공 처리가 `dirty` 를
무조건 내렸다.

  - 이전 동작: 왕복 중에 편집이 있어도 `doc.dirty = false`
  - 새  동작: 담아 간 판본(`model.getAlternativeVersionId()`)이 달라졌으면
    `dirty` 를 **유지한다**. 표식(`stamp`)은 서버가 준 새 값으로 갱신한다 —
    디스크는 실제로 우리가 쓴 그 내용이다
  - 이유: 내리는 순간 그 편집은 화면에서 저장된 것처럼 보이고(탭의 `●` 가
    사라진다), 다음 `Ctrl/Cmd+S` 는 `save()` 의 첫 줄 `if (!this._dirty) return
    false` 에 걸려 **아무 말 없이** 되돌아간다. 사용자가 접수한 *"한 번씩 저장이
    안 되고 파일을 닫고 다시 열면 가능해진다"* 가 이것이며(닫고 열면 새 문서가
    서면서 플래그가 리셋된다), **실제로 일어난 일은 그 사이 편집의 유실**이다.
    원격 접속처럼 왕복이 긴 자리에서 자주 겹친다

되돌리기를 셈에 넣는 판본 값을 쓰는 이유는, 쳤다가 `Cmd+Z` 로 되돌리면 내용이
담아 간 것과 같아지기 때문이다 — 그때는 내리는 것이 옳다.

## 5. 비목표

1. **폴링·파일 감시** (FR-EXC-8). 접수된 요구가 그것 없이 성립한다.
2. **세 갈래 병합.** 경합은 알리고 고르게 하는 것까지다. 병합은 편집기의 일이 아니다.
3. **`디스크 것으로 덮기` 선택지** (FR-EXC-9). 편집본을 버리는 길을 한 걸음
   확인창에 둘 수 없다.
4. **diff 뷰**(`file-editor-diff.js`). 자기 갱신 규약이 따로 있다.
5. **탐색기·전송 종단의 경합.** `/api/fs/*` 와 `/api/upload` 는 표식 규약 밖이다 —
   이 문서가 정하는 것은 **편집기가 연 파일의 저장**이다.

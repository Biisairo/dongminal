# SRS: 알람의 발화 조건과 포커스와의 공존 — IEEE 29148

> **문서 상태**: 승인·구현완료

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 두 줄이다.

> 1. 알림 깜빡임이 focus 에 가려서 보이지 않아. 원래는 깜빡임이 없기 때문에 순서를
>    알림-포커스 순서로 했지만 이제 꺼졌다 켜졌다 하면서 깜빡이기 때문에 포커스
>    위에 있어도 포커스와 알람을 동시에 볼 수 있어 수정해보자.
> 2. 알람이 없어야할 곳에서 울리고 있어야할곳에서 울리지 않는 현상이 여전히 있어.
> 3. claude code 가 대기중인 상태에서도 계속 알람을 만든다. (2026-09-06 재접수 — §1.8)

1 은 확정된 지시다. 2 는 재접수다 — 같은 말이 한 번 처리된 적이 있으나
([`ATTENTION_LIFECYCLE_GIT_OBSERVE_SRS`](./ATTENTION_LIFECYCLE_GIT_OBSERVE_SRS.md)),
그 문서는 §6 비목표에서 **"L2 idle 임계값·OSC 감지·`dmctl notify` 의 규약은
건드리지 않는다"** 고 선을 그었다. 그때 고친 것은 알람의 **수명**이고, 이번에
고칠 것은 알람의 **발화 조건**이다. "여전히" 라는 말이 가리키는 것이 그 선의
바깥이다.

### 1.2 범위 (Scope)

**포함:**

| 묶음 | 이름 | 접수 항목 |
|---|---|---|
| **묶음 V** | 포커스와 알람의 동시 가시성 (Visible) | 1 |
| **묶음 A** | 해제는 실제 상호작용으로 (Attend) | 1·2 |
| **묶음 F** | 발화 조건 (Fire) | 2 |
| **묶음 N** | 알람은 새 사건에만 (Novel) | 3 — §1.8 |

묶음 V 와 A 가 한 문서에 있는 이유는 **둘이 같은 뿌리**이기 때문이다 (§2.3).
표식을 그리기만 하고 해제 규칙을 두면, 포커스된 칸의 알람은 그려지는 즉시
지워져 여전히 보이지 않는다.

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **주의(attention)** | 도구가 사용자를 부르는 상태. `Tool.attention` / `AttnTracker.attention` |
| **활동(activity)** | 에이전트가 지금 무엇을 하는지. 주의와 직교하는 별개 레이어 |
| **무장(armed)** | L2 idle 이 발화할 수 있는 상태. 출력이 세우고, 발화·해제가 내린다 (`attnArmed`) |
| **재무장(rearm)** | 내려간 무장이 다시 서는 것 |
| **주목(attend)** | 사용자가 그 도구를 실제로 만진 사건. 클릭 또는 키 입력 |
| **에이전트 도구** | 활동을 보고한 적이 있고 아직 세션이 끝나지 않은 도구 (FR-ATF-1) |
| **L1** | OSC 알림 시퀀스 감지 + `dmctl notify` 명시 신호 |
| **L2** | 출력 정적(靜寂)으로 판정하는 idle 알람 |

### 1.7 AS-2 는 반증되었다 (2026-09-04)

접수한 말은 이것이다.

> **"알람이 있을때 크롬배너가 안떠"**

조사로 원인을 확정했다. 브라우저와 macOS 는 정상이었고(사용자가 콘솔에서
`new Notification` 을 띄워 확인했다), 막고 있던 것은 **AS-2 의 억제**였다.

관측으로 억제의 경계를 확인했다.

| 상황 | `new Notification` |
|---|---|
| 보고 있는 그 탭에 알람 | **억제** |
| 다른 탭의 도구에 알람 | 뜬다 |
| 다른 앱을 보는 중 | 뜬다 |

**가정이 놓친 것은 이 앱의 쓰임새다.** AS-2 는 "눈앞에 있는 것을 다시 부르는 것은
방해" 라고 보았는데, 이 앱에서 알람이 서는 가장 흔한 순간이 바로 **에이전트가
도는 것을 지켜보다 끝나는 순간**이다 — 그때 사용자는 그 탭을 보고 있고, 그래서
배너가 한 번도 뜨지 않았다. 방해를 막으려던 조건이 기능 자체를 막고 있었다.

그러므로 **억제를 없앤다.** 소리와 데스크톱 알림은 각각 설정에 끄는 스위치가 이미
있으므로(Settings ▸ Notifications), 시끄러움에 대한 판단은 그 스위치가 맡는다 —
우리가 사용자를 대신해 짐작하지 않는다.

**판정 함수 자체는 남는다.** `_attnUserIsWatching` 은 OSC 52 복사창의 게이트가
빌려 쓰고 있으며(FR-ETR-44), 그쪽에서는 그 물음이 여전히 옳다 — 한 도구의 출력이
붙어 있는 모든 브라우저로 가므로, 복사창은 **보고 있는 창에만** 서야 한다.

### 1.8 대기 중에도 알람이 선다 (2026-09-06 재접수)

접수한 말은 한 줄이다.

> **"claude code 가 대기중인 상태에서도 계속 알람을 만든다"**

관측으로 재현했다. 실서버(`/api/commands/sse`)에 붙어 알람 이벤트만 걸러 받은
3분간의 기록이다.

```
22:06:53  tool_attention  reason=done     01a0768a
22:07:00  tool_attention_clear            01a0768a
22:07:17  tool_attention  reason=done     01a076cf   ← 이하 넷은 같은 도구
22:07:22  tool_attention  reason=waiting  01a076d2
22:07:25  tool_attention  reason=done     01a076cf
22:07:34  tool_attention  reason=done     01a076cf
22:07:56  tool_attention  reason=done     01a076cf
```

`01a076cf` 는 그 3분 동안 **사용자 입력을 한 번도 받지 않았다.** 백그라운드 작업
알림으로 깨어난 턴이 끝날 때마다 Claude Code 의 `Stop` 훅이 발화했고, 그것이
그대로 알람이 되었다. 배경 이벤트를 끊자 즉시 멈췄다.

### 1.9 인터뷰로 확정한 결정 (2026-09-06)

| # | 물음 | 확정 |
|---|---|---|
| **D-4** | `Stop` 훅의 `done` 알람을 언제 낼까 | **사용자 프롬프트로 시작된 턴이 끝났을 때만.** 배경 이벤트로 깨어난 턴의 종료는 사용자를 부를 사건이 아니다 |

| **D-6** | 유휴인지 권한 요청인지를 무엇으로 가를까 | **서버가 이미 가진 활동 상태로.** 훅 메시지 문자열에 기대지 않는다 — 문구는 에이전트 판이 바뀌면 갈린다 |

## 2. 전체 설명 (Overall Description)

### 2.1 감사로 확정한 사실

| # | 사실 | 근거 |
|---|---|---|
| **B1** | L2 idle 의 판정은 "전경 프로세스가 있고 임계 시간 조용" 이 전부다. **에이전트인지 묻지 않는다** | `toolhub/tool.go:maybeIdle`, `hub/attn_tracker.go:sweepIdle` |
| **B2** | 무장은 출력 한 조각으로 무조건 선다. 해제 뒤에도 마찬가지다 | `tool.go:observeOutputAt`, `attn_tracker.go:FeedOutput` |
| **B3** | `working` 억제는 **상태만 보고 갱신 시각을 보지 않는다** | 같은 두 함수 |
| **B4** | 알람 표식은 포커스된 칸·활성 탭에서 **그려지지 않는다** | `app-attn.js:_attnRefresh` — `!(focusedPane&&active)`, `!pn.classList.contains('focused')` |
| **B5** | 분할 칸의 알람 링은 포커스 테두리를 **덮는다.** 링은 `inset:-2px` 의 겹에 `inset 0 0 0 3px` 로 그려지고, 포커스는 요소의 2px `border` 다 | `style.css:150,220` |
| **B6** | 포커스를 얻는 **모든 경로**가 알람을 해제한다 — `_setFocus`, `window.focus`, `_attnRestore`, 그리고 알람이 뜨는 순간의 `_onToolAttention` | `app-attn.js`, `app-focus.js` |

### 2.2 B1~B3 이 "없어야 할 곳의 알람" 이다

B1 로 `vim`·`less`·`top`·`ssh`·빌드 대기가 전부 알람을 낸다. 전경 프로세스가
있다는 것은 "무언가 돌고 있다" 는 뜻이지 "나를 기다린다" 는 뜻이 아니다.

B2 가 그것을 되풀이하게 만든다. TUI 는 유휴 상태에서도 화면을 갱신하므로, 한 번
해제한 알람이 출력 한 조각으로 되살아나 임계 시간 뒤 다시 운다. 사용자가 그 칸을
보지 않는 한 이 고리는 멈추지 않는다.

### 2.3 B3~B6 이 "있어야 할 곳의 침묵" 이다

B3: 훅이 끊긴 채 `working` 으로 굳은 도구는 idle 알람이 **영구히** 억제된다.
관측 시점의 서버에도 30분째 `working` 인 도구가 실제로 있었다.

B4·B5·B6 은 하나의 사슬이다. 알람이 포커스된 칸에서 뜨면 — 브라우저가 뒤에 있는
동안 뜬 알람이 그렇다 — 화면에는 아무것도 그려지지 않고(B4·B5), 사용자가 다른
앱에서 브라우저로 **돌아오는 순간** `window.focus` 가 그것을 지운다(B6). 소리와
데스크톱 알림은 사용자가 자리에 없을 때 이미 지나갔으므로, 돌아온 사용자에게
남는 것은 아무것도 없다. 이것이 접수 1 과 접수 2 의 "울리지 않는다" 가 만나는
자리다.

### 2.4 데몬 모드의 `모두 제거` 는 지워지지 않았다

| # | 사실 | 근거 |
|---|---|---|
| **B7** | 직접 모드의 `ClearAllAttention` 은 도구마다 `Attend()` 를 부른다 — 무장까지 내린다 | `toolhub/tool.go:907` |
| **B8** | 데몬 모드의 같은 이름은 주의 비트만 CAS 한다. 무장은 그대로다 | `hub/attn_tracker.go` |

실사용 배치는 데몬 모드다. 그래서 `모두 제거` 를 눌러도 무장이 남고, 이미 임계
시간을 넘긴 도구들은 **다음 1초 tick 에서 통째로 다시 울었다.** 사용자가 명시적으로
지운 것이 1초 만에 돌아오는 것이므로, 이것도 "없어야 할 곳의 알람" 이다.

### 2.5 왜 지금 표식을 겹칠 수 있는가

개정 전의 표식은 정지해 있었다. 포커스와 알람을 같은 자리에 겹쳐 그리면 하나가
다른 하나를 영구히 가리므로, 그때의 선택(알람이 있으면 포커스 표식을 양보한다)은
옳았다. `ATTENTION_PULSE_SRS` 가 표식에 2초 주기의 맥박을 준 뒤로 그 전제가
사라졌다 — 겹쳐도 시간축에서 갈라지므로 둘 다 보인다. 접수 1 이 말하는 것이
정확히 이 변화다.

### 2.6 감사로 확정한 사실 — 접수 3

| # | 사실 | 근거 |
|---|---|---|
| **B9** | `SignalAttention` 은 **edge 게이팅이 없다.** 상태를 무조건 세우고 무조건 방송한다 | `toolhub/tool.go:405`, `hub/attn_tracker.go:175` |
| **B10** | 프론트도 중복을 묻지 않는다 — `_onToolAttention` 은 이미 알람이 선 도구에도 데스크톱 알림과 비프를 다시 낸다 | `web/js/core/app-attn.js:46` |
| **B11** | `Stop` 훅은 **턴이 왜 시작되었는지 묻지 않는다.** 사용자 프롬프트에 대한 응답이든, 배경 이벤트로 깨어난 턴이든 똑같이 `dmctl notify done` 을 친다 | `runtime/install.go:409`, §1.8 관측 |
| **B12** | `Notification` 훅도 마찬가지다 — 권한 요청과 입력 유휴가 같은 `dmctl notify waiting` 한 줄로 합쳐진다 | `runtime/install.go:411` |
| **B13** | L2 의 `working` 억제는 **종결 보고를 모른다.** 에이전트가 `done` 을 보고한 뒤에도, 화면 갱신 한 조각이 무장을 세우면 임계 시간 뒤 같은 사실을 다시 알린다 | `ActivityStillWorking` (`tool.go:499`) |

### 2.7 B9~B13 이 "대기 중의 되풀이" 다

B9 는 결함이 아니라 **의도**였다 — "각 완료·대기 사건은 앞선 알람이 남아 있어도
다시 알려야 한다" (`tool.go:401` 주석). 그 전제는 훅이 오는 **모든 순간이 새
사건**이라는 것인데, B11·B12 가 그 전제를 깬다. 배경 턴의 종료와 입력 유휴 알림은
사건이 아니라 **같은 상태의 되풀이**다. 전제가 깨진 자리에서 B10 이 그것을 소리와
배너로 증폭한다.

B13 은 같은 되풀이의 L2 판이다. §2.2 가 B2 로 지적한 고리("TUI 는 유휴 상태에서도
화면을 갱신하므로 … 이 고리는 멈추지 않는다")는 재무장 잠금(FR-ATF-5)으로 막았지만,
그 잠금은 키 입력 한 번으로 풀린다(FR-ATF-6). 풀린 뒤에는 고리가 그대로 남는다.

**그러므로 고칠 것은 "알람을 몇 번 방송하는가" 가 아니라 "무엇을 사건으로 볼
것인가" 다.** edge 게이팅을 더하는 것은 답이 아니다 — 그러면 사용자가 알람을 지운
뒤의 되풀이는 그대로이고, 진짜로 연달아 일어난 두 완료를 한 번으로 뭉갠다.

### 3.4 묶음 N — 알람은 새 사건에만 (D-4·D-5·D-6)

#### 3.4.1 턴의 출처를 기억한다

| ID | 요구사항 |
|---|---|
| **FR-ATN-1** | 서버는 도구마다 **사용자 턴 표시**를 갖는다. `UserPromptSubmit` 활동 보고가 그것을 세우고, `done` 알람의 발화가 그것을 **소비한다**(내린다) |
| **FR-ATN-2** | 활동 보고는 그것이 사용자 프롬프트에서 온 것인지를 **곁들이 값으로** 실어 나른다. 활동 상태 어휘(`working`·`waiting`·`done`·`idle`·`ended`)는 한 글자도 바뀌지 않는다 — 활동 패널의 동작이 이 변경으로 달라지면 안 된다 (FR-CBG-1 의 선례를 따른다) |
| **FR-ATN-3** | 표시를 세우는 것은 `UserPromptSubmit` **뿐이다.** `PreToolUse`·`PostToolUse`·`SubagentStop`·`PreCompact` 도 `working` 을 보고하지만, 그것들은 턴의 출처를 말하지 않는다 |
| **FR-ATN-4** | `reason="done"` 인 명시 신호(`dmctl notify done` — `Stop` 훅)는 표시가 서 있을 때만 알람이 된다. 표시가 없으면 알람을 세우지 않으며, **방송도 하지 않는다** |
| **FR-ATN-5** | 표시는 도구의 상태를 통째로 버리는 자리(`Tool.kill`·`AttnTracker.Forget`)와 `ended` 보고가 함께 버린다 |

#### 3.4.2 유휴 알림은 알람이 아니다

| ID | 요구사항 |
|---|---|
| **FR-ATN-3a** | **배경 알림은 사용자 턴이 아니다** (2026-09-11 관측). `UserPromptSubmit` 은 사람이 친 것과 배경 알림을 **구별하지 않는다** — 백그라운드 작업이 끝나 턴이 깨어날 때도 같은 훅이 오고 `prompt` 에 그 알림의 본문이 실린다. 프롬프트가 `<task-notification>`·`<system-reminder>` 로 **시작하면** 사용자 턴 표시를 세우지 않는다. §2.7 이 "배경 이벤트로 깨어난 턴의 종료는 사건이 아니다" 로 막으려던 자리이며, 그 전제(FR-ATN-3 의 "출처를 말하는 훅")가 실제와 달랐다.<br>**휴리스틱임을 인정한다** — 훅 payload 에 출처 필드가 없어 본문이 유일한 근거다. 그래서 **못 가르면 종전처럼 사용자 턴으로 읽는다**: 알람이 한 번 더 우는 것이 울려야 할 때 울지 않는 것보다 낫다 (§1.7 과 같은 판단).<br>활동 상태는 어느 쪽이든 `working` 이다 — 에이전트는 실제로 일을 시작했고 활동 패널의 어휘는 이 변경으로 달라지지 않는다 (FR-ATN-2) |
| **FR-ATN-6** | `reason="waiting"` 인 명시 신호(`dmctl notify waiting` — `Notification` 훅)는 **턴이 진행 중일 때만** 알람이 된다. 그때가 권한 요청이고, 그 밖은 입력 유휴다 (AS-3) |
| **FR-ATN-7** | 진행 중인지의 판정은 **진행 표시** 하나로 한다. `working` 보고가 세우고 `done` 보고가 내린다. 시각을 견주지 않는다 — 세움과 내림의 두 사건이 이미 순서를 말하고, 시각으로 견주면 "보고한 적 없음"과 "시각 0 에 보고함"이 구별되지 않는다 |
| **FR-ATN-8** | `waiting`·`idle` 보고는 진행 표시를 **건드리지 않는다.** 근거가 2026-09-11 에 개정됐다 (`AGENT_EVENT_ABSTRACTION_SRS` `FR-AEV-30`) — 옛 근거였던 "한 훅의 두 명령(`notify`+`activity`)이 순서 없이 도착한다" 는 **경합은 사라졌다.** `notify` 배선을 걷고 알람을 활동 보고에서 파생하면서 명령이 하나가 됐기 때문이다 (`FR-AEV-20`). 남은 근거는 **순환 방지**다: `waiting` 이 `inProgress` 를 세우면 "턴이 진행 중일 때만" 이라는 `FR-ATN-6` 의 판정이 자기 자신을 참으로 만든다 |
| **FR-ATN-9** | 판정은 훅 메시지 문자열을 읽지 않는다 (D-6). `dmctl notify` 의 인터페이스는 그대로다 — 라벨 하나만 받는다 |
| **FR-ATN-15** | 서버는 도구마다 **대기 표시**를 갖는다. `waiting` 알람의 발화가 그것을 세우고, 표시가 서 있는 동안의 `waiting` 신호는 알람이 되지 않으며 **방송도 하지 않는다**. `Notification` 훅은 대기가 이어지는 동안 되풀이 발화하므로, 그 되풀이를 새 사건으로 읽으면 같은 대기 하나가 몇 번이고 운다 (B7). `done` 이 사용자 턴 표시를 소비하는 것과 **같은 규약**이다 |
| **FR-ATN-16** | 대기 표시를 내리는 것은 "사용자가 새 일을 시켰다" 는 신호다: ① `working` 활동 보고 ~~② 키를 누른 주목(`AttendTyped`)~~. ①이 있어야 웹 UI 를 지나지 않고 터미널에서 직접 응답한 경로가 덮인다. **②는 `FR-ATN-16a` 가 폐기했다** |
| **FR-ATN-16a** | **주목은 대기 표시를 내리지 않는다** (사용자 보고 `U-24`, 2026-09-11). 보기만 한 것이든 키를 누른 것이든 같다 — 대기가 끝났다고 말할 수 있는 것은 `working` **하나뿐**이다.<br><br>`FR-ATN-16` ②는 *"일을 시켰으므로 그 결과를 다시 기다린다"* 를 전제했다. 그러나 **권한 요청을 기다리는 중에 그 터미널을 만진 것은 일을 시킨 것이 아니다.** 대기는 그대로인데 표시만 풀려, 에이전트가 같은 대기로 `Notification` 을 재전송할 때마다 다시 울렸다 — 접수한 말이 *"한 번 봐도 여전히 waiting 상태이기 때문에 울리면 안 된다"* 이다.<br><br>①은 **그대로 둔다.** 없애면 한 턴 안의 두 번째 권한 요청이 조용해진다 — 도구를 쓴다는 것은 대기가 아니라 가동이고, 그 보고가 곧 이전 대기의 해소다.<br><br>재무장 잠금을 가르는 `Attend`/`AttendTyped` 의 구분(FR-ATF-5·6)은 **남는다.** 그것은 정적 감지(L2)의 것이고 이 조항이 만지는 것은 명시 신호(L1)의 것이다 |

#### 3.4.3 L2 는 이미 알린 것을 다시 알리지 않는다

| ID | 요구사항 |
|---|---|
| **FR-ATN-10** | L2 idle 은 **턴이 진행 중일 때만** 발화한다 — FR-ATN-7 과 **같은 판정**을 쓴다. 에이전트가 종결을 보고한 뒤의 정적도, 아직 한 번도 일을 시작하지 않은 도구의 정적도 새 사건이 아니다. 전자는 L1 이 이미 알렸고, 후자는 알릴 것이 없다 |
| **FR-ATN-11** | FR-ATN-10 은 FR-ATF-10 을 **약화하지 않는다.** 훅이 끊긴 채 `working` 으로 굳은 도구는 종결 보고가 없으므로 여전히 L2 로 울린다 — B3 의 회귀를 만들지 않는다 |
| **FR-ATN-11a** | **L2(정적 감지) 는 기본이 꺼짐이다** (사용자 결정 `U-24`, 2026-09-11). `attnDefaultIdleMS` 가 `10000` → `0` 이다.<br><br>판정 코드는 **한 줄도 지우지 않는다** — `DONGMINAL_ATTENTION_IDLE_MS` 에 값을 주면 종전 동작이 그대로 선다. 직접 모드와 데몬 모드가 같은 자리(`AttentionIdleThreshold`)를 딛으므로 한 값으로 둘 다 꺼진다.<br><br>이유는 **재무장의 문턱이 너무 낮다**는 것이다: `observeOutputAt` 은 **출력 한 조각**이면 다시 무장하므로, 에이전트가 간헐적으로 출력하며 일하는 동안 출력 → 정적 → 알람이 끝없이 반복됐다. 그리고 10초는 생각하는 에이전트에게 짧다. 접수한 말이 *"idle 알람도 최초 1회만. 너무 계속 떠"* 이고, 사용자는 그 뒤 **끄는 쪽**을 골랐다.<br><br>명시 신호(L1 — `waiting`·`done`)는 그대로다. 에이전트가 **스스로 알린** 사건은 여전히 울린다 |

#### 3.4.4 이 묶음이 개정하는 기존 요구사항

| 기존 | 개정 |
|---|---|
| **FR-ATF-1~3** — L2 는 에이전트 도구에 전경 프로세스가 있고 조용하면 운다 | 관문이 하나 늘었다: **턴이 진행 중이어야 한다** (FR-ATN-10). 에이전트 표시(FR-ATF-2)의 규약 자체는 그대로다 — 활동 보고는 여전히 상태를 가리지 않고 그 표시를 세운다 |
| **V-ATF-2** — 활동을 보고한 도구는 `idle`·`waiting`·`done` 어느 상태에서든 운다 | **뒤집힌다.** `done`·`waiting`·`idle` 만 보고한 도구는 울지 않는다. L2 가 우는 자리는 이제 **굳은 `working`** 하나뿐이며, 그것이 원래 L2 를 남겨 둔 이유다 (B3·FR-ATF-10) |
| **B1 의 처방** — "전경 프로세스가 있다는 것은 나를 기다린다는 뜻이 아니다" | 그대로다. 이번 개정은 같은 문장을 에이전트 도구 안쪽으로 한 겹 더 민 것이다 — **일하고 있지 않은 에이전트가 조용한 것** 역시 "나를 기다린다"는 뜻이 아니다 |

#### 3.4.6 남는 위험

| # | 위험 | 판단 |
|---|---|---|
| **R-1** | 오케스트레이션 멤버(`claude` 를 argv 프롬프트로 띄우는 헤드리스 도구)에서 `UserPromptSubmit` 이 발화하지 않으면, 그 도구의 완료 알람이 사라진다 | 발화 여부를 이 환경에서 확인하지 못했다. **알람이 사라지는 쪽으로 실패한다** — 그래서 구현은 표시를 세우는 자리를 한 곳(`UserPromptSubmit`)으로 좁히되, 그 자리가 비었을 때 무엇이 사라지는지 테스트로 고정한다 (V-ATN-2). 실제로 사라지면 표시를 세우는 자리에 `SessionStart` 를 더하는 것이 최소 수정이다 |

### 3.5 묶음 S — 평문 접속에서 알림이 막히는 사실 (M5 `TLS-1`, 2026-09-12)

평문 HTTP 로 접속하면 `window.isSecureContext` 가 거짓이고, 그때 브라우저는
`Notification` 을 통째로 막는다. **그 사실이 화면 어디에도 없었다** — 토글은
켜진 채였고 알림은 오지 않았으며, 사용자가 그것을 아는 방법이 없었다.

> **조치가 바뀐 항목이다.** 이 항목의 옛 문안은 "HTTPS 로 접속하세요" 를 안내하는
> 것이었다. 로드맵 **결정 9**(2026-09-11)로 **TLS 는 영구 제외**됐고 —
> 기밀성은 오버레이 망(Tailscale·WireGuard)에 위임한다 — 제품이 제공하지 않는
> 길을 안내할 수 없게 됐다. 남는 조치는 **표시와 대체 수단**뿐이다.
>
> 이름에 `TLS` 가 들어 있는 것은 감사 리포트의 번호일 뿐이며, 이 묶음은
> `crypto/tls` 를 부르는 코드를 한 줄도 넣지 않는다.

**FR-ATN-17** `window.isSecureContext` 가 거짓이거나 `Notification` 이 없으면
데스크톱 알림 토글이 **비활성화되고 그 사유가 표시된다.** 문구는 두 가지를 말한다:
① 브라우저가 막았다는 사실 ② 대체 수단이 무엇인가.

문구에서 **"HTTPS 로 접속하세요" 를 뺀다.** 제품이 제공하지 않는 길이다.

**FR-ATN-18** 같은 조건에서 **알림음이 기본 켜짐**으로 전환된다. 다만 저장된
값이 있으면 **사용자의 선택이 우선**이다 — 갈리는 것은 "정한 적 없음" 의 해석뿐이며,
`attnDesktop` 이 `'0'` 명시만 끄는 것과 같은 규약이다.

**FR-ATN-19** 막힌 환경에서는 권한을 **요청하지 않는다.** `requestPermission` 이
조용히 거절되고, 사용자는 아무 일도 일어나지 않는 클릭을 한 번 더 한다.

**FR-ATN-20** 막힌 환경에서는 알림 생성을 **시도하지 않는다.** 종전에는
`new Notification` 이 던진 예외를 `try` 가 삼켜 아무 흔적도 남지 않았다.

**FR-ATN-21** 탭 제목 배지는 **이미 있다** (`PAGE_TITLE_SRS` FR-PGT-8,
`app-settings.js` 의 `_applyPageTitle`). **새로 만들지 않는다** — 로드맵의
"`document.title` 대입 0곳" 은 그 사이에 낡은 사실이었고, 확인만 했다.

## 6. 비목표 (Non-goals)

- **알람 이력** — 해제된 과거 알람의 보관·타임라인은 여전히 범위 밖
- **OSC 감지 규약의 변경** — 어떤 시퀀스가 알림인가는 그대로다 (`DetectAttentionSignal`)
- **L2 임계값의 기본값 변경** — 10초와 `DONGMINAL_ATTENTION_IDLE_MS` 는 그대로다
- **훅 배선의 확장** — 어떤 훅이 무엇을 보고하는가는 그대로다 (FR-AAP-7). 묶음 N 은 훅을 더하거나 빼지 않는다. 바뀌는 것은 **서버가 그 보고를 어떻게 읽는가** 뿐이다
- **`dmctl notify` 의 인터페이스** — 라벨 하나를 받는 규약은 그대로다. 묶음 N 은 stdin 훅 JSON 을 읽지 않는다 (FR-ATN-9)
- **알람 방송의 edge 화** — 같은 알람을 두 번 방송하지 않게 만드는 것은 이 묶음의 답이 아니다 (§2.7)
- **다중 브라우저 완전 동기화** — NFR-PAN-7 가정 유지
- **읽음 표시·스누즈** — 알람에 "나중에" 를 주는 것은 별도 묶음이다
- **TLS·HTTPS 제공** — **영구 제외**다 (로드맵 결정 9). 묶음 S 는 평문 접속에서
  알림이 막힌다는 **사실을 말할 뿐**이고, 그 상태를 해소하지 않는다. 기밀성은
  오버레이 망(Tailscale·WireGuard)에 위임한다

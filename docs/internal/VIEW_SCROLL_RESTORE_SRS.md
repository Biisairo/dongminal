# SRS: 시선 보존 — 탭을 떠났다 돌아와도 스크롤이 남는다 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

사용자 보고 `U-20`(2026-09-11 접수)을 근본 원인에서 없앤다. 접수한 말은 이렇다.

> *"editor 가 스크롤값을 저장하지 않는다. 다른 화면을 갔다오면 스크롤이 맨 아래로
> 가있는다. 이처럼 터미널에서도 기본은 스크롤 저장이 맞다. 맨위로 가는 현상을
> 막는것도 스크롤 저장의 일부이다."*

요구가 셋이다.

1. **편집기 탭의 시선을 저장·복원한다.**
2. **터미널도 기본이 저장이다** — 저장이 옵션이 아니라 기본 동작임을 확인·확정한다.
3. **복원이 최상단을 만들지 않는다**(`U-3`) — 그것도 이 일의 일부다.

이 문서는 "스크롤 값을 하나 더 들고 있는 코드"를 더하는 문서가 아니다. 이 저장소에는
시선을 지키는 자리가 **이미 다섯**이고(§2.1) 계기·수단·근거가 자리마다 다르다.
여기서 정하는 것은 **편집기 탭의 소유자와 계기**이며, 나머지 넷의 어휘를 늘리지
않는다.

### 1.2 범위 (Scope)

- `web/js/ui/renderer.js` — `_mountTabBody`(붙이는 자리) · `_hideOthers`(떼는 자리) ·
  `_keepScrollAll`/`_restoreScroll`(갈무리·복원의 리듬) · `_restoreScrollOf`(터미널).
- `web/js/ui/file-editor.js` — Monaco 뷰 상태의 갈무리·복원 (**신규**).
- `web/js/ui/doc-render.js` — `.dr-body` 스크롤의 갈무리·복원 (**신규**).
- 신규·변경 e2e.

비포함:

- **새로고침 뒤의 복원**(영속). 요구는 "다른 화면을 갔다 오면"이며 세션 안의 일이다.
  선례 다섯도 전부 메모리에만 든다 (§2.1).
- 탐색기(`_scrollY`) · git 뷰(`_keepScrollAll`) · 사이드바(`__sbTop`) · git
  History(`_top`) 의 기존 대비. 고치지 않는다.
- ~~`U-17`(가끔 스크롤이 안 된다 — 재현 대기)~~ → **범위에 들어왔다.** 2차 보고와
  실측이 `U-3` 과 **한 뿌리**임을 확정했다 (§2.8). 묶음 C 가 받는다.
- Monaco·xterm 업그레이드, CSS 소유권(그쪽은 `UI_LAYOUT_DEFAULTS_SRS` 의 것이다).

### 1.3 정의 (Definitions)

- **시선(view state)**: 사용자가 지금 보고 있던 자리. 편집기에서는 Monaco
  `saveViewState()` 가 내는 것 — **스크롤·커서·선택·접힘**이 한 덩이다.
- **갈무리(keep)**: 요소가 문서에서 떨어지기 전에 시선을 적어 두는 일.
- **복원(restore)**: 요소가 다시 붙은 뒤 적어 둔 시선을 되돌리는 일.
- **라이브 위젯**: `PANE_DOM_RECONCILE_SRS §1.3` 의 것과 같다 — 자기 상태를 DOM 이나
  인스턴스에 담고 있어 다시 만들면 잃는 요소.
- **탭 전환 경로**: 같은 pane 에서 활성 탭이 바뀌는 경로. `_hideOthers` 가 옛 탭의
  위젯을 문서에서 떼고, 돌아올 때 `_mountTabBody` 가 다시 붙인다.

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 시선을 지키는 자리가 다섯인데 편집기 탭에는 없다

| 자리 | 수단 | 갈무리 계기 | 근거 |
|---|---|---|---|
| 탐색기 | `FileTree._scrollY` (`web/js/ui/file-tree.js:45·110·208`) | render 중, `isConnected` 일 때 | `FR-EDT-68` |
| 터미널 | `_grabScroll`/`_restoreScrollOf` (`web/js/ui/renderer.js:92·116`) | 부모가 바뀔 때만 | `FR-PDR-10~12` |
| git 뷰 | `_keepScrollAll`/`_restoreScroll` (`web/js/ui/renderer.js:180·201`) | 매 `_rLayout` 머리 | `FR-SCR-1·2` |
| git History | `History._top` (`web/js/git/history.js:67·573·585`) | 탭을 떠날 때 | — |
| 사이드바 탭 | `el.__sbTop` (`web/js/ui/sidebar-tabs.js:412·416`) | 탭을 갈 때 | — |
| **편집기 탭** | **없다** | — | — |

`web/js/ui/file-editor.js` 전수 grep 에 `saveViewState`·`restoreViewState` 가 **한
자리도 없다.** 모델은 문서가 캐시해 재사용하지만(`web/js/ui/file-editor.js:321`
`_model`) **뷰 상태는 아무도 들고 있지 않다.**

### 2.2 탭을 떠나면 편집기의 DOM 이 문서에서 떨어진다

`_hideOthers`(`web/js/ui/renderer.js:827`)는 `vis` 를 걷는 것으로 그치지 않고
`c.remove()` 한다. 그 이유는 그 자리에 적혀 있다(숨지 않은 git 뷰가 본문을 덮어
클릭을 가로챘다). 그러므로 탭 전환은 **언제나 이동**이다.

### 2.3 갈무리 장부는 터미널만 받는다

```js
if(el.parentNode!==body){
  // FR-PDR-10: **여기가 유일한 이동이다.**
  if(term) this._moved.push(this._grabScroll(term));   // renderer.js:805
  body.appendChild(el);
}
```

`term` 은 터미널 도구일 때만 값이 있다(`web/js/ui/renderer.js:803`). 편집기·DocRender·
Run 뷰는 **장부에 오르지 않는다.**

### 2.4 편집기 인스턴스는 산다 — 잃는 것은 DOM 이 떨어지는 순간이다

`_mountTabBody`(`web/js/ui/renderer.js:781-795`)는 `app.fileEditors` 에
`_slotKey(id,slot)` 로 인스턴스를 캐시하고 `editor.el` 을 그대로 쓴다. 즉 Monaco
에디터 객체는 살아 있다. 그런데도 시선을 잃으므로 원인은 **DOM 이동**이며, 이는
`EXPLORER_ROOT_KEYS_SRS §7.1` 이 포커스에 대해 이미 적어 둔 함정과 **같은 자리**다.

### 2.5 Monaco 의 스크롤은 DOM `scrollTop` 이 아니다 — 그래서 계기가 달라야 한다

두 가지가 따라온다.

1. `_keepScrollAll` 의 훑기(`push(n)` — `scrollTop`·`scrollLeft` 가 있는 노드를
   전부 적는다)로는 **잴 수 없다.** Monaco 는 가상 스크롤러이며 그 값은 인스턴스가
   들고 있다. 그래서 편집기는 그 훑기에 넣는 것으로 해결되지 않는다.
2. **뗀 뒤에는 잴 수 없다.** 터미널은 `_grabScroll` 을 *다시 붙일 때* 불러도 값이
   옳다 — xterm 의 `buffer.active.viewportY` 가 인스턴스에 남기 때문이다
   (`web/js/ui/renderer.js:95-99`). Monaco 는 컨테이너가 떨어진 뒤 크기가 0 으로
   측정되는 순간을 지나며, 그때의 뷰 상태는 사용자가 보던 자리가 아니다.

따라서 편집기의 갈무리는 **떼기 전**이어야 하고, 그 계기는 `_hideOthers` 다.
`FR-PDR-10` 의 "이동 직전 갈무리"와 뜻은 같으나 **자리가 다르다** — 그 조항의
갈무리는 붙이는 쪽(`_mountTabBody`)에 있다. 조항이 하나 늘어나는 이유가 이것이다.

### 2.6 DocRender 는 DOM 스크롤러인데 아무도 지키지 않는다

`web/js/ui/doc-render.js:254` 의 `.dr-body.ui-scroll` 이 스크롤 표면이다. 탭 타입은
편집기와 하나이고 실체만 둘이므로(`DOC_RENDER_VIEW_SRS D-1`) §2.2 의 이동을 **똑같이**
받는다. `_keepScrollAll` 은 git 패널만 훑으므로(`web/js/ui/renderer.js:198`) 이
표면은 어느 대비에도 들지 않는다.

한 가지가 더 얽힌다 — `FR-DRV-44`(소스를 스크롤하면 렌더가 따라간다)가 있으므로
**소스 편집기의 복원이 렌더 뷰를 움직인다.** 두 탭이 함께 보이는 배치에서 편집기의
시선을 되돌리면 렌더 뷰는 그 줄로 따라오는 것이 옳다. 그러나 소스 탭이 보이지 않는
배치에서는 그 계기가 없으므로, 렌더 뷰는 **자기 값**을 가져야 한다.

### 2.7 복원이 최상단에 남는 갈래가 있다 (`U-3` 가설)

```js
if(target>0){ p.term.scrollToTop(); p.term.scrollToLine(target) }   // renderer.js:127
else if(max>0){ p.term.scrollToBottom(); p.term.scrollToTop() }     // renderer.js:128
```

첫 줄은 xterm 이 `scrollToLine(ydisp)` 를 무시하는 것을 피하려 **한 번 흔든다.**
그 흔들기의 첫 동작이 `scrollToTop()` 이다. 두 번째 동작이 듣지 않으면 화면은
**최상단에 남는다** — 이것이 `U-3`("최상단으로 붙는다")과 `U-17`("가끔")이 같은
뿌리일 수 있다는 근거다. 방금 붙은 요소는 행 수·높이가 아직 측정되지 않은 프레임을
지나므로 "가끔" 이라는 성질과도 맞는다.

이 문서는 그 기전을 단정하지 않는다. 대신 **불변식**을 세운다 — 복원은 어떤
경로에서도 최상단을 결과로 남기지 않는다(`FR-VSR-22`). 재현 조건이 오면 그 위에
얹는다.

### 2.8 `U-3`·`U-17` 의 원인 — 실측으로 확정했다 (2026-09-11 2차)

§2.7 이 "재현 조건을 기다린다" 며 열어 둔 자리다. 사용자가 증상을 정확히 기술했고
(*"보이기에는 맨 아래가 보이나 실제 스크롤은 맨 위에 가 있다. 올리면 올라가지 않고,
내리면 맨 위에 있던 스크롤이 내려가며 화면이 갱신된다"*) 실측이 그것을 그대로 냈다.

**가설은 틀렸다.** §2.7 은 흔들기의 착지 실패를 지목했으나, 실측 전 구간에서
`_ignoreNextScrollEvent` 는 `false` 였고 흔들기는 이 경로를 지나지도 않는다.
원인은 **`atBottom` 갈래**이며 기전이 셋으로 갈린다.

창 전환 왕복 직후의 실측 한 줄이 전부를 말한다:

```
vY=199 baseY=199 len=233 rows=34 rowH=19 want=3781 have=0
sH=4427 cH=646 ign=false lst=3781 conn=true vis=true op=true
```

`sH-cH = 3781` 이므로 스크롤 여유는 멀쩡히 있는데 `scrollTop` 만 `0` 이다. 클램프가
아니라 **값의 유실**이다.

1. **떼면 브라우저가 버린다.** `_hideOthers` 의 `c.remove()` 로 요소가 문서에서
   떨어지는 순간 `.xterm-viewport.scrollTop` 이 `0` 이 된다 (실측: 그 구간이
   `conn=false sH=0 cH=0`). `viewportY` 는 인스턴스에 남으므로 **캔버스는 맨 아래를
   그린다** — 그래서 보이는 것과 실제가 갈린다.
2. **`rec.top` 은 죽은 값이었다.** `_grabScroll` 은 `_mountTabBody` 의 이동 갈래에서,
   즉 **이미 떨어진 뒤** `vp.scrollTop` 을 읽는다. 그 값은 언제나 `0` 이므로
   `_restoreScrollOf` 의 `if(vp&&rec.top) vp.scrollTop=rec.top` 은 **한 번도 실행되지
   않는다.** §2.5 의 *"터미널은 다시 붙일 때 불러도 값이 옳다"* 는 `viewportY` 에
   대해서는 참이고 **`scrollTop` 에 대해서는 거짓**이었다 — 그 한 줄이 이 결함의
   출처다.
3. **xterm 은 스스로 회복하지 않는다.** `atBottom` 갈래는 `scrollToBottom()` 뿐인데
   `ydisp === ybase` 면 그것은 `scrollLines(0)` 이라 내부에서 즉시 반환한다 —
   `onScroll` 이 나지 않으니 `Viewport` 도 깨지 않는다. 그리고 `syncScrollArea` 는
   `_lastScrollTop === ydisp × rowHeight` 이면 `_refresh` 를 **건너뛴다.** 실측의
   `lst=3781` 이 정확히 그 값이라 조건이 성립하고, **어긋남이 고착된다.**

사용자가 겪는 두 증상이 여기서 갈라져 나온다.

- **올려도 안 올라간다**: `scrollTop` 이 이미 `0` 이라 브라우저가 scroll 이벤트를
  내지 않는다. 실측에서 휠 업 11회 연속 이벤트 `0`건.
- **내리면 맨 위로 튄다**: 첫 이벤트에서 `Viewport` 가
  `round(scrollTop / rowHeight) - ydisp` = `round(4/19) - 199` = `-199` 를 계산해
  `ydisp` 를 최상단으로 끌어내린다.

**"가끔"의 정체도 같은 자리다.** PTY 출력이 한 줄만 들어와도 xterm 이 맨 아래를
따라가며 `onScroll` 을 내고, 그때 `Viewport` 가 `scrollTop` 을 다시 맞춘다 (실측
`25.75`·`29.20`). 조용한 터미널에서만 어긋남이 살아남는다 — Claude Code 처럼 출력이
멎어 있는 동안 창을 다녀오는 것이 정확히 그 조건이다.

**중간 스크롤 갈래는 우연히 무사했다.** 그쪽은 흔들기가 `ydisp` 를 실제로 옮기므로
`onScroll` 이 나고 `Viewport` 가 따라온다. 결함이 `atBottom` 에만 보이는 이유이며,
기존 e2e 셋이 전부 `scrollUp(80)` 으로 **중간 상태만** 재고 있었던 이유이기도 하다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 A — 편집기 탭의 시선

| ID | 요구사항 | 우선순위 |
|----|---------|---------|
| FR-VSR-1 | 편집기(FileEditor)는 자기 시선을 갈무리·복원하는 짝을 갖는다. 값의 임자는 **뷰 인스턴스**다 — 같은 파일을 두 칸이 볼 때 시선은 칸마다 다르다 (`FR-SVS-51·52`) | 필수 |
| FR-VSR-2 | 갈무리는 **요소를 떼기 전**에 한다. 계기는 `_keepScrollAll`(render 의 머리)이며, 그 자리에서 문서에 붙어 **보이는**(`isConnected` + `.vis`) 위젯에만 한다. 떼는 자리는 셋(`_hideOthers`·`_domGC`·`_place`)이고 그 전부에 훅을 걸면 어휘가 늘어난다 — 그래서 **떼기 전의 유일한 공통 시점**을 쓴다 (`FR-SCR-1` 과 같은 규약) | 필수 |
| FR-VSR-3 | 복원은 **요소를 다시 붙인 뒤**에 한다. 계기는 `_mountTabBody` 의 이동 갈래(`el.parentNode!==body`)이며, **이동하지 않은 경로에서는 어떤 복원도 부르지 않는다** (`FR-PDR-10` 의 규약) | 필수 |
| FR-VSR-4 | 갈무리한 값이 없으면 복원하지 않는다. 처음 열린 편집기의 자연스러운 자리(맨 위·`revealLine` 의 결과)를 덮지 않는다 | 필수 |
| FR-VSR-5 | 저장 단위는 Monaco 의 뷰 상태 한 덩이다 — 스크롤·커서·선택·접힘. 스크롤만 따로 뽑지 않는다 | 필수 |
| FR-VSR-6 | 요소에서 위젯 인스턴스를 찾는 자리는 **하나**다. `_hideOthers` 는 DOM 자식을 훑으므로 요소→인스턴스 대응이 필요하며, 그 대응은 붙이는 자리에서 한 번 등록한다 (`FR-PDR-8` 과 같은 규약: 클로저로 가두지 않는다) | 필수 |

## 4. 설계 결정 (Design Decisions)

- **D-1. 여섯 번째 어휘를 만들지 않고 계기를 대칭 쌍으로 둔다.** 선례 다섯은 계기가
  자리마다 다르다(§2.1). 편집기에 여섯 번째 값을 더하는 대신, 이미 유일한 이동 지점인
  `_hideOthers`(떼기)와 `_mountTabBody`(붙이기)를 **짝**으로 쓴다. 그 두 자리는
  `FR-PDR-10` 이 이미 "유일한 이동"으로 못 박은 곳이다.
- **D-2. 갈무리를 떼는 쪽에 두되, 자리는 render 의 머리 하나다.** 터미널처럼 붙이는
  쪽에서 재려면 값이 인스턴스에 남아 있어야 한다. Monaco 는 그렇지 않다(§2.5).
  그런데 편집기가 문서에서 떨어지는 자리는 하나가 아니다 — 탭 전환은
  `_hideOthers`(`c.remove()`), 창·칸 전환은 `_domGC`(쓰이지 않은 골격 회수),
  배치 변경은 `_place` 다. 셋에 각각 훅을 걸면 새 자리가 생길 때마다 조용히
  빠지므로(§2.1 의 다섯이 그렇게 갈렸다), **그 셋보다 앞선 유일한 공통 시점**인
  `_keepScrollAll` 에서 한 번 갈무리한다. 복원은 그와 달리 **이동 경로에만** 둔다 —
  화면을 만지는 쪽은 조건이 좁아야 한다 (`FR-PDR-10`).
- **D-3. 뷰 상태 한 덩이를 쓴다.** 스크롤만 뽑는 것은 Monaco 의 내부 표현에 손을
  넣는 일이고, 커서·접힘도 같은 이동으로 잃는다. 한 번의 호출로 셋을 지킨다.
- **D-4. 영속은 하지 않는다.** 요구는 세션 안의 왕복이다. 영속은 (a) 저장 위치,
  (b) 파일이 바뀐 뒤의 무효화, (c) 두 칸의 충돌을 새로 정해야 하며 그 셋 모두
  요구에 없다. 필요해지면 별개의 일로 다룬다.
- **D-5. DocRender 를 같은 조항에 넣는다.** 탭 타입이 하나(`type==='editor'`)이고
  이동 경로가 같으므로, 빼면 "편집기 탭인데 어떤 것은 남고 어떤 것은 안 남는다"가
  된다. 비용은 갈무리 한 갈래다.
- **D-7. 되돌리지 않고 되읽힌다 — 새 상태를 만들지 않는다.** 사용자가 요구를
  이렇게 갈랐다: *"기본은 스크롤 유지다. 맨 위로 튀는 것만 막고 싶다. 그러나 이걸
  위해 스크롤 위치를 지속적으로 저장해야 한다면 맨 아래로 내리는 게 낫다."* 그
  대가는 치르지 않아도 된다 — §2.8 이 보인 대로 **위치는 이미 살아 있고**(`vY=199`)
  어긋난 것은 픽셀 하나다. 그래서 값을 보관했다 되돌리는 대신 붙은 자리에서
  `ydisp` 를 읽어 DOM 에 맞춘다. 유지가 기본으로 남고, 튐이 사라지고, 저장 상태는
  **늘지 않고 하나 줄어든다**(`rec.top`).
- **D-8. `rowHeight` 를 xterm 내부에서 꺼내지 않는다.** `_currentRowHeight` 는
  minify 를 지나서도 남아 있으므로 읽을 수는 있으나, 그 이름에 기대면 vendor 를
  올리는 날 **조용히** 깨진다 (`VENDOR_VERSIONS.md` 의 해시 게이트는 파일이 바뀐
  것만 알려 주지 어느 필드가 사라졌는지는 말하지 않는다). 같은 값이 공개 표면에서
  나온다 — `(scrollHeight - clientHeight) / (length - rows)`. 실측으로 검산했다:
  `3781 / 199 = 19`. 분모가 `0` 이하면 스크롤백이 없다는 뜻이고, 그때는 맞출 것도
  없으므로 **아무 것도 하지 않는다**(이것이 크기가 아직 없는 프레임의 판정도 겸한다).
- **D-6. `U-3` 은 불변식으로 받는다.** 재현 조건 없이 `_restoreScrollOf` 의 판정을
  고치면 `FR-PDR-11`(bottom-follow 우선)을 되돌릴 위험이 있다. 지금 할 수 있는 것은
  "흔들기의 실패가 최상단을 남기지 않는다"는 순서의 문제이며, 그것만 한다.

## 7.1 구현 중에 실제로 걸린 것

**Monaco 는 떼었다 붙이는 것만으로는 스크롤을 잃지 않았다.** §2.1 의 "편집기만
없다" 는 코드의 사실이지만, "그래서 잃는다" 는 **추론이었다.** 실측: 탭 왕복 ·
창 왕복 · 떠나 있는 동안 1.8초를 두는 왕복 셋 모두에서 스크롤과 커서가 남았다
(구현 전에 돌린 `V-VSR-1`·`2`·`2a`·`10` 이 전부 통과했다).

그러므로 묶음 A 가 한 일은 **결함의 수리가 아니라 우연을 계약으로 옮긴 것**이다 —
그 보존은 Monaco 내부 동작에 딸려 있었고 어느 검증도 그것을 잡고 있지 않았다.
`V-VSR-1`~`2a`·`10` 이 이제 그것을 못 박는다.

**실제로 잃던 것은 렌더 뷰였고, 그 자리에 함정이 둘 있었다.**

1. `_paint()` 가 **머리에서 읽은 자리**를 끝에서 대입했다(`FR-DRV-43`). 그리기는
   비동기이므로, 떼여 있는 동안 시작한 그리기는 0 을 읽고 **복원 뒤에** 그것을
   대입했다.
2. `FR-DRV-44`(소스 → 렌더 추종)가 **재부착 뒤 레이아웃이 낸 스크롤 이벤트**로
   같은 줄을 다시 밀어, 방금 되돌린 자리를 덮었다. 실측 로그가 그 순서를 그대로
   보였다 — `600` 으로 되돌린 **9ms 뒤** `0`.

→ **한 계기에 기계를 둘 두지 않았다.** 처음에는 "복원이 낸 스크롤" 에 표시를
달아 추종이 물러서게 했는데, 그 이벤트는 복원 프레임보다 **뒤에** 오기도 해서
표시가 이미 걷혀 있었다. 판정을 "소스가 실제로 움직였는가" 로 바꾸자
(`FR-DRV-44a`) 표시가 필요 없어졌다.

**검사가 처음 통과한 이유는 검사가 틀렸기 때문이다.** 첫 판은 파일을 열고 **숨은**
편집기를 스크롤했다(다른 탭이 활성인 상태). 그 값은 갈무리를 지나지 않으므로
(`FR-VSR-2`) 왕복이 재려는 것을 재지 못했고, 구현을 넣자 **오히려 실패했다** —
갈무리한 옛 자리(0)를 되돌렸기 때문이다.
  → **왕복을 재는 검사는 보이는 상태에서 조작해야 한다.** 이 저장소의 교훈
    "흔들리는 것은 검증 수단이 아니다"(`UI_LAYOUT_DEFAULTS_SRS §2.12`)와 같은
    부류다 — 여기서는 흔들린 것이 아니라 **엉뚱한 것을 재고 있었다.**

**방금 붙은 요소에는 크기가 없다.** 복원의 `scrollTop` 대입이 0 으로 잘렸다
(실측: 본문 201개 · `scrollHeight` 6860 인데도 `clientHeight` 0). 그래서 놓지
못한 값을 **한 프레임까지** 들고 있다가 다시 놓는다 — 터미널의 사후 처리가
`TIMERS.frame` 에 있는 것과 같은 이유·같은 자리다 (`FR-PDR-10`).

**현재 상태 (2026-09-11)**: 묶음 A·B·C 구현·검증 완료.

`FR-VSR-22` 를 `V-VSR-11` 로 받았다. 그 RED 가 **`U-3` 의 가설 기전을 실물에서
처음 재현했다** — 흔들기의 착지 동작(`scrollToLine`)을 눌러 두고 탭을 왕복하면
`viewportY` 가 `0` 이 된다(§2.7). 고친 것은 흔들기의 **출발점**뿐이다:
`scrollToTop()` 대신 갈무리한 자리의 이웃 줄에서 출발하므로, 같은 실패가 최상단이
아니라 한 줄 차이로 끝난다. `_restoreScrollOf` 의 판정(`FR-PDR-11` bottom-follow)은
그대로다 — `FR-VSR-23` 이 재현 조건 전의 변경을 금지하고, 이 변경은 그것을 지킨다.

**개정 (2026-09-11 2차)**: `U-3`·`U-17` 의 **원인이 확정됐다** (§2.8). 1차가 세운
불변식(`FR-VSR-22`)은 흔들기의 착지 실패를 겨눴는데, 실측은 그 경로를 지나지도
않는다고 답했다 — 결함은 **`atBottom` 갈래**이고 어긋난 것은 `ydisp` 가 아니라 DOM
`scrollTop` 하나였다.

그러므로 1차의 조치는 **틀리지 않았으나 결함에 닿지 않았다.** 불변식은 그대로 두고
(`V-VSR-11` 무변경 통과) 그 위에 원인 조치를 얹는다: `FR-VSR-24`(복원 뒤 DOM 과
`ydisp` 가 일치한다) · `FR-VSR-25`(그 대가로 새 상태를 만들지 않는다).

`FR-VSR-23` 이 금지한 것은 **재현 조건 없는 판정 변경**이다. 재현 조건이 왔고,
그런데도 판정(`FR-PDR-11` bottom-follow)은 **여전히 바꾸지 않는다** — 바뀌는 것은
그 판정이 내린 결론을 DOM 에 반영하는 방법뿐이다.

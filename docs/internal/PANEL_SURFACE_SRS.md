## 1. 개요

### 1.1 목적

접수한 말은 넷이다.

> ① **"agents 패널에 window 이름에 따라 그룹를 만든다. tree 내에서 드래그드롭으로
> 순서 변경 가능. 그룹은 실제 윈도우의 순서를 따른다. 윈도우 순서가 드래그드롭으로
> 변경되면 그룹 순서에도 반영되어야한다."**
>
> ④ **"좌측 패널 줄였을 때도 리스트가 보이도록하고싶다."**
>
> ⑦ **"changes 에서 changes/untracked 둘을 합친다. 굳이 나누지 않아도 되고 둘의
> 차이는 파일이름 앞단의 기호로 확인 가능하다."**
>
> ⑨ **"history 상단에 검색이 두개다. 하나로 합치자. 또한 검색 옵션, 필터는
> 드롭다운으로 뭉친다."**

넷의 공통점은 **화면이 나눠 놓은 것을 사용자는 하나로 본다**는 것이다. 에이전트는
어느 창에 있는지가 카드 안의 글자로만 있고, 접힌 사이드바는 목록을 통째로 감추며,
같은 워킹 트리의 파일이 두 그룹에 갈려 있고, 하나의 "찾기" 가 입력 두 개다.

### 1.2 범위

**포함**
- ① `agents-panel` 의 창 단위 그룹화, 그룹 안 카드 재배치, 창·탭 이동의 즉시 반영
- ④ 접힌 사이드바(레일, 40px)에서의 목록 표시
- ⑦ Changes 탭의 `changes`+`untracked` 화면 통합과 일괄 폐기의 확인 절차
- ⑨ History 상단 입력 둘의 통합과 옵션·필터의 드롭다운화

**비포함**
- 알람 판정·수명 (`_attnRefresh` / ATTENTION_LIFECYCLE) — 표시만 다룬다
- git 서버 응답의 모양 (`/api/git/status` 의 네 배열) — **화면에서만** 합친다 (D-7)
- 사이드바 폭 규약·접힘 상태의 저장 자리 (SIDEBAR_COLLAPSE_SRS 가 이미 갖는다)
- Runs 패널 (묶음 C)

### 1.3 정의

| 용어 | 정의 |
|------|------|
| **그룹** | agents 패널에서 창 하나에 대응하는 머리 + 그 창의 카드들 |
| **레일** | 접힌 사이드바. 폭 40px, 탭 아이콘과 `⟳`·`⚙` 만 있다 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 에이전트 카드는 평면이고 창은 글자다

`_agentsRender`(`app-agents.js:145`)는 `ws.agentsOrder`(toolId 배열) 순서로 카드를
한 줄씩 쌓는다. 창은 `.ag-loc` 의 텍스트 `창이름 · 도구이름` 으로만 나타난다.
재배치(`_reorderAgents`)는 그 평면 배열 안의 자리바꿈이다.

**필요한 정보는 이미 매 렌더마다 계산된다** — `_findToolLocation(toolId)`
(`app-tool.js:563`)이 `{win, pane, tab}` 을 돌려주고, 그것을 못 찾은 도구는 이미
목록에서 빠진다. 그룹화는 **새 상태가 아니라 이 값의 묶음**이다.

`ws.windows` 는 창 순서의 진실이고, 사이드바의 재배치가 그 배열을 직접 바꾼다
(`sidebar-tabs.js` 의 `reorder.apply`). 탭 이동은 `_moveTabToWindow`
(`app-dnd.js:48`)가 워크스페이스 트리를 옮긴다.

### 2.2 레일은 목록을 통째로 감춘다

`html.sb-collapsed body:not(.mobile) .sb-panel{display:none}` (`style.css:219`).
남는 것은 `#sb-tabs`(아이콘 세로 나열, `:224~230`)와 `#sb-bottom`(`:243`)뿐이다.
탭 전환은 접힌 채로도 되지만(FR-SBC-17·18 개정), **전환한 그 탭의 내용은 보이지
않는다.** 접힌 상태에서 창을 고르려면 반드시 펼쳐야 한다.

### 2.3 Changes 의 네 그룹 중 둘은 성질이 거의 같다

`GIT_GROUPS`(`constants-git.js:114`) = `conflicts` · `staged` · `changes` ·
`untracked`. 그중 `changes` 와 `untracked` 를 비교하면:

| | changes | untracked |
|---|---|---|
| diff 축 (`GIT_GROUP_AXIS`) | `worktree-index` | `worktree-index` (**같다**) |
| 행 동작 (`GIT_ROW_ACTS`) | `openFile,stage,discard` | `openFile,stage,discard` (**같다**) |
| 그룹 일괄 (`GIT_GROUP_BULK`) | `stage,discard` | `stage,discard` (**같다**) |
| 상태 문자 | `M A D R C` | `?` |
| discard 의 실제 명령 | `checkout -q` (index 로 되돌림) | `clean -q -f` (**파일 삭제**) |

**갈리는 것은 상태 문자 하나와 폐기의 명령이다.** 접수한 말("둘의 차이는 파일이름
앞단의 기호로 확인 가능하다")은 앞의 것을 정확히 짚었고, 이 문서가 다뤄야 하는 것은
뒤의 것이다.

그룹 키에 매달린 다른 자리들: `_toggleGroup`(접기) · `_growGroup`(무한 스크롤의
`dataset.group`) · `GIT_DIR_ACT_TITLE_GROUP` · `GIT_BULK_TITLE_GROUP` ·
`GIT_DIALOG_FP_GROUPS`(`constants-git.js:515`) · 트리 보기가 그룹마다 따로 서는 규약
(FR-WBR-82).

### 2.4 History 상단에는 입력이 둘, 손잡이가 일곱이다

`history.js:104~120` 의 한 줄에 있는 것:

```
[검색][모드] [정렬▾] [Author][Since][Until][Path] [Apply] [reflog☑] ──여백── [+ Branch] [해시·브랜치·태그][Go]
```

- 왼쪽 검색(`.git-hist-search`)은 **두 모드**를 갖는다 — `loaded`(즉시 필터,
  `_match` 가 subject·authorName·authorMail·oid prefix 를 본다)와 `repo`(Enter 로
  `grep=` 을 실어 서버 재질의).
- 오른쪽 입력(`.git-hist-jump`)은 **리비전 이동**이다 — `log?ref=<rev>&limit=1` 로
  해석하고, 로드 범위 밖이면 최대 `GIT_JUMP_MAX_PAGES`(20)장까지 받아 가며 찾는다.

**서버가 아는 검색은 `--grep`(커밋 메시지) 하나다** (`query/log.go:163`). 작성자는
별도 인자(`--author`)이고, 해시·ref 는 검색이 아니라 `ref=` 로 해석된다. 이 사실이
§3.4 의 설계를 정한다.

### 2.5 사용자 결정 (2026-09-08 인터뷰)

- **D-1** ① 의 드래그는 **그룹 안의 카드 순서**다. 그룹 자체는 패널에서 끌지 않는다 —
  **그룹 순서는 실제 창 순서에서 파생한다.**
- **D-2** 카드는 **자기 도구가 실제로 있는 창의 그룹**에 있어야 한다. 탭을 다른 창으로
  옮기면 **즉각** 그 그룹으로 옮겨 가고, 창 순서를 바꾸면 그룹 순서도 즉각 따라간다.
- **D-3** ④ 는 **레일에 아이콘 행으로 세로 나열**한다. 이름은 툴팁이고, 클릭하면
  그 항목이 열린다.
- **D-4** ⑦ 의 일괄 폐기는 **버튼 하나 + 확인창에서 둘을 나눠 보임**이다.
- **D-5** ⑨ 는 검색 대상을 나누지 않는다 — **내용·커밋·ref 전체를 하나의 입력**으로
  찾는다.
- **D-6** ⑨ 의 범위는 **불러온 것을 즉시 거르고, 저장소 전체는 이어서 자동으로**
  넓힌다. 사용자가 모드를 고르지 않는다.

### 2.6 설계 결정

- **D-7 서버 응답을 건드리지 않는다.** ⑦ 은 `/api/git/status` 의 네 배열을 그대로
  받고 **화면에서만** 합친다. 근거 둘: ① 두 그룹의 폐기가 서로 다른 git 명령이므로
  각 항목이 자기 출신을 알아야 하고(D-4 의 확인창이 그것을 보인다), ② 응답 모양은
  e2e·다른 뷰·다이얼로그가 함께 딛는 공개 계약이다.
- **D-8 워킹 그룹은 `GIT_GROUPS` 의 항목 하나다.** 접기·무한 스크롤·트리 보기가
  전부 그룹 키를 딛고 있으므로(§2.3), 목록만 이어 붙이고 그룹은 둘로 두면 그 세
  규약이 갈라진다. 키는 `working` 이고 원천은 `['changes','untracked']` 다.
- **D-9 그룹은 상태가 아니라 파생이다** (①). `ws` 에 그룹 배열을 저장하지 않는다 —
  저장하면 창 순서·탭 이동과 **두 개의 진실**이 생기고, D-2 의 "즉각" 이 동기화
  코드가 된다. 그룹은 매 렌더에서 `ws.windows` × `_findToolLocation` 으로 만든다.
- **D-10 `ws.agentsOrder` 는 그대로 둔다.** 지금도 toolId 의 평면 배열이고, 그룹 안
  순서는 그 배열을 창별로 걸러 낸 것이면 충분하다 — 스키마를 바꾸면 마이그레이션이
  생기고, 카드가 창을 옮겼을 때 옛 창의 순서 배열에 유령 id 가 남는다.
- **D-11 레일 목록은 `SidebarList` 가 그린다.** 서술자(`SB_TAB_DEFS`)가 이미 항목·
  이름·활성·알람·배지를 주므로 레일 전용 데이터가 필요 없다. 레일은 같은 서술자의
  **다른 렌더**다 (FR-BLP-3 의 "타깃만 다르다" 를 한 번 더 쓰는 자리).
- **D-12 리비전 해석은 검색을 대신하지 않고 얹힌다.** 입력이 실재하는 리비전이면
  결과 맨 위에 그 줄이 뜬다 — `Go` 버튼이 하던 일을 결과의 한 줄로 옮긴 것이다.
- **D-13 저장소 전체 확장은 `--grep` 갈래만이다.** 작성자로 저장소 전체를 찾는 일은
  필터 드롭다운의 `Author` 가 이미 정확히 하는 일이고, 세 갈래 질의를 병합하면
  페이지네이션(skip/limit)의 뜻이 사라진다 (§5 리스크).

### 4.1 ④ 의 구현이 남긴 자리 (2026-09-08)

검증은 `sidebar-collapse.spec.ts` 의 `묶음 RAL` 여덟(RAL1~RAL8)이다. 같은 파일의
**SBC5 를 함께 고쳤다** — `#sb-panel-windows` 가 레일에서 숨는다고 재던 자리이며,
그것이 FR-SBC-11 의 옛 문장이었다. 회귀가 아니라 개정의 증거다.

구현이 밝힌 것 셋:

- **`title` 은 조건부일 수 없다** (FR-RAL-3). `SidebarList._build` 는 `r.title` 이
  있을 때만 붙이고 있었고, 창 목록의 서술자는 그 값을 주지 않는다 — 레일에서
  창 이름에 닿을 길이 하나도 없었다. `r.title || r.name` 으로 늘 채운다.
- **재배치 차단은 CSS 로 되지 않는다** (FR-RAL-9). `_bindDrag` 의 `dragstart` 에서
  끊고, 판정은 `app._sbRail()` 한 자리다 — CSS 선택자
  `html.sb-collapsed body:not(.mobile)` 와 같은 뜻이며 모바일을 함께 뺀다
  (FR-RAL-10). 접힘만 보면 모바일 드로어에서 재배치가 사라진다.
- **점의 색은 활성이 이미 쓰고 있다** (FR-RAL-7). `.sbl-item.active .sbl-dot` 가
  accent 이므로 활성 행에서는 배지 축약이 더할 것이 없다. 알람은 반대로 비켜
  주어야 한다 — `has-badge:not(.attn)` 로 한정하지 않으면 레일 규칙의 특정도가
  높아 `.attn` 의 색을 덮는다 (실측).

### 4.2 첫 글자는 구분에 쓰이지 않았다 (2026-09-08 접수)

FR-RAL-2 의 첫 판은 레일에 **이름의 첫 글자 하나**를 남겼다. 40px 에 무엇도 읽히지
않는다는 전제 위에서 "그래도 자리는 알린다" 를 고른 것이었다.

접수한 말은 그 전제를 부순다 — `창`·`메`·`d` 로는 어느 항목인지 알 수 없고, 알려면
결국 `title` 을 띄워야 한다. 그러면 레일의 목록은 있으나 마나다.

개정은 셋이다.

1. **첫 글자 대신 이름을 싣는다.** 글자를 `--sb-rail-fs`(9px)로 줄이면 남는 폭
   26px 에 한글 두세 자·라틴 네댓 자가 들고, **두 줄**이면 그 배다. 한 글자와
   비교할 것이 아니다.
2. **넘치면 마지막 줄 끝에 `…`** (`-webkit-line-clamp:2`). `overflow:hidden` 만으로
   자르면 이름이 짧아서 끝난 것인지 잘린 것인지 구별되지 않는다.
3. **`.sbl-initial` 을 걷었다.** 이름을 싣는 요소가 이미 있는데 첫 글자를 따로 든
   요소를 남기면 같은 값이 두 자리에 살고, 그 둘은 언젠가 갈린다. 요소가 하나면
   FR-RAL-6(레일 전용 데이터 없음)이 더 강하게 성립한다.

크기를 토큰 하나로 둔 것(FR-RAL-2a)은 접수한 말의 나머지 절반이다 — 두 목록이 각자
값을 들면 레일이 계단처럼 보인다. `title` 은 그대로 남는다 (FR-RAL-3): 두 줄에도
들지 않는 이름이 있고, 그때 닿는 길이 그것뿐이다.

### 5.1 구현이 밝힌 것 (2026-09-08)

- **FR-HSU-5 에 예외가 하나 필요했다.** 입력이 **리비전으로 해석되면 `--grep` 확장을
  하지 않는다.** `--grep` 은 커밋 메시지를 찾으므로 해시·ref 이름을 그 갈래로 보내면
  0건이 돌아오고, 그 0건이 목록을 비워 **방금 뜬 리비전 줄이 가리키는 커밋조차
  목록에서 사라진다** — 누를 곳으로 갈 수 없게 된다 (V-13 이 그 자리에서 멎었다).
  리비전 줄이 곧 그 물음의 답이므로 넓힐 이유도 없다.
- **FR-HSU-6 의 "결과 맨 위" 는 목록 밖의 줄이다.** 가상 스크롤의 좌표 계산이 항목
  수와 1:1 이라 목록에 없는 항목을 끼우면 그 계약이 깨진다. `.git-hist-rev` 를 목록
  **바로 위**에 두어 같은 뜻을 만족시켰다.
- **FR-HSU-3 의 즉시 필터는 확장이 끝나면 걷힌다.** 확장 뒤의 목록은 그 물음에 대한
  서버의 답이므로, 그 위에 클라이언트의 좁은 규칙(`_match`)을 다시 얹으면 서버가
  찾아 준 것을 도로 걸러낸다. 판정은 `_grep === _q.trim()` 하나다.

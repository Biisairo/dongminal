# SRS: 파일 전송(업로드·다운로드)과 탐색기 이동 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 네 줄이다.

> ① download 등의 파일 업로드·다운로드가 이상한 것 같으니 확인한다.
> ② 그 기능들을 **에디터의 파일 탐색기에서도** 쓸 수 있게 한다.
> ③ 탐색기에서 파일·폴더를 **최상위 경로로 옮기는 것**이 안 되니 확인한다.
> ④ 그 과정에서 **폴더의 폴더의 폴더** 같은 깊은 경로에도 넣을 수 있는지 확인한다.

조사 결과 ①은 서버 다섯 · 클라이언트 넷의 결함이었고, ②는 미구현, ③은 드롭
대상이 아예 없는 미구현, ④는 **서버·클라이언트 모두 깊이를 제한하지 않으나 접힌
폴더가 드래그 중 펼쳐지지 않아** 목적지를 미리 펼쳐 둔 경우에만 실질적으로
가능한 상태였다 (§2).

본 SRS 는 파일 전송을 **두 표면으로 나눈다.** 터미널의 전송은 사용자가 경로를
직접 지목하는 것이고, 탐색기의 전송은 트리에서 파생된 경로를 다루므로 **루트
아래로 제한된다** — `handlers_fs.go` 가 조회·조작에 이미 세운 경계와 같다
(FR-EDT-112·113).

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 다운로드 종단 | `Content-Disposition` 규격화, 디렉터리 거부, 오류 본문에서 경로 제거 |
| **B** 업로드 종단 | 크기 상한, 대상 디렉터리 검사, `/api/cwd` 의 근거 표시 |
| **C** 터미널 표면 | OSC 시퀀스의 청크 분할 유실, 무방비 `term.write`, 업로드 뒤 엔터 주입 |
| **D** 탐색기 다운로드 | 파일 행에서 내려받기. 루트 가드를 받는 새 종단 |
| **E** 탐색기 업로드 | OS 파일 드롭 + 우클릭 메뉴. 루트 가드를 받는 새 종단 |
| **F** 루트 이동 | 헤더·빈 여백을 드롭 존으로. 접힌 폴더의 자동 펼침 |

**미포함:** §6 비목표.

| 용어 | 정의 |
|------|------|
| **터미널 전송** | 터미널 pane 의 드래그 업로드와 `download` 헬퍼가 일으키는 전송 |

## 2. 현재 상태 (조사로 확정한 사실)

**추측이 아닌 파일:줄과 실측으로만 적는다.** 실측은 실행 중인 서버(포트 58146)에
직접 요청해 얻은 것이다.

### 2.1 다운로드 — 이름이 깨지고, 폴더가 200 으로 나간다

```
$ curl -sD - -o /dev/null '.../api/download?path=<…/한글 파일 이름.txt>'
Content-Disposition: attachment; filename=한글 파일 이름.txt
```

`handlers_files.go:107` 은 `"attachment; filename="+filepath.Base(fp)` 를 그대로
쓴다. RFC 6266 의 `filename` 은 **토큰 또는 quoted-string** 이라 공백에서 끊기고,
non-ASCII 는 애초에 올 수 없다. 브라우저는 이름을 버리거나 latin-1 로 읽어
깨뜨린다.

디렉터리도 200 이다 — `os.Open` 은 디렉터리를 열고(`:100`), `Content-Length` 는
디렉터리 엔트리 크기로 나가며(`:111`), `io.Copy` 는 EISDIR 로 실패하지만 그때는
이미 헤더가 나간 뒤라 **본문 0바이트의 성공 응답**이 된다. 실측: `Content-Length:
128`, 본문 0.

404 본문은 `open /private/tmp/…: no such file or directory` 로 서버의 절대경로를
그대로 싣는다 (`:101`).

### 2.2 업로드 — 상한이 없고, 대상 폴더를 확인하지 않는다

`apiUpload` (`handlers_files.go:54`) 는 `r.FormFile` 의 기본값(메모리 32MB, 나머지는
임시 파일)에 맡길 뿐 **본문 크기 상한이 없다.** `safeResolve("/", dir)` 은 base 가
`/` 라 언제나 통과하므로 (`:64`) 가드가 아니다 — 이것은 터미널 전송의 성격상
의도된 것이지만(§2.4), 대상 디렉터리가 실재하는지조차 보지 않아 없는 경로면
`os.Create` 가 실패해 500 만 남는다 (`:73`).

**경로 탈출은 막혀 있다.** `header.Filename` 을 `filepath.Base` 없이 쓰지만
(`:71`), Go 의 `multipart.Part.FileName()` 이 이미 `filepath.Base` 를 적용한다 —
`filename=../../escaped.txt` 로 올려도 `dir/escaped.txt` 에 떨어지는 것을
실측했다. 이 사실을 모른 채 고치면 없는 결함을 고치게 되므로 여기 적는다.

### 2.3 터미널 — OSC 가 청크 경계에서 사라진다

`_doFlush` (`term-pane.js:414`) 는 `_outputBuf` 를 **통째로 비운 뒤** 정규식
`/\x1b\]777;(\w+);([^\x07]*)\x07/g` 를 돌린다. WebSocket 청크가
`…Download;/path/to/f` 와 `ile\x07` 로 갈리면 매치가 없고, 버퍼는 이미 비었으므로
**명령은 영영 유실되고 잔여 이스케이프가 화면에 찍힌다.** `Cwd` 도 같은 경로를
타므로 cwd 표시와 git 신호(FR-GIT-18)까지 함께 잃는다.

`_downloadFile` (`:436`) 의 `this.term.write` 는 무방비다 — 바로 위 `_doFlush` 는
같은 호출을 `try{}catch{}` 로 감쌌다(`:424`). term 이 아직 없는 pane 에서는
TypeError 로 다운로드 자체가 끊긴다.

`_uploadFiles` (`:442`) 는 전송이 끝나면 `OP.INPUT, 0x0d` — **엔터를 셸에 밀어
넣는다** (`:445`). 셸 프롬프트를 새로 그리려는 것이지만, 그 순간 돌고 있는 것이
셸이 아니면 그 프로그램이 엔터를 받는다.

`/api/cwd` 는 도구의 cwd 를 모를 때 **서버 프로세스의 cwd** 를 돌려준다
(`handlers_files.go:126`). 업로드는 그것을 대상 폴더로 그대로 믿으므로
(`term-pane.js:445`), 사용자는 자기가 보고 있는 폴더가 아닌 곳에 파일을 올린다.
이 폴백은 `app-statusbar.js:325`·`app-tool.js:124`·`gitToolCwd`
(`gitapi/handlers_git.go:169`) 가 함께 딛고 있으므로 **종단의 폴백 자체는 바꿀 수
없다.**

### 2.4 탐색기 — 전송이 없고, 루트에는 놓을 자리가 없다

탐색기의 우클릭 메뉴는 새 파일·새 폴더·이름 변경·삭제 넷뿐이다
(`file-tree.js:686-695`). 업로드·다운로드는 터미널 pane 에만 있다.

드래그 이동의 `dragover`·`drop` 은 `.ed-row[data-kind="dir"]` 에만 걸린다
(`:723`·`:734`). **루트는 행이 아니라 헤더(`.ed-head`)이므로 드롭 대상이 아예
없다.** 우회로도 없다 — 이름 변경 입력은 `/` 를 거부하므로(`:523`) 경로를 바꿀 수
없고, 잘라내기·붙여넣기는 없다.

깊은 경로로의 이동은 **제한이 없다.** 서버는 `fsResolveTarget` 으로 부모를 풀어
루트 아래인지만 보고(`handlers_fs.go:159`), 클라이언트도 폴더 행이면 깊이를 묻지
않는다. 다만 드래그 중 접힌 폴더를 펼치는 수단이 없어, 목적지가 화면에 이미
펼쳐져 있어야만 놓을 수 있다.

### 2.5 두 표면의 가드가 다른 것은 설계다

`handlers_fs.go:20-25` 가 그 이유를 적어 두었다 — `/api/file/{read,write}` 의
`safeResolve("/", …)` 는 사용자가 경로를 **이미 알고 지목한** 읽기·쓰기이고,
`/api/fs/*` 는 트리 탐색에서 파생된 경로를 지우고 옮기므로 루트 상한이 있어야
한다. 본 SRS 는 전송에도 같은 선을 긋는다 (D-2).

## 3. 요구사항 (Requirements)

### 3.1 묶음 A — 다운로드 종단

**FR-FTR-1.** 다운로드 응답의 `Content-Disposition` 은 이름을 **두 벌**로 싣는다.

```
attachment; filename="<ASCII 폴백>"; filename*=UTF-8''<퍼센트 인코딩>
```

- ASCII 폴백은 `filepath.Base` 의 결과에서 U+0020 미만·U+007E 초과 문자와
  `"` · `\` 를 `_` 로 바꾼 것이다. 빈 문자열이 되면 `download` 를 쓴다.
- `filename*` 은 RFC 5987 의 `attr-char` 이 아닌 모든 바이트를 퍼센트
  인코딩한다.

**FR-FTR-2.** 대상이 디렉터리면 `400` 으로 거절한다. 헤더를 하나도 쓰기 **전에**
판정한다 — 나간 헤더는 되돌릴 수 없다 (§2.1).

**FR-FTR-3.** 다운로드 실패 본문에 서버의 경로를 싣지 않는다. 없으면 `not found`,
읽을 수 없으면 `cannot read file`, 디렉터리면 `not a file` 이다.

**FR-FTR-4.** 이 규칙 셋은 `/api/download` 와 `/api/fs/download` 가 **같은 함수**로
만든다. 두 벌이 되면 한쪽만 고쳐진다.

### 3.2 묶음 B — 업로드 종단

**FR-FTR-5.** 업로드 본문에 상한을 둔다. 기본 512MiB 이며, 넘으면 `413` 이다.
상한은 `http.MaxBytesReader` 로 강제한다 — `ParseMultipartForm` 이 디스크에 임시
파일을 만들기 **전에** 끊는다.

**FR-FTR-6.** 대상 `dir` 이 실재하는 디렉터리가 아니면 `400` 이다. 만들지 않는다 —
업로드는 폴더를 만드는 조작이 아니다.

**FR-FTR-7.** `/api/cwd` 응답에 근거를 함께 싣는다: `{"cwd":…, "source":"tool"}`
또는 `"server"`. 폴백 자체는 유지한다 — 기존 소비자 넷이 그것을 딛고 있다
(§2.3). 새 필드를 무시하는 소비자의 동작은 바뀌지 않는다.

### 3.3 묶음 C — 터미널 표면

**FR-FTR-8.** `_doFlush` 는 버퍼 끝에 **완성되지 않은 OSC 시퀀스**가 있으면 그
조각을 `_outputBuf` 에 남기고 나머지만 화면에 쓴다. 조각의 길이가
`OSC_CARRY_MAX`(4096) 를 넘으면 OSC 가 아니라고 보고 그대로 흘려보낸다 — 종결자
없는 입력에 화면이 영영 멈추지 않게 한다.

**FR-FTR-9.** `_downloadFile` 은 term 이 없어도 다운로드를 일으킨다. 화면 기록은
실패해도 전송을 막지 않는다.

**FR-FTR-10.** 업로드가 끝난 뒤 셸에 엔터를 보내지 않는다. 완료는 터미널에 쓰는
줄로만 알린다.

**FR-FTR-11.** 터미널 업로드는 `/api/cwd` 의 `source` 가 `tool` 일 때만 진행한다.
`server` 면 업로드하지 않고 사유를 터미널에 쓴다 — 보고 있지 않은 폴더에 파일을
떨어뜨리지 않는다.

### 3.4 묶음 D — 탐색기 다운로드

**FR-FTR-12.** `GET /api/fs/download?root=<abs>&path=<abs>` 를 신설한다. `root` 는
`fsRoot` 로 대조하고 `path` 는 `fsResolveExisting` 으로 푼 뒤 루트 아래인지 본다
(FR-EDT-112·113 과 같은 규약). 이름 헤더는 FR-FTR-1 을 따른다.

**FR-FTR-13.** 탐색기 우클릭 메뉴에 **다운로드**를 더한다. 파일 행에서만
활성이고, 폴더·링크에서는 비활성이며 사유를 `title` 에 보인다 (`GitMenu` 의
`disabled` 규약).

**FR-FTR-14.** 다운로드는 `<a download>` 앵커로 일으킨다. `fetch` 로 blob 을 받지
않는다 (D-1).

### 3.5 묶음 E — 탐색기 업로드

**FR-FTR-15.** `POST /api/fs/upload?root=<abs>&dir=<abs>` 를 신설한다. multipart 의
`file` 필드 하나를 받는다. `root`·`dir` 가드는 FR-FTR-12 와 같고, 크기 상한은
FR-FTR-5 와 같다.

**FR-FTR-16.** 대상에 같은 이름이 이미 있으면 **거부한다** (`exists`, 409). 덮어쓰지
않고 이름을 자동으로 바꾸지도 않는다 — 탐색기의 모든 조작이 그렇다
(FR-EDT-86·115). 터미널 업로드의 `(1)` 자동 개명과 다른 것은 의도다 (D-3).

**FR-FTR-17.** 탐색기는 **OS 드롭**을 받는다. `dataTransfer.types` 가 `Files` 를
포함하면 그것은 바깥에서 온 파일이므로 트리 내부 이동과 가른다 — 내부 이동은
`this._drag` 가 서 있을 때만이다. 대상 폴더는 놓인 폴더 행이고, 루트 드롭
존이면 루트다 (FR-FTR-20).

**FR-FTR-18.** 탐색기 우클릭 메뉴에 **업로드**를 더한다. 폴더 행이면 그 안,
파일 행이면 그 형제 자리다 — 새 파일·새 폴더와 같은 규칙(FR-EDT-81)이다. 파일
선택은 `<input type="file" multiple>` 로 받는다.

**FR-FTR-19.** 여러 파일은 **순차**로 올린다. 하나가 실패하면 거기서 멈추고 사유를
그 자리에 보인다 (FR-EDT-92) — 이미 올라간 것은 되돌리지 않는다. 끝나면 대상
폴더만 다시 읽는다 (FR-EDT-88).

### 3.6 묶음 F — 루트 이동과 자동 펼침

**FR-FTR-20.** 탐색기 헤더(`.ed-head`)와 트리의 **빈 여백**은 루트 드롭 존이다.
여기에 놓으면 항목은 Editor 루트로 옮겨진다. 드롭 가능한 동안 존을 표시한다
(`.ed-drop-root`).

**FR-FTR-20b.** 이동이 끝나면 **도착 폴더를 펼친다.** 접힌 폴더로 옮기면 옮긴
것이 화면에서 사라져 사용자가 잃은 것으로 읽는다. 업로드도 같은 이유로 대상
폴더를 펼친다 (FR-FTR-19).

**FR-FTR-21.** 이미 루트에 있는 항목을 루트에 놓는 것은 아무 일도 아니다 — 서버에
묻지 않는다. 폴더 행 위의 같은 규칙(`file-tree.js:740`)과 같다.

**FR-FTR-22.** 루트로의 이동도 FR-EDT-85·86 을 그대로 받는다 — 같은 이름이 있으면
거부하고, 자기 하위로 가는 경우는 애초에 성립하지 않는다.

**FR-FTR-23.** 드래그 중 **접힌 폴더 위에 600ms 머무르면 그 폴더를 펼친다.**
포인터가 그 행을 벗어나거나 드래그가 끝나면 타이머는 취소된다. 이미 펼쳐진
폴더에는 아무 일도 하지 않는다. 자동 펼침으로 열린 폴더는 드래그가 끝나도 접지
않는다 — 사용자가 방금 본 것을 되감지 않는다.

**FR-FTR-24.** 자동 펼침은 **탐색기 내부 이동과 OS 드롭 둘 다**에서 동작한다.

## 4. 설계 결정 (Design Decisions)

| # | 결정 | 근거 |
|---|---|---|
| **D-1** | 탐색기 다운로드는 앵커로 일으킨다 | `fetch`+blob 은 파일 전체를 메모리에 올리고 스트리밍을 잃는다. 폴더는 메뉴가 막고(FR-FTR-13) 나머지 실패는 브라우저가 알린다 |
| **D-2** | 전송 종단을 표면별로 나눈다 | 터미널 전송은 사용자가 지목한 경로이고 탐색기 전송은 트리에서 파생된 경로다. `handlers_fs.go:20-25` 가 조회·조작에 이미 그은 선이다 |
| **D-3** | 탐색기 업로드는 충돌 시 거부, 터미널 업로드는 자동 개명 유지 | 탐색기의 다른 조작 전부가 거부한다(FR-EDT-86). 터미널 쪽을 바꾸면 `api.md` 의 공개 계약이 깨진다 |
| **D-4** | `/api/cwd` 의 서버 폴백을 없애지 않는다 | 소비자 넷이 딛고 있다(§2.3). 근거를 **덧붙여** 판단은 호출자가 하게 한다 |
| **D-5** | 자동 펼침 지연은 600ms | Finder·VS Code 의 체감과 같은 대역이다. 상수 하나로 두어 조정 가능하게 한다 |
| **D-6** | 업로드 상한 512MiB | 임의의 값이다. 상한이 **있다**는 것이 값보다 중요하다 — 없으면 브라우저 하나가 디스크를 채운다 |

## 6. 비목표 (Non-goals)

- **폴더 다운로드(zip).** 서버 표면과 항목 수·크기 상한을 새로 정해야 한다.
- **덮어쓰기 선택지.** 탐색기의 모든 조작이 거부로 통일돼 있다 (FR-EDT-86).
- **전송 진행률·취소 UI.** 순차 업로드의 줄 기록으로 갈음한다.
- **잘라내기·붙여넣기.** 이동 수단은 드래그 하나로 둔다.
- **`/api/upload`·`/api/download` 의 인증.** 이 종단들은 인증 없이 임의 경로를
  읽고 쓴다. `--expose` 로 0.0.0.0 에 띄우면 LAN 의 누구나 닿는다. 이는 본 SRS 가
  만든 것이 아니라 **이미 있던 성질**이며, 고치려면 전 종단의 인증 설계가
  필요하므로 별건으로 남긴다. **§7 에 위험으로 기록한다.**

## 7. 위험 (Risks)

| 위험 | 등급 | 대응 |
|---|---|---|
| `--expose` 시 `/api/upload`·`/api/download` 로 임의 파일 읽기·쓰기 | **HIGH** | 본 SRS 범위 밖. 별건 SRS 로 인증을 설계할 때까지 `--expose` 는 신뢰된 망에서만 쓴다 |
| OSC 조각 보류가 화면 출력을 늦춘다 | LOW | 보류는 **불완전 시퀀스**에만, 상한 4096 (FR-FTR-8) |
| 자동 펼침이 의도치 않은 폴더를 연다 | LOW | 600ms 체류가 필요하고, 열린 것은 되감지 않는다 (D-5) |

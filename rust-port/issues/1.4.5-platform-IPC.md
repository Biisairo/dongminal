# 1.4.5 platform IPC

## 목표

웹서버↔데몬 로컬 전송(유닉스 도메인 소켓, 0600, Exists·Remove 규약, SiblingSocket)을 옮긴다. Windows 는 Go 와 같이 AF_UNIX 를 쓴다 — std·tokio 가 지원하지 않으므로 windows-sys 로 직접 구현한다(unsafe, C-RSP-4). 공개 API 는 부모 이슈 1.4 의 진행 기록 "공개 API 안" 을 따른다. 바꿔야 하면 조정자에게 먼저 알린다.

## 대상 Go 코드

- `internal/shared/platform/ipc.go` (약 100줄, Windows AF_UNIX 구현이 더해진다)

## 완료 조건

- 대상 Go 코드의 관측 동작을 Rust 가 동등하게 제공한다 (FR-RSP-1·3)
- 관측 동작을 검증하는 Go 테스트가 Rust 테스트로 옮겨져 통과한다 (V-RSP-1)
- `cargo fmt --check`, `cargo clippy -D warnings`, 격리 실행 `cargo test` 통과 (NFR-RSP-4)
- OS 의존 코드가 있으면 windows·linux 대상 `cargo check` 통과 (NFR-RSP-5)
- 작업 전후 `rust/scripts/prod-pids.sh` 출력이 같다 (V-RSP-5)
- 진행 기록에 공개 API 요약과 Go 와 다르게 한 내부 결정이 있다

- 2026-11-23 **review** (owner 117bca6d, 커밋 `965df586` on rp/1.4.5)
  - prod-pids.sh 시작·끝 출력이 같다:
    ```
    38173 start --foreground
    58470 d --handover-fd
    ```
  - **공개 API** (`dm-shared-platform`, lib.rs·Platform 은 고치지 않음)
    - `trait Ipc { endpoint, listen, dial(&Path, Duration), exists, remove }`. 값은 `current().ipc`. dial 의 timeout 0 은 끝없이 기다린다(Go `DialTimeout`).
    - `IpcListener::accept() -> io::Result<IpcStream>`. Drop 하면 소켓 파일을 지운다(Go `UnixListener.Close` 의 unlink). unix `AsFd`/`AsRawFd`, windows `AsRawSocket`.
    - `IpcStream`: `Read`·`Write` 는 `IpcStream` 과 `&IpcStream` 모두에 있다. 그래서 `Arc` 로 나눠 읽는 스레드와 쓰는 스레드가 같이 쓸 수 있다. `set_read_timeout`/`set_write_timeout(Option<Duration>)`(넘기면 `ErrorKind::TimedOut`, 문구 `i/o timeout`), `shutdown(Shutdown)`(다른 스레드의 막힌 read 를 깨운다), unix `into_std()`, `AsFd`/`AsRawFd`/`AsRawSocket`.
    - `SOCKET_FILE_NAME`, `sibling_socket(home, name)`.
  - **관측 동작**: 소켓 0600, Exists 판정(POSIX 소켓 비트, Windows 존재), Remove 멱등(Go `os.Remove` 알고리즘, 빈 디렉터리도 지움), backlog(Go `maxListenerBacklog`), 주소 길이 규칙(EINVAL). 오류 문구는 Go `*net.OpError` 와 같다. 이 문구는 go1.27.2 를 macOS 에서 격리 실행한 결과와 대조했다: `dial unix P: connect: no such file or directory`, `listen unix P: bind: address already in use`, `read unix ->P: i/o timeout`, `write unix P->: write: broken pipe`(linux 는 `@->P`·`P->@`). 문구는 gocompat `path_error`·`syscall_error` 를 조합해 만든다.
  - **테스트**: Go 테스트 5개(ipc_test 4 + sibling_test 1)를 옮겼고, 문구·모드·unlink·EOF·timeout·remove 테스트 12개를 더했다. 모두 17개이고 macOS 에서 통과한다. platform 전체 78개가 통과한다. clippy `-D warnings` 는 darwin·windows·linux 세 대상에서 `--all-targets` 로 통과한다.
  - **Go 와 다르게 한 내부 결정**
    1. Go 의 `isSocket func(FileInfo)` 를 `is_endpoint: fn(&Path) -> bool` 로 바꿨다. Windows 판정은 std `metadata` 가 실패하면 링크가 아닌 재분석 지점을 lstat 으로 본다. std 는 AF_UNIX 재분석 지점을 따라가다 실패하고, Go `os.Stat` 은 따라가지 않기 때문이다.
    2. 읽기·쓰기 시간 제한은 Go 의 절대 시각 deadline 대신 std 모양의 상대 시간 `set_*_timeout` 으로 했다. 시간이 넘었을 때의 문구와 종류는 Go 와 같다.
    3. Windows 는 Go 의 overlapped IOCP 대신 블로킹 Winsock 호출을 쓴다(FR-RSP-33). 오류 이름(acceptex·wsarecv·wsasend)은 Go 와 맞췄다. connect 는 Go 와 같이 블로킹이고 timeout 을 쓰지 않는다.
    4. 디렉터리 정리 `Remove`·`chmod` 는 Go 알고리즘을 ipc 모듈 안에 직접 옮겼다(Windows 는 `GetFileAttributesW`·`DeleteFileW` 등).
    5. Linux backlog 는 커널 4.1 미만의 uint16 상한 분기를 두지 않았다. 지원 범위 밖이다.
    6. Cargo.toml 에 `[target.'cfg(unix)'.dependencies] libc` 와 windows-sys 의 `Win32_Networking_WinSock` feature 를 더했다. 1.4.3·1.4.4 와 병합할 때 이 두 줄이 충돌할 수 있다.
  - **남은 위험**
    - Linux 와 Windows 에서는 실행 검증을 하지 못했다(이 기계에 docker 데몬이 없고 Windows 실기도 없다). Linux 문구 기대값(`@` 표기, 평범한 파일에 dial 할 때의 `connection refused`)은 Go 소스를 읽고 정했다. Windows AF_UNIX 코드는 컴파일과 clippy 만 통과했다 — MEDIUM.
    - Windows `SO_RCVTIMEO` 로 시간이 넘으면 소켓 상태가 정해지지 않는다(Winsock 문서). 시간 제한 뒤에는 연결을 버려야 한다.
    - `into_std()` 뒤의 오류 문구는 Go 모양이 아니다.
    - Go 와 달리 다른 스레드에서 리스너를 닫아 accept 를 풀 수 없다. 이 기능이 필요한 소비자(3.2 등)가 생기면 API 를 더해야 한다.

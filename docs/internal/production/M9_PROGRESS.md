### 1-4. M9-B2 — 사용자 진단 로그가 재현을 대신했다 (2026-09-14, P2)

P1 은 B2 를 **재현하지 못하고** 조건 셋을 남겼다(§1-1). P2 착수 중 사용자가 `?diag=1`
로그를 보냈고(`/tmp/m9-b2/b2-evidence.txt` 에 보존), 그 안에 증상이 그대로 있었다.

| 확정 | 근거 (로그 줄) |
|---|---|
| **복원은 돌고 있다** — P1 의 가설 ③(`_restoreScrollOf` 가 안 돈다)은 **틀렸다** | `42.21 vY=97 → 42.21 vY=96`. `renderer.js:180` 의 흔들기 두 줄(`scrollToLine(target+1)` → `scrollToLine(target)`)이 그대로 찍혔다. `target=96` |
| **복원이 틀린 자리로 정확히 복원한다** | 사용자가 두고 간 자리는 `33.09 vY=174 baseY=189`. 창을 다녀오자 `42.21` 에 `96`. `baseY`·`len` 은 그대로(189·238)이므로 **그 사이 출력은 없었다** |
| **한 번 어긋나면 스스로 낫지 않는다 — 이것이 접수한 증상이다** | `57.08~57.24`: `baseY` 가 190→195 로 오르는 동안 `vY` 는 **96 에 못 박혀 있다**. xterm 은 `ydisp!==ybase` 면 새 출력을 따라가지 않는다. 사용자의 "아래에 내용이 있는데 안 내려간다" 가 이것이고, "입력·새로고침·살짝 올렸다 내리기" 가 푸는 이유도 같다 — 셋 다 `ydisp` 를 `ybase` 에 다시 붙인다 |
| **두 기기가 아니다** | 사용자 확인(2026-09-14): 한 브라우저에서 사이드바로 창 둘을 오갔고 **문제가 난 창은 49줄 쪽**이다. B3(크기 통보)와 한 뿌리가 아니라 **별개 결함**이다 |
| **`RESIZE` 는 단서가 아니었다** | 전환마다 따라오던 `RESIZE 222x49`↔`222x63` 은 `resendWindowSizes`(`app-focus.js:298`)가 **PTY 로만** 보내는 것이다. 이 클라이언트의 xterm 크기를 바꾸지 않으므로 `ydisp` 와 무관하다 |

**구조적 결함 (로그가 증명한 것)**: `_grabScroll` 은 `_mountTabBody` 의 이동 갈래에서,
즉 **요소가 문서에서 떨어진 뒤** `viewportY` 를 읽는다. 격리 인스턴스 실측이 그것을 직접
찍었다 — `grab … conn=false vis=false`. 편집기는 이미 `FR-VSR-2` 로 *"문서에 붙어
**보이는**(`isConnected`+`.vis`) 위젯에만"* 갈무리하도록 고쳤고, **터미널만 그 규약 밖에
남아 있다.** `VIEW_SCROLL_RESTORE_SRS` §2.8 ②가 `rec.top`(픽셀)에 대해 같은 말을 했으나
`rec.y`(`viewportY`)는 *"다시 붙일 때 불러도 값이 옳다"* 는 §2.5 의 전제를 그대로 받았다.
로그가 그 전제를 깬다.

**아직 모르는 것**: `174 → 96` 을 만든 것이 무엇인가. 그 구간은 요소가 떨어져 있던
동안이라 `term.onScroll` 이 나지 않아 로그가 비어 있다. 재현 시도 넷이 전부 `vY` 를
**보존했다** — ① 창 왕복(바닥 상태) ② 창 왕복(위로 올린 상태) ③ `rows` 왕복(42→28→42)

셋을 더했다(`ydisp` 200ms 폴링 · `grab` · `restore`). 다음 발생의 로그가 판정한다.

## 2. 배운 것

### 2-1. (P1) "경고" 라 불린 것이 기동 거부였다

접수한 말은 "최초 expose 실행 시 … 경고가 뜬다" 였다. 실측은 경고가 아니라 **exit 1** 이었다 —
`--insecure-no-acl` 없이는 서버가 아예 뜨지 않는다. 그리고 사유 셋(목록이 없다·꺼져 있다·
항목이 없다)이 각각 다른 문장을 내는데, 사용자에게는 그 셋이 하나로 읽혔다("IP 등록을 요구한다").
**사유를 가르는 것은 고칠 자리를 알려 주는 것이지, 막는 이유를 설명하는 것이 아니었다.**

재감사가 아니었으면 "경고 문구를 지운다" 로 끝났을 것이고 게이트는 남았을 것이다. 접수한
말의 **등급**을 실측으로 확인하는 것이 재감사의 첫 값어치다.

### 2-2. (P1) 같은 바이트를 다른 폭으로 읽으면 그 해석이 틀린다

M9-B3 의 가설은 넷이었다(리사이즈 소유 · 재생 스냅샷 · 기기 간 cols/rows · xterm 리플로우).
한 클라이언트 안에서는 **어느 것도 재현되지 않았다** — 데스크톱 → 모바일 → 데스크톱 왕복 뒤
버퍼가 정확히 원래대로 돌아왔다(25줄, 문자 단위 일치). xterm 의 리플로우는 멀쩡했다.

깨진 것은 **두 클라이언트가 동시에 볼 때**였다. 모바일이 포커스 소유자가 되어 PTY 를 44열로
잡으면 zsh 의 줄편집기가 44 기준으로 커서를 옮기고, 그 바이트를 151열로 해석한 데스크톱에서는
앞 4줄이 사라졌다. **소유는 이미 있었고(FR-XDF) 없던 것은 그 사실을 나머지에게 말하는 길이다** —
`toolhub/conn.go` 의 서버→클라이언트 op 는 다섯뿐이고 그중에 크기가 없다.

교훈: "리플로우가 깨진다" 는 한 프로세스 안의 가설이고, 접수한 말("다른 기기에서 쓰고
돌아오면")은 **둘**을 말하고 있었다. 재현 환경이 사용자의 환경과 같은 수의 참여자를 가져야 한다.

### 2-3. (P1) 죽은 옵션은 반대로 적혀 있었다

`GIT_DIFF_OPTIONS` 의 `minimap:{size:'fill'}` 에는 "미리보기도 같은 좌표계에 선다" 는 열 줄짜리
근거가 붙어 있었다. 실측하니 diff 의 `minimap.enabled === false`(폭 0) — `createDiffEditor` 의
기본값이 그렇고 `size` 는 켜진 미니맵의 값이다. **주석이 말하는 동작이 한 번도 일어나지 않았다.**

그래서 사용자가 본 "미니맵 영역" 은 미니맵이 아니라 편집기 안의 개요 눈금 14px 이었고, 고칠
자리도 미니맵이 아니었다. 고친 뒤 `enabled:false` 를 **적어 둔** 것이 이 변경의 절반이다 —
없는 것을 없다고 적지 않으면 다음 사람이 같은 착각을 한다.

### 2-4. (P1) 검사가 결함 위에서 초록이었다 — 쉼표 선택자

FR-M9-7 의 첫 검사는 `querySelector('.pn-tab-x svg, .pn-tab-x')` 로 닫기 표식을 집었다. 쉼표
선택자는 **문서 순서상 먼저 오는 것**을 돌려주므로 언제나 상자(`.pn-tab-x`)가 잡혔고, 그 상자는
세로 44 를 받아 탭 안에서 이미 가운데에 선다. 결함을 되돌려 놓고 돌려도 초록이었다.

RED 를 **실제로 보는** 것이 이것을 잡았다(`git stash` → 실행 → 15.5px 이 아니라 통과). 아이콘을
집도록 고치고, "상자를 쟀으면 이 검사는 아무것도 말하지 않는다" 는 단정을 하나 더 넣었다.
**테스트가 무엇을 집었는지도 테스트의 대상이다.**

### 2-5. (P1) 가로 스크롤 상자 안에서 `absolute` 는 내용과 함께 밀린다

키바의 가려짐 표식을 `position:absolute; left:0` 으로 두자 스크롤과 함께 밀려 화면 밖으로
나갔다 — 스크롤 상자의 절대 위치는 **보이는 끝이 아니라 스크롤 원점** 기준이다. 키바가 flex 라
두 의사요소가 곧 flex 항목이고, `position:sticky` 가 그것을 보이는 끝에 붙인다. 음수 마진으로
자리를 없애 키의 수는 줄지 않는다(E-3 의 근거를 건드리지 않는다).

### 2-6. (P1) §2-39 의 교훈이 두 번째로 값을 했다

TC-BGK-12 를 군집에 넣기 전에 `--repeat-each=8` 로 돌렸고 3/8 이 재현됐다. 실패는 전부
`Expected "1" / Received ""` — 빈 문자열은 **요소가 문서에서 떨어졌다**는 뜻이다. 그리고 바로
**한 줄 아래**의 `boundingBox` 단정에는 그 사유를 적은 주석과 `expect.poll` 이 이미 있었다.
같은 재렌더를 아는 코드가 한 줄 위에는 적용되지 않았다.

TC-AGT-4 는 그렇게 잡은 제품 결함이었고 이번 것은 테스트 결함이다. 갈라지는 자리는 같다 —
**반복으로 재현한 뒤 무엇이 규약을 어겼는지 본다.**

### 2-7. (P1) M8 이 "초록" 이라 적은 명령이 흔들리고 있었다

P1 을 마치고 `go test -race -shuffle=on -count=1 ./...` 을 돌리자 `git/jobs` 가 떨어졌다
(`기록: []`). 내 변경은 그 패키지를 스치지도 않는다. **clean 트리에서 같은 명령을 12회
돌리자 3회 떨어졌다** — 선재 결함이고, M8 P7 의 "초록" 은 그 회차의 사실이었다.

원인은 한 함수 안에 있었다. `Jobs.finish` 는 M8 P1 ②가 **훅**을 "끝이 공개되기 전" 으로
옮기면서 그 사유를 열 줄짜리 주석으로 적어 두었는데, **기록**(`RecordWrite`/
`RecordUnguarded`)은 여전히 공개 **뒤**에 있었다. 규칙은 세웠고 그 규칙을 어기는 이웃은
세 줄 아래 그대로 있었던 것이다.

교훈 둘. ① **한 번의 `-shuffle` 초록은 판정이 아니다** — 흔들리는 것은 반복으로만 보인다
(§2-6 과 같은 도구, 다른 층). ② **규칙을 세운 커밋은 그 규칙의 다른 적용처를 함께 세어야
한다.** "훅은 공개 전에" 를 적을 때 "이 함수에서 공개 뒤에 도는 것이 또 무엇인가" 를
묻지 않았다.

검사는 훅 **안에서** 기록 수를 센다. 밖에서 `Done` 을 기다렸다 세는 형식은 창이 좁아
12회 중 3회만 걸리고, 그런 검사는 결함이 있어도 대개 초록이다.

### 2-8. (P1) 계약을 바꾸면 그 계약을 못박은 검사를 찾아야 한다

FR-M9-5 는 `GIT_DIFF_OPTIONS.minimap` 의 값을 바꿨다. 근거 문서(`M9_SRS`)는 고쳤고 새 검증
(`git-diff.spec.ts` D14)도 썼다. 그런데 **그 옛 값을 못박는 검사가 이미 있었다** —
`editor-minimap.spec.ts` 의 `V-MMP-2b`("diff 옵션이 편집기와 갈라졌다"). 전량 e2e 가 그것을 잡았다.

내가 돌린 것은 **내가 건드린 파일의 스펙**뿐이었다(`git-diff`·`editor-find-panel`·새 파일).
계약을 바꾸면 찾아야 하는 것은 그 **값**이지 파일이 아니다 — `GIT_DIFF_OPTIONS.minimap` 한 줄만
`grep` 했어도 나왔다.

그리고 고칠 것은 검사만이 아니었다. `V-MMP-2b` 는 `UX_BATCH8_SRS` FR-MMP-2("편집기와 diff
둘 다")를 딛고 있었으므로 그 조항도 개정해야 했다 — diff 가 그 조항에서 빠진다는 것, 그리고
**그 값이 diff 에서 한 번도 효력이 없었다**는 사실과 함께. "동작을 바꾸면 근거 문서를 같은
변경에서 고친다" 의 근거 문서는 **한 장이 아닐 수 있다.**

### 2-9. (P1) 전량이 도는 중에 소스를 고쳤고, 그 회차를 통째로 잃었다

규약은 "전량 중 `web/js`·CSS·`scripts/`·`e2e/` 를 고치지 마라" 였다. 나는 **Go 소스**를 고쳤다 —
목록에 없다는 이유로. 각 샤드는 시작할 때 `go build` 로 자기 바이너리를 만들고, 마침 그 순간
미사용 import 로 빌드가 깨져 있었다. 샤드 6·7·8 이 `go build` 에서 죽고 샤드 5 는 158건이 떨어졌다.

목록은 예시였고 규칙은 **"전량이 도는 동안 제품 소스를 건드리지 않는다"** 였다. 회차 하나를
잃는 것으로 끝났지만, 더 나쁜 결과는 그 회차를 **믿는 것**이었다.

### 2-10. (P1) 표적 실행이 전량의 리포트를 덮는다 — 리밸런스는 **직후**다

전량이 `unexpected 0` 을 낸 뒤 flaky 넷을 `--repeat-each` 로 확인했고(§2-39 규약), 그러고 나서
`make e2e-rebalance` 를 불렀더니 "JSON 리포트를 찾지 못했다" 였다. 표적 실행이 `test-results/`
아래 샤드별 `report.json` 을 덮은 것이다.

규약은 이미 그 순서를 적고 있었다 — "전량 직후 `make e2e-rebalance`, **그 뒤** 표적". 순서가
취향이 아니라 **의존**이라는 것을 읽지 못했다. 되돌리는 값은 전량 한 회차(7분)였다.

### 2-11. (P1) `stop` 의 홈과 포트는 각각 풀린다 — 운영 인스턴스를 내렸다

검사용 격리 인스턴스를 치우려고 이렇게 돌았다:

```
for h in <격리홈들>; do dongminal stop --all --home "$h"; done
```

`--home` 으로 격리를 지목했으니 격리만 죽는다고 읽었다. **`--port` 를 주지 않으면 포트는**
**환경변수 `DONGMINAL_PORT` 에서 온다** — 도구 셸이 물려준 그 값은 **운영 포트(58146)** 였다.
홈과 포트는 한 덩어리가 아니라 각각 풀리는 값이고, 그래서 "격리 홈 + 운영 포트" 라는 조합이
만들어져 운영 서버가 내려갔다.

잃은 것은 없었다 — 데몬(`dongminal d`)이 PTY 를 들고 있어 창·탭·도구가 전부 살아 있었고
`dongminal start` 한 번으로 그대로 돌아왔다. 그 사실이 이 사고를 **작게** 만들었을 뿐
옳게 만들지는 않는다.

규칙 둘. ① **인스턴스를 지목하는 명령은 `--home` 과 `--port` 를 함께 준다.** 한쪽만 주면
나머지는 환경이 채우고, 이 워크스페이스의 환경은 언제나 운영을 가리킨다. ② 격리 인스턴스를
띄울 때 그 **정지 명령을 그 자리에 적어 둔다** — 기동 출력이 이미 `정지: dongminal stop --all
--port <P> --home <H>` 를 통째로 찍어 준다. 그것을 그대로 쓰면 이 실수가 나지 않는다.

### 2-12. (P2) 검사가 **증상**을 재면 부수 경로가 대신 답한다

FR-M9-10 의 첫 검사는 접수한 증상을 그대로 옮겼다 — "끊긴 동안 지워진 탭이 복귀 뒤
사라진다". 구현 없이 **초록이었다.** 조건을 넷까지 좁혔는데 전부 그랬다:

| 조건 | 결과 |
|---|---|
| A 의 SSE 를 끊고 B 가 삭제 → A 재연결 | 수렴 |
| A 의 `PUT /api/workspace` 를 가로채 저장을 막음 | 수렴 |
| `POST /api/focus/claim` 까지 막음 | 수렴 |
| B 의 저장이 **서버에 반영된 것을 확인한 뒤** A 를 깨움 | 수렴 |

추적하니 재연결한 클라이언트에는 `server_hello` 뒤에 `workspace_changed` 방송이
**따라오고**, 그것이 이미 있던 경로(`_onWorkspaceChanged(rev)`)로 수렴을 만든다.
A 자신은 `PUT` 을 내지 않았고(요청 목록으로 확인) 서버는 구독 시작 시 `server_hello`
만 보낸다(`commands.go:281`) — 그런데도 온다.

**P1 의 실측과 어긋난다.** §2.3 M9-B9 는 "14초까지 수렴하지 않았다" 였는데, 그
재현은 `fetch` 를 통째로 막은 상태였다(§3-3) — `/api/state` 를 받을 수 없으니
수렴이 애초에 불가능하다. **재현 환경의 인공물이었을 가능성이 높다.**

사용자 결정(2026-09-14): 구현을 유지하고 **보장으로 못박는다.** 검사가 재는 것을
옮겼다 — "탭이 맞는가"(부수 경로가 대신 답한다)에서 **"재연결이 재수신을
부르는가"**(그 경로만이 답한다)로. 옮기자 RED 가 보였다.

교훈: **증상이 사라진 것과 요구가 충족된 것은 다르다.** 증상을 재는 검사는 그
증상을 없애는 **아무** 경로에나 초록을 준다. 그 경로가 문서화되지 않은 부수 효과면,
어느 판에서 그것이 어긋나는 순간 증상이 조용히 돌아오고 **그때 이 요구를 다시 찾을
근거가 없다.** §2-4 는 "검사가 무엇을 집었는지도 테스트의 대상" 이라 했고, 이것은
그 한 겹 위다 — **검사가 무엇을 재는지**도 대상이다.

### 2-13. (P2) 전량이 **내가 만든 회귀**를 잡았다 — "다시" 라는 낱말 하나

FR-M9-10 을 `bus.subscribe('sse:open', …)` 한 줄로 구현했다. 요구는 이렇게 적혀 있었다:

> 명령 SSE 가 **끊겼다 다시 붙으면** 클라이언트는 그 자리에서 워크스페이스를 다시 받아 적용한다.

**"다시" 를 읽지 않았다.** `sse:open` 은 최초 연결에서도 난다. 그래서 부팅 직후에도 한 번 더
`/api/state` 를 받아 적용했고, 그것이 **그 사이의 로컬 변경을 덮었다.** 전량 e2e 가
`session.spec.ts` "rename via double-click" 으로 그것을 잡았다 — 단독 반복 **6/6 실패**,
구독 한 줄을 빼면 **15/15 통과**. 증상은 "이름을 고치는 중에 그 행이 사라진다" 였고, 이
요구와 무관해 보이는 자리다.

고친 것은 `gen>1` 한 조건이다(`event-bus.js` 의 `_gen` 은 `connect()` 마다 오르므로 첫
연결이 1). 그리고 **그 조건을 검사로 고정했다**(TC-M9-10d) — 조건을 빼면 그 검사가 떨어진다.

교훈 둘.

① **요구의 낱말은 조건이다.** "끊겼다 **다시** 붙으면" 의 "다시" 는 수식이 아니라 게이트였고,
그것을 빠뜨리자 요구가 **고치려던 것과 반대 방향의 결함**을 만들었다 — 놓친 변경을 메우려다
진행 중인 변경을 덮었다.

② **내 검사 넷이 전부 초록인데 회귀가 있었다.** `workspace-resync.spec.ts` 의 셋은 전부
재연결만 보았고 **최초 연결을 보지 않았다.** 검사가 요구를 덮는다는 것은 그 요구가 말하는
경로를 덮는다는 뜻이지, 그 요구가 **건드리는** 경로를 덮는다는 뜻이 아니다. 전량이 있는
이유가 이것이다 (§2-8 이 같은 교훈의 다른 얼굴이다 — 그때는 남의 검사가, 이번에는 남의
기능이 잡았다).

### 2-14. (P3) "군집" 이라 불린 것은 **각자 다른 결함 넷**이었다

M9-A2 는 flaky 여섯을 **한 덩어리**로 묶고 판정 질문까지 미리 정해 두었다 — "두 헬퍼가
*요청이 왔는가* 를 기다리는지 *화면이 반영했는가* 를 기다리는지". 여덟 달을 그 이름으로 살았다.

전수로 보니 **헬퍼는 둘 다 멀쩡했고**, 넷은 각자 다른 사실을 빠뜨리고 있었다 (§1-8) — 워치독
문턱 둘 중 하나를 안 연 것 · 기준값을 목록이 서기 전에 읽은 것 · 넷 중 하나만 기다리고 셋을
동기로 잰 것 · 떨어진 요소를 한 번만 본 것. 공통점은 "무언가를 덜 기다렸다" 하나뿐이고, 그것은
**증상의 이름이지 원인의 이름이 아니다.**

교훈 둘.

① **군집은 가설이지 사실이 아니다.** 같은 증상으로 묶인 목록은 조사를 시작할 자리를 주지만,
그 목록의 **이름**이 원인의 이름이라고 읽으면 넷을 한 번에 고치려다 하나도 못 고친다. §2-39 가
"군집에 넣기 전에 재현하라" 고 한 것의 반대편이 이것이다 — **군집에서 꺼낼 때도 하나씩이다.**

② **이미 일어난 실패가 재현보다 강한 증거다.** `--repeat-each` 로 흔들기 전에 전량 회차의
`report.json` 을 읽었다. 거기에는 실패한 **줄 번호와 실제 값**이 있다 — `Expected < 0,
Received 1` 한 줄이 "`all` 이 0 이었다" 를 곧바로 말해 주고, 그것이 곧 원인이다. 부하에서만
나는 실패를 단독 반복으로 재현하려 들면 시간을 다 쓰고도 못 만든다.

### 2-15. (P3) 고정 대기가 **이름과 다른 사실**을 지키고 있었다

`TestToolClientAutoReconnect` 의 `time.Sleep(150ms)` 에는 이런 주석이 붙어 있었다:

> Kill the daemon → client connection drops, supervisor starts redialing.

그래서 ① 로 옮기며 **"끊긴 것을 클라이언트가 알았는가"** 를 기다리게 했다. `pc.Connected()` 가
거짓이 되는 데 걸린 시간은 **2.8µs~11ms** — 150ms 보다 훨씬 짧다. 그런데 **5/5 실패**했고,
로그에는 `toolclient: reconnected` 가 멀쩡히 찍혀 있었다. 재접속은 됐는데 `pc.List()` 가 8초
내내 비었다.

그 150ms 가 실제로 지키던 사실은 **저장**이었다. 대체 데몬은 `tools.json` 으로 도구를
되살리는데(`pm2.LoadAll(allToolIDs(dataDir))`), 내가 그보다 **빨리** pm2 를 세우자 되살릴
것이 없었다. 조건을 `len(allToolIDs(dataDir)) > 0` 으로 바꾸니 통과했다.

교훈: **고정 대기를 조건 대기로 옮길 때, 그 자리의 주석이 말하는 조건을 믿지 마라.** 주석은
그 값을 넣은 사람이 *의도한* 것을 적고, 값이 실제로 지키는 것은 그 사이에 끼어든 **다른
비동기**일 수 있다. 확인법은 하나다 — **옮긴 뒤 반복해서 돌린다.** 한 번의 초록으로 넘어갔으면
이 자리는 전량에서 흔들리는 검사가 되어 돌아왔을 것이다 (§2-7 과 같은 말, 다른 층).

그리고 이것이 ①을 옮기는 일의 값어치이기도 하다 — **옮기지 않았으면 이 사실을 아무도
몰랐다.** 150ms 는 그 자리에서 영원히 옳아 보였을 것이다.

### 2-16. (P3) 되울림과 실행을 가르지 못하면 준비 대기가 **헛돈다**

`sandboxplace` 의 고정 대기(700·900ms)를 "셸이 준비됐는가" 로 옮기려면 그 사실을 **볼** 수
있어야 한다. 표식을 그냥 `echo dm-ready` 로 치면 PTY 가 입력을 **되울리므로** 스냅샷에
`dm-ready` 가 즉시 나타난다 — 셸이 아직 뜨지도 않았는데 준비됐다고 읽는다.

그래서 `echo dm""-ready` 로 친다. 되울림에는 따옴표가 남고, **셸이 파싱해 실행한 출력에만**
따옴표가 빠진 `dm-ready` 가 나온다. 실측 스냅샷이 그것을 그대로 보여 준다:

```
":; echo dm\"\"-ready\r\n:; echo dm\"\"-ready\r\n\x1b[?2004hroot@5161ce2ff089:/#
 :; echo dm\"\"-ready\r\n\x1b[?2004l\rdm-ready\r\n\x1b[?2004hroot@5161ce2ff089:/# "
```

되울림이 **세 번** 먼저 오고(입력은 셸이 뜨기 전에 tty 에 들어간다) 프롬프트 뒤에야 실행
출력이 온다. 계측을 심어 이것을 눈으로 본 것이 이 변경의 절반이다 — §2-12 가 말한 "검사가
무엇을 재는지" 를 **준비 대기**에 적용하면 이 자리다.

덤: 조건 대기가 고정 대기보다 **빨랐다.** 컨테이너 넷 전부 9.9초 — 종전에는 그중 3.6초가
`time.Sleep` 이었다.

### 2-17. (P3) 같은 일을 **다시 적은 헬퍼**는 배움을 받지 못한다

`git-history.spec.ts` 의 `openHistory` 는 `fixtures.ts` 의 `openGit` 과 **같은 걸음을 따로
적어** 두고 있었다 — 창을 열고, 사이드를 Changes 로 돌리고, 뷰 일곱을 열고, 탭 수를 센다.

그 사이 `openGit` 은 셋을 배웠다. ① 뷰가 실제로 설 때까지 **다시 여는** `toPass` 골격
(`git-remote` R20 이 값을 치렀다) ② 사이드가 섰는가의 단정(로컬 16벌 중 14벌이 보던 것)
③ **첫 관측이 닿았는가** — 상한이 20→30→45 로 두 번 올라온 자리다. 각 줄에 왜 그런지가
열 줄씩 붙어 있다.

`openHistory` 는 **셋 중 아무것도 받지 못했다.** 그래서 관측이 아직 닿지 않은 패널 위에서
History 의 적재를 기다렸고, 전량에서 H4 가 `loadedCount` **0** 을 30초 내내 보았다.

교훈: **복사본은 원본이 배우는 동안 배우지 않는다.** 그리고 그 사실은 복사한 시점에는 보이지
않는다 — 복사할 때 두 벌은 같았다. 갈라지는 것은 **나중에** 일어나고, 갈라졌다는 신호는
"왜 이 파일만 흔들리는가" 로만 온다. `git-*` 스펙 스물아홉 중 `app.openGitWindow` 를 직접
부르는 것이 아직 여럿이다 — 다음 회차가 그중 어디를 가리킬지 이 교훈이 미리 말해 준다.

### 2-18. (P3) 흔들림에는 **결함**과 **꼬리**가 있고, 이름이 그 둘을 가른다

세 회차의 flaky 열 건에 **겹치는 이름이 하나도 없었다** (4 → 2 → 4). 고친 넷은 다음 회차에서
다시 나오지 않았고, 대신 매번 다른 넷이 나왔다.

그 둘은 같은 것이 아니다.

- **결함** — 검사가 어떤 사실을 **빠뜨렸다.** 고치면 그 이름은 다시 오지 않는다. P3 가 여덟을
  이렇게 닫았다 (워치독 문턱 하나 · 기준값을 목록 전에 읽음 · 넷 중 하나만 기다림 · 떨어진
  요소 · `openGit` 복사본 둘 · 상한 둘이 같은 크기 …)
- **꼬리** — 검사는 옳고 **상한이 부하의 분포를 덜 덮는다.** 이름이 매번 바뀌는 것이 그 증거다.
  8샤드 병렬에서 `git status` 한 바퀴가 45초를 넘는 회차가 드물게 있고, 그 회차에 **어느**
  검사가 걸릴지는 우연이다

**둘을 가르는 신호는 이름의 반복이다.** 같은 이름이 두 번이면 결함이고, 매번 다르면 꼬리다.
그래서 판정을 `flaky 0` 에서 `unexpected 0` 으로 옮겼다 (D-M9-11, 사용자 결정) — 꼬리를 0 으로
만드는 조건은 요구가 아니라 **부하**가 정하며, 그것을 DoD 로 두면 끝나지 않는 일이 된다.

**세는 일은 그만두지 않는다.** 회차마다 이름과 기전을 적는 것이 다음 회차에 그 신호를 준다 —
기록이 없으면 "매번 다르다" 를 말할 근거조차 없다. §1-10 의 표가 그 기록이다.

한 가지 더: **M9-A2 가 여덟 달 동안 이것을 "군집" 이라 부른 이유도 여기 있다.** 이름이 매번
바뀌니 하나로 묶여 보였다. 묶인 것은 원인이 아니라 **꼬리의 성질**이었고, 그 안에는 진짜 결함
여덟이 섞여 있었다 (§2-14).

### 2-19. (P6) **단일 진입점이 하나가 아니었다**

포커스의 단일 진입점은 `setFocusState` 다 — 파일 머리의 주석이 *"single entry point for the
focus invariant … REG-2~8 회귀 클래스 차단용"* 이라고 못박고 있다. 그래서 자리 기록을 거기
한 줄로 걸었다.

**탭을 둘 만들어도 기록이 0 이었다.** `+` 로 새 탭을 만드는 길은 *이미 포커스인 칸*에 탭을
얹으므로 포커스가 바뀌지 않고, 그래서 그 함수를 지나지 않는다. 단일 진입점은 **포커스의**
것이었지 **자리의** 것이 아니었다 — 자리는 (창, 칸, 탭) 셋이고 셋째의 주인은 `paneTabSet` 이다.

교훈: **"단일 진입점" 이라는 주석은 그 함수가 무엇의 단일 진입점인지까지 읽어야 한다.**
내가 재려는 것이 그 불변식과 같은 집합인지 묻지 않으면, 주석을 믿은 만큼 정확히 빗나간다.
둘을 같은 `_navNote` 로 모았으므로 **판정은 여전히 한 벌**이다 — 진입점이 둘인 것과 판정이
둘인 것은 다르다.

그리고 이것을 잡은 것은 검사가 아니라 **계측**이었다. 검사는 "다른 탭으로 갔다" 만 말했고
(`Expected … Received …` 의 uuid 둘), 기록이 **비어 있다**는 사실은 스택의 길이를 찍어 보고서야
보였다. 그래서 `navCounts()` 를 계약에 넣어 검사가 그것을 직접 재게 했다 (V-M9-24b·d).

### 2-20. (P6b) **재현이 아니라 산수가 원인을 확정했다**

M9-B2 는 P1 이 재현하지 못했고 P2 도 못 했다. 세 세션이 가설을 세우고 지웠다 —
`_restoreScrollOf` 가 안 돈다(틀렸다) · 떼인 뒤 갈무리한다(맞지만 원인이 아니었다) ·
두 기기 문제다(아니었다).

닫은 것은 **사용자 로그의 네 숫자**였다. `clientHeight/rows` 가 행 높이를 주고,
`areaH/행높이` 가 영역이 아는 줄 수를 주고, 그 둘의 차가 `rows` 와 **정확히** 같았다.
그 순간 가설이 필요 없어졌다 — 남은 것은 "누가 그 영역을 낡은 채로 두었는가" 하나였고,
그 답은 이미 `VIEW_SCROLL_RESTORE_SRS` §2.8 에 적혀 있었다(*"`ydisp===ybase` 면
`scrollToBottom()` 은 즉시 반환한다"*).

교훈 셋.

① **재현만이 길이 아니다.** 재현은 "같은 조건을 다시 만드는 것" 이고, 계측은 "그 순간의
   값을 적어 두는 것" 이다. 뒤의 것이 값싸고, 부하·기기·타이밍에 매인 결함에서는 **유일한**
   길이다. P2 가 계측을 심어 둔 것이 이 세션의 30분을 벌었다
② **재현되지 않는다고 조건을 넓히지 마라.** 내가 만든 첫 검사는 창만 왕복했고 **깨진
   코드에서도 초록**이었다 — 조건("떨어져 있는 동안 버퍼가 자란다")이 빠졌기 때문이다.
   조건을 아는 것이 곧 원인을 아는 것이고, 그 전에 쓴 검사는 아무것도 말하지 않는다
③ **이미 적혀 있는 기전을 다시 읽어라.** 고칠 자리의 근거 문서가 그 기전을 **문장으로**
   갖고 있었다. 세 세션이 그것을 읽고도 "그럼 바닥 갈래는 무엇이 깨우는가" 를 묻지 않았다

### 2-21. (P6b) **같은 물음에 두 문장으로 답하면 그 차이가 결함이다**

`term-pane.js` 의 `dragover` 와 `drop` 이 "이 드래그가 파일인가" 에 다르게 답했다 —
앞은 `types.includes('Files')`, 뒤는 `files || items`. 탭 드래그에도 `items` 가 실리는
판에서 뒤의 문장이 참이 되어 **그 드롭을 삼켰고**, 분할이 조용히 사라졌다.

두 함수는 **열 줄 거리**에 있었다. 한쪽이 옳았다는 것이 이 결함을 더 나쁘게 만든다 —
옳은 문장이 바로 위에 있으니 읽는 사람은 "판정은 되어 있다" 고 넘어간다.

그리고 증상이 **침묵**이었다. 오류도 경고도 없고 화면은 그대로다. 그래서 접수도 늦고
(사용자가 "긴급" 으로 올릴 때까지) 찾기도 어려웠다 — 콘솔에서 `DROP` 은 나는데
`splitPaneWithTab` 이 안 불린다는 **두 줄의 대조**가 자리를 지목했다.

교훈: **같은 물음이 두 자리에 있으면 그 둘을 한 이름으로 묶어라.** `isFileDrag()` 가
그 이름이고, 그것을 두는 자리는 이미 있었다 (`drop-entries.js` — 의존 0, 터미널·탐색기
공용). 없던 것은 함수가 아니라 **그것을 하나로 보려는 눈**이었다.

### 2-22. (P7) **`stash` 는 커밋에서 조용히 빠지고, 검사가 그것을 말하지 못했다**

P6b 가 M9-B2 를 고쳤다고 커밋했는데 사용자 화면은 그대로였다. 커밋 `70c1eea` 에
**고쳐야 할 파일이 없었다** — 일곱 파일 중 `web/js/ui/renderer.js` 만 빠졌고, 그
파일은 그 순간 `stash` 안에 있었다.

경위는 규약을 지키다 생겼다. **"RED 를 실제로 보아라 — `git stash push <바꾼 파일>`
→ 실행 → `stash pop`"** 의 앞 둘을 하고 셋째를 빠뜨린 채 커밋했다. `git status` 는
깨끗하다고 답했고 그 답은 참이었다. 인수인계 문서도 "작업 트리는 깨끗하다" 를 그대로
적어 넘겼다 — **그 문장은 아무것도 보증하지 않는다.**

**더 무거운 것은 검사 쪽이다.** stash 를 되살리기 **전에** V-M9-29 를 돌렸더니
`6 passed` 였다. 지키기로 한 코드가 통째로 없는데 초록이다. 그 검사는 이미 같은
자리를 두 번 밟았고(주석이 스스로 적고 있다 — 첫 판은 버퍼를 키우지 않아서, 둘째
판은 *다른 창의* 터미널을 키워서 "깨진 코드에서도 초록" 이었다) 이번이 세 번째다.

§2-12 는 "증상을 재는 검사는 그 증상을 없애는 **아무** 경로에나 초록을 준다" 였다.
이번 것은 한 단계 더 나쁘다 — **아무 경로도 없는데 초록을 줬다.**

교훈 둘.

① **커밋의 파일 목록을 요구와 대조하라.** "무엇을 고쳤다" 를 메시지에 적었으면 그
   파일이 `--name-only` 에 있어야 한다. 메시지와 diff 가 갈리면 메시지가 거짓말을
   하고, 그 거짓말은 다음 세션이 **사실로 읽는다** (이번에 그렇게 읽었다).
② **세 번 미끄러진 검사는 그 조항을 지킬 수 없다고 보라.** 헤드리스에서
   `.xterm-scroll-area` 가 낡는 조건과 실물에서 낡는 조건이 같다는 보장이 없다.
   고칠 곳은 검사의 **조건**이 아니라 재는 **대상**일 수 있다.


### 2-23. (P7) **"준다는 문서" 를 읽고 "주지 않는다" 를 단정했다**

P7 스펙의 첫 판이 `D-M9-22` 에 *"플랜 사용량은 프로토콜이 주지 않는다"* 를 적었다.
근거는 조사 문서(`M9_P7_GUI_SURVEY` §3)였고, 그 문서가 본 것은 **"CLI 의 `/usage` 가
그 값을 보인다"** 였다. 거기서 **"그러므로 스트림에는 없다" 로 건너뛰었다.**

한 줄이면 반증됐다:

```
claude -p --output-format stream-json --verbose "say OK" | grep rate_limit
```

`rate_limit_event` 프레임이 온다. 그리고 우리 어댑터는 그것을 **알아본 뒤 버리고
있었다** — `claude_proto.go:271` 의 `return nil, true`. "모르는 프레임" 이 아니라
**아는 프레임을 의도적으로 버리는 한 줄**이었고, 그래서 grep 으로도 안 보였다.

세 가지가 겹쳤다.

① **조사 문서를 실측으로 읽었다.** §3 의 표는 "우리가 지금 받는가" 열에 "안 받는다" 를
   적었지만, 그것을 **잰 것이 아니라 추론한 것**이었다. 조사와 실측은 다른 일이고,
   같은 문서에 나란히 적히면 다음 사람이 구별하지 못한다
② **`return nil, true` 는 침묵한다.** `false` 였다면 "모르는 프레임" 으로 로그에 남거나
   드리프트 검사에 걸렸을 것이다. **알아보고 버리는 것**이 가장 조용한 버림이다
③ **사용자가 그 자리를 먼저 짚었다.** *"에이전트마다 어떨지 모르니 자유롭게 기입할 수
   있게"* 라는 요구가 없었다면 `ProtoUsage` 의 고정 필드를 그대로 두었을 것이고,
   그랬다면 프레임이 온다는 것을 알았어도 담을 자리가 없었다

교훈: **"오지 않는다" 는 실측의 결론이어야 한다.** 문서가 다른 길(`/usage`)을 말한다는
것은 이 길에 없다는 뜻이 아니다. 그리고 **어댑터가 `true` 를 돌려주는 자리는 전부
"받았다" 가 아니라 "처리했다" 일 뿐**이므로, 무엇을 처리했는지 한 번은 세어 봐야 한다.

### 2-24. (P7) **없는 줄 알았던 것이 네 번 다 이미 있었다**

P7 의 요구 넷은 전부 "새로 만들어야 한다" 로 접수됐다. 실측하니 **네 자리 모두
값이 이미 오고 있었고, 쓰는 쪽이 없었다.**

| 무엇 | 어디까지 와 있었나 | 없던 것 |
|---|---|---|
| 셸 에이전트의 **세션 id** | 훅 → `/api/runs/context` 까지 | Run 밖에서 앉을 자리 |
| **플랜 사용량** | `rate_limit_event` 프레임 | 어댑터가 `return nil, true` 로 버렸다 |
| **cwd·저장소** | `/api/cwd` · `/api/git/repo-at?tool=` | 에이전트 화면에 잇는 자리 |
| **resume 기동** | `POST /api/tools?kind=agent&resume=` | 그 질의를 쓰는 프론트 한 줄 |

`cache read/write` 와 omp 의 `contextUsage.percent` 까지 세면 여섯이다.

**왜 안 보였나.** 셋이 같은 모양으로 숨었다.

① **"처리했다" 가 "받았다" 로 읽힌다.** `return nil, true` 는 "아는 프레임이고
   이벤트는 없다" 인데, 계약 검사는 `false`(모르는 프레임)만 센다. 알아보고 버리는
   자리는 **어떤 검사에도 걸리지 않는다**
② **폴백이 성공처럼 보인다.** `ObserveContext` 의 `found=false` 는 정상 경로이고
   주석이 그렇게 적혀 있다. 그 문장이 옳았기 때문에 **그 옆에 다른 일이 필요하다는
   것을 아무도 묻지 않았다**
③ **질의는 있는데 부르는 쪽이 없다.** `resume` 파라미터는 서버에 있었고 프론트에
   없었다. 서버만 보면 "된다" 이고 프론트만 보면 "없다" 다

교훈: **요구를 받으면 "만들 것" 을 먼저 세지 말고 "이미 지나가는 것" 을 한 번
세어라.** 세는 방법은 §3-6 이다. 그리고 **어댑터가 `true` 를 돌려주는 자리는 전부
"처리했다" 일 뿐**이므로, 무엇을 처리했는지는 따로 물어야 한다.

### 2-25. (P7) **홀로 싣는 검사가 있는 파일에는 생성자에 전역을 더하지 마라**

`term-pane.js` 생성자에 `UIKit.button` 한 줄을 더했더니 **두 층이 한꺼번에**
`ReferenceError: UIKit is not defined` 로 떨어졌다.

| 층 | 건수 | 무엇 |
|---|---|---|
| 전량 e2e | **5** | `reconnect-storm.spec.ts` — 합성 페이지에 그 파일만 싣는다 |
| 프론트 단위 | **25** | `web/js/test/term-resume.test.mjs` 외 — node 에서 파일 넷을 합쳐 싣는다 |

내 검사 넷과 `agent-tool.spec.ts` 19건은 **전부 초록이었다.** 전량과 `make unit` 이
각각 잡았다 (§2-13 이 "다시" 한 낱말로 겪은 것과 같은 자리다).

**처음 고친 방향이 틀렸다.** 하네스에 `ui-kit.js` 한 줄을 더해 e2e 5건을 살렸는데,
그것은 `reconnect-storm` 의 주석이 권하는 길이기도 했다:

> 이 하네스는 전역을 손으로 세우므로 **같은 변경에서** 여기 한 줄이 늘어야 한다.

그런데 `make unit` 이 25건으로 **같은 값을 한 번 더 치르라**고 말했다. 하네스가
둘이면 다음에는 셋이 된다. 그래서 반대로 갔다 — **생성자에서 의존을 뺐다.** 버튼은
조건이 처음 설 때(`refreshLift`) 만든다.

그 편이 설계와도 맞았다. 조건이 서지 않는 터미널에는 이 버튼이 **숨는 것이 아니라
아예 없다.** 고치고 나니 하네스에 더했던 한 줄도 되돌릴 수 있었다.

교훈 둘.

① **파일에 전역 의존을 더할 때는 그 파일을 홀로 싣는 검사가 있는지 먼저 보라.**
   `grep -rn "<파일명>" e2e/ web/js/test/` 한 번이면 나온다. 실서버를 태우는 검사만
   보면 드러나지 않는다
② **하네스를 고치기 전에 "의존을 만드는 자리를 옮길 수 있는가" 를 물어라.** 하네스
   목록은 늘어나고 그때마다 값을 치러야 하지만, **생성자에서 나중으로 미루는 것은
   한 번이다.** 그리고 대개 그쪽이 동작에도 더 맞다

## 3. 실측 방법 (다음 세션이 그대로 쓸 것)

### 3-1. 격리 인스턴스

```
DONGMINAL_HOST=127.0.0.1 /tmp/dm-m9 start --isolated --port 39321
```

`DONGMINAL_HOST` 를 **명시**해야 한다 — 도구 셸이 운영 인스턴스의 `0.0.0.0` 을 물려준다.
(FR-M9-2 가 그것을 고쳤으므로 그 뒤로는 `--isolated` 만으로 된다.)

**정지는 기동 출력이 찍어 준 줄을 그대로 쓴다:**

```
dongminal stop --all --port <그 포트> --home <그 격리홈>
```

`--port` 를 빼면 환경변수의 **운영 포트**가 채워져 운영 서버가 내려간다 (§2-11 에서 실제로 냈다).

### 3-2. 두 클라이언트 (M9-B3·B9 가 쓴 것)

Playwright 의 탭 둘은 **뷰포트가 따로**다 — `browser_tabs new` 뒤 각 탭에서
`browser_resize` 하면 한 브라우저로 모바일 폭과 데스크톱 폭을 동시에 세울 수 있다.
같은 도구를 두 탭이 열면 그것이 곧 두 기기다.

### 3-3. 잠든 기기 (M9-B9)

```js
window.__origFetch = window.fetch;
window.fetch = (u)=> /\/api\/(workspace|events)/.test(String(u)) ? new Promise(()=>{}) : window.__origFetch(...arguments);
app.bus._es.close();
window.EventSource = function(){ throw new Error('offline') };
```

되살릴 때는 둘을 되돌리고 `visibilitychange`·`focus`·`online` 을 쏜다.

### 3-4. Monaco 의 사실

레이아웃은 픽셀이 아니라 `editor.getLayoutInfo()` 로 읽는다(`minimap.minimapWidth`·
`overviewRuler.width`·`contentWidth`). 옵션의 실제 값은 `editor.getOption(monaco.editor.EditorOption.<name>)` —
**우리가 넘긴 값이 아니라 Monaco 가 채택한 값**이며, B5 의 실체가 그 차이였다.

### 3-5. 컨테이너가 필요한 검사를 로컬에서 돌리기 (FR-M9-13 이 쓴 것)

이 기계에는 docker 명령이 있으나 데몬이 없고, podman 머신이 **꺼진 채로** 있다.
docker CLI 를 podman 소켓에 물리면 `sandboxplace` 의 컨테이너 검사가 그대로 돈다:

```
podman machine start
export DOCKER_HOST="unix://$(podman machine inspect --format '{{.ConnectionInfo.PodmanSocket.Path}}')"
docker info --format '{{.OSType}}'      # linux 가 나와야 한다 (runtimeReady 의 판정)
go test -race -count=1 -v ./internal/shared/sandboxplace/
podman machine stop                     # 원래대로 되돌린다
```

`sandbox.FindRuntime` 이 찾는 이름은 `docker` 하나이므로 podman 을 **그 이름으로** 쓰는 것이
이 우회의 요점이다. **전량 e2e 전에 머신을 내려라** — 2GiB VM 이 여덟 샤드와 CPU 를 다툰다.

### 3-6. 와이어가 실제로 무엇을 싣는지 세기 (P7 이 쓴 것)

문서가 "다른 길로 온다" 고 적었다는 것은 **이 길에 없다는 뜻이 아니다** (§2-23).
프레임을 직접 세어라.

```
cd /tmp && claude -p --output-format stream-json --verbose "say OK" > s.jsonl
LC_ALL=C grep -ao '"type":"[a-z_]*"' s.jsonl | sort | uniq -c
LC_ALL=C grep -ac "rate_limit\|usage\|session_id" s.jsonl
```

프론트가 **조용히 반환할 때**는 응답을 수집해 자리를 지목한다 — 콘솔 오류가 없는
실패는 "요청이 아예 나가지 않았다" 인 경우가 많다.

```ts
page.on('response', async (r) => {
  if (r.url().includes('/api/tools?kind=agent')) errs.push(`${r.status()} ${await r.text()}`);
});
```

P7 에서 이 두 줄이 `this.app` 오류를 지목했다 — 터미널 도구는 생성자가 `(id, name)`
이고 **전역 `app`** 을 쓴다 (`renderer.js:1241` 이 그 규약이다).

## 1. 개요

### 1.1 목적

브라우저가 다시 붙으면 **새 xterm 이 선다.** 그 인스턴스는 앱이 켜 둔 터미널
모드를 하나도 모른다 — 모드는 앱이 보낸 `ESC[?…h` 를 **본** 터미널만 아는
것이기 때문이다.

화면은 복원된다. 스크롤백을 재생하므로. 그러나 **모드는 복원되지 않는다.**

### 1.2 어떻게 드러났나 — 이미지 붙여넣기가 조용히 죽는다

접수된 증상의 사슬은 이렇게 닫힌다.

1. 이미지를 `Cmd+V` 하면 브라우저의 `text/plain` 은 **빈 문자열**이다 (관측:
   `types: ['Files']`, `text: ""`).
2. xterm 의 붙여넣기는 그 빈 문자열에도 돈다. 감싸기의 **유일한 조건**이
   `decPrivateModes.bracketedPasteMode` 다 (`web/vendor/xterm.js`):

   ```js
   function s(e,t){ return t ? "\x1b[200~"+e+"\x1b[201~" : e }
   ```

3. 모드가 켜져 있으면 12바이트(`ESC[200~ESC[201~`)가 나가고, 꺼져 있으면 빈
   문자열이다. 그리고 `term-pane.js:232` 가 그것을 버린다:

   ```js
   _sendText(s){ if(!s) return; … }
   ```

4. Claude Code 는 **빈 붙여넣기**를 "텍스트가 아닌 것이 붙여넣어졌다" 로 읽고
   시스템 클립보드를 스스로 뒤진다. 3의 12바이트가 그 신호다. 그것이 나가지
   않으면 claude 는 `Cmd+V` 가 눌린 사실조차 모른다.

**왜 재시작하면 고쳐지는가.** claude 는 시작할 때 `ESC[?2004h` 를 한 번 보낸다.
새 xterm 이 그것을 보면 모드가 선다.

**왜 들쭉날쭉한가.** 재생의 재료는 서버의 출력 링버퍼이고 그 크기는
`bufMax = 1<<20`(1MB)이다. claude 를 켠 뒤 출력이 1MB 를 넘으면 시작 시점의
`ESC[?2004h` 는 이미 밀려나 있다. **넘기 전에 재접속하면 되고, 넘긴 뒤면 안 된다.**

**왜 셸에서는 드러나지 않았나** (검증 중 실측, 2026-09-18). `bash 5`·`zsh` 는
**프롬프트를 그릴 때마다** `ESC[?2004h` 를 다시 보낸다. 그래서 셸 앞에서는 재접속
직후의 첫 프롬프트가 모드를 되켜고, 유실이 눈에 띄지 않는다.

이 사실은 검사가 가르쳐 주었다 — 복원을 통째로 들어낸 채로도 셸 기반 검사가
**통과했다.** 그래서 `V-TMR-9` 는 `printf '…2004h'; seq …; cat` 으로 **프롬프트가
다시 그려지지 않는 상태**를 만든다. 그것이 claude 와 동형이다: **시작할 때 한 번
켜고 계속 도는 앱.** 이 결함이 claude 에서만 보인 이유가 정확히 그것이다.

### 1.3 같은 유실의 다른 얼굴 (사용자 결정 D-2)

bracketed paste 는 이 유실의 **한 사례**다. 앱이 켜 두는 모드는 더 있고, 같은
이유로 같이 사라진다.

| 모드 | 잃으면 |
|---|---|
| `2004` bracketed paste | 붙여넣기가 타이핑이 된다 · 빈 붙여넣기 신호가 사라진다 (§1.2) |
| `1000`·`1002`·`1003` 마우스 추적 | TUI 에서 **마우스가 먹지 않는다** |
| `1005`·`1006`·`1015` 마우스 인코딩 | 좌표가 깨지거나 넓은 화면에서 잘린다 |
| `1004` 포커스 이벤트 | 앱이 포커스 전환을 보지 못한다 |

### 1.4 범위

**포함** — 위 표의 모드들, 그 추적과 재접속 시 복원.

**비포함** — 대체 화면 버퍼(`1049`·`47`·`1047`), 커서 모양·가시성, 줄바꿈 모드,
문자셋. 대체 화면은 **재생이 이미 화면을 되살리므로** 다른 규칙이 필요하고
(버퍼 전환은 내용을 동반한다), 나머지는 접수된 증상과 무관하다. 넓히는 일은
근거가 생겼을 때 한다.

### 1.5 정의

| 말 | 뜻 |
|---|---|
| **DEC private mode** | `ESC[?<n>h`(켜기) · `ESC[?<n>l`(끄기)로 앱이 터미널에 켜는 상태 |
| **프로토콜** | 마우스 보고의 종류. `9`·`1000`·`1002`·`1003` 중 **하나**다 |
| **인코딩** | 마우스 좌표의 표현. `1005`·`1006`·`1015` 중 **하나**다 |
| **복원 시퀀스** | 재접속 직후 서버가 보내는, 켜진 모드를 다시 세우는 바이트 |

## 2. 현재 상태 (조사로 확정, 2026-09-18)

### 2.1 추적은 하나뿐이고, 리터럴 두 개만 본다

`bracketpaste.go` 의 `scanBracketedPaste` 는 `ESC[?2004h`·`ESC[?2004l` **정확한
리터럴**을 찾는다. 그래서 `ESC[?1002;1006h` 처럼 **파라미터를 묶어 보내는 형태**를
구조적으로 볼 수 없다 — 마우스 모드는 그 형태가 흔하다.

### 2.2 서버는 이미 진실을 안다 (bracketed paste 한정)

`Tool.BracketedPaste()` 가 PTY 출력을 읽는 고루틴의 관찰로 유지된다
(`tool.go:377`). **웹서버가 재시작해도 데몬의 Tool 은 그대로이므로 이 값은 살아
있다.** 잃는 쪽은 브라우저뿐이다.

### 2.3 재접속의 순서는 이미 정해져 있다

`handleWSDirect`·`handleWSDaemon` 이 같은 순서를 지킨다 — `OpToolID` → 크기 →
재생(`OpOutput`) → 좌표(`OpSeq`). 크기가 재생보다 **앞**인 이유가 적혀 있다
(`FR-M9-3` ①: "재생 바이트는 PTY 폭 기준으로 쓰인 이스케이프를 담고 있다").

### 2.4 xterm 의 모델은 값 셋이다

`web/vendor/xterm.js` 를 읽었다. 마우스는 플래그 여럿이 아니라 **`activeProtocol`
하나**이고(`case 1e3: "VT200"`, `case 1002: "DRAG"`, `case 1003: "ANY"`), 인코딩도
하나다. 그러므로 서버가 비트 집합으로 기억하면 **순서를 잃어** 복원이 틀린다 —
`1002h` 뒤에 `1003h` 가 오면 `1003` 만 남아야 한다.

## 3. 요구사항

### 3.1 묶음 M — 모드 추적 (`FR-TMR-1`~)

**FR-TMR-1** `Tool` 은 PTY 출력에서 **DEC private mode 설정**을 일반적으로 읽는다.
`ESC[?` 뒤의 파라미터를 `;` 로 갈라 각각을 하나의 설정으로 본다 — `ESC[?1002;1006h`
는 둘을 켠 것이다. 종전의 리터럴 대조(§2.1)를 대체한다.

**FR-TMR-2** 기억하는 것은 **값 셋과 플래그 둘**이다 (§2.4 의 모델 그대로).

| 기억 | 값 |
|---|---|
| bracketed paste | 켜짐/꺼짐 (`2004`) |
| 마우스 프로토콜 | 없음 · `9` · `1000` · `1002` · `1003` 중 하나 |
| 마우스 인코딩 | 기본 · `1005` · `1006` · `1015` 중 하나 |
| 포커스 이벤트 | 켜짐/꺼짐 (`1004`) |

**FR-TMR-3** 같은 갈래의 켜기가 겹치면 **마지막이 이긴다.** 프로토콜·인코딩은
하나뿐이므로 새 값이 옛 값을 밀어낸다.

**FR-TMR-4** 갈래에 속한 **어느 번호의 끄기**든 그 갈래를 비운다. `1002l` 은
프로토콜을 없음으로 만든다 — 그것이 xterm 의 동작이며(§2.4), 우리가 다르게
기억하면 복원이 화면과 어긋난다.

**FR-TMR-5** 관심 밖의 모드는 **무시한다.** `ESC[?25h`(커서 보이기)처럼 흔한
것들이 상태를 흔들지 않는다.

**FR-TMR-6** 시퀀스가 읽기 경계에 걸려 쪼개져도 놓치지 않는다 (`FR-BPT-3` 승계).
이월 상한은 파라미터가 묶인 형태를 담을 만큼 넓힌다 — 종전 8바이트는
`ESC[?1000;1002;1003;1006h` 를 담지 못한다.

**FR-TMR-7** 판정은 `readPTY` 고루틴만 하고, 결과는 원자적으로 공유한다
(`FR-BPT-4` 승계).

**FR-TMR-8** `Tool.BracketedPaste()` 의 계약은 **한 글자도 바뀌지 않는다.** 새
모델 위의 얇은 접근자가 된다 — `SendPaste` 가 그것을 딛고 있고(`FR-BPW-1`), 그
경로는 이 문서의 대상이 아니다.

### 3.2 묶음 R — 복원 (`FR-TMR-20`~)

**FR-TMR-20** 재접속하면 서버가 **켜져 있는 모드를 다시 세우는 바이트**를 보낸다.
클라이언트는 그것을 여느 출력과 똑같이 xterm 에 넘긴다 — **프론트는 한 줄도
바뀌지 않는다.** 모드를 세우는 일은 원래 터미널의 몫이고, 우리는 앱이 보냈을
바이트를 대신 보낼 뿐이다.

**FR-TMR-21** 자리는 **재생 바로 뒤, 좌표 통보 앞**이다.

- 재생 **앞**이면 안 된다: 재생 데이터 안에 낡은 `ESC[?2004l` 이 있으면 그것이
  우리 복원을 덮는다.
- 좌표(`OpSeq`) **뒤**면 안 된다: 그 뒤의 `OpOutput` 은 라이브 PTY 바이트뿐이라는
  것이 `FR-TRS-8` 의 계약이고, 클라이언트는 길이를 더해 좌표를 유지한다.

**FR-TMR-22** 켜진 것이 하나도 없으면 **아무것도 보내지 않는다.** 새 xterm 의
기본값이 전부 꺼짐이므로 보낼 이유가 없다 — 끄기를 명시적으로 보내는 것은 없는
문제를 위해 바이트를 쓰는 일이다.

**FR-TMR-23** 순서는 **프로토콜 → 인코딩 → 나머지**다. 앱이 보내는 관례와 같게
둔다. xterm 에서는 서로 독립이므로 결과는 같지만, 로그로 읽을 사람이 앱의
출력과 견줄 수 있어야 한다.

**FR-TMR-24** direct 모드와 daemon 모드가 **같은 바이트를 같은 자리에서** 보낸다
(`FR-TRS-12` 승계). daemon 모드는 값을 RPC 로 받아야 하므로 `ToolSnapshot` 에
싣는다 — `Cols`·`Rows` 가 같은 이유로 이미 거기 있다.

**FR-TMR-25** 값이 없는 옛 데몬과 붙어도 **깨지지 않는다.** 필드가 비면 복원이
없을 뿐이고, 그것이 지금의 동작이다.

## 5. 비목표

1. **대체 화면 버퍼의 복원** (§1.4). 재생이 화면을 되살리는 것과 규칙이 다르다.
2. **프론트에서의 모드 추측.** 브라우저가 스스로 "claude 니까 켜져 있겠지" 를
   판단하는 길은 두지 않는다 — 진실은 PTY 출력에 있고 서버가 그것을 본다.
3. **이미지 붙여넣기 자체의 구현.** dongminal 이 클립보드의 `Files` 를 받아
   업로드하는 것은 별건이며, 이 문서는 **있던 것이 사라지는 결함**을 고친다.
4. **링버퍼 확대.** 1MB 를 늘려도 시점만 미룰 뿐 같은 결함이 남는다.

## 6. 리스크

- **MEDIUM — 마우스 모드를 잘못 복원하면 클릭이 앱으로 새어 간다.** 껐어야 할
  것을 켜면 사용자가 선택·복사를 못 한다. `FR-TMR-4`(끄기는 갈래를 비운다)와
  `V-TMR-3` 이 그 자리를 지킨다.
- **LOW — 복원 바이트가 좌표를 어긋내는 것처럼 보일 수 있다.** `FR-TMR-21` 이
  자리를 좌표 통보 앞으로 못박는다. `OpSeq` 는 서버가 계산한 값을 싣지 재생
  길이를 세지 않는다.
- **LOW — 추적 대상이 늘어 뜨거운 경로가 무거워진다.** 스캔은 여전히 ESC 가 없는
  청크에서 한 번의 `IndexByte` 로 빠져나간다 (`NFR-BP-1` 유지).

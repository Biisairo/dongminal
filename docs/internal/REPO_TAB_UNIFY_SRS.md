## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 넷이다.

> **① "git, editor 통합 작업이야. 둘을 하나의 탭으로 만들고 탭 내에서는 왼쪽을
> git, 오른쪽을 editor 로 pane 을 나눠줘. add 를 하면 무조건 git, editor 가 같이
> 나오는거고, git 작업소가 없으면 빈 pane 에 git init 버튼을 만들어서 사용자로
> 하여금 git init 을 할 수 있게 만들어줘야해."**
>
> **② "창 좌측에 git, 탐색기를 두고 진짜 git 처럼 editor 창에 diff 를 띄우고
> history 를 띄우고 하는거야. changes 만 좌측 고정이고. 오른쪽에 뜨는 diff,
> history 등은 tab 으로 그냥 editor 와 동일한 취급으로 1개의 탭으로 취급하는거지."**
>
> **③ "git changes 와 파일탐색기도 탭으로 교체가능하도록 하면 오른쪽 영역이 더
> 넓어지고 탐색기와 git changes 를 보는게 더 편해지겠지?"**
>
> **④ "diff 창도 vsc 처럼 되었으면 좋겠어. 새 문서면 그냥 보여주는거. 그리고 diff
> 편집 가능한거."**

넷을 합치면 하나의 그림이 된다.

```
┌──────────────────┬─────────────────────────────────────┐
│ [Explorer][Changes]  [a.ts][b.ts ⇄][History][×]        │
├──────────────────┼─────────────────────────────────────┤
│ ◉ ⏲ ⎇ ≣ › ⧉     │                                     │
│ [커밋 메시지…]    │            monaco                   │
│ [Commit] □ amend │                                     │
│ main ↑2 ↓0       │                                     │
│ ▾ Staged (1)     │                                     │
│    M src/a.ts    │                                     │
│ ▾ Changes (2)    │                                     │
│    M src/b.ts    │                                     │
└──────────────────┴─────────────────────────────────────┘
```

**저장소 하나가 창 하나다.** 좌측은 `Explorer` 와 `Changes` 를 탭으로 갈아 끼우고,
diff·history·branches 는 **오른쪽에 편집기 탭과 똑같은 자격으로** 뜬다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **T** 사이드바 | `Git`·`Editor` 두 탭을 `Repo` 하나로. 목록도 하나 |
| **W** 창 | 좌측 사이드(Explorer↔Changes 탭) + 우측 편집기 영역. 폭·상태의 영속 |
| **C** Changes 사이드 | 진입점 아이콘 줄 · 커밋 입력 · 브랜치 줄 · 변경 목록의 순서. `git init` |
| **V** git 뷰 탭 | Diff·History·Branches·Stash·Console·Worktrees 가 우측 탭이 된다 |
| **P** 미리보기 탭 | 한 번 클릭은 재사용, 더블클릭은 고정 (VSCode 규약) |
| **D** diff 편집 | 워킹 트리 쪽 편집·저장. untracked 는 단일 편집기 |
| **S** 패널 수명 | 창마다 `GitPanel` 하나. **관측기도 저장소마다 하나** (D-RTU-16) |
| **M** 마이그레이션 | 기존 `WINDOW_TYPE_GIT` 창의 소멸과 라우팅 이관 |
| **B** 모바일 | 좌측 사이드와 우측 pane 을 한 줄로 순회 |

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|---|---|
| **Repo 창** | 경로 하나에 대응하는 창. 코드상 타입은 `editor` 그대로다 (D-RTU-1) |
| **사이드 (side)** | Repo 창 좌측의 고정 영역. 분할 트리 **밖**이며 `Explorer`·`Changes` 두 탭을 갖는다 |
| **본문 (main)** | Repo 창 우측. 기존 pane·탭·분할 트리가 그대로 산다 |
| **git 뷰 탭** | 본문에 뜨는 `type==='git'` 탭. `gitView` 로 어느 뷰인지 갈린다 |
| **미리보기 탭** | 다음 미리보기가 **대체하는** 탭. 고정되기 전까지 하나만 존재한다 |
| **워킹 트리 축** | 오른쪽이 **디스크의 파일**인 축 — unstaged·untracked. index·커밋 축과 다르다 |

## 2. 현재 상태 (조사로 확정한 사실)

**파일:줄로만 적는다.**

### 2.1 창 타입이 셋이고 그중 둘이 같은 경로 집합을 본다

| 타입 | 개수 | 좌측 | 우측 |
|---|---|---|---|
| `terminal`(기본) | N | — | pane·탭·분할 |
| `git` | **워크스페이스에 1개** (FR-GIT-26) | — | 고정 탭 7개 |
| `editor` | 루트마다 1개 | 탐색기 | pane·탭·분할 |

그리고 `git.pinned[]` 와 `editors.list[]` 는 **이미 같은 집합이다** — 연동
(FR-EDT-31~34)이 한 번의 저장 안에서 둘을 함께 바꾼다. 실측한 워크스페이스에서도
다섯 경로가 두 목록에 똑같이 들어 있다.

> **따라서 사이드바 목록 둘을 하나로 합치는 데 새 서버 표면이 필요하지 않다.**
> 화면이 둘을 따로 그리고 있을 뿐이다.

### 2.2 git 뷰의 DOM 은 이미 탭과 독립이다

```js
web/js/git/panel-life.js:76-84   elFor(view) { … 뷰별 DOM 을 만들어 캐시하고 돌려준다 }
web/js/ui/renderer.js:425-433    if(at.type===TAB_TYPE_GIT){ … _gitPanel(slot).elFor(at.gitView) … }
```

`_mountTabBody` 는 **탭 타입별 분기**이고 git 분기가 이미 있다. 탭이 어느 창에
있는지는 보지 않는다.

> **그러므로 git 뷰를 Repo 창 본문의 탭으로 올리는 데 렌더러의 새 분기가 필요
> 없다.** 막고 있는 것은 창 게이트 하나뿐이다 (§2.3).

### 2.3 Editor 창은 편집기 탭만 받도록 막혀 있다

```js
web/js/core/app-layout.js:285-292
  if (this._isGitWin(s)) return;                          // Git 창엔 탭 추가 금지
  if (this._isEditorWin(s) && type !== 'editor') return;  // Editor 창엔 editor 만
```

FR-EDT-54 의 자리다. **이 한 줄이 요구 ②를 막는 전부다.**

드래그드롭 게이트도 창 타입을 본다 (`app-dnd.js:16`·`35`·`51`·`54`·`99`·`123`).
탭 타입 자리에는 조건이 없다 (D-25) — 그래서 git 뷰 탭이 Repo 창 **안에서**
움직이는 것은 지금 규약으로도 성립한다.

### 2.4 `GitPanel` 은 칸마다 하나이고 창을 모른다

```js
web/js/core/app-git.js:24-31    _gitPanel(slot){ … key=this._slotKey('git',slot||0) … }
web/js/core/app-git.js:551-552  get gitPanel(){ return this._gitPanel(this._slotFocused()) }
```

키에 창 id 가 없는 이유가 주석에 있다 — "Git 창은 워크스페이스에 하나뿐이므로
(FR-GIT-26) 키에 창 id 를 넣을 이유가 없다".

> **그 전제가 이번에 깨진다.** 창이 경로마다 생기므로 키가 (루트, 칸)이 되어야
> 하고, `app.gitPanel` 이 무엇을 돌려주는지도 다시 정해야 한다 — 지금은 **활성
> 칸**만 보고 활성 **창**은 보지 않는다.

관측은 앱에 하나다 (`_gitObs`, FR-SVS-30).

> **착수 시점에는 "이쪽은 바뀌지 않는다" 고 적었고, 구현이 그것을 뒤집었다**
> (D-RTU-16). `GitObserver` 는 status·signature·소실·실패 누적을 **통째로** 들고
> 있고 주기 타이머가 `any()` 로 아무 패널이나 골라 수집한다 — 관측기가 하나면
> 마지막에 수집한 저장소의 상태를 모든 Repo 창이 함께 본다.

### 2.5 뷰 전환이 Git 창의 탭 바를 딛는다

```js
web/js/git/panel-diff.js:56-62
  openView(view){
    const w=this.app._gitWindow(); if(!w||!w.layout) return;
    …그 창의 pane 에서 gitView 가 맞는 탭을 찾아 switchTab…
  }
```

파일을 클릭해 Diff 를 여는 경로가 여기다. **Git 창이 사라지면 이 함수가 갈 곳을
잃는다.**

### 2.6 diff 는 완전히 읽기 전용이다

```js
web/js/core/constants-git.js:331-332   readOnly:true, originalEditable:false
web/js/core/constants-git.js:358       GIT_DIFF_DRAWABLE=new Set(['text','absent'])
```

새 파일은 서버가 `original.kind='absent'` 를 주고(`query/diff.go:138`), 클라이언트가
그것도 그릴 수 있는 것으로 보아 **빈 왼쪽과 비교하는 화면**을 그린다.

VSCode 의 실동작은 다르다 — untracked 를 고르면 diff 가 아니라 **편집기**가 열리고,
Working Tree diff 의 오른쪽은 **편집·저장된다.** Index diff 의 오른쪽은 읽기
전용이다.

### 2.7 편집기의 저장 경로는 이미 하나다

`FileEditor.save()`(`file-editor.js:454`)가 `Cmd+S`(`:375-378`)에 걸려 있고
`/api/file/write` 로 간다. dirty 표시도 그 안에 있다 (`:520`·`:531`).

> **diff 편집의 저장은 이 경로를 그대로 써야 한다** — 새 쓰기 표면을 만들면 같은
> 파일을 두 길로 쓰게 되고, dirty·충돌 규약이 둘로 갈린다.

### 2.8 미리보기 탭이라는 개념이 없다

`addTab` 은 언제나 새 탭을 만들고, 편집기 탭은 **이미 열려 있으면 그 탭으로
이동한다**(`_findEditorTab`, FR-EDT-101). 즉 중복은 막지만 "훑어보다 버리는 탭" 은
없다. 변경 20개를 훑으면 탭이 20개 남는다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 T — 사이드바 `Repo` 탭

**FR-RTU-1.** 사이드바 탭은 **둘**이 된다 — `Windows` · `Repo`. `Git` 과 `Editor`
서술자를 하나로 합친다.

**FR-RTU-2.** `Repo` 목록의 항목은 **경로 하나**다. 표시 이름은 마지막 조각, 툴팁은
절대경로 전체다.

**FR-RTU-3.** 목록의 원천은 `editors.list[]` 다. `git.pinned[]` 는 연동으로 같은
값을 갖지만 **화면이 읽는 자리는 하나**여야 한다 (D-RTU-2).

**FR-RTU-4.** root 행(`~`)은 최하단 고정이며 제거·재정렬 대상이 아니다 (FR-EDT-14·15
그대로).

**FR-RTU-5.** `+ Add` 는 종전대로 경로를 받아 `POST /api/editors/add` 를 부른다.
연동이 Git 핀을 함께 만든다 — **요구 ①의 "add 하면 git·editor 가 같이 나온다" 는
이미 서버가 하는 일이며, 화면이 둘로 보이던 것이 문제였다.**

**FR-RTU-6.** 행에는 변경 개수 배지가 붙는다. 근거는 `/api/git/repos` 의 마지막
관측값이며, 저장소가 아닌 행에는 배지가 없다 (FR-GOB-14 규약 유지).

**FR-RTU-7.** 직행 키는 배열에서 파생된다 — `Ctrl+Shift+2` 가 `Repo` 다.
`sidebarTab3` 은 **사라진다.** 설정 화면의 단축키 목록도 배열에서 파생되므로 손으로
지우지 않는다 (FR-EDT-5 의 규약).

**FR-RTU-8.** 순회 키는 `Repo` 행을 돈다. root 행이 마지막 자리로 포함된다.

**FR-RTU-9.** git 이 없는 환경(`_gitOff`)에서도 `Repo` 탭은 **사라지지 않는다.**
탐색기와 편집기는 git 없이도 성립한다 — 그 경우 Changes 사이드가 사유를 보인다
(FR-RTU-25). 옛 FR-SBT-8(git 없으면 탭 자체를 감춘다)은 여기서 폐기된다.

### 3.2 묶음 W — Repo 창

**FR-RTU-10.** 창 타입 문자열은 **`editor` 그대로**다 (D-RTU-1). 기존
`WINDOW_TYPE_EDITOR` 판정과 워크스페이스 값이 그대로 산다.

**FR-RTU-11.** 창은 **사이드**와 **본문**으로 나뉜다. 사이드는 분할 트리 밖의 고정
영역이며 어떤 드롭으로도 쪼개지지 않는다 (FR-EDT-46 계승).

**FR-RTU-12.** 사이드는 탭 **둘**을 갖는다 — `Explorer` · `Changes`. **한 번에
하나만 보인다.**

> 요구 ③의 근거를 그대로 따른다 — 세로로 쌓으면 파일 목록도 변경 목록도 절반
> 높이가 된다. 탭이면 보이는 쪽이 사이드 전체 높이를 쓴다.

**FR-RTU-13.** 사이드의 활성 탭은 **창마다** 기억되고 워크스페이스에 저장된다
(`window.editor.side`). 폭도 종전대로 저장된다 (`explorerWidth`, FR-EDT-47).

**FR-RTU-14.** 파일을 열면 사이드가 `Explorer` 로 바뀌지 **않는다.** 사용자가 고른
탭은 사용자의 것이다.

**FR-RTU-15.** 본문은 기존 pane·탭·분할 모델을 그대로 쓴다. 분할은 드래그드롭만이며
(FR-EDT-51) 분할 단축키·버튼은 감춰진다 (FR-EDT-50).

**FR-RTU-16.** 본문에는 **편집기 탭과 git 뷰 탭**이 산다. 터미널·run 탭은 여전히
만들 수 없다 — `app-layout.js:288` 의 게이트를 `type!=='editor' && type!==TAB_TYPE_GIT`
로 좁힌다.

**FR-RTU-17.** 탭 이동은 **같은 창 안에서만** 가능하다 (FR-EDT-53 계승). git 뷰
탭도 같은 규칙을 받는다.

**FR-RTU-18.** 창에 pane 이 하나도 없을 수 있다 (FR-EDT-55). 그때 본문은 안내문이며
사이드는 그대로 동작한다.

### 3.3 묶음 C — Changes 사이드

**FR-RTU-20.** `Changes` 사이드의 세로 순서는 **위에서부터** 다음과 같다.

| 순서 | 내용 |
|---|---|
| 1 | **진입점 아이콘 줄** — History · Branches · Stash · Console · Worktrees |
| 2 | **커밋 입력** — 메시지 · `Commit` · `amend` |
| 3 | **브랜치 줄** — 브랜치명 · ahead/behind · 원격 버튼 |
| 4 | **변경 목록** — Staged · Changes · Untracked · Conflicts (스크롤) |

커밋 입력이 브랜치 줄보다 **위**인 것은 사용자 지시다 (D-RTU-4). 1~3은 고정이고
4만 스크롤한다 — 목록이 길어도 커밋 입력이 자리를 떠나지 않는다.

**FR-RTU-21.** 아이콘 줄의 다섯 진입점은 각각 **본문에 그 뷰의 탭을 연다.** 이미
열려 있으면 그 탭으로 이동한다 (FR-RTU-31).

**FR-RTU-22.** 아이콘 줄은 `Explorer` 탭에서는 보이지 않는다 — 그쪽은 git 의 자리가
아니다.

**FR-RTU-23.** 변경 목록의 행 동작(선택·스테이지·discard·컨텍스트 메뉴)은 **한 줄도
바뀌지 않는다.** 바뀌는 것은 그 목록이 놓인 자리뿐이다.

**FR-RTU-24. 루트가 저장소 안이면 그 저장소를 보인다** (GIT_DIR_ENTRY_SRS FR-DIR-40
과 같은 기준). 사이드 머리에 그 저장소의 이름을 적어, 지금 보는 것이 상위의
것임을 알린다.

**FR-RTU-25. 저장소가 없으면 `Changes` 사이드가 그 사실과 `git init` 을 보인다.**

```
┌──────────────────┐
│ [Explorer][Changes]
├──────────────────┤
│                  │
│  이 폴더는 git   │
│  저장소가 아닙니다│
│                  │
│  [git init]      │
│  ~/notes         │
└──────────────────┘
```

**FR-RTU-26.** `git init` 은 **확인을 거친다.** 확인창은 대상 절대경로를 밝힌다 —
홈처럼 넓은 경로에서 실수로 누르면 되돌리기가 사용자의 몫이 된다.

**FR-RTU-27.** `git init` 이 성공하면 그 경로가 **Git 핀에도 더해진다.** 이미 Repo
목록에 있으므로 목록은 변하지 않는다.

**FR-RTU-28.** init 직후 색과 목록이 곧바로 선다. 서버는 `RepoRoot` 실패를 2초
캐시하므로(`store.go:198-215`) init 을 수행한 종단이 **그 캐시를 무효화한다** —
그러지 않으면 사용자가 누른 뒤 2초 동안 아무 일도 일어나지 않은 것처럼 보인다.

**FR-RTU-29.** `git init` 종단을 신설한다.

```
POST /api/git/init  {"path":"<abs>"}  → {"repo":"<abs>"}
```

절대경로만 받고, 이미 저장소면 `exists`(409), 디렉터리가 아니면 `bad_request`(400)다.
초기 브랜치 이름은 **git 의 기본값을 그대로 쓴다** — 우리가 정하면 사용자의
`init.defaultBranch` 설정과 어긋난다.

### 3.4 묶음 V — git 뷰 탭

**FR-RTU-30.** `Diff` · `History` · `Branches` · `Stash` · `Console` · `Worktrees`
여섯은 **본문의 탭**이 된다. 탭 타입은 기존 `TAB_TYPE_GIT` 이고 `gitView` 가 어느
뷰인지 말한다.

**FR-RTU-31.** `Changes` 를 뺀 다섯은 창에 **하나씩만** 열린다. 이미 있으면 그
탭으로 이동한다.

**FR-RTU-32.** `Changes` 는 본문 탭이 **되지 않는다.** 사이드에만 있다 (요구 ②).

**FR-RTU-33.** git 뷰 탭은 편집기 탭과 **같은 자격**이다 — 이름·닫기·드래그·분할이
모두 같다. 탭 이름은 뷰 이름이며, Diff 만 대상 파일명을 쓴다 (FR-RTU-41).

**FR-RTU-34.** git 뷰 탭을 닫는 것은 자유다. 다시 열면 새로 만들어지고, 그 뷰의
상태(스크롤·선택)는 패널이 들고 있으므로 보존된다.

**FR-RTU-35.** 창을 닫거나 행을 지우면 그 창의 git 뷰 탭도 함께 사라진다 — 창의
수명이 곧 탭의 수명이다.

### 3.5 묶음 P — 미리보기 탭

**FR-RTU-40. 변경 목록의 한 번 클릭은 미리보기 탭을 재사용한다.** 다음 클릭이 그
탭의 대상을 갈아 끼우므로 탭이 쌓이지 않는다.

**FR-RTU-41.** 미리보기 탭의 이름은 대상 파일명이며 **기울임**으로 그린다 — 이 탭이
곧 대체될 것임을 보이는 표시다 (VSCode 규약).

**FR-RTU-42. 고정되는 계기는 넷이다** — ① 탭 더블클릭 ② 그 탭에서 편집을 시작
③ 탭 이름 더블클릭 ④ **탐색기·변경 목록 행의 더블클릭**. 고정되면 기울임이 풀리고
다음 미리보기는 **새 탭**을 만든다.

④ 는 구현 중에 더했다 — 초판이 빠뜨렸고 VSCode 는 그것도 고정 계기로 둔다. 목록에서
더블클릭하는 손짓은 "이것을 열어 둔다" 이지 "잠깐 본다" 가 아니다.

**FR-RTU-43.** 미리보기 탭은 창에 **하나뿐**이다. 편집기 탭도 미리보기가 될 수 있다
— 탐색기에서 파일을 한 번 클릭한 경우다.

**FR-RTU-44.** 미리보기 상태는 워크스페이스에 저장한다 (`tab.preview`). 저장하지
않으면 새로고침 뒤 모든 탭이 고정으로 되살아나 사용자가 정리해야 한다.

**FR-RTU-45.** 이미 **고정된** 탭이 있는 대상을 다시 고르면 미리보기를 만들지 않고
그 탭으로 이동한다 (FR-EDT-101 의 규약을 미리보기까지 넓힌 것이다).

### 3.6 묶음 D — diff 편집 (VSCode 규약)

**FR-RTU-50. 축마다 다르다.** 판정 기준은 **오른쪽이 디스크의 파일인가** 하나다.

| 고른 것 | 여는 것 | 오른쪽 | 편집 |
|---|---|---|---|
| Changes (unstaged) | diff | 워킹 트리 파일 | **가능** |
| Conflicts | diff | 워킹 트리 파일 | **가능** |
| Staged | diff | index | 읽기 전용 |
| Untracked (새 파일) | **단일 편집기** | 워킹 트리 파일 | **가능** |
| 삭제된 파일 | diff | 없음(`absent`) | 읽기 전용 |
| History 의 커밋 | diff | 커밋 스냅샷 | 읽기 전용 |

**FR-RTU-51.** untracked 는 diff 가 아니라 **편집기 탭**으로 연다. 비교할 왼쪽이
없으므로 diff 는 빈 쪽과의 비교가 되고, 그 화면은 자리만 절반 쓰면서 알려 주는
것이 없다.

**FR-RTU-52.** 편집 가능한 diff 의 저장은 **`FileEditor` 와 같은 경로**를 쓴다
(`/api/file/write`, §2.7). 새 쓰기 표면을 만들지 않는다.

**FR-RTU-53.** `Cmd+S`(`Ctrl+S`)가 저장하고, 저장되지 않은 변경은 탭 이름에 `●`
로 표시된다 — 편집기 탭과 같은 표시다.

**FR-RTU-54.** 읽기 전용 쪽을 고치려 하면 **그 사실을 알린다.** 조용히 무시하면
"타이핑이 먹지 않는다" 가 된다. 문구는 그 축이 왜 읽기 전용인지 말한다 (index 는
파일이 아니다 / 커밋은 지나간 것이다).

**FR-RTU-55.** 저장 뒤에는 git 관측을 즉시 갱신한다 (`_gitSignal('write')`). 방금
고친 것이 목록과 색에 곧바로 선다.

**FR-RTU-56.** 편집 중인 diff 의 대상이 폴링으로 바뀌어도 **사용자의 편집을 덮지
않는다.** dirty 인 동안 그 뷰는 다시 읽지 않는다 (기존 `isStale` 규약 위에 dirty
게이트를 더한다).

**FR-RTU-57.** hunk 단위 스테이징(FR-GIT-278·279)은 그대로 둔다. index 를 고치는
일은 여전히 그쪽의 몫이다 (D-RTU-7).

### 3.7 묶음 S — 패널 수명과 관측

**FR-RTU-60. `GitPanel` 은 (루트, 칸)마다 하나다.** 키에 창의 루트가 들어간다.

**FR-RTU-61.** 패널은 **창마다 유지한다** (사용자 지시, D-RTU-6). 창을 떠나도
파괴하지 않으므로 돌아왔을 때 스크롤·선택·diff 대상이 그대로다.

**FR-RTU-62.** 대신 **관측은 활성 창만** 한다 (FR-GIT-24·FR-EDT-76 계승). 비활성
창의 패널은 살아 있어도 git 을 부르지 않는다.

**FR-RTU-63.** 목록에서 사라진 루트의 패널은 재조정이 회수한다 (FR-EDT-42 가 창을
지우는 그 자리다).

**FR-RTU-64. 관측기(`GitObserver`)는 저장소마다 하나다** — FR-SVS-30 을 개정한다.

그 규칙이 "앱에 하나" 였던 근거는 Git 창이 워크스페이스에 하나여서 **활성 저장소도
하나**였다는 것이다 (FR-GIT-26·29). 관측기가 관측 상태를 통째로 들고 있으므로,
저장소마다 창이 서는 지금 그것을 하나로 두면 서로의 상태를 덮어쓴다 (D-RTU-16).

요청 수는 늘지 않는다 — 관측이 도는 조건은 그 표면이 화면에 있을 때이고
(FR-RTU-62), 화면에 있는 저장소만큼만 폴링이 돈다.

**FR-RTU-65.** `app.gitPanel` 은 **활성 창의 루트 + 포커스 칸**의 패널을 돌려준다.
활성 창이 Repo 창이 아니면 `null` 이며, 그것을 딛는 호출자는 없을 때를 견딘다.

### 3.8 묶음 M — 마이그레이션

**FR-RTU-70. `WINDOW_TYPE_GIT` 창은 사라진다.** 워크스페이스를 읽을 때 제거하며,
확인창은 띄우지 않는다 (D-9 와 같은 근거 — 로드 시점이고 잃는 데이터가 없다).

**FR-RTU-71.** 제거는 창을 순회하는 자리에서 한다 (`app.js` 로드 · `app-cmd.js`
SSE 동기화) — `_migrateGitWindow` 가 이미 그 자리에 있다.

**FR-RTU-72.** `openGitWindow(repo)` 는 **그 경로의 Repo 창으로 전환**한다. 그
경로가 목록에 없으면 먼저 더한다 (`/api/editors/add`). 이 함수를 부르는 자리가
사이드바 행·`dmctl`·e2e 셋이므로 이름과 계약을 유지한다.

**FR-RTU-73.** `openView(view)` 는 **활성 Repo 창의 본문**에서 탭을 찾거나 만든다.
`_gitWindow()` 의존을 걷어낸다 (§2.5).

**FR-RTU-74.** `_gitBackTarget`·`_gitCloseWindow` 는 폐기한다 — 돌아갈 자리를
계산하던 이유가 Git 창이라는 특수 창이었고, 그것이 사라진다.

**FR-RTU-75.** 옛 워크스페이스의 Git 창 안에 있던 탭은 **버린다.** 그 탭들은 전부
고정 뷰 탭이라 재현 가능하며, 옮길 자리도 이미 없다.

### 3.9 묶음 B — 모바일

**FR-RTU-80.** 모바일에서 Repo 창은 **사이드와 pane 들을 한 줄로 순회**한다.
기존 pane 순회(`‹ 1/3 ›`)의 첫 자리에 사이드가 들어간다.

**FR-RTU-81.** 사이드 자리에서는 `Explorer`·`Changes` 탭이 그대로 동작한다.

**FR-RTU-82.** 순회 표시는 사이드를 포함해 센다 — pane 이 둘이면 `1/3` 이다.

### 3.10 비기능 요구 (NFR)

**NFR-RTU-1.** git 실행 횟수가 저장소 수에 비례해 늘지 않는다. 활성 창만 관측하므로
(FR-RTU-62) 창이 10개여도 폴링은 한 벌이다.

**NFR-RTU-2.** 창 전환이 250ms 안에 화면에 닿는다. 패널을 유지하므로(FR-RTU-61)
재구성이 없어야 한다.

**NFR-RTU-3.** Monaco 인스턴스 수는 **열린 diff/편집기 탭 수 + 창당 미리보기 1**을
넘지 않는다. 창마다 패널을 유지하되 **뷰 DOM 은 탭이 있을 때만 만든다**.

**NFR-RTU-4.** 사이드 폭 최소값에서 `Explorer`·`Changes` 두 탭 이름이 잘리지 않는다.

**NFR-RTU-5.** 다시 그리기 보존 규약(FR-RPT-*)을 깨지 않는다 — 사이드 탭 전환이
목록의 DOM 을 파괴하면 hover·드래그가 죽는다.

## 6. 비목표 (Non-goals)

1. **Git 뷰 내부의 개선.** History·Branches·Stash·Console·Worktrees 의 동작은 한
   줄도 바뀌지 않는다. 바뀌는 것은 어디에 뜨느냐뿐이다.
2. **index 편집.** 스테이지된 내용을 고치는 일은 hunk 단위 스테이징의 몫이다
   (D-RTU-7).
3. **탐색기의 새 기능.** EDITOR_TAB_SRS 의 다섯 조작 그대로다.
4. **사이드를 좌우로 옮기는 설정.** 좌측 고정이다.
5. **여러 저장소를 한 창에서 보기.** 창 하나에 저장소 하나다.
6. **미리보기 탭의 설정화.** VSCode 에는 끄는 설정이 있으나 여기서는 두지 않는다 —
   설정이 늘면 두 동작을 다 검증해야 한다.
7. **diff 에서의 되돌리기(revert hunk).** 지금의 discard 와 hunk 스테이징이 그
   자리를 이미 갖는다.

## 7. 확정 결정 (Decisions)

인터뷰(2026-09-04)로 확정했다. **본문과 어긋나면 이 표가 이긴다.**

| id | 결정 | 근거 |
|---|---|---|
| **D-RTU-1** | 창 타입 문자열은 `editor` 를 유지하고 개념만 넓힌다 | 워크스페이스 값과 e2e 가 그 문자열 위에 서 있다. 이름을 바꾸면 얻는 것 없이 마이그레이션만 는다. 사용자에게 보이는 이름은 `Repo` 다 |
| **D-RTU-2** | 사이드바 목록의 원천은 `editors.list` 하나 | 두 목록은 서버 연동으로 이미 같은 집합이다(§2.1). 화면이 둘을 읽으면 어긋난 순간을 그린다 |
| **D-RTU-3** | 사이드는 **탭 교체**이고 세로 스택이 아니다 | 사용자 지시(요구 ③). 스택은 목록 둘을 반씩 잘라 어느 쪽도 한눈에 들어오지 않는다 |
| **D-RTU-4** | 커밋 입력은 브랜치 줄 **위** | 사용자 지시. 가장 자주 쓰는 입력이 목록의 스크롤에 밀리지 않는다 |
| **D-RTU-5** | 나머지 다섯 뷰의 진입점은 **Changes 사이드 머리의 아이콘 줄** | 사용자 지시. git 진입점이 한 자리에 모이고 Explorer 탭에서는 보이지 않아 파일 작업을 방해하지 않는다 |
| **D-RTU-6** | `GitPanel` 은 **창마다 유지** | 사용자 지시. 전환이 즉시이고 스크롤·선택이 남는다. 대가(메모리)는 뷰 DOM 을 탭이 있을 때만 만들어 줄인다 (NFR-3) |
| **D-RTU-7** | diff 편집은 **워킹 트리 쪽만** | 사용자 지시("VSCode 와 동일하게"). index 편집은 VSCode 에 없고, 우리에겐 이미 hunk 단위 스테이징이 그 일을 한다 — 규칙이 둘이 되면 무엇이 스테이지를 정하는지 말할 수 없다 |
| **D-RTU-8** | untracked 는 **단일 편집기**로 연다 | 사용자 지시. 빈 왼쪽과의 비교는 자리를 절반 쓰면서 알려 주는 것이 없다 |
| **D-RTU-9** | 미리보기 탭을 도입한다 | 사용자 지시. 변경 20개를 훑는 것이 탭 20개가 되면 목록을 보는 일 자체가 정리를 부른다 |
| **D-RTU-10** | 루트가 저장소 **안**이면 상위 저장소를 보인다 | 사용자 지시. 색의 기준(FR-DIR-40)과 패널의 기준이 같아야 한다 — 다르면 같은 화면이 두 저장소를 말한다 |
| **D-RTU-11** | 모바일은 **영역 순회** | 사용자 지시. 기존 pane 순회에 자리 하나를 더하는 것이라 새 조작을 배우지 않는다 |
| **D-RTU-12** | git 이 없어도 `Repo` 탭은 남는다 | 탐색기와 편집기는 git 없이 성립한다. 옛 규칙(FR-SBT-8)은 그 탭이 git 전용일 때의 것이었다 |
| **D-RTU-13** | `git init` 은 확인을 거치고 캐시를 무효화한다 | 홈처럼 넓은 경로에서 되돌리기는 사용자의 몫이 된다. 그리고 무효화하지 않으면 누른 뒤 2초 동안 아무 일도 없는 것처럼 보인다 (§FR-RTU-28) |
| **D-RTU-14** | 옛 Git 창의 탭은 **버린다** | 전부 고정 뷰 탭이라 재현 가능하고 옮길 자리도 없다 |
| **D-RTU-15** | UI 라벨은 **영어** | 사용자 지시. 기존 사이드바 탭(`Windows`)과 git 뷰 이름(`Changes`·`History`)이 이미 영어다 — 한 화면에서 두 언어가 섞이지 않는다 |
| **D-RTU-16** | **관측기도 저장소마다 하나다** — FR-SVS-30 개정 | 구현 중 실측으로 뒤집혔다. `GitObserver` 는 status·signature·소실·실패 누적을 **통째로** 들고 있고, 주기 타이머가 `any()` 로 아무 패널이나 골라 수집한다. 관측기가 하나면 마지막에 수집한 저장소의 상태를 모든 Repo 창이 함께 본다 — 다른 창에서 파일을 만들어도 이 창의 목록이 갱신되지 않았다. FR-SVS-30 의 근거("앱에 하나")는 **Git 창이 하나여서 활성 저장소도 하나**라는 것이었고, 그 전제가 이번에 깨졌다 |
| **D-RTU-17** | **M7(마이그레이션)을 M3 직후로 앞당겼다** | 스펙의 순서 근거("옛 창을 남겨 둔 채 새 자리를 세운다")가 M3 에 의해 무효화됐다 — 사이드바에서 `Git` 탭이 사라진 순간 옛 Git 창으로 가는 **진입점이 이미 없어졌다.** 남겨 두면 중간 상태의 e2e 를 두 번 고쳐야 했다 |
| **D-RTU-18** | **Repo 창의 신원은 id 가 아니라 루트다** | 실측한 결함이다 — 목록에 없던 경로를 `openGitWindow` 로 열면 로컬이 창을 만들고 전환하는데, 곧이어 온 `workspace_changed` 가 서버 스냅샷으로 목록을 덮고 재조정이 같은 루트의 창을 **새 id 로** 만든다. `activeWindow` 는 옛 id 를 가리킨 채 남아 폴백이 엉뚱한 일반 창을 고른다. `_edKeepActive` 가 루트로 다시 찾는다 |
| **D-RTU-19** | `repo-side.js` 를 만들지 않았다 | 사이드는 자기 상태도 DOM 도 소유하지 않는다(탐색기·패널이 소유) — 파일을 나눌 이유가 없어 `renderer._rSide` 한 함수로 두었다. §5.1 의 표는 착수 전 예상이다 |
| **D-RTU-20** | `_gitBackTarget` 은 폐기하지 않았다 | FR-RTU-74 가 `_gitCloseWindow` 와 함께 폐기라 했으나, 그 계산은 `Windows` 탭이 돌아갈 자리로도 쓰인다 (FR-SBT-23·36). 폐기한 것은 `_gitCloseWindow` 와 `_gitLeaveIfRemoved` 의 본문뿐이다 |
| **D-RTU-21** | `git init` 은 `writeCommands` 에 들어가되 **인자를 받지 않는다** | `Exec` 은 읽기 전용이라 가드에 막힌다 (FR-GIT-95). 경로 인자를 허용하면 핸들러의 존재·디렉터리 검사를 우회해 다른 자리에 저장소가 생긴다 |

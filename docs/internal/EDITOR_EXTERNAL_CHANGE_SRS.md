# 편집기와 외부 변경 — SRS

- 문서 상태: **초안 (구현 전)**. 2026-09-11 접수·판정, 구현은 다음 세션.
- 접수: 사용자 보고 `U-22`
- 관련: [`EDITOR_TAB_SRS`](./EDITOR_TAB_SRS.md) · [`SLOT_VIEW_STATE_SRS`](./SLOT_VIEW_STATE_SRS.md)
  (`FR-SVS-50`~`54` — 내용·dirty 는 **문서**의 것이다) ·
  [`REPO_TAB_UNIFY_SRS`](./REPO_TAB_UNIFY_SRS.md) `FR-RTU-103` (U-10 — 편집을 확인 없이 잃지 않는다)

---

## 1. 개요

### 1.1 목적

편집기로 연 파일이 **밖에서 바뀌었을 때** 무엇을 보여줄지 정한다.

접수한 말 그대로다:

> *"사용자가 editor 에서 수정에 들어가기 전, 즉 파일을 열기만 하고 수정하기 전에는
> 해당 파일이 외부에서 수정·저장되면 그대로 바뀌어야 할 것 같다. 이게 맞는
> 동작인 것 같다."*

### 1.2 범위

`FileEditor` 가 연 텍스트 파일. 이미지·이진은 대상이 아니다(열지 않으므로).
git diff 뷰(`file-editor-diff.js`)는 자기 갱신 규약이 따로 있으며 이 문서 밖이다.

### 1.3 정의

| 말 | 뜻 |
|---|---|
| **clean** | 연 뒤 한 글자도 고치지 않은 상태 (`_dirty === false`) |
| **dirty** | 고쳤고 아직 저장하지 않은 상태 |
| **경합** | 우리가 읽은 뒤 디스크의 그 파일이 바뀐 것 |

## 2. 현재 상태 (조사로 확정한 사실, 2026-09-11)

### 2.1 `refresh()` 는 있는데 **dirty 를 보지 않는다**

`file-editor.js` 의 `refresh()` 는 파일을 다시 읽어 내용이 다르면 `setValue` 한다.
내용이 같으면 넣지 않는다 — `setValue` 가 커서를 1,1 로 되돌리고 undo 스택을
버리기 때문이다 (`FR-LSP-26b`).

**그러나 `_dirty` 를 확인하지 않는다.** 그래서 지금도 편집 중인 파일을 그 경로로
지나가면 편집본이 디스크 것으로 덮인다.

### 2.2 자동 감지는 **없다**

`refresh()` 를 부르는 자리는 둘뿐이다.

| 자리 | 계기 |
|---|---|
| `app-layout.js:480` | **이미 열린 파일을 다시 열 때** |
| `app-reload.js` | 내부 새로고침 |

즉 파일을 열어 둔 채 보고 있는 동안 밖에서 바뀌어도 화면은 그대로다.

### 2.3 파일 단위 감시 수단이 없다

`/api/fs/stamp` 는 **디렉터리** 감시이고 탐색기가 쓴다. `/api/file/probe` 는
`{kind, mime, size, maxBytes}` 를 주며 **`mtime` 이 없다.**

### 2.4 저장은 경합을 보지 않는다

`POST /api/file/write` 는 받은 내용을 그대로 쓴다. 우리가 읽은 뒤 디스크가
바뀌었는지 묻지 않는다 — **마지막에 저장한 쪽이 이긴다.**

## 3. 요구사항

### 3.1 묶음 C — clean 일 때 (요구의 본문)

**FR-EXC-1** clean 인 편집기는 외부 변경을 **반영한다.** 내용이 같으면 넣지
않는다 (`FR-LSP-26b` 그대로 — 커서와 undo 를 지킨다).

**FR-EXC-2** 반영은 조용하다. clean 이었으므로 잃을 것이 없고, 물어볼 일도 없다.

### 3.2 묶음 D — dirty 일 때 (사용자 판정 2026-09-11)

**FR-EXC-3** dirty 인 편집기는 **건드리지 않는다.** 외부에서 바뀌었어도 편집본이
화면에 그대로 남는다.

> 접수한 판정: *"그냥 놔두고 저장하려 할 시 경합."*
>
> `U-10` 이 같은 값을 이미 치렀다 — 편집을 확인 없이 잃는 것이 이 제품에서 가장
> 비싼 실패다 (`FR-RTU-103`).

**FR-EXC-4** `refresh()` 는 **dirty 면 내용을 넣지 않는다.** §2.1 의 자리를 고치는
것이 이 요구다 — 자동 감지를 붙이지 않더라도 지금 있는 경로만으로 편집본이 덮인다.

### 3.3 묶음 S — 저장할 때 (경합)

**FR-EXC-5** 저장은 **경합을 검사한다.** 우리가 읽은 뒤 디스크의 그 파일이
바뀌었으면 그대로 덮지 않는다.

**FR-EXC-6** 검사의 재료는 서버가 정한다 — 읽을 때 준 표식(`mtime`+크기 또는
해시)을 저장 때 함께 보내고, 서버가 **자기가 아는 현재 값**과 견준다. 클라이언트가
스스로 판정하지 않는다: 판정을 클라이언트에 두면 두 창이 같은 파일을 볼 때 서로
다른 답을 갖는다.

**FR-EXC-7** 경합이면 **409** 다. 사용자에게는 그 사실과 선택지를 보인다.
무엇을 보일지는 §6 의 미해결 1 이다.

### 3.4 묶음 P — 감지 (사용자 판정)

**FR-EXC-8** **폴링하지 않는다.** 접수한 판정은 *"파일 저장 시도할 때"* 다.
반영의 계기는 이미 있는 것들로 충분하다 — 탭으로 돌아올 때(§2.2)와 저장 시도다.

> 폴링을 두지 않는 이유는 비용만이 아니다. 열린 편집기 수만큼 종단이 늘고, 그
> 주기가 또 하나의 설정이 된다 (`POLL_INTERVAL_SETTINGS_SRS`). 지금 접수된 요구는
> 그것 없이 성립한다.

## 5. 비목표

1. **폴링·파일 감시** (FR-EXC-8). 접수된 요구가 그것 없이 성립한다.
2. **세 갈래 병합.** 경합은 알리고 고르게 하는 것까지다. 병합은 편집기의 일이 아니다.
3. **외부 삭제의 처리.** 다른 사건이며 따로 접수되지 않았다 — §6 미해결 2.
4. **diff 뷰**(`file-editor-diff.js`). 자기 갱신 규약이 따로 있다.

---

## 6. 미해결 — 착수 전에 물을 것

1. **경합했을 때 사용자에게 무엇을 주는가.** 알림 줄 하나인가, "디스크 것으로
   덮기 / 내 것으로 덮기" 두 버튼인가, 확인창인가. `GitConfirm` 의 어휘를 빌릴
   수 있다.
2. **열어 둔 파일이 밖에서 지워지면.** 탭을 닫는가, 그대로 두고 저장 때 새로
   만드는가.
3. **표식을 무엇으로 할까.** `mtime`+크기는 싸지만 같은 초 안의 변경을 놓친다.
   내용 해시는 정확하지만 읽을 때마다 전체를 지난다 — 상한이 10 MiB 이므로
   (`FR-FAB-8`) 비용이 유한하다.

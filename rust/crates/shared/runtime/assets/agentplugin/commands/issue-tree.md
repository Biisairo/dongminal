# issue-tree

이슈마다 에이전트 하나를 둔다. 에이전트는 자기 이슈를 계획하고, 나눌 필요가 있으면 하위 이슈를 만들어 그 하위마다 에이전트를 띄운다. 나눌 필요가 없으면 직접 일한다. **진행 중인 경로에만** 에이전트가 떠 있다.

**인자**: `$ARGUMENTS`. 첫 낱말이 이슈다. 이슈가 없으면 사용자에게 묻는다. 그 밖의 인자가 없으면 기본값을 쓰고, 되묻지 않는다.

| 인자 | 기본값 | 뜻 |
|---|---|---|
| `--ctx <퍼센트>` | 설정 `issueTreeCtxPct`(기본 50) | 노드가 안전 지점에서 migration 을 판단하는 맥락 기준(「맥락 판단」). 주면 설정보다 우선한다. 설정 `issueTreeMigration` 이 꺼져 있으면 맥락 때문에 넘기지 않는다 |
| `--no-commit` | 없음 | 트리 전체가 커밋하지 않는다. 사용자가 그렇게 말했을 때만 붙인다 |
| `--mode tree\|coord` | `tree` | 실행 방식(「보관 방식과 실행 방식」). `tree` 는 이슈마다 노드를 세우고, `coord` 는 이 세션이 조정자가 되어 ready 이슈마다 일꾼을 띄운다 |

노드가 따를 절차는 **이 문서뿐**이다. 대상 저장소에서 otterminal 의 SRS 를 찾지 않는다.

## 보관 방식과 실행 방식

이슈를 어디에 두는가(보관 방식)와 누가 일을 나누는가(실행 방식)를 따로 고른다. 네 조합을 모두 쓴다.

**보관 방식**은 첫 낱말로 정한다. 먼저 판정한다:

```
otterctl issue resolve <첫 낱말>
```

- `local\t<폴더>\t<ID>\t<별칭>:<ID>` 이면 **local** 이다. `<폴더>#<ID>` 꼴이고 그 폴더가 있다(예: `docs/internal/perf/issues#2`). 이슈는 폴더의 파일 하나가 하나다. 「로컬 이슈」 를 따른다.
- `github\t<인자>` 이면 **github** 다. 지금처럼 GitHub 이슈로 읽는다.

**실행 방식**은 `--mode` 다. 주지 않으면 `tree` 다.

| 조합 | 따를 절차 |
|---|---|
| `github + tree` | 「발사대 절차」 → 「노드 절차」 → 「트리 종료」 그대로 |
| `local + tree` | 같은 절차를 따르되, 이슈에 닿는 걸음은 「로컬 이슈」 의 대응표로 바꾼다 |
| `github + coord` | 「조정자 절차」. 일꾼은 「일꾼 규칙」. 이슈 쓰기는 「이슈 접근 규칙」 을 지난다 |
| `local + coord` | 「조정자 절차」 와 「로컬 이슈」. 일꾼은 「일꾼 규칙」 |

`tree` 에서 노드는 자기 이슈를 나누고 하위 노드를 띄운다. `coord` 에서는 조정자 하나가 ready 이슈마다 일꾼을 띄운다. 일꾼은 자기 이슈 하나만 하고, 다른 에이전트를 띄우지 않는다. 일꾼이 커밋하고 조정자가 병합한다.

## 역할

| 역할 | 누구 | 하는 일 |
|---|---|---|
| **발사대 · 조율 에이전트** | 이 명령을 실행한 세션 | 트리를 세우고 루트 노드만 띄운다. 그 뒤 **조율 에이전트로 남는다**: 루트의 `완료` · `실패` · `종료 요청` 을 받고, 「트리 종료」 를 한다. 그룹 밖에 있다. 자기 탭은 닫지 않는다(사용자의 탭이다) |
| **노드** | 이슈 하나를 맡은 에이전트 | 아래 「노드 절차」. 이 문서를 엔벨로프로 받아 읽는다 |
| **루트 노드** | 최상위 이슈의 노드 | 노드 절차. 부모는 조율 에이전트다. 조율이 없으면 「대신 조율」 |
| **조정자** (`coord`) | 이 명령을 실행한 세션 | 「조정자 절차」. 통합 브랜치를 만들고, ready 이슈마다 일꾼을 띄우고, review 를 확인해 병합한다 |
| **일꾼** (`coord`) | 이슈 하나를 맡은 에이전트 | 「일꾼 규칙」. 자기 이슈 브랜치에서 일하고 `review` 까지 한다 |

## 절대 원칙

1. **노드는 바로 아래 자식만 띄운다.** 여러 단계를 한꺼번에 띄우지 않는다.
2. **일하지 않을 노드로 가는 길은 띄우지 않는다.** 병렬이 없으면 일하는 잎은 하나다.
3. **중간 노드는 하위를 띄운 뒤 턴을 끝낸다.** 메시지(트리 방에서 나를 부른 글, 「트리 방」)가 와야 깨어난다. 상태를 폴링하지 않는다. sleep 루프를 짜지 않는다.
4. **트리의 window·탭은 트리 그룹 안에만 만든다.** 그룹 밖의 window·탭을 만들거나 옮기거나 닫지 않는다.
5. **각 걸음은 기대 출력을 확인한 뒤 다음으로 간다.** 확인하지 못하면 멈추고 말한다.
6. **push 와 사용자 브랜치로의 병합은 사용자의 확인 뒤에만 한다.** 커밋과 이슈 닫기는 이 명령의 실행으로 승인된 것이다. `--no-commit` 이면 커밋하지 않는다.
7. **트리를 닫는 것은 조율 에이전트뿐이다.** 사용자가 노드에서 닫자고 해도 노드는 스스로 정리하지 않고 부모에게 `종료 요청` 을 올린다. 문제가 있으면(`막힘`) 아무것도 닫지 않는다.

## 식별자

| 값 | 어디서 | 어디에 쓰나 |
|---|---|---|
| 탭 `uuid` | `who-am-i` 의 `uuid=` · 응답의 `newTabs[0].uuid` | `--at` (탭 명령 · `send-input` · `wait` · `status` · `close-tab`) |
| `toolId` | `who-am-i` 의 `toolId=` · `newTabs[0].toolId` | `otterctl msg --to`. 엔벨로프의 `from=` 과 같다 |
| window `uuid` | `newWindows[0]` | `run start --window` · `move-window --at` |
| 그룹 `uuid` | `new-group` 의 `newGroups[0]` · `list-groups` | `--group` · `move-group --at` · `delete-group --at` |

좌표·라벨(`W1.P1.T1`)은 어디에도 넣지 않는다. 레이아웃 명령에 `--help` 를 붙여 도움말을 보지 않는다 — `otterctl --help` 를 쓴다.

## 이름

- **별칭**: 저장소 이름을 `-` · `_` · `.` 로 나눈 낱말의 첫 글자를 소문자로 잇는다. 낱말이 하나면 앞 세 글자다. 예: `common-chart-renderer-ts` → `ccr`.
- **사슬 이름**: `<별칭>#<루트>›<번호>›…›<이 노드>`. 다른 저장소의 하위 이슈는 그 칸에 별칭을 다시 붙인다(`ccr#32›otter#120`).
- **탭 이름**: `<사슬 이름> <이슈 제목의 짧은 형태>`. 예: `ccr#32›33›35›62 피킹`.
- **window 이름**: 그 window 에 처음 선 노드의 사슬 이름.
- **그룹 이름**: `<별칭>#<루트> <루트 제목>`. 트리 표지는 `owner/repo#<루트>` 다.

## 트리 방

트리의 통신은 채팅 방 하나(트리 방)에서 한다. 이 문서의 메시지(보고 · 지시 · 완료 · 실패 · 종료 요청 · 종료 준비 · 준비됨 · 막힘 · review · blocked · split · commit)는 모두 트리 방에서 오간다.

- **만들기**: 발사대(조율) 또는 조정자가 그룹을 만든 뒤 MCP `chat_create` 로 만든다. 이름은 그룹 이름, 목적은 `<트리 표지> <루트 제목>` 이다. 돌려받은 방 id 를 `otterctl run start … --chat-room <방 id>` 로 Run 에 적는다. 가지 Run 은 루트 Run 의 방을 잇는다 — `--chat-room` 을 주지 않는다.
- **들어가기 · 나가기**는 otterminal 이 한다. Run 에 방을 적으면 이 PC 의 사람 참가자가 들어간다. 트리 멤버(배정을 가진 Run 멤버)와 조율 · 조정자의 세션이 채팅에 붙으면 들어가고, 세션이 끝나면 나간다. 에이전트는 `chat_join` · `chat_leave` 를 하지 않는다(트리 종료의 마지막 나가기만 예외다).
- **보내기**: `chat_send room=<방 id> call=[<받을 이의 toolId>] text="<종류> <사슬 이름>\n<본문>"`. 이 문서의 `otterctl msg --to <X> - <<'M' … M` 는 트리 방이 있으면 모두 이 꼴로 바꾼다 — 받을 이 X 를 `call` 에 넣고, 본문(첫 줄의 종류 포함)은 그대로다. 트리 안에서는 `otterctl msg` 를 쓰지 않는다.
- **받기**: 나를 부른 글이 오면 깨어난다. `chat_read` 로 읽는다. 나를 부르지 않았거나 나와 무관한 글이면 아무것도 하지 않고 턴을 끝낸다.
- **화면에 옮기기**: 보낸 글과 받은 글을 응답에도 쓴다. 그 탭의 화면만 봐도 주고받은 것이 보인다.
  - `보냄 → <상대>: <본문>`
  - `받음 ← <보낸 이>: <요지>`
- **사용자 확인**: 안내 · 공지 · 알람 · 사용자 확인도 트리 방에 쓴다. 사용자 확인은 AskUserQuestion 대신 트리 방에 `call=["user"]` 로 묻고, 같은 질문을 응답에도 쓴 뒤 턴을 끝낸다. 답은 터미널 입력과 채팅(웹 · 텔레그램) 가운데 먼저 온 것을 따른다. 답을 받으면 트리 방에 `결정: <내용> (터미널에서|채팅에서)` 를 남긴다.
- **첫 지시**: 노드 · 일꾼의 첫 지시(배정 · 프리앰블 · 이슈)는 claude 실행 인자다. 트리 방이 있는 Run 이면 서버가 프리앰블 응답에 `promptFile` 을 싣고, `otterctl run launch` 가 프리앰블을 `<홈>/prompts/<member>.md` 로 쓴다. 첫 프롬프트는 그 파일을 읽으라는 한 줄이다. 대화 기록은 남지 않으므로 brief 에 일에 필요한 맥락을 모두 담는다.
- 서버가 보내는 승계 알림(`[ISSUE-TREE 승계]`)은 지금처럼 엔벨로프로 온다. 트리 밖의 일에는 `otterctl msg` 를 그대로 쓴다.
- **끝**: 트리 종료의 마지막 걸음에서 조율 · 조정자가 `chat_leave` 로 트리 방에서 나간다. 트리의 Run 이 모두 닫히면 사람 참가자도 나가고, 이 PC 의 참가자가 없으면 방이 사라진다(텔레그램 토픽도 지워진다).

## 이슈 규약

이슈 규약(프로젝트 보드 · 담당자 · 필드 · 커밋 메시지의 이슈 번호 · 닫는 방식)은 **그 프로젝트의 지시 문서**(CLAUDE.md · README 등)를 따른다. 이 명령은 규약을 만들지 않는다. 규약이 없으면 GitHub 기본 동작(하위 이슈 만들기 · 닫기)만 한다.

로컬 이슈(보관 방식 local)는 이 절과 「이슈 접근 규칙」 대신 「로컬 이슈」 를 따른다.

이슈 관계는 GitHub 하위 이슈(sub-issues)를 근거로 한다.

```
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){issue(number:$n){
  number title state body
  parent{ number title repository{ nameWithOwner } }
  subIssues(first:100){ nodes{ number title state body repository{ nameWithOwner } } }
}}}' -F o=<owner> -F r=<repo> -F n=<번호>
```

- `parent` 가 `null` 이면 그 이슈가 루트다.
- `subIssues` 의 순서가 진행 순서다.

## 이슈 접근 규칙

이 절은 **이슈에 닿는 모든 걸음**에 적용된다. 읽기 · 하위 이슈 만들기 · 코멘트 · 보드 옮기기 · 라벨·마일스톤 바꾸기 · 닫기가 모두 그렇다. 발사대만의 규칙이 아니다. 이 문서의 다른 걸음이 「이슈 접근 규칙」 을 가리키면 이 절을 그대로 한다.

어떤 이슈를 할지는 사용자가 정한다 — 남의 이슈, 어사인이 없는 이슈도 다룬다. 그래서 보는 것은 **지금 계정이 그 저장소에서 할 수 있는가**(권한)다. 누구의 이슈인지는 따지지 않는다.

### 권한

- 세션을 시작할 때, 그리고 **처음 다루는 저장소**의 이슈에 닿을 때(하위 이슈가 다른 저장소에 있을 수 있다) 그 저장소의 권한을 본다:
  ```
  gh api graphql -f query='query($o:String!,$r:String!){viewer{login} repository(owner:$o,name:$r){nameWithOwner viewerPermission}}' -F o=<owner> -F r=<repo>
  ```
- 쓰기(만들기 · 코멘트 · 라벨 · 어사인 · 닫기)에는 `viewerPermission` 이 `WRITE` · `MAINTAIN` · `ADMIN` 중 하나여야 한다.
- 프로젝트 규약이 보드를 쓰면 토큰에 `project` 범위가 있어야 한다(`gh auth status` 의 `Token scopes`). 없으면 `gh auth refresh -s project` 를 사용자에게 안내한다.
- 모자라면 쓰지 않는다. 멈추고 자기 탭에서 사용자에게 묻는다.
- 쓰기가 권한·인증으로 거절되면(계정이 바뀌었거나 토큰이 만료됐을 수 있다) 다시 시도하거나 다른 길로 우회하지 않는다. 지금 계정(`gh api user -q .login`)과 거절 사유를 보이고 사용자에게 묻는다.

### 설정 점검

다루는 이슈의 설정을 읽어 기준과 견준다.

```
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){issue(number:$n){
  number state
  assignees(first:20){ nodes{ login } }
  labels(first:50){ nodes{ name } }
  milestone{ title }
  issueType{ name }
  projectItems(first:20){ nodes{ project{ title number } fieldValueByName(name:"Status"){ ... on ProjectV2ItemFieldSingleSelectValue{ name } } } }
  parent{ number repository{ nameWithOwner } }
}}}' -F o=<owner> -F r=<repo> -F n=<번호>
```

- **언제**: 세션 시작(자기 이슈) · 하위 이슈를 만든 직후(그 하위) · 하위를 열기 전(그 하위) · 이슈를 닫기 전(자기 이슈).
- **기준**: 프로젝트 지시 문서의 규약이 먼저다. 규약이 없는 항목은 이렇게 둔다.
  - 라벨 · 마일스톤 · 엮인 프로젝트: 부모 이슈와 같게 둔다. 부모 이슈의 설정도 같은 쿼리로 읽는다.
  - 어사인: **그 일을 하는 사람**이다.
    - 이 트리가 진행하는 이슈(내가 하는 일)면 지금 계정(`gh api user -q .login`)을 어사인한다.
    - 이 트리가 진행하지 않는 이슈(만들었지만 다른 사람이 할 일)면 그 사람을 어사인한다. 누구인지 모르면 사용자에게 묻는다.
    - 이미 다른 사람만 어사인된 이슈를 이 트리가 진행하게 됐으면(남의 이슈를 가져왔다) 나를 더할지 사용자에게 묻는다.
  - 루트 이슈(부모 없음): 발사대가 「0. 접근 확인」 에서 보이고 확인받은 그대로.
- **어긋날 때**:
  - 기준이 값을 정해 주면 고치고, 무엇을 고쳤는지 그 이슈에 코멘트로 남긴다(예: `설정: 라벨 chart 추가, 프로젝트 rnd-unit4 연결 — 부모 #32 를 따름`).
  - 값을 정할 수 없으면(규약이 모호함 · 부모도 비었음 · 고를 것이 여럿) 자기 탭에서 사용자에게 묻는다. 답을 받기 전에는 그 이슈의 일을 시작하지 않는다.

### 하위 이슈 만들기

만들 때 기준의 설정(어사인 · 라벨 · 마일스톤 · 프로젝트)을 함께 준다. 이 트리가 진행할 하위면 어사인은 지금 계정이고, 다른 사람이 할 일이면 그 사람이다(모르면 묻는다). 만든 뒤 「설정 점검」 으로 다시 읽어 확인한다. 하위로 붙이는 것(`addSubIssue`)과 순서(`reprioritizeSubIssue`)도 쓰기이므로 「권한」 을 먼저 지난다.

## 로컬 이슈

보관 방식이 local 이면 이슈는 원본 폴더의 파일이다. 파일 하나가 이슈 하나이고, 머리말은 `id · title · status · deps · owner · branch` 다. 폴더의 `README.md` 가 형식과 상태 흐름을 적는다. 원본 폴더는 `otterctl issue resolve` 가 준 `<폴더>` 다(절대 경로로 적는다).

- **이슈는 `otterctl issue` 로만 읽고 고친다.** 파일을 직접 고치지 않는다. 명령이 형식을 검사하고, 잠금 아래에서 원자적으로 쓰고, 허용되지 않은 전이를 거절한다.
- 원본 폴더는 `run start --issue-dir` 로 Run 에 기록된다. 트리 안에서는 `--dir` 없이 부르면 명령이 그 폴더를 찾는다. 트리 밖(Run 이 서기 전)에서는 `--dir <원본 폴더>` 를 붙인다.
- worktree 안의 이슈 폴더는 사본이다. 사본은 고치지 않는다. `local + tree` 에서 원본 폴더는 사용자 작업 트리 안에 있을 수 있다 — 사용자 작업 트리를 고치지 않는다는 원칙에서 이 폴더의 이슈 파일만 예외다.
- 상태 흐름: `todo → ready → in-progress → review → done`. 곁가지는 `→ blocked`(이유 필수) · `blocked → ready | in-progress` · `in-progress → split` 이다. `ready` 는 `deps` 가 모두 `done` 인 `todo` 다. `otterctl issue tree` 는 시작할 수 있는 `todo` 를 `ready` 로 보인다.
- 「이슈 접근 규칙」(권한 · 설정 점검)은 건너뛴다. 발사대 「0. 접근 확인」 대신 원본 폴더가 있고 `otterctl issue tree --dir <원본 폴더>` 가 읽히는지 본다.

**GitHub 걸음 → 로컬 걸음**

| GitHub 이슈의 걸음 | 로컬 이슈에서 |
|---|---|
| 이슈 읽기(GraphQL) | `otterctl issue show <ID>` |
| 트리 · 하위 이슈 목록 | `otterctl issue tree [상태…]`. `<ID>.` 로 시작하는 바로 아래 ID 가 하위다 |
| 부모 · 루트 | 부모는 ID 의 마지막 조각을 뗀 ID 다. 조각이 하나인 ID 가 루트다 |
| 서브이슈 순서 · 본문의 `의존:` | ID 차례가 진행 순서다. 의존은 머리말 `deps` 다. 앞 형제를 기다리는 기본 규칙은 없다 — 열 수 있는 것은 `ready` 다 |
| 하위 이슈 만들기 | `otterctl issue new <ID>.<n> "<제목>" [--deps a,b]`. 순서를 바꿀 일은 없다 — ID 를 고를 때 정한다 |
| 보드의 진행 중으로 옮기기(착수) | `otterctl issue set <ID> --status ready`(`todo` 일 때) 뒤 `otterctl issue set <ID> --status in-progress --owner <내 toolId>` |
| 코멘트 · 결정(`결정:`) | `otterctl issue log <ID> <<'L'` … `L`(진행 기록에 덧붙는다) |
| 닫기 · 보드의 완료 | `otterctl issue set <ID> --status review` 뒤 `--status done` |
| 막힘 | `otterctl issue set <ID> --status blocked --reason "<이유>"` |
| 브랜치 기록 | `otterctl issue set <ID> --branch <브랜치>` |

**이름**

- **별칭**: `otterctl issue resolve` 의 넷째 칸 `<별칭>:<ID>` 의 앞부분이다. 폴더 이름이고, 폴더 이름이 `issues` 면 부모 폴더 이름이다(예: `perf`).
- **트리 표지**: `<별칭>:<ID>`(루트 ID). 사슬 이름은 `<별칭>:<루트>›<ID>›…` 다.
- **그룹 이름**: `<별칭>:<루트> <루트 제목>`. 그룹은 `--tree` 없이 만든다(`new-group --tree` 는 GitHub 꼴만 받는다). 서버는 이 이름으로 트리의 그룹을 찾는다. 이름을 바꾸지 않는다.

**Run 과 배정**

```
otterctl new-group --name "<별칭>:<루트> <루트 제목>"
otterctl run start --objective "<별칭>:<루트> 이슈 트리" --window <newWindows[0]> --isolation per-run \
  --tree <별칭>:<루트> --issue-dir <원본 폴더 절대 경로> --chat-room <방 id>
```

- 같은 트리의 그룹은 `otterctl list-groups --json` 에서 이름이 `<별칭>:<루트> ` 로 시작하는 행이다.
- 가지 Run 은 `--tree <별칭>:<루트> --branch` 로 연다. `--issue-dir` 을 빼면 루트 Run 의 원본 폴더를 잇는다.
- 노드 배정은 `run member … --issue <별칭>:<ID>` 다. 트리 보기는 `otterctl run tree --ref <별칭>:<루트>` 다.
- 트리 종료의 이슈 쓰기도 위 표로 바꾼다: WIP 메모는 `otterctl issue log`, 닫기는 `review → done`. 버린 노드의 이슈는 `blocked --reason "트리 종료로 중단"` 으로 둔다.

## 발사대 절차

### 0. 접근 확인

그룹 · window · Run 을 만들기 **전에** 한다. 여기서 멈추면 정리할 것이 없다.

1. 지금 gh 계정과 토큰 범위를 본다:
   ```
   gh auth status
   gh api user -q .login
   ```
   로그인돼 있지 않으면 사용자에게 `! gh auth login` 을 안내하고 멈춘다.
2. 입력 이슈의 저장소 권한을 본다(「이슈 접근 규칙」 의 「권한」 쿼리). 2의 경로에서 루트 이슈가 다른 저장소에 있으면 그 저장소도 본다.
3. 입력 이슈의 저장소와 이 셸(cwd)의 저장소가 같은지 본다: `gh repo view --json nameWithOwner -q .nameWithOwner`. 다르면 사용자에게 말하고 멈춘다.
4. 루트 이슈의 설정을 읽는다(「설정 점검」 쿼리). 프로젝트 규약에 없는 라벨 · 마일스톤 · 프로젝트는 하위 이슈의 기준이 되므로 지금 값을 함께 보인다. 어사인이 어긋나면(비었음 · 다른 사람만 있음) 어떻게 할지 함께 보인다.
5. **사용자에게 한 번 확인받는다.** 예:
   > `dy-kim` 계정으로 `owner/repo` 의 이슈를 읽고 쓴다(권한 WRITE, 토큰 범위 repo·project). 루트 #32: 라벨 `chart` · 프로젝트 `rnd-unit4` · 어사인 없음(진행하면 `dy-kim` 을 어사인한다). 이 계정과 권한으로 진행할까?
   - 거절하거나 계정을 바꾸라고 하면(`gh auth switch`) 그대로 하고 1부터 다시 한다.
   - 권한이 `WRITE` 미만이거나 `project` 범위가 없는데 규약이 보드를 쓰면 진행하지 않는다 — 무엇이 모자란지 말하고 멈춘다.

### 1. 자기 자리

```
otterctl who-am-i
```

`uuid=` · `toolId=` 를 적는다. 실패하면 otterminal 안이 아니다 — 사용자에게 말하고 멈춘다.

### 2. 경로

입력 이슈에서 `parent` 를 따라 루트까지 오른다. **루트 → 입력 이슈의 경로**(이슈 번호 목록)를 적는다. 이 경로가 루트 노드에 넘길 「목표 경로」다.

### 3. 그룹

```
otterctl list-groups --json
```

`tree` 가 `owner/repo#<루트>` 인 그룹이 있으면 그것을 쓴다. 없으면 만든다. 트리가 이미 도는지는 4의 `run start --tree` 가 서버에서 판정한다.

```
otterctl new-group --name "<별칭>#<루트> <루트 제목>" --tree <owner/repo>#<루트>
```

기대 출력: `newGroups` 가 하나. 그 값을 적는다.

그룹을 만들었으면 트리 방을 만든다(「트리 방」): MCP `chat_create` 에 이름 `<별칭>#<루트> <루트 제목>`, 목적 `<owner/repo>#<루트> <루트 제목>` 을 준다. 돌려받은 방 id 를 적는다. 그룹이 이미 있었고 그 트리의 방이 `chat_rooms` 에 보이면 그 방을 쓴다.

### 4. 루트 window 와 Run

```
otterctl new-window -n --group <그룹> --name "<별칭>#<루트>" --cwd "<저장소 루트>"
cd "<저장소 루트>"
otterctl run start --objective "<별칭>#<루트> 이슈 트리" --window <newWindows[0]> --isolation per-run --tree <owner/repo>#<루트> --chat-room <방 id>
```

**같은 트리는 두 번 열리지 않는다.** 같은 트리의 열린 Run 이 있으면 `run start` 가 `tree_open` 으로 거절한다.

- 안내에 「이미 돌고 있다」가 나오면 멈추고 사용자에게 말한다. 4에서 만든 window 는 닫는다(`otterctl close-window -n --at <그 window 의 탭 uuid> --force`).
- 「멈췄다(살아 있는 멤버 없음)」가 나오면 사용자에게 정리할지 묻는다. 정리하라고 하면 안내의 `otterctl run close --run <id> --force` 를 실행하고 4를 다시 한다.

- 새 window 의 `newTabs[0].uuid`·`toolId` 를 적는다. 이 탭이 루트 노드의 자리다.
- 트리의 진행은 Runs 대시보드의 「이슈 트리」 에 보인다(노드를 누르면 그 탭으로 간다). 같은 내용을 `otterctl run tree --ref <owner/repo>#<루트>` 로 읽는다.
- `run start` 의 `run=` 을 적는다. `--isolation per-run` 이 사용자 작업 트리와 분리된 worktree 를 만든다. 사용자 작업 트리는 트리가 도는 동안 고치지 않는다.

### 5. 루트 노드를 띄운다

「노드 띄우기」 를 루트 window 의 첫 탭으로 한다. `--parent` 는 주지 않는다(루트는 부모가 없다 — 보고와 질문은 자기 탭의 사용자에게 한다). `--goal` 은 2의 경로에서 루트를 뺀 나머지다. 배정 엔벨로프는 보내지 않는다.

### 6. 보고하고 조율로 남는다

루트 노드가 `state=working` 이면 사용자에게 다음을 보고한다: 그룹 이름 · 루트 window · Run · 목표 경로. 그 뒤 턴을 끝내고 **조율 에이전트로 남는다.** 루트의 메시지(`완료` · `실패` · `종료 요청` · `준비됨` · `막힘`)가 오면 깨어나 「트리 종료」 를 따른다. `실패` 는 사용자에게 알리기만 한다. 트리의 탭 · window 는 트리 종료 때만 닫는다. **자기 탭은 닫지 않는다.**

루트 노드의 프리앰블에서 부모는 이 세션의 `toolId` 다. 사용자가 이 탭을 닫으면 루트가 대신 조율한다. 맥락이 모자라 새 세션으로 넘길 때는 `/otterminal:migration` 을 쓴다 — 그 절차가 `otterctl run coordinate` 로 조율 자리를 넘기고, 서버가 루트에 새 주소를 알린다.

## 노드 띄우기 (공통)

부모가 자식 하나를 띄우는 절차다. 발사대가 루트 노드를 띄울 때도 같다.

### 자리

| 경우 | 자리 | Run |
|---|---|---|
| 사슬의 자식 · 병렬 자식 중 첫째 | `otterctl new-tab -n --at <자기 탭 uuid> --after <자기 탭 uuid> --name "<자식 탭 이름>"` | 부모와 같은 Run |
| 병렬 자식 중 둘째부터 | `otterctl new-window -n --group <그룹> --name "<자식 사슬 이름>" --cwd "<자기 worktree>"` | 새 Run (아래) |

새 Run 은 자식 window 를 갖고, 부모 브랜치의 지금 HEAD 에서 갈라진다. 부모의 worktree 에서 실행한다.

```
otterctl run start --objective "<자식 사슬 이름>" --window <newWindows[0]> --isolation per-run --base "$(git rev-parse HEAD)" --tree <owner/repo>#<루트> --branch
```

기대 출력을 확인한다: `newTabs` 하나, `timedOut:false`. `delivered:0` 이면 브라우저가 없다 — 사용자에게 말하고 멈춘다.

### 이름 · 등록 · 기동

탭 이름은 사슬 이름이고, 사용자가 트리를 찾는 길이다. `new-tab` 으로 만든 자식은 `--name` 으로 이미 이름이 붙었다 — 따로 `rename-tab` 을 부르지 않는다. 만든 뒤 붙이면 다른 화면의 저장과 겹쳐 이름이 사라질 수 있다. `new-window` 로 만든 탭(병렬 자식 중 둘째부터 · 발사대의 루트)은 이름을 줄 길이 없으므로 `rename-tab` 을 부른다(아래 첫 줄).

`rename-tab` 은 이름이 남았는지 확인한다. exit 1 이면 이름이 붙지 않은 것이다. 한 번 더 부르고, 그래도 exit 1 이면 사용자에게 보고하고 계속한다.

```
otterctl rename-tab --at <새 탭 uuid> "<자식 탭 이름>"      # new-window 로 만든 탭만
otterctl run member --run <Run> --role "<자식 사슬 이름>" --agent claude --at <새 탭 uuid> \
  --issue <owner/repo#번호> --title "<제목>" --parent <내 member uuid> \
  [--goal "<남은 번호 목록>"] [--parallel] [--ctx <퍼센트>] [--no-commit] --brief - <<'B'
<자식 이슈 한 줄 요약>
B
otterctl run launch --member <member uuid> | otterctl send-input --at <새 탭 uuid> --execute -
otterctl wait --at <새 탭 uuid> --for ready --timeout-ms 180000
otterctl read-screen --at <새 탭 uuid>
otterctl status --at <새 탭 uuid>
```

**배정은 등록 플래그로 넘긴다.** 서버가 배정을 기록하고, 기동줄의 프리앰블에 `[ISSUE-TREE 배정]` 블록으로 싣는다(노드 · 사슬 이름 · 목표 경로 · 부모 · 그룹 · Run · member · 병렬 가지 · 맥락 기준 · 커밋 · 이 문서의 절대 경로). 그래서 배정 엔벨로프를 따로 보내지 않는다. 자식은 기동하자마자 배정을 안다.

| 플래그 | 언제 |
|---|---|
| `--parent <내 member uuid>` | 언제나. 발사대가 루트를 띄울 때만 뺀다 |
| `--goal` | 목표 경로가 남았을 때 |
| `--parallel` | 병렬 가지의 노드일 때 |
| `--ctx` | 사용자가 `--ctx` 를 줬을 때만. 주지 않으면 설정을 따른다 |
| `--no-commit` | 사용자가 커밋하지 말라고 했을 때 |

배정이 바뀌면(맥락 기준 정정 등) `otterctl run assign --member <자식 member uuid> --ctx <퍼센트>` 로 고친다. 자식의 다음 프리앰블(승계)부터 반영된다. 이미 일하는 자식에게는 `otterctl msg` 로도 알린다.

`run member` 가 `node_taken` 으로 거절하면 그 이슈는 다른 노드가 이미 맡고 있다. 거절에 그 멤버와 상태가 실린다.
- 상태가 `lost` 면(옛 탭이 닫혔다) 새 노드로 맡지 말고 **이어받는다**: `otterctl run succeed --member <그 member> --at <새 탭 uuid>` 뒤 `run launch --member <새 member>`.
- 그 밖이면 그 하위를 띄우지 않는다. 만든 탭·window 를 닫고 부모에게 `보고` 로 알린다.

`wait` 가 `ready` 를 내도 입력을 받을 준비가 아닐 수 있다. `read-screen` 을 본다. 신뢰·권한 확인을 묻고 있으면 답한 뒤 다시 확인한다.

`status` 가 `state=working` 이어야 한다 — 자식이 프리앰블의 배정으로 일을 시작했다. 세 번 확인해도 아니면 `read-screen` 으로 막힌 곳을 보고, 풀리지 않으면 멈추고 사용자에게 말한다.

## 노드 절차

### 1. 자기 자리와 이슈

```
otterctl who-am-i
```

`uuid=` · `toolId=` 를 적는다. 배정은 프리앰블의 `[ISSUE-TREE 배정]` 블록에 있다. 「이슈 접근 규칙」 의 「권한」 을 먼저 지난다. 배정의 이슈를 위 GraphQL 로 읽고, 「설정 점검」 을 한다. 프로젝트의 지시 문서에서 이슈 규약을 확인한다. **이슈를 프로젝트 보드의 진행 중으로 옮긴다**(규약이 없으면 건너뛴다).

**세션을 시작할 때마다** 이 걸음을 한다. 부모가 연 세션도, 승계로 들어온 세션도 같다.

- 이 이슈의 상태를 확인한다: 열림·닫힘, 보드의 상태 칸.
- 규약이 정한 보드(예: 프로젝트 지시 문서의 `rnd-unit4`)에서 이 이슈의 필수 필드가 모두 채워졌는지 확인하고, 빠진 것은 채운다. 어떤 필드가 필수인지는 프로젝트 지시 문서가 정한다. 값을 정할 수 없으면 자기 탭에서 사용자에게 묻는다.
- 규약이 없으면 상태 확인만 한다.

### 2. 갈래를 고른다

1. **목표 경로가 남아 있다** → 그 첫 번호의 노드 **하나만** 띄운다. 배정의 목표 경로에는 나머지를 넣는다. 4로 간다.
2. **끝나지 않은 하위 이슈가 있다** → 3에서 지금 열 것을 고른다.
3. **하위 이슈가 없다** → 직접 할지 나눌지 정한다.
   - 직접 한다 → 「잎 노드의 일」.
   - 나눈다 → 하위 이슈를 만든다(프로젝트 규약 · 「이슈 접근 규칙」 의 「하위 이슈 만들기」). 하위 이슈를 만들 때 순서와 의존을 정해 본문에 적는다(아래). 그 뒤 3.

### 3. 지금 열 하위 이슈

- 기본은 **서브이슈 순서대로 하나씩**이다. 각 이슈는 바로 앞 형제에 의존한다고 본다.
- 본문에 `의존: 없음` 이 있으면 앞 형제를 기다리지 않는다. `의존: #61, #63` 이면 그 이슈들이 닫힌 뒤에 연다.
- 열 수 있는 이슈가 여럿이면 함께 연다(병렬). 상한은 없다.
- 의존 대상이 모두 닫혔는지 확인한 뒤 연다.
- 열기 전에 그 하위 이슈를 「이슈 접근 규칙」 의 「설정 점검」 으로 본다. 다른 저장소의 이슈면 「권한」 도 본다.

**하위 이슈를 만들 때**: 앞 형제에 의존하지 않으면 본문에 `의존: 없음` 을 적는다. 작업이 시스템 성능에 예민하면(측정 · 부하 시험 등) 병렬로 만들지 않는다.

### 4. 하위를 띄우고 쉰다

열기로 한 하위마다 「노드 띄우기」 를 한다. 병렬이면 첫째는 사슬 탭, 둘째부터 새 window 다. 그 뒤 **턴을 끝낸다.**

### 5. 메시지가 왔을 때

엔벨로프 본문의 첫 줄이 종류다.

| 종류 | 할 일 |
|---|---|
| `보고` | 공유 문서(결정 · 설계)에 남길 것이면 **내가** 문서에 적는다(프로젝트 규약이 있을 때). 하위는 문서를 고치지 않는다 |
| `보고: 선행 #<번호>` | 하위가 먼저 해야 할 이슈를 찾았다. 아래 「선행 이슈」 |
| `질문` | 하위가 **내 범위의 사실**(형제 이슈의 상태 · 결과)을 묻는다. 코드 · 문서 · 이슈로 확실히 답할 수 있으면 `답` 을 보낸다. 판단 질문은 오지 않는다 — 하위가 자기 탭에서 사용자에게 묻는다 |
| `완료` | 아래 「하위가 끝났을 때」 |
| `실패` | 지우지 않는다. 무엇이 막혔는지 사용자에게 내 탭에서 말한다 |
| `종료 요청` · `종료 준비` · `준비됨` · `막힘` | 아래 「트리 종료」 |

### 6. 하위가 끝났을 때 (안전 지점)

1. 그 하위의 탭을 닫는다. 병렬 가지의 마지막 노드였으면 window 를 닫는다. **하위는 스스로 닫지 않는다 — 닫는 것은 나다.**
   ```
   otterctl close-tab --at <하위 탭 uuid> --force
   otterctl close-window -n --at <하위 탭 uuid> --force
   ```
   둘 중 하나만 쓴다.
2. 병렬 가지였으면 그 브랜치를 내 브랜치에 병합한다. 충돌은 내가 푼다. 풀 수 없으면 사용자에게 묻는다. 병합 뒤 `otterctl run close --run <그 가지의 Run>`.
3. 그 하위 이슈와 내 이슈의 **결정 코멘트**(첫 줄 `결정:`)를 읽는다. 내 범위의 다른 이슈나 앞선 결정과 충돌하면 사용자에게 묻는다. 공유 문서로 옮길지는 프로젝트 규약을 따른다 — 규약이 없으면 옮기지 않는다.
4. 보고에 문서에 남길 것이 있으면 적는다(프로젝트 규약이 있을 때).
5. 하위 이슈를 더했거나 진행 순서가 바뀌었으면 서브이슈 순서를 진행 순서에 맞게 다시 놓는다(쓰기 — 「이슈 접근 규칙」 의 「권한」 을 먼저 지난다). 닫힌 하위는 닫힌 순서대로 앞에 둔다.
   ```
   gh api graphql -f query='mutation($i:ID!,$s:ID!,$a:ID){reprioritizeSubIssue(input:{issueId:$i,subIssueId:$s,afterId:$a}){issue{number}}}' -F i=<내 이슈 node id> -F s=<옮길 하위 node id> -F a=<그 앞에 올 하위 node id>
   ```
6. 맥락 사용률을 본다:
   ```
   otterctl status --json
   ```
   `context.usedPct` 로 「맥락 판단」 을 한다(배정이 `끔` 이면 넘기지 않는다). 다음 일은 다음 하위를 띄우고 그 완료를 처리하는 것까지다. 넘기기로 하면 `/otterminal:migration` 으로 새 세션에 넘긴다. 이 노드는 Run 멤버이므로 migration 의 **멤버 갈래**(자기 승계 `run succeed --self`)를 탄다 — 배정 · 탭 이름 · worktree 가 그대로 가고, 서버가 부모와 하위에게 새 `toolId` 를 알린다. 값이 없으면 넘기지 않고 계속하며, 그 사실을 보고에 적는다.
   migration 은 **같은 이슈**를 이어 갈 때만 쓴다. 다른 이슈로 넘어가는 수단이 아니다.
7. 다음에 열 하위 이슈가 있으면 3으로 간다. 모두 닫혔으면 내 이슈를 끝낸다(「잎 노드의 일」 의 끝내기).

### 맥락 판단

안전 지점에서 넘길지를 정하는 규칙이다. 기준은 배정의 맥락 기준 n, 지금 값은 x(`context.usedPct`)다. 고정 문턱이 아니다 — 다음 일의 크기를 본다.

1. x 가 85% 이상이면 판단하지 않고 지금 넘긴다. n 과 무관하다. 넘기는 일 자체도 맥락을 쓰고, 자동 압축이 없는 세션은 100% 에 닿으면 넘길 수 없다.
2. x 가 기준 × 0.8 보다 작으면 넘기지 않는다(n=50 이면 40%).
3. 그 사이에서는(n 을 넘은 경우도 같다) 다음 일을 끝냈을 때의 맥락을 가늠한다.
   - n 을 크게 넘거나 85% 에 닿을 것 같으면 그 일을 시작하지 않고 지금 넘긴다.
   - n 에서 크게 벗어나지 않을 것 같으면 그 일을 끝내고 넘긴다. 끝냈을 때 아직 기준 × 0.8 보다 아래면 다음 안전 지점에서 다시 판단한다.
4. 판단을 보고에 한 줄로 적는다: 지금 x% · 기준 n% · 다음 일 뒤 예상 · 그래서 지금 넘김 / 끝내고 넘김.

### 선행 이슈 (`보고: 선행` 을 받았을 때)

하위가 자기 이슈보다 먼저 해야 할 이슈를 찾아, 그 이슈를 내 하위로 만들고 앞 순서에 놓았다. 하위는 하던 변경을 WIP 커밋으로 남기고 멈췄다.

1. 그 하위의 탭을 닫는다(6의 1).
2. 선행 이슈의 노드를 띄운다(「노드 띄우기」).
3. 선행 이슈가 닫히면 원래 이슈의 노드를 다시 띄운다. 다시 뜬 노드는 WIP 커밋과 이슈의 진행 메모에서 이어 간다.

## 잎 노드의 일

1. 이슈를 계획하고 일한다. 공유 문서는 고치지 않는다 — 남길 것은 보고에 담는다. 진행 메모가 필요하면 이슈에 코멘트로 남긴다. 이 잎의 모든 이슈 쓰기(코멘트 · 결정 · 하위 만들기 · 닫기)는 「이슈 접근 규칙」 을 지난다.
2. 시험한다(프로젝트 규약).
   **잎의 안전 지점** — 일의 한 단계(시험이 통과하는 단위)를 커밋한 뒤 `otterctl status --json` 의 `context.usedPct` 로 「맥락 판단」 을 한다. 다음 일은 다음 단계다. 넘기기로 하면 `/otterminal:migration` 의 멤버 갈래로 넘긴다(같은 이슈를 새 세션이 잇는다). 배정이 `끔` 이면 넘기지 않는다. 값이 없으면 넘기지 않고, 그 사실을 보고에 적는다.
3. **질문이 생기면:**
   - 사실 질문(코드 · 문서로 답이 나오는 것)은 스스로 찾는다. 내 범위 밖의 사실(형제 이슈의 상태 · 결과)만 부모에게 `질문` 으로 보낸다.
   - 판단 질문은 먼저 기존 결정을 찾는다: 프로젝트 문서 · 내 이슈와 부모 이슈의 코멘트(첫 줄 `결정:`). 있으면 따른다.
   - 없으면 부모를 거치지 않고 **내 탭에서** 사용자에게 묻는다(AskUserQuestion 을 써도 된다).
   - 받은 결정은 이슈 코멘트로 남긴다. 첫 줄은 `결정:` 이다. 내 이슈에만 걸리면 내 이슈에, 형제 이슈에도 걸리면 부모 이슈에 남긴다.
4. **먼저 해야 할 이슈를 찾으면** 다른 이슈로 스스로 옮겨 가지 않는다:
   1. 그 이슈를 부모 이슈의 하위로 만들고, 내 이슈보다 **앞** 순서에 놓는다(`reprioritizeSubIssue`, 노드 절차 6의 5). 만들 때와 만든 뒤는 「이슈 접근 규칙」 의 「하위 이슈 만들기」 를 따른다 — 기준은 부모 이슈다.
   2. 하던 변경을 WIP 커밋으로 남긴다: `wip(#<내 번호>): <한 줄>`. 배정이 커밋 `금지` 면 `git stash push -m "issue-tree #<내 번호>"`.
   3. 내 이슈에 어디까지 했는지 코멘트로 남긴다.
   4. 부모에게 알리고 멈춘다. 탭은 닫지 않는다 — 부모가 닫는다.
      ```
      otterctl msg --to <부모 toolId> - <<'M'
      보고: 선행 #<번호> <사슬 이름>
      WIP: <커밋 해시 | stash 이름>
      M
      ```

**끝내기**

5. 커밋한다(배정이 `금지` 면 하지 않는다). 메시지는 프로젝트 규약을 따른다. AI 서명을 넣지 않는다.
6. 「설정 점검」 을 한 번 더 한 뒤, 이슈를 프로젝트 규약대로 닫고 보드의 완료로 옮긴다.
7. 기록하고 부모에게 알린다:
   ```
   otterctl run report --outcome succeeded --summary "<세 문장>"
   otterctl msg --to <부모 toolId> - <<'M'
   완료 <사슬 이름>
   커밋: <해시 목록>  브랜치: <병렬 가지면 브랜치 이름>
   문서에 남길 것: <없음 | 내용>
   M
   ```
8. `msg` 가 `전송 완료` 였는지 확인하고 멈춘다. **내 탭은 닫지 않는다** — 부모가 닫고 다음 하위를 연다. 다음 형제 이슈로 스스로 넘어가지 않는다.

루트 노드의 부모는 조율 에이전트다. 조율이 `완료` 를 받아 「트리 종료」 를 한다. 보내기 전에 조율이 있는지 본다(「대신 조율」 의 판정). 없으면 「대신 조율」 로 간다.

실패로 끝나면 커밋하지 않은 변경을 지우지 않는다. `otterctl run report --outcome failed` 와 `실패` 메시지를 보낸다.

## 트리 종료

트리를 닫는 길은 하나다. 정상 완료(루트의 `완료`)와 중간 종료(`종료 요청`)가 같은 길을 쓴다. 정리는 조율 에이전트가 하고, 각 노드는 자기 범위만 정리한다.

정리 중의 이슈 쓰기(WIP 코멘트 · 이슈 닫기 · 보드 옮기기)도 「이슈 접근 규칙」 을 지난다. 권한이 모자라거나 쓰기가 거절되면 쓰지 않고 `막힘` 으로 올린다.

메시지는 `otterctl msg --to <부모 | 자식 toolId>` 로 보낸다. 본문 첫 줄이 종류다.

| 종류 | 방향 | 본문 |
|---|---|---|
| `종료 요청 <사슬 이름>` | 아래 → 위 | 둘째 줄: 사용자가 말한 이유 |
| `종료 취소` | 조율 → 요청한 노드 | 사용자가 확인하지 않았다 |
| `종료 준비` | 위 → 아래 | 미완료 노드마다 `#<번호>: 보존` 또는 `#<번호>: 버림` 한 줄 |
| `준비됨 <사슬 이름>` | 아래 → 위 | `남긴 브랜치: <없음 \| 목록>` · `닫은 이슈: <목록>` |
| `막힘 <사슬 이름>` | 아래 → 위 | 무엇이 막혔는가 |

### 1. 종료 요청을 올린다 (노드)

- 사용자가 내 탭에서 트리를 닫자고 하면 **스스로 정리하지 않는다.** 하던 일을 멈추고(커밋도 되돌리기도 하지 않는다) 부모에게 보낸다.
  ```
  otterctl msg --to <부모 toolId> - <<'M'
  종료 요청 <사슬 이름>
  <사용자가 말한 이유>
  M
  ```
- 하위에게서 `종료 요청` 을 받으면 판단을 더하지 않고 내 부모에게 그대로 넘긴다. 루트는 조율에게 넘긴다.
- 부모에게 보낸 `msg` 가 전송되지 않으면 사용자에게 내 탭에서 알리고 멈춘다. 루트라면 「대신 조율」 로 간다.
- `종료 취소` 를 받으면 사용자에게 알리고 기다린다.

### 2. 확인한다 (조율)

1. 미완료 노드를 찾는다. `run report` 를 하지 않은 노드이고, `nodes` 에서 `endedAt` 이 없는 노드다.
   ```
   otterctl run tree --ref <owner/repo>#<루트> --json
   ```
2. 사용자에게 트리를 닫을지 확인한다. 미완료 노드마다 **보존**(WIP 커밋으로 남기고 브랜치를 보존한다) 또는 **버림**(커밋하지 않은 변경을 버린다)을 고르게 한다. 판단에 필요하면 그 노드 worktree 의 `git -C <worktree> status --short` 를 보여 준다.
3. 확인하지 않으면 요청한 노드에 `종료 취소` 를 보내고 끝낸다. 아무것도 닫지 않는다.
4. 확인하면 루트에 `종료 준비` 를 보낸다. 본문에 미완료 노드마다 고른 답을 한 줄씩 적는다.

정상 완료(루트의 `완료`)면 이 절의 1~4를 건너뛰고 「4. 정리한다」 로 간다.

### 3. 자기 범위를 정리한다 (노드)

`종료 준비` 를 받으면:

1. 일하는 하위가 있으면 받은 본문 그대로 하위 전부(사슬의 자식 · 병렬 가지)에 보내고 턴을 끝낸다. 하위가 모두 `준비됨` 을 보낸 뒤 2로 간다. 하위 하나라도 `막힘` 이면 그것을 그대로 부모에게 올리고 멈춘다. 하위의 탭은 닫지 않는다 — 조율이 닫는다.
2. 내 이슈가 미완료면 받은 답대로 한다.
   - **보존**: `wip(#<내 번호>): <한 줄>` 로 커밋한다. 배정이 커밋 `금지` 면 `git stash push -m "issue-tree #<내 번호>"`. 커밋할 변경이 없으면(사슬의 하위가 같은 worktree 를 이미 커밋했다) 하지 않는다. 내 이슈에 어디까지 했는지 코멘트로 남긴다.
   - **버림**: 내 worktree 의 커밋하지 않은 변경만 버린다(`git restore .` · `git clean -fd`). 다른 노드의 커밋은 건드리지 않는다.
   - 그 뒤 보고한다. 이미 보고했으면 다시 하지 않는다.
     ```
     otterctl run report --outcome failed --summary "트리 종료로 중단: <어디까지 했는가>"
     ```
3. 병렬 가지의 이슈가 닫혔으면 그 브랜치를 내 브랜치에 병합한다. 닫히지 않았으면 병합하지 않고 「남긴 브랜치」 에 적는다. 충돌은 스스로 풀고, 풀 수 없으면 `막힘` 이다.
4. 내 worktree 가 깨끗한지 본다. 출력이 비어 있어야 한다.
   ```
   git status --porcelain
   ```
5. 깨끗하면 `준비됨`, 아니면 `막힘` 을 부모에게 보내고 멈춘다. **내 탭은 닫지 않는다.**
   ```
   otterctl msg --to <부모 toolId> - <<'M'
   준비됨 <사슬 이름>
   남긴 브랜치: <없음 | 목록>
   닫은 이슈: <목록>
   M
   ```

### 4. 정리한다 (조율)

루트의 `준비됨`(중간 종료) 또는 `완료`(정상 완료)를 받으면 한다. `막힘` 을 받으면 **아무것도 닫지 않는다.** 무엇이 막혔는지 사용자에게 알리고, 사용자가 풀면 루트에 `종료 준비` 를 다시 보낸다.

1. 사용자에게 루트 Run 브랜치를 어떻게 할지 묻는다: 사용자 브랜치에 병합 · push · PR · 브랜치만 남김. **답을 받기 전에는 하지 않는다.** 병합 충돌이 나면 사용자 작업 트리에서 풀지 않고 알린다.
2. 트리의 열린 Run 을 **가지 Run 부터** 닫는다. `runs` 에서 `treeBranch` 인 Run 이 가지 Run 이다. 노드가 깊은 가지가 먼저이고 루트 Run 이 마지막이다. `--force` 를 쓰지 않는다. 보고하지 않은 멤버 때문에 거절되면 그 멤버의 `state` 를 본다. 모두 `lost`(탭이 이미 닫혔다)면 사용자에게 알리고 확인을 받은 뒤 `--force` 로 닫는다. 살아 있는 멤버가 있으면 멈추고 사용자에게 알린다.
   ```
   otterctl run tree --ref <owner/repo>#<루트> --json
   otterctl run close --run <id>
   ```
   `run close` 가 세션 종료 · 탭 닫기 · worktree 정리를 한다. 트리 Run 의 worktree 는 그 브랜치가 병합 대상(그 Run 을 연 곳의 브랜치)에 들어가 있을 때만 지워진다. 아니면 잔여물 `unmerged` 로 남고 Run 기록도 남는다. 나중에 병합한 뒤 `otterctl run close --run <id> --force` 로 다시 정리한다.
3. 그룹에 남은 window 를 모두 닫고 그룹을 지운다. 그룹 uuid 는 `list-groups` 에서 `tree` 가 이 트리인 행이다. 남은 window 는 `list-workspace` 에서 `groupUuid` 가 그 그룹인 행이다. `windowUuid` 마다 탭 `uuid` 하나로 닫는다.
   ```
   otterctl list-groups --json
   otterctl list-workspace --json
   otterctl close-window -n --at <그 window 의 탭 uuid> --force
   otterctl delete-group --at <그룹 uuid>
   ```
4. 내 탭에 최종 보고를 남긴다: 닫은 이슈 · 남긴 브랜치 · worktree 잔여물(`run close` 응답의 `residue` 와 사유) · 병합/push 결과. 같은 요약을 트리 방에도 쓴 뒤 `chat_leave` 로 트리 방에서 나간다. **내 탭은 닫지 않는다.**

### 5. 대신 조율 (루트)

조율이 없으면 루트가 2~4를 내 탭에서 한다. 조율이 없다는 것은 셋 중 하나다: 프리앰블이 「부모: 없음」 이다 · 조율에게 보낸 `msg` 가 전송되지 않는다 · `otterctl status --at <조율 toolId>` 가 `live=false` 이거나 `state=unknown` 이다(에이전트가 끝나면 활동 기록이 지워져 `unknown` 이 된다. 탭만 남은 셸에 보낸 엔벨로프는 셸 명령으로 실행된다). 루트는 조율에게 `완료` · `종료 요청` · `준비됨` · `막힘` 을 보내기 전에 늘 `status` 를 본다. 다른 점은 다섯이다.

- 2의 4에서 `종료 준비` 는 나에게 보내지 않는다. 내가 받은 것으로 보고 3의 1부터 한다.
- 4의 2에서 가지 Run 은 그대로 닫는다. 루트 Run 은 아직 닫지 않는다.
- 4의 3에서 내 window 는 닫지 않는다. 그 대신 내 window 의 다른 노드 탭을 닫는다. `run tree --json` 의 `nodes` 중 루트 Run 의 다른 노드다. 이들은 모두 멈췄다.
  ```
  otterctl close-tab --at <그 노드의 tabId> --force
  ```
- 루트 Run 은 **맨 마지막 명령**으로 닫는다. 내 `run report` 를 먼저 하고(이미 했으면 건너뛴다) `--keep-tools` 로 닫는다. `--keep-tools` 는 내 세션과 탭을 닫지 않는다. 대신 다른 탭도 닫지 않으므로 바로 앞 걸음이 필요하다. 이 명령이 내 worktree 를 지울 수 있으므로 그 뒤에는 명령을 실행하지 않는다.
  ```
  otterctl run close --run <루트 Run> --keep-tools
  ```
- 최종 보고에 「이 탭과 window 는 직접 닫는다」 를 적는다.

## 조정자 절차

실행 방식 `coord` 에서 이 명령을 실행한 세션이 조정자다. 조정자는 일을 직접 하지 않는다. 통합 브랜치를 만들고, ready 이슈마다 일꾼을 띄우고, 일꾼의 `review` 를 확인해 병합한다. 「절대 원칙」 의 4~7과 「식별자」 는 그대로 지킨다.

이 절의 `<트리 이름>` 은 local 이면 `<별칭>:<루트>`, github 이면 `<별칭>#<루트>` 다. `<트리 표지>` 는 local 이면 `<별칭>:<루트>`, github 이면 `owner/repo#<루트>` 다.

### 1. 자리와 이슈

1. `otterctl who-am-i` 로 `uuid=` · `toolId=` 를 적는다.
2. 이슈 트리를 읽는다.
   - local: `otterctl issue tree --dir <원본 폴더>`.
   - github: 발사대 「0. 접근 확인」 을 그대로 한다. 그 뒤 루트의 하위 이슈를 GraphQL 로 읽는다(「이슈 규약」).
3. 일감을 사용자에게 한 번 보인다: 이슈 수 · 지금 ready 인 이슈 · 통합 브랜치 이름. 사용자가 멈추라고 하지 않으면 진행한다.

### 2. 통합 브랜치와 통합 worktree

사용자 작업 트리는 고치지 않는다. 통합 worktree 를 저장소 옆에 만든다.

```
git worktree add "<저장소 루트>-<별칭>" -b integ/<별칭>
```

- 통합 브랜치는 `integ/<별칭>` 이다. 일꾼 브랜치 `<별칭>/<ID>` 와 이름이 겹치지 않는다.
- local 이면 **원본 폴더를 통합 worktree 안의 이슈 폴더로 옮겨 잡는다**: `<통합 worktree>/<저장소 안의 이슈 폴더 상대 경로>`. 이 뒤로 상태는 이 폴더만 고친다. 사용자 작업 트리의 이슈 폴더는 병합 전까지 그대로다.

### 3. 그룹 · window · Run

```
otterctl new-group --name "<트리 이름> <루트 제목>"             # github 이면 --tree owner/repo#<루트> 를 붙인다
otterctl new-window -n --group <그룹> --name "<트리 이름> 일꾼" --cwd "<통합 worktree>"
cd "<통합 worktree>"
otterctl run start --objective "<트리 이름> coord" --window <newWindows[0]> \
  --tree <트리 표지> --mode coord --chat-room <방 id> [--issue-dir <통합 worktree 안의 원본 폴더>]
```

- 그룹을 만든 뒤 `run start` 전에 트리 방을 만든다(「트리 방」의 만들기). 이름은 그룹 이름, 목적은 `<트리 표지> <루트 제목>` 이다.

- `--issue-dir` 은 local 일 때만 준다. `--isolation` 은 주지 않는다 — worktree 는 조정자가 이슈마다 만든다.
- 이 Run 의 조정자가 나다. 일꾼의 프리앰블에서 부모는 나의 `toolId` 다.
- `tree_open` 으로 거절되면 「발사대 절차」 4의 안내를 그대로 따른다.

### 4. ready 이슈

- local: `otterctl issue tree ready`. 하위가 있는 이슈(`<ID>.` 로 시작하는 이슈가 있는 것)는 일꾼에게 맡기지 않는다 — 그 하위가 일감이다.
- github: 열린 잎 이슈 가운데 의존(blocked by)이 모두 닫힌 것이다. 의존은 GraphQL 의 `blockedBy` 로 읽는다.
  ```
  gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){issue(number:$n){
    number state blockedBy(first:50){ nodes{ number state repository{ nameWithOwner } } }
  }}}' -F o=<owner> -F r=<repo> -F n=<번호>
  ```
  API 가 `blockedBy` 를 거절하면 본문의 `의존:` 줄로 판정한다(「노드 절차」 3과 같다). github 에는 상태 필드가 없으므로 상태는 이렇게 센다: 열림 + 맡은 멤버 없음 = ready, 맡은 멤버가 일함 = in-progress, 멤버가 `run report --outcome succeeded` = review, 닫힘 = done.

### 5. 일꾼을 띄운다

ready 이슈마다 띄운다. **동시 일꾼 수에 정해진 상한은 없다.** 조정자가 정한다:

- 디스크를 본다: `df -h "<저장소 루트>/.."`. worktree 마다 빌드 산출물(예: `rust/target`)이 커진다. 남은 공간이 빌드 몇 벌을 못 담으면 줄인다.
- 이슈 크기와 겹침을 본다. 같은 파일을 고칠 이슈는 함께 띄우지 않는다. 성능 측정 · 부하 시험 이슈는 혼자 돌린다.

이슈 하나마다:

```
git -C "<통합 worktree>" worktree add "<저장소 루트>-<별칭>-wt/<ID>" -b <별칭>/<ID> integ/<별칭>
otterctl issue set <ID> --status ready --branch <별칭>/<ID>           # local. 이미 ready 면 --branch 만
otterctl new-tab -n --at <일꾼 window 의 탭 uuid> --name "<트리 이름>›<ID> <제목의 짧은 형태>"
otterctl send-input --at <새 탭 uuid> --execute "cd '<저장소 루트>-<별칭>-wt/<ID>'"
otterctl run member --run <Run> --role "<트리 이름>›<ID>" --agent claude --at <새 탭 uuid> \
  --issue <별칭>:<ID 또는 owner/repo#번호> --title "<제목>" [--no-commit] --brief - <<'B'
작업 경로: <저장소 루트>-<별칭>-wt/<ID>  브랜치: <별칭>/<ID>
<이슈 한 줄 요약>
B
otterctl run launch --member <member uuid> | otterctl send-input --at <새 탭 uuid> --execute -
otterctl wait --at <새 탭 uuid> --for ready --timeout-ms 180000
otterctl read-screen --at <새 탭 uuid>
otterctl status --at <새 탭 uuid>
```

- `--issue` 는 local 이면 `<별칭>:<ID>`, github 이면 `owner/repo#번호` 다. `--parent` 는 주지 않는다.
- 일꾼 window 는 3에서 만든 window 하나다. 탭이 많아지면 같은 그룹에 window 를 더 만든다(`new-window -n --group <그룹>`).
- 신뢰 · 권한 확인과 `state=working` 확인은 「노드 띄우기」 와 같다.
- 띄운 뒤 **턴을 끝낸다.** 일꾼의 메시지가 와야 깨어난다. 폴링하지 않는다.

### 6. 메시지가 왔을 때

본문 첫 줄이 종류다.

| 종류 | 할 일 |
|---|---|
| `review <트리 이름>›<ID>` | 아래 「병합」 |
| `blocked <트리 이름>›<ID>` | 이유를 읽는다. 내가 풀 수 있으면(다른 이슈를 먼저 끝내야 함 등) 순서를 바꾼다. 판단이 필요하면 사용자에게 묻는다. 탭은 그대로 둔다 |
| `split <트리 이름>›<ID>` | 일꾼이 하위 이슈를 만들고 자기 이슈를 `split` 으로 바꿨다. 그 일꾼의 변경을 확인하고(커밋이 있으면 병합), 탭을 닫고, 4로 간다 |
| `질문` | 범위 밖 사실(다른 이슈의 상태 · 결과)이면 답한다. 판단 질문은 일꾼이 자기 탭에서 사용자에게 묻는다 |
| `commit <트리 이름>›<ID>` | 일꾼의 커밋이 막혔다. 둘째 줄의 메시지 파일로 내가 커밋한다: `git -C <일꾼 worktree> add -A` 뒤 `git -C <일꾼 worktree> commit -F <파일>`. 일꾼에게 `커밋함 <해시>` 를 보낸다 |
| `실패` | 지우지 않는다. 사용자에게 알린다 |
| `종료 요청` | 사용자가 일꾼 탭에서 트리를 닫자고 했다. 아래 「중간 종료」 를 한다 |

**병합**

1. 일꾼의 일을 확인한다: `git -C "<통합 worktree>" log --oneline integ/<별칭>..<별칭>/<ID>`, 진행 기록(local: `otterctl issue show <ID>`), 프로젝트 규약의 시험.
2. 충돌을 미리 본다: `git -C "<통합 worktree>" merge-tree --write-tree --name-only integ/<별칭> <별칭>/<ID>`. 충돌하면 그 일꾼에게 자기 worktree 에서 `git merge --no-commit integ/<별칭>` 으로 풀게 하고, 풀린 뒤 다시 1.
3. 통합 브랜치에 병합한다: `git -C "<통합 worktree>" merge --no-ff <별칭>/<ID>`.
4. 이슈를 닫는다. local: `otterctl issue set <ID> --status done`. github: 「이슈 접근 규칙」 을 지나 이슈를 닫는다.
5. 일꾼 탭을 닫고 worktree 를 지운다. 디스크를 비운다.
   ```
   otterctl close-tab --at <일꾼 탭 uuid> --force
   git -C "<통합 worktree>" worktree remove "<저장소 루트>-<별칭>-wt/<ID>"
   ```
   worktree 를 남겨야 하면(사용자가 보려 함 등) 지우지 않고, 그 안의 `rust/target/debug/incremental` 처럼 큰 빌드 잔여물만 지운다.
6. 하위가 모두 done 인 상위 이슈가 있으면 닫는다. local: `ready` → `in-progress` → `review` → `done` 을 차례로 `set` 한다(`todo` 면 `ready` 부터).
7. 4로 간다. ready 가 없고 일하는 일꾼도 없으면 7. 「끝」 으로 간다.

맥락은 안전 지점(병합 하나를 끝낸 뒤)에서 「맥락 판단」 으로 본다. 넘길 때는 `/otterminal:migration` 을 쓴다.

### 7. 끝

1. 남은 이슈가 없는지 본다(local: `otterctl issue tree`, github: 루트의 하위가 모두 닫힘). `blocked` 가 남았으면 사용자에게 알리고 어떻게 할지 묻는다.
2. 사용자에게 통합 브랜치를 어떻게 할지 묻는다: 사용자 브랜치에 병합 · push · PR · 브랜치만 남김. **답을 받기 전에는 하지 않는다.** 병합은 `--no-ff` 다.
3. `otterctl run close --run <Run>` 뒤 그룹의 window 를 닫고 그룹을 지운다(「트리 종료」 4의 3).
4. 통합 worktree 는 사용자 브랜치에 병합된 뒤에만 지운다(`git worktree remove`). 아니면 남기고 보고에 적는다.
5. 내 탭에 최종 보고를 남긴다: 닫은 이슈 · 남은 이슈 · 통합 브랜치 · 남은 worktree · 병합/push 결과. 같은 요약을 트리 방에도 쓴 뒤 `chat_leave` 로 트리 방에서 나간다. **내 탭은 닫지 않는다.**

**중간 종료**: 사용자가 멈추자고 하면 일하는 일꾼마다 보존(WIP 커밋) · 버림(커밋하지 않은 변경 버림)을 묻고, 일꾼에게 `종료 준비` 와 고른 답을 보낸다. 모든 일꾼이 `준비됨` 을 보내면 3~5를 한다. 하나라도 `막힘` 이면 아무것도 닫지 않고 사용자에게 알린다.

## 일꾼 규칙

`coord` 의 일꾼이 따른다. 프리앰블의 `[ISSUE-TREE 배정]` 이 이슈와 조정자(부모)를 알려 주고, brief 가 작업 경로와 브랜치를 알려 준다. 프로젝트 지시 문서도 지금처럼 따른다.

1. **자리**: `otterctl who-am-i` 로 `toolId=` 를 적는다. brief 의 작업 경로(자기 worktree) 안에서만 파일을 고친다. 브랜치는 `<별칭>/<ID>` 다.
2. **상태는 원본 폴더만** 고친다(local). `otterctl issue` 로만 고치고, worktree 안의 사본은 고치지 않는다. 착수할 때 `otterctl issue set <ID> --status in-progress --owner <내 toolId>` 를 한다. github 이면 상태 필드가 없다 — 진행 메모만 이슈 코멘트로 남기고(「이슈 접근 규칙」), 이슈를 닫지 않는다.
3. **시험을 먼저** 쓰고 실패(RED)를 확인한 뒤 구현한다. RED 를 확인하지 못했으면 진행 기록에 그 사실을 적는다.
4. **막히면** 추측해서 구현하지 않는다. 다른 이슈의 결과가 필요하거나 판단 근거가 없으면 `otterctl issue set <ID> --status blocked --reason "<이유>"`(github 이면 코멘트) 뒤 조정자에게 `blocked <트리 이름>›<ID>` 를 보낸다. 판단 질문은 먼저 기존 결정을 찾고, 없으면 자기 탭에서 사용자에게 묻는다.
5. **문서와 코드가 다르면** 코드가 기준이다. 문서는 고치지 않고 진행 기록(`otterctl issue log`)에 목록으로 남긴다.
6. **나눌 필요가 있으면** 하위 이슈 파일을 만든다(`otterctl issue new <ID>.<n> "<제목>" [--deps …]`). 그 뒤 `otterctl issue set <ID> --status split` 을 하고 조정자에게 `split <트리 이름>›<ID>` 와 만든 ID 목록을 보낸다. 하위를 누가 언제 할지는 조정자가 정한다.
7. **다른 에이전트를 띄우지 않는다.** 다른 이슈로 스스로 옮겨 가지 않는다. 자기 탭을 닫지 않는다 — 조정자가 닫는다.
8. **커밋**: 자기 브랜치에만 커밋한다(배정이 커밋 `금지` 면 하지 않는다). 메시지는 프로젝트 규약을 따르고 AI 서명을 넣지 않는다. 통합 브랜치나 사용자 브랜치에 병합하지 않는다. push 하지 않는다. **커밋이 막히면**(권한 확인 · 분류기 거절) 메시지를 `/private/tmp/<별칭>-<ID>-commit.txt` 로 남기고 조정자에게 `commit <트리 이름>›<ID>` 와 그 파일 경로를 보낸다.
9. **끝내기**: 진행 기록에 바꾼 것 · 동작 변경(이전 / 새 / 이유) · 시험 결과 · 남은 위험 · 코드와 어긋난 문서를 남긴다. `otterctl issue set <ID> --status review`(local) 뒤 `otterctl run report --outcome succeeded --summary "<세 문장>"` 을 하고 조정자에게 보낸다. done 은 조정자가 한다.
   ```
   otterctl msg --to <조정자 toolId> - <<'M'
   review <트리 이름>›<ID>
   커밋: <해시 목록>  브랜치: <별칭>/<ID>
   M
   ```
10. **디스크**: 일이 끝나면 자기 worktree 의 큰 빌드 잔여물(예: `rust/target/debug/incremental`)을 지운다.
11. `종료 준비` 를 받으면 고른 답대로 한다: 보존이면 `wip(<ID>): <한 줄>` 커밋, 버림이면 커밋하지 않은 변경만 버린다. 그 뒤 `준비됨 <트리 이름>›<ID>` 또는 `막힘 <트리 이름>›<ID>` 를 보낸다.

## 이 명령이 하지 않는 것

- 이슈 규약을 정하지 않는다. 프로젝트의 문서를 따른다.
- 병렬 가지의 결과를 자동으로 비교하지 않는다. 병합은 부모가 한다.
- 그룹 밖의 window · 탭을 건드리지 않는다.
- 사용자에게 묻지 않고 push 하거나 사용자 브랜치에 병합하지 않는다.
- 트리의 일부만 닫지 않는다. 종료는 트리 전체다.
- 병합되지 않은 worktree 를 지우지 않는다.

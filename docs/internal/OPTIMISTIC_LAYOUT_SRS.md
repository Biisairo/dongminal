# SRS: 아직 저장되지 않은 로컬 레이아웃은 원격 채택에 지지 않는다 — IEEE 29148

> **문서 상태**: 초안

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

e2e 전량에서 되풀이 관측된 흔들림 아홉 건 중 **다섯**이 같은 증상이었다 —
**방금 연 git 뷰 탭(또는 그 탭을 담은 창)이 사라진다.**

`11-git-polling.md §5` 가 그 아홉을 코드로 매핑해 판정을 확정했다:

> 기전은 셋이고, 그중 가장 많은 다섯(H14·D1·BR11·X4·V10-13)은 **관측과
> 무관하다.** `_onWorkspaceChanged` 가 서버 레이아웃을 채택하면 방금 연 git 뷰
> 탭이 사라진다.

1차 감사(`TEST-5`)가 적은 *"재렌더는 앱의 정상 동작이므로 견디는 쪽은
테스트다"* 는 **근거가 없다.** git 관측은 `render()` 를 부르지 않는다
(`app-git.js:610`). 탭이 사라지는 진짜 이유는 **워크스페이스 재채택**이고,
그것은 정상 동작이 아니라 고쳐야 할 자리다.

본 SRS 는 그 채택에 **하나의 불변식**을 세운다:

> **원격이 본 적 없는 로컬 레이아웃 변경은 채택이 덮지 않는다.**

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 창 보호 | 원격이 본 적 없는 로컬 창은 채택이 지우지 않는다 (`app.js` 409 경로에만 있던 것을 **채택기 한 자리**로 옮긴다) |
| **B** 탭 보호 | 원격이 본 적 없는 로컬 탭은 채택이 지우지 않는다. 대응 창·대응 칸을 찾아 그 자리에 되얹는다 |
| **C** 활성 탭 보존 | 되얹은 탭이 로컬의 활성 탭이었으면 그 자리도 함께 되살린다 |
| **D** 창 신원 | Repo(Editor) 창의 대응은 **id 가 아니라 루트**로도 찾는다 — 재조정이 같은 루트의 창을 새 id 로 세우기 때문이다 (`app-cmd.js:326` `_edKeepActive` 가 같은 사실을 이미 딛는다) |
| **E** 되쓰기 | 병합은 화면의 사실이지 원격의 사실이 아니다 — 병합이 일어나면 그 결과를 저장한다 |

**미포함:** §6 비목표. 특히 **창 합집합**(닫힌 창을 되살리는 것)은 범위 밖이며
`WORKSPACE_SAVE_CONFLICT_SRS §1.5` 가 이미 배제했다.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **채택** | 원격 워크스페이스 스냅샷을 이 화면의 `this.ws` 로 삼는 일. 주체는 `_applyRemoteWorkspace` 하나다 |
| **원격이 아는 창/탭** | 우리 PUT 이 성공시켰거나 원격 스냅샷에 실려 온 창/탭. `_wsSavedIds`·`_wsSavedTabs` 가 그 기억이다 |
| **미관측 로컬 변경** | 로컬에는 있고 원격 스냅샷에 없으며 **원격이 아는 것도 아닌** 창/탭. 곧 *아직 나가지 못한 우리 변경*이다 |
| **삭제** | 원격이 **알았다가 없앤** 창/탭. 채택이 지워도 되는 유일한 갈래다 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 채택은 `this.ws=sv` 한 줄이다

`app-cmd.js:_applyRemoteWorkspace` 는 마이그레이션·재조정을 거친 뒤
`this.ws=sv` 로 **통째로 갈아끼운다**. 그 뒤 되살리는 것은 셋뿐이다 —
`activeWindow`·`focusedPane`·활성 리포. **레이아웃은 그 목록에 없다.**

### 2.2 보호는 이미 있다 — 다만 한 경로에만 있다

`app.js:531-556`(409 재시도)은 `_wsSavedIds` 로 *"원격이 본 적 없는 창"* 을
가려내 `rem.windows` 에 얹은 뒤 채택기에 넣는다. 그 판정은 정확하다.

**그러나 `_onWorkspaceChanged` → `_applyRemoteWorkspace` 경로에는 없다.**
그리고 흔들림이 오는 자리는 그쪽이다 — `git pin` 하나에도
`workspace_changed` 가 방송된다(`GIT_SRS §2.4`).

### 2.3 탭에는 어느 경로에도 보호가 없다

`git-head-mobile` V10-13 이 관측한 것은 **탭 수 7 → 1** 이다. 창은 살아 있고
그 안의 탭 여섯이 사라졌다. `openView`(`app-layout.js:435-455`)는 탭을
`pn.tabs.push` 로 **로컬 배열에만** 넣고 `save()` 는 뒤따른다 — 그 사이에 오는
채택 한 번이 여섯을 지운다.

### 2.4 Repo 창의 id 는 채택 중에 바뀔 수 있다

`_edReconcile`(`app-editor.js:214-270`)은 같은 루트의 Editor 창이 둘이면
**id 사전순으로 앞선 하나만 남긴다.** 그래서 채택 직후의 창 id 가 채택 직전의
것과 다를 수 있고, id 로만 대응을 찾으면 그 창의 탭을 전부 잃는다.
`_edKeepActive`(`app-cmd.js:330`)가 활성 창에 대해 같은 일을 이미 하고 있다.

## 3. 요구사항 (Requirements)

### 3.1 기능 요구 (Functional)

**FR-OPL-1** 채택기는 `this.ws=sv` 전에 **미관측 로컬 변경을 원격 스냅샷에
병합**한다. 병합 대상은 창과 탭 둘이다.

**FR-OPL-2** 원격이 아는 것의 기억은 **창 id 와 탭 id 두 벌**이다.
`_wsMarkSaved(windows)` 가 둘을 함께 적는다. 갱신하는 순간은 종전과 같다 —
저장 성공(`FR-WSC-12`)과 원격 채택이다.

**FR-OPL-3** 탭 id 는 **창 밖에서도 유일**하다(`newEntityId()` = UUIDv4,
`WORKSPACE_IDENTITY_SRS FR-UNI-3`). 그러므로 기억은 창별 맵이 아니라
**평평한 집합**이다 — 탭이 칸 사이를 옮겨도 판정이 흔들리지 않는다.

**FR-OPL-4** 로컬 창 `w` 의 원격 대응은 다음 순서로 찾는다:
1. `sv.windows` 에서 같은 id
2. `w` 가 Editor 창이면 `sv.windows` 에서 **같은 루트의 Editor 창**
대응이 없고 `_wsSavedIds` 에도 없으면 **미관측 로컬 창**이다 — `sv.windows` 에
그대로 얹는다. 대응이 없는데 `_wsSavedIds` 에 있으면 **삭제**이며 지운다.

**FR-OPL-5** 대응이 있는 창에서는 탭을 본다. 로컬 탭 `t` 가 대응 창의
레이아웃 어디에도 없고 `_wsSavedTabs` 에도 없으면 **미관측 로컬 탭**이다.

**FR-OPL-6** 미관측 로컬 탭이 들어갈 자리는 이 순서로 정한다:
1. 로컬에서 그 탭을 담던 칸과 **같은 id 의 칸**이 대응 창에 있으면 거기
2. 없으면 대응 창의 **첫 칸**
칸이 하나도 없으면(레이아웃이 빈 Editor 창) 로컬 칸을 그대로 옮긴다.

**FR-OPL-7** 탭의 **순서**는 로컬의 그것을 따른다 — 로컬에서 그 탭의 앞에
있던 탭이 대응 칸에도 있으면 그 뒤에 넣고, 없으면 끝에 붙인다.

**FR-OPL-8** 로컬 칸의 `activeTab` 이 미관측 로컬 탭이었으면 대응 칸의
`activeTab` 도 그것으로 둔다. 되얹지 못한 경우에는 건드리지 않는다.

**FR-OPL-9** 병합이 한 건이라도 일어나면 채택기는 **저장을 예약**한다
(`FR-WSC-13` 과 같은 이유 — 화면에만 남기면 다음 새로고침에서 사라진다).

**FR-OPL-10** 기억의 시점이 둘 다 중요하다.

| 무엇 | 시점 |
|---|---|
| 병합의 **근거** | **이 채택이 시작되기 전**의 기억. 채택기가 자기 앞머리에서 집어 둔다 |
| 기억의 **갱신** | **병합 이전의 원격 스냅샷**으로 적는다 |

앞을 어기면 — 채택기가 기억을 먼저 갈아끼우면 — 다른 화면이 **닫은** 탭이
"원격이 본 적 없는 탭" 과 같은 모양이 되어 되살아난다. 영영 닫히지 않는다.
뒤를 어기면 방금 되얹은 것이 "원격이 아는 것" 이 되어 다음 채택에서 지워진다.

**FR-OPL-11** 409 재시도 경로(`app.js`)는 **자기 병합을 걷는다.** 판정이 두
벌이 되면 한쪽만 고쳐진다 — 채택기 하나가 그 일을 한다.

**FR-OPL-12** 도구 목록을 모르는 채택(`toolsKnown===false`)에서도 병합은
같다. 병합은 도구의 생사를 판정하지 않는다 — `clean()` 이 그 일을 하고
이미 `live` 판정을 딛는다(`FR-TLU-5`).

**FR-OPL-13** 병합은 **채택기 안에서 `clean`·마이그레이션·재조정보다 뒤,
`this.ws=sv` 보다 앞**이다. 앞에 두면 되얹은 탭이 `clean()` 의 도구 판정에
걸리고(git·editor 탭은 통과하지만 terminal 탭은 걸린다), 뒤에 두면 이미
`render()` 가 없는 화면을 한 번 지난 뒤다 — `app.js:550` 의 주석이 그
함정을 적고 있다.

### 3.2 비기능 요구 (Non-functional)

**NFR-OPL-1** 병합의 비용은 창 수 × 탭 수의 선형이다. 상한은
`GitWatchCap` 류가 아니라 사용자의 레이아웃 크기이며, 실측 기준 창 10개·
탭 100개 규모에서 1ms 미만이다. 채택은 SSE 마다 도는 경로이므로 **정렬·
깊은 복사를 하지 않는다.**

**NFR-OPL-2** 병합은 원격 스냅샷 객체를 **제자리에서** 고친다. 채택기가
이미 `sv` 를 제자리에서 고치는 코드(마이그레이션·재조정)를 딛고 있다.

## 4. 설계 결정 (Design Decisions)

**D-OPL-1: 합집합이 아니라 "본 적 없음" 판정이다.**
합집합은 닫힌 창을 되살린다 — 다른 화면에서 창을 닫으면 이 화면이 그것을
되살려 영영 닫히지 않는다. `_wsSavedIds` 판정은 **삭제와 미도착을 가른다.**
`WORKSPACE_SAVE_CONFLICT_SRS §1.5` 가 같은 이유로 합집합을 배제했다.

**D-OPL-2: 탭 기억을 창별 맵이 아니라 평평한 집합으로 둔다.**
탭 id 가 전역 유일(UUIDv4)이므로 창별로 나눌 이유가 없다. 나누면 탭을 다른
창으로 옮긴 직후의 채택에서 그 탭이 "본 적 없는 것" 으로 판정되어 **두 곳에
생긴다.**

**D-OPL-3: 되얹기의 자리를 칸 id 로 먼저 찾는다.**
첫 칸으로만 넣으면 분할된 창에서 탭이 엉뚱한 칸으로 옮겨 간다. 칸 id 는
레이아웃 안에서 유일하고 원격도 같은 id 를 쓴다.

**D-OPL-4: 순서 복원은 "앞 탭 기준" 이다.**
인덱스를 그대로 쓰면 원격이 앞에 탭을 더한 경우 위치가 어긋난다. 로컬에서
바로 앞에 있던 탭을 앵커로 삼으면 두 목록이 달라도 상대 순서가 산다.

**D-OPL-5: 병합을 채택기 안에 둔다 (409 경로에서 걷어낸다).**
`app.js` 의 것은 **창만** 본다. 탭 보호를 그쪽에도 복제하면 판정이 두 벌이
된다. 채택기는 두 경로가 반드시 지나는 목이므로 거기 하나면 족하다.

**D-OPL-6: `fixtures.ts` 의 재시도 클릭은 걷지 않는다.**
그 헬퍼는 탭 유실 말고도 *"관측이 닿을 때 행이 detach 된다"* 를 함께
견딘다(`GP-9` 의 자리). 본 SRS 가 닫는 것은 탭 유실뿐이므로, 우회 **주석**의
근거 없는 서술만 정정하고 재시도 자체는 `GP-9` 조치 뒤에 다시 본다.

## 6. 비목표 (Non-goals)

- **창/탭 합집합** — 닫힌 것을 되살리지 않는다 (D-OPL-1)
- **내용의 병합** — 같은 id 의 탭이 양쪽에서 서로 다르게 바뀐 경우는 원격이
  이긴다. 레이아웃의 **존재**만 보호한다
- **`_rSide`·`reconcileList` 등 DOM 보존** — `GP-6`·`GP-9` 의 일이며 별도
- **저장 디바운스 단축** — 창을 좁히는 것은 확률을 낮출 뿐 불변식이 아니다

# SRS: 칸 마커 — 누르기 전에 어디가 열릴지 안다 — IEEE 29148

> **문서 상태**: 승인·구현중
> **남은 것**: 전건. 구현 착수 전이다 (스펙만 선다).

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 두 단계로 왔다.

> **① "현재 UX 쪽으로 제일 불편한 게 여러 슬롯이 있을 때 좌측패널의 역할이다."**
>
> **② "막 사용하다 보면 지금 어느 창이 포커스되어 있어서 사이드바를 누를 때
> 어디를 열려고 하는지 모른다."**

②가 ①의 내용이다. 불편은 **보는 문제**와 **여는 문제**가 따로 있는 것이 아니라,
**여는 곳의 정체가 안 보여서 누르는 손이 멎는** 한 가지다.

사이드바에서 창을 여는 모든 경로는 **포커스 칸**으로 간다 (`WINDOW_SLOTS_SRS`
FR-WSL-54). 규칙은 명확하고 바뀌지 않는다. 문제는 **그 규칙의 목적어**(지금 어느
칸이 포커스인가)를 누르는 순간에 알 수 없다는 것이다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 표시 | 상단바에 서는 칸 마커. 무엇을 그리고 무엇을 안 그리는가 |
| **B** 조작 | 마커를 눌러 칸을 옮긴다 |
| **C** 색·크기 | 토큰에서 파생하는 값 |
| **X** 인터페이스 | 새 DOM·상수의 이름 계약 |

**미포함:** §6 비목표. 특히 **슬롯 모델·여는 경로(FR-WSL-54)·사이드바 목록은 한
줄도 바뀌지 않는다.** 이 SRS 는 **이미 있는 사실을 어디에 보이게 하느냐**만 다룬다.

### 1.3 개정하는 기존 요구 (Supersedes)

| 조항 | 출처 | 개정 내용 |
|---|---|---|
| FR-STB-12 | SLOT_TITLE_BOUNDARY_SRS | **개정하지 않는다.** `#window-name` 은 칸이 여럿일 때 종전대로 빈다. 마커는 **별도 요소**로 그 옆에 선다 — 이름을 되풀이하지 않으므로 D-1(*"어느 칸의 것인지 매번 판정해야 한다"*)과 충돌하지 않는다 |
| FR-CHR-9 | UIUX_OVERHAUL_SRS (D-6) | 상단바가 담는 것이 **전역 여섯**에서 **일곱**이 된다. 칸 배치는 전역이므로 D-6 의 축(*"무엇에 관여하는가"*)에 그대로 들어맞는다 |

## 2. 현행 분석 (Current State)

### 2.1 사이드바 목록은 칸을 모른다

    grep -c "slot" web/js/ui/sidebar-list.js   →  0

목록을 그리는 블루프린트(`UX_REVISION_SRS` FR-BLP-*)에 슬롯이라는 낱말이 한 번도
없다. 목록은 **워크스페이스의 창 전부**를 한 줄씩 낼 뿐이다.

### 2.2 활성 표시가 하나뿐이다

`sidebar-tabs.js` 의 창 목록 서술자:

    currentKey: app => app.ws.activeWindow      (:57)
    active:     s.id === app.ws.activeWindow    (:68)

`ws.activeWindow` 는 **포커스 칸의 창** 하나다. 칸이 넷이면 화면에 창 넷이 떠 있는데
목록은 하나만 활성으로 칠하고, 나머지 셋은 **"안 열린 창"과 구별되지 않는다.**

### 2.3 칸이 여럿이면 상단바 왼쪽이 **비어 있다**

`renderer-chrome.js:102` (FR-STB-11·12·14):

    const multi = !this.app.isMobile && this.app.slotCount() > 1;
    document.getElementById('window-name').textContent = multi ? '' : this._rWinTitle(a);

비우는 **이유**가 *"칸 머리글이 그 자리를 이어받기 때문"* 이다. 그래서 칸이 여럿일
때 창의 소속을 말하는 자리는 `#area` **안쪽뿐**이고, 상단바와 사이드바는 둘 다
침묵한다.

**마커가 필요한 조건(`multi`)과 그 자리가 비는 조건이 정확히 같다.**

### 2.4 마우스로 칸을 옮기는 명시적 수단이 없다

칸 전환은 pane 을 눌러야 일어난다 (`renderer-pane.js:590`). 그 클릭은 터미널에
입력으로 갈 수도 있는 자리다. 칸 `±`(`#slot-add`·`#slot-remove`)는 칸을 **만들고
없앨** 뿐 **고르지** 않는다.

### 2.5 이미 있는 재료

| 필요한 답 | 이미 있는 것 |
|---|---|
| 칸이 몇인가 | `app.slotCount()` |
| 어느 칸이 포커스인가 | `app.slotFocused()` |
| 그 칸으로 옮기려면 | `app.slotFocusTo(i, opts)` |
| 칸의 방향·비율 | `app.slotDir` · `_slots.sizes` (이 SRS 는 **쓰지 않는다** — FR-SMK-4·5) |

새 모델이 필요 없다. 화면이 이미 아는 것을 **다른 자리에서 되풀이할** 뿐이다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 A — 표시

**FR-SMK-1** 마커는 **상단바(`#topbar`) 왼쪽**, `#window-name` **바로 다음**에 선다.

**FR-SMK-2** 마커가 서는 조건은 **`!isMobile && slotCount() > 1`** 이다 — 2.3 의
`multi` 와 **같은 식**이다. 칸이 하나면 마커는 없다.

> **단일 칸 화면은 한 픽셀도 바뀌지 않는다.** 모바일에는 칸이 없다 (FR-WSL-60).

**FR-SMK-3** 칸 하나당 사각형 하나. **인덱스 오름차순으로 왼쪽에서 오른쪽**이다.

**FR-SMK-4** 사각형은 **가로로 나열한다.** `slotDir` 이 `vertical` 이어도 가로다.

**FR-SMK-5** 사각형의 폭은 **균등**하다. `_slots.sizes` 의 비율을 반영하지 않는다.

**FR-SMK-6** **포커스 칸은 채운 사각형, 나머지는 빈 사각형**이다. 이 둘이 마커가
가진 상태의 전부다.

**FR-SMK-7** 사각형 안에 **아무것도 적지 않는다.** 창 이름·칸 번호·알람·샌드박스
표시 그 무엇도 넣지 않는다.

> 근거(D-4): 칸 머리글이 이미 이름을 말한다 (FR-STB-12). 마커가 답하는 물음은
> *"어느 칸인가"* 하나이고, 그 답에 글자는 필요 없다.

**FR-SMK-8** **빈 칸**(창이 없는 칸, `slot-empty`)도 같은 규칙을 따른다. 창의 유무로
사각형의 모양이 갈리지 않는다.

> 근거: 마커가 재는 것은 **칸**이지 창이 아니다. 창의 유무는 칸 머리글이 이미
> 말한다 (`FR-STB-5` — 빈 칸의 머리글은 `창 없음`).

**FR-SMK-9** 마커는 **칸 수와 포커스를 즉시 따라간다.** 칸을 더하거나 없애면 사각형
수가 따라 바뀌고, 포커스가 옮겨가면 채움이 따라 옮겨간다.

### 3.2 묶음 B — 조작

**FR-SMK-10** 사각형을 누르면 **그 칸이 포커스가 된다** — `app.slotFocusTo(i)`.

**FR-SMK-11** 이미 포커스인 칸을 눌러도 **아무 일도 일어나지 않는다.** `slotFocusTo`
가 이미 그 자리에서 되돌아간다 (`app-slots.js`).

**FR-SMK-12** 각 사각형은 `<button>` 이며 **킷 등급을 받는다** (`KIT_APPLICATION_SRS`
FR-KIT-21). 예외표에 올리지 않는다.

**FR-SMK-13** 이름과 현재 표시.

| 속성 | 값 |
|---|---|
| `aria-label` | 카탈로그를 지난다 (`data-i18n-label`). 칸 번호를 포함한다 |
| `aria-current` | 포커스 칸만 `"true"` |

> `aria-label` 은 **낱말 키로 먼저 선다.** 단축키 표를 기다리지 않는다 — 기다리면
> `if(d.i18nShortcut && !sc) continue` 에 걸려 이름 없이 남는다 (UIUX 인계 ⑥).

**FR-SMK-14** 키보드로 닿는다. 탭 순서에 들고 포커스 링을 갖는다 (킷 등급이 준다).

**FR-SMK-15** **새 단축키를 만들지 않는다.** 칸 이동 단축키는 이미 있다
(`slotNavigate`). 마커는 **마우스 경로**를 더한다.

### 3.3 묶음 C — 색과 크기

**FR-SMK-20** 색은 **토큰에서 온다. 새 토큰을 만들지 않는다.**

| 상태 | 색 |
|---|---|
| 포커스 (채움) | `var(--accent)` |
| 비포커스 (빔) | 테두리 `var(--text-muted)`, 배경 없음 |

> 근거(D-5): 포커스 칸의 머리글이 이미 `--accent` 다 (FR-STB-26). **포커스의 언어는
> 이미 서 있고**, 마커가 그것을 다른 색으로 말하면 사용자는 둘을 다른 종류의
> 정보로 읽는다.

**FR-SMK-21** 크기는 **상수에서 온다.** 값을 CSS 에 흩지 않는다.

**FR-SMK-22** 마커는 상단바의 높이를 **바꾸지 않는다.** 지금 비어 있는 자리 안에
든다 (2.3).

### 3.4 묶음 X — 인터페이스

**FR-SMK-30** 이름 계약. 아래는 e2e·CSS 가 딛는 표면이다.

| 종류 | 이름 | 비고 |
|---|---|---|
| DOM | `#slot-marker` | 마커의 그릇. `desktop-only` |
| DOM | `.slot-marker-cell` | 사각형 하나. `<button>` |
| 데이터 | `data-slot` | 그 사각형의 칸 인덱스 (`#area` 의 `.slot` 과 같은 이름) |
| 상수 | `SLOT_MARKER_CELL_PX` | 사각형의 폭 |
| 상수 | `SLOT_MARKER_GAP_PX` | 사각형 사이 간격 |

**FR-SMK-31** 기존 이름은 **바뀌지 않는다** — `#window-name`·`.slot-head`·
`.slot-handle`·`.slot-ctl`·`#slot-add`·`#slot-remove`. 기존 e2e 가 그 위에 서 있다.

**FR-SMK-32** `#window-name` 의 **동작은 바뀌지 않는다.** FR-STB-11·12·14 가 그대로
유효하다. 마커는 그 요소를 건드리지 않는 **별도 요소**다.

## 4. 설계 결정 (Design Decisions)

**D-1. 자리는 상단바 왼쪽이다.** → FR-SMK-1 의 근거.

| 안 | 결과 | 채택 |
|---|---|---|
| 사이드바 상단 | 목록과 물리적으로 붙어 결합이 가장 강하다. 그러나 세로 한 줄을 새로 내고, 사이드바를 접으면 사라지며, D-6 축과 어긋나 개정이 필요하다 | 기각 |
| 상단바 오른쪽 (`− Slot +` 옆) | 칸에 관한 것이 한자리에 모인다. 그러나 사이드바(왼쪽)에서 화면 대각선으로 눈이 이동한다 | 기각 |
| **상단바 왼쪽 (`#window-name` 옆)** | **칸이 여럿일 때만 비는 자리**를 쓴다 — 자리 비용 0. 사이드바 바로 위라 눈 이동이 짧다. D-6 축에 맞다 | **채택** |

**D-2. 축소판을 버리고 균등 가로로 간다.** → FR-SMK-4·5 의 근거.

처음 설계는 `#area` 의 **축소판**이었다 — 방향(`slotDir`)과 폭 비율(`sizes`)을 그대로
줄여 그린다. 화면과 모양이 같으니 번호를 읽지 않고 위치로 잇는다는 것이 값어치였다.

**상단바 높이가 그것을 막는다.** 상단바는 32px 가로 줄이고, 세로 분할에서 칸 넷을
그 안에 위아래로 쌓으면 칸당 4~5px 다 — 포커스 구분도 클릭 과녁도 성립하지 않는다.
세로 분할을 가로로 눕혀 그리면 **축소판이 축소판이 아니게 되므로** 값어치가 사라지고,
상황에 따라 자리를 옮기는 것은 더 나쁘다.

> **사용자 결정 (2026-09-22).** *"축소판으로 하지 말고 가로 분할로 하며 실제 사이즈와
> 상관없이 균등 분할로 가자. 상단바에 적용하고 내부에 뱃지는 넣지 않는다. 단순
> 표시이다. 포커스는 꽉 찬 사각형, 포커스가 아니면 빈 사각형으로."*

**치르는 값:** 세로 분할일 때 화면의 **위→아래**가 마커의 **왼→오른쪽**으로 읽힌다.
→ §7 R-1.

**D-3. 누를 수 있다.** → FR-SMK-10 의 근거. 마커가 표시만 한다면 2.4 의 구멍(마우스로
칸을 고르는 수단이 없다)은 그대로 남는다. 사각형은 이미 칸을 가리키고 있으므로,
그것을 과녁으로 삼는 것이 새 UI 없이 구멍을 메우는 가장 싼 길이다.

**D-4. 사이드바 행의 칸 뱃지는 이번 범위가 아니다.** 인터뷰에서 후보였다 —
각 행에 그 창이 떠 있는 칸을 적어(`● dev-server ①`) *"이미 다른 칸에 떠 있는 창을
모르고 또 여는"* 문제를 함께 풀자는 것. `app.windowVisible(id)` 가 답을 이미 갖고
있어 구현도 싸다.

> **사용자 결정 (2026-09-22):** *"3. 제거."* — 이번 범위는 **누르기 전에 안다**까지다.

**D-5. 화면 쪽 표현은 손대지 않는다.** 검토하고 기각한 둘:

| 안 | 기각 이유 |
|---|---|
| 포커스 칸을 **칸 전체 테두리**로 두른다 | 포커스 강조색이 이미 있다 (FR-STB-26·FR-WSL-35). **같은 채널을 키우는 것**뿐이고, 여러 창을 동시에 보는 화면을 더 시끄럽게 한다 |
| 비활성 칸을 **어둡게** 깐다 (iTerm2 식) | *"여러 창을 동시에 보는 목적"* 과 정면으로 어긋난다 (사용자 결정) |

**D-6. 오버레이로 부르는 목록은 기각됐다.** tmux `choose-tree`·`Cmd+P` 계열은 자리를
쓰지 않고 **뜨는 위치가 곧 목적지**라 두 문제를 함께 풀지만, *"오버레이를 부르는 데
동작이 추가로 든다"* (사용자 결정). 상시 보이고 한 번 클릭으로 열린다는 지금의 성질이
요구의 전제다.

| TC-SMK-15 | FR-SMK-12·20 | `make gates` 의 버튼 등급·하드코딩 색·포커스 표시 검사를 지난다 |

> **모바일 검증은 `toBeHidden()` 으로 한다** — 요소는 남고 CSS 가 감춘다 (인계 ⑪).

### 5.1 개정이 필요한 기존 테스트

없을 것으로 본다 — 새 요소이며 기존 이름을 건드리지 않는다 (FR-SMK-31·32). 구현 중
`#topbar` 의 자식 수·순서를 세는 검사가 있으면 그때 개정한다.

**`check-button-kit.mjs` 의 예외표가 `web/index.html` 의 줄 번호를 든다.** 마커
마크업이 그 줄을 밀면 숫자를 함께 고친다 (인계 ⑦).

## 6. 비목표 (Non-goals)

1. **슬롯 모델을 바꾸지 않는다.** 칸 수·방향·비율·영속·포커스 규칙은
   `WINDOW_SLOTS_SRS` 그대로다.
2. **여는 경로를 바꾸지 않는다.** FR-WSL-54(사이드바의 모든 경로는 포커스 칸에 연다)는
   유효하다. 이 SRS 는 그 규칙을 **보이게** 할 뿐이다.
3. **사이드바 목록을 바꾸지 않는다.** 행 뱃지·칸별 구획·목록의 소속(워크스페이스의
   것인가 칸의 것인가) 모두 이번 범위 밖이다 → D-4.
4. **마커를 드롭 과녁으로 만들지 않는다.** *"행을 특정 칸에 끌어다 놓기"* 는 별도
   결정이다.
5. **칸 머리글·상단바 창 이름·칸 `±` 를 바꾸지 않는다.**
6. **새 단축키를 만들지 않는다** → FR-SMK-15.

## 3. 이 세션이 값을 치르고 안 것

**다음 세션이 같은 값을 다시 치르지 않게** 적는다.

### 3-1. 감사가 화면에서 센 수는 **표본이다** — 다섯 번 반복됐다

| 감사가 적은 것 | 실측 | 배수 |
|---|---:|---:|
| 킷 없는 버튼 "6종 98개" | **73자리 · 26파일** | — |
| 빈 상태 "다섯" | **13** | 2.6× |
| 섹션 머리글 "여섯 자리" | **9규칙** | 1.5× |
| 스크롤 표면 "33/34" | 둘 다 맞다 (정의가 달랐다) | — |
| 키캡 (언급 없음) | **둘** (`.sc-key` + 죽은 `kbd`) | — |

감사의 수는 **1440×900 한 화면에서 보이던 인스턴스**다. 소스 자리로 세면 다르다.

이것은 이 저장소가 **이미 기록한 교훈의 반복**이다 — `FR-A11Y-28`:
*"인계서가 적은 여섯은 **표본**이었고 실측은 17종이었다 — 손으로 적은 목록을 보는
검사는 손으로 적은 만큼만 본다."* 그리고 `DESIGN_TOKENS_SRS` §7.6 잔여표가 같은
모양이었다.

**B4 에서도 같다.** §2.2 는 "상단바 9개" 라 적지만 실측은 **20개**다. 그래서 이
세션은 §0-3 에 실측을 넣어 두었다 — **그 표를 써라.**

### 3-2. 요구가 도달 대상을 **손으로 열거하면** 그 밖은 요구된 적이 없다

`FR-A11Y-16` 이 *"창 목록 항목 · 분할 칸 탭 · 탐색기 행"* 셋만 열거한다. 그 셋은
구현됐고 **git 뷰 여덟과 스크롤 표면 47개는 요구된 적이 없다.** 그래서 키보드
도달을 별도 작업으로 뺀 것이고(D-KIT-8), 착수점이 표면이 아니라 **요구의 세는
방법**이라고 적어 두었다 (`KIT_APPLICATION_SRS` §3.8).

### 3-3. **내가 쓴 검사가 다섯 번 아무것도 재지 않았다**

이 세션에서 가장 값진 발견이다. 전부 코드를 되돌려 **RED 를 실제로 본 뒤** 고쳤다.

| 검사 | 왜 아무것도 안 쟀나 |
|---|---|
| `TC-KIT-7` | e2e 안에서 **마크업을 스스로 지어** 기대값과 견줬다 — 변경 전에도 초록 |
| `TC-KIT-6a` | `b.kit` 로 **킷 등급인 것만 걸러서** *"이미 킷인 것이 킷이다"* 만 확인 |
| `TC-KIT-9` | `getComputedStyle(el, ':focus-visible')` — 의사**클래스**라 빈 문자열이 온다 |
| `TC-CMP-4` | `.ui-switch` 가 없으면 **빈 배열끼리** 견준다 |
| `TC-CMP-3` | 앞 스펙이 남긴 ACL 줄에 따라 갈렸다 (반복 행의 체크박스는 설정이 아니다) |

**규약: 검사를 쓰면 코드를 되돌려 RED 를 본다.** 초록인 검사와 재고 있는 검사는
다르다. `git stash push web/` → 검사 → `git stash pop` 이 이 세션의 방법이었다.

### 3-4. 감사 보고서를 **네 자리에서 정정했다**

1. 스크롤 표면 "33 vs 34" — 둘 다 맞다. CSS 만 보면 34, `.dr-body` 는 JS 가
   클래스를 단다
2. *"`.ui-btn` 이 CSS 전체에서 유일한 버튼 포커스 규칙"* — **틀렸다.** 여섯이다
3. `.fe-offer-no` 의 원인이 타입 선택자 `.fe-offer button` — **그 규칙은 이미
   없다.** 실제 원인은 **규칙이 하나도 없는 맨 `<button>`**(UA 기본)
4. `.git-ref.head` 가 글자색만 — **맞았다**

**B4 에서도 보고서를 그대로 믿지 마라.** 특히 §2.2 의 "9개" 와 §2.3 의 목록.

### 3-5. **죽은 규칙 둘**을 컴포넌트를 세우다 찾았다

- `.gpp-note` — 철회된 `FR-GIT-271`(*"Push preview ⊘ 철회"*)의 잔해
- `kbd` — 오지 않은 치트시트(`production/03-uiux.md:185`)를 위해 미리 넣은 규칙

둘 다 게이트가 아니라 **이주하다** 드러났다. 새 게이트는 *"아무도 만들지 않는
규칙"* 을 따로 보고하게 했다 (`check-scrollbar.mjs`).

### 3-6. 명시도 — 킷은 **먼저** 오므로 다투면 진다

`input[type="checkbox"]`(0-1-1)가 `.ui-switch`(0-1-0)를 이겨 스위치가 14px 네모로
그려졌다. 킷은 `<link>` 순서상 먼저 오고(FR-UIK-1) `!important` 가 없으므로
(FR-UIK-11) **명시도가 같거나 낮으면 언제나 진다.**

**해법은 명시도를 올리는 것이 아니라 상대의 대상을 좁히는 것이다** —
`input[type="checkbox"]:not(.ui-switch)`. B4 의 색 작업에서도 같은 일이 난다.

### 3-7. **사용자 접수를 감사 제안으로 뒤집지 마라** — 전량 e2e 가 잡았다

`AUDIT-uiux.md` §4.2 가 *"설정 모달의 고정 높이를 걷고 내용에 맞춰 늘게 둔다"* 고
제안했고 이 세션이 `FR-CMP-83` 으로 옮겨 적었다. 그것이 뒤집는 대상이
**`UI_KIT_SRS` FR-UIK-12 (2026-09-08 사용자 접수)** 였다.

- **부분 실행 74건에서는 초록이었다.** 전량 1,742건에서 `poll-interval` PIS19 가 졌다
- 사용자 확인: *"설정모달은 기존 고정을 유지"* → `daa83ce1` 로 되돌리고 D-CMP-6 기록

**감사 보고서의 제안 중 기존 요구와 부딪히는 것이 더 있을 수 있다.** SRS 를 쓸 때
제안마다 *"이것이 뒤집는 기존 요구가 있는가"* 를 한 번 물어라.

### 3-8. **`make e2e` 의 종료 코드를 놓쳤다** — 인계서가 경고한 그 함정

배경 작업이 `exit code 0` 으로 보고했는데 그것은 뒤따른 `echo` 의 것이었고
`make e2e` 는 **2** 였다. 파이프를 안 물렸는데도 `; echo` 패턴이 같은 결과를 냈다.

**샤드별 요약을 직접 세어라:**

```
for i in 1 2 3 4 5 6 7 8; do echo -n "샤드 $i: "; \
  LC_ALL=C grep -a "샤드 $i/8" <로그> | LC_ALL=C grep -aoE '[0-9]+ (passed|failed|flaky)' | tr '\n' ' '; echo; done
```

`✘` 로 grep 하면 **안 잡힌다** (색 코드가 섞인다). `N failed` 를 세라.

### 3-9. 레이아웃 기준선이 **초록인 채 측정을 그만둔다**

`ui-layout-defaults` 의 대조는 `if (!b) continue` 로 **양쪽에 있는 키만** 본다.
키가 클래스 목록이므로 **킷 클래스를 더하면 그 자리가 조용히 빠진다.**

이 세션의 절차 (B4 도 그대로 써라):

1. `cp e2e/baseline/ui-layout.darwin.json /tmp/bc.json`
2. `LAYOUT_BASELINE=write npx playwright test ui-layout-defaults`
3. 사라진 키를 **킷 클래스 차이로 짝짓고** 값 변화를 본다
4. 커밋된 기준선에 **이름만 바꿔** 반영한다 (전체 재생성 금지 — 무관한 드리프트
   116건을 흡수해 남의 회귀를 덮는다)
5. `inset` 은 판을 타므로(§9) linux·win32 에 **값을 옮기지 않는다**

실적: B2-D 에서 darwin 192 · linux/win32 각 132개 이름 바꿈.

### 3-10. e2e 의 알려진 부하 flake

`make e2e` 는 flaky 를 **단독 3회씩 다시 돌아** `부하 N · 결함 0` 으로 판정한다.
이 세션에서 그 판정을 받은 것: `git-worktrees` V151 · `git-menu` N3 ·
`git-branch-actions` BR8 · `editor-link` L3 · `git-hunk` V-DHB-6.

**회차마다 다른 스펙이 걸린다** — 그것이 부하 flake 의 표식이다. 같은 것이 반복
되면 결함을 의심해라 (`DM_E2E_STRICT_FLAKY=1`).

## 4. 변하지 않는 규약

`CONTRIBUTING.md` 가 원본이다.

1. **SRS → 테스트 → 코드.** RED 를 **실제로** 보고 나서 구현한다. 이미 구현했다면
   `git stash push web/` 로 코드만 되돌려 확인한다 (§3-3)
2. **게이트를 느슨하게 만들어 통과시키지 않는다.** 다만 **재는 대상이 달라진 것**은
   느슨하게 만드는 것이 아니다 — 이 세션이 `TC-BGK-11` 에서 그렇게 했고
   (`CONVENIENCE_SRS` V-BGK-11 에 근거를 적었다) 판정 기준은 *"요구의 원문이
   무엇을 금지하는가"* 다
3. **새 게이트를 세우면 탐침으로 검출을 확인하고 지운다.** 잡아야 하는 것과
   **잡으면 안 되는 것**을 둘 다
4. **동작을 바꾸면 근거 문서를 같은 변경에서 고친다.** 이전 / 새 / 이유 셋
5. **커밋 메시지에 FR 번호를 단다. AI 서명 금지**
6. **생성물을 직접 고치지 않는다** — `docs/external/errors.md` · `docs/internal/decisions.md`
7. **색은 팔레트를 바꾸지 않는다** (`DESIGN_TOKENS_SRS` FR-TOK-16). 테마 **54종**,
   모든 색은 기존 토큰의 조합. **새 hex 를 넣지 마라** — B4 의 색 작업이 정확히
   이 제약 위에서 돈다

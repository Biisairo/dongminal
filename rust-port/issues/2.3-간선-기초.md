  - **Go 와 다르게 한 결정**
    1. 세션 재개를 끔(서버 티켓 0, 세션 저장 없음). rustls 는 재개 때 검증기를 부르지 않기 때문. Go 는 재개를 받되 VerifyConnection 으로 다시 거른다 — 관측 결과(해제한 짝 거절)는 같다.
    2. 시한: TLS 핸드셰이크 10s, hyper `header_read_timeout` 10s(keep-alive 대기에도 걸림 — Go IdleTimeout 120s 보다 엄격하지만 Go 간선 클라이언트는 keep-alive 를 끄므로 관측 차이 없음), Go ReadTimeout(15s) 대신 핸들러 시한 20s, 넘기면 응답 없이 연결을 끊음. 헤더 상한 16KiB+4096(hyper max_buf_size).
    3. hyper 는 101 응답에 Date 머리를 붙인다(Go 원시 101 에는 없음).
    4. Client 는 `Accept-Encoding: gzip` 을 보내지 않는다(받은 gzip 을 풀지 않으므로). 그 밖의 머리(Host·User-Agent `Go-http-client/1.1`·Content-Type·`Connection: close`)는 Go 와 같다.
    5. 신원 읽기: 키는 ECDSA P-256(PKCS8·SEC1)만 받는다. 다른 공개키면 `tls: private key type does not match public key type`. 키 해석 실패는 `tls: failed to parse private key` 까지만(Go 의 asn1 상세 문구는 없음), 인증서 해석 실패는 `x509: malformed certificate`. PEM 머리줄은 단순 처리. 그 밖의 X509KeyPair 문구는 Go 와 같다(시험함).
    6. rcgen 인증서에는 SubjectKeyIdentifier 확장이 붙는다(Go 비 CA 인증서에는 없음). 지문(SPKI SHA-256)·CN·기간·KeyUsage(critical)·EKU·BasicConstraints 는 같다.
    7. 닿지 못함 상세: 1.6 의 `neturl_err::UrlError::new("POST", url, 사유)` 로 `Post "<url>": …` 를 만든다. `from_reqwest` 는 쓰지 못한다 — Client 가 클라이언트 인증서·지문 고정·dial.sock 연결 때문에 reqwest 가 아닌 hyper 를 직접 쓰기 때문. 사유 규칙(`dial tcp <addr>: connect: <errno>`, rustls 는 `tls: …`, 끊긴 응답 `EOF`, 시한 `context deadline exceeded (Client.Timeout exceeded while awaiting headers)`)은 neturl_err 와 맞춤. 이름 해석 실패 문구는 OS 문구 그대로.
    8. 핸드셰이크 실패 로그 줄의 오류 부분은 rustls 문구다(줄 형식·1분 묶기는 Go 와 같음).
    9. bind 에 IPv6 zone(`fe80::1%en0`)이 있으면 std 가 열지 못한다(검증은 Go 처럼 받음).
  - **남은 위험**: windows·linux 교차 clippy 는 ring 의 C 교차 컴파일러가 없어 못 함(조정자 결정대로 8.3 에서). crate 안에 OS 분기 코드는 없다(시험의 unix 권한 확인뿐). `cargo deny` 실패 항목(chrono RUSTSEC-2026-0543, notify 의 CC0/BSL 라이선스, 골격 crate 의 와일드카드)은 기존 것이고 새 의존성(p256·rcgen·x509-parser)과 무관. dm-gocompat 를 `reqwest` 기능으로 켜서 이 crate 가 reqwest 를 끌어온다.

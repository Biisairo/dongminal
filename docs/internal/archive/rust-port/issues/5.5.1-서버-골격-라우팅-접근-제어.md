# 5.5.1 httpapi: 서버 골격·라우팅·접근 제어

## 목표

5.5 의 하위 이슈. `internal/webserver/httpapi` 의 다음 파일과 해당 `_test.go` 를 옮긴다(crate `dm-webserver-httpapi`). 프로덕션 약 3100줄.

server.go(`Run` 의 리바인드·진단 회차 배선 제외) · server_state.go · server_middleware.go · deps.go · reqgate.go · reqid.go · access.go · access_api.go · access_denied.go · access_matcher.go · access_normalize.go · httperr.go · fail.go · codefail.go · handlers_api.go 의 라우트 표·`handleAPI`·`apiPing` · toolhub_req.go · handlers_toolio.go(공용 도우미 `toolIOReady`·`resolveToolID`·`decodeJSONBody`·`writeJSON`·`writeToolIOError*`·`agentEnvelope`·`deliverToTool` 과 종단 output·input·message)

- `Server`·`Config`·`Deps`(주입 trait 전부)·`New`·`Handler()` 미들웨어 사슬(reqID → logging → accessGate → requestGate → recover → mux)을 세운다.
- `/api/git/` 갈래는 라우트 표를 훑지 않고 넘기는 자리만 둔다(주입형 처리기 `Option`). gitapi 배선은 5.5.10 이 한다.
- `New` 의 설정 저장소 기본값(`newSettingsStore`)은 5.5.8 이 채운다 — 그때까지는 `Deps.settings` 주입만 받는다.
- 다른 하위 이슈가 공용으로 쓰는 도우미(도구 입출력, 본문 디코드, 오류 방언)를 여기서 낸다.

## 완료 조건

5.5 와 같다. 라우트 표(`apiRoutes`)와 `Server` 필드는 이 하위 이슈가 옮긴 핸들러·상태까지만 더한다. 다른 하위 이슈의 핸들러를 미리 만들지 않는다.

### 공개 API 요약 (다음 하위 이슈가 쓰는 자리)
- `Server::new(Config, Deps) -> Arc<Server>`, `Server::serve(req, remote: SocketAddr) -> Response`(합성 루트·5.5.8 `Run` 이 연결마다 부른다), `start_access_refresh(CancellationToken)`.
- `Config { port, data_dir: PathBuf, allowed_hosts, version }` — 5.5.8 이 정적 자산 등 필드를 더한다.
- `Deps { tools: Option<Arc<dyn ToolHub>>, commands, tool_io, work_index, git: Option<Arc<dyn GitHandler>> }`. **각 하위 이슈가 자기 주입 필드와 trait 을 여기에 더한다**(Go 의 Deps 필드 전부를 미리 만들지 않았다).
- `ToolHub` trait(Go `toolhub.ToolHub`+`DaemonHub` 전 메서드, 동기) + `ToolError{ToolCap,NotFound,Other}`·`ToolIdentity`·`Unsubscribe`. 2.2.3 결정대로 소비자 쪽 trait 이다 — 합성 루트가 toolclient·ToolManager 를 감싸 구현한다. 블로킹 호출이라 오래 걸리는 것(create 60s 등)은 핸들러가 `spawn_blocking` 으로 감싼다.
- `GitHandler` trait — 5.5.10 이 gitapi `GitServer::handle` 를 감싼다(`handle_api` 가 `/api/git/` 을 표를 훑지 않고 넘긴다).
- crate 안 공용: `req::{Req, Handler, BoxFut}`(핸들러 모양은 gitapi 와 같다: `fn(&Server, &mut Req) -> BoxFut<Response>`), `routes::API_ROUTES`(Go 표 순서대로 자기 줄을 끼운다, `h!` 매크로), `serve::mux_table()`(`/ws`·`/api/commands` 등 mux 패턴은 5.5.2·`/` 는 5.5.8 이 더한다), `httperr::{http_err, fail, fail_read, read_body_err, code_fail, read_json_body, read_body_http, decode_json_body, write_json, write_tool_io_error(_code), JSON_BODY_LIMIT}`, `settings_etag::{settings_tag, settings_stale}`, `access_denied::CSP_REST`(static.go 의 `cspRest` — 5.5.8 이 재사용), `ansi::{strip_ansi, go_string}`, `Server::{tools(Some(&r)), tool_io_ready, resolve_tool_id, resolve_sender, resolve_tool_strict, deliver_to_tool}`, `toolio::{agent_envelope, quote_envelope, envelope_sender}`, 진단 계수 `access_api::ACCESS_DENIES`·`reqgate::REQUEST_DENIES`(5.5.8 `/api/diag`).

### Go 와 다르게 한 내부 결정
- 미들웨어 사슬은 `http.Handler` 겹 대신 `serve_addr → logged → gated → recovered → mux` 함수 사슬이다. 핸들러는 따로 tokio task 로 돌고(gitapi 와 같은 방식), 패닉은 `JoinError` 로 잡아 500 `internal error` 다. 응답을 기다리던 쪽이 떠나면 `Req.ctx`(CancellationToken)가 취소된다.
- Go `http.Server`·`ServeMux` 가 하던 일을 serve 에 옮겼다: 경로 퍼센트 인코딩 오류 → `400 Bad Request`(Connection: close), 정리되지 않은 경로·하위 트리 루트의 307 리다이렉트, `404 page not found`, `Content-Type` 이 없는 크기 고정 본문의 `DetectContentType` 짐작(흐르는 본문은 핸들러가 형식을 정한다).
- 업그레이드(101) 응답은 접근 로그에 Go 처럼 200 으로 적는다. 기간은 Go(WS 수명 전체)와 달리 업그레이드 응답까지다(로그 문구만 다르다).
- `ToolHub` 는 동기 trait 이다(toolclient 가 동기 API). `Deps` 는 5.5.1 이 쓰는 필드만 있다.
- netip·url.Parse·net.SplitHostPort 의 필요한 부분을 crate 안 `netx` 에 두었다(edge·dmenv 가 netip 판정을 각자 둔 선례와 같다). Go 로 뽑은 표로 시험한다. gocompat 으로 옮길 후보다.
- JSON 으로 내는 터미널 출력의 잘못된 UTF-8 은 Go 처럼 바이트마다 U+FFFD 다(`ansi::go_string`; Rust `from_utf8_lossy` 는 묶어서 하나로 바꾼다). gocompat 에 같은 도우미가 없어 crate 안에 두었다 — gocompat 으로 옮길 후보다.
- 호스트명 해석은 std `ToSocketAddrs` 를 시한 스레드로 감싼다. 실패 문구는 Go `*net.DNSError` 모양(`lookup <이름>: no such host`, 시한 초과 `i/o timeout`)으로 맞췄다.

### 남은 위험
- 호스트명 해석 실패 문구는 실패 종류(NXDOMAIN 외의 resolver 오류)에 따라 Go 와 다를 수 있다(`/api/access` 의 entries[].error 로 화면에 보인다).
- Go `strings.ToLower` 와 Rust `to_lowercase` 는 일부 비 ASCII 글자(İ 등)에서 다르다 — Host·별명 비교에만 쓰이며 정상 이름(LDH)은 ASCII 다.
- 흐르는 본문(크기를 모르는 본문)에 `Content-Type` 을 짐작하지 않는다 — 그런 핸들러는 반드시 형식을 적어야 한다(5.5.2 SSE·WS 는 적는다).
- `record_run_message`(Go handlers_runs_graph.go)는 Run 저장소 배선 전이라 지금은 아무 일도 하지 않는다(Go 의 `Runs == nil` 갈래와 같다) — **5.5.5 가 본문을 채운다**.

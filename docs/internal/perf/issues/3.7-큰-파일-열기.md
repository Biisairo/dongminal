# 3.7 큰 파일 열기

## 목표

2만 3천 줄 JS 를 편집기로 열 때 CodeMirror 언어 파서 79 ms, 미니맵 `edMinimapScale`+canvas `fillText` 38 ms, 첫 트랜잭션 21 ms 작업이 생긴다(`perf/SPA_PROFILE_2026-11-24.md` §2·§3). 언어 파서의 시간 나눔(작업 예산) 설정을 확인·적용하고, 큰 파일에서 미니맵 그리기를 나누거나 늦춘다.

## 완료 조건

- 큰 파일 열기의 16 ms 초과 작업 감소 측정(이전/새), 편집·미니맵 동작 유지 시험 한두 개. 3.3 과 같은 편집기 영역이므로 cm-find.js 는 건드리지 않는다. 전체 시험 금지.

## 진행 기록

### 2026-11-24 기준선 측정과 막힌 이유 (agent-pf-3-7)

**잰 조건**: `pf/3.7` HEAD(24fcf881) 바이너리, 격리 인스턴스(포트 60610), Playwright Chromium 헤드리스(GPU), 창 1600×1000. 3.1 의 `profile-spa.mjs` 를 복사해 vendor 프레임과 가장 바깥 프레임을 함께 적게 고쳤다(`/private/tmp/pf3.7/profile.mjs`, 커밋하지 않음). 큰 파일은 3.1 과 같은 내용(2만 3천 줄)이다. 3.2·3.3 이 같은 시각에 빌드·측정했다. 두 번 재서 값이 비슷했다.

| # | 작업 | 1회 / 2회 (ms) | 무엇이 시간을 썼나 |
|---|---|---|---|
| 1 | 파일 열기 | 69 / 73 | `edOpenFile` — `tabsFit`·`apiSend`·`_placeLayout`. 편집기 밖이다 |
| 2 | 뷰 만들기 | 30 / 35 | 미니맵 `TextState.updateMapImpl`(문서 전체 줄을 훑는다)·`edCmLspAttach`·GC |
| 3 | 첫 측정 프레임 | 44 / 47 | 미니맵 `ownLayout`→`lineColumns`(문서의 모든 글자를 센다, `cm-scrollbar.js` read 가 부른다) + `drawLine`(fillText) |
| 4 | 언어 붙이기 트랜잭션 | 24 / 24 | `@codemirror/language` 의 처음 파싱. 예산 `Work.Apply = 20 ms` 상수 |
| 5 | 유휴 콜백 파싱 | 74 / 72 | `@codemirror/language` 의 `ParseWorker.work` |

**확인한 사실**

- 언어 파서의 시간 나눔은 이미 켜져 있다. 설정으로 바꿀 수 있는 값은 없다(예산은 모듈 안의 상수다). Chromium 에는 `navigator.scheduling.isInputPending` 이 있다. 그래서 CM 은 유휴 콜백 한 번에 **최대 100 ms** 를 쓰고, 입력이 들어오면 멈춘다(`min(chunkBudget, 100, isInputPending ? 1e9 : max(25, timeRemaining-5))`). 5번의 72 ms 는 이 설계대로 돈 결과다. 입력 지연은 막지만 그동안 프레임은 그려지지 않는다.
- 4번의 첫 트랜잭션도 상수 `Work.Apply = 20 ms` 를 따른다.
- 미니맵 비용(2·3번)은 모두 포크 코드(`scripts/codemirror/minimap/index.js`) 안에 있다. 포크는 `scripts/build-codemirror.mjs` 로 vendor 묶음(`web/vendor/codemirror/cm.js.gz`)에 들어간다. 앱(`cm-setup.js`·`file-editor.js`) 쪽에서는 미니맵을 켜는 시점만 늦출 수 있다. 그러면 첫 페인트는 앞당겨지지만 2·3번 작업은 그 뒤에 그대로 생긴다. 16 ms 초과 작업의 수와 크기는 줄지 않는다.
- 측정 파일은 올바른 JS 가 아니다(`line 1 const …`). lezer 의 오류 복구 때문에 실제 JS 보다 파싱이 느릴 수 있다.

**막힌 이유**: 16 ms 초과 작업을 실제로 줄이려면 vendor 묶음을 다시 만들어야 한다(미니맵 포크를 나눠 계산하게 고치거나 `@codemirror/language` 의 예산을 패치). 조정자 지시가 "vendor 를 고쳐야 하면 멈추고 돌아온다" 이므로 여기서 멈춘다. 코드 변경과 커밋은 없다.

### 2026-11-24 구현 — 사용자 결정 A(미니맵 포크를 고치고 vendor 를 다시 만든다) (agent-pf-3-7)

커밋 `b3768923` (pf/3.7). 고친 곳은 미니맵 포크(`scripts/codemirror/minimap/index.js`)와 그 출력뿐이다. 상위 CodeMirror 와 언어 모듈의 100 ms 예산(C안)은 건드리지 않았다.

**바꾼 것**

- `TextState.updateMapImpl` 은 이제 문서 전체를 훑지 않는다. 줄 span 은 그 줄을 그릴 때 `get` → `lineSpans` 로 만든다. 강조는 겹치지 않고 차례대로 온다. 그래서 "앞 줄 끝을 넘는 첫 강조"부터 시작하면 원본의 한 번 훑기와 결과가 같다.
- `lineColumns` 는 `[from, to)` 구간만 센다. 칸 수는 줄바꿈이 켜져 있을 때만 쓴다(`visualAccum`). 처음 셀 때는 배치를 처음 물은 자리에서 4 ms 를 세고, 그 뒤로는 플러그인의 프레임 콜백에서 프레임마다 8 ms 씩 센다. 다 세면 빈 효과(`columnsCounted`)를 보낸다. 한 번 다 센 뒤 문서나 접힘이 바뀌면 원본처럼 곧바로 다시 센다.
- 줄 그리기(`render` → `drawRows`)는 화면 밖 캔버스에 한다. 다 그리면 보이는 캔버스로 한 번에 옮긴다. 256줄 이하는 곧바로 그리고, 그보다 많으면 다음 프레임부터 프레임마다 8 ms 씩 그린다.
- `doc.toString()` 은 파서가 있을 때만 만든다.
- `minimapDrawn` 이 `built`(span 을 만든 줄 수)도 돌려준다. `minimapLineSpans`·`minimapLineColumns` 를 내보낸다(`entry.js`, 단위 시험용).
- vendor 묶음을 다시 만들었다(`cd scripts/codemirror && npm ci` → `node scripts/build-codemirror.mjs`). 의존과 잠금 파일은 바꾸지 않았다. 고치기 전에 다시 만들어 보니 바이트가 같았다. 바뀐 출력은 `cm.js.gz` 하나다: **66,788 → 67,464 바이트**. `docs/internal/VENDOR_VERSIONS.md` 의 codemirror 해시를 `cbd026dd6db1d6e9…` 에서 `check-vendor.sh` 가 낸 새 값으로 고쳤다(그 문서 ④ 의 절차).
- 포크 README 의 "고친 자리" 에 7번을 더했다.

**측정 (이전 / 새)**

- 조건: 기준선 바이너리(`/private/tmp/pf3.7/otterminal-base`, 포트 60610)와 새 바이너리(포트 60620)를 번갈아 쟀다. 일반 3회, 줄바꿈 켬 2회다. 3.2·3.3 이 같은 시각에 빌드·측정했다.
- 측정 파일을 **올바른 JS** 로 바꿨다: `const value_N = recompute(N, 'sN') // some remark text` 2만 줄 + `added(N);` 3천 줄. 앞의 기준선(잘못된 JS)과 숫자를 바로 견주지 않는다.

**동작 변경 (이전 / 새 / 이유)**

1. 큰 문서(그릴 줄이 256줄 초과)의 미니맵 그림. 이전: 측정 프레임에서 한 번에 그렸다. 새: 다음 프레임부터 여러 프레임에 나눠 그린 뒤 한 번에 바꾼다. 그동안에는 지난 그림이 보인다. 처음 열 때는 빈 미니맵이 몇 프레임(2만 줄 기준 약 2~3프레임) 이어진다. 이유: 그리기 25 ms 가 CM 자신의 측정과 한 작업에 겹쳤다. 다 그린 그림은 같다.
2. 줄바꿈이 켜진 큰 문서를 처음 열 때. 이전: 칸 수를 측정 안에서 한 번에 셌다. 새: 프레임마다 나눠 센다. 다 셀 때까지 미니맵 배치가 없어서 스크롤바 thumb 는 CM 높이를 쓰고 미니맵은 그리지 않는다. 다 세면 미니맵 슬라이더와 thumb 가 다시 같은 자리에 선다(V-PF37b).
3. `minimapDrawn().rows` 는 그리기를 시작할 때 정한다. 나눠 그리는 동안에는 아직 다 그리지 않은 줄도 들어 있다.
4. 줄바꿈이 꺼져 있으면 칸 수를 세지 않는다. 결과는 원본과 같다: 원본도 그 값을 쓰지 않았다.

**남은 위험**

- 미니맵은 여전히 편집할 때마다 `parser.parse` 를 한다(`TextState.updateImpl`). 큰 JS 파일의 첫 편집은 `_previousTree` 가 없어서 문서 전체를 동기로 파싱한다. 기존 동작이며 이번에 재지 않았다.
- 칸 수는 한 번 다 센 뒤 편집할 때마다 원본처럼 동기로 다시 센다(줄바꿈 켬, 2만 줄에서 약 13 ms).
- 남은 16 ms 초과 4건 가운데 둘(`_init` 19~22 ms, 언어 붙이기 25 ms)은 CM 과 앱 쪽이다. 유휴 파싱 72 ms 는 C안 범위다.

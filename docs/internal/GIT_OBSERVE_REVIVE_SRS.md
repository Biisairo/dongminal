## 1. 개요

### 1.1 목적

접수한 것은 브라우저 콘솔 한 뭉치다.

```
[git] 관측이 멈춰 있어 되살립니다 — age=never poll=on  repo=/Users/dykim/personal/dongminal
[git] 관측이 멈춰 있어 되살립니다 — age=297s  poll=off repo=/Users/dykim/personal/dongminal
[git] 관측이 멈춰 있어 되살립니다 — age=1763s poll=off repo=/Users/dykim/personal/dongminal
… (age 가 107s~2722s 로 제각각인 줄이 이어짐)
```

워치독(`UX_BATCH9_SRS` 묶음 B)은 "조용한 정지를 없앤다" 는 장치다. 그런데 지금 그것은
**정지를 알리기만 하고 되살리지 못하는 회차**를 갖는다. FR-GLR-2 가 요구한
"그 자리에서 한 번 수집하고 주기를 다시 건다" 중 **수집이 빠진다.**

이 문서는 새 기능을 세우지 않는다. **이미 있는 요구(FR-GLR-2)가 코드에서 지켜지도록
고치고**, 그 과정에서 드러난 관측 조건 판정의 결함 하나를 함께 닫는다.

### 1.2 범위

**포함**
- 워치독이 되살릴 때 **반드시 한 번 수집**하게 하는 것 (FR-GLR-2 의 교정)
- 되살리기가 요청원이 되지 않도록 **시도 자체에 주기를 거는 것**
- 폴링 조건 판정을 **관측기 단위**로 옮기는 것 — 지금은 패널 하나의 판정이 다른 패널의
  판정을 덮는다 (§2.3)
- 되살리기 로그에 **어느 관측기인지**를 싣는 것 (FR-GLR-6 의 보강)

**미포함**
- `499` 응답 (§2.5 — 결함이 아님이 실측으로 확인됐다)
- 적재 시점의 첫 수집이 유실되는 **경로 자체의 특정**. 워치독이 그 자리를 덮으므로
  증상은 사라진다 (§6 비목표 #1)
- `TimerHub._fire` 의 재무장 누락 (§6 비목표 #2)
- 폴링 주기·백오프 규칙 (`GIT_REPO_MISSING_SRS` FR-RMS-22~26 그대로)

## 2. 현재 상태 (실측)

측정: 2026-09-09 15:55~15:58, `/tmp/dongminal.log` · `?diag=1` 산출 2건
(`/tmp/dongminal-diag-1788936976173.txt`).

### 2.1 워치독은 `poll=on` 갈래에서 아무것도 하지 않는다

```js
// web/js/git/panel-poll.js
_watchdog(){ …  this._reschedule(); return true }              // :358
_reschedule(){ if(this._applyCadence()) this.collect() }       // :363
_applyCadence(){ …
  if(this._pollOn && this._pollSt===st) return false;          // :293
```

폴링이 켜져 있고 실효 주기가 그대로면 `_applyCadence` 는 거짓을 돌려주고, 그러면
`collect()` 가 **불리지 않는다.** 워치독은 경고만 찍고 물러난다.

그 갈래가 바로 `D-3` 이 워치독의 존재 이유로 든 상태다 — "타이머는 살아 있는데 응답이
오지 않는" 모양. **장치가 자기 목적의 절반에서 무력하다.**

### 2.2 그래서 적재 직후 관측이 5.4초 동안 없었다

같은 문서의 diag 와 서버 로그가 맞물린다 (t=0 ≈ 15:55:57.97).

| 시각 | 근거 |
|---|---|
| t=0.02 | 타이머 걸림 — `git.status:… every=30000 runs=0 in=24111ms` |
| t=0.80 · 5.34 | `git: … obs=**never** poll=30000` (두 번 다) |
| t≈5.30 | 버스 `window_focus … ago=612ms` — 사용자가 창을 클릭 |
| t≈5.45 | 서버 `15:56:03.32 GET /api/git/status 200 48ms` ← 이 문서의 **첫** 관측 |

`15:55:57.97`~`15:56:03.32` 사이 서버에 status 요청이 **한 건도 없다.** 적재 시의
"즉시 1회 수집"(FR-GIT-22)이 유실됐고, 타이머의 첫 발화는 24초 뒤였다. 화면을 되살린
것은 설계된 계기가 아니라 **사용자가 창을 클릭한 것**이다(`focus` → `signal()` →
150ms 디바운스). 클릭이 없었으면 Changes·History 는 **30초 동안 빈 채**로 서 있었다.

그 5.4초 동안 콘솔이 찍은 것이 `age=never poll=on` 이다 — 워치독은 정확히 보고 있었고,
§2.1 때문에 아무것도 하지 못했다.

### 2.3 폴링 조건을 패널 하나가 대표한다

관측기는 저장소(루트)마다 하나이고 패널은 **칸마다** 있다 (FR-SVS-30 · FR-RTU-64).
그런데 타이머의 점멸을 정하는 판정은 패널 자기 것이다:

```js
_applyCadence(){ if(!this._pollOk()){this._stop();return false} …   // :291
```

`_pollOk()` 는 **그 패널의 표면**을 본다 (`panel-poll.js:243`). 타이머는 관측기의
것이므로, 같은 관측기의 패널 둘 중 하나가 보이지 않으면 그 패널의 `_applyCadence`
한 번이 **보이는 칸의 폴링까지 끈다.** 전 패널을 도는 자리(`_gitRescheduleAll`,
`app-git.js:53`)에서는 순서가 결과를 정한다 — 마지막에 도는 패널이 이긴다.

접수된 로그의 `poll=off` 줄들이 그 자리다. 실측에서도 관측기가 둘 이상 돌고 있었다
(재적재 전 구간에서 포트 54618·54619 가 각각 30초 주기로 status 를 번갈아 냈다) —
콘솔의 age 가 107s~2722s 로 제각각인 이유다.

### 2.4 로그가 어느 관측기인지 말하지 않는다

찍히는 것은 `repo` 뿐이다 (`panel-poll.js:354`). 관측기가 **루트마다** 서는 지금 같은
`repo` 문자열이 여럿이므로, 이 한 줄로는 어느 표면이 멎었는지 특정할 수 없다.
FR-GLR-6 이 "새는 계기를 사후에 특정할 수 있어야 한다" 고 했으나 그 값이 모자란다.

### 2.5 `499` 는 결함이 아니다 (조사 결과)

접수 자료에 함께 있던 `499` 는 **재적재의 흔적**이다.

- 서버는 13:01:27 이후 재시작이 없고(`dongminald started pid=30381` 이후 없음), 자산은
  `304` 로 같은 해시(`f46c5abba994`)를 돌려줬다 → `version-watch` 는 발화하지 않았다.
  문서 적재는 15:55:25 · 15:55:57 · 15:56:32 세 번, 수동 새로고침이다.
- 모든 `499` 가 `15:55:57.670`~`.972` **300ms 창**에 모여 있고 소요는 0~59ms 다.
  시한 초과가 아니라 teardown 이다. 같은 시각 `/ws` 넷이 32.3s 만에 닫혔다.
- `git status` 실측 22ms, 그 구간 앞뒤 status 는 전부 `200`(0~48ms).

`499` 는 `core.ErrCanceled` → `apierr.StatusClientClosed` 매핑 그대로이며
(`apierr/tables.go:106`), 요청이 사라진 것을 사라졌다고 적은 것이다. **고칠 것이 없다.**

## 4. 설계 결정

- **D-1. 수집을 `_applyCadence` 의 반환값에 매달지 않는다.** 그 값이 답하는 질문은
  "주기를 다시 걸었는가" 이고, 워치독이 묻는 것은 "관측이 낡았는가" 다. 둘은 다른
  질문이며, 하나로 묶여 있던 것이 §2.1 의 결함이다. `_reschedule()`(조건이 참이 된
  순간의 규약, FR-GIT-22)은 그대로 두고 워치독만 자기 길을 갖는다.
- **D-2. 되살리기의 절제는 "나이" 가 아니라 "시도" 로 건다.** 나이(`_lastObsAt`)는
  **성공한 관측**의 것이라 실패가 이어지면 영영 낡은 채다 — 그 값으로 절제하면 절제가
  되지 않는다. 시도 시각을 따로 들고 그것으로 문턱을 세운다. `_lastObsAt` 의 뜻은
  건드리지 않는다 (FR-GLR-5 · 진단이 그 값을 읽는다).
- **D-3. 조건 판정을 관측기로 올린다.** 대안은 `_gitRescheduleAll` 의 **순서**를
  고치는 것(보이는 패널을 마지막에 돌리기)이었으나, 그것은 부르는 자리마다 같은 규칙을
  다시 지켜야 하고 한 곳이 새면 같은 증상이 돌아온다. 타이머가 관측기의 것이면 그
  타이머를 켤지 정하는 판정도 관측기의 것이어야 한다 — 소유와 판정을 같은 자리에 둔다.
- **D-4. 적재 시 첫 수집의 유실 경로는 쫓지 않는다.** 실측된 것은 "요청이 나가지
  않았다" 까지이고 그 앞은 짐작이다 (§2.2). 워치독이 제 일을 하면 그 자리는 1초 안에
  덮인다 — 안전망이 있는데 안전망을 못 믿어 원인을 짐작으로 만지면 경로만 늘어난다
  (D-2 의 정신: 계기를 하나 더 메우지 않는다).

## 6. 비목표

1. **적재 시 첫 수집이 왜 유실됐는가.** §2.2 는 증상을 확정했고 원인은 열려 있다.
   워치독이 그 자리를 덮으므로 이 문서의 범위 밖이다 (D-4).
2. **`TimerHub._fire` 의 재무장 누락.** `!_alive(job)` 과 `inflight`+`overlap:'drop'`
   두 조기 반환이 `job.nextAt` 을 과거로 남기고, 그러면 `_reschedule` 이 `setTimeout(0)`
   을 되풀이한다 (`timer-hub.js:118·120·290`). git status job 은
   `whenHidden:'run'` 이고 `run` 이 즉시 resolve 하므로 이 증상과 무관하다. 별건이며
   `EVENT_TIMER_HUB_SRS` 의 자리다.
3. **`499`.** §2.5 — 결함이 아니다.
4. **로그 수위.** `console.warn` 자체는 그대로 둔다. 되살리기가 실제로 드물어지면
   줄 수도 함께 준다.

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

`retries: 1` 이 봐준 항목(= flaky)을 **격리된 조건에서 세 번 더** 돌려, 그것이
**부하**인지 **결함**인지 그 회차 안에서 가른다.

지금 게이트는 flaky 를 세기만 한다. 그 판정의 근거는 `CI_GATES_SRS §3.1` 한 줄에
얹혀 있다.

> 재현할 길이 **CI 왕복뿐이다.** 고쳤는지 확인하는 데 한 회차씩 든다.

**이 스펙은 그 문장을 거짓으로 만든다.** 재현 수단이 회차 안에 생기면 봐줄 이유가
그만큼 줄어든다.

### 1.2 범위 (Scope)

들어오는 것:

- 본 실행이 남긴 flaky 목록을 **기계가 읽을 형식**으로 산출
- 그 목록을 **프로세스 분리 3회**로 재실행
- 세 번 모두 지면 **실패로 올린다**
- CI(`e2e.yml`)와 로컬(`make e2e`)이 **같은 판정**을 쓴다

나가는 것 (§5):

- 본 실행에서 이미 **failed** 인 항목 — 그것은 이미 실패다. 대상은 flaky 뿐이다
- 흔들림의 **원인**을 고치는 일 — 이 스펙은 가리기만 한다
- `retries: 1` 자체의 변경 (`FR-DRC-17` 이 양쪽 1 로 묶어 둔 것을 건드리지 않는다)

### 1.3 정의 (Definitions)

| 말 | 뜻 |
|---|---|
| **flaky** | 본 실행에서 `retry > 0` 이면서 최종 통과한 항목 (`parity-reporter.ts` 의 기존 정의 그대로) |
| **독립 재실행** | 새 playwright 프로세스 · `workers=1` · `retries=0` 으로 그 항목 하나만 도는 것 |
| **부하** | 독립 재실행 3회 중 **한 번이라도 통과**한 항목 |
| **결함** | 독립 재실행 **3회 모두 실패**한 항목 |

### 1.4 참고 (References)

- `CI_GATES_SRS §3.1` — flaky 판정이 두 번 갈린 기록. 이 스펙이 그 조항을 개정한다
- `E2E_PARALLEL_SRS` FR-EPL-7·13·14 — 워커 수, 포트·산출물 격리
- `playwright.config.ts:104` — `retries: 1`, `:126` — `workers: workerCount()`
- `e2e/parity-reporter.ts` — flaky 를 세는 유일한 자리
- `DRIFT_RECLAIM_SRS` FR-DRC-17 — 로컬과 CI 가 같은 조건을 쓴다

## 2. 현황과 제약 (Identified Issue)

### 2.1 지금 무엇이 일어나는가

```
본 실행 (workers=2~4, retries=1)
  └ 항목 실패 → 곧바로 재시도 → 통과 → flaky 로 집계 → 초록
```

재시도는 **같은 프로세스 · 같은 워커 편성 · 같은 서버 상태**에서 곧바로 돈다.
그래서 "부하 때문에 진 것"과 "가끔 지는 결함"이 **같은 모양**으로 끝난다. 세어도
가릴 수 없고, 가릴 수 없으니 봐줄 수밖에 없었다.

### 2.2 세 회차의 실측 (2026-09-16, v1.1.0 릴리스)

| 회차 | 실패 항목 | 성질 |
|---|---|---|
| `6a61a13` attempt 1 | `editor-save` TC-ESV-3 | retry 까지 짐 |
| `6a61a13` attempt 2 | 없음 | 초록 |
| `v1.1.0` tag | `editor-link` L3 | retry 까지 짐 |

**매 회차 다른 항목이고, 모두 UI 전파 지연 계열이다.** L3 는 서버가 `pinned` 에서
빠졌다고 응답한 뒤 UI 행만 10초 안에 사라지지 않았다 — 서버 상태는 맞았다.

§3.1 이 "git·부하 계열"이라 부른 그 양상이 세 회차 연속 그대로 관측됐다. 그런데
**그것이 부하라는 것을 아무도 증명하지 않았다.** 지금까지는 증명할 수단이 없었다.

### 2.3 로컬은 8샤드를 한 기계에서 병렬로 돈다 (핵심 제약)

`make e2e` 는 `xargs -P $(E2E_JOBS)` 로 샤드를 동시에 띄우고, 동시 워커 곱이
`E2E_CAP` 을 넘으면 **시작조차 하지 않는다** (FR-M10-5).

그러므로 **샤드 안에서 독립 재실행을 시작하면 그것은 독립이 아니다** — 다른
일곱 샤드의 부하를 그대로 받는다. 부하를 없애려고 도는 검사가 부하 속에서 돌면
답이 뒤집힌다.

CI 는 샤드마다 러너가 다르므로 이 제약이 없다.

### 2.4 `parity-flaky.txt` 는 이미 샤드끼리 덮어쓴다

리포터가 그것을 **cwd** 에 쓴다 (`parity-reporter.ts:86`). CI 는 샤드마다 러너가
달라 드러나지 않지만, 로컬 8샤드 병렬에서는 여덟이 같은 파일을 쓴다. 새로 만드는
산출물은 이 실수를 되풀이하지 않는다 (FR-EFI-2).

## 3. 요구사항 (Requirements)

### 3.1 묶음 A — 목록 산출 (FR-EFI-1~3)

**FR-EFI-1** `parity-reporter.ts` 가 flaky 목록을 **기계가 읽을 형식**으로 남긴다.
항목마다 `file`(리포 상대 경로) · `line` · `title` 을 싣는다. 재실행은 제목이 아니라
**위치**로 건다 — 제목에는 `›` 와 괄호와 한글이 섞여 있어 셸을 지나며 깨진다.

**FR-EFI-2** 그 파일은 **샤드마다 다른 자리**에 쓴다. playwright 의 `outputDir`
아래에 둔다 — 그것은 이미 샤드별로 갈려 있다 (`--output=test-results/s$i`).
`parity-flaky.txt`(수)는 잡 요약이 읽으므로 자리를 그대로 둔다.

**FR-EFI-3** flaky 가 없으면 파일을 만들지 않는다. 있는지 없는지가 곧 할 일이
있는지 없는지다.

### 3.2 묶음 B — 독립 재실행 (FR-EFI-4~8)

**FR-EFI-4** 목록의 각 항목을 **새 playwright 프로세스로 3회** 돈다. 매 회차가
새 프로세스이므로 서버·홈·포트가 함께 새것이 된다 — `webServer` 가 없고 서버는
워커 스코프 픽스처가 띄우며 `E2E_HOME` 이 pid 를 품기 때문이다 (D-3).

**FR-EFI-5** 각 회차는 `--workers=1 --retries=0` 이다. 워커 1 이 부하 가설의 직접
검정이고, 재시도 0 이라야 회차의 답이 하나로 떨어진다.

**FR-EFI-5a** 한 회차가 **통과하면 남은 회차를 돌지 않는다.** 그 시점에 판정은
이미 `부하` 로 정해졌고(FR-EFI-7), 더 도는 것은 답을 바꾸지 못한 채 값만 쓴다.
`결함` 판정에 필요한 3회는 그대로 3회 다 돈다.

**FR-EFI-6** 회차마다 **포트 뿌리를 옮긴다**. 본 실행이 끝난 뒤에 돌지만, 죽는
중인 서버가 포트를 붙들고 있을 수 있다 (FR-EPL-14 와 같은 근거).

**FR-EFI-7 (판정)** **3회 모두 실패한 항목이 하나라도 있으면 실패로 올린다.**
한 번이라도 통과하면 **부하**로 확정하고 통과시킨다.

> **결정 (2026-09-16, 사용자)**: 규칙을 "전부 틀리면" 으로 둔다. 잡히는 것은
> *독립 실행에서 100% 재현되는 항목* 뿐이다. 거짓 경보가 사실상 0 이 되는 대신
> **간헐 결함은 통과한다.** 그 균형을 택한 것이다.

**FR-EFI-8 (상한)** flaky 가 **8건을 넘으면** 독립 재실행을 돌지 않고 그 사실을
남긴다. 그 수를 넘었다는 것은 개별 격리로 가릴 일이 아니라 계통 문제이고,
9건 × 3회 = 27번의 서버 기동은 게이트가 치를 값이 아니다.

> **가정 (중요)**: 8 은 실측이 아니라 판단이다. 세 회차 관측에서 샤드당 flaky 는
> 0~1 이었다. 실측이 쌓이면 고친다.

### 3.3 묶음 C — 붙는 자리 (FR-EFI-9~11)

**FR-EFI-9 (CI)** `e2e.yml` 의 e2e 스텝 **뒤에** 독립 재실행 스텝을 둔다. 그
러너에서는 다른 샤드가 돌지 않으므로 거기서 바로 도는 것이 곧 독립이다.

**FR-EFI-10 (로컬)** `make e2e` 는 **8샤드가 전부 끝난 뒤에** 모아서 돈다 (§2.3).
샤드 안에서 돌면 독립이 아니다.

**FR-EFI-11** 판정하는 코드는 **한 벌**이다 (`scripts/e2e-isolate-flaky.mjs`).
CI 와 로컬이 그 하나를 부른다. 판정이 두 벌이면 한쪽만 고쳐진다 — `e2e.yml` 의
기존 주석이 같은 이유로 판정을 리포터 하나에 몰아 두었다.

> 리포터와 이 스크립트는 **판정이 두 벌인 것이 아니다.** 리포터는 *본 실행*을,
> 스크립트는 *독립 재실행*을 판정한다. 서로 다른 실행이다.

### 3.4 묶음 D — 드러냄 (FR-EFI-12~13)

**FR-EFI-12** 결과를 잡 요약에 적는다: `부하 N · 결함 M`. 결함이 있으면 **어떤
항목인지** 이름을 적는다. 수만 적으면 아무도 열지 않는다 (§3.1 이 값을 치르고 안 것).

**FR-EFI-13** 부하로 확정된 항목도 목록을 남긴다. 회차를 건너 같은 이름이 쌓이면
그것이 §3.1 의 "되뒤집을 조건" 을 사람이 판단할 재료다.

### 3.5 비기능 (NFR)

**NFR-EFI-1** flaky 0 인 회차에 **한 푼도 더 들지 않는다.** 목록 파일이 없으면
스크립트는 즉시 끝난다.

**NFR-EFI-2** flaky 1건일 때 추가 벽시계는 **3분 이내**를 목표로 한다 (서버 기동
포함 회차당 1분 가정). 상한(FR-EFI-8)에서 최악은 8건 × 3회.

### 3.6 제약 (Constraints)

**C-1** `retries: 1` 도 `workerCount()` 도 바꾸지 않는다. 이 스펙은 본 실행의
조건을 건드리지 않는다 — 건드리면 지금까지 쌓인 관측과 비교할 수 없게 된다.

**C-2** `internal/shared/agentadapter` 는 건드리지 않는다 (사용자 지시).

## 4. 검증 (Verification)

| ID | 무엇을 | 어떻게 |
|---|---|---|
| **V-EFI-1** | flaky 0 이면 아무것도 안 한다 | 목록 파일 없이 스크립트 실행 → exit 0, 출력 한 줄 |
| **V-EFI-2** | 3회 전부 지면 실패 | 항상 지는 고정 항목을 넣어 실행 → exit 1, 이름이 출력에 |
| **V-EFI-3** | 1회라도 통과하면 통과 | 2회 지고 1회 통과하도록 조작한 항목 → exit 0, `부하` 로 분류 |
| **V-EFI-4** | 위치로 건다 | 제목에 `›`·괄호·한글이 있는 항목이 그대로 재실행됨 |
| **V-EFI-5** | 상한이 듣는다 | flaky 9건 목록 → 재실행 없이 건너뛴 사실이 출력에 |
| **V-EFI-6** | 샤드끼리 안 덮어쓴다 | 로컬 8샤드 병렬 후 샤드별 목록 파일이 각자 남아 있다 |
| **V-EFI-7** | 로컬과 CI 가 같은 판정 | 같은 목록을 두 경로로 넣어 같은 결론 |

읽는 목록과 `npx playwright test` 를 대신하는 가짜 실행기로 판정 로직만 잰다 —
그러지 않으면 테스트가 몇 분씩 걸리고 그 자체로 흔들린다.

## 5. 비목표 (Non-Goals)

- **흔들림을 고치지 않는다.** 이 스펙은 가리는 장치다. 결함으로 확정된 항목을
  고치는 것은 그때의 별도 작업이다.
- **본 실행에서 failed 인 항목은 다루지 않는다.** 이미 실패로 올라가 있다.
- **`DM_E2E_STRICT_FLAKY` 를 없애지 않는다.** 그것은 "flaky 를 전부 실패로" 라는
  다른 손잡이다. 이 스펙은 그 사이에 한 단계를 넣을 뿐이다.
- **통계를 쌓아 추세를 보지 않는다.** 회차 안에서 가르는 것이 전부다.

## 6. 구현 계획 (Implementation Plan)

| # | 무엇 | 파일 |
|---|---|---|
| 1 | flaky 목록 JSON 산출 | `e2e/parity-reporter.ts` |
| 2 | 판정 스크립트 (유일한 판정자) | `scripts/e2e-isolate-flaky.mjs` (신규) |
| 3 | 판정 로직 테스트 | `scripts/test/e2e-isolate-flaky.test.mjs` (신규) · `package.json` 의 `unit` glob 확장 |
| 4 | CI 스텝 | `.github/workflows/e2e.yml` |
| 5 | 로컬 — 전 샤드 뒤 | `Makefile` (`e2e` 타깃) |
| 6 | §3.1 개정 | `docs/internal/CI_GATES_SRS.md` |

순서는 **3 → 2 → 나머지** 다 (TDD). 판정 규칙이 이 작업의 전부이므로 그것부터
실패하는 테스트로 고정한다.

### 6.1 `CI_GATES_SRS §3.1` 을 어떻게 고치는가

그 조항의 근거 문장 — *"재현할 길이 CI 왕복뿐이다"* — 이 더 이상 사실이 아니게
된다. 조항을 지우지 않고 **한 줄을 더한다**: 2026-09-16 의 판정("올리지 않는다")은
**독립 재실행을 통과한 것에 한해** 유지되고, 3회 모두 진 항목은 그 면제에서 빠진다.

두 번 뒤집힌 기록은 그대로 둔다. 그것이 이 조항을 읽는 사람이 알아야 할 전부다.

## 7. 리스크 (Risks)

| | 무엇 | 다루는 법 |
|---|---|---|
| **R-1** | 독립 재실행이 그 자체로 흔들려 거짓 결함을 만든다 | 3회 **전부** 져야 결함이다 (FR-EFI-7). 세 번 연속 지는 흔들림은 흔들림이라 부르기 어렵다 |
| **R-2** | 항목 하나를 단독으로 돌면 **앞 항목이 만든 상태가 없어** 다른 이유로 진다 | 실재하는 위험이다. `fullyParallel: false` 가 파일 안의 순서 의존을 인정하고 있다. 그때 결함으로 뜨면 그것은 **검사가 단독으로 성립하지 않는다**는 사실이고, 그 자체로 고칠 값이 있다 |
| **R-3** | 벽시계가 늘어 러너 상한(60분)에 닿는다 | FR-EFI-8 의 상한. flaky 0 이면 0 원 (NFR-EFI-1) |
| **R-4** | 로컬이 전 샤드 뒤에 도는 탓에 CI 와 **시점**이 다르다 | 판정 규칙과 격리 조건은 같다. 시점 차이가 답을 바꾼다면 그것은 §2.3 의 제약이 드러난 것이고 기록한다 |

### 8.2 스펙 대비 정정

**`config.rootDir` 은 리포 루트가 아니다.** FR-EFI-1 을 처음 구현할 때
`relative(config.rootDir, …)` 을 썼더니 `file` 이 `__tmp-flaky.spec.ts` 로 나왔다 —
`e2e/` 가 빠졌다. playwright 의 `rootDir` 은 **`testDir`**(`./e2e`) 이다.

그대로 두면 같은 이름의 spec 이 다른 자리에 생기는 순간 어느 것인지 말할 수 없다.
기준을 **cwd** 로 바꿨다 — CI 도 `e2e-shard-run.sh` 도 리포 루트에서 playwright 를
부른다.

**값을 치르고 안 것**: 이것은 단위 테스트로 잡히지 않았다. 주입한 가짜 실행기는
경로를 만들지 않기 때문이다. **임시 flaky 를 실제로 하나 만들어 돌려서** 걸렸다.

### 8.3 확인한 것 (실측, 2026-09-16 · darwin)

| 검증 | 방법 | 결과 |
|---|---|---|
| V-EFI-1 | 없는 목록으로 실행 | `flaky 0 — 돌 것이 없다`, exit 0 |
| V-EFI-2 | 있을 수 없는 위치 3회 실패 | `결함 1`, **exit 1** |
| V-EFI-3 | 통과하는 항목 | `부하 1`, exit 0 |
| FR-EFI-5a | 통과하는 항목 | `Running 1 test` 가 **한 번만** — 남은 회차를 돌지 않았다 |
| FR-EFI-1·2 | 임시 flaky 1건 | `test-results/isotest/parity-flaky.json` 에 `e2e/…:8` |
| 전 구간 | 리포터 산출 JSON → 스크립트 | 부하 1 판정까지 이어짐 |
| 판정 로직 | `npm run unit` | 193/193 (기존 182 + 신규 11) |

**아직 재지 못한 것**: V-EFI-6(로컬 8샤드 병렬에서 목록이 서로 덮어쓰지 않는다)과
V-EFI-7(로컬과 CI 가 같은 판정)은 **전량 실행과 CI 회차가 있어야** 잰다. 코드로는
`outputDir` 이 샤드별로 갈려 있다는 사실에 기대고 있고, 그 사실 자체는
`e2e-shard-run.sh` 의 `--output=test-results/s$i` 로 확인했다.

### 8.4 아직 답이 없는 것

- **상한 8 (FR-EFI-8) 은 실측이 아니다.** 세 회차 관측에서 샤드당 flaky 는 0~1
  이었다. 그 수를 넘는 회차를 아직 보지 못했다.
- **R-2 가 실재하는지 모른다.** 단독 실행에서 순서 의존으로 지는 항목이 있는지는
  CI 가 실제 flaky 를 만났을 때 처음 알게 된다. 사용자 결정(2026-09-16)으로
  **처음부터 판정에 반영**하므로, 그때 막히면 그 자리에서 고친다.
- **로컬과 CI 의 시점 차이(R-4)** 가 답을 바꾸는지 모른다. 바꾼다면 §2.3 의
  제약이 드러난 것이고 기록한다.

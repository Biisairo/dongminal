# SRS: 슬롯 제목과 경계 — 어느 칸이 무엇인지, 어디까지가 한 칸인지 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 두 줄이다.

> **① 슬롯 갯수에 상관없이 제목은 지금 어떤 걸 하고 있는지(windows·git·editor)와
> 창 이름을 합쳐서 보여주자.**
>
> **② 각 슬롯을 좀 더 눈에 띄게 구분해줬으면 한다. 지금은 그냥 분할과 잘 구분이
> 안 간다.**

두 요구는 같은 뿌리에서 나온다. 화면에는 **두 계층의 나눔**이 있다 — 슬롯(창을
담는 그릇, WINDOW_SLOTS_SRS)과 분할(창 안의 pane 배치). 지금은 둘이 같은 언어로
그려져 있고, 이름은 계층마다 다른 규칙으로 적혀 있다. 그래서 "어느 칸이 무엇인지"
와 "어디까지가 한 칸인지" 가 둘 다 즉시 읽히지 않는다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **T** 제목 | 창의 표시 제목을 만드는 단일 규칙. 토프바·슬롯 머리글의 역할 분담 |
| **B** 경계 | 슬롯 계층의 시각 언어. 팔레트에서 파생하는 경계색과 굵기 |
| **X** 인터페이스 | 새 CSS 변수·함수의 이름 계약 |

**미포함:** §6 비목표. 특히 **창 타입의 불변식·슬롯 모델은 한 줄도 바뀌지 않는다** —
이 SRS 는 **이미 있는 것을 어떻게 보이게 하느냐**만 다룬다.

### 1.3 개정하는 기존 요구 (Supersedes)

| 조항 | 출처 | 개정 내용 |
|---|---|---|
| FR-WSL-34 | WINDOW_SLOTS_SRS | 토프바의 창 이름 → **FR-STB-11·12** 로 대체 |
| FR-WSL-35 (1)(2) | WINDOW_SLOTS_SRS | 머리글의 내용과 강조 표현 → **FR-STB-12·21** 로 대체 |
| FR-GIT-231 계열 | `_rWinName` 의 근거 | 폐기하지 않는다. **FR-STB-2** 가 그 값을 그대로 딛는다 |

## 2. 현행 분석 (Current State)

### 2.1 이름이 나오는 자리는 셋이고, 규칙은 셋 다 다르다

브라우저에서 실측한 값이다 (슬롯 2칸, 칸0=Git 창, 칸1=Editor 창).

| 자리 | 근거 코드 | terminal | git | editor |
|---|---|---|---|---|
| 토프바 `#window-name` | `_rWinName(w)` — `renderer.js:79` | `og` | `dongminal` | `~` |
| 슬롯 머리글 `.slot-head` | `win.name` 원본 — `renderer.js:183` | `og` | **`Git`** | `~` |
| 사이드바 목록 | 탭별 서술자 — `sidebar-tabs.js` | `og` | `dongminal` | `~` |

**결함 A.** `.slot-head` 만 `_rWinName` 을 거치지 않는다. Git 창은 저장된 이름이
`Git` 고정이고 리포명 파생이 `_rWinName` 안에만 있으므로, **같은 창을 토프바는
`dongminal` 로, 머리글은 `Git` 으로 부른다.** `_rWinName` 의 주석은 "여기서 경로를
따로 잘라 쓰면 목록과 상단이 같은 리포를 다른 이름으로 부를 수 있다" 며 출처를 한
자리에 모았는데, 나중에 선 머리글(FR-WSL-35)이 그 규칙 밖에 남았다.

**결함 B.** 어느 자리도 **창 타입을 말하지 않는다.** `dongminal` 이라는 제목은 Git
창일 수도 Editor 창일 수도 있다 — 실제로 이 워크스페이스에는 그 이름의 창이 둘
있다. `~` 는 어느 것인지 더더욱 말하지 않는다.

### 2.2 슬롯 경계와 분할 경계가 같은 언어를 쓴다

| 계층 | 요소 | 현행 |
|---|---|---|
| 슬롯 | `.slot-handle` | `flex:0 0 4px; background:var(--border)` — `style.css:161` |
| 분할 | `.sp>.sh` | `3px; background:var(--border)` — `style.css:179` |

같은 색(`--border`)에 굵기만 1px 다르다. 화면에서 두 계층은 **구분되지 않는다.**
FR-WSL-35 는 "칸 사이는 손잡이가 가른다" 로 이 문제를 이미 다뤘지만, 그 손잡이가
분할 손잡이와 같은 색인 이상 가르는 일을 하지 못한다.

### 2.3 머리글의 기본색은 정의된 적이 없다

```css
.slot-head{ ... color:var(--fg);opacity:.6; ... }   /* style.css:152 */
```

**`--fg` 는 어디에도 정의되지 않은 변수다.** 전수 검색 결과 이 한 줄이 유일한
등장이며, 테마를 적용하는 `applyThemeObj` (`helpers.js:62`) 가 설정하는 토큰은
`--text`·`--text-muted`·`--text-bright`·`--text-dim` 이다. fallback 인자도 없으므로
머리글의 글자색은 **상속색으로 떨어진다** — 어느 테마에서 어떤 값이 되는지는
누구도 정한 적이 없다.

**결함 C.** 머리글이 토프바의 창 이름 자리를 이어받으려면(FR-STB-12) 그 자리와 같은
색이어야 하는데, 지금은 같은 색이기는커녕 정해진 색조차 없다.

### 2.4 색은 하드코딩하지 않고 **ui 토큰에서** 파생한다

테마는 54종이고 각각 색이 다르다. 색을 박으면 53개 테마에서 어긋난다. 이 코드베이스
에는 파생의 선례가 둘 있는데, **둘은 서로 다른 자리에서 나온다.**

| 선례 | 출처 | 파생원 |
|---|---|---|
| `pickAttnColor` | `helpers.js:39`, FR-PAN-10 | 테마의 **terminal(ANSI) 팔레트** |
| `--border-strong` | `helpers.js:75`, FR-GIT-216 | 테마의 **ui 토큰** (`mixHex(border,text,.35)`) |

**슬롯 경계는 후자를 따른다.** terminal 팔레트의 magenta·cyan 은 **터미널 텍스트를
위해 고른 색**이지 그 테마의 UI 와 조화되도록 고른 색이 아니다 — 거기서 뽑으면
"겹치지는 않지만 그 테마에 어울리지도 않는" 색이 나올 수 있다. `ui` 토큰은 UI 를
위해 고른 색이므로 그 안에서 섞은 값은 조화가 보장된다.

`--border-strong` 의 주석이 이 방법의 근거를 이미 적어 두었다.

> 팔레트에 그런 색이 없고, `--text-dim` 같은 기존 토큰을 빌리면 테마마다 밝기
> 관계가 달라 어떤 테마에서는 오히려 흐려진다 — border 를 text 쪽으로 섞으면 밝은
> 테마·어두운 테마 모두에서 바탕과의 대비가 반드시 커진다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 T — 제목

**FR-STB-1** 창의 표시 제목은 **한 형식**이다.

```
<타입 라벨> · <창 이름>
```

예: `Windows · og` / `Git · dongminal` / `Editor · dongminal` / `Editor · ~`

**FR-STB-2** `<창 이름>` 은 `_rWinName(w)` 의 값이다. 새로 파생하지 않는다 — Git 창의
리포명 파생(§2.1)이 이미 그 함수 한 자리에 있고, 사이드바 목록도 같은 출처를 딛는다.

**FR-STB-3** `<타입 라벨>` 은 **사이드바 탭 라벨과 같은 출처**다 (`SB_TAB_DEFS[].label`
— `Windows`·`Git`·`Editor`). 타입 이름을 이 SRS 가 새로 발명하지 않는다. 사용자가
사이드바에서 읽는 단어와 제목에서 읽는 단어가 달라지면 둘을 잇는 일이 사용자 몫이
된다.

**FR-STB-4** 제목을 조립하는 자리는 **하나**다 (`Renderer._rWinTitle(w)`). 토프바와
슬롯 머리글이 그 하나를 부른다. 결함 A 는 자리가 둘이어서 생겼다 — 자리를 하나로
두는 것이 이 SRS 의 본체다.

**FR-STB-5** 창이 없는 칸의 머리글은 종전대로 **`창 없음`** 이다 (FR-WSL-6). 제목
형식을 적용할 대상이 없다.

**FR-STB-6** 타입 라벨을 알 수 없는 창(미래의 새 타입)은 라벨 없이 창 이름만 낸다.
`undefined · 이름` 을 내지 않는다.

#### 자리 분담

**FR-STB-11** 슬롯이 **1개**면 토프바(`#window-name`)가 제목을 낸다. 슬롯 머리글은
종전대로 서지 않는다 (FR-WSL-4 — 단일 슬롯의 DOM 은 바뀌지 않는다).

**FR-STB-12** 슬롯이 **2개 이상**이면 각 슬롯 머리글이 **자기 칸의 제목**을 내고,
토프바의 창 이름은 **빈다**.

> 근거(D-1): 머리글이 이미 칸마다 제목을 말하는데 토프바가 그중 하나를 되풀이하면,
> 사용자는 그 값이 **어느 칸의 것인지** 를 매번 판정해야 한다. 포커스 칸의 강조
> (FR-STB-21)가 그 일을 이미 하고 있으므로 되풀이는 정보를 더하지 않는다.

**FR-STB-13** 토프바의 **나머지 버튼**(`Split H`·`Split V`·`+` 등)은 종전대로 포커스
슬롯의 창을 대상으로 한다 — FR-WSL-34 의 그 절반은 유효하며 바뀌지 않는다.

**FR-STB-14** 모바일에는 슬롯이 없다 (FR-WSL-60). 토프바가 언제나 제목을 낸다 —
FR-STB-11 과 같은 규칙이다.

### 3.2 묶음 B — 경계

**FR-STB-20** 슬롯 계층은 **분할 계층과 다른 색**을 쓴다. 굵기 차이 1px 로는 두
계층이 구분되지 않는다 (§2.2).

**FR-STB-21** 그 색(`--slot-edge`)은 **테마의 `ui` 토큰에서 파생한다.**

```
--slot-edge = mixHex(ui.border, ui.accent, SLOT_EDGE_MIX)    // SLOT_EDGE_MIX = .55
```

색상값을 하드코딩하지 않는다. 테마를 바꾸면 경계색도 따라 바뀐다.

**FR-STB-22** 파생원은 **`ui` 토큰이며 terminal(ANSI) 팔레트를 쓰지 않는다.**

> 근거(D-2): ANSI 의 magenta·cyan 은 터미널 텍스트를 위해 고른 색이지 그 테마의 UI
> 와 조화되도록 고른 색이 아니다 (§2.4). 경계는 UI 요소이므로 UI 의 색에서 나와야
> 한다. `border` 를 파생원으로 삼는 것은 **경계가 경계 계열이라는 뜻**이고, `accent`
> 쪽으로 섞는 것은 **그 경계가 주목을 요구한다는 뜻**이다 — 둘 다 목적에서 나온다.

**FR-STB-23** 파생값은 세 축 모두에서 구별되어야 한다. 54개 테마 전부에서 확인한다.

| 축 | 뜻 | 실측 (54개 테마) |
|---|---|---|
| vs `--border` | 분할 손잡이와 구분 | 평균 116 · 최소 73 |
| vs `--accent` | 포커스 강조와 구분 | 평균 95 · 최소 60 |
| vs `--bg` | 바탕과 구분 | 평균 150 · 최소 110 |

거리는 RGB 유클리드 거리다. `SLOT_EDGE_MIX` 를 바꾸면 이 세 값이 함께 움직이므로,
값을 조정할 때는 **세 축을 모두 다시 확인한다** — 한 축만 보고 올리면 다른 축이
무너진다.

**FR-STB-24** 슬롯 손잡이(`.slot-handle`)는 `--slot-edge` 를 배경으로 하고, 굵기는
분할 손잡이(3px)와 **한눈에 다른** 값이다. 8px 로 한다.

**FR-STB-25** 슬롯 머리글(`.slot-head`)의 **기본 글자색은 토프바 창 이름과 같은
토큰**이다 — `var(--text-muted)`. 정의되지 않은 `--fg` 를 쓰던 자리를 이것이 대신한다
(결함 C).

> 근거(D-3): 칸이 여럿일 때 토프바는 비고(FR-STB-12) 머리글이 그 자리를 이어받는다.
> **같은 일을 하는 자리는 같은 색이어야 한다** — 이어받은 자리가 다른 색으로 보이면
> 사용자는 그것을 다른 종류의 정보로 읽는다.

**FR-STB-26** 포커스 칸의 머리글은 **종전대로** `--accent` 로 강조한다 (FR-WSL-35 (2)
유지). 포커스의 언어는 이미 서 있으므로 이 SRS 가 바꾸지 않는다.

**FR-STB-27** `--slot-edge` 는 **경계(손잡이)에만** 쓴다. 머리글 글자색에는 쓰지
않는다 — 머리글의 색은 FR-STB-25·26 이 정한다.

**FR-STB-28** 분할 손잡이(`.sp>.sh`)는 **바뀌지 않는다.** 이 SRS 는 슬롯 계층에만
색을 준다 — 두 계층이 모두 화려해지면 구분이라는 목적이 다시 사라진다.

### 3.3 묶음 X — 인터페이스

**FR-STB-30** 이름 계약. 아래 이름은 e2e·CSS가 딛는 표면이다.

| 종류 | 이름 | 비고 |
|---|---|---|
| CSS 변수 | `--slot-edge` | 슬롯 계층의 색 |
| 상수 | `SLOT_EDGE_MIX` | `.55`. `BORDER_STRONG_MIX` 옆 |
| 메서드 | `Renderer._rWinTitle(w)` | 제목 조립의 단일 자리 |
| 상수 | `SLOT_HANDLE_PX` | 8. 분할 손잡이와 구분되는 굵기 |

**FR-STB-31** 기존 DOM 이름(`.slot-head`·`.slot-handle`·`#window-name`)은 **바뀌지
않는다.** 기존 e2e 가 그 위에 서 있다.

## 4. 설계 결정 (Design Decisions)

**D-1. 토프바는 칸이 여럿일 때 침묵한다.** → FR-STB-12 의 근거.

**D-2. 경계색은 ui 토큰에서 섞어 만든다.** → FR-STB-21·22 의 근거. 검토한 대안:

| 안 | 결과 | 채택 여부 |
|---|---|---|
| terminal 팔레트에서 고르기 | 겹침은 없으나 UI 조화가 보장되지 않는다 | 기각 |
| `--accent-border` 재사용 | Monokai 등에서 `border` 와 거리 19 — 구분 실패. 3개 테마는 `accent` 와 값이 같다. hover 테두리 의미와 중복 | 기각 |
| `mixHex(border,text,.6)` | 구분은 가장 크나 무채색이라 밝기 차이로만 읽힌다 | 기각 |
| 54개 테마에 `slotEdge` 키 추가 | 가장 정확하나 각 테마 저자의 팔레트 감각을 대신해야 한다. 새 테마마다 누락 위험 | 기각 |
| **`mixHex(border,accent,.55)`** | 세 축 모두 안전거리. 테마 파일 무수정 | **채택** |

**D-3. 이어받은 자리는 같은 색을 쓴다.** → FR-STB-25 의 근거. 슬롯 계층에 준 색
(`--slot-edge`)은 **경계에만** 쓴다 — 머리글까지 그 색으로 칠하면 "지금 어느 칸에
있는가"(포커스, `--accent`)와 "여기까지가 한 칸이다"(경계)가 같은 색으로 섞인다.

**D-4. 제목의 조립은 한 자리다.** 결함 A 는 "같은 것을 두 자리가 각자 만들었다" 는
한 문장으로 요약된다. 형식을 바꾸는 이번 변경에서 자리를 둘로 남겨 두면 같은 결함이
다시 자란다. → FR-STB-4.

**D-5. 타입 라벨을 새로 만들지 않는다.** 사이드바 탭이 이미 `Windows`·`Git`·`Editor`
라고 부른다. 제목이 `Terminal · og` 라고 부르면 사용자는 두 어휘를 잇는 일을 떠맡는다.
저장된 타입 값(`WINDOW_TYPE_TERMINAL='terminal'`)과 **보이는 라벨**은 별개이며, 보이는
쪽의 출처는 사이드바 탭 서술자 하나다. → FR-STB-3.

### 5.1 개정이 필요한 기존 테스트

`e2e/git-window-name.spec.ts` 의 세 케이스는 `#window-name` 의 **정확한 텍스트**를
검사하므로 FR-STB-1 로 전부 깨진다. 형식 변경에 맞춰 개정한다.

| 줄 | 현행 기대 | 개정 후 |
|---|---|---|
| `toHaveText(wantA)` | `dongminal` | `Git · dongminal` |
| `not.toHaveText('Git')` | — | 유지 (여전히 `Git` 단독이면 안 된다) |

## 6. 비목표 (Non-goals)

1. **슬롯 모델을 바꾸지 않는다.** 칸 수·방향·영속·포커스 규칙은 WINDOW_SLOTS_SRS
   그대로다.
2. **창 타입의 불변식을 바꾸지 않는다.** Git 창은 여전히 탭을 더할 수 없다.
3. **탭 이름을 제목에 넣지 않는다.** 접수 시 한 번 거론됐으나 요구자가 철회했다 —
   제목은 타입과 창 이름 둘이다.
4. **분할 계층의 표현을 바꾸지 않는다.** → FR-STB-28.
5. **`_buildPane` 이 `_aw()` 로 창 타입을 판정하는 문제**(비포커스 칸의 탭 바에 `+`
   가 잘못 붙고, 탭 드래그가 활성 창의 레이아웃을 만진다 — `renderer.js:482`)는 이
   SRS 의 대상이 아니다. 조사 중 발견했으나 이름·경계와 무관한 동작 결함이며 별도
   스펙이 필요하다.

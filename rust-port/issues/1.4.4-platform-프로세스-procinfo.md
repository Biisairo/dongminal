# 1.4.4 platform 프로세스·ProcInfo

## 목표

프로세스 생명주기(신호·Job Object·Detach·그룹)와 읽기 전용 프로세스 조회(lsof·procfs·Windows 스냅샷과 캐시), CommandLines 를 옮긴다. 외부 명령(lsof·pgrep·ps) 인자와 파싱 규칙은 Go 와 같아야 한다. 공개 API 는 부모 이슈 1.4 의 진행 기록 "공개 API 안" 을 따른다. 바꿔야 하면 조정자에게 먼저 알린다.

## 대상 Go 코드

- `internal/shared/platform/process*.go`, `procinfo*.go`, `cmdlines_*.go` (약 1300줄)

## 완료 조건

- 대상 Go 코드의 관측 동작을 Rust 가 동등하게 제공한다 (FR-RSP-1·3)
- 관측 동작을 검증하는 Go 테스트가 Rust 테스트로 옮겨져 통과한다 (V-RSP-1)
- `cargo fmt --check`, `cargo clippy -D warnings`, 격리 실행 `cargo test` 통과 (NFR-RSP-4)
- OS 의존 코드가 있으면 windows·linux 대상 `cargo check` 통과 (NFR-RSP-5)
- 작업 전후 `rust/scripts/prod-pids.sh` 출력이 같다 (V-RSP-5)
- 진행 기록에 공개 API 요약과 Go 와 다르게 한 내부 결정이 있다

- 2026-11-23 **review 요약** (rp/1.4, 커밋 f32f5a62, rust-port 병합 9332757c)
  - 고친 파일: `process.rs`(+`process/tests.rs`), `procinfo.rs`·`procinfo/{darwin,linux,windows}.rs`(+각 tests), `lib.rs` 재수출 두 줄, `Cargo.toml`(unix 는 libc, windows 는 windows-sys feature 6개를 더했다)
  - **공개 API**
    - `Process { alive, terminate, kill, detach(&mut Command), shutdown_signals() -> &'static [ShutdownSignal], new_group(&mut Command) -> Box<dyn Group> }`
    - `Group { bind(&Child), terminate, kill, close }`
    - `ShutdownSignal::{Interrupt, Terminate, Hangup}`
    - `ProcInfo { has_children, children_of, cwd, cwds, names, listener_pids, parent_pid, parents, connection_owner_pid }`(pid 는 `i32`, "모름" 은 None/빈 표)
    - `command_lines() -> io::Result<Vec<String>>`
    - kill 계열 오류는 Go 와 같이 접두어 없는 errno 다. 출력할 때는 `dm_gocompat::oserr::go_error_string` 을 쓴다.
  - **승인된 API 안에서 바꾼 것**: `shutdown_signals` 의 반환을 `&[i32]` 에서 `&[ShutdownSignal]` 로 바꿨다. Windows 에는 libc 신호 번호가 없고, Go 도 `os.Interrupt` 같은 추상값을 쓰기 때문이다. 소비자는 이 값을 tokio signal 이나 ctrl_c 에 대응시킨다.
  - **관측 동작**
    - 외부 명령의 인자는 Go 와 글자 단위로 같다(`exact_arguments` 검사).
    - `/proc` Glob 의 결과 순서를 Go 와 같게 했다. 이름의 바이트 순서이므로, listener 가 여럿일 때 첫 pid 가 같다.
    - Windows TCP 표 오프셋·포트 바이트 순서·스냅샷 캐시 TTL 2s 와 single-flight 는 Go 와 같다.
    - 실행 파일이 없을 때 오류 문구는 Go 의 `exec: "ps": executable file not found in $PATH` 다.
  - **테스트**
    - 116개(platform 전체) 통과.
    - 옮긴 Go 테스트: process_posix·procinfo·procinfo_parents·procinfo_wincache·cmdlines_posix 의 관측 검사 전부.
    - 더한 검사: 외부 명령 인자 고정, Glob 순서, 실기 자기 조회(parent_pid·names·parents·cwd).
  - **게이트**: fmt, clippy -D warnings(다섯 대상), 격리 테스트를 통과했다.
  - **Go 와 다르게 한 내부 결정**
    1. POSIX `Group` 은 `bind` 에서 리더 pid 를 기억한다. Go 는 `cmd.Process` 를 직접 보므로 bind 없이도 신호를 보냈다. Rust 는 bind 를 부르지 않으면 terminate·kill 이 아무것도 하지 않는다. 계약상 bind 는 필수이므로 정상 경로에서는 차이가 없다.
    2. Windows `detach`·`new_group` 은 std `Command` 의 생성 플래그를 OR 하지 않고 덮어쓴다. std 에 플래그를 읽는 getter 가 없기 때문이다.
    3. POSIX `detach` 는 `pre_exec(setsid)` 다. Go 처럼 호출자의 Setpgid 를 내릴 수 없으므로, 호출자는 `process_group` 을 함께 쓰지 않는다.
    4. Glob 은 crate 없이 고정 패턴(`*`·`[0-9]*`)만 이식했다. Go 와 같이 IO 오류는 빈 결과다. 그래서 Go 의 "bad pattern 이면 Parents 가 not ok" 갈래는 생기지 않는다.
    5. Windows `Group` 은 drop 할 때 Job 을 닫지 않는다(Go 와 같다).
  - **남은 위험**
    1. Windows 코드(Job Object·Ctrl+Break·toolhelp·iphlpapi)는 cargo check·clippy 만 통과했고 실기에서 돌려 보지 않았다. 8.x 상호 운용·크로스 검증에서 확인해야 한다.
    2. linux 실기 실행도 없다. 판단 로직은 가짜 /proc 으로만 검증했다.

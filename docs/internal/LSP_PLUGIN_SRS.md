> **문서 상태**: 승인·구현완료

| 항목 | 값 |
|---|---|
| 문서 | LSP_PLUGIN_SRS |
| 선행 | EDITOR_LSP_SRS (묶음 A 를 **개정한다**) · LSP_WINDOWS_PORTABILITY_SRS · CROSS_PLATFORM_SRS |

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 것은 사용자의 말이다 — **"embedded lsp 는 빼자. 대신 플러그인 형식으로 넣자.
컴퓨터에는 영향을 미치지 않고 이 dongminal 에서만 쓰이도록 격리하자."**

지금 방식은 두 자리에서 그 요구를 어긴다.

**첫째, 호스트에 툴체인을 요구한다.** `go` 나 `npm` 이 없는 기계에서는 설치가
불가능하며, 우리가 할 수 있는 일은 "먼저 설치하세요" 라고 말하는 것뿐이다. 그 말은
사용자의 컴퓨터를 바꾸라는 요구다.

**둘째, 격리했다고 적어 놓고 실제로는 흔적을 남긴다** (§2.1). `install.go:isolate`
가 격리하는 것은 산출물의 자리뿐이고, 빌드 캐시·모듈 캐시·npm 캐시는 사용자 홈에
그대로 쌓인다.

이 문서는 서버 조달을 **플러그인 선언**으로 옮기고, 실행에 필요한 모든 상태를 우리
디렉터리 한 칸 안에 가둔다. 그 칸을 지우면 원상복구된다 — 그것이 이 작업의 완료
판정이다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **P** 플러그인 모델 | 매니페스트가 서버를 선언한다. Go 코드에 서버 목록이 없다 |
| **F** 조달 | 매니페스트가 적은 대로 받는다. 우리는 집행기이지 배포자가 아니다 |
| **I** 격리 | 실행·설치의 모든 상태가 `<데이터>/ext/` 안에만 산다 |
| **R** 런타임 | node 는 특례가 아니라 `kind: "runtime"` 인 플러그인 하나다 |
| **B** 동봉 | 기본 매니페스트 9종을 저장소에 두고 첫 기동에 전개한다 |

**미포함:** §6 비목표. 특히 **세션·프로토콜·Monaco 연동(EDITOR_LSP_SRS 묶음 B~H)은
이 변경의 대상이 아니다.** 그쪽은 "실행 파일 경로 하나"만 받으며, 그 경로가 어디서
왔는지 묻지 않는다.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **플러그인** | 언어 서버 하나 또는 여럿을 선언하는 매니페스트(JSON)와 그것이 조달한 파일들 |
| **팩** | 한 번의 조달로 여러 서버를 내는 플러그인 (`vscode-langservers-extracted` 가 서버 다섯을 낸다). **조달 단위**이며, **세션 단위는 여전히 서버**다 (FR-LSP-13) |
| **런타임 플러그인** | 서버가 아니라 서버를 실행할 것을 내는 플러그인 (`kind: "runtime"`). node 가 그것이다 |
| **격리 칸** | `<데이터>/ext/`. 플러그인·런타임·캐시가 사는 유일한 자리 |
| **타깃** | 플랫폼 문자열. VS Code 의 표기를 그대로 쓴다 — `darwin-arm64`·`linux-x64`·`win32-x64` … (§2.4) |
| **조달** | 매니페스트가 적은 방법으로 실행 파일을 격리 칸에 놓는 일 |
| **임베드** | 우리 배포물이 그 파일을 갖고 다니는 것. 공식 URL 에서 받는 것은 임베드가 **아니다** (I-2) |

**이름 주의:** 이 저장소에는 이미 "플러그인" 이 있다 —
`runtime.AgentPluginDir` 의 Claude Code 플러그인이다 (§2.6). 서로 다른 계층이며
섞이지 않도록 **Go 패키지와 디렉터리 이름은 `ext`** 를 쓴다. 사용자에게 보이는
말은 "플러그인" 이다.

### 1.5 착수 전 확정된 결정

| # | 물음 | 답 |
|---|---|---|
| **I-1** | 플러그인이 담는 것은 | **레시피.** 매니페스트가 무엇을 어디서 받을지 선언하고, 우리가 그대로 집행한다 |
| **I-2** | 우리 배포물에 서버·런타임을 넣는가 | **절대 넣지 않는다.** `go:embed` 도, 우리가 빌드해 올린 릴리스 애셋도 임베드다. 공식 URL 에서 받는 것은 임베드가 아니다 |

| **I-4** | 기본 서버 목록은 | **매니페스트 9종을 동봉한다** (§2.7). Go 코드에는 목록이 없다 |
| **I-5** | node 는 어떻게 얻는가 | **런타임 플러그인으로 선언한다.** 특례 분기가 0 이면 그것은 데이터이지 임베드가 아니다 |
| **I-6** | gopls 는 | **호스트 `go` 에 위임한다.** prebuilt 가 어디에도 없으므로(§2.3) 받을 URL 이 없다. VS Code 의 Go 확장도 같은 자리에 있다 (§2.4) |
| **I-7** | 무결성 검증 | **한다.** 네트워크에서 받은 것을 실행하므로 sha256 이 매니페스트에 있고, 어긋나면 버린다 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 지금의 격리는 산출물뿐이다 — 실측

`install.go:isolate` 가 주는 것은 `GOBIN` 과 `--prefix` 뿐이다.

| 도구 | 격리하는 것 | **격리하지 못하는 것** |
|---|---|---|
| `go` | `GOBIN` → `<데이터>/lsp/bin` | `GOMODCACHE`(`~/go/pkg/mod`) · `GOCACHE`(`~/Library/Caches/go-build`) |
| `npm` | `--prefix` · `npm_config_global=false` | `npm_config_cache`(`~/.npm`) · 사용자 `.npmrc` |

`GOBIN`·`GOMODCACHE`·`GOCACHE` 를 모두 빈 디렉터리로 두고
`go install golang.org/x/tools/gopls@latest` 를 실측했다 (darwin/arm64, go1.25.4,
찬 캐시):

| 항목 | 크기 |
|---|---|
| `GOMODCACHE` | **459 MB** |
| `GOCACHE` | **430 MB** |
| 결과물 `gopls` | 39 MB |
| 빌드 시간 | 24.6초 |

**지금 사용자가 `받기` 를 누르면 그의 홈에 889 MB 가 쌓인다.** 우리는 그것을
격리라고 적어 두었다. 이 문서의 첫 근거가 이것이다.

### 2.2 EDITOR_LSP_SRS §2.9 의 전제는 서버에만 참이고 런타임에는 거짓이다

그 절은 이렇게 단정했다: *"우리가 tarball 을 내려받아 풀 수 있는 대상이 아니다."*

**서버에 대해서는 지금도 참이다.** 그러나 그 문장이 검사하지 않은 칸이 있다 —
**런타임**이다.

| 대상 | 공식 prebuilt tarball | 확인 |
|---|---|---|
| Node.js | **있다** | `https://nodejs.org/dist/v24.20.0/` · LTS v24.20.0 (Krypton) · npm 11.19.0 **동봉** |
| Go 툴체인 | **있다** | `https://go.dev/dl/?mode=json` · go1.27.1 · sha256 제공 |
| gopls·tsls·pyright | 없다 | §2.3 |

서버를 못 받는 것과 **서버를 실행할 것**을 못 받는 것은 다른 문제였고, 앞 문서는
둘을 하나로 묶어 둘 다 불가능하다고 적었다. 이 한 칸이 이번 전환의 자리다.

### 2.3 gopls 는 어디에도 prebuilt 가 없다 — 출처 셋

| 출처 | 확인 결과 |
|---|---|
| `golang/tools` GitHub 릴리스 | gopls v0.23.0·v0.22.0·v0.21.1 **모두 `assets: []`** — 소스 tarball 뿐 |
| mason-registry `gopls/package.yaml` | `pkg:golang/golang.org/x/tools/gopls@v0.23.0` — Mason 도 Go 툴체인을 쓴다 |
| VS Code Go 확장 | 없으면 확장이 **`go install` 을 직접 호출**한다. `go.toolsManagement.checkForUpdates` 로 갱신을 관리하고 GOPROXY 로 새 판을 본다 |

**셋이 같은 답에 도달해 있다.** gopls 만 다른 길인 것은 우리 설계의 결함이 아니라
생태계의 사실이며, 그러므로 I-6 은 예외가 아니라 관측의 수용이다.

### 2.4 VS Code 는 이 문제를 풀지 않았다 — 만나지 않는다

공식 가이드가 못박는다: *"VS Code already ships with a Node.js runtime, there is no
need to provide your own."* Electron 에 node 가 있으므로 JS 로 짠 서버는 확장 폴더에
넣고 경로 하나로 띄운다 (`ServerOptions.run = { module: serverModule }`).

**dongminal 은 Go 단일 바이너리다.** 그 전제가 우리에게 없다.

네이티브 바이너리가 필요할 때만 VS Code 도 문제를 만나며, 그때 갈래는 셋이다.

| 갈래 | 방식 | 사례 |
|---|---|---|
| (a) 플랫폼별 패키지 | `vsce package --target darwin-arm64`. 마켓플레이스가 맞는 VSIX 를 고른다 | rust-analyzer (현재) |
| (b) 확장이 런타임에 받는다 | GitHub 릴리스에서 플랫폼 맞는 것을 받아 `storagePath` 에 | rust-analyzer(초기) · clangd |
| (c) 호스트 툴체인에 위임 | 확장이 `go install` 을 부른다 | **Go 확장 (gopls)** |

우리가 채택하는 것은 **(b)** 이며, (a)는 `fetch` 가 타깃 키를 갖는 것으로 흡수된다.
**타깃 문자열은 VS Code 의 것을 그대로 쓴다** — `win32-x64`·`win32-arm64`·`linux-x64`
·`linux-arm64`·`linux-armhf`·`alpine-x64`·`alpine-arm64`·`darwin-x64`·`darwin-arm64`.
표기법을 새로 만들면 매니페스트를 쓰는 사람이 우리 표기를 따로 배워야 한다.

### 2.5 조달 패턴의 선례가 이미 있다

`internal/shared/sandbox/helper.go` 가 하고 있는 것:

1. **버전이 경로에 박힌다** (`HelperCachePath`) — 고정 경로를 쓰면 갱신 후에도 옛
   것을 계속 쓰고, 그 불일치는 오류가 아니라 조용한 오동작으로 나타난다
2. `Stat` 이 먼저다 — 있으면 아무것도 하지 않는다
3. `Fetch`·`Stat`·`Remove` 가 **주입**된다 — 네트워크 없는 호스트에서 검사된다
4. **사용자가 그 자리에 직접 놓아둔 파일도 쓰인다** (FR-SBX-29) — 네트워크가 없는
   환경의 도피구
5. `PruneHelperCache` 가 지금 판이 아닌 것을 치우며, **실패를 삼킨다** — 정리는
   곁다리이므로 그 실패가 본 기능을 막지 않는다

**다섯이 그대로 이 작업의 요구가 된다.** 새로 발명할 것이 없다.

### 2.6 "플러그인" 이라는 말이 이미 쓰이고 있다

`runtime.AgentPluginDir(binDir)` → `<bin>/agent-plugin/`, `.claude-plugin/plugin.json`
(SKILL_INJECTION_SRS). Claude Code 의 플러그인이며 이 문서의 것과 다른 계층이다.
§1.3 의 이름 규칙이 여기서 나온다.

`runtime.Install` 이 저장소의 파일들을 사용자 디렉터리로 전개하는 모양은 **기본
매니페스트 동봉(묶음 B)이 따를 선례**다.

### 2.7 동봉 대상 9종 — npm 레지스트리 실조회로 검증

| 팩 | 판 | 서버 (`exe`) | 런타임 |
|---|---|---|---|
| `vscode-langservers-extracted` | 4.10.0 | `vscode-html-language-server` · `vscode-css-language-server` · `vscode-json-language-server` · `vscode-markdown-language-server` · `vscode-eslint-language-server` | node |
| `typescript-language-server` | — | `typescript-language-server` (+`typescript`) | node |
| `pyright` | — | `pyright-langserver` | node |
| `yaml-language-server` | 1.24.0 | `yaml-language-server` | node |
| `svg-language-server` | 0.2.0 | `svg-ls` · `svg-language-server` (별칭) | node |
| `gopls` | — | `gopls` | **없음** (Go 바이너리) |

전부 `--stdio` 로 띄운다.

**둘이 여기서 따라 나온다.**

1. **조달 단위와 서버 단위가 갈린다.** `vscode-langservers-extracted` 하나가 서버
   다섯이다. FR-LSP-1 은 "단위는 언어가 아니라 서버" 라고 정했는데, 이제 그 위에
   **팩**이 한 겹 더 선다 (§1.3).
2. **node 의존이 압도적이다.** 9종 중 **8종이 node** 이고 gopls 하나만 아니다.
   node 를 사용자 책임으로 두면 "node 없으면 LSP 없음" 과 같은 말이 된다 — I-5 의
   근거가 이것이다.

**`svg-language-server` 에 대한 기록:** 0.2.0 · unpacked 7.9 KB · 단일 메인테이너 ·
초기 단계. 동봉하되 다른 여덟과 같은 성숙도로 보지 않는다.

### 2.8 npm 은 node tarball 안에 들어 있다

공식 node 배포본은 npm 을 함께 담는다 (v24.20.0 ↔ npm 11.19.0). 그러므로 **npm 을
따로 조달할 필요가 없다.** 실행 방법은 OS 마다 다르다 — POSIX 는 `bin/npm`,
Windows 는 `node_modules/npm/bin/npm-cli.js` 를 node 로 부른다. 이 차이는 코드가 아니라
**매니페스트의 타깃별 값**으로 표현된다 (FR-EXT-13).

### 2.9 묶음 B~H 는 이 변경에 영향받지 않는다

`session.go`·`conn.go`·`codec.go`·`manager.go` (1,121줄) 는 **실행 파일 경로와 인자**
만 받는다. 그것이 어디서 왔는지 묻지 않으므로 이 작업은 그 아래를 갈아 끼우는 일이다.

걷어내는 것은 `descriptor.go`·`install.go`·`locate.go` (466줄) 이며, 종단
(`handlers_lsp.go`) 의 두 API 는 이름을 지키고 내용이 바뀐다 (FR-EXT-30·31).

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 묶음 P — 플러그인 모델 (FR-EXT-1~9)

- **FR-EXT-1** 언어 서버의 목록은 **Go 코드에 없다.** 매니페스트가 유일한 출처이며,
  코드에 서버 이름·패키지 이름·URL 이 문자열로 나타나면 그것은 이 요구의 위반이다.
- **FR-EXT-2** 매니페스트는 JSON 파일 하나이며 `<데이터>/ext/plugins/<id>/plugin.json`
  에 산다.
- **FR-EXT-3** 매니페스트는 **팩**을 선언한다: `id` · `kind`(`server`|`runtime`) ·
  `needs`(선행 런타임 id 들) · `source`(조달 방법) · `servers`(이 팩이 내는 서버들).
- **FR-EXT-4** `servers` 의 각 원소가 **세션의 단위**다 (FR-LSP-13 유지):
  `id` · `langs`(Monaco language id) · `exts`(소문자, 점 포함) · `exe` · `args`.
- **FR-EXT-5** 한 팩이 서버를 여럿 낼 수 있다 (§2.7). **조달은 한 번**이고 서버는
  그 산출물을 나눠 쓴다 — 팩마다 따로 받으면 같은 패키지를 다섯 번 받는다.
  그러므로 **팩을 조달하면 그것이 내는 서버 전부가 함께 선다.** 다섯 중 하나만
  받는 길은 없다: npm 패키지가 하나이므로 우리가 쪼갤 수 있는 것이 아니다.
- **FR-EXT-6** `kind: "runtime"` 인 플러그인은 `servers` 대신 `provides` 를 갖는다:
  이름 → 팩 안의 상대 경로 (`node` → `bin/node`).
- **FR-EXT-7** `needs` 가 적힌 팩은 그 런타임이 **먼저 확보된 뒤에만** 조달·실행된다.
  없으면 그 사실을 런타임의 **이름으로** 알린다 (FR-LSP-11 의 규약을 잇는다).
- **FR-EXT-7b** 런타임은 **미리 받지 않는다 (lazy).** 그것을 요구하는 팩이 **처음
  조달될 때** 함께 확보되고, 그 뒤의 팩들은 이미 있는 것을 쓴다. 아무 팩도 조달하지
  않으면 런타임도 받지 않는다 — 첫 기동에 node 를 미리 받아 두는 길은 FR-EXT-16
  ("눌러야 네트워크를 쓴다")을 깨고, 서버를 쓰지 않을 사용자에게 100 MB 를 떠안긴다.
- **FR-EXT-8** 매니페스트를 읽지 못하거나 형식이 어긋나면 **그 팩만** 죽는다. 나머지
  플러그인과 편집기는 그대로 동작한다.
- **FR-EXT-9** 사용자는 매니페스트를 더하거나 고치거나 지울 수 있다. 그것이
  "플러그인 주입" 이며, 우리 UI 를 거치지 않아도 된다.
- **FR-EXT-9b** **선언을 우리 편집기로 열 수 있다.** 고치라고 만든 파일인데
  (FR-EXT-9) 그 자리가 사용자의 Editor 루트 밖이면(`fsRoot`, FR-LSP-49) 열 길이
  없다 — 파일 관리자를 켜서 숨은 디렉터리를 찾아가라는 것은 "플러그인으로 넣자" 의
  답이 아니다.

  방법은 **탐색기에 자리를 하나 세우는 것**이며, 선례가 있다 — 메모장이 리포가
  아닌 자리를 목록의 한 줄로 세운다 (NOTES_LIVE_EXPLORER_SRS FR-NOT-9,
  `EDITOR_NOTES_NAME`). 같은 모양으로 격리 칸의 `plugins/` 를 한 줄로 세우면
  매니페스트 편집·추가·삭제가 이미 있는 편집기로 이루어진다.
- **FR-EXT-9c** 선언을 고쳐 저장하면 **다음 관측이 그것을 읽는다** (FR-EXT-33).
  다시 띄우게 하지 않는다 — 고쳐 놓고도 안 바뀌는 것이 사용자가 우리를 못 믿게
  되는 자리다.

### 3.2 묶음 F — 조달 (FR-EXT-10~19)

- **FR-EXT-10** `source.kind` 는 셋이다: `archive` · `npm` · `toolchain`.
- **FR-EXT-11** `archive` 는 **타깃별**로 `url` · `sha256` · 압축 해제 규칙을 갖는다.
  타깃 문자열은 VS Code 의 표기다 (§2.4).
- **FR-EXT-12** `npm` 은 패키지 명세(`name@version`)를 갖고, `needs` 에 node 를
  요구한다. 설치는 **그 런타임의 npm** 으로 하며 호스트 npm 을 찾지 않는다.
- **FR-EXT-13** npm 실행 경로는 **매니페스트의 타깃별 값**이다 (§2.8). 코드가
  OS 로 갈라지지 않는다 (FR-XPL-5 와 같은 근거).
- **FR-EXT-14** `toolchain` 은 호스트의 도구(`go`)와 인자를 갖는다. **그 도구가
  없으면 조달하지 않고**, 없다는 사실을 도구 이름으로 알린다.
- **FR-EXT-15** 받은 아카이브는 **sha256 이 매니페스트와 일치할 때만** 푼다 (I-7).
  어긋나면 버리고 그 사실을 알린다 — 네트워크에서 받은 것을 검증 없이 실행하지
  않는다.
- **FR-EXT-16** 조달은 **사용자가 눌러야** 일어난다 (FR-LSP-8 유지). 서버가 스스로
  네트워크를 쓰지 않는다.
- **FR-EXT-17** 어떤 조달도 **셸을 거치지 않는다** (FR-LSP-51 유지).
- **FR-EXT-18** 조달에는 시간 상한이 있고, 진행과 결과(성공·실패 사유·출력 끝쪽)가
  화면에 남는다 (FR-LSP-10·12 유지).
- **FR-EXT-19** 성공의 판정은 **도구의 종료 코드가 아니라 실행 파일의 존재**다
  (FR-LSP-10 유지). 탐색과 **같은 함수**로 찾는다 (FR-LWP-6 유지).

### 3.3 묶음 I — 격리 (FR-EXT-20~26)

- **FR-EXT-20** 플러그인이 만드는 모든 상태는 `<데이터>/ext/` 안에만 산다.

  ```
  <데이터>/ext/
  ├── runtimes/<id>-<version>-<target>/
  ├── plugins/<id>/          plugin.json · 조달된 파일
  └── cache/                 HOME·npm·go 캐시
  ```

- **FR-EXT-21** **조달과 실행의 환경이 격리된다.** 최소한 `HOME`(Windows 는
  `USERPROFILE`) · `npm_config_cache` · `npm_config_prefix` · `GOMODCACHE` ·
  `GOCACHE` · `GOBIN` · `PATH` 가 격리 칸을 가리킨다. §2.1 이 이 조항의 근거다.
- **FR-EXT-22** **`<데이터>/ext/` 를 지우면 원상복구된다.** 그 밖의 어떤 경로도
  우리 때문에 생기거나 커지지 않는다. 이것이 이 작업의 완료 판정이다 (V-EXT-3).
- **FR-EXT-23** `toolchain` 조달이 끝나면 **빌드 캐시를 즉시 지운다.** §2.1 의
  889 MB 는 산출물이 아니라 부산물이다.
- **FR-EXT-24** 버전이 경로에 박힌다 (§2.5 ①). 갱신은 새 칸을 만들고, 옛 칸은
  정리가 치운다.
- **FR-EXT-25** 정리의 실패는 삼킨다 (§2.5 ⑤) — 본 기능을 막지 않는다.
- **FR-EXT-26** 사용자가 격리 칸에 **직접 놓아둔 파일도 쓰인다** (§2.5 ④). 네트워크
  없는 환경의 도피구이며, 조달 없이 플러그인을 주입하는 길이기도 하다 (FR-EXT-9).

### 3.4 묶음 D — 탐색과 상태 (FR-EXT-27~33)

- **FR-EXT-27** 탐색 순서는 넷이다: ① 사용자가 설정에 적은 절대경로 ② `PATH`
  ③ 격리 칸의 조달물 ④ 없음. 먼저 찾은 것을 쓴다 (FR-LSP-4 를 잇되 ③ 의 뜻이 바뀐다).
- **FR-EXT-28** **어디서 찾았는지를 함께 낸다** (FR-LSP-5 유지). `config` · `path` ·
  `managed` 에 더해, `path` 로 찾은 것은 **격리되지 않았음**을 화면이 말할 수 있어야
  한다 — 사용자가 자기 것을 쓰는 것은 정당하지만, 그것이 우리 격리의 예외라는 사실은
  드러나야 한다.
- **FR-EXT-29** 못 찾았을 때 **무엇이 없어서인지**를 이름으로 알린다: 런타임이
  없는가(`node`), 호스트 도구가 없는가(`go`), 조달을 아직 안 했는가.
- **FR-EXT-30** `POST /api/lsp/status` 는 이름을 지킨다. 응답에 팩·런타임·격리
  여부가 더해진다.
- **FR-EXT-31** `POST /api/lsp/install` 은 이름을 지킨다. 대상이 서술자 id 에서
  **팩 id** 로 바뀐다 (FR-EXT-5).
- **FR-EXT-32** 같은 팩의 두 번째 조달 요청은 거절된다 (FR-LSP-48 유지).
- **FR-EXT-33** 상태는 캐시가 아니라 **관측**이다 (FR-LSP-47 유지). 사용자가 격리
  칸을 지우면 다음 조회가 "없음" 을 낸다.

### 3.5 묶음 B — 동봉 (FR-EXT-34~37)

- **FR-EXT-34** 기본 매니페스트 9종(§2.7)과 node 런타임 매니페스트를 저장소에 두고,
  첫 기동에 격리 칸으로 전개한다. `runtime.Install` 이 이미 같은 모양이다 (§2.6).
- **FR-EXT-35** **전개하는 것은 매니페스트뿐이다.** 서버도 런타임도 함께 놓지 않는다
  (I-2).
- **FR-EXT-36** 사용자가 고친 매니페스트를 전개가 덮지 않는다. 지운 것을 되살리지도
  않는다 — 지움은 의사표시다.
- **FR-EXT-37** 동봉 매니페스트는 판이 박힌 것을 적는다 (`yaml-language-server@1.24.0`).
  `@latest` 는 sha256 을 적을 수 없고(FR-EXT-15), 같은 매니페스트가 기계마다 다른
  것을 받게 한다.

### 3.6 묶음 E — 경계 (FR-EXT-38~41)

- **FR-EXT-38** 매니페스트의 값은 **셸에 닿지 않는다** (FR-EXT-17). 조달 명령은
  이름과 인자가 분리된 채 실행된다.
- **FR-EXT-39** 매니페스트의 경로 값(`bin`·`provides`·압축 해제 대상)은 격리 칸을
  벗어날 수 없다. `..` 과 절대경로는 거절된다 — 아카이브가 격리 칸 밖에 파일을
  쓰는 것을 막는다.
- **FR-EXT-40** `url` 은 `https` 만 받는다.
- **FR-EXT-41** 실행 가능 판정은 `platform.Paths.IsExecutable` 한 벌이다
  (FR-LWP-1 유지). 조달의 "놓였는가" 와 탐색의 "있는가" 가 같은 규칙을 쓴다.

## 5. 확정 결정 (Decisions)

- **D-P1 매니페스트가 유일한 출처다.** 코드에 목록을 두면 서버를 더하는 일이 릴리스를
  요구하게 되고, 그것은 "플러그인" 이 아니다.
- **D-P2 우리는 집행기이지 배포자가 아니다** (I-2·I-3). 우리 배포물에 서버·런타임을
  넣지 않고, 우리가 빌드해 올리지도 않는다. 그러므로 보안 패치 추적 의무를 지지
  않는다. **EDITOR_LSP_SRS D-5 와 비목표 4 는 그대로 살아 있으며 이 문서가 강화한다.**
- **D-P3 node 는 특례가 아니다** (I-5). `kind: "runtime"` 인 플러그인 하나이며, Go
  코드에 "node" 라는 문자열이 나타나지 않는다. 특례 분기가 0 이면 그것은 데이터다.
  9종 중 8종이 node 를 쓰므로(§2.7) 이것 없이는 기능이 사실상 0 이 된다.
- **D-P4 gopls 는 호스트 `go` 에 위임한다** (I-6). prebuilt 가 없어(§2.3) 받을 URL 이
  없고, 우리가 빌드하면 D-P2 를 어긴다. 격리 툴체인을 받는 길은 **1.16 GB 피크 ·
  상시 271 MB** 로 재어 보고 버렸다 — node 는 110 MB 로 서버 여덟을 켠다.
- **D-P5 타깃 표기는 VS Code 의 것을 빌린다** (§2.4). 우리 표기를 만들면 매니페스트를
  쓰는 사람이 그것을 따로 배워야 한다.
- **D-P6 조달 단위(팩)와 세션 단위(서버)를 가른다** (§2.7). `vscode-langservers-extracted`
  가 이 구분을 강제한다 — 하나를 받아 다섯을 쓴다.
- **D-P7 판을 박는다** (FR-EXT-37). `@latest` 는 무결성 검증과 양립하지 않으며, 같은
  매니페스트가 기계마다 다른 것을 받게 한다.
- **D-P8 격리의 판정은 문장이 아니라 검사다** (V-EXT-3). §2.1 이 보여준 것은 "격리했다"
  는 주석이 사실과 어긋날 수 있다는 것이며, 그 재발을 막는 것은 홈을 실제로 재는
  검사뿐이다.

## 6. 비목표 (Non-goals)

1. **EDITOR_LSP_SRS 의 비목표 전부를 승계한다** — 자동완성(D-7), 이름 바꾸기·코드
   액션, 워크스페이스 심볼, 언어 서버 설정 UI, Git diff 뷰의 코드 탐색.
2. **원격 플러그인 레지스트리.** 목록 서버·검색·평점 따위를 만들지 않는다. 매니페스트는
   동봉되거나 사용자가 놓는다 (FR-EXT-9).
3. **플러그인이 코드를 실행하는 것.** 매니페스트는 순수 선언이다. Zed 는 wasm 으로
   격리를 샀지만, 실행할 것이 없으면 그 격리도 필요 없다 — 더 단순한 쪽을 택한다.
4. **호스트 툴체인의 자동 설치.** `go` 가 없으면 없다고 말한다. 우리가 남의 기계에
   툴체인을 놓지 않는다.
5. **컨테이너·VM 수준의 격리.** 언어 서버는 호스트 프로세스로 돈다. 컨테이너 런타임을
   요구하면 없애려던 전제를 더 무겁게 되살리는 일이 된다.
6. **자동 갱신.** 판은 매니페스트가 정하고(FR-EXT-37), 바꾸는 것은 사용자다.
7. **기존 `<데이터>/lsp/` 의 이관.** 새 칸(`<데이터>/ext/`)을 쓰고 옛 칸은 정리 대상으로만
   다룬다 — 옛 자리의 산출물이 어떤 환경에서 만들어졌는지 우리가 알지 못한다.

### 7.1 아직 닫지 않은 것

- **V-EXT-3** (홈 스냅숏으로 재는 격리)은 **실제 조달을 돌려야** 성립한다. 지금
  격리는 V-EXT-4(넘긴 env 를 잰다)로 지켜지고 있으며, 그쪽이 네트워크 없이 도는
  대신 "그 env 를 도구가 실제로 따르는가" 는 재지 못한다.
- **V-EXT-14** (Windows CI) 는 푸시 뒤 CI 가 판정한다. 이 작업의 판정을
  개발 호스트에서 끝낼 수 없는 자리다 (CROSS_PLATFORM_SRS R-1).
- `svg-language-server` 는 §2.7 에 적은 대로 성숙도가 다르다. 동봉하되 같은 무게로
  보지 않는다.
- `vscode-langservers` 의 `eslint` 서버는 `exts` 가 비어 있다. eslint 서버는
  확장자가 아니라 설정으로 켜지는 것이며, `.ts`·`.js` 를 주장하게 두면
  `typescript` 팩과 같은 확장자를 다투어 어느 쪽이 뜰지가 이름 순서로 정해진다
  (TC-EXT-63 이 그 충돌을 막는다). 조달은 되고 세션은 서지 않는다.

M1~M2 는 네트워크를 쓰지 않으므로 어느 호스트에서도 검사된다. M3 부터 `Fetch` 주입이
그 자리를 대신한다 (§2.5 ③).

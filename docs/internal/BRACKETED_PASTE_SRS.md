# SRS: 붙여넣기 모드를 물어보고 감싼다 — IEEE 29148

## 1. 개요

### 1.1 목적

API·에이전트가 도구에 넣는 입력은 **조건 없이** bracketed paste 로 감싸여 나간다.

```go
paste = append(paste, 0x1b, '[', '2', '0', '0', '~')
paste = append(paste, text...)
paste = append(paste, 0x1b, '[', '2', '0', '1', '~')
```

그 모드를 지원하지 않는 셸은 마커를 **글자 그대로** 명령줄에 받는다.

    $ 200~echo dongminal-e2e-ok201~
    bash: 200~echo: command not found

이 문서는 그 결함을 없앤다. 감싸는 것은 **셸이 그 모드를 켰을 때만** 이다.

### 1.2 어떻게 드러났나

v1.0.0 릴리스 게이트의 macOS 잡이 실패했다. `dongminal verify` 의 입력→출력 왕복이
표시를 한 번(에코)만 보고 실행 결과를 보지 못했다.

**게이트가 없었으면 이 결함이 그대로 1.0.0 에 실렸다.** 종전 CI 의 왕복 검사는
표시를 한 번만 찾았으므로 에코만으로 통과했을 것이다.

macOS 러너의 `$SHELL` 은 `/bin/bash` 이고, macOS 가 싣는 bash 는 **3.2.57**(2007년,
GPLv2 이후 갱신이 멈췄다)이라 bracketed paste 를 모른다. Linux CI 의 bash 5.x 와
zsh 는 지원하므로 그 둘에서는 드러나지 않았다.

### 1.3 영향

`SendPaste` 를 지나는 것 전부다.

| 경로 | 무엇 |
|---|---|
| `POST /api/tools/input` | API·`dmctl` 입력 주입 |
| `POST /api/tools/msg` | **에이전트 간 메시지** |
| `handlers_runs_context.go` | 오케스트레이션 컨텍스트 전달 |

브라우저 타이핑은 **무사하다** — WebSocket 경로는 `SendPaste` 를 지나지 않는다.

### 1.4 정의

| 용어 | 뜻 |
|---|---|
| **bracketed paste** | 붙여넣은 텍스트를 `ESC[200~ … ESC[201~` 로 감싸 앱이 "타이핑" 과 구별하게 하는 규약. 여러 줄을 붙여도 줄마다 실행되지 않게 한다 |
| **DECSET 2004** | 앱이 그 모드를 켜고 끄는 신호. 켜기 `ESC[?2004h`, 끄기 `ESC[?2004l`. **앱이 터미널에게 보낸다** |

## 2. 현황

### 2.1 규칙이 두 벌이다

`adapters.Tool.SendPaste` 안에 **같은 감싸기가 두 번** 적혀 있다 — direct 모드
갈래와 daemon 모드 갈래. 제출 지연 120ms 도 두 벌이다. 이 저장소가 반복해서
경계하는 모양이며, 이번 수정은 그 둘을 하나로 접는다.

### 2.2 결정이 도구에서 멀다

"이 셸이 그 모드를 켰는가" 는 **PTY 출력을 읽는 쪽만 안다.** 그런데 감싸기는
`adapters` 에서 일어난다. daemon 모드에서 `Hub.Get(id)` 은 cmd 없는 합성 Tool 을
주므로 거기서는 그 사실을 물을 수조차 없다.

`Cwd`·`Busy` 가 같은 이유로 이미 데몬 RPC 를 경유한다 (`hub.go` 주석). 이 트랙은
그 선례를 따른다.

## 3. 요구사항

### 3.1 묶음 A — 모드 추적 (FR-BPT)

**FR-BPT-1** `Tool` 은 PTY 출력에서 DECSET 2004 를 추적한다. `ESC[?2004h` 를 보면
켜짐, `ESC[?2004l` 을 보면 꺼짐이다. 초기값은 **꺼짐**이다.

**FR-BPT-2** 한 청크에 켜기와 끄기가 함께 오면 **마지막 것**이 이긴다. 순서가 곧
상태다.

**FR-BPT-3** 시퀀스가 읽기 경계에 걸쳐 쪼개져도 놓치지 않는다. `attnCarry` 와 같은
방식으로 꼬리를 이월한다. 이월 길이에 상한을 둔다 — 상한이 없으면 ESC 로 시작하고
끝나지 않는 출력이 메모리를 먹는다.

**FR-BPT-4** 판정은 `readPTY` 고루틴만 쓰고, 결과는 원자값으로 공유한다. 묻는 쪽은
입력 경로다 (다른 고루틴).

**FR-BPT-5** 셸이 바뀌거나 앱이 끝나 모드를 끄면 그대로 따라간다 — 상태를 기억해
두지 않는다. vim 을 열면 켜지고 나오면 꺼지는 것이 정상이다.

### 3.2 묶음 B — 감싸기 (FR-BPW)

**FR-BPW-1** 감싸기는 **도구가 사는 곳**에서 한다. `ToolManager.SendPaste(id, text,
submit)` 를 신설하고 `adapters` 의 두 벌을 그것으로 접는다.

**FR-BPW-2** 모드가 켜져 있으면 감싸고, 꺼져 있으면 **원문 그대로** 보낸다.

**FR-BPW-3** `submit` 이면 제출 지연 뒤 `\r` 을 보낸다. 지연 값은 한 곳에만 적는다.

**FR-BPW-4** daemon 모드는 `paste` RPC 로 같은 일을 데몬에서 시킨다. `write`·`cwd`·
`busy` 와 같은 형태다. **감싸기 판단이 클라이언트로 새지 않는다.**

**FR-BPW-5** `ToolHub` 인터페이스에 `SendPaste(id string, text []byte, submit bool)
error` 를 더한다.

### 3.3 비기능

**NFR-BP-1** 추적은 `readPTY` 의 뜨거운 경로에 있다. ESC 가 없는 청크는 **한 번의
스캔으로** 빠져나가야 한다.

**NFR-BP-2** 새 외부 의존 없음.

## 5. 비목표

1. **bash 3.2 를 위한 다른 우회** — 모드를 물어보는 것이 정답이고 그것으로 충분하다
2. **여러 줄 입력의 다른 보호책** — 모드가 꺼진 셸에서 여러 줄을 넣으면 줄마다
   실행된다. 그것은 그 셸의 정상 동작이다
3. **브라우저 붙여넣기 경로** — xterm.js 가 이미 모드를 보고 결정한다

## 7. 구현 결과

### 7.1 확인한 것

| 조건 | 이전 | 이후 |
|---|---|---|
| zsh (모드 켬) | ✅ 22/22 | ✅ 22/22 |
| `SHELL=/bin/bash` (bash 3.2, 모드 없음) | ❌ 왕복 실패 | ✅ 22/22 |

`adapters.Tool.SendPaste` 의 두 벌이 한 벌로 접혔다 — 이제 위임만 한다.

### 7.2 사고 기록 — 테스트가 구현을 베꼈다

구현 중에 **감싸는 마커와 모드 신호를 같은 상수로 썼다.** 방향도 뜻도 다른 것이다.

| | 방향 | 시퀀스 |
|---|---|---|
| 모드 켜기·끄기 | 앱 → 터미널 | `ESC[?2004h` · `ESC[?2004l` |
| 붙여넣기 마커 | 터미널 → 앱 | `ESC[200~` · `ESC[201~` |

증상은 `zsh: command not found: 2004hecho` 였다. 고치려던 결함과 똑같은 모양이
반대편에서 다시 난 것이다.

**단위테스트가 이것을 잡지 못했다.** 기대값을 구현의 상수(`bpOn`/`bpOff`)로 조립해
대조했기 때문이다. 상수가 틀리면 기대값도 함께 틀린다 — 테스트가 계약이 아니라
구현을 베낀 것이다. 잡은 것은 종단간(`verify`)이었다.

지금은 기대값을 리터럴(`"\x1b[200~echo hi\x1b[201~"`)로 적고,
`TestWrapPaste_UsesPasteMarkersNotModeSignals` 가 감싸기에 `2004` 가 섞이지 않는지
따로 못박는다.

**교훈**: 상수의 값 자체가 검증 대상이면, 기대값을 그 상수로 만들지 않는다.

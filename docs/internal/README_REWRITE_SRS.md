# SRS: README 재작성 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

> **"최상위 readme 를 완전 사용자 측면에서 재작성. 사진도 캡쳐하고 설치, 사용법을
> 사용자가 알아보기 편하게 적는 등 사용자 친화적으로 재작성하자."**

지금 README 는 **처음 온 사람이 읽는 문서와 고치는 사람이 읽는 문서가 섞여 있다.**
346줄 중 절반 이상(§82~207, §229~346)이 빌드·검사·배포·패키지 트리·로드맵이다.
받아서 써 보려는 사람은 그 사이에서 "무엇을 할 수 있는가" 를 찾아야 한다.

그리고 **그림이 하나도 없다.** 화면을 쓰는 도구인데 화면이 없다.

### 1.2 범위 (Scope)

| 묶음 | 내용 |
|---|---|
| **A** 재작성 | README 를 사용자 관점으로 다시 쓴다 |
| **B** 이관 | 지금 있는 개발자 내용을 **잃지 않고** 옮긴다 |
| **C** 그림 | 화면을 찍어 싣는다 |

**미포함:** §5 비목표.

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 무엇이 사용자 것이고 무엇이 아닌가

| 절 | 성격 |
|---|---|
| 설치 · 빠른 시작 | 사용자 |
| 지원 플랫폼 | 절반 — "내 OS 가 되는가" 는 사용자, ConPTY·seam 규칙은 개발자 |
| 소스에서 빌드 · 검사 · 배포 · 테스트 | 개발자 |
| 문서 · 주요 기능 | 사용자 |
| 아키텍처 개요 · 프로젝트 구조 · 기술 스택 | 개발자 |
| TODO | 개발자 |
| 알려진 문제 | **사용자** — 겪는 사람이 읽어야 한다 |

### 2.2 옮길 곳이 이미 있다 — 하나만 빼고

`architecture.md` 에 패키지 레이아웃이 있으므로 README 의 `프로젝트 구조` 는
겹친다. 그러나 **`아키텍처 개요` 의 "프로세스 역할 넷" 다이어그램은 그 문서에
없다** — 옮기지 않으면 사라진다.

빌드·검사·배포·테스트를 담을 문서는 없다. 새로 만든다.

### 2.3 그림은 운영 워크스페이스에서 찍으면 안 된다

지금 이 저장소의 화면에는 사용자의 홈 경로(`/Users/<이름>/…`), 호스트명
(상태바의 `💻` 항목과 셸 프롬프트), 실제 저장소·브랜치 이름이 그대로 보인다.
README 는 공개되므로 **격리 인스턴스에서 찍어야 한다.**

`dongminal start --isolated` 가 그 수단이다 — 임시 홈과 빈 포트를 쓰므로 운영
인스턴스를 건드리지 않는다 (FR-ISO-1/2).

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 묶음 A — 재작성

- **FR-RDM-1** README 의 첫 화면(스크롤 없이 보이는 범위)이 **무엇인지·어떻게
  생겼는지**를 답한다 — 한 문단 소개와 대표 그림 하나.
- **FR-RDM-2** 설치는 OS 별로 **복사해서 붙이면 되는 명령**이다. macOS 의 `xattr`
  처럼 없으면 막히는 단계는 이유와 함께 남긴다.
- **FR-RDM-3** 설치 다음에 **처음 할 일**이 이어진다 — 접속, 창·분할, 설정.
- **FR-RDM-4** 기능은 **화면과 함께** 설명한다. 그림 없는 기능 나열이 아니다.
- **FR-RDM-5** 문제를 겪는 사람을 위한 절이 있다 — `doctor`·`health`·알려진 문제.
- **FR-RDM-6** 개발자를 위한 것은 **맨 아래 한 절**로 줄이고 링크로 보낸다.
- **FR-RDM-7** 문장은 사용자의 말로 쓴다. 요구사항 번호·SRS 참조·내부 파일 경로를
  본문에 늘어놓지 않는다.

### 3.2 묶음 B — 이관

- **FR-RDM-8** 옮기는 내용은 **잃지 않는다.** 지우는 것은 다른 문서에 이미 같은
  내용이 있을 때뿐이고, 그때는 그 문서를 가리킨다.
- **FR-RDM-9** 빌드·검사·배포·테스트·기술 스택·로드맵은 새 문서
  `docs/internal/building.md` 로 간다.
- **FR-RDM-10** "프로세스 역할 넷" 다이어그램은 `architecture.md` 로 간다 (§2.2).
- **FR-RDM-11** 알려진 문제는 README 에 남는다 — 겪는 사람이 읽는 것이다 (§2.1).

### 3.3 묶음 C — 그림

- **FR-RDM-12** 그림은 **격리 인스턴스**에서 찍는다 (§2.3).
- **FR-RDM-13** 그림에 개인 정보가 없어야 한다 — 홈 경로·호스트명·실제 저장소
  이름이 보이지 않는다.
- **FR-RDM-14** 그림은 `docs/images/` 에 두고 저장소에 함께 넣는다. GitHub 에서
  README 가 그대로 보이려면 저장소 안에 있어야 한다.
- **FR-RDM-15** 그림 전체 크기는 1MB 를 넘지 않는다. 이 저장소는 바이너리를 커밋하지
  않기로 했고(RELEASE_SRS §2.1), 그림도 같은 저울에 올린다.
- **FR-RDM-16** 찍는 절차는 스크립트로 남긴다 — 화면이 바뀌면 다시 찍어야 하고,
  손으로 찍으면 매번 다른 화면이 된다.

## 4. 검증 (Verification)

| ID | 검증 | 수단 |
|---|---|---|
| **V-RDM-1** | 모든 그림 파일이 존재하고 README 가 그것을 가리킨다 | 스크립트 |

## 5. 확정 결정 (Decisions)

- **D-1 격리 인스턴스에서 찍는다.** 운영 화면에는 지울 수 없는 것들이 있다 (§2.3).
- **D-2 그림을 저장소에 넣는다.** 밖에 두면 README 가 GitHub 에서 깨지고, 링크가
  죽는 날 아무도 모른다. 대신 크기 상한을 둔다 (FR-RDM-15).
- **D-3 지우지 않고 옮긴다.** 지금 README 의 개발자 내용은 정확하고, 사라지면
  복원할 곳이 없다.
- **D-4 촬영을 스크립트로 남긴다.** 화면이 바뀌면 그림도 낡는다. 다시 찍는 비용이
  낮아야 실제로 다시 찍는다.

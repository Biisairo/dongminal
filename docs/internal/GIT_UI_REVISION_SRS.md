## 1. 서론 (Introduction)

### 1.1 목적 (Purpose)

MVP(M1~M5) 구현 후 사용자 검토에서 나온 UI 결정 셋을 요구사항으로 확정한다.

1. **Git 창과 일반 창의 경계** — 지금은 Git 창 안에서 분할·탭 추가가 되어 두 세계가
   섞인다. 그것을 막는다.
2. **Git 창의 진입점** — 지금은 WINDOWS 목록과 창 전환 단축키가 Git 창을 일반 창과
   같이 다룬다. GIT 섹션만 진입점으로 남긴다.
3. **선택 어휘와 표식** — 파일 목록의 체크박스를 없애고 행 클릭 + 보조키로 옮긴다.
   GIT 섹션의 이모지 표식을 없앤다.

### 1.2 범위 (Scope)

**대상**: 좌측 사이드바 WINDOWS·GIT 섹션, Git 창의 창 골격(탭 행·상단 바·분할),
Changes 탭 파일 목록의 선택, `Open File` 의 대상 창.

**비대상**: git 실행 계층(`internal/git`), API 표면, Diff·History·Branches·Stash 의
내부 동작, 안전 정책(묶음 J), 다이얼로그 규약(묶음 P).

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **Git 창** | `type: "git"` 인 창. 워크스페이스에 최대 1개 (FR-GIT-26) |
| **일반 창** | `type` 이 없거나 `terminal` 인 창 |
| **follow 항목** | GIT 섹션 최상단 1줄. 포커스된 터미널의 cwd 로 확정한 리포 (FR-GIT-9) |
| **핀 항목** | 사용자가 고정한 리포 (FR-GIT-11) |
| **선택(selection)** | 일괄 동작(스테이지·언스테이지·버리기)의 대상 집합 |
| **포커스 행** | 선택 안에서 마지막으로 클릭한 행. 미리보기가 이 행을 보인다 |

## 2. 전반 기술 (Overall Description)

### 2.1 근거 (Rationale)

Git 창을 일반 창처럼 다룬 원 설계(FR-GIT-27·30)의 의도는 "특수 창을 새로 배우게
하지 않는다" 였다. 실사용에서 그 대가가 드러났다:

- Git 창 안에서 터미널을 띄우고 편집기를 열 수 있으니 **Git 창이 또 하나의 작업
  창**이 된다. Git 을 창으로 분리한 의도(단일 리포·싱글턴·고정 탭)가 흐려진다.
- WINDOWS 목록에 `Git` 이 섞여 있어 **진입점이 둘**이다. 사용자는 GIT 섹션의 리포
  목록을 진입점으로 쓰는데, 창 목록의 `Git` 은 "어느 리포인지 모르는 창"이다.

따라서 Git 창을 **닫힌 창**으로 다시 정의한다: 고정 탭 6개만 있고, 진입은 리포
항목으로만 한다.

### 2.2 제약 (Constraints)

- 창 데이터 모델의 `type`(FR-GIT-25)과 싱글턴(FR-GIT-26)은 그대로다.
- 활성 내부 탭·활성 리포의 영속(FR-GIT-29)과 브로드캐스트(FR-GIT-31)도 그대로다.
- 기존 워크스페이스에 이미 Git 창 안의 터미널·편집기 탭이 있을 수 있다 — 하위호환
  처리가 필요하다 (FR-GIT-189).

## 3. 요구사항 (Requirements)

### 3.1 폐기 (Withdrawn)

|---|---|---|
| **FR-GIT-27** | "Git 창은 일반 창이다 — 사용자가 그 안에서 분할해 터미널 탭을 배치할 수 있어야 한다" | §2.1. FR-GIT-179 가 대체한다 |
| **FR-GIT-30** | "Git 창은 다른 창과 마찬가지로 창 목록·창 전환 단축키의 대상이다" | §2.1. FR-GIT-181 가 대체한다 |

### 3.2 개정 (Amended)

- **FR-GIT-13 (개정)** 좌측 사이드바는 GIT 섹션을 가지며 follow 1개와 핀 목록,
  `+ Add` 진입점을 표시한다. **표식에 이모지를 쓰지 않는다** (FR-GIT-187·188).
- **FR-GIT-41 (개정)** 파일 우클릭의 `Open File` 은 **Git 창이 아닌 창**에 편집기
  탭을 열고 그 창을 활성화한다 (FR-GIT-185).
- **FR-GIT-69 (개정)** 파일 다중 선택의 수단은 체크박스가 아니라 **행 클릭 +
  보조키**다 (FR-GIT-183).
- **FR-GIT-35 (개정)** 상태는 `git status --porcelain=v2 -z --branch
  --untracked-files=all` 을 파싱해 얻는다. 기본값(`normal`)은 추적되지 않는
  디렉터리를 접어 **안의 파일을 보이지 않게 한다** (FR-GIT-215).
- **FR-GIT-28 (개정)** 고정 탭 6개는 그대로다. `Console` 은 **더 이상 "준비 중"이
  아니다** — 실행 기록을 보인다 (FR-GIT-218).

### 3.3 신규 — Git 창의 경계

- **FR-GIT-179** Git 창은 **닫힌 창**이다. 내부는 고정 탭 6개
  (`Changes / Diff / History / Branches / Stash / Console`)뿐이며, 사용자는 그 안에
  분할 칸을 만들거나 탭을 더할 수 없다.
- **FR-GIT-180** Git 창이 활성인 동안 분할·새 탭 진입점은 **동작하지 않고 화면에도
  보이지 않는다**: 상단 바의 `Split H`·`Split V`, 탭 행의 `+`, 단축키
  `splitH`·`splitV`·`newTab`, 모바일 상단의 `+`.
  - 근거: 눌리지만 아무 일도 하지 않는 버튼은 고장으로 읽힌다. 자리를 없앤다.
- **FR-GIT-181** 다른 창의 탭을 끌어다 Git 창에 놓을 수 없다. 드래그 중 Git 창의
  탭 행·본문은 드롭 대상으로 표시되지 않는다.
- **FR-GIT-182** Git 창은 WINDOWS 목록에 표시하지 않으며, 창 전환 단축키
  (`windowNext`·`windowPrev`)의 순환 대상이 아니다. **유일한 진입점은 GIT 섹션의
  리포 항목이다** (FR-GIT-15).
- **FR-GIT-183** Git 창을 닫는 수단은 Git 창 자신의 상단 바에 둔다 — WINDOWS 목록의
  `×` 가 사라지기 때문이다. 닫은 뒤 리포 항목을 다시 클릭하면 새로 만들어진다
  (FR-GIT-26 유지).
- **FR-GIT-184** Git 창이 활성인 동안에도 WINDOWS 목록의 다른 창은 클릭으로 갈 수
  있어야 한다. Git 창에서 나가는 길이 항상 있어야 한다.
- **FR-GIT-185** `Open File` 의 대상 창은 **직전에 활성이었던 일반 창**이다. 그런
  창이 없으면 새로 만든다. 연 뒤 그 창을 활성화한다 — 열었는데 보이지 않으면
  사용자는 실패로 읽는다.
- **FR-GIT-186** 이 개정 이전에 만들어져 Git 창 안에 터미널·편집기 탭을 가진
  워크스페이스는 로드 시 그 탭들을 **일반 창으로 옮긴다**. 조용히 버리지 않는다 —
  사용자의 작업 상태다.

### 3.4 신규 — 파일 목록의 선택

- **FR-GIT-187** 파일 행의 체크박스를 없앤다. 선택은 행 자체로 한다. 그룹 머리의
  일괄 버튼(`모두 스테이지` 등, FR-GIT-66~68)은 그대로 둔다 — 선택과 무관한 별개의
  진입점이다.
- **FR-GIT-188** 선택 조작 (FR-GIT-52 의 클릭 의미를 유지한다):

  | 조작 | 선택 | 미리보기 |
  |---|---|---|
  | 클릭 | 그 행 **하나로 바꾼다** | 그 행 |
  | `Cmd`/`Ctrl` + 클릭 | 그 행을 **토글**한다 | 그 행 |
  | `Shift` + 클릭 | 앵커부터 그 행까지 **범위**로 바꾼다 | 그 행 |
  | 더블클릭 | 바뀌지 않는다 | Diff 탭으로 연다 (FR-GIT-52) |

  - 앵커는 마지막으로 보조키 없이 클릭한 행이다. 범위는 화면에 보이는 순서를
    따르며 그룹 경계를 넘는다 (기존 FR-GIT-69 규약 유지).
- **FR-GIT-189** 선택된 행은 배경 강조로, **포커스 행은 그것과 구분되는 표식**으로
  보인다. 둘을 같게 그리면 미리보기가 어느 행을 보이는지 알 수 없다.
- **FR-GIT-190** 일부만 스테이지된 파일(FR-GIT-70)의 표시는 체크박스의
  indeterminate 가 아니라 **행의 상태 문자 색**으로 한다.
- **FR-GIT-191** 선택은 status 에 남아 있는 경로만 뜻한다 (기존 동작 유지) —
  사라진 경로의 선택은 저절로 잊힌다.

### 3.4.1 신규 — 동작의 진입점

지금은 **선택 동작 줄**(파일 목록 위의 `Stage`·`Unstage`·`Discard`·`Clear`)과
**행 인라인 버튼**(`+`·`−`·`↺`)이 같은 일을 두 자리에서 한다. 화면이 무거워지고,
"이 버튼은 무엇을 대상으로 하나"가 자리마다 달라 읽히지 않는다.

- **FR-GIT-207** 선택 동작 줄을 **없앤다**. 스테이지·언스테이지·버리기의 진입점은
  **행 인라인 버튼 하나**다 (그룹 머리의 일괄 버튼 FR-GIT-66~68 은 그대로 둔다).
- **FR-GIT-208** 행 인라인 버튼의 **대상은 클릭한 행이 선택에 들어 있는지로
  정한다**:

  | 상황 | 대상 |
  |---|---|
  | 클릭한 행이 현재 선택에 **들어 있다** | **선택된 행 전체** |
  | 클릭한 행이 선택에 **없다** | 그 행 하나 |
  | 선택이 비어 있다 | 그 행 하나 |

  - 선택 전체가 대상일 때도 그 동작이 뜻을 갖는 행만 남긴다 (기존 `_selTargets`
    규약 유지) — staged 행을 stage 하거나 untracked 행을 unstage 하는 것은 아무
    일도 하지 않는다.
- **FR-GIT-209** `Clear`(선택 해제) 버튼을 없앤다. 다른 행을 평클릭하면 선택이 그
  행으로 바뀌므로(FR-GIT-188) 해제만을 위한 자리가 필요 없다.

### 3.4.2 신규 — 목록의 구조가 보이게

- **FR-GIT-211** 트리 보기에서 **깊이를 세로선으로 보인다**. 들여쓴 단계마다 선이
  하나씩 서고, 깊이 0 인 행에는 선이 없다.
  - 트리 보기의 행은 중첩 DOM 이 아니라 **패딩으로 들여쓴 평평한 목록**이다
    (`_emitDir` 이 depth 를 `padding-left` 로 접는다). 그래서 선은 조상 요소가
    아니라 **행 자신의 배경**으로 그린다 — 행마다 깊이를 실어 그 수만큼 반복한다.
  - 들여쓰기 단위(12 px)와 선 위치는 한 곳에서 나온다. 두 곳에 적으면 한쪽만
    고쳐져 선이 글자와 어긋난다.
- **FR-GIT-212** `Conflicts`·`Staged`·`Changes`·`Untracked` 그룹은 **선으로
  나뉜다**. 첫 그룹 위에는 선이 없다 — 목록의 시작이지 경계가 아니다.

### 3.4.2.1 개선 — 섹션 경계가 행 구분선과 구별되지 않는다

**증상**(사용자 검토): Changes 에서 섹션(그룹)이 나뉘는 자리를 알아보기 어렵다.
"색이나 두께로 구분해 달라." **다른 화면의 섹션 경계도 마찬가지다.**

**원인**: FR-GIT-212 가 그은 선이 `1px solid var(--border)` 로, 화면의 다른 선과
**완전히 같다.** 같은 굵기·같은 색이면 그것이 섹션의 시작인지 그저 또 하나의 선인지
읽히지 않는다. Branches 의 그룹(로컬·원격·태그)과 History 의 refs 그룹은 아예 선이
없어 머리글의 크기만으로 구분해야 한다.

- **FR-GIT-216** 섹션 경계는 **행 구분선과 다르게** 그린다: 굵기 **2 px**, 색은
  `--border` 보다 **진한** 것을 쓴다.
  - 진한 색은 팔레트에서 빌리지 않고 **`--border` 를 `--text` 쪽으로 섞어 만든다**
    (`--border-strong`). `--text-dim` 같은 기존 토큰을 빌리면 테마마다 밝기 관계가
    달라 어떤 테마에서는 오히려 흐려진다. 섞으면 밝은 테마·어두운 테마 모두에서
    바탕과의 대비가 **반드시 커진다**. 색을 하드코딩하지 않는 규약(FR-GIT-119)은
    그대로다.
  - 적용 자리: Changes 그룹(FR-GIT-212), Branches 그룹, History 의 refs 그룹,
    사이드바의 `WINDOWS ↔ GIT` 경계, GIT 섹션의 `follow ↔ 핀` 경계(FR-GIT-193).
  - **대상이 아닌 것**: Branches 의 접두사 묶음(`feature/…`)은 그룹 **안**의 하위
    묶음이지 섹션이 아니다. Stash 는 그룹이 없다. 값은 한 곳(`--git-sec-divider`)에
    두어 자리마다 달라지지 않게 한다.
  - 첫 섹션 위에는 여전히 선이 없다 (FR-GIT-212 유지).

### 3.4.3 신규 — 커밋 영역의 정렬

지금은 입력창 **오른쪽**에 세로 칸을 두고 `amend` 를 위, `Commit` 을 아래로
`space-between` 으로 밀어 둔다. 입력창은 입력에 따라 자라므로(FR-GIT-74) **둘
사이 간격이 계속 달라지고**, 어느 것과도 가로줄이 맞지 않는다.

- **FR-GIT-213** 커밋 입력창은 **폭을 다 쓰고**, `amend`·서명 표시·`Commit` 은 그
  **아래 한 줄에 왼쪽으로 모여** 선다.
  - 입력창 높이가 변해도 그 줄의 정렬은 변하지 않는다.
  - 양끝으로 밀지 않는다 — 한 벌로 쓰는 것들이 화면 폭만큼 멀어지면 서로 상관없는
    것처럼 보인다. 파일 목록이 왼쪽이므로 눈이 그쪽에서 내려온다.

### 3.5 신규 — GIT 섹션의 표식

- **FR-GIT-192** GIT 섹션 항목은 **이모지를 쓰지 않는다**. 상태 표식은 WINDOWS
  목록의 점(`.si-dot`)과 **같은 어휘**다: 활성 리포는 accent 로 채운 점, 그 밖에는
  흐린 점.
- **FR-GIT-193** follow 항목과 핀 항목의 구분은 표식이 아니라 **배치**로 한다.
  follow 는 항상 최상단 1줄이고, 그 아래에 얇은 구분선을 둔다.
- **FR-GIT-194** 저장소가 아닌 follow 항목은 흐리게 보이고 점을 그리지 않는다 —
  가리키는 리포가 없으므로 상태가 없다 (FR-GIT-10 유지).

### 3.5.1 결함 — follow 가 서버의 cwd 로 넘어간다

**증상**: dongminal 과 아무 상관 없는 디렉터리에서 follow 항목을 눌러 Git 창에
들어가면, follow 줄이 곧바로 `dongminal` 로 바뀐다.

**원인**: follow 는 "포커스된 터미널 칸의 도구"(`?tool=`)로 정해지는데, 포커스가
터미널이 아니면(Git 창·편집기 탭) 빈 값이 가고 **서버가 자기 cwd 로 답한다**
(`gitFollowCwd`). 서버의 cwd 는 dongminal 을 띄운 자리이므로 사용자가 가 본 적
없는 리포가 뜬다. FR-GIT-182 로 Git 창 진입이 잦아지며 늘 보이게 됐지만, 원인은
그 전부터 있었다.

- **FR-GIT-210** 포커스가 터미널이 아닐 때 follow 는 **마지막으로 포커스됐던
  터미널**의 cwd 를 유지한다. 서버의 cwd 로 넘어가지 않는다. 그 터미널이 사라졌으면
  follow 는 "저장소 아님"이다 — 임의의 리포를 가리키지 않는다 (FR-GIT-10 과 같은
  뜻이다).

### 3.5.2 신규 — GIT 섹션의 간격

**증상**(사용자 검토): 좌측 GIT 섹션에서 리포 목록과 `+ Add` 가 **딱 붙어** 있고,
`+ Add` 와 설정(⚙)도 붙어 있다. 세 덩이가 한 덩이로 읽혀 목록의 마지막 행이
버튼처럼, `+ Add` 가 설정의 일부처럼 보인다.

**원인**: `#git-repos` 에 아래 여백이 없고(간격 0), `#git-add-repo` 의 아래 여백은
WINDOWS 버튼들과 공유하는 4 px 뿐이다. WINDOWS 는 **버튼이 목록 위**에 있어 같은
값이어도 이 문제가 생기지 않는다 — 순서가 다른 GIT 섹션에서만 드러난다.

- **FR-GIT-214** GIT 섹션은 **목록 → `+ Add` → 설정(⚙)** 순으로 놓이며, 이웃한
  덩이 사이에 여백을 둔다. 목록과 `+ Add` 사이는 **6 px 이상**, `+ Add` 와 ⚙
  사이는 **10 px 이상**이다. 뒤쪽이 더 넓은 것은 ⚙ 이 GIT 섹션에 속하지 않기
  때문이다 — 같은 값을 주면 세 덩이가 같은 무리로 읽힌다.

### 3.5.3 결함 — untracked 디렉터리가 이름 없는 행으로 보인다

**증상**(사용자 검토): Untracked 그룹에 `?` 만 있고 **이름이 없는 행**이 있다.
클릭해도 아무것도 뜨지 않는다. 실제로는 그 자리에 `.md` 파일이 있다.

**원인**: 서버가 `git status --porcelain=v2 -z --branch` 를 그대로 쓴다
(FR-GIT-35). `--untracked-files` 의 git 기본값은 `normal` 이고, 그것은 **추적되지
않는 디렉터리를 `newdir/` 한 줄로 접는다** — 안의 파일을 하나도 열거하지 않는다
(git 2.50.1 실측). 클라이언트는 항목이 파일이라고 전제하므로:

- 트리 보기의 이름은 `path.split('/').pop()` 인데 `'newdir/'` 은 **빈 문자열**이다.
- 클릭하면 디렉터리 경로로 diff 를 걸어 양쪽 모두 없는 것이 되어 아무것도 못 그린다.
- 배지의 "변경 파일 수"(FR-GIT-14, 해석 I3)가 디렉터리 하나를 **1** 로 세어
  실제 파일 수와 어긋난다.

**고칠 자리는 클라이언트가 아니다.** FR-GIT-34 가 분류 대상으로 못박은 것은
"변경 **파일**" 이고, 디렉터리를 파일처럼 그리는 것은 그 문면을 만족하지 못한다.
git 에게 파일을 달라고 해야 한다.

- **FR-GIT-215** status 조회는 `--untracked-files=all` 을 함께 준다. 추적되지 않는
  디렉터리를 접지 않고 **그 안의 파일을 개별로** 열거한다. **FR-GIT-35 를 개정한다**
  — 명령은 `git status --porcelain=v2 -z --branch --untracked-files=all` 이다.
  - 대가: 추적되지 않는 큰 디렉터리가 있으면 status 가 그만큼 걷는다. 받아들이는
    이유는 ① 그 값은 사용자가 `.gitignore` 로 정하는 것이고 ② 접힌 목록은 보이지도
    열리지도 세어지지도 않아 **기능이 아예 없는 것과 같기** 때문이다.
  - `--ignored` 는 여전히 주지 않는다 (기존 결정 유지).

### 3.5.4 결함 — 취소된 요청이 500 으로 기록된다

**증상**(21단계 실사, `GIT_REMAINING §1`): 페이지를 새로고침할 때마다 서버 로그에
`/api/git/status`·`/signature`·`/refs` 가 **500** 으로 서너 줄 남는다. 본문은
`{"error":"git_failed","message":"git rev-parse --show-toplevel: signal: killed"}`.

**진단**: 브라우저가 언로드하며 **취소한** 요청이다. 핸들러가 `r.Context()` 를
그대로 git 실행에 넘기므로 요청이 끊기면 `exec.CommandContext` 가 git 을 SIGKILL
하고, 그 오류가 500 이 된다. 화면에는 영향이 없다 — 같은 순간의 폴링 60회는 전부
200 이었다. 문제는 **진짜 장애와 로그에서 구분되지 않는다**는 것이다.

**이미 반쪽은 있다**: `execGit` 은 `context.DeadlineExceeded` 를 `ErrTimeout` 으로
갈라 504 로 마감한다. 취소는 그 대칭인데 빠져 있다.

- **FR-GIT-217** 실행이 **호출자의 취소**로 끝나면 `ErrCanceled` 로 갈라 올린다.
  서버는 이를 **499**(client closed request)로 마감한다. 500 으로 낮추지 않는다 —
  서버가 실패한 것이 아니라 요청이 사라진 것이고, 둘을 같은 코드로 적으면 로그가
  장애를 가린다.
  - `signal: killed` 라는 문면으로 판정하지 않는다. 그 문면은 사용자가 보낸 진짜
    kill 과 구분되지 않는다 — **`ctx.Err()` 이 `context.Canceled` 인지**로 가른다.
    `DeadlineExceeded` 판정보다 뒤에 둔다: 마감 초과는 이미 뜻이 정해진 취소다.
  - 499 는 표준 코드가 아니라 nginx 관례다. Go 에 상수가 없으므로 서버에 이름을
    두고 그것만 쓴다.

### 3.5.5 신규 — Console 탭을 채운다

**질문**(사용자 검토): "console 이 다음에 추가된다고 나와 있는데 **어차피 dongminal
이 콘솔인데** 굳이 필요한가?"

**분석**: Console 탭은 터미널이 아니다. `Recorder`(FR-GIT-5)가 담는 것은 **dongminal
이 사용자를 대신해 실행한 git 명령**이고, 그것은 서버 프로세스 안에서 돌기 때문에
사용자의 터미널에서는 볼 수 없다. 실행 **전**은 2단계 확인이, **실패**는 recovery
hint(FR-GIT-92)가 이미 명령을 보인다. 비어 있는 것은 **성공한 쓰기의 이력**이다 —
discard·clean·checkout 이 실제로 무엇을 지웠는지 되짚을 자리가 없다.

기록은 이미 다 있다(argv·cwd·exit·소요·stderr·파괴적 여부·stdin 바이트). 없는 것은
그것을 내보내는 길과 보이는 화면뿐이다. **사용자 결정: 이름은 `Console` 그대로 두고
구현한다.**

- **FR-GIT-218** Console 탭은 **현재 리포에서 dongminal 이 실행한 git 명령의 기록**을
  최신이 위로 오도록 보인다. **FR-GIT-28 의 "준비 중"을 해제하고, `GIT_SRS §5` 의
  비목표("Console 탭 표시는 P1")를 MVP 로 올린다.**
  - 한 줄에 시각 · argv · exit · 소요(ms)를 싣고, 실패(exit≠0)와 파괴적 실행
    (FR-GIT-95 의 선언, 해석 I5)은 표식으로 구분한다. 펼치면 cwd·stderr 를 본다.
  - 서버는 `GET /api/git/records?repo=&n=` 로 낸다. **리포로 거른다** — Git 창은
    리포 하나에 매인 창이고, 다른 리포의 실행이 섞이면 이력이 아니라 잡음이다.
    거르는 기준은 요청값이 아니라 `rev-parse` 로 확정한 루트다 (FR-GIT-62).
  - **자격증명은 내보내지 않는다** (FR-GIT-104, 보안 기준 S.1·S.2). argv 와 stderr
    에서 `scheme://user:secret@host` 꼴을 지운 뒤 보낸다. git 이 스스로 가려 주는
    버전에 기대지 않는다 — 가려 주지 않는 경로가 하나라도 있으면 토큰이 화면과
    브라우저 캐시로 흐른다.
  - **stdin 내용은 여전히 남기지 않는다** (해석 I6). 커밋 메시지는 바이트 수뿐이다.
  - 상한은 `Recorder` 의 링 버퍼가 이미 정한다 (FR-GIT-6). 화면이 상한을 새로
    발명하지 않는다.
  - **폴링을 기본에서 감춘다.** status 폴링(FR-GIT-18~24)은 1초에 한 번 기록되므로,
    거르지 않으면 500칸 버퍼가 `status --porcelain=v2 …` 로만 차서 이력이 아니라
    벽지가 된다. 기본은 **쓰기만** 보이고, 토글로 읽기까지 본다.
    - 쓰기 판정은 새로 만들지 않는다 — `writeCommands`(FR-GIT-95)가 이미 그 목록
      이고, 두 경로를 가르는 바로 그 기준이다. 기록 한 줄이 자기가 쓰기였는지를
      싣는다.
    - 실패(exit≠0)는 읽기라도 감추지 않는다. 사용자가 Console 을 여는 이유가
      대개 그것이다.

### 3.6 신규 — 컨트롤 치수

지금 치수를 실측한 결과다 (데스크톱 1440×900, 기본 테마):

| 요소 | 현재 | VSCode 기준 |
|---|---:|---:|
| 파일 행 (`.git-file`) | **17px** | 22px (list row) |
| 행 인라인 버튼 (`.git-file-act`) | **18×15** | 22×22 (action bar item) |
| 그룹 일괄 버튼 (`.git-group-bulk`) | 77×**17**, 글꼴 **10px** | 26px |
| Fetch·Pull·Push (`.git-remote-btn`) | 46×**19** | 26px |

- **FR-GIT-195** Git 표면의 **누를 수 있는 모든 컨트롤**은 최소 히트 영역
  **22×22 px** 을 갖는다. 아이콘 하나짜리 버튼(`▾`, `‹`, `›`, `+`, `−`, `↺`)이
  여기 해당한다.
- **FR-GIT-196** 라벨을 가진 버튼(Fetch·Pull·Push·Commit·트리·플랫·일괄·선택

- **FR-GIT-197** 목록 행(파일·GIT 섹션 리포·브랜치·stash)은 최소 높이 **22 px** 을
  갖는다. 파일 행은 FR-GIT-187 로 **행 자체가 클릭 대상**이 되었으므로 히트 영역이
  곧 행 높이다.
- **FR-GIT-198** 컨트롤 라벨의 글꼴은 **11 px** 미만이 되지 않는다. 목록 본문은
  **12 px** 미만이 되지 않는다.
- **FR-GIT-199** 모바일(FR-GIT-94)의 치수는 위 값 **이상**이어야 한다 — 좁은 화면
  에서 작아지면 터치가 어긋난다.

**비대상**: 앱 전역의 `.tbtn`(22px), `.si`(30px), `.pn-tab`(27px), 상태바는 이
개정의 범위가 아니다. 탭 높이는 터미널 창과 공유하므로 별건으로 다룬다.

### 3.7 신규 — 버튼 라벨의 언어

- **FR-GIT-200** Git 표면의 **버튼 라벨은 영어**로 쓴다. `스테이지`·`언스테이지`·
  `버리기`·`모두 스테이지`·`해제`·`트리`·`플랫`·`실행`·`취소`·`복사`·`닫기`·
  `적용`·`이동`·`생성`·`되돌리기`·`다시 시도` 등이 대상이다.
  - 근거: git 자체의 어휘(stage·unstage·discard·stash·amend)가 영어이고 화면에
    이미 `Fetch`·`Pull`·`Push`·`Commit`·`Apply`·`Pop`·`Drop` 이 영어로 서 있다.
    같은 줄에서 한글과 영어가 섞이면 어느 것이 git 명령인지 흐려진다.
- **FR-GIT-201** 다이얼로그의 **선택지 버튼**도 같다 (dirty checkout 3선택,
  이름 충돌 선택지).
- **FR-GIT-202** **버튼이 아닌 것은 바꾸지 않는다** — 안내문·사유·오류 메시지·
  placeholder·툴팁(`title`)·그룹 머리는 한글로 남는다. 그것들은 설명이고, 설명은
  읽는 사람의 말이어야 한다.

### 3.8 신규 — 폼 컨트롤의 테마

지금은 체크박스·라디오가 **브라우저 기본 위젯**이다. 앱의 테마(44종)와 무관한 색
으로 그려져 어두운 테마에서 흰 사각형이 튀고, 라이트 테마에서도 앱의 accent 와
어긋난다. 실제로 보이는 자리: 커밋의 `amend`, 커밋 옵션 3개(sign-off·no-verify·
commit all), Fetch·Pull·Push 의 `▾` 옵션, Diff 의 `Ignore Whitespace`, stash 생성
옵션 2개, 브랜치 생성의 checkout 옵션, 설정 모달의 알림 항목.

- **FR-GIT-203** 체크박스·라디오는 **앱 테마의 토큰**(`--bg`·`--border`·`--accent`)
  으로 그린다. 브라우저 기본 위젯을 그대로 쓰지 않는다.
- **FR-GIT-204** 상태는 **채움**으로 구분한다: 꺼짐은 빈 상자(투명 바탕 +
  `--text-dim` 테두리), 켜짐은 accent 로 **꽉 찬** 상자다. **체크 표식(✓)을 그리지
  않는다.**
  - 근거: 14 px 상자 안의 획은 어떤 방식으로 그려도(회전 테두리·SVG 마스크·
    clip-path·글리프) 끝이 뭉툭하거나 비율이 어긋나 지저분하다 — 4종을 실제로
    그려 비교한 결과다.
  - 비었나 찼나는 색이 아니라 **면적**의 차이이므로 흑백으로 떨어뜨려도 남는다.
    비활성은 흐림, 포커스는 윤곽선으로 따로 구분한다.
- **FR-GIT-205** `select` 도 같은 토큰으로 그린다.
- **FR-GIT-206** 컨트롤 상자는 **14 px**, 그것을 담은 라벨 행은 **22 px** 이상이다.
  히트 영역은 상자가 아니라 행 전체다 — 상자를 키워 라벨보다 무겁게 만들지 않는다.

**범위 주의**: 이 요구는 Git 표면만이 아니라 **앱 전역**이다. 컨트롤을 두 벌로
그리면 같은 체크박스가 자리마다 달라 보인다.

## 5. 결정 (Decisions)

| # | 결정 | **확정값** | 근거 |
|---|---|---|---|
| O15 | `Open File` 의 대상 창 | **직전 활성 일반 창**, 없으면 새로 만든다 | "어디에 열렸는지 모르겠다"를 피하려면 규칙이 하나여야 한다. 새로 만드는 쪽이 거절보다 낫다 — 사용자는 파일을 보려고 눌렀다 |
| O16 | Git 창 닫기 자리 | **Git 창 상단 바** (`Split H`·`Split V` 가 사라진 자리) | WINDOWS 의 `×` 가 사라지므로 닫는 길이 없으면 한 번 연 창을 영원히 못 닫는다 |
| O17 | 선택 표식 | 선택 = 배경 채움, 포커스 = 좌측 세로 바 | 배경 둘을 농도로만 구분하면 테마에 따라 구분이 사라진다. 형태가 다르면 어느 테마에서도 남는다 |
| O18 | GIT 섹션 점의 뜻 | **활성 리포 여부만** | follow·핀 구분은 배치가 이미 한다(FR-GIT-193). 점 하나에 두 뜻을 실으면 둘 다 읽히지 않는다 |
| O19 | 하위호환 이관 대상 창 | **첫 번째 일반 창**, 없으면 새로 만든다 | O15 와 같은 규칙. 규칙이 둘이면 어느 쪽인지 예측할 수 없다 |

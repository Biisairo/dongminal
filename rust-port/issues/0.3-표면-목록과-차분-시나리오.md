# 0.3 관측 표면 목록과 차분 시나리오 카탈로그

## 목표

이후 이슈가 "무엇이 같아야 하는가"를 빠짐없이 알 수 있게, Go 기준선의 관측 표면 전수 목록을 만들고 차분 시나리오로 옮긴다.

1. `rust/parity/SURFACE.md` 에 표면 전수 목록을 만든다. 각 항목에 담당 이슈 ID 를 단다.
   - 제어 CLI(`internal/ctl/cli`)의 모든 하위 명령과 옵션
   - 런타임 헬퍼(`internal/helper/runtimebin`)의 모든 명령(dmctl·edit·download·detach·chat-mcp)과 옵션
   - HTTP 라우트 전부(메서드·경로·담당 Go 핸들러 파일). `httproute`·`httpapi`·`gitapi` 의 등록 지점에서 뽑는다
   - WebSocket·SSE 엔드포인트와 이벤트 이름
   - IPC 소켓(paned·chat·dial·node·report 등)과 메시지 종류
   - 홈 아래 파일(`homeLayout()` 표 기준)
   - 읽는 환경변수
2. 격리 실행에서 안전하게 돌릴 수 있는 것부터 차분 시나리오로 만든다. 우선순위: 모든 CLI 명령의 `--help`·인자 오류·알 수 없는 명령 → 서버를 띄운 뒤 읽기 전용 HTTP GET → 홈 파일 생성 결과.
3. 아직 Rust 쪽이 구현되지 않은 시나리오는 담당 이슈 ID 로 표시해, `dm-parity` 가 "담당 이슈가 done 이 아닌 시나리오"를 실패가 아니라 보류로 보고하게 한다.
4. 모든 시나리오는 `run.sh --self-test`(Go 대 Go)로 결정론적임을 확인한다.

## 완료 조건

- SURFACE.md 의 각 항목에 담당 이슈가 있다. 담당 이슈를 정할 수 없는 항목은 조정자에게 알린다
- CLI `--help`·인자 오류 시나리오가 모든 명령에 대해 있고, Go 대 Go 자체 검사를 통과한다
- 운영 인스턴스를 건드리는 명령(service·uninstall·update·rollback 의 실제 실행 경로)은 시나리오에 넣지 않거나, 격리 실행에서 안전함을 진행 기록에 근거로 적는다
- `cargo fmt --check`, `cargo clippy -D warnings`, 격리 실행 `cargo test -p dm-parity` 통과
- 작업 전후 `rust/scripts/prod-pids.sh` 출력이 같다

### 결과 요약

- **표면 목록** `rust/parity/SURFACE.md`. 모든 항목에 담당 이슈를 달았다. 담당을 정하지 못한 항목은 없다. 담고 있는 내용은 다음과 같다.
  - 제어 CLI: 액션 16개, 옵션, 최상위 분기
  - 런타임 헬퍼: argv0 6개, dmctl 하위 명령 전부, run·edge·account 하위 명령
  - HTTP: 최상위 mux 7개, 라우트 226개(메서드·경로·핸들러 파일:줄·담당·도메인 이슈)
  - WebSocket·SSE: 엔드포인트 5개, `/ws` 바이너리 op, SSE action 이름 전부
  - IPC 소켓: 7개와 프레이밍, 메시지 종류, handover fd
  - 홈 파일: `homeLayout()` 전부와 표에서 빠진 항목
  - 환경변수: 읽는 것과 자식 프로세스에 심는 것
  - 환경 의존 값, 시나리오 목록, 안전 근거
- **차분 시나리오 44개** (`src/scenarios/{cli,helper,http,home}.rs`). 모두 담당 이슈를 단다.
  - CLI 36개: 최상위 5개, 액션마다 `-help`·`-args` 15쌍, `cli-otp`
  - 헬퍼 3개
  - HTTP GET 3개: api 54단계, git 27단계, 정적 3단계
  - 홈 파일 2개
- **Go 대 Go 결과**: 3회 연속 44개 모두 같았다. `run.sh --self-test` 도 통과했다. Go 대 Rust(빈 껍데기)는 `같음 0, 다름 0, 보류 44` 이고 종료 코드는 0 이다.
- **dm-parity 에 더한 것** (공개 API)
  - `Scenario::owner(id)`·`owner_issue()`
  - `issues::{load_status, verdict, Verdict::{Same,Differ,Pending}}`
  - `dm-parity --issues <폴더>` 와 환경변수 `DM_PARITY_ISSUES`. 결과는 `ok`·`DIFF`·`PEND` 로 찍고, 마지막 줄에 `같음/다름/보류` 를 센다
  - `--list` 는 이름과 담당 이슈를 찍는다
  - `run.sh` 는 `<저장소>/rust-port/issues` 를 넘긴다(`DM_PARITY_ISSUES` 로 바꿀 수 있다)
- **안전 장치 C-PAR-7** (실행기가 검증한다): argv0 가 `dmctl`·`edit`·`detach`·`open-url` 인 단계는 같은 시나리오의 앞에 `serve` 가 있어야 한다. 헬퍼는 격리 홈에 주소 파일이 없으면 `serverconf` 기본 포트로 붙으므로, 운영 서버에 요청이 갈 수 있기 때문이다. argv0 `claude`·`dongminald` 는 거절한다.
- **운영 인스턴스를 건드리는 명령의 근거** (SURFACE.md 9.2)
  - `stop`·`service`·`uninstall`·`update`·`rollback`·`restore`·`migrate`·`backup` 은 도움말과 파서 오류만 넣었다. `Parse*` 가 첫 잘못된 인자에서 오류를 내고, `settle` 은 이때 액션을 부르지 않는다. 코드를 읽어 확인했다.
  - 자기 검증 `go_observations_match_scenario_intent` 가 다음을 실측으로 확인한다: `cli-*-args` 의 종료 코드는 모두 2, `cli-*-help` 는 모두 0, `helper-*` 는 0·2 뿐(요청까지 가지 않았다), 서버 시나리오에 `error` 관측값이 없다.
  - `otp` 는 인자 없음, 도움말, 모르는 하위 명령만 넣었다.
- **테스트**: 단위 33, fake 바이너리 통합 8, 목록 검사 1, Go 자기 검증 2.
- **게이트**: fmt 통과. clippy 는 darwin·windows-msvc·linux-gnu 에서 `-D warnings` 로 통과했다.
- **조정자 결정 반영**: 격리 데몬의 특권 도우미 `info` 조회는 허용되었다. `"helper":true` 는 SURFACE.md 8절에 "환경 의존 값" 으로 표시했다.
- **내린 결정**
  - `cli-no-args` 는 `cli-empty` 로 이름을 바꿨다. `-args` 로 끝나는 이름 규칙과 겹쳤기 때문이다.
  - `/api/stats`·`/api/diag` 는 실행마다 수치가 달라서 GET 시나리오에서 뺐다. WS·SSE·long-poll 도 뺐다.
  - 노드 신원(지문, 태그, 참가자 ID)과 `nextTickAt` 은 `body` 에만 정규화한다.
  - `home-after-start` 의 홈 트리에서는 일시 항목(`paned.*`, `run/`, `.lastexit`, 소켓, 로그, `bin/`, `tool-history/`)을 뺐다. 데몬이 언제 끝났는지에 따라 남거나 사라지기 때문이다(실측).
- **남은 위험·발견**
  - 상태를 바꾸는 라우트, WS·SSE, IPC 프레이밍, 서버에 실제로 요청하는 dmctl 명령에는 아직 시나리오가 없다(SURFACE.md 9.1). 담당 이슈가 단계 종류와 시나리오를 더해야 한다.
  - 기준선 게이트 `scripts/check-home-layout.sh` 는 `SiblingSocket` 으로 만든 소켓 4개(`report`·`chat`·`node`·`dial.sock`)가 `homeLayout()` 에 없는 것을 잡지 못한다.
  - 이슈 worktree 의 `rust-port/issues` 사본은 낡을 수 있다. 정확한 보류 판정에는 `DM_PARITY_ISSUES` 로 통합 worktree 의 폴더를 준다.

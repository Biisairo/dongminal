# 성능 기준선 — 2026-11-24

> 측정 도구: `scripts/perf/scenario.mjs` · `scripts/perf/agent-sim.py`
> 대상: `main` `97e08c62` 의 Rust 판, 격리 인스턴스(포트 61950)
> 기계: Apple M4, 코어 10개. 브라우저: Playwright Chromium 새 헤드리스(GPU Metal 사용)

## 1. 시나리오

| 항목 | 값 |
|---|---|
| 창·탭 | 창 5개, 탭 16개 |
| 보이는 에이전트 | 3개 (첫 창을 세로로 나눈 칸) |
| 숨은 에이전트 | 9개 (다른 창의 탭) |
| 출력 | 에이전트마다 초당 60줄, 5초마다 200줄 몰아치기. TUI 모드는 화면 아래 25줄을 초당 20번 다시 그린다 |
| 단계 | idle(출력 없음), load(출력), contention(load + `yes` × 10), remote(load + 브라우저 CPU 4배 감속 + 망 지연 150ms), long(load 10분) |
| 입력 지연 | 셸 프롬프트에 글자 하나를 치고, 그 글자가 화면에 그려진 프레임까지. 단계마다 20번 |

측정 시 주의: 기본 헤드리스(소프트웨어 WebGL)는 그리기 비용이 부풀려진다. 같은 load 에서 메인 스레드 사용률이 98.5% 대 10.6% 로 달랐다. 새 헤드리스(`channel: 'chromium'`)로 잰다.

## 5. 발견 (순위)

1. **메모리가 출력량만큼 계속 는다.** 스크롤백이 터미널마다 5만 줄(`TERM_SCROLLBACK_LINES`)이고, 보이지 않는 터미널도 모두 브라우저 힙에 보관한다. 에이전트 12개가 10분 만에 힙 85 MB 가 됐고, 계속 늘었다. 몇 시간이면 수백 MB 가 된다. 기계의 RAM 이 빠듯할 때 버벅이는 증상과 맞는다.
2. **보이지 않는 터미널도 모든 일을 한다.** 12개 중 3개만 보이는데 12개 전부의 출력을 받고(TUI 에서 610 KB/초), 해석하고, 버퍼에 쌓는다. 약한 기기를 흉내 낸 remote 단계에서 메인 스레드가 50% 바빴다. 받는 일의 약 75% 가 화면에 나오지 않는다.
3. **아무것도 안 해도 분당 82건을 요청한다.** `/api/ping`·`/api/stats` 3초마다, `/api/runs`·`/api/tools/activity`·`/api/tools/background` 5초마다.
4. **부팅이 요청 338건이다.** 로컬에서는 빠르지만, 원격에서는 HTTP/1.1 동시 연결 6개 제한 때문에 왕복 지연이 곱해진다. 브라우저 탭마다 SSE 가 연결 하나를 계속 붙잡으므로 탭이 늘수록 남는 연결이 준다.
5. **서버·데몬은 병목이 아니다.** CPU 2~3%, 서버 RSS 25 MB 로 일정하다. 데몬 RSS 는 30 MB 에서 멈췄다.

## 6. 재현하지 못한 것

이 기계(M4)의 Rust 판에서는 위 시나리오 모두 입력 p95 가 예산(50 ms) 안이었고 긴 작업도 0이었다. 사용자가 겪는 입력 정지와의 차이로 짐작되는 것:

- 운영은 Go 판이다.
- 실제 사용은 더 무겁다. 편집기·git 창이 함께 열려 있고, 몇 시간씩 켜 둔다. 위 1번의 메모리 증가가 그만큼 커진다.
- 같은 앱을 브라우저 탭·기기 여럿에서 연다. 탭마다 위의 모든 일이 반복된다.
- 기계의 부하가 CPU 가 아니라 메모리 부족(스왑)일 수 있다.

# 2.4.2 간선 relay: edgerelay

## 목표

서버(TCP 노드 포트)와 데몬(노드 소켓·dial.sock) 사이의 중계를 옮긴다. 2.3 의 `Listener::use_listen`(Acceptor)·`Client::via`(Dial)에 붙는다. Go 서버·데몬과 섞어 써도 중계가 되어야 한다.

## 대상 Go 코드

- `internal/shared/edgerelay` (프로덕션 약 395줄)

## 완료 조건

- 대상 Go 코드의 관측 동작을 Rust 가 동등하게 제공한다 (FR-RSP-1·3)
- 관측 동작을 검증하는 Go 테스트가 Rust 테스트로 옮겨져 통과한다 (V-RSP-1)
- `cargo fmt --check`, `cargo clippy -D warnings`, 격리 실행 `cargo test` 통과 (NFR-RSP-4)
- OS 의존 코드가 있으면 windows·linux 대상 `cargo check` 통과 (NFR-RSP-5)
- 작업 전후 `rust/scripts/prod-pids.sh` 출력이 같다 (V-RSP-5)
- 진행 기록에 공개 API 요약과 Go 와 다르게 한 내부 결정이 있다

  - **Go 와 다르게 한 결정**
    1. platform IPC 가 블로킹이라, IPC 연결은 스레드 둘이 tokio duplex 와 잇는 다리(bridge)로 감싼다(연결당 스레드 2). tokio 쪽이 끝나면 쓰기를 닫고 상대 끝을 DRAIN_TIMEOUT(20s)까지 기다린 뒤 닫는다 — Go splice 와 같은 규칙.
    2. 블로킹 accept 는 멈출 때 자기 소켓에 한 번 붙어 깨운다(Go 는 Listener.Close).
    3. Go `Dialer` 의 network 인자(tcp 아님 → errNotTCP)는 없다 — edge `Dial` 은 주소만 받고 늘 TCP 다. Go TestDialerRejectsNonTCP 는 옮기지 않았다. ctx 마감 대신 고정 시한(DIAL_TIMEOUT+5s)을 쓴다(edge Client 가 전체 시한을 따로 건다).
    4. 이름 해석 실패 문구는 `dial tcp: lookup <host>: no such host` 로 고정(Go 는 리졸버 문구).

- 2026-11-23 간헐 실패 해결(커밋 f2119cbb, rp/2.4). **원인**: bridge 의 읽기 스레드(IPC→tokio)가 tokio 쪽에 쓰기 실패하면 IPC 를 `shutdown(Both)` 했다. TLS 서버가 거절 경보를 쓰고 닫는 순간 이것이 돌면, 쓰기 스레드(tokio→IPC)가 아직 내보내지 못한 경보 바이트가 버려져 클라이언트가 `Rejected` 대신 끊김(`Unreachable … connection error`)을 받았다. **고침**: 읽기 스레드는 양방향을 닫지 않고 남은 입력을 읽어 버리며, 닫기는 쓰기 스레드가 다 내보낸 뒤에 한다. 함께 edge `Client` 의 TLS 연결을 `AlertFirst` 로 감쌌다 — 쓰기가 끊김(broken pipe·reset)으로 실패하면 먼저 읽기 쪽 오류(거절 경보)를 본다(Go Transport 가 쓰기 오류 뒤 응답 읽기 오류를 앞세우는 것과 같다). 검증: edgerelay 시험 전체 40회 반복 0회 실패, edge 91·edgemesh 30·relay 13 + Go 상호 운용(edge 1, relay 4) 통과.

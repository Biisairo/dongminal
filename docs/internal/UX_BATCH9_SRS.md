# SRS: 저장·갱신·조합 — 손이 한 일이 화면에 닿지 않는 세 자리 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수된 결함 셋을 고친다. 셋은 기능이 다르지만 사용자에게는 한 가지로 읽힌다 —
**내가 한 일이 화면에 닿지 않는다.**

- **A. 편집기의 `Cmd+S` 가 저장하지 않는다.** 창을 닫을 때는 저장된다.
- **B. Git 화면이 스스로 갱신되지 않는다.** 보고 있는 동안에도 바뀌지 않고,
  새로고침을 누를 때까지 영영 낡은 채다. 수동 새로고침은 언제나 동작한다.
- **C. 한글 조합 중의 키가 순서를 어긴다.** 조합이 끝나지 않은 글자가 있을 때
  `Cmd+←/→` 를 누르면 커서가 먼저 옮겨지고 그 자리에 글자가 찍힌다. 모바일에서는
  입력과 지움을 되풀이하면 글이 통째로 되풀이되거나 어긋난다.

### 1.2 범위 (Scope)

- A: `web/js/ui/file-editor.js`, `web/js/core/helpers.js`(단축키 기본값),
  `web/js/core/app-edsearch.js`(캡처 경로).
- B: `web/js/git/panel-poll.js`·`observer.js`, `web/js/core/app-git.js`.
  서버(`hub/gitwatch.go`)는 **읽기만 한다** — 이 문서는 서버를 고치지 않는다.
- C: `web/js/ui/term-pane.js`.
- 각 묶음의 e2e.

비포함:
- Monaco 버전 변경, xterm 버전 변경.
- git 관측의 주기·백오프 정책 자체(FR-RMS 계열)의 재설계.
- 서버 감시(`GitWatcher`)의 TTL·상한 조정.

### 1.3 정의 (Definitions)

- **관측(observation)**: `/api/git/status` 응답 한 벌. Changes 의 목록과 머리글이
  그것으로 그려지고, 다른 뷰는 그 변화를 계기로 자기 목록을 다시 받는다.
- **자동 갱신의 두 경로**: (1) 주기 폴링 `obs.tick()` → `collect()`,
  (2) 서버 방송 `git_changed` → `_onGitChanged` → `collect()`.
- **표면(surface)**: 그 관측을 실제로 쓰는 화면. Repo 창의 사이드 Changes 이거나
  본문의 git 뷰 탭이다 (FR-RTU-62).
- **조합(composition)**: IME 가 아직 확정하지 않은 입력. `compositionstart` 와
  `compositionend` 사이.

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 A — `Cmd+S` 는 **마지막에 만들어진 편집기**로 간다

`file-editor.js:394-398`

```js
this._editor.addCommand(monaco.KeyMod.CtrlCmd | monaco.KeyCode.KeyS, () => this.save());
```

Monaco standalone 의 `editor.addCommand` 는 인스턴스가 아니라 **전역 keybinding
서비스**에 동적 바인딩을 건다. 편집기를 열 때마다 `_mount` 가 이 등록을 하나씩
더하고, `when` 조건이 없으므로 나중 등록이 앞선다. 그래서 두 번째 편집기를 연 뒤
첫 번째에서 `Cmd+S` 를 누르면 **두 번째 편집기의 `save()`** 가 불린다.

그 편집기가 dirty 가 아니면 `save()` 는 첫 줄에서 되돌아간다:

```js
async save() { if (!this._editor || !this._dirty) return; ... }
```

**아무 일도 일어나지 않는다.** 창을 닫는 경로는 그 뷰의 `save()` 를 직접 부르므로
정상이고, 사용자가 본 비대칭이 정확히 이 모양이다.

### 2.2 A — 이 파일은 이미 반대 규약을 적어 두었다

`file-editor.js:466-469`

> **FR-EKB-5: `addCommand` 로 굳히지 않는다.** 그것은 조합을 코드에 박는 일이고,
> 박으면 설정에서 바꾼 키가 Monaco 안에서만 듣지 않는다 — 위의 keydown 이 그
> 자리를 대신한다.

검색·LSP 여섯 키는 `this.el` 의 capture 리스너(`_edTrySearchKey`)로 옮겨졌고
(`file-editor.js:439`), 그 여섯은 `SHORTCUT_DEFAULTS` 에 있어 설정에서 바꿀 수
있다. **저장만 옛 방식으로 남았고**, 그래서 목록에도 없다 (`helpers.js:237-277`).

### 2.3 B — 자동 갱신의 두 경로는 **한 뿌리**에 매달려 있다

```
주기 폴링 ─┐
           ├─→ collect() ─→ _applyStatus() ─→ paintAll / reloadViewsAll / reloadDiffAll
서버 방송 ─┘
```

그리고 서버 방송은 폴링에 **의존한다**. 서버는 `/api/git/status` 요청 하나를
"관심 표명" 으로 받아 그 저장소를 90초 동안만 감시하기 때문이다
(`gitapi/handlers_git.go:417` → `hub.GitWatcher.Note`, `GitWatchTTL = 90s`).
브라우저의 폴링 주기는 30초다 (`GIT_STATUS_POLL_MS`).

**폴링이 멎으면 방송도 90초 뒤 함께 멎는다.** 두 경로가 아니라 하나였다.

### 2.4 B — 폴링은 조건이 거짓이면 **완전히 멈추고**, 스스로 깨어나지 않는다

`panel-poll.js:291`

```js
_applyCadence(){ if(!this._pollOk()){ this._stop(); return false } ... }
```

`_pollOk()`(244-259)는 `document.hidden`, 저장소 소실, **창이 보이는가**
(`_windowVisible`), **이 패널의 표면이 화면에 있는가**(`_gitSurfaceOn`), 저장소가
정해졌는가를 본다. 하나라도 거짓이면 타이머를 없앤다.

되살아나는 계기는 **밖에서 알려 주는 것뿐이다** — `_gitRescheduleAll()`
(`app-git.js:53`)을 부르는 자리들과, 패널을 처음 만드는 `_gitPanel()`
(`app-git.js:106`). 그 파일의 주석이 이 설계를 못 박는다:

> **여기서만 부른다.** 매 부름마다 부르면 렌더마다 조건을 다시 보게 되고 …
> 표면이 바뀌는 계기는 `_gitRescheduleAll` 을 부르는 자리들이 든다.

즉 **계기가 하나라도 새면 그 패널의 자동 갱신은 영구히 죽는다.** 그리고 죽었다는
것을 아무도 알지 못한다 — 화면에는 낡은 목록이 정상처럼 그려져 있다.

### 2.5 B — 그래서 수동 새로고침만 살아남는다

`refresh()`(panel-poll.js:112~)는 `collect()` 를 기다리기 **전에** 모든 뷰를 직접
다시 받는다:

```js
try{ for(const p of this.obs.panels) jobs.push(...p._reloadViews(true)) } catch(e){...}
await Promise.allSettled([this.collect(), ...jobs]);
```

`collect()` 가 어떤 이유로 아무것도 하지 않아도 뷰는 갱신된다. 사용자가 보고한
비대칭 — "자동은 안 되고 새로고침은 된다" — 이 이 두 코드 경로의 차이 그대로다.

### 2.6 B — 접수된 재현 조건 (사용자 확인)

- 변경을 만든 주체: dongminal 터미널의 git 명령, 터미널에서 도는 에이전트의 파일
  수정, dongminal 밖의 외부 터미널·에디터 — **UI 밖 전부**.
- 그때 Git 화면은 **계속 보고 있었다**.
- 기다려도 갱신되지 않고 **새로고침을 누를 때까지 그대로**다.

"보고 있는데도" 와 "영영" 이 함께 참이라는 것이 §2.3·2.4 의 정지 상태를 가리킨다.
30초 폴링이 살아 있었다면 늦어도 30초에는 따라잡혔을 것이다.

**어느 계기가 새는지는 아직 특정하지 못했다.** e2e 는 이 경로를 폭넓게 검사하고
(`git-push-observe.spec.ts`, `git-view-refresh.spec.ts` 의 G1~G12) 모두 통과한다 —
검사는 창을 막 열어 짧게 쓰고, 사용자는 오래 열어 둔 채 칸과 창을 오간다.

### 2.7 C — 수식키 조합은 **조합 게이트를 지나지 않는다**

조합 보류 장치는 xterm 의 `attachCustomKeyEventHandler` 안에만 있다
(`term-pane.js:44-46` → `_imeGate`). 그런데 같은 파일 56-70 줄에 **별도의 keydown
리스너**가 있다:

```js
this.box.addEventListener('keydown', e => {
  if (e.metaKey && !e.ctrlKey && !e.altKey) {
    if (e.key === 'ArrowLeft')  { e.preventDefault(); this._send(...0x01); return }  // Home
    if (e.key === 'ArrowRight') { e.preventDefault(); this._send(...0x05); return }  // End
  }
  if (e.altKey && !e.ctrlKey && !e.metaKey) { /* Alt+←/→ 단어 이동 — 즉시 전송 */ }
  if (e.ctrlKey && !e.metaKey) e.preventDefault();
});
```

`_imeGate` 가 `false` 를 돌려줘도 `stopPropagation` 은 하지 않으므로 keydown 은
그대로 `box` 로 버블한다. 그래서 조합 중에도 이 리스너가 **즉시** 커서 이동을
보낸다:

1. 게이트가 그 키를 큐에 넣는다 (`_imePush`)
2. box 리스너가 곧바로 `0x01` 을 보낸다 — **커서가 먼저 움직인다**
3. 조합 문자가 그다음에 나간다 — 옮겨진 자리에 찍힌다
4. 큐에 든 키가 `_imeFlush` 에서 재생되어 **한 번 더** 움직일 수도 있다

접수된 "cmd + 좌/우" 가 정확히 이 경로다. `Alt+←/→` 도 같다.

### 2.8 C — Enter 와 모바일 되풀이는 코드만으로 특정되지 않는다 (M4 실측으로 갱신)

Enter 는 box 리스너의 어느 분기에도 걸리지 않고, `_imeGate` 가 `_imeSettling`
창까지 포함해 잡는다 (UX_BATCH6 FR-IME-3). 모바일의 되풀이 입력은 조합 중
백스페이스(`deleteContentBackward`)가 `_onBeforeInput` 의 `inputType!=='insertText'`
필터에서 무시되고 xterm 의 CompositionHelper 가 textarea 값 diff 로 누적분을 다시
보내는 경로가 의심되나, **관측 없이는 단정할 수 없다.**

**M4 에서 실측했다.** 합성 `dispatchEvent` 로는 브라우저 안쪽을 태우지 못하므로
CDP 의 `Input.imeSetComposition`·`Input.insertText` 로 실제 IME 와 같은 자리에
넣고 전송 바이트와 이벤트 순서를 함께 기록했다 (데스크톱·모바일 두 모드).

| 시나리오 | 결과 |
|---|---|
| 조합 확정(`insertText`) 뒤 Enter | 정상 — `"한"` 다음 `"\r"` |
| 데스크톱에서 조합을 쳤다 지웠다 되풀이 | 정상 — `"안녕"` 한 번만 |
| **모바일 모드**에서 같은 되풀이 | 정상 — `"안녕"` 한 번만 |
| 모바일에서 조합·백스페이스·새 조합을 섞음 | 정상 — `"한"`, `"강"` |
| 조합을 **연 채로** Enter (확정 없음) | 아무것도 전송되지 않는다 |

마지막 줄은 CDP 로만 만들어지는 순서다. 실제 IME 에서 Enter 는 조합을 확정시키고
`compositionend` 가 뒤따르며, 그때 `_imeClose` 가 보류분을 흘려보낸다. 조합이
영영 열려 있는 상태는 관측을 위해 인위적으로 만든 것이므로 **접수된 증상의 특정이
아니다.** FR-IMK-5 에 따라 이 자리를 고치지 않았다 — 그 조건에서만 도는 방어를
넣으면 실제 경로를 바꾸지 않으면서 조합 코드만 늘어난다.

**그러므로 접수된 두 증상은 아직 특정되지 않았다.** 다음 근거는 실기기 로그다:
`?diag=1` 로 열면 키·조합 이벤트마다 게이트의 상태(`ime=open/settling q=N`)가 함께
찍히므로, 증상이 난 순간의 순서를 그대로 받을 수 있다 (FR-IMK-4).

### 3.3 묶음 C — 조합 중에는 어떤 키도 앞지르지 않는다

| ID | 요구사항 | 우선순위 |
|----|---------|---------|
| FR-IMK-1 | 조합이 정리되기 전에는 **어떤 경로로도** 키가 먼저 나가지 않는다. 수식키 조합(`Cmd+←/→`, `Alt+←/→`)도 조합 게이트를 지난다 | 필수 |
| FR-IMK-2 | 게이트가 잡은 키는 **한 번만** 전송된다. 보류와 즉시 전송이 겹쳐 두 번 움직이는 일이 없어야 한다 | 필수 |
| FR-IMK-3 | 조합이 없을 때의 동작은 완전히 그대로다 — `Cmd+←/→` 는 Home/End, `Alt+←/→` 는 단어 이동 | 필수 |
| FR-IMK-4 | 계측: 조합 중 들어온 키와 그 처리(보류·즉시)를 진단에 남긴다. Enter 와 모바일 되풀이(§2.8)를 실측으로 특정하기 위한 것이다 | 필수 |
| FR-IMK-5 | §2.8 이 특정되면 그 원인에 대한 요구를 이 문서에 덧붙인다. **특정 전에는 고치지 않는다** — 짐작으로 만진 IME 경로는 다른 증상을 만든다 | 필수 |

### 3.4 비기능 (Non-functional)

| ID | 요구사항 |
|----|---------|
| NFR-B9-1 | 세 묶음은 서로의 코드를 건드리지 않는다. 각각 따로 되돌릴 수 있어야 한다 |
| NFR-B9-2 | git 요청 수는 현행 이하다 (FR-GLR-7) |
| NFR-B9-3 | 조합 경로에 새 타이머를 더하지 않는다. UX_BATCH6 이 세운 두 tick 규약이 그대로 남는다 |

## 4. 설계 결정 (Design Decisions)

- **D-1. 저장을 앱의 단축키 체계로 옮긴다.** Monaco 의 `addCommand` 를 인스턴스별로
  격리하는 길(`when` 조건, 컨텍스트 키)도 있으나, 그것은 Monaco 의 내부 규약에
  기대는 일이고 이 저장소는 이미 반대 방향으로 결정해 두었다 (FR-EKB-5). 여섯 키가
  간 자리로 일곱째를 보낸다.
- **D-2. B 는 "계기를 하나 더 찾는" 방식으로 고치지 않는다.** 새는 계기를 메워도
  다음 계기가 또 샌다 — 지금 설계는 **정지가 조용하다**는 것이 문제다. 조용한 정지를
  시끄럽게 만들거나(진단) 스스로 깨어나게(워치독) 해야 같은 결함이 다시 자라지 않는다.
- **D-3. 워치독은 시간이 아니라 관측의 나이를 본다.** "타이머가 있는가" 로 판정하면
  타이머는 살아 있는데 응답이 오지 않는 경우(§2.5 의 `_busy` 계열)를 놓친다.
  **마지막으로 성공한 관측이 얼마나 낡았는가** 가 사용자가 겪는 것과 같은 값이다.
- **D-4. 워치독의 계기는 이미 도는 것에 얹는다.** 새 타이머를 만들지 않고 렌더·
  가시성 변화처럼 이미 있는 계기에서 검사한다 — 검사 자체가 요청을 내지 않으므로
  자주 돌아도 비용이 없다 (FR-GLR-7).
- **D-5. C 는 게이트를 옮기지 않고 넓힌다.** box 리스너를 지우고 그 동작을
  `attachCustomKeyEventHandler` 안으로 넣는 길도 있으나, 그러면 xterm 이 그 키를
  자기 표로 해석하는 경로와 다투게 된다. 리스너는 그대로 두고 **그 앞에서 게이트를
  묻게** 한다 — 조합 중이면 보류하고 아니면 종전대로 보낸다.
- **D-6. Enter·모바일은 계측부터 한다.** 조합 경로는 브라우저·IME·xterm 셋이
  얽혀 있어 코드 독해만으로는 순서를 확정할 수 없다. UX_BATCH6 이 그 자리에서
  세 번 고쳐졌고, 그 문서의 주석이 모두 **실측**을 근거로 적혀 있다.

## 5. 마일스톤

| M | 내용 | 산출 |
|---|------|------|
| M1 | 묶음 A — 저장 | `edSave` 기본값, capture 경로, `addCommand` 제거, e2e |
| M2 | 묶음 C 앞부분 — 수식키 게이트 | `_imeGate` 를 box 리스너 앞에 세움, e2e |
| M3 | 묶음 B — 워치독과 진단 | 관측 나이 기반 되살리기, 진단 노출, e2e |
| M4 | 계측 회수 — Enter·모바일 | **완료(특정 실패)** — CDP 실측으로 §2.8 갱신. 재현되지 않았고, 인위적 조건에서만 나는 자리는 고치지 않았다. 실기기 로그를 기다린다 |

M1·M2 는 원인이 확정돼 있어 곧바로 간다. M3 은 구조를 고치는 것이므로 요청 수
회귀를 함께 잰다. M4 는 사용자의 실사용 로그가 필요하다.

| TC-ESV-2 | 두 번째 편집기가 dirty 인 채로 첫 번째에서 `Cmd+S` | 두 번째는 dirty 그대로 — 남의 저장이 일어나지 않는다 |

| TC-ESV-4 | 편집기가 아닌 곳(터미널)에서 `Cmd+S` | 종전과 같다 — 편집기의 저장이 불리지 않는다 |
| TC-ESV-5 | dirty 가 아닌 편집기에서 `Cmd+S` | 쓰기 요청이 나가지 않는다 |

## 7. 비목표 (Non-goals)

- Monaco 의 키 처리 방식 자체를 바꾸는 것.
- git 폴링 주기·백오프 정책의 재설계 (FR-RMS 계열은 그대로).
- 서버 `GitWatcher` 의 TTL·상한 조정. 브라우저가 제때 물으면 지금 값으로 충분하다.
- IME 조합 자체의 전송 경로 교체 (UX_BATCH6 D-1: xterm 에 맡긴다).
- Enter·모바일 되풀이의 **수리** — 이 문서에서는 계측까지다 (FR-IMK-5).

# SRS: 서브모듈 행이 왜 사라지지 않는지 말한다 — IEEE 29148

## 1. 개요

### 1.1 목적

접수한 말은 한 줄이다.

> **"서브모듈은 커밋이 안되고있는거같아. 해당내용 확인."**

확인한 결과 **버그가 아니었다.** 재현은 이렇다 (실측):

```
1 .M S.MU 160000 … sub      ← 서브모듈 워킹트리가 dirty
$ git add -- sub            → exit 0
1 .M S.MU 160000 … sub      ← 상태 그대로
$ git diff --cached --stat  → 비었다
```

`sub` 필드의 둘째 자리(기록된 커밋이 바뀌었는가)가 `.` 다. 부모 저장소가 커밋할
수 있는 것은 **gitlink 하나** — 서브모듈의 커밋 해시 — 인데 그 해시가 바뀌지
않았으므로 `git add` 가 index 에 올릴 것이 없다. 서브모듈 **안**의 커밋하지 않은
변경은 부모가 커밋할 방법이 없다.

**고칠 것은 동작이 아니라 침묵이다.** 지금 UI 는 이 행을 다른 서브모듈 행과
똑같이 그리고, `Stage` 를 눌러도 아무 말을 하지 않는다. 사용자는 앱이 고장났다고
읽었고 — 그 판단은 화면이 준 것이 전부였을 때 옳은 판단이다.

이 SRS 는 서버가 **이미 보내고 있는** `sub` 필드를 읽어, 그 행이 여기서 처리될
수 있는 것인지를 말하게 한다.

### 1.2 범위

**포함**
- `sub` 필드에서 "여기서 커밋할 수 있는 몫"과 "서브모듈 안의 몫"을 가르는 판정
- 그 판정에 따라 갈리는 **행 툴팁**과 **미리보기 안내문**

**미포함**
- git 의 동작 — 부모가 gitlink 만 커밋한다는 사실은 바꿀 수 없다 (§6 비목표 #1)
- 서브모듈 행의 액션 구성 — `Stage` 는 그대로 붙는다 (§2.3, §6 비목표 #2)
- Submodules 탭 (§6 비목표 #3)
- 중첩 저장소(`.gitmodules` 에 없는 것) — `sub` 가 비어 있어 가를 것이 없다
  (§6 비목표 #4)

## 2. 현재 상태

### 2.1 서버는 이미 근거를 보낸다

`FileEntry.Sub` 가 porcelain v2 의 `sub` 필드를 그대로 싣는다
(`query/status.go:24`). 형식은 `S<c><m><u>` 이고 자리마다 뜻이 있다.

| 자리 | 값 | 뜻 |
|---|---|---|
| c | `C` / `.` | 기록된 커밋(gitlink)이 바뀌었다 |
| m | `M` / `.` | 서브모듈 안에 추적 중인 변경이 있다 |
| u | `U` / `.` | 서브모듈 안에 추적되지 않는 파일이 있다 |

`FileEntry.Dir` 도 이 필드에서 파생된다 (FR-DIR-1). **판정의 재료는 이미 화면에
와 있고, 읽는 코드가 없을 뿐이다.**

### 2.2 지금 화면이 말하는 것은 한 문장뿐이다

```js
// panel-changes.js:583
(e.dir?' — '+(e.sub?GIT_DIR_ENTRY_TITLE_SUB:GIT_DIR_ENTRY_TITLE_NESTED):'')
```

```js
// panel-diff.js:567
view.clear(f.sub?GIT_DIR_ENTRY_NOTE_SUB:GIT_DIR_ENTRY_NOTE_NESTED, …)
```

두 자리 모두 `f.sub` 를 **참/거짓으로만** 본다. 그래서 "기록된 커밋이 바뀌어
지금 스테이지하면 담기는 행"과 "여기서는 아무리 눌러도 사라지지 않는 행"이
같은 문장을 받는다.

기존 문구 `안의 변경은 여기서 보이지 않습니다` 는 **참이지만 부족하다** — 보이지
않는다는 말과 처리할 수 없다는 말은 다르고, 사용자가 부딪힌 것은 뒤쪽이다.

### 2.3 `Stage` 는 오류를 내지 않는다

`git add -- <submodule>` 은 dirty-only 인 서브모듈에서도 exit 0 이다 (§1.1 실측).
서버도 UI 도 실패로 다룰 근거가 없고, 다뤄서도 안 된다 — 혼합 상태(`SCM.`)에서는
gitlink 몫이 실제로 스테이지되기 때문이다. 그래서 **버튼은 그대로 두고 안내만
더한다** (§6 비목표 #2).

## 3. 요구사항

### 3.1 판정

**FR-SDN-1** `sub` 문자열에서 두 성분을 뽑는다.

| 성분 | 근거 | 뜻 |
|---|---|---|
| `commit` | c 자리가 `C` | 이 저장소가 커밋할 수 있는 몫이 있다 |
| `inner` | m 자리가 `M` **또는** u 자리가 `U` | 서브모듈 안에만 있는 몫이 있다 |

**FR-SDN-2** 판정은 **함수 하나**다 (`gitSubParts`). 툴팁과 안내문이 각자
문자열을 뜯으면 두 자리가 서로 다른 답을 낼 수 있고, 그 어긋남은 둘을 나란히
놓고 보기 전까지 아무도 모른다.

**FR-SDN-3** `sub` 가 없거나 `S` 로 시작하지 않으면 두 성분 모두 거짓이다 —
서브모듈이 아닌 것에 서브모듈의 사정을 말하지 않는다.

**FR-SDN-4** 자리 수가 모자란 문자열(`S`, `SC`)도 오류가 아니다. 없는 자리는
`.` 로 읽는다 — git 이 형식을 늘려도 화면이 깨지지 않아야 한다.

### 3.2 세 가지 상태

**FR-SDN-5** 서브모듈 행은 세 상태 중 하나로 말한다.

| 상태 | 성분 | 말해야 하는 것 |
|---|---|---|
| A. 커밋만 | `commit && !inner` | 스테이지하면 이 저장소에 담긴다 |
| B. 안쪽만 | `!commit && inner` | **여기서는 스테이지·커밋해도 사라지지 않는다.** 서브모듈 안에서 먼저 커밋해야 한다 |
| C. 둘 다 | `commit && inner` | 기록된 커밋은 담기고, 안쪽 몫은 남는다 |

**FR-SDN-6** B 는 사용자가 부딪힌 상태다 (§1.1). 문장은 **사라지지 않는다는
사실**을 먼저 말하고, 그다음에 무엇을 해야 하는지를 말한다 — 순서가 뒤집히면
"먼저 커밋하라"가 조언으로 읽히고 지금 눈앞의 행은 설명되지 않는다.

**FR-SDN-7** 성분이 하나도 없으면(`S...`) 종전 문구를 그대로 쓴다. 그 행이 왜
목록에 있는지를 이 SRS 가 알지 못하며, 모르는 것에 대해 말하지 않는다.

### 3.3 두 자리

**FR-SDN-8** **행 툴팁** (`panel-changes.js` `_row`): 상태별 문장이 종전 문장을
**대체한다**. 뒤에 덧붙이면 "서브모듈" 이 한 툴팁에 두 번 나오고, 종전 문장이
말하던 것을 새 문장이 더 정확히 말한다. 툴팁은 짧아야 하므로 사실 하나씩만
싣는다.

**FR-SDN-9** **미리보기 안내문** (`panel-diff.js`): 상태별 문장으로 갈린다.
여기는 자리가 넓으므로 무엇을 해야 하는지까지 싣는다.

두 자리의 갈래는 **같은 모양**이다 (`_dirTitle` / `_dirEntryNote`) — 구조가
다르면 상태가 하나 늘 때 한쪽만 고쳐진다.

**FR-SDN-10** 안내문에 딸린 진입점(`저장소로 이동`·`저장소로 추가`·
`Submodules 탭`)은 그대로다 (FR-DIR-22). B 상태에서 사용자가 갈 곳이 바로
그 첫 번째이며, 이미 거기 있다.

**FR-SDN-11** 중첩 저장소(`sub` 가 빈 값)의 문구는 바뀌지 않는다.

**FR-SDN-12** (D-2a) 상태 B(`!commit && inner`)의 행에서 `Stage` 는 **비활성**이다.
판정은 다른 자리와 같은 `gitSubParts` 하나를 딛는다 (FR-SDN-2).

**FR-SDN-13** 꺼진 `Stage` 의 `title` 은 사유를 말한다 — 이 저장소가 담을 변경이
없다는 것과, 서브모듈 안에서 먼저 커밋해야 한다는 것.

> **개정.** 그 문장은 **영어**다 (UX_BATCH5_SRS FR-TIP-2). 버튼의 `title` 은 언어가
> 정해져 있고, 이 자리도 버튼이다 — 초판이 한국어로 적은 것은 그 규약을 지나쳤다.
> 말하는 **내용**은 그대로다: `Nothing here for this repository to stage — commit
> inside the submodule first`.

**FR-SDN-14** A·C 의 `Stage` 는 그대로 살아 있다. `Discard` 는 상태와 무관하게
바뀌지 않는다 — 그것은 gitlink 를 되돌리는 별개의 동작이다.

### 3.4 비기능

**NFR-SDN-1** 문구는 상수에 산다 (`constants-git.js`) — 만드는 자리에 적으면
표가 두 벌이 된다 (FR-TIP-1 의 규약).

**NFR-SDN-2** 새 요청을 만들지 않는다. 재료는 이미 관측 안에 있다 (§2.1).

## 4. 설계 결정

**D-1 판정은 문자열 파싱 하나로 끝낸다.** 서버가 `sub` 를 해석해 boolean 두 개로
보내는 편이 깔끔해 보이지만, `FileEntry.XY` 를 그대로 보존한 판단(§2.1 의 주석:
"표시 계층이 해석을 바꿀 수 있어야 한다")과 어긋난다. 서버는 관측을 옮기고,
해석은 화면이 한다.

**D-2 `Stage` 버튼을 없애지 않는다.** 혼합 상태(C)에서는 실제로 담기는 것이
있고, B 에서 누르는 것도 오류가 아니다 (§2.3). 버튼을 지우면 C 를 설명할 수
없다.

**D-2a (2026-09-06 개정 — 말만으로는 모자랐다).** 접수한 말은 "여전히 서브모듈이
staging 조차 되지 않는다" 였고, 실측이 상태 B 의 버튼이 여전히 **아무 일도 하지
않는다**는 것을 확정했다.

    1 .M SC.U … sub     ← C. 커밋 몫 + 안쪽 몫
    Stage 클릭          → 1 MM S..U   (커밋 몫은 담겼다)
    화면                 Staged(1) sub/ · Changes(1) sub/   ← 같은 행이 둘 다에 있다
    남은 행에서 Stage    → 상태 그대로. 요청도 200. 아무 일도 없다

즉 C 를 한 번 담고 나면 남는 것은 B 이고, 그 행의 `Stage` 는 **누를 수는 있으나
할 일이 없는 버튼**이다. 툴팁으로만 알린 것은 모자랐다 — 사용자는 툴팁을 열기
전에 버튼을 먼저 누른다.

버튼을 지우지 않는다(D-2 는 유효하다). **담을 몫이 없을 때만 끈다**: A·C 에서는
살아 있고 B 에서만 꺼지며, 꺼진 사유는 `title` 이 말한다 (FR-GIT-101 이 원격
버튼에 세운 규약과 같다 — 사유 없이 꺼진 버튼은 사용자가 해소할 수 없다).

**D-3 상태문자(`M`)를 바꾸지 않는다.** 그것은 git 이 답한 사실이며, 화면이
사실을 고쳐 쓰기 시작하면 어디까지가 관측인지 알 수 없게 된다. 덧붙이는 것은
말이지 표시가 아니다.

## 6. 비목표

1. **git 의 동작** — 부모가 gitlink 만 커밋한다는 사실은 바꿀 수 없다. 이
   SRS 가 하는 일은 그 사실을 화면에 세우는 것뿐이다.
2. **서브모듈 행의 액션 구성** — `Stage`·`Discard` 는 그대로다 (D-2).
3. **Submodules 탭** — init·update·sync 는 그 자리의 것이다. 여기서는 그리로
   가는 길만 종전대로 붙는다 (FR-SDN-10).
4. **중첩 저장소** — `.gitmodules` 에 없으므로 `sub` 가 비어 있고 가를 것이
   없다 (FR-SDN-11).
5. **서브모듈 안의 변경을 부모에서 커밋하게 만드는 것** — 불가능하다. 길은
   서브모듈을 자기 저장소로 여는 것 하나이며 그 진입점은 이미 있다.

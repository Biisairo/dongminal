# SRS: 돌지 않은 회차도 마감을 다시 건다 — 스케줄러의 공회전 교정 — IEEE 29148

> **문서 상태**: 승인·구현완료

## 1. 개요

### 1.1 목적

`TimerHub` 는 앱의 모든 시간이 지나는 한 지점이고(`EVENT_TIMER_HUB_SRS` INV-1),
그 내부는 **가장 이른 마감 하나만 예약하는 단일 타이머**다 (FR-SCH-3). 그 설계가
성립하려면 모든 job 의 `nextAt` 이 늘 **미래**여야 한다 — 과거의 마감이 하나라도
남으면 그것이 언제나 "가장 이른 마감" 이 되어 `setTimeout(…, 0)` 이 되풀이된다.

지금 그 자리가 둘 있다. `_fire` 의 조기 반환 두 갈래는 콜백을 부르지 않고 나가면서
**마감도 옮기지 않는다.** 재무장(`_arm`)이 콜백이 끝난 뒤에만 있기 때문이다.

**콜백 횟수로는 보이지 않는다** — 도는 것은 스케줄러이지 job 이 아니다. 그래서
`T-10b` 같은 기존 검사는 이 상태를 그대로 통과한다.

### 1.2 범위

**포함**
- `_fire` 의 두 조기 반환(`!_alive` · `inflight` 겹침)이 마감을 다시 거는 것
- 그 계약을 고정하는 검사 (깨어난 횟수를 재는 T-13·T-13b)

**미포함**
- `whenHidden`·`overlap`·`when` 의 **의미**. 무엇이 도는가는 한 줄도 바뀌지 않는다
  (§6 비목표 #1)
- 마감 힙의 자료구조 (FR-SCH-3 의 단일 타이머 그대로)
- 숨은 탭에서 job 을 아예 걷어내는 최적화 (§6 비목표 #2)

## 2. 현재 상태 (실측)

### 2.1 마감이 과거에 남는다

```js
// web/js/core/timer-hub.js
async _fire(job){
  if(!this._alive(job)) return;                                  // :118  ← 마감 그대로
  if(job.inflight){
    if(job.overlap==='queue') job.again=true;
    return;                                                      // :120  ← 마감 그대로
  }
  …
  this._arm(job);                                                // 끝난 뒤에만 다시 건다
}

_tick(){
  …
  for(const j of Array.from(this._jobs.values())){
    if(j.nextAt>0&&j.nextAt<=now) this._fire(j);                 // :306  마감을 옮기지 않는다
  }
  this._reschedule();
}

_reschedule(){
  let at=0;
  for(const j of this._jobs.values()) if(j.nextAt>0&&(!at||j.nextAt<at)) at=j.nextAt;
  …
  this._nextT=setTimeout(()=>{ this._nextT=null; this._tick() },Math.max(0,at-Date.now()));
}
```

`_tick` → `_fire`(조기 반환) → `_reschedule` → 과거 마감 → `setTimeout(…, 0)` →
`_tick` … 조건이 바뀔 때까지 닫히지 않는 고리다.

### 2.2 실측

빈 페이지에 `timer-hub.js` 만 얹고 원시 `setTimeout` 호출 수를 셌다 (T-13·T-13b).
주기 50ms, 관측 창 400ms — **정상이라면 8회 안팎**이다.

| 상황 | 깨어난 횟수 |
|---|---|
| `when: () => false` (FR-SCH-6 의 조건 거짓) | **85** |
| 한 회차가 300ms 걸리는 job (`overlap:'drop'`) | **75** |

400ms 에 85회는 회당 4.7ms — 브라우저의 `setTimeout` 최소 지연에 붙어 돈다.

### 2.3 왜 지금까지 드러나지 않았는가

- **콜백은 정확히 옳게 돈다.** 스핀은 스케줄러 안에서만 일어나므로 `runs`·
  결과·순서를 재는 검사는 전부 통과한다.
- 가장 흔한 조건인 `whenHidden:'pause'` 는 **탭이 숨어 있을 때**만 참인데, 그때
  브라우저가 배경 탭의 타이머를 1초(그리고 5분 뒤 1분)로 조인다. 스핀이
  1Hz 로 눌려 눈에 띄지 않았다.
- 보이는 탭에서 남는 자리가 `when` 거짓과 **주기보다 오래 걸리는 회차**다. 후자는
  느린 응답이 겹칠 때마다 그 응답이 끝날 때까지 4ms 마다 깨어난다.

### 2.4 이 결함은 접수된 git 증상과 무관하다

`git.status` job 은 `whenHidden:'run'` 이고 `run:()=>this.obs.tick()` 이 즉시
resolve 하므로 두 갈래 어디에도 들어가지 않는다 (`GIT_OBSERVE_REVIVE_SRS` §6-2 가
별건으로 미룬 이유). 조사 중에 발견해 따로 닫는다.

## 3. 요구사항

### 3.1 기능 요구

| ID | 요구사항 | 우선순위 |
|----|---------|---------|
| FR-SRA-1 | 마감이 왔으나 **돌지 않은** 회차도 다음 마감을 건다. `_fire` 가 콜백 없이 나가는 모든 갈래가 그렇다 | 필수 |
| FR-SRA-2 | 그 결과 등록된 job 의 `nextAt` 은 **언제나 미래이거나 0**(주기 0, 걸지 않음)이다. 과거의 마감이 남지 않는다 | 필수 |
| FR-SRA-3 | 조건(`when`·`whenHidden`)은 **주기마다 다시 묻는다.** 조건이 참으로 바뀌면 그 다음 회차에 돈다 — 조기 반환이 job 을 영구히 재우지 않는다 | 필수 |
| FR-SRA-4 | 무엇이 도는가는 바뀌지 않는다. `_alive`·`overlap`·`revalidateOnShow` 의 판정과 콜백 호출 횟수가 종전과 같다 | 필수 |

### 3.2 비기능

| ID | 요구사항 |
|----|---------|
| NFR-SRA-1 | 돌지 않는 job 하나가 만드는 깨어남은 **주기당 1회**를 넘지 않는다 |
| NFR-SRA-2 | 새 상태·새 필드를 만들지 않는다. 고치는 것은 재무장이 빠진 두 자리뿐이다 |

## 4. 설계 결정

- **D-1. 재우지 않고 다시 건다.** 대안은 돌지 않는 job 의 `nextAt` 을 0 으로
  두고(=예약 없음) 조건이 참이 될 때 깨우는 것이다. `whenHidden` 은 그 계기가
  있지만(`visibilitychange`) **`when` 에는 없다** — 임의의 술어이며 바뀌었다고
  알려 주는 자리가 없다. 그 길로 가면 `when` 이 거짓이던 job 은 영영 돌아오지
  않는다 (T-10b 가 그것을 금한다). 주기마다 술어를 다시 묻는 것이 이 스케줄러가
  이미 택한 규약이다 (FR-SCH-4: 판단은 job 의 것이고 스케줄러는 묻기만 한다).
- **D-2. 재무장을 `_fire` 안에 둔다.** `_tick` 이 발화 전에 미리 옮기는 길도
  있으나, 그러면 마감을 옮기는 자리가 둘이 되고(`_tick` 과 `_fire` 의 끝) 그 둘이
  어긋날 수 있다. `_fire` 는 "이 회차를 끝냈다" 를 아는 유일한 자리다.
- **D-3. 겹침으로 버린 회차도 같다.** `drop` 은 "이 회차를 버린다" 이지 "이 job 을
  멈춘다" 가 아니다. `queue` 도 마찬가지로 다시 걸어 둔다 — 비행이 끝나면
  `again` 이 즉시 한 번 더 돌리고 그쪽이 다시 재무장하므로, 여기서 건 마감은
  그때 덮인다.

## 5. 검증

| ID | 상황 | 기대 |
|----|------|------|
| T-13 | `when:()=>false`, 주기 50ms, 400ms 관측 | 깨어남 < 30 — 실측 **85 → 8**. 그리고 조건이 참이 되면 돈다 (FR-SRA-3) |
| T-13b | 한 회차가 300ms 인 job, 주기 50ms, 400ms 관측 | 깨어남 < 30 — 실측 **75 → 9** |

문턱을 30 으로 둔 이유는 재는 것이 **값이 아니라 자릿수**이기 때문이다. 주기당
한 번(8~9)과 4ms 스핀(75~85) 사이의 어디를 잡아도 판정이 같다.
| 회귀 | T-5·6·7·7b·10·10b·11·12 | 그대로 통과 — 콜백 횟수와 판정이 바뀌지 않는다 (FR-SRA-4) |

## 6. 비목표

1. **무엇이 도는가.** `whenHidden:'pause'` 의 "숨으면 멈춘다", `when` 의 게이트,
   `overlap` 의 두 정책은 한 줄도 바뀌지 않는다.
2. **숨은 탭에서 job 을 걷어내는 것.** 주기당 한 번의 깨어남조차 아끼는 최적화는
   `revalidateOnShow` 의 계기와 얽히므로 별건이다. 이 문서는 4ms 스핀을 주기로
   되돌리는 데서 멈춘다.

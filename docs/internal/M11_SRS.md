### 2.2 M11-B1 — 잔재가 **공백 칸에만** 앉는다

세 줄 전부에서 규칙이 하나다: **낱말 사이의 공백만** 옛 내용을 그대로 이고 있고,
글자가 있는 칸은 새 내용으로 덮여 있다. 셋째 줄의 배경은 폭 전체를 채운 `─`
(TUI 의 구분선)이고, 그 위에 글자만 찍혔다.

**그러므로 쓰는 쪽이 공백 칸을 건너뛴다.** 실제 바이트가 그것을 확인한다 —
운영 중인 `claude` 도구의 PTY tail 400 KiB(`dmctl read-output`)에서:

```
^[[2C^[[1B^[[38;5;249mTools: 9 done… ^[[20G ^[[19G📦️^[[21G ^[[38;5;151m92%…
```

`^[[2C`(커서 전진) · `^[[20G`·`^[[19G`(절대 열)로 **칸을 건너뛰며 글자만 찍는다.**
정상 단말에서는 그 칸이 이미 공백이므로 맞지만, 버퍼가 TUI 의 모형과 어긋나면
어긋난 내용이 **정확히 공백 자리에** 남는다. 접수한 화면이 그 모양이다.

### 2.3 실측이 뒤집은 전제 둘

| 전제 (`M10_SRS` §2.1b) | 실측 |
|---|---|
| *"화면은 claude TUI(**대체 화면**)이고 그 위에 겹쳤다"* | **틀렸다.** tail 1 MiB 에 `1049` 가 **0 건**이다 — claude TUI 는 **주 화면**에서 돈다 |
| 잔재는 버퍼인가 렌더인가가 **미지** | **렌더 쪽의 증거가 하나도 없다** — 아래 여섯 배치 전부에서 `term.buffer.active` 와 `.xterm-rows` 의 DOM 텍스트가 **완전히 일치**했다 (불일치 0행) |

### 2.4 재현하지 못했다 — 여섯 배치, 잔재 0

| # | 배치 | 잔재 | buf vs DOM |
|---|---|---|---|
| ① | `top`(전량 재그리기 TUI) 라이브 → `_refreshForWidth()` 전량 재생 | 없음 | 0 |
| ② | 실제 claude tail 697 KiB 를 **전체 창**으로 재생 (`termReset`+`termHardClear`+`alignHead`) | 없음 | 0 |
| ③ | 같은 tail 을 **뒤 절반만** 재생 — 창이 늦게 시작한 경우 | 없음 (②와 **화면이 동일**) | 0 |
| ④ | claude TUI · 169열 ↔ 25열 소유권 전환 1회 | 없음 | 0 |
| ⑤ | 같은 전환 3회 반복 | 없음 | 0 |
| ⑥ | 같은 칸에 새 탭을 열어 **숨겼다가 되돌아오기** 2회 (인계 때의 손) | 없음 | 0 |

②와 ③이 **글자 하나까지 같았다**는 것이 요점이다 — 재생 창의 시작점이 달라도
전량 재생은 **수렴한다.** 그러므로 `FR-M10-2` 의 재생 경로는 잔재의 출처가 아니다.
④·⑤는 M10-B1·B2 의 경로이고 거기서도 나지 않는다.

**여섯이 말한 것**: 잔재는 **버퍼에 있고**(렌더가 아니다), 잘 도는 전량 재생은
**수렴한다.** 그러므로 찾을 것은 재생의 결함이 아니라 **재생이 걸리지 않는 자리**다.

25열로 그려진 글이 169열에서 낱말마다 25칸 간격으로 흩어진 채 남았다:

⑦b(대조군, 되살린 뒤 같은 전환): **깨끗하다.** 갈래가 여기서 갈린다.

### 2.4c ⑦d 는 **다른 홀이었다** — 재지 않고 적을 뻔했다

무력화 없이 닿는지 보려고 **서버만 정지**하고(`dongminal stop` — `--all` 이 없으면
dongminald 와 세션은 살아남는다) 그 틈에 창의 폭을 바꿨다.

| | 값 |
|---|---|
| 기준 | `cols=169 ptyCols=169 seq=862 ws=true` |
| 서버 정지 뒤 | `cols=169 ptyCols=169 seq=862 **ws=false**` |
| 끊긴 동안 폭 변경 | `cols=**62** ptyCols=169 **seq=862** ws=false` |
| 서버 재기동 뒤 | `cols=62 ptyCols=62 **seq=917**` — 862 에서 이어 붙었다 = 델타 |

**`_seq` 가 862 그대로다 — `_refreshForWidth` 를 부르지도 않았다.** `ptySize()` 는
`had` 를 `doFit()` **뒤**의 `term.cols` 와 비교하는데, 창 크기 변경이 이미
`doFit()` 을 돌려 놓았으므로 `cols===had` 다. 이 경로는 **소유자 자신의 리사이즈**
이고, 그것을 전량 재생에서 뺀 것은 D-M10-3 의 결정이다(드래그마다 tail 을 다시
받지 않는다). 살아 있는 claude TUI 로 같은 리사이즈를 다시 재었을 때 **잔재는
나지 않았다** — 리플로우가 감당한다.

> **그래서 ⑦d 는 §2.4d 의 근거가 아니다.** 처음에 그렇게 적었다가 `_seq` 를 보고
> 되물러섰다. `M10_PROGRESS` §2-13 과 같은 자리다 — 한 회차의 겉모습으로 판정을
> 세우면 안 된다.

### 2.4d 원인 — 폭이 바뀐 사실이 소켓과 함께 사라진다

```js
_refreshForWidth(){
  if(this._destroyed||this._exited||!this.ws) return false;   // ← 여기
  this._seq=-1; this._seqLive=false;
  return this.reconnectNow({quiet:true});
}
```

`!this.ws` 로 물러날 때 **`_seq` 를 그대로 둔다.** 그리고 호출처 둘
(`_applyPtySize`:831 · `ptySize`:883)은 **반환값을 버린다.** 그러므로 소켓이 없는
순간의 폭 전환은 아무 데도 기록되지 않고, 뒤이은 재접속은 `_seq>=0` 이므로
**델타**를 받는다 (`_wsURL`:594 — `since` 가 붙는다). 옛 폭의 그림은 영영 남는다.

`!this.ws` 는 드문 상태가 아니다 — 재접속 대기·백오프 구간 전부가 그렇고, 서버
재시작·기기 절전·망 전환이 모두 그 구간을 만든다. 닿는 길은 **되찾기**다
(`ptySize()` ← `resendWindowSizes`): 숨어 있던 넓은 창이 포커스를 되찾는 순간
`_ownCols`(자기 폭)와 `had`(따라가던 PTY 폭)가 다르고, 그때 소켓이 재접속 중이면
그 전환은 **아무 데도 남지 않는다.**

**증거의 층을 분명히 한다** — 이 조항의 근거는 ⑦a(재생이 **하는 일**이 있다)와
**코드**(그 갈래가 좌표를 버리지 않고 물러나며 호출처가 반환값을 버린다)다.
헤드리스에서 그 순간을 만드는 것은 하지 않았고, 그래서 검증은 **계약 층**이다
(D-M10-4 와 같은 근거).

> **M11-B1 은 이 조항으로 닫히지 않는다.** 접수한 화면 그대로를 아직 재현하지
> 못했다 — 닫은 것은 **잔재를 만들 수 있는 홀 하나**이고, 추적은 계속된다.

`agp-perm` 과 `agp-sess` 만 값을 얻었고 나머지는 전부 빈 문자열이라 `:empty` 로
사라졌다 — 컨텍스트 바·한도 바·비용·캐시·모델·cwd·저장소·열린 요청이 모두 없다.
그러므로 갈래는 **그리는 쪽이 아니라 값이 오는 쪽**이다.

`auto` 가 두 번 보이는 것도 이 화면이 말한다 — 같은 값이 두 자리에 서고 있다.

### 2.7 M11-B9 — 명령이 **모든 브라우저**에서 실행된다 (코드 근거)

실행자 지명은 **한 자리**가 정한다 (`hub.IsSingleExecutorAction`). 두 경로가 모두
그것을 본다 — dmctl 의 `/api/commands`(`commands.go:188`)와 서버 내부의
`broadcastLayout`(`handlers_runs_headless.go:240`). 지명이 없으면 `event-bus.js:245`
의 게이트를 그냥 지나가므로 **붙어 있는 브라우저 전부가 수행한다.**

허용 명령 21개 중 지명되는 것은 **7개**뿐이다:

```
newWindow · newTab · splitH · splitV · openEditorTab · restoreTool · openUrl
```

나머지의 근거는 그 자리 주석이 적고 있다 — *"Everything else stays ungated —
focus is per-client by definition, and the remaining mutations are idempotent
across clients."*

**"idempotent across clients" 가 성립하지 않는다.** 트리는 같아지지만 **시선은
같아지지 않는다.** 게이팅 없는 것 중 열둘이 전부 화면을 옮긴다:

| 종류 | 명령 |
|---|---|
| 시선만 옮긴다 | `focus` · `windowNext` · `windowPrev` · `tabNext` · `tabPrev` · `paneUp` · `paneDown` · `paneLeft` · `paneRight` |
| 워크스페이스를 줄인다 (+시선 부작용) | `closeTab` · `closeWindow` · `detachTab` |
| 순수 데이터 — 해당 없음 | `renameTab` · `renameWindow` |

**둘째 결함**: `closeWindow` 는 `--no-focus` 를 지키지 않는다. `force`·`keepTool`
갈래(`app-cmd.js:631`)가 공통 경로를 타지 않아 `keepFocus` 복원 블록
(`app-cmd.js:665~680`)을 건너뛴다. `dmctl close-window --at <uuid> --force` 는
`-n` 을 주어도 모든 브라우저의 시선을 옮긴다.

**실측** (격리 인스턴스 · 브라우저 둘 · A 는 alpha, B 는 beta 를 본다):

| 명령 | A | B |
|---|---|---|
| 기준 | `1c30ab4c`(alpha) | `8a626663`(beta) |
| `dmctl focus <alpha 탭>` | 그대로 | **그대로** |
| `dmctl window-next` | → `8a626663` | **→ `69affc7e`** |
| `dmctl close-window <beta> --force -n` | → `1c30ab4c` | **→ `1c30ab4c`** |

`window-next` 와 `close-window` 가 **두 브라우저를 모두** 움직인다. `close` 는 beta 를
보지도 않던 B 까지 끌고 갔고, **`-n` 도 듣지 않았다.**

`focus` 만 움직이지 않았는데 그것은 `_execRemote` 의 `sourcePane` 가드 때문이다
(*"소스 pane 이 이 창의 활성 창에 없으면 가만히 있는다"*) — 이 측정에서는 dmctl 이
운영 도구의 id 를 실어 보내 격리 인스턴스에서 해석되지 않았다. **그러므로 `focus`
에는 가드가 있고, 나머지 열둘에는 없다.**

> **접수의 출처가 이 세션이다 (확정).** M11-B7·B8·B9 를 재느라 돌린 `dmctl` 이 전부
> **운영 서버로 갔다** — dmctl 이 보는 것은 `DONGMINAL_PORT` 인데 `PORT` 를 주어
> 조용히 기본 포트(58146)로 붙었다. 운영 창이 11 → 20 이 되었고(`alpha`·`beta`·
> `Window`×7), `focus`·`window-next`·`close-window --force` 가 사용자의 브라우저
> 셋에 그대로 나갔다. **잃은 것은 없다** — 원래 창 11개는 전부 남아 있었다.
>
> 이 사고가 조항의 근거를 하나 더 준다: 한 번의 `dmctl` 에 `delivered:3` 이 찍혔고,
> 지명이 없는 명령은 그 셋이 **전부** 수행한다.

### 2.4e 재현했다 — **주인 자신의 폭 변경** (2026-09-19)

접수 화면의 진단값이 왔다: `cols:162 rows:8 seq:5278 ws:true owner:false`.
`owner:false` 는 **콘솔을 연 탓**이다 — `resizeCheck` 의 첫 줄이
`if(!this.windowFocused) return false` 이므로 개발자도구로 포커스가 옮겨가면 그
순간 거짓이 된다. 잔재가 **난 시점**의 값이 아니다.

두 컨텍스트(1600×1000 주인 · 700×900)로 재현했고, **깨지는 쪽은 주인이었다.**

| 창 | owner | 화면 |
|---|---|---|
| 비주인 | `false` | **깨끗** — 표식 1회, 3줄 정확 |
| 주인 | `true` | **잔재** — 표식 5회, `ROW1-yyy…ROW0-yyy…` 로 섞였다 |

비주인은 `_applyPtySize()` → `_refreshForWidth()`(전량 재생)를 타서 화면이 새 폭으로
다시 파싱된다. 주인은 **자기 리사이즈**라 그 경로에서 빠진다 (`D-M10-3`).

§2.4c 가 그 자리를 이미 짚어 두었다 — *"`ptySize()` 는 `had` 를 `doFit()` 뒤의
`term.cols` 와 비교하는데, 창 크기 변경이 이미 `doFit()` 을 돌려 놓았으므로
`cols===had` 다."* 그때는 **리플로우가 감당한다**고 보아 경계로 두었다. 이번 재현이
그 전제를 깬다: 앱이 **커서를 올려 덮어쓰는** 방식이면 감당하지 못한다. 옛 폭에서
그린 줄이 새 폭에서 래핑되어 줄 수가 달라지면 앱의 "몇 줄 위로" 셈이 틀어지고, 그
아래에 옛 글자가 남는다. claude 가 정확히 그 방식이며 접수 화면이 그 모습이다.

처음에는 **처방이 이미 코드에 있다**고 적었다 — 주인 창에 `_refreshForWidth()` 를
걸었더니 표식이 5회에서 1회가 됐기 때문이다. **그 판정은 틀렸다.** 조건을 바꿔
다시 재니 같은 처방이 표식을 6회에서 **8회로 늘렸다.**

이유는 tail 의 성질이다. 앱이 어긋나게 그린 결과는 **이미 PTY 출력 기록에 들어가
있고**, 전량 재생은 그 기록을 되뿌리는 일이다 — 잔재를 지우는 것이 아니라 **다시
그린다.** 처음 회차에서 줄어 보인 것은 그때의 tail 이 짧아 우연히 깨끗해 보인
것이었다. `M10_PROGRESS §2-13` 이 경고한 자리를 또 밟았다.

### 2.4f 넛지가 잔재를 **늘린다** (2026-09-19 실측)

같은 배치에서 `_redrawNudge()` 만 무력화하고 다시 쟀다.

| | 화면에 남은 표식 |
|---|---|
| 넛지 있음 (현재 동작) | **6** |
| 넛지 없음 | **2** |

넛지는 `rows-1` → `rows` 로 리사이즈를 **두 번** 보낸다 (FR-TRS-20). 앱은 `SIGWINCH`
를 두 번 받아 두 번 다시 그리고, **화면을 지우지 않고 커서만 올려 덮어쓰는 앱**은
그때마다 어긋난 그림을 하나씩 더 쌓는다.

`FR-TRS-18` 이 넛지를 들인 근거는 *"tail 밖에서 켜진 모드는 되살아나지 않으니 앱이
전체를 다시 그리게 한다"* 이고 그 자체는 유효하다. 다만 **다시 그리는 방식이 앱마다
다르다**는 것이 이 실측이 보탠 사실이다 — 화면을 지우는 앱에는 약이고, 커서를 올려
덮어쓰는 앱에는 독이다. claude 가 후자다.

**처방** (사용자 결정 2026-09-19): 넛지를 **alt screen 인 앱에만** 건다
(`TERMINAL_RESUME_SRS` `FR-TRS-18a`). 넛지가 막는 영구 desync 는 alt screen
앱에서만 일어나므로(`§2.4`), 약을 버리는 것이 아니라 필요한 곳에만 남기는 일이다 —
vim·top 은 종전대로 받고 claude 는 받지 않는다.

## 3. 요구

### FR-M11-1 — 폭이 바뀐 사실은 소켓보다 오래 산다

폭이 바뀌면 `_refreshForWidth()` 는 **소켓의 상태와 무관하게 재생 좌표를 버린다.**
소켓이 있으면 종전대로 즉시 다시 붙고(quiet), 없으면 **버린 좌표만 남긴다** —
그러면 이미 비행 중인(또는 뒤이을) 재접속이 `since` 없이 붙어 전량 재생을 받는다.

- **이전 동작**: `!this.ws` 면 `_seq` 를 그대로 둔 채 `false` 를 내고 물러난다.
  뒤이은 재접속이 델타가 되어 옛 폭의 그림이 남는다 (§2.4c·§2.4d)
- **새 동작**: `_destroyed`·`_exited` 가 아니면 **먼저** `_seq=-1`·`_seqLive=false`
  를 세우고, 소켓이 없으면 거기서 멈춘다. 좌표를 버렸으므로 다음 접속은 전량이다
- **이유**: 폭이 바뀐 것은 **화면의 사실**이고 전송로의 사실이 아니다. 전송로가
  잠깐 없다고 화면의 사실을 잃으면, 그 사실은 다시 오지 않는다 — 폭은 이미
  바뀌어 있어 다음 `ptySize()` 도 `cols!==had` 를 보지 못한다

좌표를 버릴 때 **디코더도 함께 판정한다** (`_resetDecoderIfNoResume`, FR-TRS-4).
종전에는 `reconnectNow` 안에서 그 판정이 돌았고, 소켓 없는 갈래는 그 자리를
지나지 않는다 — 반쪽 멀티바이트가 전량 재생의 첫 바이트에 이어 붙는다.

> **`ws` 없는 갈래는 `false` 를 그대로 낸다.** 반환값은 *"지금 다시 붙였는가"* 이고
> 그 뜻을 바꾸지 않는다. 바뀐 것은 **좌표를 버리는 일이 그 앞에 선다**는 것뿐이다.

### FR-M11-2 — GUI 의 스크롤은 앱의 스크롤이다 (M11-B4)

에이전트 GUI 안에서 넘치는 표면은 전부 `ui-scroll` 의 규약을 따른다 — 대화
(`agp-log`) · 입력(`agp-ta`) · 도구 카드의 입력·결과(`agp-tool-in`·`agp-tool-res`) ·
승인 다이얼로그의 입력(`agp-appr-in`).

- **이전 동작**: 넷 다 브라우저 기본 스크롤바다 (실측 — `scrollbar-width:auto`)
- **새 동작**: `style-kit.css` 의 `.ui-scroll` 선택자에 이 표면들이 함께 선다
- **이유**: 규약은 **이미 있고 GUI 만 쓰지 않았다.** 새 모양을 만드는 것이 아니라
  빠져 있던 자리를 잇는 일이다 — 새로 그리면 두 벌이 된다

좁은 목록의 4px(`sbl-list`·`theme-list`)은 여기 들지 않는다. 그 자리의 뜻이 다르고
`style-kit.css` §6 이 이미 비목표로 적었다.

### FR-M11-3 — 말한 사람이 색으로 갈린다 (M11-B5)

대화의 조각은 **누가 말했는가**로 색이 갈린다: 사용자 · 에이전트 · 생각 · 도구 ·
오류. 종전에 색이 붙은 것은 사용자 말풍선(`accent-subtle`)과 오류(`danger-text`)뿐이고
나머지는 전부 같은 테두리·같은 바탕이었다.

- **이전 동작**: 에이전트 말·도구 카드·생각이 같은 `--border`·`--sidebar-bg` 다
- **새 동작**: 조각마다 **왼쪽 띠 하나**로 갈린다. 바탕은 건드리지 않는다
- **이유**: 접수한 말이 *"읽고 구분하기 힘들다"* 이므로 필요한 것은 **경계**지
  채도가 아니다. 바탕을 칠하면 대비가 무너지고 `hardcoded-color`·대비 검사가
  지키는 것을 되돌린다 — 색은 전부 토큰에서 온다

### FR-M11-4 — 도구 사용은 접힌 채 선다 (M11-B6)

도구 카드(`agp-tool`)는 `details`/`summary` 로 서고 **기본이 접힘**이다. 머리에
도구 이름과 결과 여부가 남고, 입력·결과는 펴야 보인다.

- **이전 동작**: 입력과 결과가 항상 펼쳐져 있다 (각각 `max-height:240px`)
- **새 동작**: 접힌 채 서고, 머리를 누르면 펴진다. **오류는 펼친 채 선다**
- **이유**: 대화를 읽는 것이 목적인데 도구 본문이 화면을 먹는다. 오류를 예외로
  두는 것은 그것이 **읽으라고 있는 것**이기 때문이다

> `agp-raw` 는 이미 `details` 다 — 같은 모양을 쓰는 것이지 새 관용구가 아니다.

### FR-M11-5 — 끝난 것을 보고 연다 (M11-B2)

`agentLiftFromTerminal` 은 셸 쪽 에이전트가 **사라진 것을 확인한 뒤에만** GUI 탭을
연다. 확인하지 못하면 **열지 않고** 그 사실을 말한다.

- **이전 동작**: `exitCommand` 를 넣고 **답을 기다리지 않은 채** GUI 를 열었다.
  에이전트가 턴 중이면 그 한 줄은 입력창에 얹힐 뿐이라 프로세스가 살아남는다 —
  접수한 말이 *"gui 탭도 켜지고 에이전트도 살아서 돌아가고있다"* 다
- **새 동작**: 턴 중이면 **먼저 끊고**(ESC) · 종료 명령을 넣고 · 활동 등록부에서
  그 도구가 사라지기를 기다린다. 시한(`AGENT_LIFT_EXIT_MS`) 안에 사라지지 않으면
  GUI 를 **열지 않는다**
- **이유**: 둘을 다 여는 것보다 **하나도 안 여는 쪽**이 낫다. 같은 세션을 두
  프로세스가 `--resume` 으로 잡으면 충돌하고, 그 충돌은 화면이 말하지 못한다

판정의 원천은 **활동 등록부**다 (`SessionEnd` 훅 → `_onToolActivity` 가 항목을
지운다). 화면 출력으로 짐작하지 않는 것은 `refreshLift` 와 같은 근거다 —
fingerprint 는 `FR-SKL-2` 가 이미 지운 방식이다.

> **탭과 에이전트를 가른다.** 사용자 결정은 *"전환하면 반대쪽은 닫힌다"* 이고
> 접수한 말은 *"에이전트도 살아서 돌아가고있다"* 다. 죽는 것은 **에이전트**이며
> 터미널 **탭**은 남는다 — 거기에는 사용자의 셸이 살고, 그것이 D-M9-20 이다.
> 반대 방향(`agentOpenTerminal`)은 이미 옛 탭을 닫는다 (FR-M9-31).

### FR-M11-6 — 아는 것은 턴 전에도 말한다 (M11-B3)

대시보드는 **턴을 돌리기 전에도** 우리가 아는 값을 전부 말한다.

- **계정·플랜** — `initialize` 응답이 주고 어댑터가 `ProtoStatus.Account` 로
  날라 오는데 **화면이 버리고 있었다.** 그리는 자리를 더한다 (`agp-acct`)
- **모델·권한 모드** — 프로토콜이 아직 말하지 않았으면 **기동 옵션**으로 답한다.
  `recordLocked` 가 이미 같은 사다리를 쓰므로 `State()` 도 같은 답을 해야 한다 —
  두 자리가 갈리면 디스크 기록과 화면이 어긋난다
- **비용·토큰·한도는 그대로 둔다.** 그 수는 턴의 결과 프레임에만 있고
  `initialize` 응답에 아예 없다(§2.5 실측). 없는 것을 지어내지 않는다 (FR-CBG-5)

> **사용자 결정 (2026-09-15)**: *"있는 것만 더 그린다."* 빈 자리를 세우고 `—` 로
> 채우는 길은 고르지 않았다 — `FR-M9-40` 이 세운 *"모르면 그리지 않는다"* 를
> 되돌리지 않는다.

### FR-M11-7 — 세션 id 도 신호다 (M11-B7)

컨텍스트 관측(`reportContext`)은 **세션 id 하나만 있어도 나간다.**

- **이전 동작**: 나갈지 말지를 **전사본과 압축**으로만 판정했다. `SessionStart` 는
  전사본이 아직 없는 자리라(그 파일은 첫 프롬프트에야 생긴다) 신원을 들고도
  조용히 돌아섰고, 서버는 그 도구의 세션을 모른 채였다
- **새 동작**: `rep.SessionID` 가 있으면 보낸다. 없는 값(경로·크기)은 **여전히 싣지
  않는다** — 지어내지 않는 규약은 그대로다 (FR-CBG-5)
- **이유**: 사용자 확인이 *"첫 프롬프트를 보내면 나와"* 였다. 버튼이 **나중에**
  서는 것은 신원이 늦게 오기 때문이고, 늦게 온 까닭이 이 판정이다

> `FR-M9-37` 이 같은 증상을 한 번 겨냥했고 그때 더한 것은 `dmctl agent-context` 의
> 플러그인 훅이다. 이 조항이 닫는 것은 **설정 훅 쪽의 같은 구멍**이다 — 두 계기가
> 같은 것을 실어야 한 쪽만 고쳐지는 일이 없다 (`reportContext` 주석이 이미 적은 규약).

### FR-M11-9 — 끝난 세션은 올릴 수 없다 (M11-B8)

**접수 (사용자, 2026-09-15)**: *"이제는 에이전트가 안켜져도 버튼이있는데? 정확히말하면
껐는데도 안사라져."*

신원을 **붙드는 자리는 있었으나 놓는 자리가 없었다** — `agentSessions` 에 지우는
호출이 하나도 없다(전수: `Store` 1 · `Load` 1 · `Range` 1). 종전에는 신원이 애초에
잡히지 않아(M11-B7) 그 사실이 드러나지 않았고, `FR-M11-8` 이 신원을 제때 잡자마자
반대편이 보였다.

- **이전 동작**: 한 번 잡힌 신원이 서버가 사는 동안 남는다 → `liftable` 이 영원히 참
- **새 동작**: 활동이 `ended` 로 오면 **같은 요청 안에서** 그 레코드를 *끝남*으로
  표시하고, `apiAgentSessionOf` 가 그때 `liftable:false` 를 낸다
- **이유**: 진입점은 **지금 올릴 수 있는가**를 말해야 한다. 없는 세션을 가리키는
  버튼은 "모른다" 를 "고장" 으로 보이게 한다 (`apiAgentSessionOf` 의 원래 근거)

**레코드를 지우지는 않는다.** `agentLiftFromTerminal` 은 셸 쪽을 **먼저 끝내고**
그 세션을 GUI 로 여는데(FR-M11-5), 지워 버리면 `transcriptFor` 가 경로를 잃어 올린
화면이 빈 채로 선다 (FR-M9-41). 바뀌는 것은 *올릴 수 있는가* 하나다.

표시도 **방송보다 먼저**다. 뒤에 하면 받는 쪽이 `ended` 를 계기로 되물을 때 아직
"올릴 수 있다" 가 나온다 — FR-M11-8 이 고친 순서 문제가 반대편에서 되살아난다.

> **남는 갭**: 에이전트가 `SessionEnd` 를 내지 못하고 죽으면(강제 종료) 표시가
> 서지 않아 버튼이 남는다. 그때의 신호는 도구의 전경 프로세스이며, 그것은 다른
> 층이다 — 지금은 **갭으로 적어 둔다**.

### FR-M11-10 — 시선을 옮기는 명령은 한 곳에서만 돈다 (M11-B9)

화면을 옮기거나 워크스페이스를 줄이는 명령은 **실행자로 지명된 클라이언트에서만**
수행된다. 지명은 이미 있는 자리(`hub.singleExecutorActions` → `Focus.Executor()`)를
그대로 쓴다 — 두 방송 경로가 그 한 자리를 함께 본다.

더하는 것은 열둘이다:

```
focus · closeTab · closeWindow · detachTab
windowNext · windowPrev · tabNext · tabPrev
paneUp · paneDown · paneLeft · paneRight
```

- **이전 동작**: 지명이 없어 **붙어 있는 브라우저 전부**가 수행한다. 한 기기에서
  낸 `window-next` 하나가 다른 기기의 화면까지 옮긴다 (§2.7 실측)
- **새 동작**: 가장 최근에 창을 주장한 클라이언트(= 사용자가 지금 쓰는 브라우저)
  하나만 수행한다. 나머지는 `workspace_changed` 로 **트리만** 따라가고, 그 경로는
  이미 로컬 `activeWindow` 를 보존한다 (`app-cmd.js:437`)
- **이유**: `openUrl` 이 같은 이유로 이미 지명된다 — *"게이팅하지 않으면 붙어 있는
  기기마다 같은 URL 이 열린다"*. 시선도 같은 성질이다

`renameTab`·`renameWindow` 는 **더하지 않는다.** 그 둘은 순수 데이터이고 시선을
건드리지 않으며, 클라이언트마다 같은 결과로 수렴한다 (그 자리 주석이 이미 그렇게
적었고 이 조항은 그 문장을 반박하지 않는다 — 반박하는 것은 *"나머지 변경도
idempotent 하다"* 쪽이다).

### FR-M11-11 — `--no-focus` 는 닫기에서도 지켜진다 (M11-B9 의 둘째)

`closeWindow` 의 `force`·`keepTool` 갈래는 공통 경로를 타지 않아 `keepFocus` 복원
블록을 지나지 않는다.

- **이전 동작**: `dmctl close-window --at <uuid> --force -n` 이 `_focusLocation` 으로
  그 창을 활성으로 만든 뒤 닫는다. `-n` 을 주어도 시선이 옮겨진다 (§2.7 실측)
- **새 동작**: 그 갈래도 닫기 전의 활성 창·포커스 칸을 기억했다가 되돌린다
- **이유**: `-n` 은 *"명령 실행 전후로 사용자 포커스를 이동시키지 않는다"* 는 약속이다.
  한 갈래만 지키지 않으면 그 약속은 없는 것과 같다

### FR-M11-12 — 아무것도 돌지 않는 도구는 올릴 수 없다 (M11-B8 의 나머지)

`apiAgentSessionOf` 는 그 도구의 **전경 프로세스가 있을 때만** `liftable` 을 낸다.

- **이전 동작**: `ended` 표시만 보았다. 그 신호는 훅이 내므로 에이전트가 그것을
  내지 못하고 죽으면 서지 않는다 — **운영 실측에서 전경이 빈 도구가 `liftable:true`
  였다** (재시동 직후, `fg=` 빈 도구 하나)
- **새 동작**: 전경이 비었으면 `false`. 셸이 프롬프트에 서 있다는 뜻이고, 거기에
  올릴 세션은 없다
- **이유**: `ended` 는 **말해 줘야 아는 것**이고 전경은 **보면 아는 것**이다. 둘을
  함께 두면 한쪽이 없을 때도 답이 선다

이름을 맞춰 보지 않는다 — 프로세스 이름으로 "에이전트처럼 보이는가" 를 짐작하는
것은 `FR-SKL-2` 가 지운 방식이다. **모르면 막지 않는다**: 도구 등록부가 없으면
종전대로 신원만 보고 답한다 (FR-CBG-5).

> **신원 자체는 지우지 않는다** — FR-M11-9 와 같은 근거다 (올리기가 전사본을 읽는다).

### FR-M11-13~18 — 두 번째 물결 (M11-B10~B15)

> **작성 중.** 접수 여섯을 §2.1 에 담았다. 순서와 근거는 아래 §2.8 이다.
> 번호는 **접수 순서**를 따른다 — B10=13 · B11=14 · B12=15 · B13=16 · B14=17 · B15=18.

#### FR-M11-15 — 하단의 글꼴은 **터미널과 같은 상수**에서 온다 (M11-B12 · B16)

접수는 두 번 왔다. 처음은 *"하단 내용의 크기를 그리고 좀 키워줘 너무 작아"* 였고,
한 단계 올리는 것으로는 부족해 **수를 지정한 재접수**가 왔다 — *"2배로 키워라"*.
그러나 두 배(18px)는 **터미널보다 커진다**. 터미널의 기본값을 사용자에게 보인 뒤
받은 지시가 이것이다:

> *"거기에 맞추자. 터미널 기본값과 같은 상수를 사용."*

  이전: `.agp-dash` 는 `--fs-xs` (9px) · 터미널은 JS 의 `TOPTS.fontSize:14`
  새로: **둘 다 `--fs-lg` (14px) 에서 온다**
  이유: *"2배"* 는 수가 아니라 **읽히는 크기**를 말한 것이었고, 기준이 터미널이다.
        같은 크기를 두 자리에 적으면 **한쪽만 바뀐다** — M11 이 이미 네 번 겪은 길이다

**값이 두 벌이 되지 않는 것이 요구의 절반이다.** 진실은 CSS 토큰 하나이고, 터미널은
`file-editor.js` 가 이미 쓰는 관용구(`getComputedStyle(document.documentElement)
.getPropertyValue(...)`)로 그것을 읽는다 — 새 규약을 만들지 않는다.

**크기는 토큰에서 온다** — `font-size` 게이트가 CSS 리터럴을 잡는다 (FR-TOK-19).

#### FR-M11-19 — 한도 게이지는 **전부이거나 전무다** (M11-B17)

> *"게이지를 보여줄거면 1달/5시간 모두 보여주거나 모두 안보여주는쪽으로 해라."*

**`FR-M9-40` 의 결정을 뒤집는다.** 그때는 *"가장 임박한 것 하나"* 였고 근거는
*"주기마다 바를 그리면 하단이 바로 가득 차고, 그때 컨텍스트 바와 구별되지 않는다"*
였다. 실제 화면에서는 **5시간만 서고 월간이 숨는 것**이 되었고, 그래서 사용자는 옆의
텍스트가 말하는 두 주기 중 하나에만 게이지가 붙은 화면을 본다 — 그 비대칭이 접수다.

  이전: 목록의 **첫 항목 하나**만 바가 된다
  새로: **주기마다 하나씩** 선다. 이름은 각 바의 `aria-label` 이 말한다
  이유: 게이지가 어떤 주기의 것인지 화면이 말하지 않으면, 하나만 선 게이지는
        **계정 전체의 상태로 읽힌다**

*"모두 안 보여주는 쪽"* 은 고르지 않았다 — 게이지 자체가 `M9-B22`(*"bar 가 차는
모양으로도 같이 보고싶어"*)의 접수이므로, 그것을 지우는 것은 앞선 요구를 되돌리는
일이다. **사용자가 둘 중 하나를 고르라 했고 보이는 쪽을 고른다.**

모를 때는 `FR-M11-16` 이 그대로 적용된다 — 주기를 모르므로 **바 하나**가 모름으로
서고, `aria-valuenow` 는 달리지 않는다.

**개정 — FR-M11-32 (M11-B30).** 첫 구현은 게이지 넷을 **한 칸에 몰아** 두고 이름·수치는 그 옆
텍스트에 따로 두었다. 접수가 그것을 되짚었다:

> *"하단 탭에서 5시간옆에 5시간 게이지를 주간 옆에 주간게이지를 넣어야한다."*

  이전: `[게이지 게이지 게이지 게이지] [5시간 44% · 주간 17% · …]`
  새로: `[5시간 44% ▭] [주간 17% ▭] [월간 5% ▭] [opus_weekly 2% ▭]`
  이유: **어느 게이지가 어느 주기의 것인지 눈으로 이어지지 않았다.** `aria-label` 은
        그 사실을 말하지만 그것은 읽히는 쪽이고, 보는 쪽에는 근거가 없었다

주기 하나가 **이름·수치·게이지를 담는 한 칸**(`.agp-limit`)이 된다.

#### FR-M11-17 — 대화의 자리는 **떠나도 남는다** (M11-B14)

> *"gui 에서 다른곳에 다녀오면 스크롤이 최상단으로 이동해. 유지해야해."*

요소가 문서에서 떨어지면 브라우저가 `scrollTop` 을 버린다. 돌아왔을 때 0 인 것은
그래서다.

  이전: 에이전트 패널의 대화(`agp-log`)는 갈무리되지 않는다
  새로: **떼기 전에** 적고 **붙은 뒤에** 되돌린다
  이유: 과거를 읽으러 올라간 사람이 탭을 한 번 오갈 때마다 처음으로 끌려간다

**규약은 이미 있었고 이 자리만 쓰지 않았다** (§2-6 의 다섯 번째). `_keepScroll()` 은
세 종류를 담는다 — git 패널은 DOM 훑기로, 터미널은 `_keepTermScroll()` 로, 편집기는
`keepView()` 로. **에이전트 패널이 그 셋 어디에도 없었다.**

이름과 판정 문장을 편집기의 것과 같게 둔다 (`keepView`·`restoreView` · `isConnected`
+ `.vis`) — 새 관용구를 만들면 두 벌이 되고, 두 벌은 한쪽만 고쳐진다.

**계기가 하나인 것이 요점이다.** 떼는 자리는 셋이고(`_hideOthers`·`_domGC`·`_place`)
render 머리의 `_keepScroll()` 이 그 셋보다 앞선 유일한 공통 시점이다 — `FR-VSR-2` 가
편집기에 대해, `FR-M9-28` 이 터미널에 대해 세운 그 규약이다.

**되돌리는 시점도 같은 규약을 딛는다** (사용자 재접수 2026-09-15 — *"다른 탭 갔다오면
스크롤이 맨 위로 오는건 남아있는거같아"*).

  이전: 편집기 옆에서 `_mountTabBody` 안에 **곧바로** 되돌렸다
  새로: 되돌릴 것을 적어 두고 **`_restoreScroll()`** 이 비운다
  이유: `_buildPane` 은 pane 을 만들어 **돌려줄 뿐**이고 문서에 붙이는 것은 그 뒤다.
        편집기는 Monaco 인스턴스가 값을 들고 있어 붙기 전에도 서지만, 대화의 자리는
        **DOM `scrollTop`** 이라 그때 쓰면 **조용히 무시된다**

**실측이 그것을 보였다** (2026-09-15): 창을 오갈 때 복원이 `scrollHeight:0` ·
`clientHeight:0` 인 요소에서 돌았고 결과가 0 이었다. **탭만 오갈 때는 서는 것이**
이 결함을 덮었다 — 그 경로에서는 pane 요소가 재사용되어 이미 붙어 있다.

**그 자리는 이미 있었다.** `_restoreScroll()` 의 주석이 *"요소가 문서에 붙은 뒤에만
`scrollTop` 이 값을 받는다"* 라고 적어 두었다 (FR-SCR-2) — §2-6 이 적은 *"규약은 대개
이미 있고, 한 자리가 안 쓴다"* 의 여섯 번째다.

#### FR-M11-20 — 항목은 **눈으로 갈린다** (M11-B18)

> *"너무 각각 항목의 구분이 안간다. 좀 항목의 구분이 되게 색도 넣고 칸도 넣고 해야할 듯?"*

지금 `agp-dash` 는 항목을 `gap` 으로만 띄운다. 값이 길면 어디서 끊기는지 보이지 않고,
`FR-M11-16` 이 자리를 전부 세운 뒤로는 항목 수가 늘어 더 그렇다.

  이전: 간격만 있다
  새로: 항목마다 **칸**(경계)과 **색 구분**이 있다
  이유: 대시보드는 훑어 읽는 자리다. 훑을 수 없으면 자리를 세운 뜻이 절반만 산다

색은 **토큰에서** 온다 (`make gates`). 새 색을 만들지 않고 있는 층을 쓴다.

#### FR-M11-21 — 입력창은 **탭의 1/3 까지 자란다** (M11-B19)

> *"gui 입력창 크기가 고정인데 너무 작다. 탭 크기의 1/3 까지는 커지게 하고 그 이후로 스크롤"*

  이전: `rows=2` 고정
  새로: 내용에 따라 자라고, **패널 높이의 1/3** 에서 멈춘 뒤 스크롤한다
  이유: 긴 프롬프트를 두 줄 창으로 쓰면 앞을 볼 수 없다. 상한이 없으면 반대로 대화가
        밀려난다 — 사용자가 그 상한을 **1/3 로 지정했다**

#### FR-M11-22 — 좌우 이동은 **터미널과 같다** (M11-B20)

접수는 *"ctrl + 좌우화살표"* 로 왔고 **사용자가 `cmd` 로 정정했다.**

  이전: GUI 입력창에는 아무 규약이 없다 (브라우저 기본에 맡긴다)
  새로: `Cmd+좌우` = 줄 처음·끝 · `Alt+좌우` = 단어 이동 — **`term-pane.js` 와 같다**
  이유: 같은 화면의 두 입력이 다른 손을 쓰면 그 자체가 결함이다

macOS 의 `Ctrl+좌우` 는 **OS 가 가져간다** — 붙여도 서지 않으므로 쓰지 않는다.

#### FR-M11-23 — 출력은 **md 로 그리되 원문으로 되돌 수 있다** (M11-B21)

접수에 *"md 가 아닐수도있으니 이건 좀 고민 해 봐야할 것 같다"* 가 함께 왔고, 인터뷰로
**md 로 그리되 메시지마다 원문 토글**을 두기로 정했다 (§2.6b).

  이전: 줄글 그대로
  새로: 마크다운으로 그린다 · 메시지마다 **원문 보기** 토글
  이유: 출력은 주로 md 다. 그러나 로그·표·ASCII 아트는 md 가 아니고, 그때 **되돌릴
        길이 없으면** 사용자는 깨진 화면만 본다

**의존을 새로 들이지 않는다** — `markdown-it`·`highlight.js`·`purify.js` 가 이미
`web/vendor/` 에 있다 (편집기 미리보기가 쓴다). `purify` 를 지나지 않는 경로를 만들지
않는다: 여기 오는 문자열은 **에이전트가 준 것**이다.

#### FR-M11-24 — 출력은 **프로토콜이 준 경계대로 나뉜다** (M11-B22)

> *"출력이 하나의 텍스트 블럭이 맞나? 실제 출력처럼 잘 잘려서 나뉘어 나오면 좋을꺼같다"*

**쟀다** (§2.11 (2)): `assistant` 프레임 하나가 **content block 하나**이고, 블록이 끝날
때마다 온다. **경계는 이미 오고 있었고 우리가 버렸다.**

  이전: `_message()` 가 `this._live` **하나**에 턴 전체를 몰아넣고, 프레임마다 그
        안을 **지우고 다시 그린다** — 앞 블록이 매번 사라졌다가 다시 선다
  새로: 블록 하나가 **자기 요소 하나**다. 덧붙일 뿐 지우지 않는다
  이유: 원본이 `⏺` 를 찍는 자리가 정확히 이 경계다 (§2.10 (2)). 한 덩이로 보이는
        것은 우리가 경계를 지운 결과이지 프로토콜이 주지 않아서가 아니다

**지우지 않는 것이 요구의 절반이다.** 지우고 다시 그리는 손이 `M11-B26`(추론이 안
보인다)의 원인이기도 하다 — 한 자리를 고치면 둘이 닫힌다.

말 블록(`text`)이 끝나면 그 자리는 **닫힌다** — 다음 블록은 새 요소다. 도구 블록
(`tool_use`)은 종전대로 카드이며 `toolUseId` 로 같은 카드를 잇는다.

#### FR-M11-25 — 시스템 텍스트는 **전사본에서 걸러진다** (M11-B23)

> *"`<local-command-caveat>`, `<command-name>` … `[request interrupted by user]` 이것도
> 포함해서 시스템에 필요한 내용은 출력 안하는게 맞다"*

**위생 결함이다.** 올린 세션의 기록을 그릴 때(`FR-M9-41`) 전사본의 **시스템·명령 블록이
그대로 화면에 선다**. 사용자가 쓴 말도, 에이전트가 한 말도 아니다.

  이전: 전사본의 사용자/어시스턴트 항목을 그대로 그린다
  새로: **하네스가 끼운 것**은 그리지 않는다
  이유: 그것을 보이면 사용자는 자기가 하지 않은 말을 자기 기록에서 읽는다

**무엇이 하네스의 것인가는 실측으로 정했다** (§2.11 (6)) — 전사본 여덟 벌을 전수로 훑어
여섯 종을 셌다. **전부 자기 항목을 통째로 차지하고** 사용자의 진짜 말과 섞인 경우가
한 건도 없으므로, 판정은 항목의 **첫 토큰**이다:

    <local-command-caveat>   <command-name>   <local-command-stdout>
    <task-notification>      [Request interrupted by user…]

**본문을 잘라 내지 않는다.** 항목 전체를 버리거나 전체를 남기거나 둘 중 하나다 —
잘라 내는 손은 사용자의 말이 같은 항목에 섞였을 때 그것을 함께 자른다.

거르는 자리는 **어댑터**다 (`claudeDecodeUser`). 형식이 어댑터마다 다르므로
`history.go` 에 두면 claude 의 형식이 모든 어댑터의 규약이 된다 — `ParseHistory` 가
어댑터에 있는 것과 같은 근거다. 스트림과 전사본이 **같은 함수를 지나므로**
`[Request interrupted by user]` 는 두 길에서 함께 걸러진다.

#### FR-M11-26 — 스크롤은 **바닥에 있을 때만 따라간다** (M11-B24)

> *"새 글이 있으면 무조건 스크롤을 아래로 내린다. 현재위치 고정해야한다. 스크롤은
> 사용자만 조작한다."*

  이전: `_scrollEnd()` 를 **무조건** 부른다 (3곳)
  새로: **부르기 전에 바닥에 있었는지 본다.** 아니면 그 자리를 지킨다
  이유: 읽는 중에 끌려가면 읽을 수 없다

사용자 결정 (§2.6b): *"절대 자동으로 움직이지 않는다"* 는 접수 문면에 더 가깝지만,
최신을 보던 사람이 턴마다 손으로 내려야 하므로 **바닥 판정**을 쓴다.

#### FR-M11-27 — 접힌 출력은 **무엇인지 말한다** (M11-B25)

> *"접히는 출력에서 요약정도(앞뒤 일부를 보이거나하는등)은 해줘라 뭔지는 알아야지.
> n 줄 이내면 그냥 출력해도좋다."*

사용자 결정 (§2.6b): **5줄 이내는 그대로, 넘으면 앞뒤 2줄씩**.

  이전: `details` 가 닫혀 있고 머리만 보인다 — 내용은 짐작할 수 없다
  새로: 짧으면 펼친 채, 길면 **앞 2줄 · 뒤 2줄**과 남은 줄 수
  이유: 도구 출력은 **끝줄에 결론**이 있는 경우가 많다 — 앞만 보이면 성패를 모른다

**개정 (사용자 결정 2026-09-15) — 긴 쪽은 한 문장이다.** §2.10 (3) 이 남긴 물음
(*"원본 쪽으로 다시 물어야 한다"*)의 답이며, `D-M11-3` 을 그대로 따른다:

  이전: 넘으면 **앞 2줄 · 뒤 2줄**과 남은 줄 수 (V-M11-49 의 옛 계약)
  새로: 넘으면 **한 문장** — 규모와 펼치는 법만 말한다
  이유: 원본이 `Searched for 1 pattern (ctrl+o to expand)` 로 그렇게 한다. 앞뒤
        두 줄은 접힌 머리를 **네 줄로 만들어** 접은 뜻을 되돌린다

**짧은 쪽은 바뀌지 않는다** — 원본도 세 줄짜리 출력은 그대로 보인다 (§2.10 (2) 의
`⎿ hello / WORLD / third line`). 접수의 *"n 줄 이내면 그냥 출력해도좋다"* 와 원본이
같은 말을 하므로 그 갈래는 손대지 않는다.

**원본의 동사는 옮기지 않는다.** `Searched for 1 pattern` 은 claude 가 도구마다 문구를
아는 덕이고 우리에게 그 사전이 없다 — 지어내면 모르는 도구에서 틀린 말을 한다. 우리가
아는 것은 **규모**이므로 그것을 말한다 (`12줄 · 눌러서 펼침`).

#### FR-M11-28 — 추론은 **주는 만큼 보인다** (M11-B26)

> *"추론내용도 보여주면 좋을 것 같은데"*

**쟀다** (§2.11 (1)): **claude 는 추론 내용을 주지 않는다.** `thinking_delta.thinking`
이 여덟 번 모두 빈 문자열이고 스냅샷의 thinking 블록도 비어 있다. 오는 것은
**토큰 수**뿐이다 (`estimated_tokens`). 원본이 `thought for 2s` 로 시간만 말하는 것이
이 때문이다.

**사용자 결정 (2026-09-15): 오면 내용, 없으면 시간·토큰.**

  이전: `thinking_delta` 를 `details` 에 잇는다 — claude 에서는 **빈 칸**이 서고,
        그나마 `assistant` 스냅샷이 올 때 **지워진다** (§2.11 (1))
  새로: 내용이 있으면 접힌 채 내용을, 없으면 **`추론 2.4s · 250 토큰`** 한 줄
  이유: `codex`·`omp` 는 내용을 준다 — 없는 쪽에 맞춰 그 값을 버리면 있는 것을
        모름으로 만든다. 반대로 claude 에서 빈 칸을 세우면 **모름이 아니라 고장**으로
        읽힌다 (FR-CBG-5 의 양쪽)

**시간은 우리가 잰다.** 프로토콜은 시간을 주지 않지만 추론 블록의 시작과 끝은 우리가
본다 — 지어내는 값이 아니라 **관측한 값**이다. 토큰은 프로토콜이 준 그대로다.

**그러므로 재생에는 시간이 없다.** 재생은 지난 이벤트를 순식간에 흘리므로 거기서 재면
`0.0초` 가 나오고, 그것은 모름이 아니라 **거짓**이다 (FR-CBG-5). 재생이면 시간을 아예
달지 않고 토큰만 적는다 — 토큰은 프로토콜이 준 값이라 재생에서도 참이다.

**지우지 않는 손이 이것을 함께 고친다** (FR-M11-24): 스냅샷이 live 를 비우지 않게
되면 세워 둔 추론 칸이 살아남는다. 한 자리다.

#### FR-M11-29 — 턴 중의 입력은 **쌓이고, 보이고, 위로 꺼낸다** (M11-B27 · B15 · B35)

> *"추론중에 입력하면 그대로 입력된다 이것도 수정해야한다"* · *"프롬프트를 연달아
> 보낼때의 동작도 실제와 달라"* · *"큐에 넣은 프롬프트를 취소할 수 없다"*

**셋은 한 자리다.** 원본을 §2.10 (5) 에서 쟀고 그것이 명세다.

  이전: 턴 중에도 `send()` 가 곧바로 `/api/agent/prompt` 로 나간다. 큐라는 개념이
        **아예 없고**, `Esc` 는 `interrupt()` 하나뿐이다
  새로: 턴 중의 프롬프트는 **큐에 쌓인다**. 쌓인 것은 입력창 **위에** `❯ <본문>` 으로
        줄줄이 서고, 입력창은 **`Press up to edit queued messages`** 로 바뀐다
  이유: 접수 셋이 전부 *"원본과 다르다"* 한 문장이다

**손이 둘이고 하는 일이 다르다** (§2.10 (5) 의 실측):

| 손 | 하는 일 |
|---|---|
| **위 화살표** | 큐의 **마지막을 꺼내 고쳐 쓴다** — 취소는 그 결과다 (빈 채로 보내지 않으면 사라진다) |
| **`Esc`** | **도는 턴을 끊고 쌓인 것을 한 번에 보낸다** — 사용자 실측: *"esc 누르면 현재 동작 취소되고 큐가 한번에 들어가"* |

**`Esc` 의 종전 동작을 지우지 않는다** — 큐가 비어 있으면 `Esc` 는 지금처럼 `interrupt()`
하나다. 더해지는 것은 *큐가 있을 때* 의 갈래다.

**위 화살표는 큐를 먼저 본다.** 지금 그 키는 프롬프트 이력을 훑는데(`_histMove`), 원본이
그 자리에 큐를 두었으므로 **큐가 있으면 큐, 없으면 이력**이다. 두 벌의 손을 만들지 않는다.

턴이 끝나면 큐의 **맨 앞 하나**가 나간다 — 원본이 *"앞 턴이 끝난 뒤 처리된다"* 이고,
한꺼번에 밀어 넣는 것은 `Esc` 쪽의 일이다.

**큐는 화면의 것이다.** 서버에 큐를 두지 않는다 — 원본의 큐도 TUI 의 것이고, 서버에
두면 보는 브라우저마다 다른 큐가 서거나 남의 큐가 내 화면에 선다 (FR-AGT-12 의 규약).

**보내는 문은 하나다.** 입력창만이 아니라 `FR-M11-14` 의 **고르는 화면**도 그 문을
지난다 — 두 자리가 각자 보내면 턴 중에 고른 값이 큐를 건너뛰고, 접수한 증상이
**한 경로에만** 남는다.

#### FR-M11-30 — 이미지를 **붙일 수 있다** (M11-B28)

> *"이미지 첨부 기능도 없다 같이해야한다"*

**쟀다** (§2.11 (4)): 프로토콜은 **받는다.** `user` 프레임의 `content` 를 배열로 보내면
`image` 블록이 통한다 (8×8 빨강 PNG 로 확인 — 답이 *"빨강"* 이었다).

  이전: `claudePrompt` 가 `content` 를 **문자열로만** 보낸다 — 실을 자리가 없다
  새로: 첨부가 있으면 **배열**로 보낸다: `[image…, {type:text}]`
  이유: 막힌 것은 프로토콜이 아니라 그 한 줄이었다

**붙이는 손은 원본과 같다** — 입력창에 **붙여넣기**(`ctrl/cmd+v`)다 (§2.10 (6)). 원본이
프롬프트에 `[Image #1]` 로 적으므로 **우리도 그 자리를 그렇게 적는다**: 본문에는
`[Image #1]` 이 서고 실제 바이트는 블록으로 간다.

**터미널의 업로드 규약을 빌리지 않는다** — 그쪽은 파일을 **디스크에 놓는** 일이고
(`term-pane.js`), 이쪽은 프롬프트에 **싣는** 일이다. 같은 이름의 다른 일이다.

**본문이 가리키는 것만 간다.** 표식을 지우는 것이 붙인 것을 **무르는 손**이며, 보낸
뒤에는 남은 것도 버린다 — 그러지 않으면 화면이 말하지 않는 바이트가 실리고, 다음
프롬프트에 **몰래** 딸려 간다. 화면이 보이는 것과 나가는 것이 같아야 한다.

**종단의 상한을 올린다.** JSON 본문의 기본 상한은 1 MiB 이고 그 값의 근거는 *"JSON
종단이 다루는 것보다 한참 크다"* 였다 (`FR-RQG-15`) — **이미지가 실리는 프롬프트는 그
전제 밖**이다. base64 는 원본의 약 4/3 이라 768 KB 남짓이 한계이고 화면 캡처는 대개 그보다
크므로, 올리지 않으면 이 요구는 413 으로만 끝난다. **이 종단만** 올린다: 나머지 열일곱
종단의 전제는 그대로 참이고, 상한 자체는 남는다 (넘으면 413 이며 조용히 잘리지 않는다).

#### FR-M11-31 — 질문에는 **직접 적어 답할 수 있다** (M11-B29)

> *"질문에 답하는 모달에서 내가 원하는 답을 자유롭게 적는것도 필요하다"*

  이전: `agp-modal` 은 에이전트가 준 **선택지만** 준다
  새로: **선택지 목록의 마지막 항목**으로 *직접 입력* 이 서고, 그것을 고르면 칸이 열린다
  이유: 선택지가 사용자의 뜻을 담지 못할 때 지금은 취소하고 다시 쓰는 길밖에 없다

**원본을 쟀고 그 모양이다** (§2.10 (9), 사용자 결정 2026-09-15): TUI 는 자유 입력을
별도 칸이 아니라 **`3. Type something.`** 으로 **선택지와 같은 목록**에 둔다. 고르는
손과 적는 손이 하나이며, 그래서 *"고른 뒤 적는다"* 가 한 흐름이다.

**항상 보이는 칸을 두지 않는다** — 그러면 라디오를 고른 채 칸에도 적은 상태가 만들어지고
무엇이 답인지 화면이 말하지 못한다. 목록의 한 항목이면 **고른 것이 곧 답**이다.

원본의 `4. Chat about this` 는 **우리 모달의 닫기와 같은 자리**다 (`FR-APS-6` — 바깥
클릭·Esc 는 답이 아니고 요청은 열린 채 남는다). 항목을 새로 만들지 않는다.

`freeText` 질문(선택지가 아예 없는 질문)은 종전대로 칸 하나다 — 고를 것이 없으면
목록도 없다.

#### FR-M11-36 — 에이전트의 내용은 **선택·복사된다** (M11-B34)

> *"터미널만 텍스트 선택이 가능한 상황인데 agent 의 내용들은 복사 가능해야한다."*

  이전: `body{user-select:none}` 이 전역이고 **터미널만** xterm 이 되살린다
  새로: 에이전트의 **읽는 영역**이 선택된다
  이유: 대화와 도구 출력은 읽고 **가져가는** 자리다

전역 규칙을 뒤집지 않는다 — `[contenteditable]` 이 이미 같은 방식의 예외이며, 그 옆에
선다. 버튼·탭 같은 **조작 자리**는 그대로 선택되지 않아야 한다: 드래그가 그쪽의 뜻이다.

#### FR-M11-34 — 저장소는 **`status.branch`** 에 있다 (M11-B32)

접수: *"저장소가 있는데 알수없음으로 뜬다."* **실측으로 원인을 확정했다** (운영,
`/api/git/status?repo=…`):

    최상위:  cached · isRepo · observedAtUnixMs · repo · requested · … · status
    status:  ahead · behind · branch · changes · … · upstream

`_refreshOrigin` 은 `st.data.branch` 를 읽는다 — **한 겹 위다.** 그래서 `!g.branch`
에서 **언제나** 되돌아섰다.

**이것은 FR-M11-16 이 만든 결함이 아니라 그것이 드러낸 결함이다.** 종전에는 이 갈래가
빈 문자열을 남겼고 `:empty` 가 그 자리를 지웠으므로 **화면에 아무것도 없었다** —
아무도 몰랐다. 자리를 세우자 *"알 수 없음"* 으로 보였다. §2-5 가 적은 *"고침 하나가
반대편을 드러낸다"* 의 다섯 번째다.

**검사가 이것을 놓친 까닭도 적는다.** `V-M9-35` 는 *"비었거나, git 이 준 이름"* 까지만
고정했다 — 환경에 달렸다는 이유로 **빈 쪽을 허용**했고, 그 허용이 결함을 덮었다.
새 계약은 **저장소인 cwd 에서는 이름이 선다** 이다.

#### FR-M11-33 — 비용은 **그리지 않는다** (M11-B31)

> *"비용은 제거하자."*

자리와 값 모두 없앤다. `FR-M9-39` 가 세운 항목 하나를 되돌리는 것이며, 근거는
사용자 결정이다 — 우리가 그 수를 못 구해서가 아니다.

#### FR-M11-35 — 작업 폴더는 **경로 그대로** 적는다 (M11-B33)

> *"현재 경로도 적어야한다."*

  이전: `pathBase(cwd)` — 마지막 한 칸만 (전체 경로는 `title` 에만)
  새로: **경로 그대로**
  이유: 같은 이름의 폴더가 여럿일 때 마지막 칸만으로는 어디인지 모른다. `title` 은
        가리키지 않으면 보이지 않으므로 *"적혀 있다"* 가 아니다

#### FR-M11-16 — 하단은 **자리를 세우고 모름을 말한다** (M11-B13)

**사용자 결정의 번복이다.** 앞서 고른 *"있는 것만 더 그린다"* 를 대체한다 (§2.8).

> *"첫 메세지를 보내기전에는 기본값 설정하고 이후 맞추면 되잖아. 없애지 말고
> 모르는걸로 해서 보여줘."*

  이전: 값이 없는 항목은 빈 문자열이 되고 `.agp-dash>span:empty` 가 자리를 **지운다**
  새로: 자리는 **항상 선다**. 값이 없으면 그 자리에 **모름을 적는다**
  이유: 빈 자리가 *"그런 항목이 아예 없다"* 로 읽혔다. 자리가 서 있으면 사용자는
        **무엇을 기다리는지**를 알고, 값이 오면 그 자리가 채워진다

**이것은 `FR-CBG-5`(모른다 ≠ 0)를 어기지 않는다** — 0 으로 채우는 것이 아니라
**모름을 모름이라고 적는 것**이다. 반대로 **아는 0 은 0 으로 적는다**: 열린 요청 수는
우리가 세는 값이므로 0 이면 `열린 요청: 0` 이고 모름이 아니다.

**닫을 수 없는 것을 기억한다** (§2.5 의 실측): `initialize` 응답에 비용·토큰·한도의
수가 **아예 없다**. 그 수는 턴의 결과 프레임에만 온다. 그러므로 이 요구는 *"값을 구해
오는 일"* 이 아니라 **"모름을 말하는 일"** 이다.

**바 둘은 텍스트와 성질이 다르다.** `role=progressbar` 는 채움이 곧 값이므로, 모르는
자리를 0% 로 그리면 그것이 `FR-CBG-5` 가 막는 바로 그 읽힘이다. **사용자 결정
(2026-09-15)**: 트랙은 **항상 세우되 채움을 0 폭으로 둔다** — 새 무늬 토큰을 만들지
않는다. 화면상 실제 0% 와 같아 보이는 것을 알고 고른 선택이며, **읽히는 쪽에서는
가른다**: 모를 때는 `aria-valuenow` 를 **달지 않는다**(WAI-ARIA 의 indeterminate).
값이 오면 그때 달린다.

문구는 카탈로그에 이미 있는 `core.unknown_paren`(`(알 수 없음)`)을 값 자리에 끼워
쓴다 — 틀이 값을 품지 못하는 다섯(비용·캐시·한도·작업 폴더·저장소)만 키를 더한다.

#### FR-M11-13 — 진입점은 **붙은 뒤에** 묻는다 (M11-B10)

> *"'에이전트로'버튼이 새로고침하면 사라졌다가 다음 이벤트가 있을때 다시 버튼이 뜨네"*

**재현이 원인을 확정했다** (2026-09-15, `lift-button-reload.spec.ts` 의 `fixme` 를 지워
빨갛게 본 뒤 계측):

| 잰 것 | 값 |
|---|---|
| 서버의 답 (`GET /api/agent/session`) | `{"liftable":true,"sessionId":"sess-reload-1"}` |
| 새로고침 뒤 그 요청의 수 | **0건** |
| `_mountTabBody` 의 갈래 | `moved=true · term=true` — **부르긴 부른다** |
| `refreshLift` 가 본 것 | **`el.isConnected === false`** |
| 손으로 다시 부르면 | 버튼이 **선다** |

**되돌아선 자리는 첫 줄이다.** `refreshLift()` 는 `!this.el.isConnected` 로 물러나는데,
첫 렌더의 그 시점에는 탭 본문(`pn-body`)이 **아직 문서에 붙지 않았다.** 탭을 오갈 때는
이미 붙어 있으므로 그 경로에서만 동작했고, 그래서 *"다음 이벤트가 있을때 다시 뜬다"* 다.

  이전: 붙기 **전에** 묻고, 붙지 않았다는 이유로 조용히 물러난다 — 그 뒤 계기가 없다
  새로: **붙은 뒤에** 묻는다
  이유: `isConnected` 가 막으려던 것은 *사라진 도구에 묻지 않는다* 이지
        *아직 붙지 않았다* 가 아니다. 두 뜻이 한 조건에 얹혀 있었다

**`FR-M11-17` 과 같은 부류다** — 그쪽은 *떼기 전에* 적고 *붙은 뒤에* 되돌리는 일이었고,
여기는 *붙은 뒤에* 묻는 일이다. 시점을 한 자리로 모으는 규약(`FR-PDR-10`)이 이미 있고
이 호출만 그 밖에 있었다.

**`await` 뒤의 같은 검사는 그대로 둔다** — 그것은 *묻는 동안 사라졌는가*이고 뜻이 다르다.

#### FR-M11-14 — `/model`·`/config` 는 **고르는 화면을 연다** (M11-B11)

> *"여전히 /model, /config 같은 tui 들은 사용이 불가"*

**쟀다** (§2.11 (5)): 두 명령 모두 **프로토콜에서 정상 응답한다.** `init` 프레임이 말하는
TUI 전용 명령은 `doctor`·`color`·`reload-plugins` **셋뿐**이고 이 둘은 거기 없다.

막힌 것은 명령이 아니라 **고를 자리**다. 원본 TUI 에서 인자 없는 `/model` 은 선택 화면을
띄우는데, 프로토콜은 사용법 텍스트를 돌려줄 뿐이다:

    /model  → "Current model: `Opus 5 …` · Usage: /model <name>. Available: sonnet, opus, …"
    /config → "Usage: /config key=value … · editor=normal|vim · thinking=true|false · …"

  이전: 그 텍스트가 대화에 한 덩이로 서고 끝난다 — 고칠 길이 없다
  새로: **인자 없는 `/model`·`/config` 는 고르는 화면을 연다**. 고른 값은
        `/model <name>` · `/config key=value [key=value ...]` 로 나간다
  이유: 원본이 그 자리에서 하는 일이 그것이다 (`D-M11-3`)

**재료를 지어내지 않는다.** 모델 목록은 `initialize` 가 준 `status.models` 이고 (메뉴가
이미 쓰는 그 값이다), config 의 키·선택지는 **`/config` 응답 텍스트가 준 목록**이다 —
`key=a|b|c` 한 줄이 한 항목이며 파싱은 결정적이다. 응답이 그 모양이 아니면 **열지
않는다**: 종전처럼 텍스트가 그대로 선다.

**고른 것이 여럿이면 여럿이 나간다** — 사용법이 `key=value [key=value ...]` 이므로
화면도 여럿을 세운다. 한 자리만 기억하면 마지막에 만진 것만 나가고, 그것은 폼이 셋을
보이면서 하나만 보내는 **거짓**이다.

**인자가 있으면 가로채지 않는다** — `/model opus` 는 사용자가 이미 고른 것이다.

#### FR-M11-37 — 편집은 **그 자리에서 무엇이 바뀌었는지 보인다** (M11-B36)

> *"실시간으로 diff 를 보여주는것도 있으면 좋겠다"*

원본은 **별도 창을 열지 않는다** (§2.10 (2)) — 도구 결과 **그 자리**에 선다:

    ⎿ Updated sample.txt (+1 -1)
     1 hello
     2 -world
     2 +WORLD
     3 third line

**재료는 결과가 아니라 입력에 있다** (§2.11 (3)): `tool_result` 는 *"has been updated
successfully"* 한 줄뿐이고, 줄 단위 `±` 는 **TUI 가 `tool_use` 의 입력에서 만든 것**이다.

  이전: `Edit` 카드에 `file_path` 한 줄만 선다 — 무엇이 바뀌었는지 화면에 없다
  새로: `old_string`·`new_string` 을 줄로 갈라 **`-`/`+` 로 그린다.** 머리는
        `<파일> (+n -m)`
  이유: 도구 카드가 이미 그 자리이고 (`FR-M11-4`), 원본도 그 자리다

**줄번호는 달지 않는다.** 그 값은 파일 내용을 알아야 나오고 프로토콜은 주지 않는다 —
없는 것을 지어내지 않는다 (FR-CBG-5). 원본이 그것을 아는 것은 TUI 가 파일을 함께 들고
있기 때문이며, 그 조건이 우리에게 없다.

**`Write` 는 `+n` 만이다** (`content` 뿐이라 지워진 줄이 없다). `Edit` 이 아닌 도구에는
서지 않는다 — 모르는 도구의 입력을 diff 로 읽으면 없는 변경을 그린다.

#### FR-M11-38 — 편집의 diff 는 **펼친 채** 선다 (M11-B37)

> *"diff 는 접지말고 기본이 펼친상태로 보고싶다"*

`FR-M11-4` 는 도구 카드를 **접힌 채** 세운다. 그 근거는 *"대화를 읽는 것이 목적"* 이고
도구 출력이 화면을 먹기 때문인데, **diff 는 출력이 아니라 결과 그 자체**다 — 무엇이
바뀌었는지가 곧 그 턴이 한 일이다.

  이전: `Edit`·`Write` 카드도 접힌 채 선다 — diff 를 보려면 눌러야 한다
  새로: **편집 도구의 카드는 펼친 채** 선다
  이유: 오류를 펼친 채 두는 것(`FR-M11-4`)과 같은 근거다 — 읽으라고 있는 것을 접으면
        접수한 증상이 그대로 돌아온다

**펼치는 것은 편집 도구뿐이다.** `Bash` 의 40줄 출력까지 펼치면 `FR-M11-27` 이 접기로
푼 문제가 되살아난다.

#### FR-M11-39 — 스크롤은 **내가 보낼 때 따라가고, 언제든 되돌릴 수 있다** (M11-B38 · B39)

> *"채팅을 치고 엔터를 누르면 스크롤 맨 아래로"* · *"스크롤 맨 아래로 내리는 버튼 추가"*

`FR-M11-26` 은 *"바닥일 때만 따라간다"* 로 정했고 그것은 **에이전트가 말할 때**의 규칙이다.
**내가 보낼 때는 다르다** — 방금 친 말은 내가 보려는 것이다.

  이전: 과거를 읽던 자리에서 프롬프트를 보내면 그 자리에 머문다 — 내 말이 안 보인다
  새로: **보내면 바닥으로 간다**
  이유: 스크롤을 움직이는 것이 사용자의 뜻이라는 규약(`FR-M11-26`)은 그대로다 —
        엔터도 **사용자의 조작**이다

**그리고 되돌아올 길을 둔다.** 바닥이 아닐 때만 서는 버튼이며, 누르면 바닥으로 간다.
자동으로 끌려가지 않는 대신 **한 번에 돌아가는 손**이 없으면 긴 대화에서 내려오는 데
드는 품이 곧 접수가 된다.

#### FR-M11-40 — 고르는 화면이 서면 **그 명령은 대화에 남지 않는다** (M11-B40)

> *"/config, /model 같은 고르는화면일때에는 출력 안해도 됨"*

  이전: `/config` 가 대화에 서고, 사용법 텍스트가 한 덩이로 서고, 그 뒤 폼이 뜬다
  새로: **내 말도 답도 서지 않는다.** 고르는 화면만 뜬다
  이유: 원본 TUI 에서 `/model` 은 **선택 화면으로 끝난다** — 사용법 텍스트는 우리가
        그것을 열기 위해 물은 것이지 사용자가 읽으려던 것이 아니다

**가로채지 못한 경우는 그대로 선다.** 응답이 목록 모양이 아니어서 폼을 열지 못하면
(`FR-M11-14`) 그 텍스트는 **보여야 한다** — 감춘 채 아무것도 열지 않으면 명령이 사라진
것으로 읽힌다.

#### FR-M11-41 — 모달을 닫는 것은 **지금 것을 그만두는 것**이다 (M11-B41)

> *"질문 모달 취소하면 거기서 interrupt 되어야하는데 무한정 기다림"*

**`FR-APS-6` 을 뒤집는다** (사용자 결정 2026-09-15). 그 조항은 *"바깥 클릭·Esc 는 답이
아니다 — 요청은 열린 채 남고 다시 열 수 있다"* 였고, 근거는 *실수로 닫은 것을 되돌릴 수
있어야 한다* 였다. 실제로 쓰니 **되돌릴 길보다 멈출 길이 급했다.**

  이전: 닫아도 요청이 열린 채 남는다 — 에이전트는 계속 기다린다
  새로: 닫으면 **거절을 보내고 이어서 턴을 끊는다**
  이유: 사용자가 고른 것은 *"턴을 끊는다"* 이고, 실측(§2.12)이 **interrupt 만으로는 그
        결정이 이뤄지지 않음**을 보였다 — 열린 승인 요청은 답을 받아야 닫히고, claude
        에는 답 없이 닫는 프레임이 없다 (`claudeProto.Cancel` 이 `nil` 인 그 사실)

**순서가 요점이다.** 거절이 먼저다: 끊기부터 보내면 그 사이 에이전트가 승인을 기다리는
채로 남아 같은 무한 대기가 된다.

#### FR-M11-42 — `Esc` 는 **패널에 포커스가 있으면** 걸린다 (M11-B42 · B47)

> *"뭔가 특정 동작을 하는중에 interrupt 가 안되는거같아"* · *"esc는 포커스하면 걸리게"*

**동작의 종류가 아니라 포커스가 갈랐다** (§2.12 의 실측 ②): 핸들러가 `this.ta` 하나에만
걸려 있어, 도구가 도는 동안 대화를 클릭하거나 스크롤하면 그때부터 키가 닿지 않는다.

  이전: `Esc`·`Shift+Tab`·좌우 이동이 **입력창에서만** 산다
  새로: **끊는 키는 패널 전체에서** 산다. 글자를 만지는 키(좌우 이동·이력)는 종전대로
        입력창의 것이다
  이유: 끊기는 *지금 도는 것*에 대한 명령이고 입력창의 상태와 무관하다. 반대로 캐럿을
        옮기는 키는 캐럿이 있는 곳의 일이다 — 둘을 한 자리에 두었던 것이 결함이다

**다른 입력을 가로채지 않는다** — 모달이 떠 있으면 그쪽이 먼저 받고(그 처리는
`FR-M11-41` 이 정한다), 패널 밖의 포커스에는 닿지 않는다.

#### FR-M11-43 — 올린 자리는 **이름을 잇고 원래 자리를 비운다** (M11-B43)

> *"에이전트로 할때 tab 이름 가져오고, 원래 탭 지우는걸로 변경"*

  이전: 새 에이전트 탭이 어댑터 이름으로 서고 **원래 터미널 탭이 남는다** — 같은 세션이
        두 자리에 보이고, 하나는 이미 끝난 셸이다
  새로: 원래 탭의 **이름을 물려받고**, 원래 탭은 **닫는다**
  이유: 올리기는 *옮기는 일*이지 *복제하는 일*이 아니다 (`FR-M11-5` 가 "끝난 것을 보고
        연다" 로 이미 그 뜻을 세웠다). 남은 빈 탭은 사용자가 손수 닫아야 할 것이다

**여는 데 실패하면 원래 탭을 닫지 않는다** — 그때 닫으면 돌아갈 자리가 사라진다.

#### FR-M11-44 — `Ctrl+C` 두 번이면 **빠져나와 터미널이 된다** (M11-B44)

> *"gui 에서도 ctrl+c 로 빠져나올 수 있고 이 경우 터미널로 빠져나올 수 있도록"*

**원본 TUI 의 동작 그대로다** (사용자 결정 2026-09-15): 첫 `Ctrl+C` 는 **턴만 끊고**,
연달아 두 번이면 **빠져나온다.**

  이전: GUI 에는 그 손이 없다 — 끝내려면 메뉴를 열어야 한다
  새로: 첫 번은 `Esc` 와 같고, 짧은 사이에 다시 누르면 에이전트를 끝내고 **그 탭이
        터미널이 된다**
  이유: `D-M11-3` — 원본에 있고 여기 없다

**`FR-M11-43` 의 반대 방향이며 같은 규약을 쓴다**: 나가는 자리도 *옮기는 일*이므로 이름을
잇고 새 자리를 만들지 않는다.

#### FR-M11-45 — 질문은 **하나씩 서고 키로 답한다** (M11-B45)

> *"선택 모달좀 질문별로 구분 잘가게 하나씩 보이도록 하고 방향키 상하로 답 선택, 방향키
> 좌우로 질문선택 엔터로 질문넘기기 + summit 페이지 tui 처럼 만들어서 최종확인 후 엔터로 제출"*

원본이 그 모양이다 (§2.10 (9) 실측): `❯` 가 현재 항목을 가리키고 `Enter to select ·
↑/↓ to navigate · Esc to cancel` 을 **늘 적는다.**

  이전: 질문이 여럿이면 `fieldset` 이 세로로 **한꺼번에** 선다 — 어디까지가 한 질문인지
        경계가 약하고, 답하는 손이 마우스뿐이다
  새로: **한 번에 한 질문.** `↑↓` 가 답을, `←→` 가 질문을 옮기고 엔터가 다음으로 넘긴다.
        마지막에 **확인 화면**이 서고 거기서 엔터가 제출이다
  이유: 접수한 그대로이며 원본의 손과 같다

**확인 화면은 원본에 없다** — 사용자가 더한 것이고 `D-M11-3` 의 *"편의는 더하는 것이지
대신하는 것이 아니다"* 에 해당한다. 원본의 손(`↑↓`·엔터)을 지우지 않는다.

**마우스를 지우지 않는다.** 키가 더해지는 것이지 대신하는 것이 아니다 — 클릭으로 고르고
버튼으로 제출하는 길은 그대로 선다 (`FR-A11Y` 의 요구이기도 하다).

#### FR-M11-46 — 하단은 **읽히는 크기와 갈리는 색**이다 (M11-B46)

> *"하단 탭글씨 이전과 지금 사이전도로 줄이자 좀 큰거같아. 그리고 색상좀 다양하게 해서
> 가시성 좋도록. 지금 너무 흐려"*

**`FR-M11-15` 의 개정이다.** 그때는 *"터미널 기본값과 같은 상수"* 로 `--fs-lg`(14px)를
골랐고 — 9px 이 읽히지 않았기 때문이다 — 실제로 쓰니 **이번엔 컸다.**

  이전: `--fs-lg`(14px) · 색은 `--text-hint` **하나**
  새로: **`--fs-md`(12px)** · 색은 **성질로 갈린다**
  이유: 9 와 14 사이를 사용자가 지정했고 그 사이의 토큰이 12 다. 색은 **한 벌이라 흐렸다** —
        열두 항목이 같은 회색이면 무엇이 무엇인지 눈이 갈라 주지 못한다

**색은 성질로 가른다** (자리마다가 아니다 — 그러면 열두 색이 된다):

| 갈래 | 무엇 | 왜 |
|---|---|---|
| 정체 | 모델 · 권한 모드 · 계정 | *이 에이전트가 누구인가* — 가장 먼저 읽는 값 |
| 사용량 | 컨텍스트 · 캐시 | 이 대화가 쓴 것 |
| 한도 | 주기별 한도 | **계정 전체**의 것이라 사용량과 출처가 다르다 (`FR-M9-34`) |
| 자리 | 작업 폴더 · 저장소 · 세션 · 열린 요청 | 우리가 아는 사실 |

**값은 토큰에서 온다** — 게이지가 이미 두 색을 그 근거로 쓰고 있다(컨텍스트는 `--accent`,
한도는 `--attn`). 글자도 **같은 짝**을 쓰면 바와 글이 서로를 가리킨다.

#### FR-M11-47 — 대화를 열면 **바로 칠 수 있다** (M11-B48)

> *"gui 탭을 클릭하면 자동으로 text area 가 선택되어서 바로 프롬프트를 적을 수 있게"*

  이전: 탭을 열고 **한 번 더 눌러야** 친다
  새로: 보이게 되면 입력창이 포커스를 받는다
  이유: 터미널 탭은 이미 그렇다 — 같은 화면의 두 도구가 다른 손을 쓰면 그 자체가 결함이다
        (`FR-M11-22` 가 좌우 키에 대해 세운 그 근거)

**모바일에서는 하지 않는다.** `FR-MTI-25` 가 터미널에 대해 이미 정했다 — 포커스된 입력
요소가 있으면 Android Chrome 이 탭마다 키보드를 다시 올린다. **규약을 새로 만들지 않고
그 판정을 그대로 쓴다.**

#### FR-M11-48 — `/글자` 는 **검색이고 키로 고른다** (M11-B51)

> *"슬레시(/)로 명령시 드롭다운이나 그런 종류로 선택지 선택 가능. /글자 로 입력하면
> / 명령어 검색 가능. 이것도 기본으로 있는 기능이다"*

  이전: **접두 일치**만이고, 고르는 손이 마우스와 `Tab` 하나뿐이었다. 설명은 `title`
        에만 있어 **가리켜야 보인다**
  새로: 이름 **어디에 있어도** 찾고(접두가 앞에 선다), `↑↓` 로 고르고 `Enter`·`Tab`
        으로 넣는다. 설명이 항목에 **선다**
  이유: 원본에 이미 있는 기능이다

**접두를 앞에 두는 것이 요점이다** — 부분 일치만으로 정렬하면 `/model` 을 치는 중에
다른 것이 먼저 서서 찾으려던 것이 아래로 밀린다.

**다 친 명령의 엔터는 보내기다.** 그러지 않으면 `/model` 을 끝까지 치고 엔터를 눌렀을
때 목록이 그것을 *고르고* 다시 눌러야 나간다 — 같은 손짓을 두 번 요구하는 것은 접수한
편의의 반대다. 인자를 받는 명령은 목록이 남으므로 이 갈래가 없으면 **언제나** 두 번이다.

#### FR-M11-49 — 서브에이전트의 것은 **부모 카드 안에 산다** (M11-B49)

> *"서브에이전트들이나 백그라운드 작업같은건 어떻게 해야할까"* · *"서브에이전트에
> 들어가거나 백그라운드 상태도 보고싶은데 … 모아볼 수 있게"*

**쟀다** (§2.13 (1)): 서브에이전트의 진행은 **같은 스트림**으로 오고
`parent_tool_use_id` 만이 그것을 가른다.

  이전: 그 필드를 **읽지도 않았다.** 서브에이전트가 받은 프롬프트가 *사용자가 친 말*
        로 서고, 그 도구가 본 대화의 카드로 선다
  새로: **그 `Agent` 도구 카드 안**에 모은다 (사용자 결정 2026-09-15)
  이유: `FR-M11-25` 와 같은 부류다 — 자기가 하지 않은 말을 자기 기록에서 읽는다

**주인은 한 자리에서 단다** (`claudeDecode` 의 나가는 길). 갈래마다 적으면 새 갈래가
생길 때 조용히 빠진다 — 이 물결에서만 그런 자리를 셋 겪었다.

**본 대화의 상태를 건드리지 않는다**: 서브에이전트의 이벤트는 부모의 활동·사용량·큐를
바꾸지 않는다. 그것들은 본 대화의 것이다.

#### FR-M11-50 — 백그라운드는 **입력이 말하는 것만** 적는다 (M11-B50)

**쟀다** (§2.13 (2)): `run_in_background` 는 **평범한 도구 호출**이고 프로토콜이 진행을
구조로 주지 않는다 — 결과가 *"Command running in background with ID: …"* 라는 **글**이다.

  이전: 다른 도구와 구별되지 않는다
  새로: 도구 머리가 **그 사실을 말한다**
  이유: 우리가 지어내지 않고 말할 수 있는 것이 그 하나다. 그 값은 **입력에 이미 있다**

**글을 파싱하지 않는다.** ID·경로를 문장에서 뽑아 파일을 읽으면 진행을 보일 수도 있으나,
그것은 **하네스의 문구에 기대는 일**이고 판이 바뀌면 조용히 빈다 — `FR-M11-25` 가
*"형식을 추측해 지우면 사용자의 진짜 말을 함께 지운다"* 로 그은 선의 같은 편이다.
갭으로 적는다 (§7).

#### FR-M11-51 — 도는 중이면 **화면이 움직인다** (M11-B52)

> *"지금이 idel, waiting 이 아니고 뭔가를 하고있을 떄 tui 에서는 애니메이션이 있잖아.
> 그런거."*

원본은 `✢ Tinkering… 60` · `✶ Tempering… (38s · ↓ 1.4k tokens)` 으로 **스피너 · 동사 ·
경과 · 받은 토큰**을 함께 돌린다 (§2.10 (4)·(5)).

  이전: 상태 글자(`작업 중`)가 **멈춰 있다** — 도는 중인지 멎었는지 화면이 말하지 않는다
  새로: `working` 동안 **스피너가 돌고 경과가 늘어난다.** 턴이 끝나면 **얼마였는지** 남는다
  이유: 접수 그대로이며, 멈춘 글자는 *"돌고 있다"* 를 말하지 못한다

**모양은 옮기지 않는다** (사용자 결정 2026-09-15 — *"모양을 또같이 할 필요는 없다"*).
원본의 무작위 동사(`Baked`·`Brewed`·`Stewing`…)는 claude 가 가진 사전이고 우리에겐
없다 — 지어내면 카탈로그 밖의 글자가 된다 (`D-M11-4` 와 같은 근거: 주지 않는 값은
옮기지 않는다). **우리가 아는 것은 경과 시간**이며 그것은 관측한 값이다.

**`waiting` 에는 붙지 않는다.** 그때는 **사람을 기다리는** 것이라 움직이면 거짓이 된다 —
접수가 그 둘을 이름으로 갈랐다 (*"idel, waiting 이 아니고"*).

**멎는 자리는 새로 만들지 않는다** — 전역 `prefers-reduced-motion` 규칙이 이미 정한다.
그리고 경과를 다시 적는 것은 **1초에 한 번**이다: 스피너는 CSS 가 돌리므로 프레임마다
DOM 을 만지지 않는다.

**B13 은 사용자 결정의 번복이다.** 앞서 *"있는 것만 더 그린다"* 를 골랐고 그 근거로
`FR-M9-40`(모르면 그리지 않는다)을 지켰다. 새 지시는 **정반대**다:

> *"첫 메세지를 보내기전에는 기본값 설정하고 이후 맞추면 되잖아. 없애지 말고
> 모르는걸로 해서 보여줘."*

즉 **자리는 항상 서고, 값이 없으면 "모름" 으로 말한다.** 이것은 `FR-CBG-5`(모른다 ≠ 0)를
어기지 않는다 — 0 으로 채우는 것이 아니라 **모름을 모름이라고 적는 것**이다. 오히려
빈 자리를 지우는 종전 동작이 "그런 항목이 없다" 로 읽혔다는 것이 접수의 내용이다.

### 2.10 원본 실측 — 실제 claude TUI 의 화면 (2026-09-15)

`D-M11-3` 이 세운 기준을 따라 **원본을 쟀다.** 격리 폴더(`/tmp/dm-tui-probe`)에 새 탭을
띄우고(`dmctl new-tab -n` — 포커스를 뺏지 않는다) 실제 `claude` 를 돌린 화면이다.

**이 절이 세 번째 물결의 명세다.** 접수마다 갈래를 세우지 않는다 — 여기 적힌 모양을
옮기면 그 접수들이 함께 닫힌다.

#### (1) 하단 상태줄 — 여섯 줄, `│` 로 갈린다

    ◆ Opus(H) │ ░░░░░░░░░░ │ 3% │ 32K/1.0M │ $0.42 │ 5h: 24% (3h11m) │ 7d: 46% (4d5h)
    📁️ dm-tui-probe (main*) │ » note.md 분석 │ 🔑️ 36296e6b │ ⏱️ 3m │ 🔥️ 9.1K/min │ ⚡️ 7 tok/s │ ⏳️ ~11m to 5h
    +Dirs: 1 │ ⚙️ Bash(ls -a && echo '---' && ca…) (4 done) │ 📦️ 99% │ 🟡️ 60%
    📊️ In 2 · Out 309 · W 323 · R 32K │ 📈️ $0.42 → ~$7.03/h │ 💰️ Today: $636.76
    +5 -1 │ v2.1.272 │ Off-Peak (4h12m)
    💬️ 16:48 그 다음 README.md 도 만들어줘 │ API 20%

**읽어야 할 것 여덟**:

1. **항목은 `│` 로 갈린다** — 간격이 아니라 **문자 구분자**다 (M11-B18 의 답)
2. **게이지는 컨텍스트 하나뿐**이다. 한도는 `5h: 24% (3h11m)` · `7d: 46% (4d5h)` 처럼
   **이름 · 퍼센트 · 남은 시간** 텍스트다.
   > **사용자 결정 (2026-09-15):** *"게이지는 컨텍스트 뿐이었는데 limit 에 추가한건
   > 좋은거같아 진행해."* — `FR-M11-19`(주기마다 게이지)를 **유지한다.** `D-M11-3` 의
   > *"편의성은 더하는 것이지 대신하는 것이 아니다"* 에 해당하는 첫 사례다. 원본이
   > 글로 말하는 것을 **글과 게이지 둘 다**로 보인다 — 원본의 정보를 지우지 않는다
3. 저장소는 **`📁️ 폴더 (브랜치*)`** — `*` 는 더러움 표시다 (M11-B32·B33)
4. **현재 작업**이 `» note.md 분석` 으로 선다 — 우리 GUI 에 없는 자리다
5. **현재 도구**가 `⚙️ Bash(ls -a && echo '---' && ca…) (4 done)` — 인자를 잘라 싣고
   **누적 완료 수**를 괄호에 단다
6. **diff 누적**이 `+5 -1` 로 선다
7. **마지막 프롬프트**가 `💬️ 16:48 <본문>` 으로 하단에 남는다
8. 비용은 **세 자리**다 — 턴 비용(`$0.42`) · 시간당 추정(`→ ~$7.03/h`) · 오늘(`$636.76`)

> 이 줄은 사용자의 `claude-dashboard` statusline 이다. `FR-M9-39` 가 *"참조는 사용자
> 화면의 statusline"* 이라 적은 그것이며, **우리 대시보드가 옮기려던 원본**이다.

#### (2) 응답과 도구 — `⏺` 와 `⎿`

    ⏺ Bash(sed -i '' 's/world/WORLD/g' sample.txt && cat sample.txt)
     ⎿ hello
       WORLD
       third line
     ⎿ Updated sample.txt (+1 -1)
     1 hello
     2 -world
     2 +WORLD
     3 third line
     ⎿ (what this command changed; a convenience view, not a review or audit of the command)
     ⎿ Allowed by auto mode classifier

    ⏺ sample.txt:2의 world → WORLD로 변경 완료.

- **`⏺` 가 블록의 머리**다 — 도구 호출이든 에이전트의 말이든 같은 표식이다
- **`⎿` 가 결과이고 여러 개가 이어진다** — 출력 · diff · 주석 · 승인 경로가 **각각 한 줄**
- **diff 는 도구 결과 안에 있다** (M11-B36 의 답) — 별도 창이 아니라 그 자리다.
  `Updated <파일> (+n -m)` 머리에 **줄번호와 `±`** 가 붙는다
- 승인 경로를 **글로 말한다** — `Allowed by auto mode classifier`

#### (3) 접힘은 **의미 요약**이다

    Searched for 1 pattern (ctrl+o to expand)

앞뒤 몇 줄이 아니라 **무엇을 했는지 한 문장**이고, 펼치는 **키를 함께 적는다**.
`FR-M11-27` 이 정한 *"앞 2줄·뒤 2줄"* 은 **원본과 다르다** — 사용자 결정(§2.6b)이
있었으나 `D-M11-3` 이 그 위에 서므로 **다시 물었고, 원본 쪽으로 왔다** (`D-M11-5`).

#### (4) 추론 · 진행 · 마침

    ✢ Tinkering… 60          ← 진행 중: 스피너 · 동사 · 누적 토큰
    thought for 2s            ← 추론을 **시간으로** 말한다 (M11-B26)
    ✻ Brewed for 14s · done 4:48 PM   ← 턴 끝: 소요 시간 · 시각

동사는 매번 바뀐다 (`Baked`·`Brewed`·`Stewing`·`Tinkering`).

#### (5) 큐잉 — **쌓이고, 보이고, 위 화살표로 꺼낸다**

턴이 도는 중에 입력하고 엔터를 누르면 그 프롬프트가 **큐에 쌓였다가** 앞 턴이 끝난 뒤
처리된다. **쌓인 것은 화면에 보인다** (실측 — 둘을 연달아 넣었다):

    ❯ 이번엔 1부터 300까지 3의 배수를 전부 나열해줘      ← 진행 중인 프롬프트
    ✶ Tempering… (38s · ↓ 1.4k tokens)
     ⎿ Tip: Use /permissions to pre-approve and pre-deny bash, edit, and MCP tools
    ❯ 큐테스트A                                           ← 큐 1
    ❯ 큐테스트B                                           ← 큐 2
    ──────────────────────────────────────────
    ❯ Press up to edit queued messages                    ← 입력창 자리의 안내
    ──────────────────────────────────────────

**읽어야 할 것 넷**:

1. 대기 중인 프롬프트가 **`❯ <본문>`** 으로 입력창 **위에** 줄줄이 선다 — 무엇이
   기다리는지 항상 보인다
2. 입력창 자리의 안내가 **`Press up to edit queued messages`** 로 바뀐다 —
   **취소·수정의 손은 위 화살표**다 (M11-B35 의 답: 별도 버튼이 아니다)
3. 진행 표시가 **`✶ 동사… (경과 · ↓ 받은 토큰)`** 으로 길어진다
4. 팁이 **`⎿ Tip: …`** 한 줄로 끼어든다 — 도구 결과와 같은 표식이다

**그리고 `Esc` 가 큐를 푼다** (사용자 실측 2026-09-15):

> *"queue 에 프롬프트가 가있는 상황에서 esc 누르면 현재 동작 취소되고 큐가 한번에 들어가."*

    턴이 돌고 + 큐에 A·B 가 쌓임  ──[Esc]──▶  도는 턴이 **중단**되고
                                              A·B 가 **한 번에** 한 프롬프트로 들어간다

**이것이 취소의 본체다.** `Press up to edit queued messages` 는 **고쳐 쓰는** 손이고,
`Esc` 는 **지금 것을 끊고 쌓인 것을 즉시 보내는** 손이다 — 둘은 다른 일이며 GUI 는
둘 다 없다. 지금 GUI 의 `Esc` 는 `interrupt()` 하나뿐이고 큐라는 개념이 아예 없다.

**GUI 는 이 중 아무것도 하지 않는다** — M11-B27·B35·B15 가 한 자리다.

#### (6) 이미지

    Image in clipboard · ctrl+v to paste

붙여넣기이며, 딸려간 이미지는 프롬프트에 **`[Image #1]`** 로 실린다 (M11-B28).

#### (7) 입력 아래의 힌트

    ⏵⏵ auto mode on (shift+tab to cycle) · ← for agents

권한 모드와 그 **순환 키**를 항상 적는다.

#### (8) 마크다운

표를 요청하자 **박스 드로잉으로 그렸다** (`┌───┬───┐`). 원본은 md 를 **렌더한다**
(M11-B21) — 줄글로 두지 않는다.

#### (9) 질문·선택지 UI — **자유 입력은 목록의 한 항목이다** (M11-B29)

원본 TUI 에 `AskUserQuestion` 을 띄워 쟀다 (2026-09-15):

    ☐ 저녁 메뉴
    저녁 메뉴는?
    ❯ 1. 김치찌개   얼큰한 한식
      2. 파스타     양식
      3. Type something.
      ────────────────────────────
      4. Chat about this

    Enter to select · ↑/↓ to navigate · Esc to cancel

**읽어야 할 것 셋**:

1. **자유 입력은 별도 칸이 아니다** — `3. Type something.` 으로 **선택지와 같은
   목록의 한 항목**이다. 고르는 손과 적는 손이 하나다
2. 그 아래 **구분선 뒤에 `4. Chat about this`** 가 또 하나 선다 — 답하지 않고 대화로
   돌아가는 길이며, 우리 모달의 닫기와 같은 자리다
3. 머리는 `☐ <header>` 이고 그 아래가 질문 본문이다. 선택지는 `label` 뒤에 여백을
   두고 `description` 을 단다

#### 아직 재지 않은 것 — **없다**

`M11-B22`(잘림 규칙)와 `M11-B29`(질문 UI)가 §2.11 과 위 (9) 에서 닫혔다.

**접은 것**:

- **`ctrl+o` 로 펼친 화면** — 재지 않기로 했다 (사용자 판단 2026-09-15: *"ctrl + o 는
  이미 우리쪽에서 접기로 되어있으므로 괜찮다"*). 정확히는 그 **키**가 우리 쪽에 있는
  것이 아니라 **펼치는 수단**이 이미 있다 — 도구 카드의 머리를 누른다 (`FR-M11-4`).
  옮겨야 하는 것은 **접힌 채로 무엇인지 말하는 한 줄**이지 키 조합이 아니다
- **큐가 쌓여 있는 동안의 화면** — 위 (5) 에서 **쟀다**

### 2.11 프로토콜 실측 — **화면을 고치기 전에 재료를 쟀다** (2026-09-15)

§2.10 이 *무엇을 그릴 것인가*를 쟀다면 여기는 *그릴 재료가 오는가*다. 남은 접수 여섯이
전부 그 물음에 걸려 있었고, **넷의 답이 예상과 달랐다.**

손은 어댑터가 실제로 쓰는 기동줄 그대로다 (`claudeProtoLaunch`):

    claude -p --output-format stream-json --input-format stream-json \
           --include-partial-messages --verbose --permission-mode bypassPermissions

#### (1) 추론 — **claude 는 내용을 주지 않는다** (M11-B26)

    {"type":"thinking_delta","thinking":"","estimated_tokens":50}
    {"type":"system","subtype":"thinking_tokens","estimated_tokens":250,"estimated_tokens_delta":100}
    assistant 의 content:  [{"type":"thinking","thinking":"","signature":"CAIStw0K…"}]

`thinking_delta` 가 **여덟 번** 왔고 `thinking` 은 **매번 빈 문자열**이다. 스냅샷의
`thinking` 블록도 비어 있고 `signature` 만 실린다. 오는 것은 **토큰 수**뿐이다.

**이것이 원본이 `thought for 2s` 로 시간만 말하는 이유다** (§2.10 (4)) — TUI 가 접어
둔 것이 아니라 **줄 내용이 없다.** `codex`·`omp` 는 다르다 (`codex_decode.go:217` ·
`omp_decode.go:226` 이 실제 텍스트를 싣는다).

**그리고 지금 GUI 는 그 빈 것조차 지운다**: `_message()` 가 live 의 자식을 전부 지우고
스냅샷으로 다시 그리는데, 스냅샷의 thinking 이 비어 있어 `b.thinking` 갈래를
건너뛴다 — `thinking_delta` 로 세운 칸이 **스냅샷이 올 때마다 사라진다.**

#### (2) 응답의 경계 — **`assistant` 프레임 하나가 블록 하나다** (M11-B22)

한 턴의 프레임 순서다 (실측, 도구 둘 + 마지막 말):

    message_start
    content_block_start(thinking) → thinking_delta×7 → signature_delta → assistant[thinking] → content_block_stop
    content_block_start(tool_use) → input_json_delta×17 → assistant[tool_use] → content_block_stop
    message_delta → message_stop
    … (턴 셋이 같은 모양으로 반복) …
    content_block_start(text) → text_delta×151 → assistant[text] → content_block_stop

`assistant` 프레임은 **블록이 끝날 때마다** 오고, `content` 배열의 길이는 **언제나 1**
이다. 즉 **프로토콜이 이미 경계를 준다** — 접수한 *"실제 출력처럼 잘 잘려서 나뉘어
나오면 좋을꺼같다"* 의 답이 여기 있고, 원본이 `⏺` 를 찍는 자리가 정확히 이 경계다.

**우리는 그 경계를 버리고 있다**: `_message()` 가 `this._live` 하나에 턴 전체를
몰아넣고, 매 프레임마다 그 안을 지우고 다시 그린다.

#### (3) 편집 결과 — **diff 는 결과가 아니라 입력에서 온다** (M11-B36)

    tool_use:    {"name":"Edit","input":{"file_path":"…/sample.txt",
                  "old_string":"world","new_string":"WORLD","replace_all":false}}
    tool_result: "The file …/sample.txt has been updated successfully.
                  (file state is current in your context — no need to Read it back)"

**결과에는 diff 가 없다.** §2.10 (2) 가 본 `⎿ Updated sample.txt (+1 -1)` 과 줄번호
붙은 `-world`/`+WORLD` 는 **TUI 가 도구 입력에서 스스로 만든 것**이다.

그러므로 우리도 입력에서 만든다. **줄번호는 만들 수 없다** — 그것은 파일 내용을 알아야
하는 값이고 프로토콜은 주지 않는다. 없는 것을 지어내지 않는다 (FR-CBG-5).

#### (4) 이미지 — **받는다** (M11-B28)

`user` 프레임의 `content` 를 **배열**로 보내면 `image` 블록을 받는다 (실측: 8×8 빨강
PNG 를 보내고 *"빨강"* 이라는 답을 받았다):

    {"type":"user","message":{"role":"user","content":[
      {"type":"image","source":{"type":"base64","media_type":"image/png","data":"iVBOR…"}},
      {"type":"text","text":"이 이미지는 무슨 색인가?"}]}}

`claudePrompt` 는 지금 `content` 를 **문자열로만** 보낸다 — 막힌 것은 프로토콜이
아니라 그 한 줄이다.

#### (5) `/model`·`/config` — **막히지 않았다. 답이 텍스트일 뿐이다** (M11-B11)

    /model  → "Current model: `Opus 5 (1M context) (default)` (effort: high)
               Usage: /model <name>. Available: sonnet, opus, haiku, fable, …"
    /config → "Usage: /config key=value [key=value ...]
                 autoCompact=true|false
                 editor=normal|vim
                 permissionMode=default|plan|acceptEdits|auto|dontAsk
                 …  (키 서른여덟)"

**둘 다 정상 응답한다.** 그리고 `init` 프레임이 **TUI 전용 명령을 따로 말한다**:

    "terminal_slash_commands": ["doctor","color","reload-plugins"]

`/model`·`/config` 는 **그 목록에 없다.** 접수한 *"사용이 불가"* 는 명령이 막혔다는
뜻이 아니라 — 원본 TUI 에서 그 둘은 **고르는 화면**을 띄우는데 여기서는 **사용법
텍스트만** 오고, 고를 자리가 없다는 뜻이다. 옮겨야 하는 것은 그 화면이다.

#### (6) 전사본의 하네스 블록 — **여섯 종이고 전부 독립 항목이다** (M11-B23)

사용자의 실제 전사본 여덟 벌(최대 2448줄)의 `user` 항목을 전수로 훑었다:

| 하네스가 끼운 것 | 건수 | 모양 |
|---|---|---|
| `<task-notification>` | 33 | 안에 `<task-id>`·`<tool-use-id>`·`<output-file>`·`<summary>`·`<status>`·`<note>` |
| `<command-name>` | 7 | 뒤에 `<command-message>`·`<command-args>` 가 같은 항목에 붙는다 |
| `<local-command-caveat>` | 5 | 한 항목에 이 태그 하나뿐 |
| `<local-command-stdout>` | 3 | 명령의 출력 |
| `[Request interrupted by user]` | 3 | 대괄호 한 줄 |
| `[Request interrupted by user for tool use]` | 5 | 같은 부류 |

**결정적인 것은 "섞이지 않는다" 이다.** 여섯 전부 **자기 항목을 통째로** 차지하며,
사용자의 진짜 말과 같은 항목에 들어간 경우가 **한 건도 없다.** 그래서 판정은 항목의
**첫 토큰**으로 충분하고, 본문을 잘라 내는 위험한 손을 쓰지 않아도 된다.

**거르지 않는 것 하나를 적어 둔다** — 슬래시 명령이 주입하는 **스킬 본문**
(`Base directory for this skill: …` 으로 시작하는 항목)은 하네스의 것이지만 그 **끝에
사용자의 요청**(`ARGUMENTS:` · `## User Request`)이 붙는다. 통째로 지우면 사용자의 말을
함께 잃으므로 **갭으로 남긴다** (§7).

#### 실측 — interrupt 가 닿지 않는 자리 셋 (M11-B41·B42)

**재고 나서 갈래가 갈렸다** (2026-09-15, 네 경로를 계측):

| 경로 | interrupt 요청 | 결과 |
|---|---|---|
| ① 입력창에 포커스 + `Esc` | **1건** | 턴이 끊긴다 — **된다** |
| ② **대화를 클릭한 뒤** `Esc` | **0건** | 상태 `working` 그대로 |
| ③ 모달이 열린 채 `Esc` | **0건** | **모달만 닫힌다.** 상태 `waiting` |
| ④ 모달을 닫고 다시 `Esc` | 1건 | **상태는 여전히 `waiting` · 열린 요청 1** |

**②가 B42 다.** `Esc` 핸들러가 `this.ta`(textarea) **하나에만** 걸려 있다. 도구가 도는
동안 화면을 보려 대화를 클릭하거나 스크롤하면 포커스가 입력창을 떠나고, 그때부터 키가
닿지 않는다. 사용자가 *"특정 동작을 하는중에"* 라고 느낀 것이 이 자리다 — 동작의 종류가
아니라 **그 사이에 화면을 만졌는가**가 갈랐다.

**④가 B41 의 함정이다.** interrupt 를 보내도 **열린 승인 요청은 닫히지 않는다.** claude
프로토콜에는 *"열린 요청을 답 없이 닫는 프레임"* 이 없다 — `claudeProto.Cancel` 이 `nil`
인 이유이며 그 주석이 이미 그렇게 적어 두었다(*"stdin EOF 가 곧 종료다"*).

> **그러므로 "닫으면 끊는다" 는 거절과 함께여야 성립한다.** 사용자 결정은 *"턴을 끊는다
> (interrupt)"* 였고(2026-09-15), 그 결정이 이루려는 것은 **무한정 기다리지 않는 것**이다.
> interrupt 만 보내면 ④ 그대로 열린 요청이 남아 그 의도가 이뤄지지 않는다. 결정을 바꾸는
> 것이 아니라 **성립시키는 유일한 경로**이므로 거절을 먼저 보내고 이어 끊는다.

### 2.13 실측 — 서브에이전트와 백그라운드 (M11-B49 · B50 · 2026-09-15)

접수: *"서브에이전트들이나 백그라운드 작업같은건 어떻게 해야할까"* · *"모아볼 수 있게"*.
**재고 답했다** — 실제 claude 에 `Agent` 도구와 `run_in_background` 를 함께 시켰다.

#### (1) 서브에이전트는 **같은 스트림**으로 온다 — 가르는 것은 `parent_tool_use_id`

    assistant  parent=null   → tool_use{name:"Agent", input:{description,subagent_type,prompt}}
    user       parent=toolu_01JGw…  → 서브에이전트가 **받은** 프롬프트
    assistant  parent=toolu_01JGw…  → 서브에이전트의 tool_use{name:"Bash"}
    user       parent=toolu_01JGw…  → 그 도구의 결과
    user       parent=null   → 부모가 받는 tool_result (Agent 의 결과)

**우리 어댑터는 그 필드를 읽지도 않았다.** 그러면 서브에이전트가 **받은 프롬프트**가
`EvUser` 가 되어 *사용자가 친 말*로 서고, 그 도구가 본 대화의 카드로 선다 —
`FR-M11-25`(자기가 하지 않은 말을 자기 기록에서 읽는다)와 **같은 부류의 결함**이다.

#### (2) 백그라운드는 **평범한 도구**다 — 진행을 알려 주지 않는다

    tool_use    {"name":"Bash","input":{"command":"sleep 2; echo BG","run_in_background":true}}
    tool_result "Command running in background with ID: bxgfstiye.
                 Output is being written to: /private/tmp/…/tasks/bxgfstiye.output.
                 You will be notified when it completes."

**구조가 아니라 글이다.** ID 와 경로가 문장 안에 있고, 완료 통지는 claude 내부로 간다.
그러므로 우리가 **지어내지 않고** 말할 수 있는 것은 *백그라운드로 돌렸다* 는 사실 하나이며,
그것은 **입력에 이미 있다** (`run_in_background:true`).

#### (3) 원본의 화면 — 이미 같은 것을 한다

터미널에서 실제 claude 에 둘을 시키고 읽은 화면이다:

    ⏵⏵ bypass permissions on · 1 shell · ← for agents

    1 teammate started
     ⏺ main
     ◯ read-a-txt   /private/tmp/…/a.txt 파일을 읽고 내용을 그대로 ...   4s · ↑ 18.0k tokens

- 백그라운드 셸의 **수**를 하단에 적는다 (`1 shell`)
- `← for agents` 가 모아보는 화면의 손이다
- 목록은 `⏺ main` + `◯ <이름>` 이고 **프롬프트 요약 · 소요 시간 · 토큰**이 붙는다

> **사용자 결정 (2026-09-15):** *"모양을 또같이 할 필요는 없다."* 그러므로 이 절은
> **무엇을 보여야 하는가**의 근거이지 화면의 청사진이 아니다. 서브에이전트의 진행은
> 부모 도구 카드 안에 모으고(사용자 결정), 백그라운드는 그 사실을 머리에 적는다.

## 5. 설계 결정

**D-M11-3 — 진실은 실제 에이전트의 동작이다. GUI 는 그것을 옮긴 것이다.** (사용자 지시 2026-09-15)

> *"그니까 결론은 모든 동작을 기존 에이전트와 동일하게 하라는거야. 하나도 안되어있거든.
> 그러면서 편의성으로 gui 를 만들어둔거야."*
> *"실제 에이전트의 사용 패턴, 동작을 그대로 옮겨적으면 돼."*

**이 결정이 세 번째 물결 전체의 상위에 선다.** B18~B36 을 접수 열아홉으로 읽으면 각각
다른 요구로 보이지만, 그 전부가 한 문장이다 — **원본에 있는데 여기 없다.**

| 접수 | 원본(TUI)에 있는 것 |
|---|---|
| B18 구분 · B21 md · B22 분할 | 출력의 **모양** — 원본은 md 를 그리고 블록을 나눈다 |
| B25 접기 요약 · B26 추론 | 도구·추론의 **접힘과 요약** |
| B27 · B35 · B15 큐잉 | 프롬프트를 **쌓고 취소**한다 |
| B28 이미지 · B29 자유 답 · B36 diff | 원본이 **이미 하는 일** |
| B24 스크롤 · B34 선택 | 읽는 자리의 **기본 성질** |

**그러므로 작업의 순서가 바뀐다.**

  종전: 접수마다 갈래를 세우고 각자 고친다
  새로: **원본을 재고**, 그 동작을 명세로 옮기고, 그대로 구현한다
  이유: 접수는 사용자가 **차이를 느낀 지점**이지 요구의 전부가 아니다. 하나씩 고치면
        접수되지 않은 차이는 영영 남고, **같은 자리를 여러 번** 고치게 된다

**재는 손은 이미 있다** (§3): 터미널 탭에서 도는 실제 `claude` 를
`dmctl read-output --at <탭> --bytes 400000 | cat -v` 로 읽는다. 그 화면이 명세다.

**"편의성" 은 더하는 것이지 대신하는 것이 아니다.** GUI 가 원본보다 나은 자리를 둘 수
있으나(예: 스크롤 복원), 그것은 **원본의 동작을 갖춘 뒤**의 덧붙임이다.

**D-M11-7 — 쓰면서 나온 접수는 앞선 결정을 이긴다.** (M11-B41 · B43, 사용자 결정 2026-09-15)

네 번째 물결이 **앞선 결정 둘을 뒤집었다.**

| 뒤집힌 것 | 그때의 근거 | 실제로 쓰니 |
|---|---|---|
| `FR-APS-6` — *"Esc 는 답이 아니다, 요청은 열린 채 남는다"* | 실수로 닫은 것을 **되돌릴 수 있어야 한다** | **되돌릴 길보다 멈출 길이 급했다** (*"무한정 기다림"*) |
| `D-M9-20` — *"터미널 탭은 남는다"* | 올린 뒤에도 셸로 **돌아갈 수 있어야 한다** | 같은 세션이 **두 자리**에 보이고 하나는 이미 끝난 셸이다 |

**둘 다 그때는 옳은 추론이었다.** 바뀐 것은 근거가 아니라 **무게**다 — 어느 쪽이 더
자주 일어나는지는 써 봐야 안다.

그러므로 이 저장소에서 *"앞서 정했다"* 는 그 자체로 논거가 아니다. **다만 뒤집을 때는
뒤집었다고 적는다** — 그러지 않으면 옛 조항을 읽는 다음 사람이 지금 코드를 결함으로
읽는다. 계약을 재던 검사도 같은 변경에서 고친다 (이 물결에서만 여덟 건).

**D-M11-4 — 주지 않는 값은 옮기지 않는다. 대신 주는 값을 옮긴다.** (FR-M11-28 · FR-M11-37)

실측이 두 자리에서 같은 모양을 냈다 — **원본이 보이는 것을 프로토콜이 주지 않는다.**
추론 내용은 아예 없고(§2.11 (1)), diff 의 줄번호는 파일을 들고 있어야 나온다
(§2.11 (3)). 둘 다 *"원본에 있으니 옮긴다"* 로 밀면 **지어낸 값**이 화면에 선다.

  고른 것: 주는 값으로 **같은 뜻**을 말한다 — 추론은 `2.4s · 250 토큰`, diff 는
           줄번호 없는 `±`
  고르지 않은 것: ① 지어내기(추론 내용을 요약으로 대신, 줄번호를 추정) ② 아예 빼기
  이유: `D-M11-3`(원본이 진실)과 `FR-CBG-5`(모른다 ≠ 값이다)가 부딪히는 자리이며,
        **뒤쪽이 이긴다.** 원본을 옮기는 것은 *모양*이지 *없는 데이터*가 아니다

**사용자 결정이 이 경계를 확인했다** (2026-09-15): 추론은 *"오면 내용, 없으면 시간·토큰"*
이다 — 내용을 주는 어댑터(`codex`·`omp`)의 값을 버리지도, 주지 않는 어댑터에서 빈 칸을
세우지도 않는다.

**D-M11-5 — 접힌 머리는 한 문장이다.** (FR-M11-27 개정, 사용자 결정 2026-09-15)

앞선 결정(*"넘으면 앞뒤 2줄"*)을 **원본 쪽으로 되돌렸다.** §2.10 (3) 이 남긴 물음의
답이며, 되돌린 근거는 앞뒤 두 줄이 접힌 머리를 **네 줄로 만들어** 접은 뜻을 스스로
없앤다는 것이다. 짧은 출력이 그대로 보이는 갈래는 원본도 같으므로 **바뀌지 않는다.**

**D-M11-6 — 큐는 화면의 것이다.** (FR-M11-29)

서버(`agentsess`)에 큐를 둘 수도 있었다. 고르지 않은 이유는 원본의 큐도 **TUI 의
것**이고, 서버에 두면 **보는 브라우저마다 다른 큐가 서거나 남의 큐가 내 화면에 선다** —
`FR-AGT-12`(소유자가 아닌 브라우저는 보기만 한다)가 이미 그은 선이다. 프롬프트는 나갈
때 비로소 서버의 것이 된다.

**D-M11-1 — 다시 붙이지 않고 좌표만 버린다.** (FR-M11-1)
소켓이 없을 때 재접속을 **새로 걸 수도** 있었다. 고르지 않은 이유는 그 자리에 이미
재접속이 돌고 있기 때문이다 — `_scheduleReconnect` 가 백오프로 깨어나고 있고, 거기에
하나를 더 걸면 `RECONNECT_STORM` 이 고친 두 벌 재접속이 되살아난다(`reconnectNow` 가
옛 소켓의 콜백을 끊는 이유가 그것이다). 좌표는 **다음에 붙는 쪽이 읽는 값**이므로,
버려 두기만 하면 누가 붙든 전량이 된다.

**D-M11-2 — 재현이 아니라 무력화로 갈래를 갈랐다.** (§2.4b)
여섯 배치가 전부 초록이었으므로 "없다" 로 접을 수도 있었다. 대신 **고침 하나만
무력화**해(`M10_PROGRESS` §3-3 의 프로브와 같은 손) 잔재가 나는지 보았고, 났다.
그 뒤에야 그 무력화가 **자연 경로로 닿는지**(§2.4c)를 물었다 — 순서가 반대였으면
서버 재시작이라는 조건을 떠올리지 못했다.

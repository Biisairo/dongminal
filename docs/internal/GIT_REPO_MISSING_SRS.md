## 1. 서론 (Introduction)

### 1.1 목적 (Purpose)

접수한 말은 **"갱신 실패하면 사실을 알리고 사용자가 해당 내용을 알고 핀을 직접
제거할 수 있게 해야할 것 같아. 사라졌으면 사라진걸 알아야하고 사라진게 아닌데
사라졌다고 표시가 되면 오류를 고쳐야할거니까"** 였다.

이 요구는 두 문장으로 갈린다. 앞은 **알림**이고, 뒤는 **알림이 참임을 판정 가능해야
한다**는 것이다. 조사 결과 두 층이 다 비어 있다.

1. **서버는 소실을 확정하지 못한다.** `core/exec.go:181` 이 프로세스를 시작조차 못한
   실패를 분류 없이 내보내고, `gitErrorCode`(`gitapi/handlers_git.go:56`)가 그것을
   `git_failed`/500 으로 받는다. `classify()`(`core/errors.go:52`)의 사유 목록에
   "작업 디렉터리가 없다"가 없다. 그래서 **폴더 소실 · 권한 오류 · `.git` 손상 ·
   git 프로세스 크래시가 전부 같은 코드**로 도착한다.
2. **클라이언트는 낡은 목록을 그대로 보인다.** `_applyError`(`panel.js:2160`)가
   `git_failed` 를 마지막 폴백(`_staleNote=true; _paint()`)으로 받고 `_status` 를
   지우지 않는다. 사라진 폴더의 파일 목록·브랜치·커밋 영역이 계속 보이고, 붙는 것은
   `갱신 실패` 네 글자뿐이다.

두 번째만 고치면 **오탐 생산기**가 된다. `git_failed` 를 "사라졌습니다"로 표시하는
순간, 권한 오류와 git 크래시까지 소실로 보고된다. 그러면 사용자가 요구한 뒤 문장 —
"사라진 게 아닌데 사라졌다고 표시되면 오류를 고쳐야 한다" — 이 성립하지 않는다.
**표시가 참인지 판정할 수 있으려면 먼저 사유가 갈려 있어야 한다.**

### 1.2 범위 (Scope)

- **범위 안**
  - `core` 의 실패 분류에 소실 사유를 더하는 일 (`errors.go`·`exec.go`)
  - `gitapi` 의 HTTP 사상 (`gitErrorCode`)
  - Git 패널 **7개 탭 전부**의 소실 상태 화면과 그 안의 두 진입점 (핀 제거 · 다시 확인)
  - 소실 확정 시의 폴링 주기
  - **일반 실패(`git_failed` 를 포함한 모든 실패)의 폴링 백오프**
  - 사이드바 핀 행이 보이는 사유 문구
- **범위 밖**
  - 핀의 뜻과 영속(FR-GIT-11·12), 활성 리포의 영속(FR-GIT-29) — 그대로 둔다
  - `not_a_git_repo`(폴더는 있고 `.git` 만 없음)의 기존 동작 — 그대로 둔다
  - `git_timeout`·`git_missing`·`git_canceled` 의 **사유 분류** — 그대로 둔다
    (다만 폴링 백오프는 이들에도 걸린다, FR-RMS-22)
- **하지 않기로 한 것** (근거는 §5)
  - 사라진 워크트리의 자동 prune 이나 자동 핀 제거 (D-RMS-6). 접수한 말이
    **"사용자가 … 직접 제거"** 였으므로 이것만은 범위 밖에 남는다

### 1.3 정의 (Definitions)

| 용어 | 뜻 |
|---|---|
| **소실 (`repo_missing`)** | git 을 실행할 **작업 디렉터리 자체가 없다.** 프로세스가 시작조차 되지 못한 상태이며, git 은 아무 말도 하지 않았다 |
| **저장소 아님 (`not_a_git_repo`)** | 폴더는 있고 git 이 실행됐으나 저장소가 아니다. git 이 stderr 로 그렇게 말했다 |
| **일반 실패 (`git_failed`)** | 위 어느 것으로도 분류되지 않은 실패. **소실의 후보가 아니다** — 여기 남는 것이 곧 "고쳐야 할 오류" 다 |
| **소실 상태** | 활성 리포에 대한 관측이 `repo_missing` 으로 답한 뒤의 패널 상태 |
| **복구** | 소실 상태에서 관측이 다시 성공하는 것. 사용자의 개입 없이 일어난다 |

## 2. 전반 기술 (Overall Description)

### 2.1 현재 동작 — 실측

임시 저장소를 만들어 실행 중인 서버(`:58146`)에 직접 물어 얻은 값이다.

| 상황 | 서버 응답 | HTTP | 클라이언트 처리 |
|---|---|---|---|
| 폴더 자체가 사라짐 | `git_failed`<br>`chdir <path>: no such file or directory` | 500 | 폴백 — 낡은 목록 유지 + `갱신 실패` |
| 폴더는 있고 `.git` 만 삭제 | `not_a_git_repo` | 404 | `_status=null`·`setRepo(null)` — 깔끔히 초기화 |

폴더 소실 쪽의 세부는 이렇다.

- `_status` 를 지우지 않으므로 **사라진 폴더의 마지막 파일 목록이 그대로 보인다.**
- `_stop()` 을 부르지 않고 `repo` 도 그대로라 `_pollOk()` 가 참이다 — status 1초 ·
  signature 0.5초마다 **영구히 500 을 받는다.**
- 사이드바 핀 행은 `.norepo` 로 흐려지고 클릭 리스너가 붙지 않는다. title 은
  `git_failed — <경로>` 다. 배지는 사라진다 — `gitPinnedEntries` 가 `RepoRoot`
  실패 시 `badge:null` 을 싣기 때문이다.
- 서버의 마지막 관측값은 살아 있다 (`store.go:145` 의 `if err == nil` — 실패는
  마지막 관측값을 덮지 않는다). 그래서 폴더가 돌아오면 값이 이어진다.

### 2.2 소실의 판정 근거

Go 는 존재하지 않는 `cmd.Dir` 로 프로세스를 띄울 때 다음을 준다. 확인한 값이다.

```
err        = chdir /definitely/not/here: no such file or directory
type       = *fs.PathError
ErrNotExist= true
PathError  Op="chdir" Path="/definitely/not/here" Err=no such file or directory
```

판정은 **`Op == "chdir"` 로 좁힌다.** `errors.Is(err, fs.ErrNotExist)` 만으로는
git 바이너리가 사라진 경우와 섞일 수 있고, 그것은 이미 `ErrGitMissing` 의 몫이다
(`exec.go:146`).

이 근거는 **stderr 문자열이 아니다.** 기존 `classify()` 가 `not a git repository`
문자열을 보는 것과 성격이 다르다 — 소실은 git 이 아무 말도 하지 않은 실패이므로
읽을 stderr 자체가 없다. 그래서 로케일에 흔들리지 않는다.

### 2.3 제약 (Constraints)

- 소실 판정은 **git 을 실행하지 않는 경로에도 일관되어야 한다.** `signature`
  (`query/signature.go`)는 `GitDirs` 로 gitdir 을 얻는데 그것이 `rev-parse` 를
  지나므로 같은 사유가 나온다.
- `store.Status` 의 실패는 마지막 관측값을 덮지 않는다 — 이 규약을 바꾸지 않는다.
- 다시 그리기 가드(FR-GIT-227)의 근거(`_obsSig`)는 사유가 붙은 화면에서 비워야
  한다. 기존 `_applyError` 가 이미 그렇게 한다.
- 클라이언트 상수는 `constants.js` 한 자리에서만 정의한다 (기존 규약).

## 3. 요구사항 (Requirements)

### 3.1 서버 — 소실의 확정

| ID | 요구사항 |
|---|---|
| **FR-RMS-1** | `core` 는 소실 사유 `ErrRepoMissing`(문자열 `repo_missing`)을 갖는다. |
| **FR-RMS-2** | `execGit` 은 프로세스를 시작하지 못한 실패가 `*fs.PathError` 이고 `Op == "chdir"` 이며 `errors.Is(err, fs.ErrNotExist)` 일 때 `ErrRepoMissing` 으로 감싼다. **stderr 로 판정하지 않는다.** |
| **FR-RMS-3** | `ErrRepoMissing` 은 `kinds` 에 등록된다 — 이미 분류된 오류를 다시 감싸지 않는 판정(`classified`)이 이것을 알아야 한다. |
| **FR-RMS-4** | `gitErrorCode` 는 `ErrRepoMissing` 을 `(404, "repo_missing")` 로 옮긴다. `not_a_git_repo` 와 같은 상태 코드다 — 둘 다 "네가 지목한 것이 거기 없다" 이고, 클라이언트는 상태 코드가 아니라 `error` 필드로 분기한다. |
| **FR-RMS-5** | 위 조건에 들지 않는 실패는 **여전히 `git_failed`** 다. 권한 오류·`.git` 손상·git 크래시를 소실로 승격하지 않는다 — 그것이 오탐을 오탐으로 드러내는 장치다. |

### 3.2 패널 — 소실 상태

| ID | 요구사항 |
|---|---|
| **FR-RMS-6** | `_applyError` 는 `repo_missing` 전용 분기를 갖는다. 소실 상태로 들어가고, `_status` 를 비운다 — **사라진 폴더의 파일 목록을 보이지 않는다.** |
| **FR-RMS-7** | 소실 상태는 **활성 리포를 해제하지 않는다** (`setRepo(null)` 를 부르지 않는다). 사용자가 보던 리포가 무엇인지 잃지 않고, 복구가 자동으로 일어날 수 있어야 한다. `not_a_git_repo` 와 갈리는 지점이다. |
| **FR-RMS-8** | Changes 탭은 소실 안내와 함께 **리포 이름을 실은 머리**를 세운다 — 어느 리포의 이야기인지가 사라지면 안 된다. 브랜치·배지는 싣지 않는다: 그것은 사라진 폴더의 값이라 지금 참인지 알 수 없다. 안내는 넷을 싣는다 — ① 사라졌다는 문장 ② **저장소의 절대경로** ③ 사유 코드(`repo_missing`) ④ 다시 확인 중이라는 사실과 그 주기. |
| **FR-RMS-9** | 안내에는 진입점 둘이 있다 — **`핀 제거`** 와 **`다시 확인`**. `핀 제거` 는 기존 `_gitUnpin` 을 지난다(새 경로를 만들지 않는다). `다시 확인` 은 기존 `refresh()` 를 지난다. |
| **FR-RMS-10** | `핀 제거` 는 **핀되지 않은 리포에서는 보이지 않는다.** 없는 핀을 지우는 버튼은 거짓말이다. 핀이 바깥에서 바뀌면 버튼이 따라온다 (`notifyPins`, FR-RPT-8). **그 절반은 화면으로 만들 수 없게 됐다** — REPO_TAB_UNIFY_SRS D-RTU-28: Repo 창이 서는 근거가 `editors.list` 이고 그 목록에 든 저장소 루트는 `LinkEditorAdd` 가 핀까지 만든다 (FR-EDT-33). 즉 "창은 있는데 핀은 없는 저장소" 라는 상태가 없다. 규칙은 남고 e2e 만 그 절반을 놓았다 (`git-repo-missing` M5). |
| **FR-RMS-10a** | `핀 제거` 뒤에는 활성 리포를 놓는다(`setRepo(null)`). 사라진 폴더의 핀까지 없앤 사용자에게 그 화면을 계속 보일 이유가 없고, 돌아갈 곳은 "리포를 선택하세요" 다. |
| **FR-RMS-11** | 복구되면 안내가 사라지고 목록이 돌아온다. 사용자의 개입을 요구하지 않는다. |
| **FR-RMS-12** | 경로·사유는 `textContent` 로만 넣는다. 경로는 사용자의 파일 이름이며 마크업으로 넣으면 화면을 고칠 수 있다 (기존 `gitHunkSpan` 과 같은 규약). |

### 3.6 실패 시 폴링 백오프

| ID | 요구사항 |
|---|---|
| **FR-RMS-22** | 연속 실패는 폴링 주기를 늘린다. 대상은 **관측이 성공하지 못한 모든 경우** — 네트워크 오류·`git_failed`·`git_timeout` 이 같다. |
| **FR-RMS-23** | 유효 주기는 `min(기준 × 2^연속실패수, GIT_FAIL_BACKOFF_MAX_MS)` 다. 기준은 사용자 설정값(`gitStatusInterval`·`gitSignatureInterval`)이고 상한은 30 000ms 다. |
| **FR-RMS-24** | 관측이 성공하면 연속 실패수가 0 이 되고 주기가 **즉시** 기준으로 돌아온다. |
| **FR-RMS-25** | 기준 0(계층 끔, FR-GIT-23)은 백오프의 대상이 아니다 — 0 은 0 으로 남는다. 소실 상태(FR-RMS-15)와 같은 규약이다. |
| **FR-RMS-26** | 소실이 확정되면 백오프 대신 FR-RMS-13 의 고정 주기를 쓴다. 소실은 "일시적일지 모른다" 가 아니라 확정된 사실이므로 점증할 이유가 없다. |
| **FR-RMS-27** | 사용자의 계기(`refresh()`·`signal()`)는 백오프를 기다리지 않는다. 그 둘은 주기를 지나지 않고 `collect()` 를 직접 부르므로 구조가 이미 그러하다 — 이 요구는 회귀 확인이다. |
| **FR-RMS-28** | 주기 재평가는 **관측 안에서 부를 수 있어야 한다.** `_reschedule()` 은 "참이 되면 즉시 1회 수집"(FR-GIT-22)을 계약으로 가지므로, 관측 결과로 주기만 바꾸는 자리는 **즉시 수집을 하지 않는 별도 진입점**을 쓴다 — 그러지 않으면 관측이 관측을 부른다. |

### 4.1 구현하며 드러난 사실

- **사라진 뒤에는 핀할 수 없다.** `/api/git/repos/pin` 이 경로를 검증하므로
  (FR-GIT-12), 폴더가 없어진 다음의 핀은 거부된다. 따라서 `핀 제거` 가 서는 경우는
  **살아 있을 때 핀해 둔 리포가 나중에 사라진 것** 하나뿐이다 — 실제 사용 흐름과
  같다. V-RMS-6 은 그 순서로 검증한다.
- **복구 검증은 30초를 실제로 기다린다** (V-RMS-8). 주기를 줄여 흉내 내면
  "사용자의 개입 없이 돌아온다" 를 검증한 것이 아니게 되므로, 테스트의 시간 상한을
  늘리는 쪽을 택했다.

## 5. 결정 (Decisions)

| ID | 결정 | 근거 |
|---|---|---|
| **D-RMS-1** | 소실을 stderr 가 아니라 `chdir`/ENOENT 로 판정한다 | 소실은 git 이 아무 말도 하지 않은 실패다. 읽을 stderr 가 없고, 있는 근거가 더 정확하며 로케일에 흔들리지 않는다 |
| **D-RMS-2** | 소실은 **작업 디렉터리에 한한다** | 넓히면 오탐이 소실로 위장한다. 사용자가 요구한 "사라진 게 아닌데 사라졌다고 표시되면 오류" 판정이 성립하려면 `git_failed` 가 좁게 남아야 한다 |
| **D-RMS-3** | 낡은 파일 목록을 지운다 | **사용자 결정.** 목록이 살아 있으면 정상으로 오독된다 — 접수한 말의 "사라졌으면 사라진 걸 알아야" 가 이것이다 |
| **D-RMS-4** | 폴링을 멈추지 않고 30초로 낮춘다 | **사용자 결정.** 워크트리를 지웠다 다시 만드는 경우를 사용자가 손으로 되돌리지 않아도 된다. 매초 실패하던 요청은 1/30 로 준다 |
| **D-RMS-5** | 활성 리포를 해제하지 않는다 | 해제하면 자동 복구가 불가능하고(무엇을 다시 볼지 잃는다), 사용자가 보던 자리도 잃는다. `not_a_git_repo` 가 해제하는 것은 그쪽이 **폴더가 살아 있어 사용자가 즉시 다른 선택을 할 수 있는** 상태이기 때문이다 |
| **D-RMS-6** | 핀을 자동으로 지우지 않는다 | 기존 규약("저장소가 아니게 된 핀은 목록에서 지우지 않고 `isRepo:false` 로 보인다 — 지울지는 사용자가 정한다", `handlers_git.go:141`)과 접수한 말("사용자가 … 직접 제거") 이 같은 방향이다 |
| **D-RMS-7** | **7개 탭 전부**에 소실을 보인다 (초안의 비목표를 뒤집는다) | **사용자 결정.** 초안이 이것을 미룬 근거는 "같은 사실을 여섯 자리에서 관리하게 된다" 였는데, 조사해 보니 그 전제가 틀렸다 — `_render(view)`(`panel.js:164`)가 7탭 **단일 디스패치**이므로 분기 한 자리와 블록 함수 하나로 끝난다. 비용이 없으니 미룰 이유도 없다 (FR-RMS-20) |
| **D-RMS-8** | 실패 백오프를 **모든 실패**에 건다 (초안의 비목표를 뒤집는다) | **사용자 결정.** 소실만 고정 주기로 낮추면 `git_timeout`·권한 오류처럼 스스로 낫지 않는 나머지가 그대로 매초 돈다. 사유별로 주기 규칙을 따로 두는 것보다 "성공하지 못한 관측"이라는 한 가지 조건으로 묶는 편이 규칙이 하나다 |
| **D-RMS-9** | 백오프는 지수이되 상한을 둔다 (기준 × 2ⁿ, 30초) | 일시적 실패(네트워크 한 번 튐)는 한두 회차에 회복하므로 점증이 눈에 띄지 않고, 지속 실패는 빠르게 상한에 닿는다. 상한을 소실의 고정 주기와 같은 30초로 맞춰 "가장 느릴 때"가 화면마다 다르지 않게 한다 |
| **D-RMS-10** | 주기 재평가에 즉시 수집을 하지 않는 진입점을 새로 둔다 | `_reschedule()` 의 "참이 되면 즉시 1회 수집"은 FR-GIT-22 의 계약이고 기존 검증(P3)이 그것을 딛는다. 관측 안에서 그대로 부르면 관측이 관측을 부른다 (FR-RMS-28) |

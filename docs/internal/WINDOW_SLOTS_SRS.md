# SRS: 창 슬롯 — 두 창을 한 화면에 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 한 줄이다.

> **window·git·editor 를 동시에 보려고 크롬 창을 두 개 켜거나 크롬의 스플릿
> 윈도우를 쓰고 있다. 이걸 내부에서 하고 싶다.**

지금 콘텐츠 영역에는 `activeWindow` **하나만** 그려진다 (`web/js/ui/renderer.js:96`
`_rLayout`). 터미널끼리는 창 안의 분할로 나란히 볼 수 있지만, Git 창과 Editor 창은
`WINDOW_TYPE_GIT`·`WINDOW_TYPE_EDITOR` 라는 **별개의 창**이므로 (`constants.js:114`·
`:129`) 같은 화면에 올 방법이 없다. 그래서 사용자는 브라우저 창 두 개로 그 일을
대신하고 있다.

본 SRS 는 콘텐츠 영역을 **슬롯** 둘로 나누고, 각 슬롯이 창 하나를 통째로 그리게
한다. 브라우저 창 두 개가 하던 일을 브라우저 창 하나 안에서 한다.

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **S** 슬롯 모델 | 슬롯의 정의·상태·영속. `activeWindow` 와의 관계 |
| **I** 신원 | 슬롯마다의 클라이언트 신원과 창 소유권. 서버 무변경의 근거 |
| **T** 도구 | 같은 도구를 두 슬롯에 그리기 위한 인스턴스 다중화 |
| **R** 렌더링 | `#area` 의 슬롯 분할, 비율 조절, 사이드바 활성 표시 |
| **N** 이동 | `paneNavigate` 경계 넘침으로 슬롯을 오간다 |
| **U** 진입점 | 토프바 토글·단축키·슬롯 초기값 |
| **M** 모바일 | 모바일에서의 축약 |
| **X** 인터페이스 | DOM·App 표면·저장소 키의 이름 계약 |
| **D** 방향 | 슬롯을 가로로 놓을지 세로로 놓을지. 설정 항목 |

**미포함:** §6 비목표. 특히 **창 타입의 불변식은 한 줄도 바뀌지 않는다** — Git 창은
여전히 탭을 더할 수 없고 (`app-layout.js:226`), Editor 창에는 여전히 편집기 탭만
산다 (`:229`). 슬롯은 창을 **담는 그릇**이지 창의 내용을 바꾸지 않는다.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **슬롯 (slot)** | 콘텐츠 영역의 세로 칸 하나. 창 0~1개를 표시한다. 최대 2개 |
| **포커스 슬롯** | 키 입력과 사이드바 클릭이 향하는 슬롯. 항상 정확히 하나 |
| **슬롯 신원 (slot identity)** | 슬롯이 서버에 대해 자신을 밝히는 `clientId`. 슬롯마다 다르다 |
| **경계 넘침 (overflow)** | 창 안에서 더 갈 pane 이 없을 때 pane 이동이 슬롯을 건너뛰는 것 |
| **단일 슬롯 모드** | 슬롯이 1개인 상태. 본 SRS 이전의 동작과 완전히 같다 |
| **슬롯 방향** | 두 슬롯이 놓이는 축. `horizontal`(좌우, 기본)·`vertical`(상하). 창 안 분할과 같은 용어다 (`style.css:138-139`) |

## 2. 현재 상태 (조사로 확정한 사실)

착수 전 조사에서 확인한 것이다. **설계 판단의 근거이므로 추측이 아닌 파일:줄로만
적는다.**

### 2.1 콘텐츠 영역은 창 하나만 그린다

`_rLayout` (`web/js/ui/renderer.js:96`) 은 `this.app._aw()` 가 준 창 **하나**의
`layout` 을 `#area` 에 그린다. 매 렌더마다 이렇게 돈다.

1. 모든 도구 DOM 을 `#area` 직속으로 되돌리고 `vis` 를 뗀다 (`:99-110`)
2. 이전 렌더가 만든 `.sp`·`.pn`·`.ed-win` 을 지운다 (`:111`)
3. 활성 창의 분할 트리를 다시 만들어 붙인다 (`:132`)

**이 구조는 다중 슬롯에 유리하다.** 도구 DOM 은 이미 풀에서 재사용되고 `vis` 로
골라 보여지므로, 붙일 자리를 슬롯으로 나누는 것이 이 루프의 자연스러운 확장이다.

### 2.2 분할 트리 CSS 는 `inset:0` 기반이다

`#area{flex:1;position:relative;overflow:hidden}` (`web/style.css:134`),
`.sp{position:absolute;inset:0}` (`:137`), `.pn{position:absolute;inset:0}` (`:149`).

분할 트리 전체가 **가장 가까운 `position:relative` 조상**을 채우는 구조다. 따라서
`#area` 안에 `position:relative` 인 슬롯 컨테이너를 두면 **기존 트리 CSS 는 한 줄도
바뀌지 않는다.**

### 2.3 한 클라이언트는 한 창만 소유한다 — 이것이 진짜 제약이다

`_focusWindow` (`web/js/core/app-focus.js:102`) 는 창을 클레임하기 전에 **이 클라이언트가
소유한 다른 창을 전부 놓는다.**

```js
// Release other windows this client owns (one client → one window).
for(const sid of Object.keys(this._windowFocusOwner)){
  if(sid!==windowId&&this._windowFocusOwner[sid]===this.clientId){
    delete this._windowFocusOwner[sid];
    changed=true;
  }
}
```

서버도 같은 모양이다 — `owners map[string]string // windowId → clientId`
(`internal/webserver/hub/focus.go:21`).

소유권이 하는 일은 둘이다.

| 결과 | 자리 |
|---|---|
| 소유자만 PTY 크기를 보낸다 | `_resizeCheck` (`app-focus.js:153`) |
| 비소유자에게는 pane 이 흐려진다 | `_applyFocusOverlay` (`:163`), `.pn-dimmed` |

**슬롯 2개를 그냥 만들면 여기에 먼저 걸린다.** 같은 창이든 다른 창이든 상관없이,
`clientId` 가 하나뿐이므로 두 슬롯 중 하나는 소유를 잃고 흐려진다.

그리고 이 규칙은 e2e 로 고정돼 있다 — `TC-XDF-3: 한 Client 는 한 Window 만 소유한다`
(`e2e/focus-owner.spec.ts:76`).

### 2.4 서버는 이미 "여러 클라이언트가 같은 창을 본다"를 지원한다

`hub.Focus` 는 `clientId` 를 키로 SSE 구독과 소유권을 결선한다
(`internal/webserver/httpapi/commands.go:68`, `hub/focus.go:22·28`). 구독이 끊기면
소유권을 해제한다 (FR-XDF-9). 같은 `clientId` 로 구독을 두 개 여는 경우까지 테스트로
정의돼 있다 (`e2e`→`internal/webserver/httpapi/focus_test.go:86`).

즉 **사용자가 지금 크롬 창 두 개로 하고 있는 일은 서버가 이미 온전히 지원하는
구성이다.** 부족한 것은 브라우저 한 개 안에서 그 구성을 만들 방법뿐이다.

### 2.5 도구 인스턴스는 `toolId` 당 하나다

`_mkTool` (`web/js/core/app.js:204`) 은 `tools` Map 에 `toolId` 를 키로
`TerminalTool` 을 하나 만들고, 그 인스턴스가 DOM 하나 (`term-pane.js:14`) 와
WebSocket 하나 (`:8`) 를 소유한다. Map 접근은 코드 전역 30곳이며 대부분
`tools.get(toolId)` 단순 조회다.

`fileEditors` Map (`app.js:7`) 과 `gitPanel` 싱글턴 (`renderer.js:141`) 도 같은 모양이다.

**같은 창을 두 슬롯에 그리려면 이 단일성을 깨야 한다.** 서로 다른 창을 그리는
경우에는 도구도 서로 다르므로 이 항목이 걸리지 않는다.

### 2.6 pane 이동은 방향 기반이고, 갈 곳이 없으면 조용히 끝난다

`paneNavigate(dir)` (`web/js/core/app-layout.js:533`) 은 포커스 pane 에서 루트까지
경로를 거슬러 올라가며 `dir` 방향의 형제를 찾는다. 못 찾으면 루프가 끝나고 아무
일도 일어나지 않는다.

**빠져나오는 자리가 셋이다.**

| 자리 | 조건 |
|---|---|
| `:534` | 활성 창이 없거나 포커스 pane 이 없다 |
| `:535` | `path.length<2` — **분할이 없는 단일 pane 창** |
| `:548` | 루프가 끝났다 — 그 방향의 형제가 없다 |

`:535` 가 중요하다. Git 창과 pane 이 하나인 창은 루프에 **들어가지도 못한다**.
경계 넘침을 `:548` 에만 붙이면 "터미널 창에서는 슬롯을 넘어가는데 Git 창에서는
안 넘어가는" 비대칭이 생긴다.

### 2.7 `activeWindow` 는 이미 반쯤 클라이언트의 것이다

`ws.activeWindow` 는 `workspace.json` 에 저장되지만 (`manager.go:496`), 로드 직후
`sessionStorage` 의 값이 그것을 덮는다 (`app.js:159-165`). `displayMode`·
`mobileBreakpoint` 도 같은 자리에 있다 (`app.js:46`·`:54`). "보는 방식은 클라이언트의
것" (FR-SBT-6) 이 이미 관행이다.

한편 서버는 `activeWindow`+`focusedPane`+`activeTab` 으로 **활성 탭**을 판정하고
(`manager.go:545`), `dmctl` 이 "지금 사용자가 보는 도구"를 찾는 근거로 쓴다.

**그런데 그 판정은 클라이언트의 현재 포커스를 따라오지 않는다.** `_save()` 는 PUT
본문에서 `activeWindow` 와 `focusedPane` 을 **벗겨낸다** (`app.js:293`) — 여러 창이
같은 워크스페이스를 볼 때 한쪽의 시선이 다른 쪽의 화면을 끌고 가지 않도록 한
것이다. 서버는 이 두 필드를 **읽기만 하고 쓰는 자리가 없다** (Go 전역에서
`ActiveWindow` 는 `manager.go:496` 선언과 `:545`·`dmctl_listworkspace.go:309` 의 읽기
뿐이다).

이것은 슬롯 이전부터의 동작이며, 슬롯이 바꾸는 것도 아니다. 스펙 1차에서 이 사실을
놓쳐 FR-WSL-3 이 서버 판정까지 보증하는 것처럼 적혀 있었고, TC-WSL-5·15 가 그
전제로 서버를 검증하다 실패해 드러났다.

## 3. 요구사항 (Requirements)

### 3.1 묶음 S — 슬롯 모델

**FR-WSL-1** 콘텐츠 영역은 슬롯을 **1개 이상 `SLOT_MAX`(4) 이하**로 갖는다. 슬롯
하나는 창 0~1개를 표시한다. 배치 방향은 **가로(`horizontal`, 좌우)** 가 기본이고 세로
(`vertical`, 상하) 를 고를 수 있다 (§3.9).

상한이 4 인 이유는 화면이다 — 1280px 가로에서 4칸이면 칸마다 320px 이고, 터미널
탭 바와 스크롤바를 빼면 그보다 좁은 칸은 읽을 것이 남지 않는다. 상한은 상수
하나(`SLOT_MAX`)이며 요구가 바뀌면 그 한 줄이 바뀐다.

**FR-WSL-2** 슬롯 상태는 `sessionStorage` 에 산다. 키는 `slots` 이며 값은
`{windows:[id|null, …], focused:number, sizes:[number, …]}` 다. `windows` 와 `sizes`
의 길이는 같고 그것이 슬롯 개수다. `workspace.json` 은 **한 필드도 늘지 않는다** —
`schemaVersion` 은 2 그대로다.

`sizes` 는 칸의 **flex 배분값**이다 — 2칸 시절의 `ratio`(경계의 위치) 로는 셋 이상을
표현할 수 없다. 창 안 분할이 이미 같은 표현을 쓴다 (`split.sizes`, `renderer.js` 의
`sc.style.flex`).

**FR-WSL-3** `ws.activeWindow` 는 **포커스 슬롯의 창**을 뜻한다. 이 정의로 `_aw()`
(`app-layout.js` 외 48곳) 는 무변경으로 정확한 답을 낸다.

서버의 활성 탭 판정 (`manager.go:545`) 은 **이 SRS 의 관심 밖이다** — `_save()` 가
PUT 에서 `activeWindow`·`focusedPane` 을 벗기므로 (§2.7) 그 판정은 슬롯 이전에도
클라이언트의 현재 포커스를 따라오지 않았다. 슬롯은 그것을 낫게도 나쁘게도 하지
않는다.

**FR-WSL-4** 단일 슬롯 모드는 본 SRS 이전의 동작과 **완전히 같다**. 슬롯 상태가
없거나 슬롯이 1개면 `#area` 에 슬롯 컨테이너를 만들지 않는다 (§4 D-4).

**FR-WSL-5** 같은 창이 여러 슬롯에 놓일 수 있다. 그때의 동작은 브라우저 창을 여럿
띄워 같은 창을 볼 때와 같다 — 포커스 슬롯이 소유하고 나머지는 흐려진다 (FR-WSL-14).

**FR-WSL-6** 슬롯이 가리키던 창이 사라지면(창 삭제·워크스페이스 동기화) 그 슬롯은
빈다. **슬롯 자체는 남는다** — 사용자가 만든 칸을 앱이 임의로 없애지 않는다. 포커스
슬롯이 비면 포커스는 창이 있는 가장 가까운 슬롯으로 간다.

**FR-WSL-7** 슬롯에 담긴 창 id 가 워크스페이스에 없으면 로드 시 그 슬롯을 비운다 —
`activeWindow` 복원이 존재 확인을 하는 것과 같은 규약이다 (`app.js:162`).

### 3.2 묶음 I — 슬롯 신원과 소유권

**FR-WSL-10** 슬롯마다 고유한 `clientId` 를 갖는다. 슬롯 0 은 `App.clientId` 를 그대로
쓰고, 슬롯 1 은 그와 다른 신원을 갖는다.

**FR-WSL-11** 슬롯 1 이 열리면 그 신원으로 **자체 SSE 구독**을 연다. 슬롯 1 이 닫히면
그 구독을 닫는다. 서버가 소유권을 해제하는 계기가 구독 드롭이기 때문이다 (FR-XDF-9) —
구독 없는 신원은 소유를 영원히 붙들게 된다.

**FR-WSL-12** `_focusWindow` 의 "한 클라이언트 → 한 창" 규칙은 **"한 슬롯 → 한 창"**
으로 읽는다. 슬롯 0 이 창을 클레임해도 슬롯 1 의 소유는 놓지 않는다.

**FR-WSL-13** `_resizeCheck` (`app-focus.js:153`) 과 `_applyFocusOverlay` (`:163`) 은
"내 신원" 을 **슬롯 신원의 집합**으로 판정한다. 어느 슬롯이든 소유하고 있으면 내
것이다.

**FR-WSL-14** 같은 창이 두 슬롯에 있으면 **포커스 슬롯이 소유**한다. 다른 슬롯의 pane
은 `.pn-dimmed` 가 되고 PTY 크기를 보내지 않는다.

**FR-WSL-15** 서버는 무변경이다. `hub.Focus` 의 `owners` 맵은 여전히 `windowId →
clientId` 이고, 여전히 클라이언트 하나가 창 하나를 소유한다. **`TC-XDF-3`
(`e2e/focus-owner.spec.ts:76`) 은 개정 없이 통과해야 한다.**

**FR-WSL-16** OS 포커스가 이 브라우저 창에 없으면 어느 슬롯도 PTY 크기를 보내지
않는다 — `_windowFocused` 게이트 (`app-focus.js:154`) 는 슬롯보다 상위다.

### 3.3 묶음 T — 도구 인스턴스 다중화

**FR-WSL-20** `tools` Map 의 키는 `toolId` 에서 **`(toolId, slotIndex)` 복합키**가
된다. 조회·생성·파괴는 전용 함수를 경유하며, 호출부는 슬롯을 명시하지 않으면 포커스
슬롯을 뜻한다.

**FR-WSL-21** 어느 슬롯에서도 더 이상 보이지 않게 된 도구 인스턴스는 파괴한다.
같은 창을 두 슬롯에 두면 WebSocket 이 두 벌이 되므로, 슬롯이 다른 창으로 바뀌는
순간 회수하지 않으면 연결이 누적된다.

**FR-WSL-22** 도구 자체를 지우는 경로 (`app-tool.js:130`·`:136`, `app-cmd.js:235`) 는
**모든 슬롯의 인스턴스**를 파괴한다.

**FR-WSL-23** `fileEditors` 와 `gitPanel` 도 같은 규칙을 따른다. 두 슬롯에 같은 Editor
창을 두면 편집기 인스턴스가 슬롯마다 선다.

**FR-WSL-24** 슬롯 1 을 닫으면 그 슬롯의 모든 인스턴스를 파괴한다.

### 3.4 묶음 R — 렌더링

**FR-WSL-30** 슬롯 2개 모드에서 `#area` 는 슬롯 컨테이너 둘과 그 사이의 손잡이를
갖는다. 슬롯 컨테이너는 `position:relative` 다 — 이것으로 `.sp`·`.pn` 의 `inset:0`
가 슬롯을 채운다 (§2.2). **`.sp`·`.pn` 의 CSS 는 바뀌지 않는다.**

**FR-WSL-31** `_rLayout` 은 슬롯마다 §2.1 의 세 단계를 돈다. 도구 DOM 을 되돌리는
자리는 `#area` 가 아니라 도구가 속한 슬롯이다.

**FR-WSL-32** 슬롯 경계 손잡이를 끌어 이웃한 두 칸의 배분을 조절한다. 손잡이는 칸
사이마다 하나씩이다. 생김새와 히트 영역은
`#sb-handle` (`style.css:87-89`) 과 같다. 배분은 `slots.sizes` 에 저장된다.
커서와 끄는 축은 슬롯 방향을 따른다 — 가로면 `col-resize`, 세로면 `row-resize`.
창 안 분할의 손잡이가 이미 그렇게 갈라져 있다 (`style.css:143-144`).

**FR-WSL-33** 사이드바 목록은 **두 슬롯의 창을 모두** 활성으로 표시하되, 포커스 슬롯의
창을 구분해서 보여준다.

**FR-WSL-34** 토프바의 창 이름 (`#window-name`) 은 포커스 슬롯의 창 이름이다. 토프바의
나머지 버튼(`Split H`·`Split V`·`+` 등)도 포커스 슬롯의 창을 대상으로 한다 — 지금
`_rTopbar` (`renderer.js:65`) 가 `_aw()` 로 판정하는 그대로다.

**FR-WSL-35** 슬롯은 **서로 구별되어야 한다.** 칸이 둘을 넘으면 "어느 칸이 무슨
창인지" 와 "지금 어느 칸에 있는지" 가 둘 다 즉시 읽혀야 한다. 셋을 만족한다.

1. **슬롯 머리글** — 칸이 2개 이상이면 각 칸 위에 얇은 머리글이 서고 그 칸의 창
   이름이 적힌다. 빈 칸은 그 사실을 적는다.
2. **포커스 칸 강조** — 포커스 슬롯의 머리글은 강조색이다. pane 포커스
   테두리(`.pn` 의 2px border) 와 다른 표현이어야 어느 층의 포커스인지 읽힌다
   (§7 R-5).
3. **칸 경계** — 칸 사이는 손잡이가 가른다 (FR-WSL-32).

머리글은 토프바의 창 이름(FR-WSL-34) 을 대체하지 않는다 — 토프바는 여전히 포커스
슬롯을 말한다.

### 3.5 묶음 N — 슬롯 간 이동

**FR-WSL-40** `paneNavigate(dir)` 은 창 안에서 갈 pane 이 없을 때 슬롯 경계를 넘는다.
**새 단축키를 만들지 않는다** — `Ctrl+Shift+←/→` 가 그대로 슬롯을 오간다.

**FR-WSL-41** 경계 넘침은 §2.6 의 세 자리 **모두**에서 일어난다. 특히 `:535` 의
`path.length<2` — 분할이 없는 창(Git 창 포함)에서도 슬롯을 넘어갈 수 있어야 한다.

**FR-WSL-42** 경계를 넘는 축은 **슬롯 방향을 따른다** — 가로면 `left`·`right`,
세로면 `up`·`down` 이다. 다른 축은 지금처럼 무동작이다. 슬롯이 좌우로 놓였는데
위아래 키가 슬롯을 넘으면 "칸으로 간다" 는 키의 뜻이 깨진다 (D-5).

**FR-WSL-43** 넘어간 슬롯에서 포커스를 받는 pane 은 **그 창이 기억하는
`focusedPane`** 이다 (`app-focus.js:34` 가 창별로 유지하는 값). 그 값이 없거나 사라졌으면
첫 pane 이다.

**FR-WSL-44** 넘어갈 슬롯이 없으면(단일 슬롯 모드, 또는 가장자리 방향) 무동작이다 —
현행과 같다. 순환하지 않는다: 마지막 칸에서 더 가도 첫 칸으로 돌아오지 않는다.

**FR-WSL-45** 경계 넘침은 포커스 슬롯을 바꾸고, `ws.activeWindow` 를 갱신하고,
`_focusWindow` 로 소유권을 클레임한다.

**FR-WSL-46** 빈 슬롯으로는 넘어가지 않는다. 넘어갈 곳에 창이 없으면 무동작이다.

### 3.6 묶음 U — 진입점

**FR-WSL-50** 토프바에 슬롯 **추가(`+`)·제거(`−`)** 버튼을 둔다. `desktop-only` 이며,
창 안 분할인 `Split H`·`Split V` 와 **떨어진 자리**에 놓는다 (§7 R-3).

토프바의 데스크톱 버튼 차례는 다음과 같다. **`Agents` 가 가장 오른쪽이다.**

    [알림] [Split H] [Split V] [Runs] [Background] [− 슬롯 +] [Agents]

`+` 는 슬롯이 `SLOT_MAX` 이면, `−` 는 슬롯이 1개이면 눌리지 않는다 (`disabled`).
눌리지만 아무 일도 하지 않는 버튼은 고장으로 읽힌다 (FR-GIT-180 이 세운 규약).

**FR-WSL-51** 같은 동작의 단축키 액션 `slotAdd`·`slotRemove` 를 둔다. 등록은 기존
체계를 그대로 탄다 — `helpers.js:84` 의 기본 바인딩 표, `app.js:229` 의
`executeAction` 맵, `app-settings.js:263` 의 설정 화면 그룹.

**FR-WSL-52** 슬롯을 더하면 새 칸은 **포커스 슬롯 바로 뒤**에 생기고 **포커스 슬롯과
같은 창**을 받는다. 더한 칸이 곧 포커스 슬롯이 된다 — 방금 만든 칸에 다른 창을 여는
것이 기대되는 흐름이고, 그러면 사이드바 클릭 한 번으로 끝난다 (FR-WSL-54).

**FR-WSL-53** 슬롯을 제거하면 **포커스 슬롯이 사라지고** 포커스는 그 자리의 이웃으로
간다. 제거된 슬롯의 도구 인스턴스는 파괴된다 (FR-WSL-24). 슬롯이 1개면 제거할 수
없다 — 그 상태가 단일 슬롯 모드다.

**FR-WSL-54** 사이드바에서 창·리포·Editor 행을 여는 모든 경로는 **포커스 슬롯**에
연다. 다른 슬롯은 건드리지 않는다.

**FR-WSL-55** 슬롯을 클릭하면 그 슬롯이 포커스 슬롯이 된다.

### 3.7 묶음 M — 모바일

**FR-WSL-60** 모바일에서는 포커스 슬롯의 창 **하나만** 그린다. 모바일이 pane 을
하나만 그리는 것과 같은 결이다. 이때의 DOM 은 **단일 슬롯 모드와 같다** — 슬롯
컨테이너도 손잡이도 만들지 않는다 (FR-WSL-4, D-4). 칸이 하나인데 칸을 나누는
요소를 두면 그것을 딛는 CSS 와 e2e 가 두 갈래가 된다.

**FR-WSL-61** 슬롯 상태는 모바일에서도 보존된다. 데스크톱으로 돌아오면 그대로 복원된다.

**FR-WSL-62** 토글 버튼은 모바일에서 보이지 않는다 (FR-WSL-50). 모바일에서 슬롯을
여는 길은 없다.

### 3.8 묶음 X — 인터페이스 계약

테스트와 구현이 같은 이름을 딛도록 여기서 못박는다. **이름이 스펙에 없으면 테스트가
구현을 앞설 수 없다.**

**FR-WSL-70** DOM. 슬롯 2개 모드에서 `#area` 의 자식은 슬롯 컨테이너 둘과 손잡이
하나다.

```html
<div id="area" data-slotdir="horizontal">
  <div class="slot slot-focused" data-slot="0">
    <div class="slot-head">창 이름</div>
    …분할 트리…
  </div>
  <div class="slot-handle" data-slot-handle="0"></div>
  <div class="slot" data-slot="1"> … </div>
  <div class="slot-handle" data-slot-handle="1"></div>
  <div class="slot" data-slot="2"> … </div>
</div>
```

손잡이는 **칸 사이마다** 하나씩이므로 id 가 아니라 클래스다 (`.slot-handle`);
`data-slot-handle="i"` 는 그것이 가르는 왼쪽/위쪽 칸의 인덱스다.

`#area` 의 `data-slotdir` 이 방향이다 (FR-WSL-80). 단일 슬롯 모드에서는 이 속성도
없다.

포커스 슬롯에만 `.slot-focused` 가 붙는다. 빈 슬롯에는 `.slot-empty` 가 붙는다.
**단일 슬롯 모드에서는 이 셋 중 어느 것도 없다** (FR-WSL-4) — `#area` 는 지금처럼
분할 트리를 직접 갖는다.

**FR-WSL-71** 토글 버튼의 id 는 `slot-toggle` 이다. 토프바에서 `#agents-toggle`
뒤에 온다 — `Split H`·`Split V` 와 떨어진 자리다 (FR-WSL-50, §7 R-3).

**FR-WSL-72** `sessionStorage` 키는 `slots` 이고 값은 JSON 문자열이다.

```json
{"windows":["<winId>", "<winId>", null], "focused":1, "sizes":[1, 1, 1]}
```

단일 슬롯 모드에서는 키가 **없다**. 파싱에 실패하거나 형식이 어긋나면 키를 지우고
단일 슬롯 모드로 떨어진다 — `activeWindow` 복원이 존재 확인에 실패했을 때와 같은
규약이다 (`app.js:162`).

**FR-WSL-73** App 표면. 모두 `window.app` 에서 닿는다.

| 이름 | 계약 |
|---|---|
| `app.slots` | 슬롯 상태. 단일 슬롯 모드면 `null` |
| `app.slotCount()` | 1 또는 2 |
| `app.slotAdd()` | 포커스 슬롯 뒤에 칸을 더한다. FR-WSL-52 |
| `app.slotRemove()` | 포커스 슬롯을 없앤다. FR-WSL-53 |
| `app.slotFocusTo(i)` | 슬롯 `i` 를 포커스 슬롯으로. FR-WSL-45 |
| `app.slotOpen(i, winId)` | 슬롯 `i` 에 창을 놓는다 |
| `app.slotNavigate(dir)` | 경계 넘침. `paneNavigate` 가 부른다. FR-WSL-40 |
| `app.slotDir` | 방향. 읽기·쓰기 모두 가능한 접근자. FR-WSL-80~84 |

**FR-WSL-74** 단축키 액션 id 는 `slotAdd`·`slotRemove` 다 (FR-WSL-51). 버튼 id 는
`slot-add`·`slot-remove` 다.

**FR-WSL-75** `tools` Map 의 복합키는 **슬롯 0 에서 `toolId` 그대로**이고, 슬롯 `i>0`
에서 `` `${toolId}@${i}` `` 이다. 단일 슬롯 모드의 Map 키가 지금과 한 글자도 다르지
않아야 D-4 의 "슬롯이 1개면 지금과 같다" 가 Map 층에서도 성립한다.

### 3.9 묶음 D — 슬롯 방향

**FR-WSL-80** 슬롯 방향은 `horizontal`(좌우) 또는 `vertical`(상하) 이며 **기본은
`horizontal`** 이다. 용어는 창 안 분할과 같다 — 한 화면에 두 종류의 분할이 보이는데
(§7 R-3) 방향 용어까지 다르면 안 된다.

**FR-WSL-81** 설정 → Display 탭에서 바꾼다. 항목은 **버튼 하나짜리 토글**이며
id 는 `ds-slotdir` 이다. 누를 때마다 두 값이 뒤집히고, `data-v` 가 지금 값을
(`horizontal`·`vertical`) 나른다.

버튼에 적히는 것은 **지금 값**이지 다음 값이 아니다 — 눌러서 바뀌는 방향은
`title` 이 말한다. 둘을 뒤집어 적으면 켜진 것이 무엇인지 읽을 수 없다.

고르는 목록이 아닌 이유는 값이 둘뿐이기 때문이다. 두 값 사이를 오가는 데 목록을
펼쳤다 고르는 두 동작을 요구할 이유가 없다 — 한 번 누르면 된다.

**FR-WSL-82** 방향은 `localStorage` 에 산다. 키는 `slotDir` 다. **슬롯 배치와 저장
위치가 다른 것은 의도다** — 어느 창을 어느 칸에 두는가는 브라우저 탭의 사정이지만
(FR-WSL-2), 가로로 볼지 세로로 볼지는 이 기기에서 화면을 쓰는 방식이고 설정 화면에
노출되는 항목이다. 탭을 새로 열 때마다 기본값으로 돌아가면 설정으로서 배신이다.

**FR-WSL-83** 방향을 바꾸면 열려 있는 슬롯이 **즉시** 재배치된다. `slots.sizes` 는
그대로 유지된다 — 배분값은 방향과 무관하다.

**FR-WSL-84** 방향은 단일 슬롯 모드에서도 저장된다. 슬롯을 닫았다 열어도 고른 방향이
유지된다.

## 4. 설계 결정 (Design Decisions)

**D-1. 창 그리드이지 탭 통합이 아니다.**
같은 목적을 "창 타입 제약을 걷어내고 한 분할 트리에 git·editor·terminal 탭을 섞는"
쪽으로도 달성할 수 있다. 그쪽이 모델은 더 깨끗하지만, Git 창의 리포 패널과 Editor
창의 좌측 탐색기가 **분할 트리 밖의 창 부속**이므로 (FR-EDT-46) 그것들을 pane 안으로
내리는 것이 본체 작업이 되고, FR-GIT-179·FR-EDT-54·94 를 비롯한 불변식을 대량으로
폐기해야 한다. 창을 통째로 담는 쪽은 그 부속을 **손대지 않는다**.

**D-2. 슬롯 상태는 `sessionStorage` 다.**
`workspace.json` 에 넣으면 서버가 슬롯 B 의 활성 탭까지 알게 되어 `dmctl` 이 슬롯을
조작할 수 있게 되지만, `schemaVersion` 마이그레이션과 `manager.go:545` 의 활성 탭
판정 개정이 따라오고, **무엇보다 데스크톱의 2칸 배치가 모바일 접속에 강제된다**.
슬롯은 "보는 방식"이고 그것은 클라이언트의 것이다 (FR-SBT-6, `app.js:46`·`:54` 의
선례).

**D-3. 슬롯마다 별개의 클라이언트 신원을 준다.**
소유권을 슬롯 단위로 만드는 방법은 둘이다 — 서버의 `owners` 맵을 클라이언트당 다중
창으로 넓히거나, 슬롯을 서버에게 **별개 클라이언트로 보이게** 하거나. 후자를 택한다.

- 서버가 무변경이다 (`hub/focus.go` 한 줄도 바뀌지 않는다)
- `TC-XDF-3` 을 비롯한 기존 소유권 e2e 가 개정 없이 통과한다 (FR-WSL-15)
- "브라우저 창 두 개로 같은 창을 볼 때와 같은 로직" 이라는 요구가 **문자 그대로**
  구현된다 — 슬롯 둘은 서버 눈에 정확히 브라우저 창 둘이다

**D-4. 단일 슬롯 모드에서는 슬롯 컨테이너를 만들지 않는다.**
DOM 을 한 겹 더 두면 `.sp`·`.pn` 의 `inset:0` 기준이 바뀌고, 그 경로는 e2e 대부분이
딛고 있다 (`#area .pn` 셀렉터가 `focus-owner.spec.ts` 전반에 있다). 슬롯이 1개면
지금과 **같은 DOM** 이어야 회귀 위험이 없다.

**D-5. 슬롯 이동은 새 단축키가 아니라 `paneNavigate` 의 경계 넘침이다.**
`Ctrl+Shift+←/→` 는 이미 "왼쪽/오른쪽 칸으로" 를 뜻한다. 창의 끝에서 한 번 더 누르면
옆 슬롯으로 가는 것은 그 뜻의 연장이고, 사용자가 외울 것이 늘지 않는다. 구현상으로도
`paneNavigate` 가 이미 "갈 곳이 없으면 조용히 끝나는" 함수라 fall-through 지점이
그대로 확장점이다 (§2.6).

**D-6a. 같은 창일 때는 포커스 슬롯만 소유를 주장한다.** (구현 중 실측)
두 슬롯이 모두 주장하면 `_focusClaim` 이 fire-and-forget POST 두 개를 내보내고, 승자가
**네트워크 도착 순서**로 정해진다 — 로컬에서는 나중에 부른 쪽이 이기지만 서버
브로드캐스트가 그것을 뒤집는다. TC-WSL-7 이 단독으로는 통과하고 전체 실행에서만
실패해 드러났다. 비포커스 슬롯이 주장하지 않으면 그 칸은 소유자가 아니게 되어
흐려지는데, 그것이 FR-WSL-14 가 원하는 결과 그대로다.

**D-6. 같은 창을 두 슬롯에 허용한다.**
금지하면 사이드바 클릭마다 "이미 다른 슬롯에 있음" 을 다뤄야 하고, 그 처리(포커스
이동이냐 맞교환이냐)가 예측하기 어려운 규칙이 된다. 허용하면 그 상황은 **이미 존재하는
동작**으로 흡수된다 — 한쪽이 흐려지는 것은 사용자가 브라우저 창 두 개에서 이미 겪고
있는 그것이다.

**D-8. 칸의 크기는 `ratio` 가 아니라 `sizes` 배열이다.** (개정)
2칸 시절에는 "경계가 어디냐"(`ratio` 하나) 로 충분했지만 셋을 넘으면 경계가 여럿이라
그 표현이 서지 않는다. 칸마다 **flex 배분값**을 주면 개수와 무관하게 같은 규칙이고,
창 안 분할이 이미 그 표현을 쓴다 (`split.sizes` → `sc.style.flex`). 레이아웃도
`absolute` + `%` 계산에서 **flex 로 옮긴다** — 칸이 늘어도 누적 좌표를 계산할 일이
없다. 단일 슬롯 모드에는 컨테이너 자체가 없으므로 (D-4) 이 변경이 닿지 않는다.

**D-9. 칸의 상한은 4다.**
무한히 늘리면 칸마다 터미널이 읽을 수 없이 좁아진다. 상한을 두되 `SLOT_MAX` 상수
하나로 두어, 요구가 바뀌면 그 한 줄이 바뀌게 한다. 한계에 닿은 버튼은 `disabled`
다 — 눌리지만 아무 일도 하지 않는 버튼은 고장으로 읽힌다.

**D-10. 칸의 구별은 머리글이 한다.**
칸이 둘일 때는 "왼쪽/오른쪽" 으로 충분했지만 셋을 넘으면 어느 칸이 무슨 창인지
위치만으로 읽히지 않는다. 색을 흐리게 하는 방식은 쓸 수 없다 — 그것은 이미 소유권
없음(`.pn-dimmed`)의 뜻이다 (§7 R-4). 그래서 **이름을 적는다.**

**D-7. 새 슬롯의 초기값은 포커스 슬롯과 같은 창이다.**
"직전에 보던 창"(`_lastPlainWindow`) 은 이력이 없을 때와 그 값이 이미 포커스 슬롯의
창일 때 두 구멍이 있고, 폴백 체인으로 메우면 토글할 때마다 무엇이 뜰지 예측할 수
없게 된다. D-6 이 같은 창을 허용하므로 초기값에 특별한 규칙이 필요 없다.

## 6. 비목표 (Non-goals)

- **슬롯 3개 이상.** 요구는 두 화면이고, 실사용이 2칸이다. 슬롯을 N-트리로 일반화하는
  것은 `window.layout` 의 분할 트리를 한 층 위에 다시 만드는 일이다.
- **창 타입 불변식 변경.** Git 창은 여전히 탭을 더할 수 없고, Editor 창에는 편집기
  탭만 산다. 슬롯은 창을 담을 뿐이다.
- **`dmctl` 의 슬롯 인식.** D-2 의 귀결이다. `dmctl` 은 지금처럼 포커스 슬롯의 창을
  "활성" 으로 본다.
- **슬롯별 사이드바·토프바.** 사이드바와 토프바는 하나이고 포커스 슬롯을 따른다.
- **슬롯 배치의 프리셋 저장.** 프리셋은 창 안의 레이아웃을 다룬다 (`constants.js:167`).
- **`gitPanel` 싱글턴 해체.** Git 창이 워크스페이스에 하나이므로 (`app-git.js:9`),
  두 슬롯에 같은 Git 창을 두는 경우에만 필요하다. FR-WSL-23 이 요구하는 최소한만 한다.

## 7. 위험 (Risks)

**R-1. WebSocket 이 두 배가 된다. (중)**
같은 창을 두 슬롯에 두면 도구마다 연결이 두 벌이다. FR-WSL-21 의 회수가 새는 순간
연결이 누적되고, 그 증상은 `reconnect-storm` 이 다루는 것과 같은 모양으로 나타난다.
슬롯 전환·닫기 경로마다 인스턴스 회수를 테스트로 고정한다 (TC-WSL-16).

**R-2. `tools` Map 복합키가 30곳을 건드린다. (중)**
대부분 `tools.get(toolId)` 단순 조회라 조회 함수 하나로 흡수되지만, `tools.values()`
순회 (`renderer.js:99`, `app-cmd.js:235`) 는 의미가 달라진다 — "모든 도구" 가 "모든
(도구,슬롯) 쌍" 이 된다. 순회 지점을 전수로 훑는다.

**R-3. 두 종류의 분할이 한 화면에 보인다. (중)**
`Split H`/`Split V` 는 창 **안**을 쪼개고 슬롯 토글은 창 **밖**을 쪼갠다. 토프바에
나란히 두면 같은 종류로 읽힌다. FR-WSL-50 이 자리를 구분하도록 요구하는 이유다.

**R-4. 같은 창을 두 슬롯에 두었을 때의 dim 이 고장으로 읽힌다. (하)**
사용자가 브라우저 창 두 개에서 이미 겪는 동작이지만, 한 화면 안에서는 "왜 한쪽만
흐리지" 로 읽힐 수 있다. D-6 이 이 대가를 받아들인 결정이므로 문서(`shortcuts.md`
또는 `features.md`)에 한 줄로 명시한다.

**R-5. 포커스 슬롯 표시가 pane 포커스 표시와 겹친다. (하)**
`.pn` 이 이미 2px border 로 포커스를 표현한다 (`style.css:149`). 슬롯 포커스를 같은
방식으로 그리면 어느 층의 포커스인지 알 수 없다. FR-WSL-35 가 다른 표현을 요구한다.

**R-6. 모바일 전환 중 슬롯 상태가 유실된다. (하)**
`displayMode` 는 런타임에 바뀔 수 있다 (`app.js:51`). 모바일로 접히는 동안 슬롯 상태를
지우면 데스크톱 복귀 시 배치가 사라진다. FR-WSL-61 이 보존을 요구한다.

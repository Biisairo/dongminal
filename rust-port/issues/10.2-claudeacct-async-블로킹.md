- **방식**: `fsutil::off_worker(f)` 를 두었다. 다중 스레드 런타임의 작업 스레드에서 부르면 `tokio::task::block_in_place` 로 그 스레드의 다른 task 를 새 스레드로 넘긴 뒤 f 를 부른다. blocking 풀·런타임 밖·current_thread 런타임에서는 그대로 부른다(block_in_place 가 current_thread 에서 패닉하므로 flavor 를 본다). 서버 런타임은 `new_multi_thread` 다(`cmd/dongminal/src/serve/mod.rs`).
- **감싼 곳(원시 호출 단위)**: 디렉터리 락 대기 루프 `dirlock::acquire_dir_lock_with`(→ `lock_claude` 전부), 파일 락 `fsutil::lock_file`(Store::lock·engine consume 락·mappings 락·profile consume 락), 키체인 `LiveStore::read`(재시도 sleep 포함)·`LiveStore::write`, `BackupStore` 의 get·write·delete, `remove_profile` 의 키체인 delete. 원시 호출에서 감쌌으므로 HTTP 처리기(switch·add·remove·refresh 등)와 `eng.run`·`auto.run` 루프가 모두 덮인다. httpapi 코드는 고치지 않았다(시험만 더함).
- **Go 와 다르게 한 내부 결정**: `spawn_blocking` 대신 `block_in_place` 를 썼다. 락 guard 를 await 너머로 쥐는 코드(engine refresh)와 `&self` 빌림을 그대로 두어 변경을 최소로 했다. 관측 동작(응답 바이트·오류 문구·락 순서·9초 시한)은 바뀌지 않았다.
- **시험(RED→GREEN)**: httpapi `claude_accounts_switch_lock_wait_does_not_block_other_requests`(작업 스레드 1개, 자격증명 락을 1.5초 쥔 동안 `/api/health` 가 500ms 안에 답하고 전환은 200) — 고치기 전 1.30초로 실패. claudeacct `tests/offload.rs` 4건(디렉터리 락·저장소 파일 락·live 키체인·backup 키체인 대기 중 다른 task 가 400ms 안에 돈다) — 고치기 전 모두 실패(1.06~2.21초).

### 결과 (rp/10.4)

**FR-RDF-3 간선 op 시한**
- `dm-daemon-ipc`: `server::EDGE_CALL_TIMEOUT = 30s`(Go `edgeCallTimeout`). `edge_op` 이 `Node::do_op_within(req, limit)` 을 부른다. 시험 전용 주입 `Inner::set_edge_call_timeout`(cfg(test)).
- `dm-shared-edgenode`(SRS 가 허락한 범위): 공개 API `Node::do_op_within(req, limit: Duration) -> Response` 추가. `do_op` 은 그대로(시한 없음). 시한이 지나면 op 를 버리지 않고 `CancellationToken` 을 취소해, Go 처럼 ctx 를 받는 자리(add·invite_accept 의 pair 호출, remove 의 unpair 알림, notify 의 mesh.notify)만 시한 초과로 끝나고 나머지 단계는 이어진다. future 를 버리면 mesh 의 걸기 상태(running)가 풀리지 않으므로 이렇게 했다.
- 시한 초과 응답은 go1.27.2 격리 실측(`Do(ctx 300ms)`, 응답하지 않는 상대)으로 고정했다:
  - notify → 502 `edge_unreachable` "상대에 닿지 못했다: 상대 노드에 닿지 못했습니다: context deadline exceeded"
  - add → 502 `edge_unreachable` `상대 노드에 닿지 못했습니다: Post "https://<addr>/edge/v1/pair": context deadline exceeded`
  - remove → 200 `{"fp":…,"name":…,"notified":false}`, 이쪽 간선은 지운다
  - 감사 줄(notify·pair·unpair 502)도 같다.
- Go 와 다르게 한 내부 결정: edgemesh 는 취소된 걸기를 `context canceled` 로 적는다(edgemesh 는 10.1 소관이라 건드리지 않음). op 의 취소는 시한뿐이므로 edgenode `deadline_cause` 가 그 원인을 `context deadline exceeded` 로 옮긴다.
- 시험: edgenode `op_deadline_answers_like_go`(notify·add·remove), ipc `edge_op_stops_at_call_timeout`. 둘 다 RED(시한에 끝나지 않음) → GREEN.

**FR-RDF-4 git 작업 SSE 끊김**
- `dm-webserver-gitapi` `remote.rs` `job_event_loop` 이 `st.closed()` 를 함께 기다린다(4688c7f7 과 같은 꼴). 시험을 위해 `pub(crate)` 로 바꿨다.
- 시험 `job_events_close_releases_subscription_without_waiting`: 본문을 버린 뒤 1초 안에 루프가 끝나고 구독 채널(rx)이 닫힌다. jobs crate 에 구독 수 API 가 없어(다른 crate) 수신 채널이 닫히는 것으로 구독 해제를 본다(`Unsubscribe` 는 같은 작업에서 함께 버려진다). RED(1초 시한 초과) → GREEN.

**남은 위험**
- Go·Rust 모두 상대 호출 하나가 15초(`REQUEST_TIMEOUT`)로 묶여 있어, 실제로 30초 시한에 닿는 경로는 사실상 없다. 시한은 안전망이다.

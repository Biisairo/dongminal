#### I5·I6 — 결정이 필요하다 (코드를 봐도 답이 나오지 않는다)

- **I5 키 배정.** 후보 둘을 함께 물어라. ① 새 키를 더한다 (예: `Ctrl+Shift+KeyG` = Git
  창으로, `Ctrl+Shift+Comma`/`Period` = 리포 순회). ② Git 창 안에서는 창 순회 키
  (`Ctrl+Shift+[ ]`)를 **리포 순회로 재해석**한다 — 키를 늘리지 않지만 모드 의존이다.
- **I6 "원래 있던 윈도우"의 정의.** ① 마지막으로 포커스가 있던 일반 창 ② Git 창을
  열기 직전의 창. 단순한 경우에는 둘이 같고, Git 창을 떠났다 돌아온 뒤에 갈린다.

#### I7 — 규모가 다르다. 스펙을 먼저 쓴다

신규 기능이고 `internal/webserver/domain/worktree` 가 이미 Run 격리용으로 worktree 를
만들고 지운다. **경계를 스펙에서 먼저 정해라 — 사용자가 만든 worktree 를 Run 정리가
지우면 안 된다.** 그 가드를 읽어 둔 결과는 이렇다 (2026-08-27).

- `Manager` 는 **`$DONGMINAL_HOME/worktrees` 아래만** 자기 영역으로 삼는다.
  `checkPath` 가 그 밖의 경로·루트 자신·저장소 자신을 `unsafe_path` 로 거부하고,
  `Remove` 는 거부당하면 `residue` 를 남긴다 (FR-WKT-8).
- 경로 규약은 `Path(runShort, leaf)` = `$DONGMINAL_HOME/worktrees/<run.short>/<member.short>`.
- **전체를 쓸어내는 경로가 없다.** `Remove` 는 `RemoveSpec` 하나씩이고, 정리는 Run 이
  자기가 만든 것만 대상으로 한다. 즉 **경로만 갈라 두면 구조적으로 안전하다.**
- 따라서 물을 것은 "사용자 worktree 를 어디에 만드는가"다. ① Run 영역 밖(예: 저장소
  옆 형제 디렉터리) — `checkPath` 가 Run 정리의 손을 아예 막는다 ② 같은 루트의 예약된
  이름공간(`worktrees/user/<name>`) ③ 사용자가 경로를 직접 지정.
- 어느 쪽이든 **보호 테스트를 하나 세워라**: Run 정리가 사용자 worktree 경로를
  거부한다는 것을 이름이 아니라 동작으로 고정한다.

범위도 정해야 한다 — 목록·생성·제거까지인가, 고른 worktree 를 **Git 창의 활성 리포로
여는 것**까지인가. 후자가 없으면 만들어도 쓸 길이 없다.

**권고 순서**: 국소 UI(I1~I4) → 결정 필요(I5·I6) → I7. I1~I4 는 서로 독립이라 하나씩
끊어 커밋할 수 있다.

### 1.4 E2 — Git Graph 의 로직으로 다시 씀 (완료)

사용자 지적("선은 merge·branch 가 아니면 혼자 휠 수 없다")을 받아 **참조 도구의
소스를 직접 읽었다** (`mhutchie/vscode-git-graph` `web/graph.ts`). 확인한 사실은
지적과 반대였다: Git Graph 는 행마다 열을 왼쪽부터 촘촘히 나눠 주므로
(`registerUnavailablePoint` 의 `nextX`, `getNextPoint`) **통과선이 자기 일 없는
행에서도 왼쪽으로 휜다.** 고정되는 것은 커밋 점의 x 뿐이다. `git log --graph` 도
같다 (`|/ /`).

그래서 `buildLaneGraph` 를 그쪽 구조(`determinePaths`/`determinePath`)로 다시 썼다.
규칙 R1~R4 와 근거 코드는 `GIT_REVIEW4_SRS` §2.3.1 에 있다. 바뀐 것 셋:

1. **열은 갈래를 머리 행 순서로 처리하며 행마다 다음 빈 열을 집어 정한다** — 그래서
   빈 열이 없고, 선은 **왼쪽으로만** 움직인다 (오른쪽으로 밀리는 일이 없다).
2. **갈래는 first-parent 사슬을 끝까지 잡는다** — 트렁크가 뿌리까지 자기 색을
   유지한다. 행 순서로 레인을 배정하던 이전 방식은 뒤 행의 갈래가 트렁크의 뿌리를
   먼저 물어 가 **트렁크가 중간에서 색을 갈아입었다.**
3. **이미 배치된 부모로 가는 선은 행마다 자기 열을 집고 내려가 부모 행에서 붙는다** —
   한 행에서 대각선으로 뛰지 않는다.

의도적 이탈은 하나다: **부모가 없는 커밋 아래로 선을 내리지 않는다.** Git Graph 는
그 경우에도 목록 끝까지 선을 그리는데, 뿌리는 보통 마지막 행이라 드러나지 않는
것이고 `--all` 에서 뿌리가 중간에 오면 아무 데도 닿지 않는 선이 늘어진다
(FR-GIT-235).

## 4. P1/P2 로 미뤄둔 기능 — **이제 범위 안이다**

**2026-08-27 사용자 지시로 방침이 바뀌었다.** 이 절은 원래 "의도적으로 남긴 것
(고치지 마라)" 였다. 이제 목표는 **이 문서에 남은 전부를 끝내는 것**이므로 아래도
할 일이다. 다만 미룬 근거는 지워지지 않았으니, 착수 순서를 정할 때 그 근거를 다시
읽어라 — P2 로 민 것들은 대체로 "터미널로 충분하다"는 판단이었다.

> **2026-08-27 갱신 (2): 이 표에서 남은 것은 셋뿐이다.** 범위와 진행은
> `GIT_ACTIONS_SRS.md`(FR-GIT-250~285)가 단일 진실 공급원이며, 남은 것은 그 문서
> §6.1 의 **283 merge editor · 284 인터랙티브 rebase · 285 clone/init** 이다.
> Blame(276)·reflog(280)·리포 드롭다운(282)은 끝났고, 커밋 mute 와 author override 는
> 사용자 결정으로 **철회**했다 (D7·D10).

| 항목 | 원래 근거 | 규모 |
|---|---|---|
| 브랜치 삭제 · 태그 생성/삭제 · cherry-pick/revert/reset · merge/rebase 실행 | 비목표 P1 | **가장 작다.** 메뉴 프레임워크(FR-GIT-146)가 자리를 열어 두었으므로 **항목 선언만 더하면 된다.** 실행 경로는 `domain/git/write` 의 `ExecWrite` 초크포인트를 지나야 하고, 파괴적 명령은 `Destructive` 선언이 기록에 남는다 (FR-GIT-95, I5) |
| hunk/line 단위 스테이징 | 비목표 P1/P2 | 중간. `git apply --cached` 로 부분 패치를 만들어야 하고, diff 뷰가 hunk 경계를 알아야 한다 |
| clone / init | 비목표 P2 — 터미널로 충분 | 작다. 다만 clone 은 원격 인증에 걸린다 — 아래 §4.1 을 먼저 읽어라 |
| 3-way merge editor · 인터랙티브 rebase | 비목표 P2 | **가장 크다.** merge editor 는 Monaco 위에 별도 모드가 필요하고, 인터랙티브 rebase 는 `GIT_SEQUENCE_EDITOR` 를 통한 대화형 편집이라 지금의 단발 실행 모델과 맞지 않는다 |

### 4.1 성격이 다른 둘 — 착수 전에 나에게 확인하라

위 넷은 "P1/P2 라 이번 범위가 아니었다"는 것뿐이다. 아래 둘은 **의도한 결정**이라
방침 변경에 자동으로 포함되지 않는다.

| 항목 | 왜 다른가 |
|---|---|
| **자격증명 저장·중계** | FR-GIT-104 의 **의도적 배제**다. "통과하지 않음을 보장하는 유일한 방법은 담을 자리를 만들지 않는 것"이라는 근거로, `TestNoCredentialFields` 가 `domain/git/*`·`gitapi`·`httpapi` 를 훑어 **필드 이름만으로** 막고 있다. 되살리려면 그 보호 테스트를 약화해야 하고, 그건 이 저장소의 안전망 셋 중 하나를 여는 일이다. **되살릴지부터 물어라.** 대안은 시스템 credential helper 에 위임하는 것 — dongminal 이 값을 보지 않는다 |
| **안내문·툴팁이 한글인 것** | FR-GIT-202 의 확정 결정이다 — 버튼만 영어이고 설명은 읽는 사람의 말이어야 한다. 결함이 아니라 설계다. 바꿀 이유가 생겼는지부터 물어라 |

## 5. 알려진 간헐 실패 (제품 결함 아님)

전체 e2e 실행에서 **0~1건이 간헐적으로 실패한다.**

| 테스트 | 성질 |
|---|---|
| `background-restore-at` TC-BGR-9 | **Git 이전부터 있던 테스트.** "창이 비는 과도 상태를 명중" 시키려는 것이라 본질적으로 타이밍 의존이다 |
| `git-stash` S2 · S3 | 우클릭 → 메뉴 항목 → git 상태 확인. 부하가 걸리면 기본 5초 단정이 흔들린다 |
| `git-commit` E11 | textarea 높이 드래그. 같은 성질 |

확인한 근거: 단독 반복 통과 · 실패하는 테스트가 실행마다 다르다 ·
`e2e/fixtures.ts` 머리말이 이 성질을 이미 설명한다(고아 도구가 쌓이면 WS open 이
늦어진다).

**권고**: 전체 실행은 `npx playwright test --retries=1` 로 돌린다. 진짜 실패는 두 번
모두 실패하므로 게이트의 뜻이 약해지지 않는다. `playwright.config.ts` 의 로컬
`retries` 를 1로 올리는 것은 게이트의 뜻을 바꾸는 결정이므로 **사용자 판단에
맡긴다** (CI 는 이미 `retries: 2`).

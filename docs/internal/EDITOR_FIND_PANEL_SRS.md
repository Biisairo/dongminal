# SRS: 편집기 파일 내 찾기 패널 — IEEE 29148

## 1. 개요 (Introduction)

### 1.1 목적 (Purpose)

접수한 요구는 결함 보고다.

> **"editor 에서 내장 finder 와 내 finder 가 충돌해서 내장 파인더가 켜지고
> 이조차 제대로 동작하지 않음"**

조사로 원인을 확정했고, **증상은 보고된 것보다 심각하다** — 찾기 키를 누른 뒤
타이핑하면 그 글자가 **문서에 삽입된다** (§2.4). 검색하려고 누른 키가 파일을
편집한다.

방향은 확정됐다: Monaco 의 find 위젯을 걷어내고 **우리 패널로 교체한다.**
자리는 편집기 우상단 오버레이이며, 갖추는 것은 찾기와 토글 옵션 셋이다
(바꾸기는 비목표 — §6).

### 1.2 범위 (Scope)

**포함**

| 묶음 | 내용 |
|---|---|
| **A** 가로채기 | 키를 Monaco **보다 먼저** 잡고, Monaco 의 find 를 여는 길을 모두 닫는다 |
| **B** 패널 | 편집기 우상단 오버레이. 질의 칸·일치 수·이전/다음·옵션·닫기 |
| **C** 표시·이동 | 일치 하이라이트, 현재 일치 강조, 그 자리로 스크롤 |
| **D** 옵션 | 대소문자·정규식·단어 단위 토글 셋과 그 보존 |
| **E** 앞선 스펙 | FR-EKB-3 개정과 그 검증의 보강 |

**미포함:** §6 비목표.

### 1.3 정의 (Definitions)

| 용어 | 정의 |
|------|------|
| **find 위젯** | Monaco 가 자기 것으로 갖는 검색 상자. 이번에 **쓰지 않게 된다** |
| **찾기 패널** | 이번에 세우는 우리 오버레이 (`.fe-find`) |
| **일치** | 질의가 지금 문서에서 맞는 자리 하나 |
| **현재 일치** | 이전/다음이 가리키는 그 하나. 다른 일치와 다르게 그려진다 |
| **가로채기** | `capture` 단계에서 키를 잡아 Monaco 에 닿지 않게 하는 일 |

## 2. 현재 상태 (조사로 확정한 사실)

### 2.1 편집기 안의 키 판정은 bubble 단계에 있다

`web/js/ui/file-editor.js:383`:

```js
this.el.addEventListener('keydown', (e) => {
  if (window.app && window.app._edTrySearchKey(e)) return;
  e.stopPropagation();
});
```

세 번째 인자가 없으므로 **bubble** 이다. 키의 실제 대상(`target`)은 Monaco 내부의
입력 요소이고, Monaco 의 키 처리는 그 안쪽에 붙어 있다 — 즉 **Monaco 가 먼저 본다.**

### 2.2 그래서 위젯이 먼저 열린다

`Mod+F` 의 순서는 이렇다.

1. Monaco 가 자기 keybinding 으로 `actions.find` 를 실행한다 → 위젯이 열리고
   **find 입력칸이 포커스를 받는다**
2. 이벤트가 `this.el` 까지 올라온다 → `_edTrySearchKey` 가 매칭한다 →
   `_edFindInFile()` 이 돈다

`stopImmediatePropagation()` 은 2 에서 불리지만 1 은 **이미 끝났다.** 전파를 멈추는
일은 지나간 리스너를 되돌리지 못한다.

### 2.3 그리고 우리가 그 포커스를 훔친다

`web/js/core/app-edsearch.js:37`:

```js
_edFindInFile(){
  const v=this._edActiveEditor();
  const ed=v&&v._editor;
  if(!ed) return;
  ed.focus();                                  // ← 위젯의 포커스를 본문으로 되돌린다
  ed.trigger('dongminal','actions.find',null);  // ← 두 번째 실행
}
```

`ed.focus()` 는 **에디터 본문**에 포커스를 준다. 방금 위젯이 가져간 포커스가
그리로 되돌아온다.

### 2.4 결과: 타이핑이 문서에 들어간다 (재현으로 확정)

Editor 창에서 파일을 열고 본문을 클릭한 뒤 `Ctrl+F` 를 누르고 `needle` 을 타이핑한
관측이다.

| 관측 항목 | 값 |
|---|---|
| 위젯 존재 | `editor-widget find-widget visible` — **열려 있다** |
| `document.activeElement` | `native-edit-context` (에디터 본문) |
| 포커스가 위젯 안인가 | **아니다** (`inFindWidget: false`) |
| 우리 `.ed-find` 패널 | 0개 (이 키는 그것을 열지 않는다) |
| 타이핑 뒤 문서 | `…\ndelta\n` **`needle`** — 문서 끝에 삽입됐다 |
| 타이핑 뒤 find 입력칸 | 값을 받지 못했다 |

**"이조차 제대로 동작하지 않음" 의 정체가 이것이다.** 위젯은 뜨지만 아무 글자도
받지 못하고, 그 글자는 전부 파일로 간다.

### 2.4b 포커스를 되돌리는 자리가 하나 더 있다

`file-editor.js` 의 `focusin` 핸들러가 그것이다.

```js
this.el.addEventListener('focusin', () => {
  if (this._editor) this._editor.focus();
});
```

**패널을 `this.el` 안에 두면 이 핸들러가 그 포커스도 되돌린다** — 질의 칸에
`focus()` 를 준 그 순간 `focusin` 이 발화해 편집기가 다시 가져간다. §2.3 과 같은
종류의 결함이며 자리만 다르다.

구현 중에 실제로 이것에 걸렸다 (패널은 떴고 Monaco 위젯도 뜨지 않았으나 질의
칸이 `inactive` 였다). 그래서 FR-EFP-5 는 `_edFindInFile` 한 곳이 아니라
**포커스를 편집기로 되돌리는 모든 자리**를 가리킨다.

### 2.5 앞선 검증은 이것을 보지 못한다

`e2e/editor-search-keys.spec.ts` 의 다섯은 `Mod+P`·`Mod+Shift+F`(우리 패널 둘)와
터미널 창의 `Mod+F` 만 잰다. **파일 내 검색이 실제로 무엇을 하는지 재는 검증이
하나도 없다** — V-EKB-1 이 "Monaco 에 포커스가 있어도 두 조합이 뜬다" 인데 그
`두 조합` 이 패널 둘이다. 그래서 이 결함이 살아 있었다.

### 2.6 Monaco 의 find 를 여는 키는 하나가 아니다

`Mod+F` 만 막아도 위젯은 여전히 열린다 — `Mod+H`(바꾸기), `Mod+E`(선택으로 찾기),
`F3`·`Mod+G`(다음 일치) 가 각자 그 위젯을 세운다. **길을 하나만 닫으면 나머지로
들어온다.**

### 2.7 `.ed-find` 는 이 자리에 쓸 수 없다

기존 패널은 `position:fixed;inset:0` 의 **화면 전체 중앙 모달**이다
(`style-editor.css:163`). 파일 내 검색은 "지금 이 줄" 을 보며 다음으로 넘겨야
하므로 코드를 가리는 껍데기를 쓸 수 없다 — 사용자가 고른 자리도 우상단이다.

### 2.8 편집기 컨테이너는 이미 positioned 다

`.file-editor{position:absolute;inset:0}` (`style.css:851`). 오버레이를 그 안에
`position:absolute` 로 넣으면 그 칸의 편집기에만 얹힌다 — 새 좌표계를 만들 필요가 없다.

### 2.9 편집기는 칸마다 서고 모델은 공유된다

`FileEditor` 인스턴스는 분할 칸마다 하나다 (FR-WSL-20). 같은 파일을 두 칸에서 보면
**모델은 하나**이고 `_doc.views` 가 그 뷰들을 안다 (`file-editor.js:194`).

따라서 질의·현재 일치는 **뷰마다** 달라야 하고(각 칸이 다른 자리를 보고 있다),
일치를 찾는 대상 텍스트는 어차피 같다.

**칸이 아니라 인스턴스가 단위다.** 인스턴스는 탭마다도 선다 — 같은 칸에서 파일
둘을 열면 `FileEditor` 가 둘이다. 그리고 Editor 창에서 **분할 칸을 만드는 길은
드래그드롭뿐이다** (FR-EDT-50·51 — `split()` 은 그 창에서 무시된다,
`app-layout.js:498`). 그러므로 이 요구가 실제로 걸리는 흔한 자리는 분할이 아니라
**탭 전환**이고, 검증도 그 경로로 선다 (V-EFP-16).

### 2.10 검색 엔진을 새로 쓸 필요가 없다

Monaco 의 `model.findMatches(query, …, isRegex, matchCase, wordSeparators, …)` 가
정규식·대소문자·단어 단위를 이미 전부 받는다. **위젯을 쓰지 않는 것과 모델의
검색을 쓰지 않는 것은 다른 일이다** — 우리가 만드는 것은 껍데기이지 검색기가 아니다.

### 2.11 Monaco 는 이 앱에 편집기 말고 **diff 뷰**로도 서 있다

Git 의 diff 는 Monaco DiffEditor 다 (`GitDiffView`). 그 뷰에는 우리 패널이 없다.

그리고 그 뷰에서 `Mod+H`·`Mod+E`·`F3`·`Mod+G` 는 **원래 Monaco 의 find 위젯을
열었다.** 그 조합들은 앱 단축키에도 `BUILTIN_HOTKEYS` 에도 없으므로 전역 핸들러가
`_blockBrowserDefault` 로 브라우저 기본 동작만 막고(전파는 멈추지 않는다) Monaco
까지 도달했기 때문이다.

`Mod+F` 는 사정이 다르다 — `BUILTIN_HOTKEYS` 가 그것을 `toggleSearch`(터미널 검색)로
잡고 `stopImmediatePropagation` 하므로 **diff 뷰에서도 원래 위젯이 뜨지 않았다.**

따라서 무효화를 `monaco.editor.addKeybindingRules` (전역)로 걸면 **diff 뷰에서
되던 것을 아무것도 되지 않게 만든다.** 그것은 이 요구가 청한 일이 아니다.

### 2.12 판(`?v=`)은 서버가 계산한다

`index.html` 은 `?v=__ASSETV__` 자리표시자만 적고 서버가 채운다
(ASSET_VERSION_SINGLE_SOURCE_SRS FR-AVS-1·5). 손으로 올릴 값이 없다.

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 묶음 A — 가로채기

- **FR-EFP-1** 편집기 안의 검색 키 판정은 **`capture` 단계**에서 일어난다 —
  Monaco 가 그 키를 보기 전이다 (§2.1·2.2).
- **FR-EFP-2** 판정이 매칭되면 그 키는 **Monaco 에 닿지 않는다.** 브라우저 기본
  동작도 막는다.
- **FR-EFP-3** 매칭되지 않으면 가로채기는 **아무것도 하지 않는다.** 전파를 멈추지
  않고 기본 동작도 막지 않는다 — 그렇게 하면 편집기가 글자를 받지 못한다.
- **FR-EFP-4** Monaco 의 find 위젯을 여는 **모든 키바인딩이 무효화된다** (§2.6).
  하나만 막으면 나머지로 위젯이 열려 이 결함이 그대로 남는다.
- **FR-EFP-4b** 그 무효화는 **이 편집기 인스턴스에만** 걸린다. Git 의 diff 뷰도
  Monaco 이고 그 뷰에는 우리 패널이 없으므로(§2.11), 전역으로 걸면 거기서 되던
  것을 아무것도 되지 않게 만든다 — 이 요구가 청한 일이 아니다.
- **FR-EFP-5** 검색 경로는 어디서도 `ed.focus()` 로 **포커스를 편집기 본문으로
  옮기지 않는다** (§2.3). 패널을 여는 일은 패널에 포커스를 주는 일이다.

### 3.2 묶음 B — 패널

- **FR-EFP-6** 패널은 편집기 **우상단 오버레이**다. 코드 위에 얹히며 화면을 가리는
  배경막이 없다 (§2.7).
- **FR-EFP-7** 구성은 한 줄이다: 질의 칸 · 일치 수 · 이전 · 다음 · 옵션 셋 · 닫기.
- **FR-EFP-8** 패널은 **편집기 인스턴스마다 하나**이며 그 인스턴스의 `el` 안에 산다
  (§2.8·2.9). 두 탭·두 칸이 각자의 질의를 가지며, 탭을 떠났다 돌아오면 그 질의가
  그대로 있다.
- **FR-EFP-9** 열 때 편집기의 **선택 영역이 한 줄 안에 있고 비어 있지 않으면** 그것을
  질의로 싣고 전체 선택한다 — 바로 다른 말로 갈아 칠 수 있어야 한다.
- **FR-EFP-10** `Escape` 로 닫는다. 닫으면 포커스가 **편집기로 돌아간다** — 그것이
  사용자가 방금까지 보고 있던 자리다.
- **FR-EFP-11** `Enter` 는 다음, `Shift+Enter` 는 이전이다. 패널 안에서 누른 키는
  **밖으로 나가지 않는다** — 앱 단축키가 끼어들면 타이핑 중에 창이 바뀐다.
- **FR-EFP-12** 패널이 이미 열려 있을 때 같은 키를 다시 누르면 **닫지 않고** 질의
  칸을 다시 고른다 (FR-EFP-9 의 싣기를 포함한다).
- **FR-EFP-13** 편집기가 없는 탭(이진 파일·이미지·로딩 중)에서는 열리지 않으며,
  키를 삼키지도 않는다.

### 3.3 묶음 C — 표시·이동

- **FR-EFP-14** 지금 문서의 **모든 일치를 하이라이트**하고, 현재 일치는 그와 **다르게**
  그린다. 둘이 같으면 이전/다음이 무엇을 옮겼는지 보이지 않는다.
- **FR-EFP-15** 현재 일치가 화면 밖이면 **그 자리로 스크롤**한다.
- **FR-EFP-16** 일치 수는 `현재/전체` 로 보인다. 하나도 없으면 그 사실이 보이고,
  질의가 비면 수를 말하지 않는다 (아직 묻지 않은 것이다).
- **FR-EFP-17** 문서가 바뀌면 일치를 **다시 센다.** 편집하는 동안 낡은 하이라이트가
  남아 있으면 그것이 거짓말이 된다.
- **FR-EFP-18** 패널을 닫으면 하이라이트를 **걷는다.**
- **FR-EFP-19** 이전/다음은 끝에서 **돌아 감는다** — 마지막 다음은 처음이다.

### 3.4 묶음 D — 옵션

- **FR-EFP-20** 토글 셋이다: 대소문자 구분 · 정규식 · 단어 단위. 각 토글은 켜진
  상태가 보인다.
- **FR-EFP-21** 검색은 Monaco 모델의 `findMatches` 로 한다 (§2.10) — 세 옵션이 그
  호출의 인자로 그대로 간다. 우리가 검색기를 쓰지 않는다.
- **FR-EFP-22** 옵션을 바꾸면 **즉시 다시 검색한다.**
- **FR-EFP-23** 옵션은 **기기별로 기억된다** (`localStorage`, D-4). 다시 열 때 앞서
  쓴 조합이 그대로 선다.
- **FR-EFP-24** 정규식이 켜져 있고 질의가 **잘못된 정규식**이면 그 사실을 알리고
  검색하지 않는다 — 조용히 0건으로 보이면 사용자가 없는 줄로 읽는다.

### 3.5 묶음 E — 앞선 스펙

- **FR-EFP-25** `EDITOR_GIT_UX_SRS` 의 **FR-EKB-3 을 개정한다.** 그 조항은 "파일 내
  검색은 패널을 만들지 않는다 — Monaco 의 find 위젯이 이미 그 자리다" 인데, 그
  전제가 §2.4 로 무너졌다. 개정문은 그 위젯을 **쓰지 않는다는 사실과 그 이유**를
  적고 이 문서를 가리킨다.
- **FR-EFP-26** 파일 내 검색의 **실제 동작을 재는 검증**을 세운다 (§2.5). 최소한
  이 셋이다: 위젯이 뜨지 않는다 · 타이핑이 문서에 들어가지 않는다 · 타이핑이
  질의 칸에 들어간다.
- **FR-EFP-27** FR-EKB-1·4·5 는 그대로다 — 키는 Monaco 안팎 두 자리에 배선되고,
  Editor 창이 아니면 삼키지 않으며, 설정에서 바꿀 수 있다.

## 5. 확정 결정 (Decisions)

- **D-1 위젯을 걷어내고 우리 패널을 세운다.** 사용자가 고른 답이다. 대안은 위젯을
  고쳐 쓰는 것(`ed.focus()` 를 지우면 §2.4 는 낫는다)이었으나, 그러면 껍데기의
  생김새·자리·용어를 Monaco 가 정하고 우리 검색 셋 셋 중 하나만 남의 것이 된다.
- **D-2 검색기는 Monaco 모델의 것을 쓴다.** §2.10 — 만드는 것은 껍데기다. 정규식·
  대소문자·단어 단위를 우리가 다시 구현하면 그 세 가지가 두 벌이 된다.
- **D-3 패널은 편집기 인스턴스가 소유한다.** 앱이 하나를 갖고 돌려 쓰면 두 칸이
  같은 질의를 공유하게 되는데, 칸마다 다른 자리를 보고 있으므로 "현재 일치" 가
  어느 칸의 것인지 정해지지 않는다 (§2.9).
- **D-4 옵션은 기기별(`localStorage`)이다.** 설정 블롭에 두는 값들(`blockBrowserKeys`
  등)은 "이 서버가 무엇인가" 를 말한다. 검색 옵션은 그런 값이 아니라 지금 이 손의
  버릇이며, 서버에 두면 다른 기계에서 켜 둔 정규식 모드가 따라와 놀라게 된다.
- **D-5 가로채기는 `capture` 다.** `addKeybindingRules` 로 Monaco 의 조합을 지우는
  길도 있으나, 그것은 조합을 코드에 박는 일이라 FR-EKB-5(설정에서 바꾸는 키)와
  어긋난다. capture 로 먼저 보면 **어떤 조합을 배정해도** 우리가 먼저 잡는다.
  FR-EFP-4 의 무효화는 그 위에 얹는 이중 안전장치다 — 사용자가 `Mod+H` 를 아무
  동작에도 배정하지 않았을 때 그 키로 위젯이 열리는 것을 막는다.
- **D-5b 그 안전장치는 인스턴스별(`editor.addCommand`)이다.** 구현 중에 전역
  (`monaco.editor.addKeybindingRules`)으로 걸었다가 §2.11 을 발견해 되돌렸다:
  전역 규칙은 Git diff 뷰의 위젯까지 죽이는데, 거기에는 우리 패널이 없어 그
  결과가 순수한 기능 상실이다. **이전 동작** — diff 뷰에서 `Mod+H`·`Mod+E`·`F3`·
  `Mod+G` 로 Monaco 위젯이 열렸다. **새 동작** — 그대로다. **이유** — 이 작업이
  고치려는 것은 Editor 창의 파일 내 찾기이며, diff 뷰의 검색은 앞선 스펙이
  명시적으로 비목표로 둔 것이다 (EDITOR_GIT_UX_SRS §6 #3). 되던 것을 조용히
  없애지 않는다.
- **D-6 바꾸기는 넣지 않는다.** 사용자가 고른 범위다 (§6 #1).

## 6. 비목표 (Non-goals)

1. 바꾸기·전부 바꾸기 — 사용자가 고른 범위 밖이다 (D-6).
2. 선택 영역 안에서만 찾기.
3. 여러 파일에서 찾기 — 이미 있다 (`Mod+Shift+F`, FR-EGS-*).
4. 찾기 이력·최근 질의 목록.
5. Monaco 의 위젯을 우리 테마로 다시 칠하기 — 쓰지 않기로 했다 (D-1).
6. 코드 레퍼런스 이동(정의·참조) — 별도 작업이며 별도 스펙이다.
